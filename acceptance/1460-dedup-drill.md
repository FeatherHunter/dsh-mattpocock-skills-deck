# BUG 建单查重：四场景人工演练（验收票 #1462 阶段一）

这份文档是给人工验收用的演练步骤，不是自动门禁，也不是要逐条执行的测试命令。要证明的事情只有一件：升到 v15 的「+ 新增BUG单」提示词，在真实会话里真的会先查重、把候选交给报告人确认、并把查重过程写进票里。

演练全程在仓库外的临时本地 Markdown 工作区里做，主仓不会因为演练多出任何票。每个场景做完，把「输入、会话实际动作、正文查重记录」三栏贴到票 #1462 的进度评论里，作为可复核的记录。

提示词版本说明：本次交付的版本是 v15（#1461 从 v14 升到 v15；规格 #1460 票面写的 v13 定稿较早，定稿之后仓库里已经先落过 v13、v14 两次提交，版本只升不降，所以这次锁在 v15，详见 #1461 的提交信息）。

## 一、造种子，进入演练工作区

1. 在仓库根目录跑一次种子脚本：

   ```
   node scripts/seed-1460-dedup-drill.ts
   ```

   脚本会在系统临时目录下新建一个本次专用的目录（不会动主仓和任何已有目录），并打印这个目录的绝对路径、两张种子单的路径与标题。记住这个路径，后面每个场景都用它。

2. 在 DSH 里新建会话，工作区选脚本打印的那个临时目录（初始化流程第 1 步「选择工作区并新建会话」）。插件读到目录里的 `docs/agents/workspace.yaml` 后，会把这个工作区绑到本地 Markdown 后端；如果右侧面板还显示未绑定后端，手动选一次「本地 Markdown」。

3. 打开右侧问题面板，确认能看到两张相似 BUG 单：

   - 01「导出 CSV 时列顺序错乱」，Status 是 needs-triage，也就是还开着的旧单；
   - 02「导出 CSV 时列顺序错乱（同一问题的更早一张单，已修）」，Status 是 resolved，也就是已关闭的旧单。

4. 每个场景都要从真实入口新开一次会话：点右侧面板的「+ 新增BUG单」按钮，或者状态栏 BUG 胶囊菜单里的「新增」。这两个入口注入的是同一份 v15 提示词。要观察的是会话接下来怎么做，不是提示词文件里写了什么。

## 二、四个场景

四个场景的差别只在两处：工作区里有没有相似旧单、报告人对候选怎么回答。除了场景 3 要临时清掉相似单之外，其余场景都用第 1 步造出来的同一份种子。

### 场景 1：有相似旧单且它还开着，报告人确认是同一问题

- 前置：用种子原样的工作区（01 开着，02 已关闭）。
- 报告人怎么说：描述 01 那个问题，例如「从列表页导出 CSV，列的顺序和页面显示对不上，第一列跑到最后去了」。会话列出候选（01、02）并问「这些是不是同一个问题」时，回答「是 01 这个问题」。
- 该看到什么：会话不建新单；在 01 下加一条评论，补充这次的现象和复现步骤；01 保持开着、不关闭；查重记录（扫描了哪些状态与标签、命中哪张、报告人怎么回答、结论是什么）写进这条评论或会话回复里。
- 通过标准：面板上没有多出新票；01 的评论区多出这次的现象；01 的状态没有变化。

### 场景 2：有相似旧单但已关闭，报告人确认是同一问题

- 前置：用种子原样的工作区（02 是已关闭的相似旧单）。
- 报告人怎么说：描述和 02 同一个问题。会话列出候选时，回答「是 02，之前修过又冒出来了」。
- 该看到什么：新建一张 BUG 单；新单正文有「## 查重记录」一节，四行齐全（扫描、命中、报告人确认、结论）；正文写明「回归：原单 #02」并关联 02；02 的状态不变。
- 通过标准：新单确实建出来了；回归说明和四行记录都在；新单能看出关联的是 02，而不是只写一句「回归」却不给票号。

### 场景 3：工作区里没有相似的旧单

- 前置：需要一份没有相似单的工作区。重新跑一次种子脚本，在新打印的目录里把 `.scratch/csv-export-drill/issues/` 下的两张种子单暂时移出该目录（移到工作区外的备份位置即可；演练完再把它们放回去，或者直接留作下一轮种子）。这样面板里就没有相似旧单了。不要在主仓里做这一步。
- 报告人怎么说：报一个与 CSV 无关的问题，例如「设置页切换成英文后，提示文案还是中文」。
- 该看到什么：会话仍然先做两次全扫（open 一轮、closed 一轮），都拿不到相似结果；然后照常建新单；新单正文的「## 查重记录」里，命中一行写「无」，其余三行照实写，不编造候选。
- 通过标准：新单已建；四行记录齐全且命中为「无」；正文没有出现任何没查过的候选编号或标题。

### 场景 4：有相似旧单，但报告人明确说不是同一问题

- 前置：用种子原样的工作区（01 是看起来相似的旧单）。
- 报告人怎么说：报一个「长得像、其实不同」的问题，例如「我报的是导入 CSV 时列顺序错乱，不是导出；导入这边列的顺序反了」。会话列出候选时，回答「不是同一个问题，这次是导入那边」。
- 该看到什么：会话照常建新单，不因为候选看着像就改判成同一问题；新单正文的「## 查重记录」写明看过的候选（编号、标题）和报告人的回答；结论写「新建」。
- 通过标准：新单已建；记录里既有候选、也有报告人「不是同一问题」的回答；没有把 01 误当成同一问题去评论或关闭。

## 三、把结论记回票里

1. 每个场景贴三栏：输入（报告人原话或摘要）、会话实际动作（建单 / 不建单 / 评论了哪张单）、正文查重记录（四行原文，或说明它写在哪条评论里）。
2. 贴完四个场景，再贴一句主仓状态：演练没有让主仓多出任何票。
3. 哪个场景没按上面「该看到什么」走，不要改提示词文件、也不要在主仓里补动作；把会话的实际行为原样贴进 #1462，等 Lead 判断是提示词问题还是演练环境问题。
4. 演练结束后可以整个删掉临时工作区目录；删之前把要留的证据（评论链接、正文摘录）先贴进票里。

阶段二（版本发布后抽检 10 张新建 BUG 单）不在这份演练里，按 #1462 的验收条目单独做。
