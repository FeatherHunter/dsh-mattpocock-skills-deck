元数据与进度：注入逻辑 · GitHub 房 vs Markdown 房

同一套 deck 工具，落到两间不同的后端房间时，元数据（幂等锚、父键）与进度分别被写到哪儿、怎么找回来。全部结论都标了代码位置。

一、一张票面上住着三种东西

锚和父键对人是隐形的（HTML 注释），进度是给人看的。面板的渲染器不处理注释，所以前两种在面板里会当普通文字显示出来。

写在票面上的样子给谁看作用定义在哪
<!-- DSH-IDEMPOTENCY-KEY: … --> 机器 幂等锚。同一个锚再提交一次，复用同一张票，不再建第二张；已关闭的票不算命中。 shared/refresh/idempotency.js:1
<!-- parentKey: 01 --> 机器 父票编号。只在 Markdown 房需要——GitHub 房用原生子议题层级，票面上不写这行。 markdown/parse.js:45（#971 读回来）
## 进度：N% 人 + 机器 进度区。面板读它画进度条；契约要求 N 是 0–100 整数，另起一段写「下一步：」。 docs/prompts-review.md:193（#75 定版）

二、带锚建票：两间房各自怎么注入、怎么找回来

上层是同一套：键先当场体检，再回查，命中就复用，没命中才建，拿不准就如实失败、绝不建票。分叉全在「回查看什么」和「锚写到哪」。

GitHub 房 锚写进 issue 正文首行

  1. 键体检：不合规（空 / 超长 / 带换行或注释收尾符）当场失败，比回查还早。 github/issues-write.js:36
  2. 回查①快路：gh search issues --match body 搜锚。便宜，但 GitHub 的正文索引是异步建的、有滞后，刚建好的几十秒常常搜不到。 github/idempotency.js:113
  3. 回查②慢路：快路没命中时，列最近更新的 100 张开票，只留创建时间在 30 分钟窗口内的候选，逐张读回正文比对（最多 40 张）。这条路不依赖索引，专治「刚建完马上重试」。 github/idempotency.js:129–165
  4. 两条路都真跑通且都没找到，才算「确实还没建过」；任一条出岔子一律如实失败。 github/idempotency.js:168–177
  5. 建票：gh api POST，正文前面拼上锚那一行。 github/idempotency.js:45（withAnchor）
// 锚是正文第一行：渲染后看不见，读回来还在
export function withAnchor(body, key) {
  if (!key) return body
  return anchorLineFor(String(key)) + (body || '')
}

Markdown 房 锚 + 父键写进票文件头两行

  1. 键体检：同一套检查，理由还多一条——键会原样写进票面，落坏就是把文件的正文写坏。 markdown/issues-create.js:114
  2. 进串行写者队列：取号、探测、落盘三段必须在同一条按工作区排队的队列里跑完，否则多路会读到同一个 max、算出同一个编号、互相覆盖（本机实测 8 路并发全部回 key="01"）。 markdown/issues-create.js:118–128（#712）
  3. 回查：在队列里扫目标 effort 的 issues 目录，逐个文件读锚比对，命中就直接复用、不取号不落盘。 markdown/issues-create.js:136–147 / :92–106
  4. 建票：编号取 max+1 并探测到没人占为止，然后整份写文件；文件头先放父键注释、再放锚注释。 markdown/issues-create.js:80–82
// 两次前置插入：先父键，再把锚插到最前
if(input.parentKey) content = '<!-- parentKey: '+input.parentKey+' -->\n' + content
// 锚在最前（含它自己的换行）
if(input.idempotencyKey) content = anchorLineFor(…)+content
同一件事，两间房的「证据」不同。 GitHub 房的证据是远端票面正文里的锚那一行——搜索接口说「找到了」不算数、内存里记着谁建过也不算数；Markdown 房的证据是票文件里那一行，因为进程重启、插件重载后内存里什么都没有，而文件还在盘上。

三、父键：一间房靠层级，一间房靠注释

这是两间房差别最大的一处，也是工具每次都说「分不出原生层级还是平级链接」的原因。

GitHub 房 走原生子议题层级，票面上不写父键
子议题是平台能力，父边直接建在层级上；所以正文里看不到 parentKey 那一行。
▼ 是否同目录
Markdown 房 · 建图时 写文件头注释
建整图时给每张子票文件头写 <!-- parentKey: 15 -->，这是降级承载，不是原生层级。读回、列举、快照都以这行注释为准（#971 修掉了「注释写了却从不读」）。
markdown/issues-create.js:80 · markdown/parse.js:45
Markdown 房 · 事后补边 直接做不到
补边工具传父键时两间房都诚实失败（本地后端恒为单根树，原生不支持），而且补边这条路径不顺手写注释——与建图时带注释是两条路径，行为实测已分开留证。
markdown/issues-patch.js:183（setParentIssue）
▼ 还有一层保险
改正文时不许把父键弄丢
整份替换正文的分支会用递进来的正文盖掉整个文件，而父注释不在字段行里、补不回来。所以写之前先以盘上旧文件的父为准补回，否则下一次读回父就从 01 掉回 00。
markdown/issues-patch.js:106–112

四、进度：契约、写入路径、以及断在哪

进度是唯一一件「写的人」和「读的人」口径不一致的东西。定义很完整，落地断了三处。

当初的定义（#75 grill 定版）

进度表达（每次动作结束前必须更新 —— 这是动作的一部分，不是可选项）
1. 格式：正文维护固定进度区 `## 进度：N%`（N 为 0-100 整数；禁止「大概 / 基本」等模糊词）
   更新前先读当前值，按最新状态写真值（可上调也可下调）
2. 阶梯：0% 未动工 · 1-94% 进行中 · 95% 已完成待确认（下一步须写明待确认什么；未确认不得 close）
   确认后立即写 100% 并 close
3. 兜底：100% = 确认完成（close 后进度区保留为历史）；首次接触无进度区的票，按现状补写

docs/prompts-review.md:193–202（写法正例见 :224–227；工作流文档称其为 prompt.progress 契约）

写入路径：一个参数，两间房的落点不同

共用的一步 改票工具的 progress 参数

参数说明就一句：只改「## 进度」那一段的内容。实现是把整段换掉，前面的正文与后面的区块原样保留，顺手清理历史留下的重复进度区。

host/tools/deckIssuePatch.js:26 · :40–58

GitHub 房 改 issue 正文

拼好新正文后走 gh issue edit --body，再 gh issue view 读回核对。

github/issues-write.js:206–212

Markdown 房 整份覆盖票文件

读文件、判断递进来的是整份正文还是片段、拼好、整份写回。整份替换 / 插入 / 字段行三条分支的边界判断，就是「改正文把新正文追加到旧正文之后」「首部出现重复锚与重复标题」这类缺陷的来源。

断点：写的人不写数字，读的人只要数字

写的人（AI）
现行注入的提示词模板里，「进度」两个字一次都没有——只剩一句「结束前把这张票的真实状态写进正文」。
src/client/kernel/prompts.js（搜「进度」零命中）
▼ 于是写出来的是整段文字，没有百分比
建票骨架
只塞 ## 进度 加一行占位注释「做到哪一步了，在这里一行一行记」，没有 N%、也没有「下一步：」。
shared/deck-tools/plan.js:58–61
▼
读的人（面板）
解析器三级锚定，三级都要求百分号；解析不出就是空值，进度条画「—」、状态算作未动工。
shared/tracker/deck-derive.js:33–43 · client/views/shared/ticket.js:24–26

占位注释为什么时有时无

走 progress 参数 占位行消失

整段替换会连占位行一起换掉。本会话关掉的 980 / 984 / 981 / 985 / 987 都走这条路，所以那几张票里没有占位行。

走改正文或人工编辑 占位行留下

工具不认识进度段的边界，占位行原地不动，与后写的记录并存。dsh-log 的 02 号票就是现场：票上评论自己记着「改正文时把新正文追加到了旧正文之后…已由人工整理」。

硬证据：地图 979 最后一次快照里，八张子票每行的进度值全是 null——可其中五张的进度段明明有整段文字。文字进去了，数字没出来。
