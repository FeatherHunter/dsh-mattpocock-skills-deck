# 票 #895「deck 工具批量写超时但副作用已落盘」在今天这棵树里还能不能复现

调查日期：2026-10-15。
调查方式：只读。读了票面原文、今天的 TypeScript 树相关文件、跑了两道与本票相关的回归门禁与一次类型检查。
本文件回答一个问题：票面描述的那条缺陷路径——工具在限时内没有回执，但服务端或盘上已经写进去了，调用方以为没成——在今天的树里从逻辑上还找不找得到。

## 一、票面写的现象（原话摘要）

- 现场是 `deck_map_plan_create`（工具名今天没变）：一次调用建整张地图的骨架，实测跑到 120 秒超时，但事后查盘上，地图票和子票都已经建出来了；调用方拿到的是「超时失败」，因为不知道已经落盘，很容易再调一次，于是重复建票。
- 同一批还有 `deck_issue_list` 偶发 120 秒超时；`deck_map_link` 补边实测 60 秒超时，这次边确实没补上。
- 票面期望：把批量写这条路做扎实——部分做完要能续、回执要如实说清哪些做了哪些没做，不要出现「以为没做其实做了」。
- 评论里的修正：60 秒和 120 秒不是工具自己定的，是调用这一层（注册/宿主那一侧）给的墙钟上限，工具是被外面掐掉的，所以工具来不及自己收尾、也来不及说清做到哪一步。

## 三、今天一共有几层时钟，各是多少

今天和本票有关的时间上限一共四个，分布在两层，互相之间没有强制关系：

1. **外层：调用这一层给的墙钟 300 秒。**
   `src/deck/registration/register-options.ts:38` 写着 `export const AGENT_TOOL_TIMEOUT_MS = 300000`，这个值分别装在工具注册的 `timeoutMs`（同文件 `:366`、`:380`）和行模块里的 `timeoutMs`（`src/deck/registration/agent-row.ts:182`、`:381`）。
   票面的 120 秒就属于这一层——今天它变成了 300 秒。这一步是票面评论里说的「外面掐的」：时辰一到，注册层不再等工具，直接回一个失败。
2. **内层：工具自己给自己的预算 300 秒，留 15 秒余量。**
   `src/deck/shell/call-budget.ts:24` `DEFAULT_TOOL_TIMEOUT_MS = 300000`，`:27` `DEFAULT_TOOL_MARGIN_MS = 15000`，`:223-224` 用 `remainingMs() <= marginMs` 判「该收手了」。工具每次要动手之前先问一次，超了就当场停、转成「部分成功 + 续跑点」。
   文件头 `:20` 的注释自己写着：**「与 agent 注册那份 AGENT_TOOL_TIMEOUT_MS 同值，改一边必须同步另一边」**——也就是说，这是靠人记住，没有任何代码在检查两者是否还相等。
3. **内层再往下：单次远端调用 30 秒。**
   `src/deck/shell/call-budget.ts:29` `DEFAULT_PER_OP_TIMEOUT_MS = 30000`，`:230` 把它与「剩余时间减去余量」取小，作为这一次调用的上限；到点就中止这次调用（`:249-253`）。
4. 宿主侧的代执行：`src/deck/registration/host-delegate.ts:15` 明确写着这一层「自己不再计时」——超时全部由上面第 1 条和第 2 条承担。

需要点出来的一处顺序问题：工具的 300 秒是从 `withCallScope` 建立那一刻开始计时（`call-budget.ts:213` `startedAt: nowFn()`），而它是在**解析会话、过闸选后端、探测沙箱策略都做完之后**才建立的——看 `src/deck/tools/map-plan-create.ts:247` 这一句，`shell.call({... sandbox: (await ...), signal: ...}, async (c) => { ... withCallScope(...) })`：沙箱探测先跑完，`withCallScope` 才被调用。所以外层那 300 秒里有一段是工具的内层根本没在数的时间。两段都是 300 秒时，这段时间差就是外层先到、内层还没收手的窗口。

## 四、超时之后，调用方是怎么收场的

### 1. 「已写入但没回执」这条路今天有没有专门的善后

有，但分成三档，档与档之间不连续：

- **单次远端调用超时**（30 秒那一层）：`call-budget.ts:187` 回一句 `kind: 'timeout'`，原文是「这一次远端调用在限时内没回来，**是否生效说不清**：先按返回里说的办法核对现状再续，不要直接重放写操作。」这句话是诚实的——它没有假装成功。但它到此为止：工具不会自己去读一次现状来把「说不清」变成「说清」。
- **整笔调用被外层掐掉**：工具根本来不及回话，也就不会有上面那句话。调用方拿到的失败里没有「可能有部分写进去了」这条信息。
- **整笔调用用光预算**（工具自己发现快超时了）：这一档是今天做得最实的，见下一小节。

### 2. 重试会不会重复建票：靠幂等锚 + 建前先查

- 幂等锚：`deck_map_plan_create` 建票时把这一批写的幂等锚带上（`planId` 加票的短标识，见 `src/deck/tools/map-plan-create.ts` 的锚生成一段），后端按锚复用同一张票。
- 建前先查：同一处有「预置带锚旧票」的预检——先读一遍带锚的旧票，命中就跳过创建。
- 门禁实测作证：`tests/verify-895-bulk-deadline.js` 的两条断言「命中预检跳过创建（新增创建 2 次：地图 1 + 新子票 1）」「续跑零重复（共 5 票、锚无重复：实 5 票、重复锚 0）」都通过。
- 所以**在工具自己收到回话的前提下**，「以为没成又重调一次」不会重复建票。但这条保护建立在「工具能走完自己的路」上；外层直接掐掉的那条路上，工具没有机会走到预检那一步，AI 若照着上一次的调用原样重放，靠的是后端那边的锚去重，不是工具这边的预检。

### 3. 写后读回

`src/deck/shell/edge-landing.ts:137` 与 `:166` 各有一段「写一条边并读回核对」，`src/deck/registration/register-options.ts:157` 的注释也说明 `readBack` 是写后回读核对。但这些都只发生在**写操作正常返回之后**，用的是同一次调用里的返回值；超时那条路上一次读回都没有发生。

### 4. 有没有如实告诉人「可能已经落盘」

只有工具自己收手那一档有（`timeout` 那句「是否生效说不清」）。外层掐掉那一档没有，因为说话的机会已经没了。

## 五、整图建骨架那条路今天的进度与断点

这是今天相对票面日期变化最大的一段，做得很实：

- 工具每建出一张票就记一次进度，进度落在**落盘游标**里（`planStore`，有文件就落盘、没有就退内存并如实把 `durable` 报成 false）。
- 预算用光时返回的状态是 `partial` 而不是失败：门禁 `tests/verify-895-bulk-deadline.js` 断言「预算打满 → 部分成功（实得 partial）」「地图票已建出」「剩下的键如实回来（`["k1","k2","k3","k4"]`）」「续跑点带回同计划标识」；续跑之后「续跑后无剩余（实得 []）」「续跑零重复」也都通过。
- 失败项会单独说明是超时还是别的，并给出核对指引，断言原文是「失败项说清超时与核对指引」。
- 同一计划并发跑第二遍会被明确拒掉并说清原因（断言「并发第二跑被拒并说清（实得 unsupported）」「第一跑不受影响（实得 ok）」），避免两次跑互相踩。

一句话：**只要工具自己还有时间收手，今天这条路是能续、能如实回报部分成功的。** 断点只覆盖「工具还有机会说话」的情形。

## 六、超时和真失败，今天分不分得开

**在代码里分得开，在回执和日志里分不太开。**

- `call-budget.ts:187` 给的是 `kind: 'timeout'`，`:190` 给的是 `kind: 'aborted'`，与后端真报错不是一回事——这是内部数据结构里的区分，存在。
- 但到了工具对外的回执上，限时用完与后端真抛错被并成同一个人类可读的原因：`tests/verify-deck-no-hang.js:157-168` 这一段（标题「挂住（但守约响应信号）的后端 get → 钳制内诚实回超时，不改判成『做不到』」）断言的是 `r.reason === 'backend-threw'`——也就是说，超时在机器可读的那一格上记成了「后端抛错」，和 `:188-197` 那条「后端抛错仍走 backend-threw」用的是同一格。
- 日志那边更粗：`src/deck/shell/call-shell.ts:420` 是整笔调用收尾时记日志的那一句，失败时它的指纹写成 `hash8(str(vRec && vRec.reason))`——也就是说日志里的失败指纹算的是「拒绝原因」这个固定字面量。于是**限时用完与后端真抛错在日志里落成同一个指纹，看日志的人分不出这次是限时到了还是后端报错了**；只有同一格内部因为不同工具拼的原文不同而略有差别，但那不是「超时/非超时」的区分。
  （对照：仓里别处已经这么做了——`src/host/detectChain.ts:498` 与 `src/deck/registration/register-options.ts:416` 都额外记了一个 `errorKind`，把「接线没给全」与「跑起来真失败」分开；套在 deck 工具这条路上的收尾日志没有这一格。）

结论：判「这次到底卡在哪」只能靠人类可读的那一句原文，机器可读的那一格和日志指纹都没有独立的超时标记。

## 七、判定

**（c）部分还在，换了形态。**

票面症状（外层限时到点、副作用已落盘、调用方以为没成）今天仍然有一条能从逻辑上走到的路径，同时票面提到的三种实测里已经有两条被今天的结构挡住了。分开说：

### 还在的部分

1. **两层时钟仍然是谁也不管谁的两个人。**
   `register-options.ts:38` 的 300 秒与 `call-budget.ts:24` 的 300 秒是两个各自独立的常量，靠 `call-budget.ts:20` 的一句注释要求人「改一边必须同步另一边」。仓里没有任何断言或校验在检查两者相等。
   → 只要有人把注册层那一个数改回 120 秒（票面当天的实际值），或者只改一边，票面症状立刻回来：外层 120 秒到点掐掉调用，工具内层还以为自己有 300 秒、正准备继续往下写，于是「盘上写了、调用方看到失败」。这是本票最容易被重新引入的一条。
2. **内层的计时起点晚于外层。**
   工具的预算从 `withCallScope` 建立时开始（`call-budget.ts:213`），而 `withCallScope` 在会话解析、过闸选后端、沙箱探测之后才被调用（`src/deck/tools/map-plan-create.ts:247`）。这一段「外层已在数、内层还没开始数」的时间，没有任何机制折算，两段同为 300 秒时它就是一个真实存在的窗口。
3. **同进程快路上，工具的活没有上限，也不认调用方的取消信号。**
   `src/deck/registration/agent-row.ts:70` `DELEGATED_CELL_WAIT_MS = 25000` 只管「等表格出现」这 25 秒（`:67-68` 的注释还写明这两处数值与位置全冻、改数字要另立票）；等到格之后的那次 `run()` 是**不设时限地等下去**。同时这条快路传给工具的执行上下文只有 `{ agent: { session: { cwd, id } } }`（`:159` 是探针里同样形状的一次调用，正式路径同形），里面没有调用方的取消信号。
   → 也就是说，同进程这条路上，一旦工具开始动手，它会一直写到做完为止；这期间调用方（注册层）已经按自己的 300 秒回失败、走人了。这正是票面症状的另一种形态：**调用方以为没成，盘上其实做完了**，而且这一次连工具自己的诚实回执都不会有。
   对照着看，走 HTTP 的那条路（`agent-row.ts:281-308` 的 `callViaFetch`）是有取消信号的：`:286` 起一个 `AGENT_TOOL_TIMEOUT_MS` 的定时器，到点 `ctrl.abort()`，`:302` 把 `ctrl.signal` 交出去。两条路在这一点上并不一样。

### 已经被今天的新结构挡住的部分

4. 工具自己的 300 秒预算、15 秒余量、单次 30 秒钳制（`call-budget.ts:24/27/29`），加上建票前预检与幂等锚，让「建一半被打断又重调一次」在正常情况下不会重复建票——门禁实测零重复。
5. 整图建骨架有了落盘续跑点与 `partial` 回执，部分成功会如实回报剩余项与续跑标识（门禁 25 条全过）。这是票面当天完全没有的东西。
6. 超时回执从不假装成功（`call-budget.ts:187` 的原话就是「是否生效说不清」）。

### 与票面相比仍然缺的三个缺口

- **超时之后不去读一次现状**，所以「是否生效说不清」永远停在「说不清」，调用方没有只读手段把状态确认下来（写后读回只在正常返回之后跑）。
- **超时不与真失败分开记**（回执的 `reason` 与日志的失败指纹都并格），事后翻日志无法只凭日志定位「这一次是限时用完还是后端返回了失败」。
- **外层掐掉的那条路没有善后**：没有部分落盘的记录、没有续跑点、也没有一句「可能已经写了一部分」。

## 八、不确定的地方

- 今天的 DSH 宿主与网页界面调这个工具时，有没有它自己的一层限时、到点之后是立刻把连接放掉还是继续等、以及这时候工具那条路会不会被真的中断——这些行为不在本仓里（`src/host/` 只覆盖本插件自己装在宿主上的部分），本次调查没有做真机实测，无法断言。若宿主的限时小于 300 秒，第一节说的第一层就被绕过，症状会比上面判断的更靠前出现。
- 同进程快路那条路径（第一节第 3 点）的结论是从注册侧代码读出来的，没有做端到端实测：「调用方超时走人、宿主侧还在继续写」这个组合没有现成的门禁覆盖，需要造一次真调用才能钉死。这也是本票判定只能是（c）而不能是（a）的原因——（a）需要一条能跑出症状的实测路径。
- 票面当天的 120 秒值是从哪里配置进去的，在今天的树里找不到对应物（`AGENT_TOOL_TIMEOUT_MS` 是硬编码的 300000，没有从配置读的痕迹）；如果当天那个 120 秒来自宿主配置而不是本插件，那么「把数改回去」的入口也不在本仓，得去宿主那一侧找。

## 九、真要做的话，一两句话的策略

最省的两条：一是把两处 300 秒收成一处来源（注册层从 `call-budget.ts` 取同一个常量，并让工具的内层计时从调用进入工具那一刻开始，而不是从选完后端、探完沙箱之后开始），再把写操作一律排在「剩余时间减去余量」之内动手；二是给外层掐掉那条路补上善后——超时回执里把「已经落盘的部分、可能生效的部分、确定没动的部分」分三段说清，并给限时用完单独一个 `reason`（日志摘要也跟着分开），同时在同进程快路上把调用方的取消信号如实交给工具，让它至少能在被放弃时停手并留下进度。
