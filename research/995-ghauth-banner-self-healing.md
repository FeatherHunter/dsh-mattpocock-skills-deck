## 一、这份文档回答什么问题

票面已经写清的现象是：状态栏那条黄色横幅「登录状态暂时确认不了 —— 点右侧重试」不会自己消失，必须人手点一次「重新检查」。本档往前再走两层：

1. 这件事在代码里到底是怎么发生的（取证到行）；
2. 如果要改，改哪里、代价多少、有哪些坑（三个方案 + 对抗式审查）；
3. 哪些问题只有维护者能拍板，以及**为什么现在故意不拍**。

本档不预设结论，也不改任何代码。文中出现的「推荐」都标了它的反面意见。

## 二、现象与取证

### 2.2 同一天本机的时间线（2026-10-10，Asia/Shanghai）

| 时间 | 发生了什么 | 证据 |
| --- | --- | --- |
| 约 12:00 | 网络不可达：`git ls-remote` 报 `schannel: failed to receive handshake`；`curl` 打 github.com／registry.npmjs.org／baidu.com 全部返回 000；本机代理 `127.0.0.1:7890` 端口在听、CONNECT 隧道返回 200，但隧道内握手失败 | 命令原始输出 |
| 同刻 | `gh auth status` 退出码 1，报 hosts.yml 里的令牌无效 | 命令原始输出 |
| 同刻 | 登录态检查判成 `pending`，黄条出现，并一直挂着 | 见第三节的判据 |
| 约 12:29 | 网络恢复：`gh auth status` 退出码 0、「Logged in to github.com account FeatherHunter」；`gh api rate_limit` 正常（core 剩余 4829） | 命令原始输出 |
| 同刻 | 维护者点一次「重新检查」，黄条消失 | 维护者口述 |

**一个必须记住的结论**：断网时那句「令牌无效」是**假象**，不是登录真的失效。同一条命令在 37 分钟后给出相反结论，中间没有任何人动过凭据。这句原话同时出现在已打开的 [#893《以 deck 开头的工具有两个调用失败》](https://github.com/FeatherHunter/dsh-mattpocock-skills-deck/issues/893) 的诊断里——那张票当时也是断网/抖动所致。**以后看到「令牌无效」四个字，先把网络排掉再谈凭据。**

### 2.3 判据链（谁决定出这条黄条）

1. **判成什么状态**：`src/host/detectChain.js` 第 155–169 行的 `preflight:ghAuth` 谓词跑 `gh auth status`：
   - 通过 → `pass`；
   - 明确报登录失效（kind 为 `auth`）→ `fail`；
   - 网络失败（kind 为 `network`）→ `pending`；
   - 其它异常 → 也 `pending`。
2. **横幅怎么选**：`src/shared/tracker/guide-steps.js`
   - `guideStepState()`（第 168–184 行）把这一步归成 `done / failed / pending / absent`；
   - `guideBannerOf()`（第 190–195 行）：`gh:authed` 处于 `pending` 时换成 `BANNER.ghAuthUnknown`（第 45 行）；
   - `guideMissingOf()`（第 201–206 行）：同一条件下按钮动作换成 `MISSING.ghAuthRecheck`（第 31 行，只强制重查，不注入登录指引）。
   - 这一步的分流出自 [#916](https://github.com/FeatherHunter/dsh-mattpocock-skills-deck/issues/916)（提交 `a8baea9`），方向是「查不到不再冒充缺登录」。
3. **文案**：`src/client/kernel/locale-panel.js` 第 51 行（中文）／第 206 行（英文）。
4. **按钮点下去**：`src/client/statusbar/bannerChain.js` 第 205–228 行，带 `user-recheck` 口令调 `wf.detect`。

### 2.4 为什么「不点就永远不算」

这是本单真正的手术部位：

- 宿主侧**一个自续定时器都没有**：`src/host/refresh/chainBackoff.js` 第 11–13 行明写「本文件不排任何定时器，一条都没有」，下一次求值只可能由四种事件带起来（切进工作区、人亲手点「重新检查」、做完可能改变它的动作、写入成功之后）。
- 客户端那一侧同样没有自轮询：`src/client/kernel/probe-chain.js` 第 45–53 行记着 #709 把「链没全绿就 8 秒后再算一次」那条整体退役了。
- 因此：`gh:authed` 停在 `pending` → 黄条出现 → 没有任何一路会自己去问第二次 → 只有人点按钮才重算。

### 2.5 已经存在一条自动重算的路，但门槛写窄了

`src/client/kernel/probe-auto.js` 第 189–228 行的活跃工作区心跳（`startActiveProbeLoop`）里，已经挂了一次条件性的链重算：

```js
// #891：初始化那一步还没过时，顺带重算一次链。……
// 这里复用正在看才跑的这一拍，不新开定时器；
if (typeof setupPendingOf === 'function' && setupPendingOf(st)) {
  chainEventRefresh(st, 'setup-pending')
}
```

它的门槛是 `setupPendingOf`（`src/client/kernel/probe-chain.js` 第 65–76 行），里面写死了一名步骤：

```js
if (it && String(it.id) === 'tracker:initialized') return String(it.status || '') !== 'done'
```

于是结论很干脆：

> **自动收尾的能力已经存在，只是绑死在「初始化未完成」这一个条件上。** 登录态那一步永远够不到它，所以只能手点。

这是 [#891《初始化完成后黄条仍提示未初始化，疑似刷新机制不再定期刷新》](https://github.com/FeatherHunter/dsh-mattpocock-skills-deck/issues/891) 的修法，当时为了控范围写成了那一步专属，没有推广。

## 三、三个候选方案

### 方案甲：机制兑现文案（自动重算）

把 `setupPendingOf` 那一个写死步骤的条件，换成一个共用纯函数（例如 `guideNeedsRecheck(steps)`），只要**当前该出横幅的那一步**不是 `done` 就返回真；心跳那一拍据此调 `chainEventRefresh`。`setupPendingOf` 退休，不并存。

- **好处**：任何新加一步、新加一条横幅都自动继承自动收尾，不需要再有人记得加一个 `xxxPendingOf`。界面状态始终是事实的函数。
- **代价**：会动到已运行的心跳路径；要新增门禁测试锁住「全绿缓存不被打碎」。
- **不变量**：宿主侧零定时器不变（搭车，不新增节奏）。

### 方案乙：文案收回承诺（不自动，但说清）

既然机制上不会自己好，就别写「暂时」。改成说清「需要点一下才会重新确认」。

- **好处**：改动最小，只有词条；不谈架构。
- **代价**：面板从「替人盯着」退化成「什么都得你亲手点」。而**这个面板存在的意义正是替人盯着**。

### 方案丙：不动（本次拍板）

把现象、根因、证据、触发条件与复现步骤落档，标「待复现」，等真机复核之后再决定改不改。

- **好处**：现在没有任何真机复核记录；改动方向还是产品口径问题，不是纯技术问题。
- **代价**：现象继续存在；同类根因（#891 已修一半）继续按症状逐个打补丁。

## 四、给决策者的四个问题

1. **产品口径**：这条横幅是「告诉用户等一下会自己好」，还是「告诉用户需要你拍板」？这决定走甲还是乙。
2. **若走甲**：触发条件只认「有步骤未通过」，还是同时认「手里这份快照已经不新鲜」？（理由见 5.4 的 A4）
3. **若走甲**：自动重算退到最慢档（5 分钟）之后，界面要不要把「已经在慢慢重试」这件事说出来？（不做的话，自动重算只是把「永远不动」变成「每 5 分钟假装动一下」）
4. **要不要把「预检成功缓存 10 分钟导致界面可能显示过期结论」单独建一张票**？（见 6.2）

## 五、对抗式审查（对方案甲逐条攻击）

### A1 「文案承诺论」可以被反驳，而且反驳成立了一半

**攻击**：#916 的设计意图可能恰恰是「让人动手」——`guide-steps.js` 第 29–31 行的注释与 #916 对抗审查的 F5 都写着「未知态保持黄色（需动手重试）」。所以「界面上写着暂时就该自动好」是我读出来的，未必是维护者定的。

**修正**：把问题从「必须自动」降级为「必须自洽」。两条路（甲／乙）都能接受，现状（文案承诺、机制不兑现）不能接受。这个取舍归维护者。

### A2 最狠的一击：通用化之后自动重算会「退到停」

**攻击**：`refresh-core/src/backoff.ts` 的 `advanceChainStep()` 规则是「没有进展就往后一档，退到最慢档就停在那里」；`CHAIN_BACKOFF_MS` 是 `[8s, 30s, 2min, 5min]`。长期失败时档位停在 5 分钟**不动**。所以自动重算**永远在重试，但可能永远不成功**——方案甲没有消灭本现象，只是把「不点就永远不算」变成「不点也要等 5 分钟，且未必算得动」。

**这条攻击成立，且是方案甲最大的洞。** 诚实的结论：

- 自动重算解决的是「临时性原因恢复后能自己好」（本单真实场景：网络断了十几分钟，恢复后应当自愈），**不是**「任何 pending 都能自愈」。
- 所以必须**同时保留手动重查**（`user-recheck` 永不降档，见 `chainBackoff.js` 第 89–92 行），文案要让用户知道自己随时能拍板。
- 界面必须能区分「还在重试」与「已退到最慢档」，否则就是假装在工作。

### A3 成本账里藏了一个乐观假设

**攻击**：按「退避是唯一闸」算不合理，因为 `chainEventRefresh` 默认 `force = true`（`probe-chain.js` 第 92 行），**force 会绕过在途去重与共享缓存**。

**修正**：心跳这一路要显式声明触发原因；实现时要在注释里写清「IPC 每 5 秒一发、出网受退避限制」这个区别，否则下一个人会误以为 5 秒一次就是 5 秒出一次网。

### A4 「宿主不用改」说满了：预检缓存会让成功态长时间不刷新

**攻击**：`preflightUsable()`（`backoff.ts`）规定预检**成功**缓存 10 分钟（`PREFLIGHT_TTL_MS`），**失败不缓存**。登录态检查正是预检（`detectChain.js` 第 155 行注册在 `preflight:` 前缀下）。所以：

- 「失败/未知」这一类会真重查，能自愈；
- 「成功但已过期」这一类要等 10 分钟 TTL 到了才会变。

**修正**：触发条件不该只有「有步骤未通过」，还应包含「这份快照已经不新鲜」。而新鲜度判定**已经有唯一真源**：`refresh-core/src/budget.ts` 的 `freshnessLevel()`（`FRESHNESS_YELLOW_MS = 5min`、`FRESHNESS_RED_MS = 30min`）。**不许在界面层另写阈值。**

### A5 通用化可能撞碎「全绿缓存」这个最省钱的机制

**攻击**：`chainCacheUsable()` 让全绿结论缓存 30 分钟（`CHAIN_ALL_GREEN_TTL_MS`），是全仓省请求最多的机制。在 pending 上自动重算，会不会顺手把它撞碎？

**结论：不会，但必须验。** `chainRefreshVerdict()` 里「全绿且未过期 → `needed: false, reason: 'all-green-cached'`」是第一条判断，先于任何 pending 逻辑。**这一条要写成断言式门禁测试，不能只在脑子里过。**

### A6 仓库的物理约束可能让设计落不了地

**攻击**：单文件 ≤350 行是硬门禁（`tests/verify-file-granularity.js`）；`src/shared/tracker/guide-steps.js` 现 284 行，余量 66 行；`src/client/kernel/probe-auto.js` **343 行，只剩 7 行**；同层不许互相 import（`tests/verify-no-same-layer-import.js`）。

**修正**：新纯函数若放不进 `guide-steps.js`，按仓库既有做法**另立叶子模块**（零 import 或只 import 类型），不许硬塞或拆人家的文件。反过来看，`probe-auto.js` 那 7 行余量意味着「删掉 `setupPendingOf` 分支、换成一个通用调用」在行数上是**净减少**——这是通用化顺带的好处。

## 六、容量账与独立发现

### 6.1 容量（方案甲走起来花多少）

- 一次链条求值 3 条请求（`CHAIN_EVAL_COST_REQUESTS = 3`，预检那 2 条会被谓词复用）。
- 心跳 5 秒一拍（`PROBE_INTERVAL_MS = 5_000`），只在有未通过步骤时才发；真正出网受退避限制。
- 稳态最坏：4 次无进展求值把档位推到最慢档 ≈ **12 条请求／5 分钟／工作区**。
- 可见工作区上限 2 个（`MAX_ACTIVE_WORKSPACES = 2`）→ 最坏约 **288 条请求／小时**，对每小时 1500 请求、1750 点的顶来说可忽略。
- 而且人只要不点，退避**只会变慢不会变快**，长期失败自然衰减——这正是想要的节流形状。

### 6.2 独立发现（建议另立一张票，不要混进 #995）

**预检成功缓存 10 分钟 ⇒ 界面可能长时间显示一个已经过期的「确认不了」。**

- 位置：`refresh-core/src/backoff.ts` 的 `preflightUsable()` + `budget.ts` 的 `PREFLIGHT_TTL_MS = 10 * 60_000`。
- 为什么算独立缺陷：它与 #995 同源（都是「界面状态落后于事实」），但成因不同（一个是缺触发器，一个是成功结论被刻意缓存）。混在一张票里，两边会互相拖累。
- 反方意见：也可以认为它不算缺陷——10 分钟缓存是**故意的省钱设计**，界面只要把新鲜度显示出来（`freshnessLevel()` 已经给了黄／红两档），用户就知道这份结论有多旧。**这条要维护者定性，不能由我替它判。**
