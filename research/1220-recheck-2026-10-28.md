## 三、为什么：钩子与黄条看的不是同一个会话状态

### 3.1 黄条画的是当前会话的 store

状态栏组件按宿主给的会话号拿状态：`src/client/statusbar/StatusBar.ts:137` 是 `const s = cx ? cx.storeSvc.useStore(sid) : useStore(sid)`；横幅判定在 `:300-323`，`guideBannerDiagnosis(s, …)` / `guideBannerStep(s, …)` 读的是 `s` 的链快照（`src/client/statusbar/bannerChain.ts:228-339`）。黄条出现与消失，只看这一份 store 的 `chainSnapshot`。

### 3.2 钩子取的是 shared，而 shared 冷启动就固定成第一个会话

`src/refresh/rooms/client/refresh-timer.ts:304-356` 是活跃探测循环；每一拍的关键几行：

- `:321` `const st: any = attentionStoreOf(null)`
- `:322-323` `cwd = st.cwd`，没有 cwd 就 return
- `:337-342` `if (setupPendingOf(st)) chainEventRefresh(st, 'setup-pending')`（#891 的钩子）

`attentionStoreOf` 在 `src/refresh/rooms/client/client-attention-heartbeat.ts:65-73`，收到 null 时的顺序是：`shared` 有 cwd 就返回 `shared`；否则第一个有 cwd 的 store。而 `shared.cwd` 只有一个写入点——`src/refresh/rooms/client/refresh-timer.ts:249-252` 的冷启动探针：`if (!shared.cwd && foundCwds.length) { shared.cwd = foundCwds[0] … }`，`foundCwds` 按「shared 的会话号 + 各 store 的键」顺序查出来，取第一个。之后 `shared.cwd` 再不改。

于是：**每 5 秒一拍的探测目标、以及钩子判断用的状态，都长期停在「第一个查到的工作区」——在这台机器上就是本仓。** 本仓那几步链早就全绿，`setupPendingOf(shared)` 恒为 false，钩子永远不发重算；探测也一直探本仓，这就是第二节里「探测全在本仓」的来源。

### 3.3 同一处 null 上报还会把宿主的探测目标拽回本仓

心跳、窗口获焦、失焦都报 null：`client-attention-heartbeat.ts:177-185`（`attentionBeat` → `reportWorkspaceAttention(null,'heartbeat',null)`）、`:206-228`（`focus` / `window-blur` 也传 null）。`reportWorkspaceAttention` 在 `:115-147` 同样用 `attentionStoreOf(st)` 取 store，再取它的工作区根去调 `wf.focus`；宿主回的探测目标写进 `_attentionPlan.root`，`probeTargetNow`（`client-attention-heartbeat.ts:277-292`）按这个 root 选目标。null 上报按 shared 取值，就把 root 反复覆盖回本仓——这是同一条「取错 store」在探测目标上的第二个症状，和 3.2 是同一个根因。

### 3.4 还有一重：shared 自己大概率没有链快照

`hydrateFromCache`（`src/refresh/rooms/client/snapshot-cache-store.ts:230-300`）只有在 `cachedChain && !st.chainSnapshot` 且能定出 `backendId` 时才水合链快照（`:292-299`）。启动时 `src/client/panelAssembly.ts:216` 只给 shared 加载快照（`loadSnapshot(shared, false)`），不加载链；全仓给 shared 发 `chainEventRefresh` / `loadChain` 的调用点一个都没有。所以即使本仓链没绿，钩子也未必有东西可判：**钩子不该看 shared，这个结论有两重独立理由。**

## 四、一个看起来更省事的修法，为什么不成立

「在注意力模块里记住最后一次具体上报的 store」看起来比新增登记更省：谁上报具体状态就记谁，null 时用它。但这个近似有洞：切回一个「缓存还在、仍然新鲜」的会话时，组件不会产生任何具体上报——`snapshotRequestPlan`（`src/client/kernel/work-route-own.ts:194-210`）在 `mode === 'switch'` 或 `hydrated && fresh` 时直接返回 null，`runSnapshotRequestPlan` 也就不会发 `loadSnapshot`，自然没有 `panel-open` 上报。指针会停在上一个会话，第一拍又看错。所以必须由界面显式登记「我现在显示的是哪个会话」。

## 五、我认可的方案（收敛）

一句话：**给注意力模块加一个「当前正在显示的会话状态」指针，由界面在挂载时登记、卸载时按同一引用清掉；`attentionStoreOf(null)` 改成「有指针且指针有 cwd 就用指针，再退回 shared，再退回第一个有 cwd 的 store」。**

### 5.1 为什么这样够

- **界面侧只有一份。** DSH 客户端把对话正文与输入坞注册成 `conversation.content`（scope 是 `session-maybe`），渲染器对它的语义是：拿到第一个会话号后就像严格会话条目一样，**切到别的会话会整棵重挂载**，回到无会话则重挂成新的空实例（`dsh-client-ui-renderer/lib/client.js:825-881` 的注释与 `useMaybeIncarnation` 的 epoch 实现）。所以同一时刻只有当前会话的那一份状态栏在挂载，最后登记的就是当前会话，不存在「多份状态栏抢着写」的问题。
- **一处改完三处同时落到当前会话。** 探测目标、心跳/焦点上报、#891 的钩子共用 `attentionStoreOf`；指针修好后，钩子评估的正是黄条依据的那份状态，root 上报也不再被最老会话拽走。
- **界面侧代价可控。** StatusBar 已贴单文件 350 有效行的粒度红线（2026-10-28 实测 348），照 #1409 的现成先例（`src/client/statusbar/suggestStream.ts:347-411` 的注释原话就是这个理由），新起一个只返回 null 的挂载组件；状态栏只在收起态与展开态两处已有渲染行里追加子节点，并加一行 declare——有效行 348 → 349。

### 5.3 修好之后黄条多久消失

钩子取对以后：下一拍（最长 5 秒）`setupPendingOf` 为真 → `chainEventRefresh(st,'setup-pending')` → 宿主退避对 `trigger=setup-pending` 有 15 秒等待封顶（`src/refresh/rooms/host/chain-backoff.ts:134-144`，`chainSetupPendingCapMs=15000`，`src/shared/time-config/src/values.ts:178`）→ 真算一次 → 回包写回 `st.chainSnapshot` → `emit` → 黄条按新快照消失。**最坏约 20 秒。** 维护者原话「15 秒内消失」比实际紧，验收措辞写「最迟约 20 秒」更准。

## 六、验收与边界

修复落地后，#1220 的真机验收步骤（本轮已证明：不隔离旁路就只能验出假通过）：

1. 打开插件面板，切到一个非本仓的、尚未初始化的 Markdown 工作区，等顶部出现 `tracker:initialized` 黄条。
2. 按注入提示词走完初始化。**不点「重新检查」、不切工作区、不做写操作**——这三条都会从旁路触发链重算，验不出真正的自动重算。
3. 日志应出现：`chain.flow` request 带 `reason=setup-pending`（若被宿主退避挡住，则是 `chain.backoff` 带 `trigger=setup-pending` / `decision=defer`）；随后 `guide.banner step=tracker:initialized outcome=cleared`；黄条消失，最迟约 20 秒。
4. 反面对照：今天的表现见第二节——`setup-pending` 0 条，黄条只有人手点或面板重挂载才收。

边界与代价：

- 初始化未完成、黄条挂着期间，每约 15 秒会真实求值一次宿主链（#891 已接受的设计，不是本修复新增的定时器）；修复后要顺带看 `chain.flow` 的量与 GraphQL 配额，太热再调 `chainSetupPendingCapMs`。
- 不改链求值与检查链本身、不改退避数值、不动 #1474 的触发条件扩宽；但 #1474 的真机验收（登录态黄条自己收）以本修复为前提，别抢在它前面验。
- 状态栏未挂载时指针为空，退回 shared，行为与今天一致；分屏/多窗口如果真能并排两份对话正文，登记就是「最后挂载者生效」，本轮证据指向同一时刻只有一份，但没有穷尽所有入口，实施时可以顺手确认。
- 新加的那次 `reportWorkspaceAttention(st,'session-switch')` 是可选加强：`ATTENTION_SIGNAL_KINDS` 早就有 `session-switch` 这个值（`src/refresh/rooms/host/host-attention.ts:100`），客户端一直没有调用点，root 要靠心跳（最多 20 秒）才跟上；不纳入也不影响 #1220 的验收。
