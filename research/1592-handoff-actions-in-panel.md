原来判「只能交给终端」的理由只有三种：要人写一段 git 之外的内容（编辑器）、要跑一条 git 之外的命令（任意命令）、要碰系统或别人的机器（系统权限、密钥、图形工具、服务端）。这三种在「宿主直接起子进程，面板自己产出那份内容」的前提下都不再成立。真正卡住面板的不是 git 的能力，而是两件工程上的事：**宿主现在只有六个写命令的通道**（暂存、撤回暂存、提交、拉取、抓取、推送），别的动作要新接；**长任务没有地方落**（120 秒票据管的是预检到执行之间的新鲜度，不是一条命令能跑多久）。

## 0. 先把三件事说清

### 0.1 前提变了，判断也跟着变

基础笔记判「只能交给终端」，靠的是三条理由，当时都成立，现在都要重算。

**第一条：git 需要一个人写一段内容。** 这是误会。git 里每一个「打开编辑器」的地方，都是同一套动作：git 准备一份文件，等人改，再读回来。`git commit` 不带 `-m` 时把模板写进 `.git/COMMIT_EDITMSG`；`git rebase -i` 把待办清单写进 `.git/rebase-merge/git-rebase-todo`；`git config --edit` 打开的是某个配置文件；`git branch --edit-description` 打开的临时文件里只有一行。面板只要自己产出那份内容，再走 git 的「从文件读」入口送回去，编辑器就整个消失了。本机实测 `git var GIT_EDITOR` 返回 `vi`，而宿主起子进程时标准输入是关掉的（`src/host/versionControl.ts:113-119`），真去调编辑器只会挂死——所以「绕开编辑器」不是偏好，是唯一可行的路。

**第二条：动作的参数本身就是一段命令。** `submodule foreach`、`bisect run`、`rebase --exec`、`filter-branch` 的过滤器，参数都是「一段交给 shell 的命令」。宿主当然能跑，但面板不该给自由命令框：300–520 像素宽的一个输入框，等于把写错路径、误删文件、跑到一半卡住的所有风险原样搬进来，而预检对它什么都预测不了。替代品是**一条登记过的检查**：从仓库已有的脚本里选（`package.json` 的 scripts、`Makefile` 的 target、`justfile` 的 recipe），或者用户自己存一条；宿主用固定参数跑，不经 shell（详见 0.3 的 E5）。动作还在，输入从「任意文本」收窄成「一条有名字的命令」，损失的那部分自由正是风险本身。

**第三条：要碰系统或别人的机器。** `maintenance start` 要写用户全局配置并注册计划任务，`credential-store` 会把口令明文写进文件，`gitk`、`mergetool` 要开窗口。这些不是「面板做不到」，是「面板做得到但不该照原样做」。该做的做（注册与关闭维护、只读状态），不该做的明确拒绝（明文凭据、开外部窗口），并给替代品（面板内的冲突编辑器、面板内的历史列表）。

一句话：归属从「外」变成「直 / 折 / 诊」，判据也从「这件事要不要离开面板」变成「这件事的风险面板能不能讲清楚」。

### 0.3 宿主要先补的五件事

后面 26 条方案的共同地基就是这五件。它们都不是「某个动作要不要做」，而是「这类动作有没有地方落」。

**E1 临时文件，加一个写文件的小程序。** 现在的写电话只能给参数列表，标准输入是关掉的，所以 `git commit -F -`（从标准输入读说明）走不通。最省事的做法是：说明、待办清单、补丁正文写到操作系统临时目录里的一个文件（不在仓库里，提交前后 `finally` 删掉），用 `-F <路径>` 交给 git。变基清单要的是 `GIT_SEQUENCE_EDITOR`，那是个「可执行的东西」，所以还得随插件发布一个几十行的小程序：读环境变量里给的源文件，覆盖到 git 追加在命令后面的那个路径上。参数里只传路径，不传内容，避免超长环境变量和转义。备选方案是宿主自己用 `cherry-pick` 加 `--amend` 循环重放提交，不要这个小程序，但代码量和失败面都大得多，只在「不想往包里加文件」时才考虑。

**E2 一次性口令通道。** 三条硬线：口令不进命令行参数（同机进程能看到）、不落盘（临时文件和配置文件都会被备份、同步、翻出来）、不进日志。手段是让 `GIT_ASKPASS` / `SSH_ASKPASS` 指向一个小助手，口令经一次性环境变量传给它，`SSH_ASKPASS_REQUIRE=force` 让 ssh 一定要用它；GPG 这边走 `--pinentry-mode loopback --passphrase-fd`。宿主在子进程退出后立刻把自己环境里的那一份清掉。日志里只记主机名和助手名，不记用户名、令牌、口令。

**E3 长任务（进度加取消）。** 现在每条写命令一个固定超时：提交 60 秒、推送 2 分钟、拉取 3 分钟（`config/timeouts.yaml:85-88`）。克隆一个大仓库可能十几分钟，没有任何地方能放下它。做法是新增一组任务通道：开始、查状态、取消，任务编号与写票据分开。进度从 git 写到标准错误里的行解析（克隆的 `Receiving objects: 45%`、打包的 `Enumerating objects`），取消走已有的进程树终止。**关键细节**：长任务开始时先把引用解析成对象号再交给 git，之后只用对象号——否则用户中途切了分支，导出的东西就说不清是哪一个。120 秒票据够不够？够，但要重新解释：票据在**启动**时校验一次，任务跑多久与票据无关，不能拿票据当任务的租约。

**E4 路径输入，不做系统文件选择器。** 理由：300–520 宽放不下面板内的目录树；系统选择器把交互弹出面板，违背「就近」这条界面规矩；选中的结果回到渲染层也只是一个字符串。做法是文本框加两段校验：失焦时给即时反馈（解析成绝对路径了吗、存在吗、是空目录吗、在仓库里吗、父目录可写吗、Windows 保留名和超长路径），提交时宿主再校验一次（渲染层的输入不可信）。默认只允许写到工作区或操作系统临时目录，要写到别处必须显式切换并确认——否则一个被利用的渲染层就能往 `C:\Windows` 里写东西。

**E5 结构化检查清单（替代任意命令框）。** 清单从仓库里已有的东西发现：`package.json` 的 scripts、`Makefile` 的 target、`justfile` 的 recipe；也可以让用户存一条（存插件配置，不写进仓库）。执行时宿主用固定参数（比如 `npm` + `run` + 脚本名），不经 shell，工作目录固定仓库根，超时固定。预检能说清的是：哪条命令、在哪个提交上跑、上次跑了多久、会不会改工作区（说不准就写说不准，并当作会改来提示）。

对 #1586 的具体要求见 8.4。

## 1. 编辑器类（5 条，全部能完全进面板）

这一组的共同机制：git 里所有「打开编辑器」的地方，都不是 git 需要一个窗口，而是它需要**一份内容**。面板只要自己产出那份内容，再用 git 的「从文件读」入口送回去，编辑器就整个不需要了。五条方案共用 E1 那一套，区别只在「内容长什么样」和「哪个环境变量指向它」。

### 1.1 不带 `-m` 的提交（完全进面板）

**界面**：提交区本来就是「标题 + 正文」两栏，这就是原来编辑器的替代品，不需要新界面。要补的只有一件事：如果仓库配了 `commit.template`，打开提交区时把模板填进两栏，而不是让人从空白开始。

**内容怎么交给 git**：说明写到操作系统临时目录下的一个 UTF-8 文件，`git commit -F <路径>`。不要用 `-m` 拼字符串——多行、引号、换行都要经过规则，`-F` 把这一层整个跳过。`-F` 时 git 的清理模式默认是 `whitespace`（官方文档：`--cleanup=default` 在「不编辑」时等同 `whitespace`），也就是说以 `#` 开头的行不会被当成注释删掉，用户写什么就提交什么。

**预检**：沿用现在提交的预检（暂存清单、索引指纹、有没有进行中的操作、i-t-a 条目），再加两条：「说明非空」（否则 git 报 `Aborting commit due to empty commit message`，白跑一趟）、「正文里有没有 `#` 行」（有也没关系，只是提醒一下不会被删）。

**确认**：不改现在的做法（提交可逆，轻确认或不确认），按钮下加一行「首行 + 正文 N 行 + 将提交 M 个文件」。

**失败怎么回显**：分三种说清楚——临时文件没写成（「说明没落盘，什么都没提交」）、git 拒绝（钩子、身份缺失、索引锁，沿用 #839 已有的一分档）、说明为空（预检就该拦，拦不住时贴 git 原话）。

**结果**：贴提交区，同时出现在历史列表第一行；说明可以点开回看。

**待核实**：`commit.cleanup` 被用户改成 `strip` 时 `#` 行会被吃掉，面板要不要强制 `--cleanup=whitespace`。

### 1.2 `rebase -i` 的待办清单（完全进面板）

**界面**：变基二级页。中间是提交清单（短号、首行、作者时间），每行一个动作下拉：`pick`（保留）、`reword`（改说明）、`squash`（合并进上一条并改说明）、`fixup`（合并进上一条、丢掉这条的说明）、`drop`（丢弃）、`edit`（停在这里让我改）；左边上移、下移按钮（300 宽放不下拖拽）；底部一块「合并后的提交说明」编辑区，`squash` 用；顶部一行汇总：「将重放 8 条：改说明 2、合并 3、丢弃 1」。

**内容怎么交给 git**：宿主按用户调好的顺序生成待办清单文本（`pick <对象号> <首行>`，动作换掉），写到临时文件。`GIT_SEQUENCE_EDITOR` 指向 E1 里那个小程序，它把临时文件覆盖到 git 追加在命令后面的待办清单路径上。`reword` 和 `squash` 的新说明另存一份，按顺序排队；`GIT_EDITOR` 也指向同一个小程序，它按「被调文件里原来的那段文字」去匹配对应的新说明，匹配不上就原样退回（等价于接受默认，不会把提交说明写成空）。环境变量只传路径，不传内容。

**预检**：工作区干净（显式加 `--no-autostash`，不让用户配置里的 `rebase.autoStash` 偷偷 stash）、基座存在、区间和用户看到的一致（重新解析一次，把区间首尾对象号绑进票据）、区间里有没有已经推送的提交（有就写「远端会分叉，之后要强推」）。

**确认**：二次确认卡写四件事——会重写哪几条（前五个短号加其余计数）、所有对象号都会变、已推送的话远端要重新推、旧提交还在 reflog 里能找回；再加一句「失败会停在哪一步，怎么继续或中止」。

**失败怎么回显**：冲突就切冲突向导（面板已有）；待办清单被 git 判非法（`invalid line`）就把那一行贴出来；小程序没跑起来要说「清单没交给 git，什么都没改」；宿主中途崩了，下次打开面板检测到 `.git/rebase-merge` 目录，直接给继续或中止。

**结果**：历史列表整段替换，顶部提示「N 条已重写」；旧位置在 reflog 里。

**待核实**：`reword` 时 git 用的消息文件路径（`.git/rebase-merge/message` 还是 `COMMIT_EDITMSG`）；`squash` 时 git 给的是几条说明拼在一起的一整段，匹配要按整段做；仓库路径带空格时 git 给小程序追加的路径有没有正确加引号。

### 1.3 `config edit`（完全进面板）

**界面**：配置二级页。按作用域分组（系统、全局、这个仓库、这个工作树），每行「键 = 值，来源文件第几行」（`--show-origin` 给的），带搜索框；点行内编辑，值用多行输入框；「新增键」一个入口；作用域默认「这个仓库」。

**内容怎么交给 git**：`git config --local|--global|--worktree --replace-all <键> <值>`，新增用 `--add`，删除用 `--unset-all`。**绝不 `--edit`**——那正是原来要编辑器的那一步。多行值作为一个参数传进去，git 自己负责转义和写盘。

**预检**：值里有 NUL 直接拒；这个键在几个作用域里存在（同名多处必须让人选改哪一处）；这个键会不会改面板自己命令的行为（`core.hooksPath`、`credential.helper`、`push.default` 之类，面板的固定前缀已经压了 `push.default` 和 `push.followTags`，仍要提示）；改全局要单独一句「影响这台机器上所有仓库」。

**确认**：写哪一层、旧值变成什么、会不会覆盖同名的其它值、要不要重启面板才生效。

**失败怎么回显**：git 的 `invalid key`、`invalid value` 原话回显；写不进去要说清是哪个文件、什么权限；**注释和顺序可能丢**（`git config` 重写文件时不保留注释，待核实具体行为）要提前在确认卡里说。

**结果**：行内值更新，来源标记跟着变；顶部提示「已写入 <文件>」。

**待核实**：`--show-scope` 要 2.26（版本底线是 2.11，只能用 `--show-origin` 的路径反推作用域）；`--worktree` 写进哪一层；某些键改了要不要重启才生效。

### 1.4 `branch --edit-description`（完全进面板）

**界面**：分支浮层里的「分支详情」增加一段只读说明和一个编辑按钮，点开是多行文本框；下面一句「这段说明会被 `format-patch` 和 `request-pull` 用到，纯文本，不渲染」。分支列表里如果有说明，就在分支名后面点一个小圆点。

**内容怎么交给 git**：`git config branch.<分支名>.description <文本>`，清空用 `--unset`。分支名先过已有的分支名规则再加 `check-ref-format --branch` 复核。

**预检**：分支存在；文本长度给个面板自己的上限（4 KB 足够，git 不限）；含 `#` 无所谓（这不是提交说明）。

**确认**：轻确认，写明「只改本地配置，不推送、不影响别人」。

**失败怎么回显**：配置写失败贴原话；分支名非法在预检就拦。

**结果**：分支详情里的说明立即变。`git branch -v` 不显示说明，所以只在详情里看得到，这一点要在界面上说一句。

### 1.5 `tag -a` 不带说明（完全进面板）

**界面**：建标签浮层：名字、目标（默认 HEAD，也可以从历史行点过来）、类型（轻量、附注、签名）、说明两栏。附注标签强制至少一行说明——否则它和轻量标签在使用上没有区别，只会让仓库里多一堆空说明的标签。

**内容怎么交给 git**：`git tag -a <名字> -F <临时文件>`；签名用 `-s`（要 GPG，见 4.3）。名字先过 `check-ref-format refs/tags/<名字>`。

**预检**：名字合法、本地没有同名、目标对象存在、打算建的是附注还是轻量、要签名的话钥匙解没解锁。

**确认**：轻确认（本地标签可删），写明「只建在本地，要另外推」。

**失败怎么回显**：名字冲突、签名失败（分成「钥匙没解锁」「口令不对」「签名程序不可用」）、说明文件没写成。

**结果**：标签折叠区多一行，历史里那个提交旁边出现标签。

### 1.6 同一机制还能接住的其它编辑器入口

`merge --edit`、不带 `-m` 的 `commit --amend`、`git notes add/edit`、`git add -e`、`git rebase --edit-todo`，还有 `GIT_MERGE_AUTOEDIT` 这个环境变量。它们不需要单独设计：有了「说明输入框 + 临时文件 + `-F`」这一套，`merge --edit` 和 `--amend` 直接就通了；`git add -e` 是让人编辑 diff 本身，面板不做（风险高、收益低），归只读诊断；`rebase --edit-todo` 在变基进行中就是 1.2 的同一个清单界面。

| 能力 | 面板做法 | 还要用户输入什么 | 风险 | 待核实 |
| --- | --- | --- | --- | --- |
| 不带 `-m` 的提交 | 提交区的标题加正文两栏，写临时文件后 `commit -F` | 标题、正文 | 说明为空白跑一趟；`#` 行是否被清理模式吃掉 | `-F` 时默认清理模式是不是 `whitespace` |
| `rebase -i` 待办清单 | 变基二级页的结构化清单，`GIT_SEQUENCE_EDITOR` 指向随包小程序 | 每条的动作、顺序、合并后的说明 | 所有对象号变化；已推送要强推；中途失败停在半路 | 消息文件路径；`squash` 时消息如何拼接；带空格路径的引号 |
| `config edit` | 配置页按作用域分组，行内改值，直接写键 | 键、值、写哪一层 | 丢注释与顺序；改全局影响全机；改到面板自己依赖的键 | 注释是否真的丢；`--worktree` 写哪层 |
| `branch --edit-description` | 分支详情里的多行文本框，写 `branch.<名>.description` | 一段说明文本 | 只存在本地配置里，换机器就没了 | 长度上限是否要拦 |
| `tag -a` 无说明 | 建标签浮层的说明两栏，`tag -a -F` | 标签名、目标、说明 | 签名失败；与远端同名标签冲突 | 空说明标签要不要一律拦 |

## 2. 任意命令类（4 条，全部有限定条件）

这一组的统一结论：**不给自由命令框。** 理由不是「做不到」——宿主当然能起任意参数的命令——而是 300–520 宽的面板里，一条自由命令输入框等于把「命令写错、路径写错、误删东西、跑到一半卡住」的全部风险原样搬进来，而预检对它什么都预测不了。

替代品是 0.3 里 E5 那条清单，落地形式是一个随包发布的小程序（和 1.2 的写入器放在同一个包里）：它按一个编号去插件配置里查一条登记过的检查，再用固定参数跑，不经 shell。这个小程序有两个用处——`git rebase --exec` 和 `git bisect run` 都只接受「一段命令」，我们就给它们一段**固定不变**的命令：`"<node 路径>" "<小程序路径>" <编号>`。参数里唯一可变的是编号，用户在界面上选的是「跑哪条检查」，不是「跑什么命令」。这条办法同时解决了两个问题：面板不用自己写变基和二分的主循环，git 原有的「失败停下、状态保留」语义也原样保留。

### 2.1 `submodule foreach`（有限定条件）

**界面**：子模块折叠区，每行一个子模块（路径、当前提交、有没有未提交改动、初没初始化），顶上是一个「对所有子模块…」菜单，选项固定四项：初始化并检出、逐个抓取、检出记录的提交、看每个的状态。**不使用 `foreach` 本身**——它的参数就是一段 shell 命令，正是这一组要避开的东西；宿主逐个跑等价命令，还能顺手把每个子模块的结果分开显示。

**交给 git**：宿主对每个子模块跑一条（`git -C <子模块路径> fetch` 这种），一行一个结果，失败不中断，最后汇总「5/6 成功，1 个失败」，失败那一行带「重试这一个」。子模块多的时候这就是个长任务，用 E3 的通道，进度是「第几个」。

**预检**：列出将动几个子模块、哪些还没初始化、哪些有未提交改动（有改动的默认跳过并说明）。

**确认**：只有「检出记录的提交」要二次确认（会丢子模块里的改动）；其余轻确认。

**失败怎么回显**：每个子模块的错误贴它自己那一行，保留 git 原话；旁边给「打开这个子模块目录」，方便接着看。

**结果**：折叠区每行状态更新，失败的行标出来。

**待核实**：`--recursive` 对嵌套子模块的顺序和深度；子模块地址要认证时走哪条通道（和主仓库不是同一个远端）；`.gitmodules` 里的地址被改过时以哪个为准。

### 2.2 `bisect run`（有限定条件）

**界面**：默认是手工二分。诊断页顶部常驻一条「二分进行中：还剩 3 步，当前 `a1b2c3d`」，四个按钮：这个版本是好的、是坏的、跳过、结束并回到起点。自动档在同一个地方多一个「每一步自动跑：<下拉，来自检查清单>」。

**交给 git**：手工档就是 `git bisect start` / `good` / `bad` / `skip` / `reset`。自动档是一条命令 `git bisect run "<node>" "<小程序>" <编号>`，由 git 自己逐轮检出、跑检查、推进；退出码 0 算好、125 算跳过、其余非零算坏。

**预检**：起点两个提交存在、工作区干净（自动档必须，git 每轮要检出，脏工作区会直接失败）、没有别的操作在进行、选中的检查上次跑了多久、大概还要几轮。

**确认**：自动档的确认卡写「每一步会切到哪个提交、跑哪条检查、它的退出码怎么算、最多跑 N 轮、随时可以停」。

**失败怎么回显**：检查超时算一次跳过并记一行；某一轮检出失败（子模块、权限）就停下给状态，不猜；检查自己崩了（找不到命令、退出码 127）要说「是检查没跑起来，不是这个提交坏」，否则会把好提交判成坏。

**结果**：诊断页给「第一个坏提交 `a1b2c3d` + 首行 + 作者时间」，旁边一个「在这里建分支」。`git bisect run` 的进度从标准错误里的「还剩几轮」解析，取消就是终止进程树，二分状态留在仓库里，下次打开还能接着手工做。

**待核实**：`bisect run` 在检查写工作区时会不会被下一轮检出挡住（大概率会，所以自动档只对「不写仓库内已跟踪文件」的检查开放）；`bisect reset` 之后原来那个分支要不要自动切回。

### 2.3 `rebase --exec`（有限定条件）

**界面**：不单开一个「每一步跑命令」的入口。变基确认卡里加一行可选「每一步之后跑：<检查清单里选一条>」，默认关。

**交给 git**：不用宿主自己写主循环，直接把 `exec "<node>" "<小程序>" <编号>` 写进待办清单，或者用 `--exec` 传同一段固定字符串。git 每应用完一条就调一次，失败就停在那一步、把变基状态留在仓库里——这正是 `--exec` 本来的语义，我们只是把「那段命令」换成了固定的一段。

**预检与确认**：和 1.2 合并，多一句「某一步检查失败会停在那一步，同时给继续、跳过这一步、中止三个按钮」。

**失败怎么回显**：停下之后把那一步的检查输出贴出来（截尾），并说明「变基没完成，仓库停在半路，可以继续也可以中止」。中止走已有的变基中止入口。

**结果**：诊断页逐步列出「第几条通过、第几条失败」。

**待核实**：`rebase --exec` 失败后 `rebase-merge` 目录是否一定保留（文档说会停，但要实测）；`exec` 行的输出会不会混进 git 自己的提示里。

### 2.4 `filter-branch` 的过滤器（有限定条件）

**结论**：**没有 filter-repo 就不给入口。** `filter-branch` 的四种过滤器（`--tree-filter`、`--index-filter`、`--msg-filter`、`--commit-filter`）参数全是 shell 命令；把它们藏进我们自己的模板里，等于把任意命令塞进面板，只是用户看不见——这既违背「不给自由命令框」的初衷，也违背仓库纪律里「不要在仓库里用 `git filter-branch`」那一条（AGENTS.md 明写）。本机实测只有 `git-filter-branch`，没有 `git-filter-repo`。

**有 filter-repo 时**：走 6.1 的结构化表单（删路径、重命名、改作者、删大文件、字面量替换），全部是参数，不是命令。

**没装时**：只给诊断——「这个仓库有 N 个大于 1 MB 的历史文件、M 条提交，要清理需要先装 filter-repo」，不提供任何「帮你跑一条命令」的按钮。

**预检、确认、结果**：见 6.1。

| 能力 | 面板做法 | 还要用户输入什么 | 风险 | 待核实 |
| --- | --- | --- | --- | --- |
| `submodule foreach` | 子模块区固定操作菜单，宿主逐个跑并逐行报结果 | 选哪个操作；失败后要不要重试那一个 | 有的子模块有未提交改动；地址要认证 | `--recursive` 的深度与顺序 |
| `bisect run` | 默认手工二分；自动档用固定小程序加检查编号 | 好提交、坏提交、选哪条检查 | 脏工作区；检查自己崩了被当成「坏」 | 检查写工作区时能否逐轮检出 |
| `rebase --exec` | 变基确认卡里的可选一项，固定小程序加检查编号 | 选哪条检查（默认不跑） | 失败停在半路，留下未完成的变基 | 失败后状态是否一定保留 |
| `filter-branch` 过滤器 | 没有 filter-repo 就只给诊断；有就走 6.1 的结构化表单 | 无（没装时什么都不能点） | 任意命令藏进模板；官方自己也劝改用 filter-repo | filter-repo 的安装检测方式 |

## 3. 文件选择器与长任务（5 条）

这一组是两件事：路径从哪来，长任务怎么活。

**路径**：不做系统文件选择器（理由见 0.3 的 E4），一律文本框加校验。校验分两段：失焦时给即时反馈（存在吗、是空目录吗、在仓库里吗），提交时宿主再校验一次——渲染层传来的字符串不可信。

**长任务**：`init` 是秒级；`clone`、`bundle`、`archive`、`format-patch` 可能几十秒到十几分钟。现在每条写命令一个固定超时（提交 60 秒、拉取 3 分钟），票据 120 秒只管预检新鲜度，两个都不是「任务租约」。这五条里真正需要任务通道（进度加取消）的是 `clone` 和 `bundle`，其余给一个放宽的超时加取消按钮就够。

还有一个容易踩的坑：git 的进度是画给终端看的，标准错误被管道接走时默认不输出。所以克隆、抓取这类命令要显式加 `--progress`，否则界面上只能看到「正在进行」，看不到百分比。

### 3.1 `init`（完全进面板）

**界面**：一个「新建仓库」二级页：路径输入（默认当前工作区）、初始分支名（默认读 `init.defaultBranch`，没有就 `main`）、裸仓库开关（默认关）。

**交给 git**：`git init [--bare] [--initial-branch=<名字>] <路径>`。`--initial-branch` 要 2.28 以上；更旧的版本退回 `git init <路径>` 再加 `git -C <路径> symbolic-ref HEAD refs/heads/<名字>`。

**预检**：目标已经是仓库就拒；目标在另一个仓库里面就拒（嵌套仓库几乎总是误操作）；目录里已有文件要说明「这些文件会显示成未跟踪，不会自动入库」；路径合不合法；父目录可写吗。

**确认**：轻确认，写明「只是建一个空仓库，不动目录里已有的文件；删掉 `.git` 就回到原状」。

**失败怎么回显**：权限、路径非法、磁盘满，git 原话加一句下一步。

**结果**：面板切到新仓库（顶部身份条换成新路径），历史是空的，改动页列出目录里已有的文件。

### 3.2 `clone`（有限定条件）

**界面**：「克隆」二级页：地址（网址或本地路径）、目标目录（默认 `<工作区>/<仓库名>`，仓库名从地址末段推）、浅克隆深度（默认关，开了要写清「历史不完整，之后的 log 和 blame 会缺东西」）、递归子模块（默认关，浅克隆加递归要同时开 `--shallow-submodules`）、分支（默认远端 HEAD）。

**交给 git**：`git clone --progress [--depth=<n>] [--recurse-submodules] <地址> <目录>`。进度从标准错误的 `Receiving objects: 45% (…/…)`、`Resolving deltas` 里解析。取消就是终止进程树，然后把半成品目录删掉（并告诉用户删了哪个路径）。

**预检**：目标路径不存在或为空目录（非空就拒）、父目录可写、地址形状像不像一个地址、磁盘空间够不够（能查就查，查不到就说查不到）。可选地先用 `git ls-remote` 探一次地址——要认证时会走 4.3 的通道，探不通只警告，不拦。

**确认**：写「从哪克隆到哪、大概要下载多少（不知道就说不知道）、完成后会切到这个仓库、网络断了会怎样」。

**失败怎么回显**：直接复用 #839 已有的一分档（要凭据、认证被拒、没权限、网络、卡住、超时），每一档本来就配了一句人话；超时之后要明确说「半成品目录已删」还是「保留在 <路径>，可以自己删」。

**结果**：顶部身份条切到新仓库，给「打开所在目录」。

**关于票据**：120 秒票据在这里只用来确认「目标路径没被别人占」，校验一次就够，克隆跑十分钟和票据无关。

### 3.3 `archive`（完全进面板）

**界面**：「导出快照」折叠区：格式（zip、tar、tar.gz）、引用（默认 HEAD，也能选分支、标签、提交号）、前缀（默认 `<仓库名>-<短号>/`）、输出路径（默认操作系统临时目录下的 `<仓库名>-<短号>.zip`，可以改）。

**交给 git**：`git archive --format=<格式> --prefix=<前缀> -o <文件> <对象号>`。**启动时先把引用解析成对象号**，之后只用对象号——导出期间分支被人切走，导出的也得是刚才说好的那一个提交。

**预检**：引用存在、格式和后缀一致、目标文件已存在要确认覆盖、目标目录可写、这个提交里有多少文件（`ls-tree` 数一下，大仓库这一步也可以跳过，别为了一个提示卡住）。

**确认**：轻确认，写明「导出的是某一个提交的快照，不含 `.git`，也不含未跟踪和被忽略的文件」。

**失败怎么回显**：磁盘满、格式不支持、路径不可写；失败时把已经写了一半的文件删掉，并说明删了。

**结果**：「已生成 <文件名>（大小）」加「打开所在目录」和「删除」。

### 3.4 `bundle`（有限定条件）

**界面**：「离线包」二级页，三件事：创建、校验、取回。创建选范围（全部引用、一条分支、某个提交之后）和输出路径；校验只读，告诉你这个包能不能在别的机器上完整恢复；取回是从这个包往当前仓库拿东西，要二次确认。

**交给 git**：创建 `git bundle create <文件> --all` 或 `git bundle create <文件> <范围>`；校验 `git bundle verify <文件>`；取回 `git bundle unbundle <文件>`（只写对象库、不改引用，相对安全）或 `git fetch <文件> <引用>`（会改引用，更危险的那一种）。

**预检**：范围内有多少引用、目标文件已存在要确认、磁盘空间；取回时先 verify 一次，缺前置提交就直接拦。

**确认**：创建轻确认；取回二次确认，写明「会把对象和引用写进这个仓库」。

**失败怎么回显**：最经典的一种是 `git bundle verify` 报「缺前置提交」，这时候要把原话贴出来并说清楚「先用另一个更早的包补上」；创建失败多半是磁盘和路径。

**结果**：文件行加校验结论（「能在空仓库里完整恢复」或「还缺 N 个提交」）。

### 3.5 `format-patch`（完全进面板）

**界面**：「导出补丁」折叠区：区间（默认 `<上游分支>..HEAD`）、输出目录（默认操作系统临时目录下的 `patches-<日期>/`，宿主先建好）、带编号（默认开）、封面信（默认关）。

**交给 git**：`git format-patch --output-directory <目录> <区间>`，需要时加 `--cover-letter`、`--numbered`。一个提交一个 `.patch` 文件。

**预检**：区间里有多少提交（`rev-list --count`），为零就禁用按钮；输出目录里有没有同名文件会被覆盖。

**确认**：轻确认，写明「一个提交一个补丁文件，放在临时目录，不写进仓库」。

**失败怎么回显**：区间无效、目录不可写、提交数太多（给个上限，比如 500，超了让人缩小范围）。

**结果**：文件数、前几个文件名、加「打开所在目录」。**不发邮件**——`send-email` 要 SMTP 和邮箱凭据，不属于这个页面。

| 能力 | 面板做法 | 还要用户输入什么 | 风险 | 待核实 |
| --- | --- | --- | --- | --- |
| `init` | 新建仓库二级页，路径加初始分支加裸库开关 | 路径、初始分支名 | 在已有仓库里再建一个，之后很难用 | `--initial-branch` 在 2.28 以下怎么降级 |
| `clone` | 克隆二级页，长任务通道带进度和取消 | 地址、目标目录、浅克隆深度 | 半成品目录；浅克隆让历史不完整 | 取消后目录清理的时机 |
| `archive` | 导出快照折叠区，启动时把引用钉成对象号 | 格式、引用、前缀、输出路径 | 大仓库导出慢；覆盖已有文件 | 各格式是否需要外部压缩程序 |
| `bundle` | 离线包二级页：创建、校验、取回 | 范围、文件路径、从哪个引用取回 | 取回会改对象库和引用；缺前置提交 | 按范围创建时引用写法的边界 |
| `format-patch` | 导出补丁折叠区，输出到临时目录 | 区间、输出目录、要不要封面信 | 提交太多生成一堆文件；覆盖同名文件 | 区间写成单个提交时的行为 |

## 4. 系统权限与密钥（3 条，全部有限定条件）

三条硬线，来自仓库日志纪律的硬红线（`docs/design/335-logging-contract.md`）：**凭据原文不进命令行参数、不落盘、不进日志。** 参数会被同机进程看到（任务管理器、`ps`），临时文件和配置文件会被备份与同步，日志会被导出。所以这一组的设计目标不是「把口令输进去」，而是「让 git 自己去问钥匙代理，面板只负责解锁一次」。

### 4.1 `maintenance start`（有限定条件）

先订正基础笔记的一句话。基础笔记写「装计划任务要管理员权限」，但 git 的官方文档里没有这句：文档说的是 Windows 上用 `schtasks` 提交任务，任务名是 `Git Maintenance (<频率>)`，默认以当前用户身份运行，并且因为 git 是控制台程序，这些任务会弹出控制台窗口；要改成「不管用户是否登录都运行」才需要输一次密码，所以 git 故意不选那一项。也就是说，这条能力不是「必须提权」，而是「可能因为机器策略失败」。面板照实回显即可，不主动提权（`待核实`：受限账户和域策略下 `schtasks` 具体报什么）。

**界面**：「仓库维护」折叠区，先是一段只读状态：这个仓库在不在维护名单里（`maintenance.repo`）、本仓库的自动维护有没有被关掉（`maintenance.auto`）、系统计划任务里有没有那三条（`schtasks /query /tn "Git Maintenance (hourly)"`，另有 daily 和 weekly）。下面是两个动作：开启、关闭；再下面是一个一次性动作「现在整理一次」。

**交给 git**：开启 `git maintenance start --scheduler=schtasks`；关闭 `git maintenance stop` 加 `git maintenance unregister`（`stop` 只是停调度，仓库还留在名单里，`unregister` 才把它移出去，两个要一起做才符合用户说的「关掉」）；一次性整理 `git maintenance run --task=gc`。只读判断还能用 `git maintenance is-needed` 的退出码（0 表示该整理了，1 表示不用）。

**预检**：git 版本（`maintenance` 要 2.30 以上，低了就只显示 `gc --auto` 的建议）；这个仓库在不在名单里；原来的 `maintenance.auto` 是什么值（`register` 会把它改成 `false`，关掉时要恢复吗——这属于要问用户的事，不能自作主张）。

**确认**：开启的确认卡必须写三件「会动仓库外面」的事：会往**用户全局配置**里加一条 `maintenance.repo`、会把本仓库的 `maintenance.auto` 设成 `false`、会在系统计划任务里注册三条以上任务（并且之后每小时会有一个控制台窗口一闪）。关闭的确认卡写「只停调度和名单，已经跑起来的进程不管」。

**失败怎么回显**：`schtasks` 拒绝（策略、权限）就贴原话，加一句「这台机器不允许注册计划任务，自动维护只能关着」；`git` 版本太低就直说；写全局配置失败要说清是哪个文件。

**结果**：折叠区状态行更新（在名单里 / 不在；三条任务在不在）。

**边界**：不写系统级配置、不碰别人的计划任务（只碰 `Git Maintenance (*)` 这三个名字）、不静默提权。

### 4.2 `credential-store`（有限定条件）

**结论先行**：面板**不写** `~/.git-credentials`。这不是做不到，是不该做——那个文件是可重放的明文口令，抄走就能用。

**界面**：「凭据」折叠区，只读三行：现在的凭据助手是什么（`credential.helper` 可能有多条，按顺序显示）、`~/.git-credentials` 在不在（在就标红，写「这里存着明文口令」）、这台机器有没有更安全的助手可用（Windows 上通常是 Git Credential Manager，或者内存缓存）。

**认证怎么走**：面板自己不做「记住密码」，走 4.3 的一次性通道，把这一次的用户名和口令交给**用户已经配好的**助手去处理（GCM、wincred、cache）。如果当前助手是 `store`，确认卡必须写「git 会把这次输入的口令以明文写进 `<路径>`」，并且要用户显式勾选才继续——写这个文件的是 git，不是面板。面板只给建议（换成 `manager` 或 `cache --timeout=…`），不自动改配置。

**预检**：这次要连的是哪个主机、当前助手链是什么、`store` 的话那个文件在不在、有没有设 `credential.helper` 的多条覆盖关系。

**确认**：写明「凭据交给谁、存在哪、谁能读」。

**失败怎么回显**：认证失败沿用 #839 的分档；助手配错（写了个不存在的助手）要单独说，别混成「认证失败」。

**日志**：只记主机名和助手名，绝不记用户名、口令、令牌。这一条是硬红线，写进规格。

**不做**：明文落盘这一形态不提供。这是主动划的边界，不是能力缺口——面板不帮用户把口令写成明文，也不假装替他记住了。

### 4.3 GPG / SSH 口令（有限定条件）

**SSH 这边**：面板给一个「解锁 SSH 钥匙」的动作。做法是 `ssh-add` 加 `SSH_ASKPASS` 指向一个小助手、`SSH_ASKPASS_REQUIRE=force`，口令经一次性环境变量传给它；成功后 `ssh-add -l` 能列出已加载的钥匙指纹。之后所有 git 网络命令继续用现有的非交互口径（`BatchMode=yes`，见 `src/refresh/rooms/host/gh-execution.ts:140-156`），不需要再问。如果这台机器的 ssh-agent 没起来，预检就说明，并给「怎么起代理」的说明。

**GPG 这边**：本机实测没有 `gpg` 命令，所以先探测；没有就只显示「这台机器没有签名程序」，签名相关的按钮一律不出现。有的话，面板先用 `gpg --pinentry-mode loopback --passphrase-fd 0`（口令从管道进，不进参数）做一次签名测试，让 `gpg-agent` 把口令缓存住，之后的 `git commit -S` 就不再问。硬件钥匙（OpenPGP 卡）的 PIN 可能只能由系统的 pinentry 弹窗输入，面板拿不到——这种情况如实说「这一步需要你在系统弹窗里输 PIN」（`待核实`：卡片 PIN 能不能走 loopback）。

**预检**：`gpg --list-secret-keys` 有几把、`user.signingkey` 指哪一把、`gpg-agent` 在不在、钥匙是不是卡片；`ssh-add -l` 当前有没有钥匙。

**确认**：写明「口令只在这一次调用里存在，不保存；缓存多久由 ssh-agent 和 gpg-agent 自己的配置决定」。

**失败怎么回显**：分三种——口令不对、钥匙没解锁、弹窗程序不可用。**任何情况下都不把口令写进错误文本**：错误信息里只出现「口令不正确」，不出现用户输入的内容。

**红线**：口令不进参数、不进临时文件、不进日志、不进错误对象；一次性环境变量在子进程结束后由宿主主动清掉。

**结果**：顶部身份条标「签名钥匙已解锁（还剩 N 分钟）」或「SSH 钥匙已加载 N 把」。

| 能力 | 面板做法 | 还要用户输入什么 | 风险 | 待核实 |
| --- | --- | --- | --- | --- |
| `maintenance start` | 维护折叠区：只读状态加开启/关闭加一次性整理 | 确认会写全局配置和计划任务 | 改的是仓库外面的东西；可能被机器策略拒绝 | 受限账户下 `schtasks` 的报错；关掉后要不要恢复 `maintenance.auto` |
| `credential-store` | 只读凭据状态，认证走一次性通道交给已有助手 | 用户名、口令（只这一次）；选用哪个助手 | 明文落盘；用户以为面板记住了其实没记 | 没有助手时怎么办（见开放问题） |
| GPG / SSH 口令 | 一次性解锁钥匙，之后靠代理缓存 | 口令（只这一次） | 口令外泄；硬件钥匙的 PIN 拿不到 | GPG 缓存是否真能被后续签名复用；卡片 PIN 能否 loopback |

## 5. 外部图形工具（4 条：3 条完全进面板，mergetool 有限定条件）

统一结论：**不启动外部窗口。** 原型定下的「面板内闭环」不是排版偏好——一旦开了 `gitk` 或 `mergetool`，交互就跑到另一个进程里，面板既看不到结果也接不住失败，只能等一个退出码。这一组里「外部工具能做的事」面板都有自己的形态；面板缺的只是「熟悉感」，那不该用打开另一个窗口来补。能给的只剩「装没装、配的是哪个」这种只读信息。

### 5.1 `gitk`（完全进面板）

**界面**：历史页自己画。提交列表加分支与标签的装饰，加一个简单的分叉图：520 宽下留三列（主链、分叉、合并），超过两条并行链就退化成纯列表加「合并提交」标记——300 宽时本来也只能这样。`gitk` 那边值得学的是筛选（按文件、按作者、按提交说明搜索），面板做成历史页顶部的筛选器。

**不启动的理由**：`gitk` 的全部价值是「看历史」，而看历史所需的数据面板已经全有了（同一个 `git log --graph` 的数据源）；启动它只会把交互搬走。

**结果**：没有任何「启动结果」要回显，因为它不启动。只读信息里可以加一行「这台机器装了 gitk」，纯说明。

**待核实**：300 宽下分叉图到底值不值得画（列会挤成两三个字符宽），还是干脆只画「这条提交在第几条并行线上」。

### 5.2 `git gui` / `citool`（完全进面板）

**界面**：不需要新界面。`git gui` 的三块——暂存、提交、分支——面板都已经有了，`citool` 只是它的「只提交」子集。唯一 `git gui` 有、面板没有的是逐块暂存，那在能力矩阵里是 1.2，不属于本票。

**结论**：这一条在设计上就是「已有界面覆盖」，写进规格时作为对照说明，不新增入口。

### 5.3 `mergetool`（有限定条件）

**界面**：冲突文件行点开「解决」二级页。520 宽放不下三栏，所以用**冲突块列表**：每一块显示「我们这边」和「他们那边」两段（各带行号，以及各自来自哪个提交），四个按钮：保留这边、保留那边、两边都要、手动改。手动改用面板内的等宽文本框，带行号，可以直接编辑整份文件。

**交给 git**：块的内容从 `git show :1:<路径>`（共同祖先）、`:2:`（我们这边）、`:3:`（他们那边）读，或者直接解析工作区里带冲突标记的文件。用户保存之后写回工作区，再用 `git add <路径>` 标记为已解决。

**非文本冲突**：二进制文件、子模块、文件模式冲突、一边删一边改，只能「整份选一边」或「保留删除」，确认卡要写清会丢什么。非 UTF-8 的文件也只能整份选一边，并说明原因（面板按 UTF-8 读写，别的编码写回去会坏）。

**预检**：这个文件是不是文本、多大（超过 2 MB 不建议在面板里改）、换行是 CRLF 还是 LF（写回要保持原样）、还有几块没解决。

**确认**：保存到文件是写操作，轻确认；「整份选一边」对二进制和子模块要确认。

**失败怎么回显**：保存后跑 `git diff --check` 查残留的冲突标记（`<<<<<<<`），有就拦下来并指出行号；写文件失败要说清是权限还是编码。

**结果**：冲突文件行从「冲突」移回「已暂存」，计数减一。

**待核实**：大文件与超长行的渲染；CRLF 文件写回后 git 会不会认为整份都改了（换行被统一）；三方合并里「共同祖先」这一份要不要显示（520 宽只够两栏）。

### 5.4 `difftool`（完全进面板）

**界面**：面板自己的 diff 视图：统一 diff、词级高亮、可折叠。并排视图在 520 宽下左右各 260，正文根本放不下，所以不做并排，只在宽屏档位（如果有）才考虑。二进制文件只显示「二进制文件，大小从 A 变成 B」。

**交给 git**：读类命令，`git diff` 与 `git show`，不写。

**结论**：`difftool` 的「启动一个外部比较器」不需要，因为它比较的东西面板已经在显示；它比面板多的是「并排看图」和「任意两个文件比」，前者在 300–520 宽不成立，后者可以做成「选两个引用比」的只读页，但那属于 diff 视图的增强，不是这一条。

| 能力 | 面板做法 | 还要用户输入什么 | 风险 | 待核实 |
| --- | --- | --- | --- | --- |
| `gitk` | 历史页自己画列表、装饰、简单分叉图 | 筛选条件（文件、作者、关键词） | 分叉多时列太挤，图反而更难读 | 300 宽下的画法 |
| `git gui` / `citool` | 已有界面覆盖，不新增入口 | 无 | 逐块暂存不在本票范围，别让人以为漏了 | 无 |
| `mergetool` | 冲突块列表，逐块选边或手动改，保存后 `git add` | 每一块选哪边；手动改时的文本 | 非文本冲突只能整份选边；编码与换行 | 大文件、CRLF、共同祖先要不要显示 |
| `difftool` | 面板内的统一 diff 加词级高亮 | 无（只读） | 并排视图在窄面板不成立 | 无 |

## 6. 全库重写（5 条：replace 完全进面板，其余 4 条有限定条件）

统一三件事：**先备份、再二次确认、失败给恢复路径。**

**备份**：执行前 `git clone --mirror <仓库> <仓库>-backup-<时间>`，或者 `git bundle create --all`。备份路径必须写进确认卡（就在按钮上方，不是折叠在说明里），结果里给「打开备份目录」。恢复不自动做——自动恢复是第二次全库重写，错上加错，只给说明。

**二次确认**：让人输入仓库目录名才能点（像删仓库那样），不是勾一个「我知道了」。这一类动作改的是全部历史，勾选框挡不住手滑。

**失败**：每一步都把「改到哪了」写清楚，并指回备份。

这一类要不要干脆只做只读诊断？我的判断：`filter-repo` 的结构化子集（删路径、重命名、改作者、删大文件、字面量替换）值得做，因为「把误提交的大文件或密钥从历史里清掉」是真实需求，参数有限、可以预演；`filter-branch`、把 `fast-import` 用到现有仓库、`svn dcommit` 不值得做，因为它们的失败模式面板讲不清楚。

### 6.1 `filter-branch` / `filter-repo`（有限定条件）

**结论**：`filter-branch` 不提供入口（理由见 2.4）。有 `git filter-repo` 时，把它包成五个结构化表单，每个表单对应一组固定参数，绝不拼 shell：

1. 删除路径：`--path <路径> --invert-paths`。
2. 重命名路径：`--path-rename <旧>:<新>`。
3. 按邮箱改写作者：`--mailmap <生成的文件>`（filter-repo 的选项名以它自己的 `--help` 为准，`待核实`），面板把「旧邮箱 → 新名字与新邮箱」写成 mailmap 文件。
4. 删除大文件：`--strip-blobs-bigger-than <大小>`。
5. 字面量文本替换：`--replace-text <生成的文件>`，只接受「原文 → 替换成」，不接受正则、不接受回调代码。

每个表单都要先显示「会改写多少条提交、涉及多少个引用」，这个数从 `rev-list --count --all` 和 `for-each-ref` 拿，不用预演也知道量级。

**交给 git**：就是上面这些参数，加 `--force`（filter-repo 默认拒绝在「不是新鲜克隆」的仓库上跑，`--force` 是它的官方逃生口，但要不要用是预检里要问的）。本机没有这个命令，所以先检测：装了才出现入口，没装就只给诊断。

**备份**：见本节开头。备份放在仓库同级目录，名字带时间；磁盘不够时改用 bundle（开放问题 10）。

**预检**：仓库干不干净（有未提交改动先让人处理）、有几个远端（filter-repo 会重写远端引用配置）、有没有正在进行的操作、备份盘空间、filter-repo 版本。

**确认**：输入仓库目录名；写明「所有对象号都会变、远端要重新推、别人手里的克隆会分叉、旧提交只有备份里有」。

**失败怎么回显**：filter-repo 中断会留下半改的引用，读 `.git/filter-repo/commit-map` 数一下改了多少条，把「改了多少、停在哪、备份在哪」三件事一起说，然后给「打开备份目录」。

**结果**：历史整段替换，顶部提示「N 条提交被改写」；`refs/original` 之类的残留要不要清，单独说明。

**待核实**：filter-repo 拒绝运行的准确条件（未提交改动？不是新鲜克隆？多个远端？）；`--force` 的副作用；Windows 上的路径与换行问题。

### 6.2 `fast-export`（有限定条件）

**界面**：「导出历史流」折叠区：输出路径（默认临时目录下的 `<仓库名>-<日期>.export`），说明一句「这是一个文本流，不是 git 仓库，用来搬迁或备份」。

**交给 git**：`git fast-export --all`，宿主把标准输出边读边写进文件（不经过 shell 重定向）。大仓库的流可能有几百 MB，所以不能先读进内存再写盘——这一条要求宿主能把子进程的输出流式落盘（见 8.4）。

**预检**：引用数、输出文件已存在要确认、磁盘空间。

**确认**：轻确认，但要写清「流里含全部提交与文件内容，别当普通文本发出去」（可能含密钥历史）。

**失败怎么回显**：磁盘满、中途被杀，都要说清「写到哪个文件、是不是完整的」。

**结果**：文件行加大小，「打开所在目录」。

### 6.3 `fast-import`（有限定条件）

**界面**：「导入历史流」二级页：选择一个 `.export` 文件、选一个**新的空目录**，说明一句「只会导入到一个新仓库，不会往当前仓库里塞」。

**交给 git**：`git init <目录>`，再在 <目录> 里 `git fast-import`，标准输入接那个文件。这里需要宿主给子进程接一个「标准输入来自文件」的能力——现在标准输入是关掉的，`-F` 那套办法在这里用不上，因为 `fast-import` 只认标准输入。

**预检**：目标目录不存在或为空、文件头几行像不像 fast-import 的流（`blob`、`commit`、`mark` 这些关键字）、文件多大、磁盘空间。

**确认**：二次确认，写明「新仓库建在哪、会得到多少引用、原来的仓库一动不动」。

**失败怎么回显**：流格式错误（`fatal: Unsupported command`）贴原话并指到行号；失败后目标仓库是删掉还是留着让人看，要明确说。

**结果**：切到新仓库，或者给「打开所在目录」。

**待核实**：失败后目标仓库能不能直接重跑；`--done` 这类选项要不要暴露。

### 6.4 `replace`（完全进面板）

**界面**：诊断页里的「替换对象」折叠区：列出当前所有替换（`git replace -l`，每行显示被替换的对象和替换成的对象）、一个「新建替换」表单（选被替换对象，再从历史里选替换成哪个）、一个「按父提交改写」的单独表单（`--graft`）、每行的删除按钮。

**交给 git**：`git replace -l` 读、`git replace <旧> <新>` 建、`git replace -d <对象>` 删、`git replace --graft <提交> <父提交…>` 改写父提交。

**必须写在界面上的话**：「替换只影响这台机器上读这个仓库的结果，不随推送和抓取传播；别人看到的还是原来的历史。要让别人也看到，得显式推 `refs/replace/*`，本页面不做。」

**预检**：两个对象都存在、类型一致（类型不一致要 `-f`，面板不给这个开关）、`refs/replace/<对象号>` 是不是已经存在。

**确认**：轻确认（删除就恢复），但要写清「从现在起历史看起来会不一样，包括 diff 和 blame」。

**失败怎么回显**：对象不存在、类型不匹配，git 原话。

**结果**：折叠区多一行或删一行，历史页立即按替换后的结果显示。

### 6.5 `svn` 桥（有限定条件）

本机实测没有 `svn` 命令，但 `git help -a` 里能看到 `svn` 子命令——也就是说命令在，客户端和环境不一定在。所以这一条先探测再决定界面。

**能做的**：检测（`git svn --version` 能不能跑、仓库里有没有 `.git/svn` 目录）、只读信息（`git svn info`：对应的 svn 地址、版本号、分支布局）、如果是 svn 克隆就给「抓取一次」（`git svn fetch`，长任务，可能很慢）和一句说明。

**不做的**：`git svn dcommit`（把 git 提交写回 svn，双向写、失败模式复杂）、`git svn clone` 入口（一次性的迁移动作，不是这个页面的事）。

**不是 svn 克隆的仓库**：只给一句「要从 Subversion 迁移，需要 svn 客户端和一次长时间的抓取，用专门的迁移工具做」，不出现任何按钮。

**预检**：svn 命令在不在、`.git/svn` 在不在、上次抓取时间。

**确认**：抓取是只读仓库内容、但会跑很久，轻确认加进度。

**失败怎么回显**：svn 认证失败、uuid 变化、部分抓取，各说各的；抓取失败不影响已有提交。

**结果**：只读信息里多一行「上次抓取：<时间>」。

### 8.2 真正无解的清单

**为空。**

不是「暂时没想到办法」。这条前提把原来看起来无解的地方拆成了两部分：一部分靠宿主补几行代码就通了，另一部分本来就该主动拒绝，不算能力缺口。

第一，**宿主能起子进程，这就把「参数怎么给」的障碍整个拿掉了**。git 的每条命令都只要三样东西：参数列表、标准输入、工作目录。宿主现在给得了参数和工作目录，标准输入关着（`src/host/versionControl.ts:113-119`），改这一层就是几行代码。现在只有六个写命令，那是「还没接」，不是「接不上」。

第二，**git 的每个「打开编辑器」都有文件旁路**。`-F` 送提交说明和标签说明，`GIT_SEQUENCE_EDITOR` 送待办清单，`git config <键> <值>` 绕开 `--edit`，`--passphrase-fd` 送口令。没有哪一个入口是「只能交互输入」的。

第三，**长任务、权限、口令三件事都有受控通道**：任务通道管进度和取消；系统权限那条如实回显拒绝，够用；口令走一次性环境变量加代理缓存。没有一件需要「打开一个终端窗口」。

剩下的三类是「不做」，不是「做不到」，而且它们的位置各不相同：明文凭据落盘在 26 条里（4.2 明确拒绝）、启动外部图形窗口也在 26 条里（第 5 组拒绝）、平台五条不在 26 条里（#1586 的 C 组不做）。把它们写成「无解」会让人以为面板有天花板，实际上是主动划的边界，两者的后续处理完全不同——前者要等上游，后者只要改主意。

还有一句要写在明处：如果版本底线继续停在 2.11，`maintenance`（2.30 起）和 `init --initial-branch`（2.28 起）会降级成只读或走降级路径，但没有一条会因此变成无解。

### 8.3 必须由用户拍板的开放问题

**Q1 版本底线要不要从 git 2.11 提到 2.30？** 2.11 是现在的 `VERSION_FLOOR`（`src/shared/version-control/src/capabilities.ts:11`）。提到 2.30 能拿到 `maintenance`；2.28 能拿到 `init --initial-branch`；2.26 能拿到 `config --show-scope`；2.38 能拿到 `rebase --update-refs`。不提高就要给 `maintenance` 和 `init` 各写一条降级分支，代码量和测试面都涨。我的建议：提到 2.30，更旧的机器把这两件事降级为只读加提示。

**Q2 `rebase -i` 这次做到哪一档？** 只做「改说明 + 丢弃 + 调顺序」，还是连 `squash` / `fixup` 一起？后者的麻烦在「合并后的说明」要按组编辑，而且 git 给的消息是几条拼在一起的一整段，匹配逻辑要多写一层。我的建议：第一期做「改说明、丢弃、调顺序」，`squash` 第二期。

**Q3 随包发布两个小程序，还是用系统自带的命令凑？** 一个是把源文件覆盖到 git 指定路径的「写入器」，一个是按编号跑登记的检查的「运行器」。不发布的话，`GIT_SEQUENCE_EDITOR` 只能写成 `cp` 或 `copy` 加一堆引号，Windows 与 POSIX 行为还不一样。我的建议：发布，几十行 Node 脚本，和插件一起装。

**Q4 长任务做成通用任务通道，还是每个动作各写一套？** 通用通道要动现在那层执行出口（#839 那一带），影响面大；各写一套则是四份重复的进度解析和取消逻辑。我的建议：通用，但先只服务 `clone` 和 `bundle` 两个动作，跑顺了再铺开。

**Q5 检查清单从哪发现？** 先只认 `package.json` 的 scripts 加用户自存一条，还是也认 `Makefile` 的 target 和 `justfile` 的 recipe？后者要写解析器，而解析 Makefile 基本等于写半个 make。我的建议：第一期只认 `package.json` 加自存，别的以后按需加。

**Q6 没装 filter-repo 的机器上要不要给一条「生成的命令」？** 比如把 `--index-filter 'git rm --cached --ignore-unmatch <路径>'` 拼好显示出来，让用户自己复制去跑。这与「面板内闭环」直接冲突。我的建议：不给。只给诊断和「需要 filter-repo」的说明。

**Q7 本机没有任何凭据助手时，认证怎么走？** 每次手输（面板内闭环，但烦），还是引导用户去装一个助手（一次性设置，但要离开面板）？我的建议：面板内手输作为兜底，同时给「装助手」的说明；装助手是一次性环境准备，不算日常 git 操作，但这条要在 #1586 里写清楚，别让人以为面板偷偷依赖终端。

**Q8 要不要为 `credential.helper=store` 的用户提供「我就是要明文存」？** 我的建议：不提供。面板只如实告知「git 会把口令明文写进这个文件」。

**Q9 `svn` 桥只做只读加抓取，还是也给 `clone` 和 `dcommit`？** 我的建议：只做只读加抓取。`dcommit` 是双向写，失败模式面板讲不清。

**Q10 全库重写的备份用 `clone --mirror` 还是 `bundle`？** mirror 恢复最直接（就是一份完整仓库），但占一整份磁盘；bundle 是单文件、好搬，但恢复要两步。我的建议：默认 mirror，磁盘不够时自动降级成 bundle，并在确认卡上写清用的是哪种。

**Q11 配置页能改哪些键？** 任意键（能力强，但改坏 `core.hooksPath`、`credential.helper` 这种键会让面板自己失灵），还是白名单加只读（安全，但「有些事又只能终端做」）？我的建议：分组放行——常用键可改，会改面板自己行为的键只读并给说明；不搞一刀切白名单。

**待核实汇总**（这些不影响结论方向，但会影响规格里的一句文案或一个分支）：

1. `commit.cleanup` 被用户改成 `strip` 时，以 `#` 开头的行会不会被吃掉（1.1）。
2. `reword` 时 git 给的消息文件到底是哪个路径；`squash` 时几条说明怎么拼接；仓库路径带空格时小程序收到的参数有没有正确加引号（1.2）。
3. `git config` 重写配置文件时会不会丢注释与顺序（1.3）。
4. `--worktree` 写进哪一层配置（1.3）。
5. `rebase --exec` 失败后变基状态是否一定保留（2.3）。
6. `bisect run` 遇到会写工作区的检查时，下一轮检出会不会失败（2.2）。
7. filter-repo 拒绝运行的准确条件，以及 `--force` 的副作用（6.1）。
8. 取消克隆后，半成品目录该立刻删还是留给人看（3.2）。
9. GPG 的口令缓存能不能被后续 `git commit -S` 复用；硬件钥匙的 PIN 能不能走 loopback（4.3）。
10. CRLF 文件在面板里保存后，git 会不会认为整份都改了（5.3）。
11. 受限账户或域策略下，`schtasks` 注册维护任务具体报什么错（4.1）。
