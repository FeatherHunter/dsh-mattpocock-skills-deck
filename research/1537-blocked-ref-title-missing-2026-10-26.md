# #1537 分流诊断：详情页「被阻塞」引用缺目标标题（2026-10-26）

调查范围：本票正文与三张截图、详情读路径与本地 Markdown 后端读路径的源码、契约层 Issue 形状、客户端详情渲染、既有 research 笔记；另在临时目录搭了一个最小的本地 Markdown 工作区跑探针确认（跑完即删，未进仓库）。未改业务代码、未开始实施。

## 结论

- 这是 **bug**，不是增强：契约要求阻塞引用带标题，界面按契约在有标题时显示标题、没有才回落成编号；本地 Markdown 后端的详情读路径没有把引用标题补上，客户端只能显示编号。
- 触发面是 **Local Markdown 后端**的详情页；GitHub 后端不受影响（它的详情查询本身就把标题取回来了），所以截图里的现象不是「所有后端都这样」。
- 这是一次**回归**，不是一直如此：#1444（提交 e31124e1，2026-10-24）把刷新后台的详情读路径从「get + getDependencies」改成「只调 get」之后才出现。Markdown 后端的 get 一直没有回填引用标题，之前靠依赖查询兜住；换了路径，兜底那一步没了。
- 本票没有任何实施痕迹：没有提交、没有评论、没有实施记录；仓内也没有针对这条缺口的门禁。
- 建议类别与状态：**bug + ready-for-agent**；按 /tdd 先补一扇会红的回归门禁再修。

## 复现与探针读数

在临时目录搭了一个最小工作区，`.scratch/ticket-convention/` 下放四张被引票（03「中文5处」、04「英文4处」、05「对账加微信」、08「源头定稿」）和 12 号票，12 号票正文写 `Blocked by: 03, 04, 05, 08`。

用 `createMarkdownBackend(ctx)` 直接调契约操作，读数：

| 操作 | blockedBy 引用的形状 |
| --- | --- |
| `get('12')` | 4 条，全部 `{ title: '', state: 'open' }` |
| `list` 中同一张票 | 4 条，标题都有，state 是被引票真实状态 |
| `getDependencies` | 4 条，标题都有，state 正确 |

这与截图完全吻合：4 行只显示 #3 #4 #5 #8，没有标题。界面的回落写法不是缺陷，是契约允许的兜底（`title || '#' + number`）。

## 证据链（按数据流）

1. **详情电话**：刷新后台的详情处理函数只调一次后端 `get`，并原样把 `blockedBy` 映射进详情响应（保留 `title: b.title || ''`）；`blocking` 恒为空。注释写的是「Markdown 的 get 已包含」，但「包含引用」不等于「包含标题」。
2. **本地 Markdown 后端的 get**：正文解析器遇到 `Blocked by:` 或隐藏标记 `DSH-BLOCKED-BY` 时，只产出 `{ key, title: '', state: 'open' }`；`getIssue` 在解析并切评论之后直接返回，**没有**像同文件 `listIssues` 那样按被引票回填标题与状态。`listIssues` 的注释明写着「A: 回填 blockedBy 的 title/state」，用 `idOfParts(effortId, key)` 建索引后补标题、补状态。
3. **同一个后端的依赖查询**：`getDependencies` 会读被引票文件回填标题与状态，所以它有标题。
4. **GitHub 后端**：详情查询片段自带 `blockedBy(first:50){nodes{number title state}}`，归一化时填标题，所以 GitHub 详情不缺标题。
5. **客户端**：详情页只读 `blockedBy` 渲染，每行 `b.title || ('#' + b.number)`，悬停提示与行文字同一回落；客户端没有读 `blocking`，也没有拼后端专属逻辑。契约层 `IssueRef` 是「key/title/state 的轻量引用」，`Issue.blockedBy` 用它，界面这样消费是对的。

## 为什么只发生在本地 Markdown 后端

截图票的正文里有 `DSH-BLOCKED-BY` 隐藏标记，这个标记只有本地 Markdown 后端会写、会读（写票、改正文、解析三处都在 Markdown 房间）；GitHub 房间只认 `DSH-ISSUE-KIND`，不写 blocked-by 标记。加上截图编号带 `ticket-convention/` 目录前缀，而 GitHub 后端的 effort 恒为空串、编号不会带目录，可以确认截图来自 Local Markdown 工作区。上一轮分诊写的「当前工作区后端为 GitHub，需报告人确认」应作废，不必再问报告人。

## 修复方向对比

- **A（推荐）本地 Markdown 后端的 get 回填引用标题与状态**：把 `listIssues` 已有的那一步搬进 `getIssue`，或抽成两处共用的小函数；预算不变，详情仍然只读一次；同 effort 与跨 effort 的索引口径与 list 完全一致；引用目标读不到时保留编号、标题留空，界面继续回落。这个后端的依赖查询里已经有一份「读被引文件补 title/state」的实现可参考。
- **B 详情电话层补一次依赖查询（或改回旧实现）**：能修，但每次打开详情多一次查询/多读一批文件，正是 #1444 想省掉的那一步；而且治标不治本——get 的形状仍然缺标题，别的调用方还会踩。
- **C 客户端从快照行合并标题**：违背「界面只消费契约产物、不感知后端」的分层约定，且快照不保证含这条引用；只能当兜底，不能当修复。

## 附带发现

1. **同一个后端的 get 与 list 对同一字段填充不一致**：list 回填引用标题与状态，get 不回填。这不是两层各自为政，而是同一契约操作返回同一形状时口径漂了。修 get 时建议同一条门禁断言「同一张票在 get 与 list 下 blockedBy 引用形状一致」，否则以后还会漂。
2. **注释与事实不符**：详情电话里那句「Markdown 的 get 已包含」写错了——包含的是引用，不是标题；修的时候顺手改掉，免得下一个人照注释判断。
3. **卡片层已经能做对**：#1401 已让 V2 卡片的「挡路封条」画出编号+标题（列表/快照通道有标题）。缺的只是详情这条读路径，不是渲染能力。
