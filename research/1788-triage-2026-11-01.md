## 一句话结论

问题成立，但票面说的根因不是根因。**真正的缺陷**是：写侧 `ticketFormOf` 只用文件文字推断票种（`original-fields.ts:94-106`），不看票所在目录属于哪条路线，也不看可见 `Status` 取值属于 triage 角色还是 wayfinder 状态；落到 `map-ticket` 或 `legacy` 分支的**手写实施票**被认领时都会改写 triage 状态。用 feature 目录（同目录有 `spec.md`）里的最小手写票（`# 任意标题` + `Status: needs-triage`，符合随包 `issue-tracker-local.md:9-10` 对实施票的全部要求）实测：认领后变成 `Status: claimed` + 可见 `Assignees:`，回执 `ok: true` 无提醒；带加粗字段的对照票一字不动。**票面口径要修正的两点**：`# <NN>: <标题>` 与加粗字段来自 `to-tickets/SKILL.md:69-82` 模板，`issue-tracker-local.md` 只规定文件名与 `Status` 行；裸 `Type:` 只出现在地图子票章节（`issue-tracker-local.md:26`）。所以票面举的形状 A 是混合形状，不能当作「手写实施票的自然形状」。另外「认领只改认领人」对确认的地图子票不成立（原文 `issue-tracker-local.md:29` 的 claim 就是写 `Status: claimed`），正确规则是按路线分开。旧布局只读闸让 `legacy` 写分支没有合法的旧路径目标（旧路径写模式被拒，新路径手写票按真源 `original-skills.yaml:223-225` 的 plain-when-unknown 应算普通票），这是「保留旧行为」不能成立的原因。

## 根因链

1. 读侧把「编号标题 + 裸 Type 行」当成地图子票的充分条件（original-fields.ts:99-103）。这两个信号都不足以区分：随包 to-tickets/SKILL.md:69-82 的实施票模板本身就写 `# <NN>: <Ticket title>`；裸 Type 行也是地图子票原文（issue-tracker-local.md:26）要求写的字段。
2. 同仓写侧口径相反：create-render.ts:70-73、:80-82 注明明说「普通票的 type 可以随手写 task，与地图子票的类型词同名，没有专用通道时不能据此改渲染形状，一律按普通票走新布局」，读侧却拿同样的信号判子票。
3. 认领写路径按判定结果分三支（issues-patch.ts:331-345）：map-ticket 在有认领人时 `replaceBareField(Status, claimed)`；impl-ticket 只写隐藏 DSH-ASSIGNEES、可见加粗 Status 原样；legacy 写可见 `Status: claimed` + `Assignees:`。前两支都会覆盖 triage 状态。
4. 因此「裸 Type 判据」只是触发路径之一；凡最终被判成 map 或 legacy 的手写票，认领都会静默改状态。形状 E 实测证明这一点。这与 ADR 20261025 决定四（使用者按技能原文手写的文件能被列出、读、改、完成，缺插件信息时按内容推断）冲突：手写票要能被安全地认领，就不能靠一条弱信号改它的状态。
5. 连带缺陷：original-fields.ts:103 的标题正则只认第 0 行（没有 m 标志）；upsertHiddenComment 第一次写隐藏注释时插到第 0 行（:120-122、:142-145）。于是认领一次之后，同一张票从头部的 `# 01:` 再判会落到 legacy，之后的关闭、改 Blocked by、改父票全部改走 legacy 分支（实测关闭写出可见 `Status: resolved` + `Close reason`，不写 ## Answer、不写加粗 Status）。
6. 状态值本身没有纠错：`claimed` 不在实施票的两档状态里（ready-for-agent / resolved），读侧的 closedSet 只认 resolved / completed / closed / done，所以被覆盖的 triage 状态在 API 侧也读不出来，用户更难发现问题。

### 关键探针：feature 目录里的三种票（仓库外临时工作区，已删）

同一个临时 feature 目录（`createIssue` 建了 `spec.md`）里放三张票：

1. **无编号手写票**（文件名 `02-无编号手写票.md`，正文 `# 手写实施票` + `Status: needs-triage` + `## Comments`，没有 Type、没有加粗字段）：`setAssigneesIssue` 回 `ok: true`；文件被改成可见 `Status: claimed` 与 `Assignees: someone`，回执无 message / warning。这是**符合 `issue-tracker-local.md:9-10` 的最小实施票**，说明不需要裸 Type、也不需要编号标题就能触发覆盖。
2. **加粗字段对照票**（`# 03: 加粗手写票` + `**What to build:**` 等三行 + `**Status:** ready-for-agent`）：只新增 `<!-- DSH-ASSIGNEES: someone -->`，可见 `**Status:** ready-for-agent` 一字不动。impl 分支本身是对的。
3. **真正的地图子票**（deck 建：`map.md` + `issues/`、DSH-FORMAT / DSH-PARENT、`Type: research`、`## Question`）：认领后新增 `<!-- DSH-ASSIGNEES: someone -->` 与可见 `Status: claimed`，与原文 Claim 语义一致。

### 同一份文件，读侧与写侧说法不同

- 读侧 `parse.ts:240-244` 能读到 `Status: claimed`，但只把它归到 open / closed 两态；`parse.ts:349-364` 对形状 A / 无编号手写票都返回 `type: issue`，父票按目录推断为 `00`。
- 写侧 `issues-patch.ts:331` / `issues-status.ts:179` / `:269` 却用 `ticketFormOf` 的文字结论，把同一张票分到 `map-ticket` 或 `legacy`。
- 也就是说：**同一张票，读的时候是「feature 目录下的普通票」，写的时候是「地图子票 / 旧布局票」**。这不是启发式精度问题，是读写两侧对票种的定义不一致。

### 真源与门禁都支持「按路线判」而不是「按裸 Type 判」

- `original-skills.yaml:219-222` 的 layout-discovery：含 `spec.md` 或 `issues/` 的目录算 feature 目录（规格路线），含 `map.md` 的目录算探索地图目录；`:223-225` 的 fallbacks 还规定「没有 DSH-PARENT 时按所在目录判断父容器」「编号或父容器识别不了时按普通票读，不抛错」。
- `original-skills.yaml:164-168` 把 triage 角色（needs-triage / needs-info / ready-for-agent / ready-for-human / wontfix）与 wayfinder 状态（claimed / resolved）分成两套，注释明确「保持这两个集合不混用」；`tests/verify-md-format-config.ts:148` 还有一条坏数据演练：把 claimed 塞进 triage-roles 必须判红。认领把 triage 状态改写成 claimed，正是真源与门禁都禁止的混用。
- `issues-locate.ts:61-73` 的旧布局只读闸按路径判：旧扁平路径写模式在 `:354-358` 被直接拒绝。因此 `ticketFormOf` 的 legacy 写分支没有合法的旧路径目标；它实际打中的只能是新路径下手写、且前面判据都认不出的票——按 `plain-when-unknown`，这些票应当算普通票，而不是「旧布局票」。

### 根因（复核后写法）

1. 写侧票种推断只看文件文字，不看目录路线，也不看可见 Status 属于哪一套状态词。
2. 「legacy」是文件形状，不是布局；旧布局已经只读，新路径手写票又没有理由按旧布局写，于是 legacy 分支成了一个只对合法新票生效的错误分支。
3. 认领把「记认领人」与「地图子票的 claim 状态」绑在同一个动作里，而判据无法可靠区分两者，导致 triage 状态被覆盖。
4. 标题正则只认第 0 行（没有 m 标志）会让认领插入的隐藏注释把同一张票从 map 掉成 legacy；但修法不是把隐藏注释挪到 H1 之后（`original-skills.yaml:173-212` 与 `create-render.ts:250-284` 都要求插件注释在第一个可见标题之前），而是让标题识别只看第一个 H1。
5. 关闭 / 重开对「只有裸 Status 的手写实施票」也没有按字段样式写：impl 分支的 replaceBoldField 找不到加粗行时会什么都不改；路线修好后需要一并处理，否则关闭会显示成功但状态不动（分析，未实测）。

### 修法修订：目录路线优先，文字只做兜底

前文的 R（「编号标题 + triage 状态 ⇒ impl」）仍可作为最小文本修法，但它修不了「没有 Status 行的 feature 目录手写票」，也不解决读写下定义不一致。复核后推荐：

1. **写入口先定路线**：由票文件所在目录调 `workUnitKindOf`（`issues-locate.ts:113-119`；已有 `appendMapDecisionPointer` 用同目录 `map.md` 判身份的先例，`issues-status.ts:218-220`）。`map` 路线 → 地图子票语义；`spec` / `plain` 路线 → 实施 / 普通票语义。
2. **按路线分认领**：`map` 路线保留 claim = `Status: claimed`（原文如此），同时写隐藏 DSH-ASSIGNEES；`spec` / `plain` 路线认领**只写隐藏 DSH-ASSIGNEES，绝不改可见 Status**。
3. **文字判据降为路线内校验与兜底**：加粗字段 / DSH-FORMAT / `## Question` / wayfinder 标签用来确认格式细节；裸 Type 不再有把 feature 路线票提升成地图子票的权力。
4. **按字段样式写状态**：有加粗 `**Status:**` 就写加粗行；只有裸 `Status:` 就写裸行（`issue-tracker-local.md:10` 的原文形态）；不要一次写出两行状态。
5. **标题识别只看第一个 H1**，不要给 `^` 正则加 m 去扫全文（代码块里的示例标题会误伤）；隐藏注释位置保持原样。
6. **门禁调整**：`tests/verify-1489-claim-labels.ts:213-227` 的夹具在 `.scratch/demo/issues/` 且同目录有 `map.md`，按路线应判地图子票；`:223` 的 claimed 断言保留，`:224` 的可见 `Assignees:` 断言要改成隐藏注释（需 Q2 拍板）。新增 feature 目录无编号手写票、只有裸 Status 的关闭 / 重开、认领前后票种稳定三条夹具。

### 前文需要撤回或收窄的说法

1. 「认领会改写任何没有插件标记的手写票的状态」→ 收窄为「认领会改写被判成 map-ticket 或 legacy 的手写票的状态；最确定的受害者是 feature 目录里只有可见 Status 行的手写实施票」。
2. Q3 原推荐里的「隐藏注释插到 H1 之后」→ 撤回，改为「标题识别只看第一个 H1，隐藏注释保持第一个可见标题之前」。
3. 「票面期望 2（认领只改认领人）」→ 不适用于确认的地图子票，见 Q2。
4. 修法推荐里的 R 降为最小文本修法备选，首选目录路线优先。
