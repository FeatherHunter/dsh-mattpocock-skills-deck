## 根因链

1. 读侧把「编号标题 + 裸 Type 行」当成地图子票的充分条件（original-fields.ts:99-103）。这两个信号都不足以区分：随包 to-tickets/SKILL.md:69-82 的实施票模板本身就写 `# <NN>: <Ticket title>`；裸 Type 行也是地图子票原文（issue-tracker-local.md:26）要求写的字段。
2. 同仓写侧口径相反：create-render.ts:70-73、:80-82 注明明说「普通票的 type 可以随手写 task，与地图子票的类型词同名，没有专用通道时不能据此改渲染形状，一律按普通票走新布局」，读侧却拿同样的信号判子票。
3. 认领写路径按判定结果分三支（issues-patch.ts:331-345）：map-ticket 在有认领人时 `replaceBareField(Status, claimed)`；impl-ticket 只写隐藏 DSH-ASSIGNEES、可见加粗 Status 原样；legacy 写可见 `Status: claimed` + `Assignees:`。前两支都会覆盖 triage 状态。
4. 因此「裸 Type 判据」只是触发路径之一；凡最终被判成 map 或 legacy 的手写票，认领都会静默改状态。形状 E 实测证明这一点。这与 ADR 20261025 决定四（使用者按技能原文手写的文件能被列出、读、改、完成，缺插件信息时按内容推断）冲突：手写票要能被安全地认领，就不能靠一条弱信号改它的状态。
5. 连带缺陷：original-fields.ts:103 的标题正则只认第 0 行（没有 m 标志）；upsertHiddenComment 第一次写隐藏注释时插到第 0 行（:120-122、:142-145）。于是认领一次之后，同一张票从头部的 `# 01:` 再判会落到 legacy，之后的关闭、改 Blocked by、改父票全部改走 legacy 分支（实测关闭写出可见 `Status: resolved` + `Close reason`，不写 ## Answer、不写加粗 Status）。
6. 状态值本身没有纠错：`claimed` 不在实施票的两档状态里（ready-for-agent / resolved），读侧的 closedSet 只认 resolved / completed / closed / done，所以被覆盖的 triage 状态在 API 侧也读不出来，用户更难发现问题。
