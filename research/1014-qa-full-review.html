写在前面：五条第一性原理

十二问里凡是「第一性原理」那一段，指的都是这五条。它们不是口号，是每一问都能对上的判据：

  1. 一份手写真源。文件清单、产物、依赖方向、测试名册这些「能算出来」的东西，一律不许手写维护——手写的第二份一定会和第一份漂移。
  2. 检查要能被看见。不阻塞发布的检查等于文档；并且扫到的输入集合为空时必须判红——换轨期最大的假绿来源就是「改名之后扫不到文件，于是判绿」。
  3. 过渡期必须有刻度。凡「过渡期先这样」都要配一把只降不升的尺子，否则过渡期没有终点。
  4. 两张网各有分工。终态的质量上限由编译器给，过渡期的下限由门禁给；两张网各有交接点，交接点要写死，否则会长期两套并存。
  5. 三条物理事实。Node 跑不了 .ts（要靠装载钩子）；宿主逐文件加载产物（因为有动态 import，不能打成一个文件）；客户端闭包由 esbuild 从逐文件产物拼出来。

Q1 · 验收证据算哪一条

已定稿：乙对抗式审查后改过

问题

地图 01 的「做完的标志」是「随手写一个 .ts，一条命令就能被构建、被测试、被类型检查、被门禁看见」。这句话要用什么证据证明它真的成立了？

问题的背景

  • 今天没有任何东西能证明这条线是通的：全仓 348 个手写 .js、46 个 .ts，.ts 只在客户端像素系列与四个核两条窄路上被转译过。
  • 门禁体系是 231 条 tests/verify-*.js 串成的一条链（scripts/verify-chain.js 切链执行、首红即停），单条实测 211 毫秒。
  • 冷构建约 30 秒（两遍 esbuild 各约 14.5 秒）；发布门禁 scripts/publish-token.ps1 本来就是「先 build、再 test」。
  • 票面规矩里有一句维护者的话：「我排斥门禁」。

每个候选答案的优点与缺点

选项做法优点缺点
甲新增一条自检门禁：临时造一个 .ts 走完整条线（快段进默认链，慢段搭发布门禁的车）证据最强，连「故意写错会红」都能证明；边界清楚它本身就是一条新门禁，与「我排斥门禁」正面冲突；要往源码树写临时文件，清理失败就污染仓库；慢段要把 30 秒冷构建再跑一遍
乙真挑一个文件转成 .ts 留在仓库里当活样板，构建、类型检查、测试三关都会经过它零新增门禁；真实存在、长期有效；任何人随手改一行就能验证只能证明「走得通」，不能证明「故意写错会红」
丙只在文档里写一句「已人工验证通过」零成本没有任何可核对的证据，等于没有验收

我当时给的推荐答案

甲加强版：快段（临时 .ts 走同一条转译函数、断言产物落位、tsc 看见、装载钩子能 import）进默认链；慢段（完整构建往返的正反两面）搭发布门禁的车。

对抗式审查之后改成什么

  • 临时文件会污染源码树 → 加「唯一文件名 + try/finally 清理 + 结束断言该路径 git status --porcelain 为空 + 目录进扫描排除表」。
  • 慢段重复跑 30 秒冷构建太慢 → 改成两段式，只有发布门禁那次跑完整往返。
  • 更根本的一击来自维护者：「我排斥门禁」——甲这个选项整体被否掉，改乙。
  • 补一条约束：活样板必须落在第一个新域上（也就是 src/shared/<功能名>/ 这类域目录），否则它证明不了 Q5 里「域 tsconfig 用目录通配收集」这条保证。

从第一性原理出发

  • 公理二（检查要能被看见）：证据必须是一条命令就能跑出来、失败会拦人。乙满足「能被看见」，而且是零维护的看见；甲多付的是一份永久维护税。
  • 公理三（过渡期有刻度）：这里需要的刻度就是「这条活样板从今天一直存在到 13 号收口」，它天然只增不减。
最终定稿（维护者表态）：乙。作废「新增自检门禁」，改真挑一个文件转成 .ts 留在仓库当活样板；代价如实写清——不能证明「故意写错会红」。活样板落在第一个新域上。

Q2 · 引用方向拿什么管

已定稿：乙对抗式审查后改过

问题

「谁也不能引用谁」这条方向规则，过渡期用什么来管？最终又交给谁？

问题的背景

  • docs/adr/20261011-deck-ts-rewrite.md §5 的原话要求：按域拆 TypeScript 工程引用（deck 引用 tracker、tracker 引用内核，引用只能朝下，写反编译不过，方向由编译器保证不用人肉门禁），并且「今天约三十个按路径文本断言的旧门禁换成标准依赖检查工具（禁循环、禁跨层深引用、单文件行数上限），工具换成社区的」。
  • 今天撑着同类规则的两条老门禁都只读 .js 文本：tests/verify-no-same-layer-import.js（四层内部禁互引）、tests/verify-no-cross-import.js（三房禁跨房）。.ts 对它们是空窗。
  • 实测（TypeScript 7.0.2 与 5.6.3 都一致）：朝上引用报 error TS6059: File ... is not under 'rootDir' 与 TS6307: File ... is not listed within the file list of project；根配置 files: [] ＋ 若干 noEmit（不带 composite）的域配置能通过且真在检查，只有域与域之间真有 import 链、被引用那方是 noEmit 时才报 error TS6310: Referenced project '…/b' may not disable emit。

每个候选答案的优点与缺点

选项做法优点缺点
甲自写一条依赖图门禁（用仓内已有的 typescript-ast 解析 import，管方向、禁循环、禁跨层深引）零新增依赖；规则可以按本仓口径定制；一次性能替掉两条老门禁等于再造一条门禁，与「我排斥门禁」和 ADR 的「换成社区的」都冲突；动态 import、别名、.ts 说明符这些细节都要自己维护
乙引社区标准工具 dependency-cruiser，方向表、禁循环、禁跨层深引白名单全部写在它的配置里社区标准（评论记 npm 当前 18.6.0，自述支持 JS 与 TS）；同时看 .js 与 .ts；一次替掉两条老门禁；规则即配置新增一条开发依赖；要学它的规则写法；终态要拆掉「方向」那部分
丙直接上 TypeScript 工程引用，方向全交给编译器终态最强：编译器保证，不用人肉门禁今天走不通（域间真有引用链时报 TS6310，除非每个域真产出）；而且它管不了工程内的深引用

我当时给的推荐答案

丙分阶段：过渡期先自写工具管三条规则，终态（12 号收口后）上工程引用，上线即删工具里的方向规则。

对抗式审查之后改成什么

  • 「自写门禁」与「我排斥门禁」、与 ADR §5.4「换成社区的」两处都冲突 → 过渡期改乙。
  • 「分阶段」有变成两套长期并存的风险 → 写死触发条件与「上线即删」，做成一张真票挂 13 号收口图（后来按维护者确认，这类事「未来肯定会有 ISSUE」）。
  • 划清各自永久管什么：方向终态归编译器；禁循环与禁跨层深引永远归工具——编译器只能保证「不许引用没被 references 的域」，管不了工程内的深引用。

从第一性原理出发

  • 公理四（两张网分工）：终态的质量上限交给编译器，过渡期的下限交给现成工具，交接点写死；不要把「过渡期工具」和「终态编译器」当成二选一。
  • 公理一（一份真源）：方向表写在工具的配置里，不要另写一份文档再靠人对照。
最终定稿：乙。过渡期用 dependency-cruiser 管方向、禁循环、禁跨层深引，一次替掉两条老门禁且同时覆盖 .js 与 .ts；终态上工程引用后删掉工具里的方向规则，禁循环与深引永远归工具。两处前置随 Q1–Q12 一并认可：① 新增开发依赖 dependency-cruiser；② 非字面量动态 import 沿用老门禁口径「一律算违规」。

Q3 · 混存期 .ts 引用 .js 怎么办

已定稿：甲对抗式审查后加过刻度

问题

源码从 .js 慢慢转成 .ts 的这段时间里，新写的 .ts 一定会引用到还没转的 .js。类型检查该怎么面对这种引用？

问题的背景

  • 存量：src/ 下手写合计 348 个 .js、46 个 .ts（含 4 个 .d.ts），另有 73 个生成 .js；四个核 src/ 下另有 35 个 .ts。
  • 转换顺序是自上而下按改写单元推进的，所以第一个 .ts 出现时，它引用的下层几乎必然还是 .js。
  • 实测代价：allowJs 关闭时报 error TS7016: Could not find a declaration file for module './b.js'；allowJs:true ＋ checkJs:false 能通过，但对 .js 的调用是不检查的 any（把字符串传进一个读 x.n 的 .js 函数，tsc 报绿）；checkJs:true 会让 .js 里的老写法当场变红。
  • 仓内已有「只降不升」基线的先例：tests/file-granularity-baseline.json（note 原话「零增长基线：只许减不许增；达标文件由各自拆分票移出」）、tests/same-layer-baseline.json（每条带 owner），判定逻辑在 tests/verify-file-granularity.js:97-109。

每个候选答案的优点与缺点

选项做法优点缺点
甲allowJs:true ＋ checkJs:false 开闸，配两把只降不升的棘轮，重要缝手写 .d.ts 顶到转换完成迁移能按已定顺序自上而下推进；代价被量出来、看得见开了一个永久后门（这类开关一旦打开就容易忘记关），必须靠棘轮把它关回去
乙不开 allowJs，要求 .ts 只引用 .ts类型最干净，没有过渡期后门与已定的自上而下顺序物理冲突：第一张 .ts 就会撞上它引用的 .js
丙给 348 个 .js 各写一份 .d.ts类型上最完整等于造第二份真源，一定会漂移；而且是 348 份的工作量

我当时给的推荐答案

甲 ＋ 棘轮：基线＝「.ts 直接 import 的 .js 边数」与「手写 .js 文件数」，只降不升，基线外新增 .js 判红。

对抗式审查之后改成什么

  • 只说「棘轮」不够：必须同时数两样——文件数与边数。只数文件数，「一个 .ts 引 20 个 .js」这种情形量不出来；只数边数，新加一个没人引的 .js 又看不见。
  • 派生 .js（从已装上游包原样拷来的 src/host/logPkg/*）要按目录排除，单独进排除表——这条后来由 Q10 从根上解决（改成常规依赖）。

从第一性原理出发

  • 公理三（过渡期有刻度）：过渡期允许将就，但必须有一把只降不升的尺子，否则没有终点。
  • 公理一（一份真源）：丙被否掉的理由就是它造了第二份真源。
最终定稿：甲 ＋ 两把棘轮（.ts 直接 import 的 .js 边数、手写 .js 文件数），只降不升、基线入库，规则与先例同一套做法。终态三样全消失：allowJs 关掉、基线清零、手写 .d.ts 删光。

Q4 · 入库的产物要不要清、落点定在哪

已定稿：乙（不单独成票，并入 01）对抗式审查后补齐

问题

今天有一批构建产物被提交进了版本库。要不要把它们请出去？请出去之后，机器写的文件允许出现在哪几个地方？

问题的背景

  • 「产物不入库」今天只做了一半：.gitignore 忽略了 /client.js、/host.js、/package/lib/、/package/scripts/、/scripts/generated/updateEntryPanel.bundle.js，但没忽略 /package/shared/。
  • 实际在库的产物有三处：package/shared 79 个 .js（构建把 src/shared 整树原样拷过来，scripts/build.mjs:847）；像素风同名 .js 34 个（cards 16、pixel 8、skillDetail 7、views 1、kernel 2）；四个核转译出的 35 个 .js（label-color 3、refresh 14、version-control 14、config-store 4，落在 src/shared/<核名>/）。另有 3 个手写 .js 混在同一批目录里，不在此列。
  • 为「入库的产物」养着四条新鲜度门禁（tests/verify-{label-color,refresh,version-control,config-store}-freshness.js，做法是重新转译一遍再逐字比对），加上 tests/verify-build-artifacts.js:132-155 的 package/shared ↔ src/shared 逐文件 sha256 双向比对，加上 scripts/build.mjs:867-874 的「package/lib/index.js 与 src/host/index.js 逐字节一致」。
  • 维护者原话：「不用单独成票，我们先把这个想法给敲定」。

每个候选答案的优点与缺点

选项做法优点缺点
甲只清 package/shared 这一处动作最小，风险最低像素风与四核产物继续「与真源并排同名」，13 号核「手写 .js 归零」时仍然分不清哪个是产物
乙三处一起清 ＋ 落点收敛 ＋ src/ 下不再生成 .js（四个核的输出目录跟着改）＋ 守门对象换成守「允许的那几类之外没有产物」一次消掉「第二真源」和四条门禁；规则从此可机械核对动作大：跨四个核的构建脚本，上百条读双源产物的门禁要跟着改
丙保持入库，继续靠门禁守零动作那份永久税继续交，而且产物与真源越久越容易漂

我当时给的推荐答案

乙：三处一起清（git rm --cached 只动索引、文件留在盘上），落点收敛，src/ 下不再生成 .js，守门对象改写，四条 freshness 门禁删掉。超 01 原边界，建议单独立票。

对抗式审查之后改成什么

  • 「只落三处」这句话不完备：实测产物散落八处（根 client.js/host.js、package/lib、package/shared、scripts/generated、src/host/logPkg、像素风 34 个、四核 35 个、packages/*/dist）→ 交给 Q9 补成四类并逐类点名。
  • 「把 src/host/logPkg 挪出 src/」这个候选被证据推翻（src/host/logFromPackage.js:11 是相对动态 import，而 src/ 里的模块又被测试直接 import）→ 交给 Q10，最后改成常规依赖。
  • 「删四条 freshness 门禁」有前置条件：删完之后「产物与真源一致」就只剩「构建刚跑过」一个支点 → 交给 Q11。
  • 维护者把归属也一并定了：不单独成票，并进 01。

从第一性原理出发

  • 公理一（一份真源）：入库的产物就是第二份真源，不是「多一份保险」。
  • 公理三（过渡期有刻度）：拆保险之前必须先建保证——这就是 Q11 被绑批的原因。
最终定稿：乙，并入 01 号地图、不单独立票；配套三处交给 Q9（四类落点与逐类点名）、Q10（logPkg 改常规依赖）、Q11（先建保证再删四条 freshness）。执行时守单一写者：单独工作线、单独一次提交。

Q5 · 新写的 .ts 怎么被构建与类型检查「看见」

已定稿：乙（结构性保证）对抗式审查后删掉门禁

问题

新加一个 .ts 文件，构建要收到它、tsc 要检查它。今天靠人手工登记，怎么改成不会漏？

问题的背景

  • 今天有两处手工登记：tsconfig 的 include，和 scripts/build.mjs 里的清单（KERNEL_MODULES 约 60 项 :466、SHARED_SPLICE 13 项 :567、LEAF_MODULES 约 120 项 :604、像素系列的 PX_TS_DIRS 5 个目录 :1035）。
  • AGENTS.md 要求「新增 .ts 要同步登记 tsconfig 的 include 与 scripts/build.mjs 清单（不登记会静默不编译）」——两处手写登记，必然漏一处。
  • 活证：src/client/kernel/locale-cards.ts 被构建的目录扫描转译成了 .js，但 tsconfig.client.json 的 include（:24）只列了 locale-skilldetail.ts——它从没被 tsc 检查过。

每个候选答案的优点与缺点

选项做法优点缺点
甲域 tsconfig 用目录通配收集 ＋ 构建按目录扫描 ＋ 再加一条「不漏不重」门禁漏登记有专门的报错又多一条门禁；而且「不漏不重」的判断本身要有第二份清单，隐含第二真源
乙三层结构性保证：域 tsconfig 的 include 一律目录通配；构建按目录扫描收集 .ts；一个文件只属于一个域目录。兜底写进构建脚本本身（某域扫到 0 个文件就让构建失败）零门禁；结构上不可能漏；兜底就在必经之路上漏登记没有专门报错（症状是产物缺文件或测试加载失败）；新开一个域目录要在域清单加一行
丙维持逐文件登记无已被 locale-cards.ts 证伪

我当时给的推荐答案

甲：目录通配 ＋ 一条「不漏不重」门禁对齐三者。

对抗式审查之后改成什么

  • 维护者「我排斥门禁」→ 改乙，删掉「不漏不重」那条门禁。
  • 补两条兜底：① 域目录重叠今天没人管（中间期靠构建启动断言，重复归属等工程引用上线后由编译器兜住）；② 空集合必须判红——这条原则后来落成 Q11 的第 ③ 项。

Q6 · 测试怎么跑 .ts、旧的 231 条怎么办

已定稿：A对抗式审查后钉死 Node 下限

问题

测试要能直接跑 .ts，而且要不引新框架、不改生产产物链路。选哪条路？旧的两百多条门禁怎么办？

问题的背景

  • 现状：tests/ 里 283 个 verify-*.js，挂进 npm run verify 长串的是 231 条（那一行 8639 字符、超过 cmd.exe 的 8191 上限，所以由 scripts/verify-chain.js 切链执行、首红即停）。
  • 底数：全仓 175 处「按路径拼 URL 再动态 import」，171 个文件用了动态 import(、127 个用了 pathToFileURL；CJS 相对 require 只有 7 处，且都不指向产品源码——反例是 tests/verify-subdir-first-frame.js:170 的 require(path.join(root,'src/shared/tracker/guide-steps.js'))。
  • 本机 Node v24.19.0 实测：node --test 默认发现并运行 .test.ts；node a.test.ts 能直接跑；但 Node 不做 .js→.ts 映射——import './b.js' 而磁盘只有 b.ts 会 exit 1。
  • 原生剥离不支持 enum、带运行时代码的 namespace、参数属性、装饰器（全仓扫描目前一处都没有）。
  • 关键一条：本仓两条发布产物都是逐文件被同名加载的（src/host → package/lib，四个核 → package/shared），esbuild 逐文件转译会原样保留说明符。

每个候选答案的优点与缺点

选项做法优点缺点
A源码统一写 ./x.js 说明符 ＋ 自写约三十行装载钩子（同名 .ts 存在就加载 .ts，否则 .js）零新增依赖；生产产物链路零改动；产物里的说明符天然正确自造的钩子有 Node 版本风险 → 必须写死下限并让钩子自带测试
B源码说明符改写成 ./x.ts，靠 Node 原生解析一行自造代码都不用写把风险搬到发布产物（两条逐文件加载链会去 import 一个不存在的 .ts）；丢掉原生不支持的几样语法
C引进 vitest／jest 之类的成熟框架生态成熟、断言好写要把 231 条重写一遍；与「不引新测试框架」的口径冲突

我当时给的推荐答案

A ＋ 棘轮（旧条目按条迁移、未迁移数只降不升）。维护者原话：「A.」，并说「如果 node 能直接跑 ts 会降低我们项目的复杂度。Q6 那个如果有变动需要告诉我，你可以调查」。

对抗式审查之后改成什么

  • 我去查了「Node 能不能自己搞定」：能跑 .ts，但不做 .js→.ts 映射——这一条把 B 否掉了，不是偏好问题。
  • 原先打算用异步 module.register() → 实测它对 CJS 的 require('./x.js') 无效，必须用同步 module.registerHooks()（Node 22.15+）→ 由此定下 Q7 的下限，并要求钩子自带测试。
  • 明确钩子优先级：同名 .ts 优先于 .js（否则产物与真源同名并存时会读到错的）。
  • 默认串行：现有门禁里有动夹具、动 git 索引、占端口的，并行会互相踩。

从第一性原理出发

  • 公理五（三条物理事实）直接决定了形状：Node 跑不了 .ts、产物逐文件加载、闭包由 esbuild 从逐文件产物拼出。
  • 最小改动面：能不碰生产链路就不碰——这正是 A 胜过 B 的地方。
最终定稿：A。四条细则一并定下：同名 .ts 优先于 .js；旧 231 条按条迁移、未迁移数只降不升；默认串行；13 号清空那条长串；新测试一律写成 .ts。

选项做法优点缺点

从第一性原理出发

Q8 · 类型检查怎么挂进流程

已定稿：甲对抗式审查后更正一处

问题

类型检查今天分散在四处被顺手拉起、没有一条统一入口。要不要新增一条 npm run typecheck？它挂在哪、怎么防止「绿而没检查」？

问题的背景

  • 今天谁在跑 tsc：客户端 ← scripts/build.mjs:1089；契约 ← tests/verify-contract-types.js:61,275；四个核 ← 各自 build.mjs 与四条 freshness 门禁。

  • 活证：locale-cards.ts 的配置在、文件没进——「配置存在」不等于「真在检查」。

每个候选答案的优点与缺点

选项做法优点缺点

我当时给的推荐答案

甲：新增 npm run typecheck，用 glob 发现全部 tsconfig 并断言份数与编译文件数达到下限。

对抗式审查之后改成什么

  • 更正一处讲过头的话：不是「composite ＋ noEmit 被 tsc -b 引用必报 TS6310」——根 files: [] ＋ references 若干 noEmit（不带 composite）的域配置能通过且真检查（往域里塞类型错误会报 TS2322、exit 1）；只有域间真有 import 链且被引用方 noEmit 时才报 TS6310（7.0.2 与 5.6.3 都报）。

  • 公理一（一份真源）：靠 glob 发现配置，不写域清单。
最终定稿六条：① 新增 npm run typecheck → node scripts/typecheck.mjs；② 脚本做三件事——按目录发现全部 tsconfig（排除 node_modules）、逐份 tsc -p（非 0 即失败、输出原样透出）、断言「每份至少 1 个文件」且「总数 ≥ 只升不降的基线」；③ 今天不用 tsc -b（tsbuildinfo 落点未定，留给 13 号）；④ 挂进 npm test 第一段，发布门禁自动覆盖，不进 231 条长串；⑤ 构建里那次 tsc 保持原样；⑥ 坚持「一个域一份 tsconfig、逐份跑」。它管不到的：方向与禁循环归 dependency-cruiser；.js 的检查深度由 allowJs／checkJs 决定。验收：随手往任一域目录加一个 .ts、不改配置就能被看见；把某份配置的 include 指向空目录立刻红。

问题

产物出库之后，今天那批「产物与源码一致」的检查就全没了。是先把新的保证建起来再删旧的，还是分两票、先删后建？

问题的背景

  • 今天这件事由三条互不相干的检查撑着：① 四条新鲜度门禁（重新转译一遍再逐字比对）；② tests/verify-build-artifacts.js:132-155 的 package/shared ↔ src/shared 逐文件 sha256 双向比对；③ scripts/build.mjs:867-874 的「package/lib/index.js 与 src/host/index.js 逐字节一致」。
  • 产物出库、源码变 .ts 之后，②③ 物理上做不到，① 按 Q4 要删。删完之后只剩「构建刚跑过，所以产物一定是新的」——而它全押在手写的 INPUT_ROOTS（scripts/build.mjs:103）与 INPUT_EXTRA（:104）上，指纹算法在 :172-177。
  • 另有一条旧检查有洞：scripts/build.mjs:748-768 反向扫「有没有没登记进 LEAF_MODULES 的叶子文件」，今天只认 .js、只扫四个写死的目录，外层 try/catch（:766-768）只放行以 [build] 开头的错、其余吞掉——目录不存在就变成空集合，静默判绿。

每个候选答案的优点与缺点

选项做法优点缺点
甲四件事同批：输入集合自动发现；构建启动断言；修那条反向检查；以上到位后再删四条 freshness保证与删除同步；能用两个反例当场演示「保证真的在」01 里多约 10–30 行构建改动
乙分两票：先删旧保险，新保证另立一票每票都小删在前就有一段真空期；反过来说先建后删，新方案会长期挂着没人收尾
丙只删门禁、不建保证零改动等于把保险拆了不装新的

我当时给的推荐答案

甲：把输入集合结构化并加断言，然后才删四条 freshness。

对抗式审查之后改成什么

  • 我原先把它当成「一条门禁的取舍」，实际上它是今天唯一的产物新鲜度依据——于是从「可以顺手做」升级为发布安全的前置条件。
  • 「空集合判红」从一个原则落成具体一项：今天那条反向检查吞异常（静默绿），必须改成域清单驱动 ＋ 显式报数 ＋ 空集合判红。
  • 归属定清：落在 01 号地图内、不新开票、不新增门禁脚本、与 Q4 耦合、执行时守单一写者。

从第一性原理出发

  • 公理三（过渡期有刻度）：删掉旧的刻度之前，新的刻度必须先立起来。
  • 公理二（空集合判红）：一条「扫不到东西就判绿」的检查不是检查。
最终定稿：甲（四件同批）。① 输入集合改成自动发现（src、scripts 两棵固定大树 ＋ 凡含 tsconfig 的顶层目录自动发现 ＋ 所有 tsconfig 文件本身）；② 构建启动加断言（输入集合不许为空；每个域目录至少收到 1 个输入）；③ 修 scripts/build.mjs:748-768 那条反向检查（域清单驱动 ＋ 显式报数 ＋ 空集合判红）；④ 以上到位后删四条新鲜度门禁。两个验收反例：改动某个域目录里的一个文件，构建指纹必变；把一个叶子文件转成 .ts 之后，反向检查仍报数、仍判红。顺带回答「纯 TS 项目会不会遇到手写输入清单」：会遇到「增量构建靠什么判据」的问题，但纯 tsc 项目由 include／.tsbuildinfo 管、打包器从配置与真实依赖图推、monorepo 任务运行器只声明每包的通配；本仓手写是因为自建了内容指纹缓存；「结构化」不等于「零声明」——package.json 这类非 TS 输入永远存在。

Q12 · 四个核的源码放哪、引用怎么办

已定稿：甲记录内部有一处矛盾待拍

问题

四个核的 .ts 源码今天在顶层 <名>-core/src/，产物写到 src/shared/<名>/。要不要把源码搬进 src/shared/<功能名>/？搬了之后那几十处引用怎么办？

问题的背景

  • 四个核各自「src/**.ts ＋ 自己的 tsconfig.json ＋ 自己的 build.mjs」，产物写到 src/shared/<核名>/：label-color-core/build.mjs:30 → src/shared/label-color；refresh-core/build.mjs:38 → src/shared/refresh；version-control-core/build.mjs:27 → src/shared/version-control；config-store-core/build.mjs:28 → src/shared/config-store。
  • src/host 下几十处 import 直指这些产物：src/host/configStore.js:18-20、src/host/refresh/gate.js:21-24、src/host/versionControl.js:17-24、src/host/tracker/backends/markdown/label-colors-codec.js:14-15；测试里也有直接 import 源码模块的（tests/verify-969-tiered-timeout.js:69）。
  • 根构建今天只会把 src/shared 整树 cpSync 到 package/shared（scripts/build.mjs:847），并不会转译；装载钩子只按「同名」映射，跨不了目录。
  • 维护者确认：目录名要改成「符合这个核的功能的规范命名」，而且「那句『不用单独成票』只覆盖产物出库与落点」——这类事未来肯定会有 ISSUE。

每个候选答案的优点与缺点

选项做法优点缺点
甲源码搬进 src/shared/<功能名>/*.ts（与现在的产物目录同名同位置），顶层核目录退场，产物由根构建统一转译到 package/shared；引用点一个字不改「源码只有 .ts」「src/ 下没有生成物」「引用不改」三条同时成立；装载钩子按同名规则自然生效35 个 .ts 挪位置、顶层四个目录删除、四份 tsconfig 跟着搬
乙源码留顶层，产物搬走，装载钩子加四条「核名 → 产物路径」映射改动最小src/ 里出现一张手写的映射表（第二真源，迟早漂移）
丙源码留顶层，只搬产物，映射另记一笔看似折中源码树里 import 的路径当场失效，本地跑不动
丁移出 01，另立一票01 更瘦与「Q4 并入 01」的取向冲突；1019「目录归位」会被反复绊住

我当时给的推荐答案

甲：源码搬进 src/shared/<功能名>/*.ts，顶层四个 <名>-core/ 退场。

对抗式审查之后改成什么

  • 我原以为「产物在 src/shared、源码在顶层核目录」是既有折中、动了风险大；实测 src/host 几十处 import 直指那些产物、而装载钩子只按同名映射 → 甲是唯一能让「引用不改 ＋ src/ 无生成物」同时成立的形状。
  • 我提问的层次错了：真正的问题是「01 的边界要不要多一条核管线」——根构建今天只会整树拷贝，不会转译。
  • 有一处是我们反过来向四个核学：域目录自带 tsconfig.json，比在根目录集中式登记更自描述，成为本次的默认形状。
  • 我发现记录内部一处矛盾：第二节第 5 条说「四份 build.mjs 删、四份 tsconfig.json 移进域目录、四条 verify-*-freshness.js 删」，第四节又说「四个核子构建的存废（未来肯定会有 ISSUE）」——两句必居其一，落盘时写死。

从第一性原理出发

  • 公理一（一份真源、一棵树）：源码与它的产物不该分住两棵树。
  • 公理五（物理事实）：装载钩子只按同名映射 —— 形状由这条事实决定，不由喜好决定。
最终定稿：甲 ＋ 八条。① 顶层四个 <名>-core/ 目录退场；② 命名按功能，本次沿用现有四个功能名（label-color、refresh、version-control、config-store），日后换更准确的名字另立一票（代价是同时改几十处引用、产物路径与 scripts/build.mjs:586-596 那 4 条闭包拼接项）；③ 引用点一个字不改；④ 产物由根构建统一转译到 package/shared/<功能名>/*.js；⑤ 四件套去向：顶层目录删、四份 build.mjs 删、四份 tsconfig.json 移进域目录（src/shared/<名>/tsconfig.json）、四条 verify-*-freshness.js 删；⑥ 与 Q11 绑定（删 freshness 的前提是构建缓存输入集合结构化）；⑦ 验收三条：git diff -M 显示这一提交全是重命名、行为零变化；src/ 下没有生成的 .js；发布包里 package/shared/ 四份文件数不变（3／14／14／4），且故意改坏一个域里的一个文件，类型检查必须红；⑧ 本次不动那 3 个手写 .js（chain-ride.js、refusal-text.js、exec-envelope.js）。
