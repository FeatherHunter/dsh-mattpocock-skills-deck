Q8 讲解：typecheck 这个名字、这套设计、两种下限、构建里那次 tsc

2026-10-12 · 写给 TypeScript 新手 · 只讲你点名的四件事

一句话总结：typecheck 这个名字是社区惯例，不是 npm 内建命令；「一个域一份配置、逐份跑」符合官方多工程做法，但「自动发现配置 + 断言下限」是我们补的胶水；两种下限抓的漏不一样，建议两句都写且都用自动方式表达；构建里那次 tsc 不属于门禁，保不保留取决于你要不要「构建时就出声」。

1npm run typecheck 是我们发明的吗？

不是。名字是社区惯例，命令机制是 npm 自带的。

  • npm run <名字> 是 npm 的通用机制：package.json 的 scripts 里你起什么名字，它就跑什么。
  • npm 只对四个保留名有默认行为——start、test、stop、restart（所以 npm test 可以不写 run）。其余名字都必须带 npm run。
  • typecheck 在 TypeScript 项目里是很常见的命名习惯；也有项目叫 check、tsc、lint:types。它不是规范，谁都可以自取。

本仓今天没有这条。package.json 里现在只有这些脚本名：

build · update:latest · prepare · test · test:smoke
verify:parallel · verify:fast · verify:changed · verify · sync:matt

所以「新增 typecheck」的意思是：给一个社区常用的名字，挂上一条我们自己写的脚本（脚本里真正调的还是同一条 tsc）。

一句话：名字是借的，工具是真的——typecheck 里没有新发明的检查，只是把「官方编译器、逐份配置」这件事收到一条命令上。

2「逐份 tsc -p + 自动发现配置 + 断言下限」符合权威 TS 项目的思路吗？

这三截的出身不一样，要分开看。

这一截官方怎么做我们这套的定性
一个域一份 tsconfig，逐份 tsc -p 检查 官方给多工程仓库的答案叫「工程引用」：每个工程仍有自己那份 tsconfig.json，另加一份根配置列出 references，用 tsc -b 一次跑完 方向一致，只是我们现在是「手动一份份跑」，终点是官方那条 tsc -b
自动发现仓库里所有 tsconfig 没有这个命令：tsc -b 要你把 references 清单写出来，它不替你把配置全找出来 我们补的胶水（少一份手写清单）。到 13 号收口上工程引用时，发现这件事应交回编译器——引用写错，编译就不过
断言「配置份数、编译文件数」的下限 社区通行做法是 CI 里跑一次 tsc；不额外断数字 不是社区通行做法，是本仓纪律：对应我们那条「检查要能被看见」。仓内已有同款先例，见下

仓内先例（真实存在）：tests/verify-contract-types.js 就是两步走——第 1 步跑 tsc -p 只求「这次编过的文件里没有错」（:269-275）；第 2 步另跑一次要 --listFiles，拿它跟自己列出来的契约目录 .ts 清单逐一对账（:279-291），理由写在注释里：「第 1 步管不住某个文件根本没进这次编译」。若契约目录一个 .ts 都没有，它判红（:284-285）——这正是「扫到的集合是空的，就不许判绿」。

诚实说清：「自动发现 + 断言下限」这一截，官方文档里没有。它的价值不在「符合权威」，而在于挡住一个真实事故：src/client/kernel/locale-cards.ts 被构建转译成产物、能跑，却从来不在任何 tsconfig 的检查名单里——「绿」是真的，因为它压根没被看过。

3两种下限写法，区别在哪？

两者都在防「绿而没检查」，但防的是不同的漏。

写法甲：「≥ 今天实测数字」

一条绝对值，例如「发现的配置 ≥ 6 份、编译到的文件 ≥ 72 个」。

  • 抓得到：配置被误删、发现路径写错、整体塌了——总数会掉下下限，当场红。
  • 抓不到：数量守恒的搬家。比如 A 域掉了 4 个文件、B 域多了 4 个，总数没变，照样绿。

写法乙：「每个域至少 1 个文件 + 总数 ≥ N」

多了一层「逐域」的下限。

  • 抓得到：某个域整个没被检查（那份配置挂错目录、域目录改名后指向空）。
  • 代价：得知道「域有哪些」。好消息是这件事不必手写——每一份被发现的 tsconfig 就是一个域，逐份断言「你至少编到 1 个文件」即可，零手工登记。

打个比方：写法甲像「冰箱里总共至少 6 样菜」；写法乙像「每个抽屉至少 1 样菜」。抽屉被搬空、但总数恰好补回来了的时候，只有乙看得见。

我的建议（等你定）：两句都写，而且都用自动方式表达——① 对每一份被发现的 tsconfig 断言「编译文件数 ≥ 1」（自动枚举，不需要域清单）；② 对总数断言「≥ 一个只升不降的基线数字」（基线文件入库，与 Q3 那把棘轮同一套做法）。这样「某个域空了」和「总体塌了」都会当场红，而且维护量是零（没有新的手工清单）。

4构建里顺手跑的那次 tsc，要不要保留？

先分清它是什么：它不是门禁，它就在构建脚本自己身上——今天 scripts/build.mjs:1089 在转译像素风那批文件时顺手跑一次 tsc -p tsconfig.client.json。你排斥的是「再养一批判定脚本、给仓库加税」，不是「构建脚本检查一下自己刚处理的东西」。

保留的理由

  • 早失败：写错类型的 .ts 在构建那一刻就出声，而不是等到单独跑 typecheck 才发现。
  • 不违背经典 TS 项目惯例：不少 TS 项目的 build 脚本本身就是「先类型检查、再打包」一串步骤串起来的。

保留的代价

  • 同一件事跑两遍（构建里一次、typecheck 里一次）。实测客户端那份 tsc 约 102 毫秒，可以忽略。

更彻底的做法

构建只转译、完全不跑 tsc，类型检查全归 typecheck。代价是构建可能产出「类型有错但语法没问题」的产物——产物不入库、又要过发布门禁，实务上也能接受。好处是职责更干净：一个命令只做一件事。

与你至今的理念合不合：按我们讨论出来的口径（一条命令跑完检查、检查要能被看见、不新增门禁），保留不冲突——因为它没有新增任何判定脚本。真正要守的纪律只有一条：判定职责只有一处——完整性与下限断言归 typecheck，构建里那次只当「早失败」，两边跑的是同一条 tsc -p <同一份配置>，不会出现两套口径。

我的建议（等你定）：保留，构建里那次保持原样；typecheck 负责完整性（发现配置 + 逐域 ≥ 1 + 总数 ≥ 基线）。若你更想「一处只做一件事」，就选更彻底那种，我按你的选择写结论。
