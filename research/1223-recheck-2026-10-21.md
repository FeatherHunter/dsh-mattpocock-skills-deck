## 十、埋点方案（本阶段只写方案，不改代码）

本票是静态死代码清理，不是运行期故障；日志不能证明「该不该删」，只能旁证「运行时是否还在丢弃这个项」。题目要求若判「存在」给一版精确方案，所以下面给出，同时说明它对本票够不够。

### 落点与事件

- 文件与行：`src/host/detectChain.ts:386`。就在这句过滤之后、`items` 被使用之前记一行；只有后端为 github/gitlab/markdown 且走进链求值时才会执行。
- 事件名：`chain.catalog`，按需（debug）级。现有同族事件是 `chain.predicate`、`chain.cache.hit`、`chain.cache.miss`、`chain.preflight.reuse`，命名风格一致。
- 写法沿用同一函数里 `:240`、`:243` 的既有形状（先判 `logCtx.isEnabled('debug')` 再 `logCtx.fire`）。
- 去重：按「每进程每后端只记一次」处理，模块级 `Set` 放在 `:167` 附近 `chainInflight` 那一带；命中就跳过。这是高频路径，必须同时有调试开关与一次性去重两层。

### 字段（只收能排除一种故障的信号）

- `backend`：`github` / `gitlab` / `markdown`，短字符串。
- `declaredCount`：`catalogFor()` 声明的后端项数（今天 github 是 5，清理后应为 4）。
- `runtimeCount`：过滤后真正进入运行视图的条数（今天 github 是 4，清理后仍 4）。
- `droppedIds`：被过滤掉的 id 数组（今天应为 `['gh:labels']`，清理后为空）。
- `reason`：固定原因码 `backend-catalog-filtered`。

不记：工作区路径原文、完整目录项对象、locale 文本。

### #1001 提的 chain.catalog 方案对本票够不够

- **够用的部分**：实施前后各看一次，能证明「死项在运行时确实被丢弃」（`droppedIds` 含 `gh:labels`），清理后变成 `droppedIds: []`、`declaredCount == runtimeCount`。作为一次性的回归旁证是够的。
- **不够的部分**：它是「按需 + 一次性」的调试线，不开调试开关就永远没有记录；而且清理完成后，过滤那一句本身就被删掉，这个事件没有落点，只能随过滤一起消失或挪到别处。它挡不住「以后有人再往目录里加一个没有运行时视图的项」——那种问题要在目录与运行时视图之间加静态断言才能挡住（见第五节第 6 条）。所以结论是：**这条日志只适合作实施前后的一次性佐证，不适合作为本票的常驻验收证据，更不是防复发手段**。如果维护者认为不值得为一次清理加常驻事件，我建议本票不加埋点，验收走第五节的静态断言；如果确实要加，就按下面的白名单同步。

### 这条日志落盘后怎么判

- 出现 `chain.catalog` 且 `droppedIds` 含 `gh:labels`：死项仍在真源声明、仍被运行时丢弃，故障存在。
- 出现 `chain.catalog` 且 `droppedIds` 为空、`declaredCount == runtimeCount`：过滤已没有对象，死项已清理（此时过滤本身也该删）。
