## 复查（2026-10-27 中午，应对抗式审查）

复查起因：维护者要求从第一性原理重新审一遍上面的推荐。这一轮推翻并替换了第 2 问原来的推荐。

### 这一轮查到的三件事

1. 正文兜底不只让两层说法不一致，它还会压过硬证据。判定顺序是 工作区文件 → 声明文件 → 自动识别；收集证据时只要声明层给出「命中」，自动识别在 decisive 档位就直接跳过（理由是 skipped-stronger-evidence）。代码：`src/tracker/detection/backendDecision.ts:917-1021`，其中 `higherTierDecided = evidence.some((e) => e.kind === 'verdict')` 在 `:963`。于是「GitHub 远端 + 无标题旧文档里写着『以前这里用 GitLab 管票，后来迁到别处了』」会被判成 GitLab，GitHub 远端根本没人看。这比票面第 2 条更重：不是两层说法不同，是程序主动选错。
2. 低置信结果被当成身份的消费点不止判定层。`src/tracker/detection/explicitDetector.ts:87-93`、`src/tracker/detection/backendDecision.ts:900-901`、`src/refresh/registry/deck-tool-bridge.ts:212-219` 三处都没检查置信度；全仓只有 `src/tracker/rooms/gitlab/index.ts:171` 查了 `confidence === 'high'`。一个解析结果四种用法、只有一处守规矩，说明「靠每个调用点记得检查」守不住，要改数据形状：身份字段里装不进猜测。
3. 票面第 2 条验收与 #1048 的有意决定冲突。`tests/verify-detection-evidence.ts:287-295` 正钉着「只有正文关键词（没有标题行）也认」：fixture 是 `本仓库的票记在 GitHub 上，用 gh 命令读写。`，期望 `backendId === 'github'` 且 `origin === 'declaration'`，注释写明「这是本票的有意修正」。提交 `f086a8e3`（#1048）与 `0b55ae6e`（#1048 复核补做）引入。所以「判定层也不认正文」不是修 bug，是推翻 #1048 的一次决定，必须由维护者重新拍板。

### 推荐（替换原第 2 问的推荐）

走 P1「声明与提示分开」：身份只来自明确的声明或现场事实，正文提及只当提示。

1. 解析层改形状：`explicitBackendId` 只装 high；low 挪到单独的 `hintBackendId`。注释写清 #277（标题优先）与 #1555（认领只认 high）两条口径。
2. 认领层只认「声明（high）+ 现场事实」。Markdown 房把整篇正则（`src/tracker/rooms/markdown/index.ts:126-143`）换成和 GitLab 房同款的高置信判据；没有标题、只在正文写 Local Markdown 的旧文档不再认领（判定层本来就不认，#277 之后这里曾是唯一还认它的出口，标准模板本来就有标题）。
3. 判定层：low 不再算 verdict，自动识别一定有机会跑并胜出；硬证据也没有时，不拿正文猜身份，如实返回没定下来加提示线索，由面板选定一次写进 workspace.yaml。这一步同时修掉「正文盖过远端」和 #1048 的 f3 行为。
4. 文案（原第 3 问）不变：按原因分档，多命中与没选后端指向面板，确认中说明稍后重试，其余保留「写会话没开成」加诊断提示；不在本票抽跨层公共文案。
5. 门禁落点：改 `tests/verify-1555-gitlab-claim-declaration.ts:127-133`（low 不再进 explicitBackendId，只留提示字段）；重写 `tests/verify-detection-evidence.ts:287-295`（只有正文、没有硬证据时判不出来），并加反例「GitHub 远端 + 无标题旧文档提到 GitLab → 按远端选 GitHub」；`tests/verify-1129-markdown-claim.ts` 加反例「GitHub 标题 + 正文提到 Local Markdown → Markdown 不认领」；文案门禁保留「写会话没开成」并补 multi-match / no-backend / pending 三档。全链用 Node 24.15 以上跑 `npm run verify:parallel`。
