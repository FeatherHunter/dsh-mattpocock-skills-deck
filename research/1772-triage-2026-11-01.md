# #1772 分诊：GitLab 读全的增量窗口与分页上限

> *This was generated by AI during triage.*

本文件只记 #1770 没覆盖、但对「用 updated_after 做增量探针」和「分页读到上限」有直接影响的一手事实。没有改业务代码、没有建票或评论。

## 调查范围

- GitLab 官方文档：`doc/api/issues.md`、`doc/api/rest/_index.md`、`doc/administration/instance_limits.md`、`doc/user/gitlab_com/rate_limits.md`。
- GitLab 主仓源码：`app/models/concerns/updated_at_filterable.rb`、`app/finders/concerns/updated_at_filter.rb`、`lib/api/issues.rb`、`app/models/concerns/sortable.rb`、`app/finders/issuable_finder.rb`、`lib/api/helpers/pagination_strategies.rb`、`lib/gitlab/pagination/cursor_based_keyset.rb`、`doc/development/database/keyset_pagination.md`。
- 真机：2026-11-01 用匿名只读 HTTPS 调 gitlab.com 公开 REST。本机 glab 1.123.0 的 token 已失效（`glab auth status` 报 `API call failed: GET https://gitlab.com/api/v4/user: 401`，`glab api …` 报 `glab: 401 Unauthorized (HTTP 401)`），所以没有用 glab 跑。

## 事实 1：updated_after 含边界

- 源码：`scope :updated_after, ->(date) { where(scoped_table[:updated_at].gteq(date)) }`（`gteq` 即 `>=`，`updated_before` 用 `lteq` 即 `<=`），见 [updated_at_filterable.rb](https://gitlab.com/gitlab-org/gitlab/-/blob/master/app/models/concerns/updated_at_filterable.rb)；参数只做取值与 `in_time_zone`，见 [updated_at_filter.rb](https://gitlab.com/gitlab-org/gitlab/-/blob/master/app/finders/concerns/updated_at_filter.rb)。
- 文档与源码注释同一句：“Return issues updated on or after the given time”，见 [Issues API](https://docs.gitlab.com/api/issues/) 与 [lib/api/issues.rb](https://gitlab.com/gitlab-org/gitlab/-/blob/master/lib/api/issues.rb)。
- 真机：`gitlab-org/gitlab-runner` 的 issue 38828（`updated_at=2026-11-01T01:10:16.712Z`）用 `updated_after=2026-11-01T01:10:16.712Z` 查回 1 条，改成 `.713Z` 查回 0 条；写成 `2026-11-01T09:10:16.712+08:00` 也查回 1 条（按瞬间比较，不按字面）。

## 事实 2：排序只按 updated_at，没有并列用的次序键

- 源码：`scope :order_updated_asc, -> { reorder(self.arel_table['updated_at'].asc) }`，没有追加 `id`，见 [sortable.rb](https://gitlab.com/gitlab-org/gitlab/-/blob/master/app/models/concerns/sortable.rb)；`IssuableFinder#sort` 在有 `sort` 参数时走 `sort_by_attribute`，见 [issuable_finder.rb](https://gitlab.com/gitlab-org/gitlab/-/blob/master/app/finders/issuable_finder.rb)。
- 文档：issues 文档只说“This endpoint supports both offset-based and keyset-based pagination. You should use keyset-based pagination when requesting consecutive pages of results.”，没有承诺 offset 翻页在并发写下的稳定性，见 [Issues API](https://docs.gitlab.com/api/issues/)；keyset 文档明确要求排序列唯一时补主键才能 distinct，见 [keyset_pagination.md](https://gitlab.com/gitlab-org/gitlab/-/blob/master/doc/development/database/keyset_pagination.md)。
- 真机：`gitlab-org/gitlab` 的 `order_by=updated_at&sort=asc` 第 501 页末条 `13533@…11:55:22.034Z`、第 502 页首条 `13431@…11:55:22.673Z`；两页 200 行里没有完全相同的 `updated_at`，跨页也没有共享值（毫秒口径下并列罕见）。
- 按源码推断（不是文档承诺）：升序走读时被改的票只会往后挪，最坏是重复读；降序走读才可能整趟漏掉。

## 事实 3：offset 的硬顶是 50,000，且对 issues 不生效

- 文档：**默认上限 50,000**，且“This limit is only applied to endpoints that also support keyset-based pagination”；`Plan.default.actual_limits.update!(offset_pagination_limit: 10000)` 是自管实例改值的示例，不是默认值——传言的“10,000 硬顶”是把示例当成了默认，见 [instance_limits](https://docs.gitlab.com/administration/instance_limits/#max-offset-allowed-by-the-rest-api-for-offset-based-pagination)。
- 源码：`offset_paginator` 只在 `cursor_based_keyset_pagination_enforced?` 为真、且 `params[:page] * params[:per_page] > offset_limit` 时 `error!(…, 405)`；`ENFORCED_TYPES = [Group, User].freeze`，Issue 不在名单里，见 [pagination_strategies.rb](https://gitlab.com/gitlab-org/gitlab/-/blob/master/lib/api/helpers/pagination_strategies.rb) 与 [cursor_based_keyset.rb](https://gitlab.com/gitlab-org/gitlab/-/blob/master/lib/gitlab/pagination/cursor_based_keyset.rb)。
- 真机：`gitlab-org/gitlab`（325,377 张票）`page=500`（offset 49,900）与 `page=502`（offset 50,100）都返回 200、各 100 行，没有 405；超过末页（gitlab-runner 只有 96 页）的 `page=101`、`page=1000` 返回 200 与空数组，不报错。
- 真正会在 10,000 上出问题的是响应头：结果超过 10,000 条时 `x-total`、`x-total-pages`、`rel="last"` 被省略，见 [rate_limits](https://docs.gitlab.com/user/gitlab_com/rate_limits/#pagination-response-headers) 与 [REST API](https://docs.gitlab.com/api/rest/#pagination-response-headers)。→ 9,512 张票 96 页可以读全，约束是节拍与限流（免费档 burst 100 次/分钟，#1770 实测），不是硬顶；大仓则不能靠总数判断是否读完。

## 事实 4：精度、时区与什么操作会改 updated_at

- 时区/格式：JSON 里是 `2026-11-01T01:10:16.712Z`（毫秒 + Z/UTC），文档示例 `2016-01-04T15:31:51.081Z`，见 [Issues API](https://docs.gitlab.com/api/issues/)。
- 精度：同一张票用 `updated_after=.712Z&updated_before=.712Z` 查回 0 条，用 `updated_after=.700Z&updated_before=.712999Z` 查回 1 条——库里存的是亚毫秒（微秒）级，JSON 只截到毫秒。对增量游标是好事：把回包里的 `.712Z` 原样当 `updated_after` 不会漏（截断只会把下界提前），最坏重复一次；反过来 `updated_before` 用同一个值会漏掉这张票。
- 哪些操作会改：文档只说 `updated_at` 是“date and time when the issue was last updated”，没有列举操作。想真机验证“评论会不会刷新 updated_at”，但 notes 端点匿名返回 401（38828 的 `user_notes_count=11`），没能验证。

## 事实 5：文档没有增量轮询建议

- issues 文档与 REST 分页文档里检索 poll / incremental / sync 均无命中；唯一相关建议是大集合与连续翻页用 keyset（“For large collections, you should use keyset pagination (when available) instead of offset pagination, for performance reasons.”），见 [REST API](https://docs.gitlab.com/api/rest/#pagination)。

## 对 #1772 的直接含义

- 增量游标就用“本趟读到的最大 `updated_at`”，因为边界含，最后一条会重复一次，按 iid 去重即可，不会漏。
- 走读用 `order_by=updated_at&sort=asc`：中途被改的票只会往后挪，最多重复；别用 desc 走读。
- 9,512 张票读全是 96 个请求，可行，但按 5 秒节拍做不到（96 请求/5 秒 ≈ 19 请求/秒，远超免费档 100 次/分钟）；现实方案是低频全量 + 高频增量窗口。
- 大仓不能靠 `x-total` 判断读完（>10,000 被省略），要读到 200 空数组为止；≤10,000 的仓不受影响。

## 还不确定的地方

- 评论、标签、指派等各类写操作是否都刷新 `updated_at`：文档不列举，notes 端点匿名 401，未验证。
- 同一微秒的并列票如何排序：源码无 `id` 次序键，理论上无保证；实测毫秒口径没遇到。
- keyset 翻页在并发写下是否真的不重不漏：源码保证排序列 + id 唯一，但列值变动仍会让记录换位置，未做真机验证（项目级端点要求 18.3+）。
