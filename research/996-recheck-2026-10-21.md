## 五、判定：存在（限定在 Markdown 房地图；GitHub 房只在元数据未达窗口会空）

判「存在」的依据是今天仍能走通的确定路径，不是靠票面旧结论：

1. Markdown 房的地图行 `number` 恒为 0（`key '00'`，宿主按 `parseInt` 得 0，仓库自己的夹具也这么写）。
2. 完成/检查提示词把 `m.number` 交给 `String(num || '')`，0 被当成空串丢掉（`prompts-backend.ts:115/119`），`issueUrlFor` 第一步就返回空（`link.ts:50-51`）。
3. 结果：完成为「首行 /wayfinder、第二行空」，检查为「首行 `/wayfinder `（尾部空格）加空行」——后者与票面粘回来的原文形态完全一致。快照里地图行本来带着文件路径（`issues-read.ts:104`），却被这一步丢弃，因此这不是「Markdown 无模板」能解释的已知限制，而是客户端取参缺陷。
4. GitHub 房正常路径有链接（模板 + refId），但 `st.backendModules` 未达时仍返回空串（`link.ts:63-64`），这与票面「重启后好了」吻合；本机 10-15 至 10-21 的日志没有观察到这个窗口，也没有反证。

建议：**保持 open，不按「已修」关闭**。若用户手上那次是 GitHub 工作区，则对应的是第 4 条运行期窗口，仍需复现；若是 Markdown 工作区，则第 1 至 3 条可以直接复现（地图页点「完成」或零子票点「检查」）。

## 六、dsh-log 埋点方案（本阶段只写方案，不改代码）

### 事件

新增按需（debug）事件 `prompt.link`，与现有注入类事件 #64 `inject.decision`、#65 `guide.inject`、#68 `healthCheck.inject` 同一风格（领域在前、动作在后；不造新风格）。理由：由用户点击触发、一次最多一条、只在该排查注入问题时需要；本机 `log-switch.json` 已开启，加上即可落盘。

### 落点

最小方案：在 `src/client/kernel/prompts-backend.ts` 里抽一个内部 helper（例如 `promptLinkFor(st, num, promptId)`），由 `completePrompt`（`:113-117`）与 `inspectPrompt`（`:118-121`）调用；helper 负责取链接并发一条 `prompt.link`。这样完成/检查两条最先要判的路径只加一处逻辑。

若要覆盖票面列出的其余提示词（execute、takeover、supplement、diagnose、fix、discuss、research、prototype），再把 `src/client/kernel/router.ts:181/186`（startText 的检查/完成分支）、`src/client/kernel/row-actions.ts:168`（执行模板）与 `src/client/kernel/store-derived.ts:276-282`（接手/补充/诊断/修复/讨论/研究/原型）改为调同一个 helper。不要直接改 `link.ts` 的 `issueUrlFor`：它被所有行渲染高频调用，直接埋会变成垃圾。

建议同时给 `src/client/views/ListTabRow.ts:259-266` 的地图「检查」「完成」按钮补 `data-log`（例如 `list.map.inspect` / `list.map.done`），让今天的 #119 `ui.action` 能证明「用户点过哪条路径」；这一项只记稳定枚举，不新增事件。

### 字段（只收能排除一种故障的信号，全部为枚举或布尔，不记链接原文、标题、路径）

| 字段 | 取值 | 能排除/区分什么 |
| --- | --- | --- |
| `prompt` | complete / mapInspect / execute / takeover / supplement / diagnose / fix / discuss / research / prototype / specComplete / specSplit / specExecute | 哪一条提示词出问题 |
| `backend` | github / gitlab / markdown / other / empty | 哪个后端（#1226 的 Markdown 路径） |
| `numKind` | number / zero / missing | 编号正常、编号为 0、编号没传（候选路径①） |
| `metaReady` | true / false | 后端元数据到没到（候选路径②） |
| `templateDeclared` | true / false | 该后端声明链接模板没有（Markdown / #1226） |
| `refIdReady` | true / false | 仓库引用认出来没有（候选路径③） |
| `effortAware` | true / false | 调用时有没有工作单元标识（候选路径④） |
| `linkSource` | snapshot / template / none | 链接从快照行取到、从模板渲染、还是没取到 |
| `linkKind` | https / path / empty | 链接是网址、本地文件路径、还是空 |
| `verdict` | ok / empty-num / empty-snapshot-miss / empty-no-meta / empty-no-template / empty-no-refid | 本趟的终点结论 |

不记编号本身与链接原文：编号用 `numKind` 就能区分「0 / 空 / 正常」，链接用 `linkKind` 与 `linkSource` 就能定位，避免把票号、工作区路径带进日志。

### 这行落盘后怎么判

- `verdict=ok` + `linkKind=https/path` + `linkSource=snapshot/template`：链接正常，票面故障未发生。
- `verdict=empty-num` + `numKind=zero` 或 `missing`：命中本复核第五节的 Markdown 地图路径，故障存在。
- `verdict=empty-no-meta` + `metaReady=false`：命中运行期元数据未达窗口（对应「重启后好了」）。
- `verdict=empty-no-template` + `backend=markdown`：走到 #1226 的「无模板」分支（仍要求快照也没给出 url；今天第 1 节证明这里其实多层都断）。
- `verdict=empty-no-refid`：命中 #435 一类自托管 GitLab refId 为空。
- `verdict=empty-snapshot-miss`：编号在快照里查不到（工作单元维度、快照未刷新等），可再结合 `effortAware` 判断候选路径④。
