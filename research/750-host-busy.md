# 输入期间宿主在忙什么：外部命令、快照读写、日志刷盘是否挡住输入（#750）

> 地图 #747 子票 #750 · 只读调查，不改生产代码 · 落盘日期 2026-09-26
> 数据来源：源码静态读取 + 进程缓存目录下落盘文件的计数（只数行数、事件名、枚举与数字字段；不记令牌原文与路径原文，字段口径按 `research/489-appendix.md` 白名单）
> 输入的含义：人在对话框里打字的那几秒。宿主的含义：插件里常驻后台的那一部分（面板取数、后端探测、日志落盘都住这里）。

## 结论先行（验收两问的直接回答）

1. **宿主同步段只占亚毫秒级**：日志记录函数只把一行推进内存队列就返回（`src/host/index.js:62` 的 `fireLog`：进队列即返，不等写盘；`src/host/logPkg/store.js:208-222` 的 `log()`：推进数组 + 约一次刷盘，不做文件读写）。错误与告警虽然要求立即刷盘，走的也是“取消防抖、事件循环末再写”（`store.js:223-238`），调用处同样不等。
2. **真正慢的是“次数堆起来的串行等待”，不是单次调用本身**：每条外部命令上限 30 秒（两处出口同值），但一次面板快照重建要串行起约 11 次外部命令、全仓库扫描约 4~5 秒（`src/host/index.js:36` 注释、 `src/host/sessionSnapshot.js:79` 注释）。输入（打字）本身不直接起任何外部命令；挡在输入路上的是“同一时刻恰好在飞的一次重建/探测”——而好消息是 60 秒内存缓存让绝大多数输入时刻根本不重建（见第 2 章实测：落盘日志里重建事件为 0 行）。

## 1 输入期间的外部命令：两个出口、一行日志、发起链名

### 1.1 两个子进程出口（互斥，每条命令只走一条）

`gh` 直连封装 `runGh`（`src/host/repoKeys.js:59-118`）走同一超时，退出码非 0 时按文案归一成 `auth / notfound / network / exit` 四类再记一行。

### 1.2 两套日志，级别不同（决定了输入现场能不能从盘上看到）

- `exec.run`（按需 #58，调试级）：字段只有命令名（去目录只留程序名）、工作区短指纹、耗时、退出码、发起链名（`research/489-appendix.md:226`）。**调试开关关着时只读一次开关就返回，连时钟都不读**（`platformChannel.js:187`、`repoKeys.js:127`）。含义：默认情况下，输入期间起了几次外部命令、每次多慢，盘上没有逐条记录，只能靠常驻事件反推。
- `gh.exec`（常驻 #5，信息级）：字段为命令名、工作区短指纹、耗时、归一类别、退出码（`research/489-appendix.md:161`），开关关着也落盘。含义：凡经 `gh` 房内客户端出去的命令，输入对照表靠这一行。

### 1.4 单次耗时与并发数（数字）

- 单次上限：两处出口都是 30 秒超时；`gh --version` 探测那条 2 秒（`repoKeys.js:48`）。
- 并发：同一轮探测内并发为 1（串行 `await`）；降级通道（配额耗尽走 REST 逐票补）是 `for` 循环串行（`src/host/issueList.js:284-317`：每张地图 1 次详情 + 1 次子票 + 每子票 1 次依赖）；跨调用方并发由在途合并压成 1（`src/host/snapshotInflight.js:16-23`：同键在途直接搭车，强制只搭强制的车）。
- 实测（进程缓存目录下落盘日志，见 3.2 的环境说明）：`gh.exec` 在 2026-09-24 共 42 行，类别为成功 30 / 退出码非 0 有 6 / 登录态 3 / 网络 3；耗时字段全部落在 0~1 毫秒。**这不是真机输入的耗时**：同一文件里 112 行全部归属 `wf.initPublish` 这一个方法、22 次宿主启动头挤在 643 秒里，是无 `gh` 环境的测试/初始化现场（`gh.resolve.fail` 3 行伴生）。结论是“单次调用本身慢还是次数多”在真机仍需开调试开关后用 `exec.run` 的 `latencyMs` 再量一次；代码能确定的是**串行次数（约 11 次）× 单次网络耗时**这一侧，不是“某一次调用特别慢”这一侧。

## 2 面板快照与工作区共享数据读写：三层缓存，落盘是整份

### 2.1 三层缓存（命中时输入零等待、零拷贝）

| 层 | 位置 | 容量与有效期 | 命中时返回什么 |
|---|---|---|---|
| 会话快照内存表（按工作区根分桶） | `src/host/index.js:37,48-51` | 最多 20 条（超了丢最久没用），60 秒有效（`CACHE_MS`，v1.3.3 从 5 秒提到 60 秒） | 缓存里**同一个对象**直接返回（`src/host/sessionSnapshot.js:77,80-83` 的 `shortCircuit()`；选择没变时不重新拼数据、不联网核对） |
| 组装层快照表 | `src/host/tracker/snapshot.js:158-160,168-171` | 最多 20 个仓库，5 秒有效；版本号存在条目里、调用方比对，不一致才重建 | 同对象 + 304 短路（`snapshot.js:192-203`） |
| 工作区选择表（探测结论） | `src/host/tracker/detection/workspaceStore.js:12,24-27` | 单例内存表，不落盘，30 秒有效；`pending` 与环境失败不入缓存 | 同对象；命中按百分之一采样记一行， miss 全记（附录 #53） |

只有“缓存里那条选择与这一轮算出来的后端/修订号/布局不一致”时才做一份浅拷贝换上新选择（`sessionSnapshot.js:59-69`）；其余短路都不新建对象。写操作（评论、发布、改色保存）成功后只删本工作区那一格（`commentThreads.js:195`、`repoKeys.js:109` 等均按规整钥匙清自己根），不整表清空。

### 2.2 磁盘快照：整份读回、整份写回

- 整份写：`JSON.stringify` 整个快照对象（`src/host/repoKeys.js:240-251` 的 `writeDiskCache`，另加 `cacheFormat: 3` 版本戳）；整份读：`JSON.parse` 后整份校验（`repoKeys.js:225-239`，格式不对整份丢弃视为没有）。
- 写盘频率：只在 GitHub 分支重建成功后写一次（`src/host/sessionSnapshot.js:338`、`src/host/sessionRefresh.js:307`）；磁盘回放命中且“还算当前”时直接采用不再重建（`sessionSnapshot.js:266-268`）。含义：**打字不写盘**；写盘只发生在重建成功那一刻。
- 文件大小（实测字节数）：本仓库那份为 **7,301,835 字节（约 7.0MB）**；测试夹具 5 份各约 16KB（`ForkOwner__ForkRepo.json` 16624、`SameOwner__SameRepo.json` 16662、`SingleOwner__SingleRepo.json` 16678、`SSHOwner__SSHRepo.json` 16654、`upstream-org__upstream-repo.json` 16699）。含义：真机一次整份写盘是 MB 级，一次整份读回解析也是 MB 级——但 60 秒缓存 + 在途合并让它很少发生。
- 实测频率：本机缓存目录全部 20 天日志里，`snapshot.built`（每次重建必记一行，`src/host/snapshotEnvelope.js:38-48`）共 **0 行**——观测窗口里没有发生过一次重建，面板服务全部走内存短路。这与“输入高峰时快照也在高峰”的担忧相反：至少在本机，输入期间快照层是静默的。

## 3 日志落盘队列：防抖 1 秒，错误直通，跨进程不加锁

### 3.1 队列与防抖（数字都在代码里）

- 内存队列上限 1000 条（`src/host/logPkg/config.js:6` 的 `DEFAULT_MAX_QUEUE`）；满时错误/告警挤掉一条非错误行腾地方，其余直接丢弃并计数（`src/host/logPkg/store.js:196-207`）。
- 防抖 1000 毫秒：普通行进批量等 1 秒合并写（`LOG_DEBOUNCE_MS`，`config.js:5`）；错误与告警入队即取消等待、本轮事件循环末就写（`store.js:223-238`），但调用处仍不等写完。
- 单进程单写者：`flushing` 守卫 + `flushQueued` 合并（`store.js:39-40,251-287`），同一进程内一次只写一份。
- 客户端转发批量：每批最多 50 条、每 1000 毫秒、单包 128KB 或 100 条先到先截（`config.js:7-10`）；失败丢弃并计数，不阻塞调用处（附录 2.3 定版选项一）。

### 3.3 输入高峰是否与落盘高峰同峰

- 时间聚集实测（09-24 全天 112 行跨度 643 秒）：按分钟分桶后全部 112 行落在 3 个分钟桶里（39 / 37 / 36），其余分钟为 0。含义：落盘是**突发式**的（随进程启动/初始化动作来），突发内单次写是“读整文件→拼上几行→写整文件”（`store.js:317-323`），文件越写越大当天越大（峰值天 135KB）。
- 跨进程证据：09-09 日志里有 5 行解析失败的碎行（半截 JSON），与附录 3.2“两个宿主进程写同一天文件不加锁、以后写为准”一致——**落盘损坏只污染日志文件本身，不抛错、不阻塞调用处**（写失败只计数，`store.js:263-266,325-329`）。
- 对输入的含义：日志刷盘与输入不在同一条等待链上（调用处不等盘）；输入高峰（打字）本身几乎不产生日志（快照短路不记 `snapshot.built`，`exec.run` 开关关着不记）；观测到的落盘高峰全部来自“启动/初始化/无 gh 失败”这类后台事件，不是输入事件。真机若要验证“打字那几秒有没有刷盘”，做法是：打开调试开关复现一次输入，同时看 `snapshot.request`（常驻 #1，含 `force` 标记）与 `exec.run`（按需 #58，含 `via` 与 `latencyMs`）的时间戳是否落在输入窗口内——本次调查确认了这两行的字段与落点都在，缺的只是一次开着开关的真机复现。
