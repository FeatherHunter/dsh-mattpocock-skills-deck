## 四、根因链（按「一条拍」走）

1. 面板可见且宿主说在活跃集合里时，客户端每 `intervalMs`（活跃 5 秒）发一拍 `wf.probe`（`refresh-timer.ts:314-346`）。这条拍带 `background:true`，但探测退避只在**成功且没变化**时升档（`src/refresh/rooms/client/client-attention-heartbeat.ts:321-326`）；失败时档位不动，于是失败场景实际上一直按 5 秒跑。
2. 宿主 `handleProbe` 先 `selectEarly`，而它内部会跑完整 `detect`（`src/host/sessionLifecycle.ts:184`）；然后走 GitHub 主路 `fetchIssueIndexWindowed(cwd)`（`probe-handler.ts:190`）。镜像目录没有 `.git`，更早的一步 `src/refresh/rooms/host/issue-list-fetch.ts:106-108` 的 `getRepoKey` 就返回空，直接 `fail('env','无法解析 owner/repo')`；这一步发生在任何 gh 调用之前，所以镜像目录的失败不占 gh 队列、也不会耗满超时窗口。索引扫描仍会回 `{kind:'env', error:'无法解析 owner/repo'}`（`issue-index-scan.ts:84`），探针回 `{ok:false, errorKind:'env'}`（`probe-handler.ts:196`）。
3. 客户端失败分支只把本组会话置成 `snapMode='err'` + `snapFail={kind:'probe-failed'}` 并 return（`refresh-timer.ts:158-161`）。没有「这个 `env` 不会自己好」的判断，也没有暂停或终态；下一拍照旧。
4. 界面把「刷新失败」画成固定一句「刷新失败，正在重试」（`pages.yaml:31`），不区分 `env`（永不恢复）与 `network`（可能恢复），所以两种故障看起来一样。
5. 「正在探测后端」不是这条失败分支画出来的，它要求 `selection.pending=true`（`Dock.ts:354-368`、`StatusBar.ts:524-526`）。`pending` 只可能来自某家 `matches` 30 秒超时（`registry/core.ts:186-208`）。一旦选择里带了 `pending`，它能被替换的路径有四条：成功快照带回非 pending 的 selection、一次性 `wf.selection`、用户显式选择、迟到快照安装（`probe-scope-selection.ts:182-211`）；`snapshot-cache-store.ts:333-352` 里，incoming 仍是 pending 时直接保留旧值，快照/探测失败都不改 `st.selection`。补充两点：没有 `backendId` 的 pending 进不了 `st.selection`（`mergeSelection` 直接拒绝），但可以留在 `snapshot.selection`；宿主普通 `wf.snapshot` 在无 backendId 时会短路回旧快照（`session-snapshot-cache.ts:124-135`），两者合起来构成「pending 长期不清」的闭环。**但报告人没有提供远程工作区的 detect/selection 日志，无法确认 pending 当时确实为真，也无法确认他看到的是哪一块界面。**
6. 远程工作区是独立的设计缺口：插件对仓库身份的取证全在本地（见上表最后一行）。DSH 远程工作区的镜像目录天然没有 `.git`，也没有任何地方把远端仓库根或 `refId` 交给插件，所以「打开面板 → 解析不出仓库 → 失败」是结构性结果，不是偶发。
7. 浏览器卡顿的候选解释（**推测**）：每 5 秒发一条可能挂起约 10–30 秒的 `wf.probe`，失败不单飞也不暂停；叠加面板可见时每 5 秒的链自问（`refresh-timer.ts:350-366`，宿主按退避多半回 defer，但请求与回包仍要过桥）；客户端每次 emit 都会让 Dock/StatusBar 整块重渲染（`snapshot-cache-store.ts:423-430`），链快照也可能每 5 秒重发一遍（`probe-chain-subscription.ts:331-347`）。宿主 CPU 5% 只排除了宿主计算，剩下的要看浏览器 Performance 录制（主线程长任务、Layout/Paint、DOM 重建），今天没有证据，不下结论。

## 五、修复建议（分诊建议，不实施）

**R1（窄修，可交给代理）：探测失败的收口与分档。**
- 在客户端按回包 `errorKind` 分类：`env` 一类是「这个工作区不会自己好」，进入明确终态（例如面板说「当前工作区不是 git 克隆，自动探测已停止，请换真实克隆或指定仓库根」），并停掉活跃探测这条拍对该 cwd 的周期请求；`network` 一类是「网络异常，自动刷新已暂停」，按冷却退避而不是每 5 秒重跑，恢复后自动回正常节拍。
- 失败标记里保留 `errorKind`（今天只有 `kind:'probe-failed'`），界面文案按类别分开；现有 `truth.failRetry` 之外要新增词条。
- 触点在 `refresh-timer.ts` 的失败分支、`truthLines.ts` 的失败判据、`config/copy/pages.yaml`（中英各一份）、面板/状态栏的 pending 黄条条件；门禁至少加「env 失败后不再发下一拍」「network 失败按冷却」「两种类别文案不同」三条。注意 `tests/verify-1418-probe-cost-and-failure.ts` 的现有不变量不能破坏：失败要可见、同样失败不重复 emit、恢复后清标记、探测成功不抹掉取数失败标记。
- 代价：小到中等，一个代理一轮能做完，主要成本在文案与门禁。

**R2（需要先补证据）：selection.pending 的终态。**
- 现在 pending 只能被四条路径替换（成功快照、一次性 `wf.selection`、显式选择、迟到快照）；探测/快照全失败时它永久保留。更麻烦的是普通 `wf.snapshot` 在无 backendId 时会短路回旧快照（`src/refresh/rooms/host/session-snapshot-cache.ts:124-135`），闭环保住了这份 pending。建议给 pending 一个等待上限（类似 #1775 给 `selPending` 的上限），到点转成「后端未决，请手动选择」的终态并停拍。
- 但「远程工作区确实出现 pending」这一环没有日志证据，不能凭代码推断直接实施；需要报告人补该工作区的 `detection.detect`、`host.call.fail`（含 `method: wf.selection`）与界面截图。

**R3（只需取证，不是修）：浏览器卡顿。**
- 请报告人在复现时录一段浏览器 Performance（或至少记录面板可见 vs 收起时的主线程占用、二分定位到哪块 DOM/请求），再判断是不是探测叠加。今天没有证据，不建议按卡顿立项。

**R4（设计题，需要人拍板）：远程工作区的仓库根识别。**
- 可选方向：①由 DSH 远程工作区把远端仓库根或 `refId` 显式交给插件（需要 DSH 侧提供接口）；②插件增加「指定仓库根目录」入口，用户手填远端路径或 owner/name；③插件读远端 git 信息（需要跨机器通道，成本最高）。
- 这是产品/架构决定，且依赖 DSH 远程工作区的能力边界，不适合直接写 Agent Brief。

## 六、门禁为什么没抓到

- `tests/verify-1418-probe-cost-and-failure.ts` 锁的是「失败必须可见、同样失败不重复 emit、恢复后清标记、别的工作区不被误伤」（:395-423、:448-490），没有锁「失败后是否该继续按 5 秒探测」「env/network 是否要分开」。
- `tests/verify-visible-truth.ts:176-201` 只覆盖三种失败原因（配额、取数失败、取数失败且暂停），没有「探测失败且 `errorKind=env`」这一档，所以文案不分类不会有门禁红。
- 没有任何门禁覆盖「selection.pending 永久保留」——今天 pending 只在检测门禁里以「超时」形状出现，没有「后续所有请求都失败时 pending 是否该收敛」的用例。

## 七、影响与现状

- 影响人群：使用 DSH 远程工作区（本机镜像不是 git 克隆）的人会稳定遇到「解析不出仓库」；GitHub 抖动且仓库身份可解析时，探测会占用共用的 gh 读队列（排队上限 10 秒），拖慢同一队列里的 deck 工具读；镜像目录则在进入队列之前就失败。
- 已有后果：面板失败态不收敛、快照缓存没有该仓库条目、deck 工具读被探针排队拖慢；报告人还报告了浏览器卡顿（未证实）。
- 已有进展：无实施提交；#1775 给「读取后端」加过等待上限，但只覆盖 `wf.selection` 那一次询问，覆盖不到 `selection.pending` 的长期保留。
- 关联事项：#1835（探测失败没有历史记录，已单独分诊）、#1806（工作区根判定，相邻但不同根因）、#1775（等待上限的先例）。

## 八、待维护者拍板（也写在票面正文里）

❓ Q1 本票的定性与拆分：是作为一张「探测失败收口」的窄 bug 交给代理先修，还是保留本票作为总票、把远程工作区支持另开一张设计票？
➡️ 推荐（二次取证后调整）：拆成三件。①把 R1（失败收口与按 errorKind 分档）拆成一张新的 bug 票，标 `ready-for-agent`；②本票保留「面板为什么长期停在探测中、pending 从哪来」这个尚未坐实的问题，标 `needs-info`，请报告人补截图与 affected 工作区日志；③另开一张 enhancement 记 R4（远程工作区仓库根识别），标 `ready-for-human`。理由：整块探测卡与每 5 秒 env 失败在当前源码里不能同时长期成立，先分清界面形态再决定要不要修 pending；R1 的验收可以在本地驱动失败回包完成，不依赖报告人机器。

❓ Q2 状态标签：在报告人补上远程工作区的 detect/selection 日志与界面截图之前，本票按 `ready-for-human` 等拍板，还是先标 `needs-info` 等作者回复？
➡️ 推荐：`needs-info`。理由：字面「正在探测后端」要求 `selection.pending`，而 pending 只来自 30 秒 matches 超时；镜像目录正常几十毫秒就回 no-backend，报告人贴的 73 毫秒日志还来自另一个工作区。整块卡还要求快照，探针失败会把它关掉——「哪一块界面、pending 是否为真」不确认，就没法判断剩下的现象是 bug 还是另一种界面形态。拿到截图与 affected 工作区日志后，本票回 `needs-triage`，再按 Q1 的拆分走。

❓ Q3 远程工作区是否在插件支持范围内：如果不改 DSH、也不要求用户手填仓库根，插件是否接受「远程工作区镜像目录没有 .git 时显示明确终态、不再假装在探测」这一最小目标？还是必须做到「自动从远端读仓库身份」？
➡️ 推荐：先接受最小目标（明确终态 + 停拍），把自动读远端仓库身份留到 DSH 提供接口之后。理由：当前插件没有任何跨机器读 git 的通道，硬做会引入新依赖与权限问题；先让用户看到「为什么用不了、怎么绕」已经解决大部分痛苦。

## 十、二次只读取证（2026-11-03）：更正、界面形态与仍缺证据

这一轮另起了一个只读子代理，把探测链路、失效路径与界面条件重新过了一遍。结论没有翻转（R1 仍是已确认的 bug，R4 仍是设计缺口），但下面这些细节需要更正或补充，已写进上文对应位置。

### 10.1 更正

- **超时常量归属**：`wf.probe` 的 `gh issue list`/GraphQL 走读档 30 秒；15 秒只用于 `gh --version`，25 秒只用于探活档命令，45 秒只用于 REST 兜底读。票面「15/25 秒是探针超时」的前提不成立，但「长窗口 + 冷却再来」的形状成立。
- **快照路径**：宿主磁盘缓存是 `<DSH 进程 cwd>/.dsh-mattskillsdeck-cache`，文件名要 owner/name；票面写的 `~/.dsh/mattskillsdeck-cache/` 与代码不一致。没有文件是镜像目录的预期，但客户端 IndexedDB 仍可能缓存空/pending 快照。
- **空快照的构造点**：旧 `buildSnapshot`（`snapshot-build.ts:417-432`）除 `src/host/index.ts:126` 导出外没有调用点；`wf.snapshot`/`wf.refresh` 的空快照走 `session-snapshot-cache.ts` / `session-refresh-schedule.ts`。这不影响「空 selection 也能成功回快照」的结论，但引用的函数要改。
- **pending 与 `st.selection`**：无 backendId 的 pending 被 `mergeSelection` 拒绝，只能留在 `snapshot.selection`；Dock/StatusBar 读的是 `s.selection || snapshot.selection`，所以界面仍能显示它。

### 10.2 「探测中」可能是四种界面，票面没有区分

| 界面形态 | 触发条件 | 是否要求 pending |
| --- | --- | --- |
| Dock 顶部黄条 / StatusBar 黄条 | `selection.pending` 为真 | 是 |
| Dock 整块卡 | pending + `snapMode==='real'` + 有快照 | 是 |
| `banner.gateReading`「正在读取这个工作区使用哪个后端…」 | 后端未定 + `snapLoading`/`selPending` | 否 |
| `panel.repoLoading`「正在读取仓库信息…」 | 没有 repoRef 且没有快照 | 否 |
| `truth.failRetry`「刷新失败，正在重试」 | `snapMode==='err'` | 否 |

报告人的描述把「探测中」当成一种状态，但只有前两种才读 pending；后三种与 pending 无关。没有截图之前，不能把「面板长期探测中」直接归因到 pending。
