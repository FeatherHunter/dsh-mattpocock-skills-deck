Q5 深挖：TS 文件怎么被「看见」，怎么不再漏登记

2026-10-12 · 写给 TypeScript 新手

一句话总结：文件被谁看见由两处决定——类型检查看 tsconfig 的 include、构建看它自己扫的目录。今天这两处都靠人手登记，所以漏过（locale-cards.ts）；改成「目录通配 + 目录扫描 + 一个文件只属于一个域目录」，就不再有逐文件登记这件事。

1「域」是什么意思

域＝一块代码分区：谁检查它、它允许引用谁，都以它为单位定。它不是文件夹的别名，而是按「谁能引谁」划出来的边界。

今天仓库里已有四个域（每个域配一份自己的 tsconfig）：

域管哪些目录归哪份配置管
客户端界面（像素风真源）src/client/views/** 系列目录、src/client/kernel/ 的一部分tsconfig.client.json
契约层src/tracker/contract/**tsconfig.contract.json
四个计算核（各自一个域）label-color-core/src、refresh-core/src、version-control-core/src、config-store-core/src各自目录下的 tsconfig.json（共 4 份）

将来（地图 #1010 的改造）还会多几个域：src/deck/（deck 工具自己的家）、src/tracker/（跟踪器与契约）、src/host/tracker/rooms/**（三座后端房间，今天叫 backends/）。

域与域之间还有方向：按 ADR §5 的定版，deck 引用 tracker、tracker 引用内核，只能朝下；写反了不许通过。

为什么这件事对 Q5 重要：「登记」就是告诉机器「这个文件属于哪个域」。域划清了，登记这件事才能由「文件放在哪」自动决定。

2tsconfig 是什么

一句话：TypeScript 的配置文件。它告诉 tsc（TypeScript 官方编译器）三件事——① 检查哪些文件；② 用什么语法等级和严格程度检查；③ 要不要产出文件。

今天仓库里有 6 份，没有根上的那份（每份各管一个域）：

配置文件管哪个域include 写的是什么
tsconfig.client.json（:16-25）客户端像素风7 条模式（逐文件 2 条 + 逐目录通配 5 条）
tsconfig.contract.json（:23）契约层["src/tracker/contract/**/*.ts"]
四个核各自的 tsconfig.json各自的核["src/**/*.ts"]（相对自己的核目录）

六份的共同口径（都是「只检查、不产出」）：

"strict": true,           // 严格模式：类型可疑就报错
"target": "ES2020",      // 生成的目标语法版本（保守，宿主与浏览器都跑得动）
"module": "ESNext",      // 用 ES 模块语法
"moduleResolution": "Bundler",
"noEmit": true,          // 只看不产出——真正的 .js 由构建里的 esbuild 生成
"types": []              // 不引任何 @types 包

谁在跑它们（没有 npm run tsc 这种脚本，全是别的脚本顺手拉起）：客户端是 scripts/build.mjs:1089；契约是 tests/verify-contract-types.js:61,275；四个核是各自的 build.mjs 与 tests/verify-*-freshness.js。

别混淆：noEmit: true 不是说「不生成代码」，而是「这次只做检查」。生成 .js 的活由构建脚本里的 esbuild 干。

3include 是什么

一句话：tsconfig 里那条「哪些文件归我检查」的名单。没被 include 圈到的文件，tsc 根本不看——不是「看了说没问题」，而是压根没看。

写法有两种：

  • 逐文件列："src/client/kernel/locale-skilldetail.ts" —— 写谁才检查谁，新增文件必须回来补一行。
  • 目录通配："src/tracker/contract/**/*.ts" —— 这个目录（含子目录）里所有 .ts 都检查，新增文件自动进。

真实事故（这就是「漏登记」长什么样）

文件：src/client/kernel/locale-cards.ts。

  • 构建的目录扫描扫的是 src/client/kernel（scripts/build.mjs:1035 那 5 个目录之一），所以它被转译成了 .js 产物；
  • 但 tsconfig.client.json 的 include 里，kernel 只列了 locale-skilldetail.ts（:24）这一条逐文件写法——没有它；
  • 结果：它转了、能跑，却从来没被类型检查过。

为什么会漏

今天要人记两处：AGENTS.md:49 明确要求「新增 .ts 要同步登记到对应 tsconfig 的 include 与 scripts/build.mjs 清单」。两份名单、两处手工维护，靠人记，迟早漏一边。

注意 tsconfig.client.json:4 那句注释已经过期（写着「只圈 15 个像素风真源加两份声明」），实际包含的文件早已超过这个数——手写名单还会带来第二种债：注释与现实脱节。

4「用目录通配」「构建用目录扫描收集」是什么

它们是同一件事的两半，一边管检查（tsconfig），一边管构建（构建脚本）。

4.1 目录通配（配置侧）

把 include 写成模式而不是文件名：

"include": ["src/deck/**/*.ts"]     // 这个目录里以后新增的 .ts 自动进检查，不用改配置

** 表示「含任意层子目录」，* 表示「任意文件名」。契约层今天已经是这个写法（tsconfig.contract.json:23）。

4.2 目录扫描收集（构建侧）

构建脚本运行时自己去读目录、挑出 .ts，不靠手写文件名。仓里已经有现成例子，就在客户端像素风这条管线上：

  • scripts/build.mjs:1035：PX_TS_DIRS 列了 5 个目录——src/client/views、views/pixel、views/skillDetail、views/cards、src/client/kernel；
  • scripts/build.mjs:1036-1046：pixelTsTruthFiles() 挨个目录 readdirSync，收 *.ts、跳过 *.d.ts；
  • scripts/build.mjs:1047-1082：buildPixelTs() 把收来的每个文件逐个转译成同名 .js（:1057 调用 esbuild）。

所以：这 5 个目录里新增一个 .ts，不用改构建脚本，它就会自动被收进去转译——这正是「目录扫描收集」。

4.3 今天两种登记方式并存的另一套

客户端闭包那条路仍是手写清单，而且登记的是产物 .js，不是真源：

清单位置规模
KERNEL_MODULESscripts/build.mjs:466-557约 60 项
SHARED_SPLICEscripts/build.mjs:567-59713 项
LEAF_MODULESscripts/build.mjs:604-720约 120 项
打个比方：手写清单＝每次进货都要在册子上誊一遍，册子忘了改就少一件；目录扫描＝按货架取货，货架上有什么就拿什么，不用誊册子。

5我们可以避免漏登记吗

可以——改结构就行，既不用靠人记，也不用再加门禁。三层结构性保证：

  • 第一层：tsconfig 的 include 一律写目录通配（如 "src/deck/**/*.ts"）→ 新增 .ts 自动被类型检查看见。
  • 第二层：构建按目录扫描收集（像 pixelTsTruthFiles() 那样读目录）→ 新增 .ts 自动被构建看见。
  • 第三层：一个文件只属于一个域目录 → 归属由「文件放在哪」决定，没有第二处要登记，「两处不一致」这种问题从根上不存在。

再加一条兜底，而且它写进构建脚本本身，不是新加门禁：

  • 某个域扫描到 0 个文件，构建直接失败。目录改名、扫描路径写错、配置漏挂，都会当场红，而不会静默地少编译一批文件。

诚实说清：还剩三种「漏」的残留

  • 新开一个「域目录」时，要在域清单里加一行——那份清单大约 5～10 行（今天就是 PX_TS_DIRS 那 5 个），不是 348 行文件。登记量从「每文件两处」降到「每个新目录一处」。
  • 文件放错域目录不会被发现——症状是产物缺文件或测试加载失败，定位比现在稍绕；重复归属的问题在工程引用上线后由编译器报错兜住。
  • 客户端闭包的拼接顺序仍要手写有序清单——顺序本身就是信息，扫不出来；这块要靠「金标准回执夹具」那条线守（另一张票）。

结论：漏登记从「每个新文件要记两个地方」降成「每个新域目录记一个地方」，locale-cards.ts 那类事故在结构上就不会再出现。
