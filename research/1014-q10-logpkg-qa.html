Q10 深挖：src/host/logPkg/ 是什么，gate-map.mjs 与 DERIVED_PREFIXES 是什么

2026-10-12 · 写给 TypeScript 新手 · 只讲你点名的四件事

一句话总结：这个插件运行时要用的日志库叫 dsh-log；src/host/logPkg/ 里那 4 个 .js 就是它的已编译产物被原样拷进来的本地副本，构建每次都会重新拷一遍。scripts/gate-map.mjs 是「哪扇门禁守着哪些源码文件」那张表的生成器；DERIVED_PREFIXES 是那张表里的一份小名单，用来标记「这是别的包编译后拷进来的目录」。

1src/host/logPkg/ 是干什么的？

它是宿主侧日志库的本地副本目录。日志库叫 dsh-log，已经搬去独立仓库维护（票 #892），本插件从 npm 安装它（package.json:22 写着 dsh-log ^0.2.2），装了以后它躺在 node_modules/dsh-log/。

为什么不直接 import 'dsh-log/host'，而要拷一份进来？两条原因：

  • 宿主这份代码要随插件包一起发布，并且在发布包里被逐文件按相对路径加载（package/package.json 的 files 白名单里有 lib，宿主整树都在里面）。
  • 插件运行时装机环境不一定规则齐全，发布包里自带最稳，不依赖对方包的目录结构。

这 4 个文件是怎么来的

scripts/derive-log-from-package.mjs 把已安装包的 node_modules/dsh-log/dist/ 里四个文件原样复制到 src/host/logPkg/，只在每个文件开头加一段说明头（写明「派生文件、人手不改」），正文一个字节不改。

它是自动跑的：scripts/build.mjs:37 导入这个派生函数，scripts/build.mjs:1105-1110 每次构建都调用一遍。所以这 4 个文件不是靠人手工同步的，它跟着「当前装着的 dsh-log 版本」走。

谁在用它

src/host/logFromPackage.js:11 那一句：

const mod = await import('./logPkg/host.js')

它相对自己解析：源码树里能从 src/host/ 找到这个文件；构建把 src/host 整树原样拷进 package/lib 之后（scripts/build.mjs:818-847），同一个相对路径在发布包里也一样成立。这就是它必须待在 src/host/ 下的原因。源码树里的宿主模块是能被直接加载的（测试就是这么做的，例如 tests/verify-969-tiered-timeout.js:69 直接 import src/host/ 下的模块），所以这条相对引用必须解析得到。

它和旧实现在共存

这次迁移记在票 #564。旧的宿主日志实现 src/host/logStore.js、src/host/logPhones.js 原地留着、只读（有些门禁还在读它们），运行时走上面这条新路；真删旧文件另开票。

和 Q10 直接相关的一点：这 4 个文件是 src/ 下唯一由构建写进来的 .js——所以「src/ 下不再生成 .js」这条规则要落地，就得先给它们一个明白的说法（见第 4 节结尾）。

2那 4 个镜像 .js 又是什么？是 dsh-log 的日志系统吗？

是。它们就是 dsh-log 这个独立日志包的已编译产物，四件各管一摊：

文件管什么
config.js配置与命名：日志目录名、开关文件名、电话名前缀、按天日志文件名；还有事件名册的校验（允许哪些事件、字段、条数）
store.js落盘那一侧：建日志库、攒批写入（去抖）、按天分文件、开关的读写；处理 logBatch 那个电话
phones.js宿主侧另外四个电话的实作：导出日志、清理日志、读开关、写开关（createLogPhones）
host.js组装入口：createHostLog(deps, config) 把存储与电话名装起来；registerHostLogPhones 把五个电话注册进宿主

「电话」是本仓对「宿主与界面之间按名字调用的那条通道」的叫法。日志这套一共五个名字：logBatch、logExport、logClear、logGetSwitch、logSetSwitch；插件标识传的是 wf（src/host/logFromPackage.js:20），拼出来就是 wf.logBatch 这一组。

客户端那一半不在这个目录里：客户端用的是 scripts/generated/logKernel.derived.js，同一个派生脚本从日志包的 dist/client.js 打包出来的单文件，构建时拼进界面那份闭包。

为什么原样拷、不重新编译：这份代码的真源在日志包自己的仓库里，本插件只需要「消费者视角的一份可运行副本」。在本仓重新编译它，等于又造一份真源，改了一边忘了另一边就会漂移。

3scripts/gate-map.mjs 是干什么的？

它是「门禁归属表」的生成器：算出「每扇门禁守着哪些源码路径」，写进 tests/gate-map.json（这份 json 是入库的）。

为什么要有它

npm run verify 是一条两百多步的长链（清单写在 package.json 的 scripts.verify 里），改一个文件就把整条链跑一遍太贵。想要做到「改了 E 目录的代码，就只跑守着 E、守着它的父目录 B、再上一级 A 的门禁」，先得有一张表回答「每扇门禁守着哪些目录」——这张表就是它的产物。

它怎么推出来的

按可信度从高到低认五条来源：① 文件头写了 // 门禁归属: <相对路径> 这类注释的，以它为准；② 读文件（readFileSync 之类）；③ 载入模块（require / import）；④ 静态 import / export ... from 里指向本仓源码的说明符；⑤ 兜底：文件里出现的、指向本仓源码且磁盘上真实存在的字符串字面量。五条都推不出来的，记成 unattributed 并写明原因。

谁在用它

  • scripts/lib/select-gates.mjs：按「这次改了哪些文件」挑出该跑哪些门禁。
  • scripts/verify-parallel.mjs：--changed 与 --tier 两种跑法靠它挑门禁；一条都没选中时会退回全链并提示这是异常。
  • tests/verify-gate-map.js：这张表自己的门禁——表和现状不符就红（verify 长链上有它）。

和本票相关的部分：它的产物里有一节 coverage，专门报「src/ 下哪些文件没有被任何门禁守着」，并且给每一条写一句人能看懂的原因。Q10 想要的「例外被点名，而不是默认容忍」，用的正是这套现成机制。

4DERIVED_PREFIXES 是什么？

它不是什么框架或 TypeScript 的概念，就是 scripts/gate-map.mjs 里的一个常量，一行、一个前缀：

export const DERIVED_PREFIXES = ['src/host/logPkg/']

给「别的包编译好之后拷进来的目录」一个统一记号。用途只有一处：gate-map 在给「没有被门禁守着」的文件写解释时先看这份名单，命中就写——

「这是 src/host/logPkg/ 下的派生文件：由外部包（dsh-log / dsh-plugin-update）的编译产物原样复制进来，本仓库不手写它，正确性由逐字节比对发布包的门禁钉住，所以这里不另设门禁。」

同一份文件里还有几个同类常量，作用都是「把一类目录一次说清」：CODE_ROOTS（哪算本仓源码）、PATH_PREFIXES（哪算可归属路径）、GRAPH_ROOTS（建依赖图扫哪）、BUILD_OUTPUT_PREFIXES（哪是构建产物）。

一个边界要说清：DERIVED_PREFIXES 今天只影响「coverage 报告里的解释文字」这一处（全仓唯一的消费点在 scripts/gate-map.mjs:837）。它不是门禁，不拦任何东西——所以 Q10 建议「把 src/ 下允许出现的 .js 收进一张点名表、由门禁按表判红」时，那张表要落在门禁那侧（tests/verify-build-artifacts.js），不能指望这个常量替你拦住。

它值得记的地方：示范了「例外写在一处、人和机器读的是同一份」的做法——这正是 Q10 那个「logPkg 是例外，但必须是被点名的例外」结论的现成模板。
