## 一、`tsc` 的「程序文件清单」口径是否可靠到可以当判据

### 结论

可以用，但要清楚它的三个口径边界：**① `--listFilesOnly` 省掉的是语义检查，不是语法检查；② 清单是「程序实际读到的全部文件」，不是「本仓手写源码」，必须过滤；③ 清单包含被 import 拉进来的仓库外文件，所以它天然比 `include` 大。**

### 1.1 `--listFilesOnly` 与 `--listFiles` 的区别

**依据（文档，来自编译器自身的 `--all` 帮助文本）：** 跑 `node node_modules/typescript/bin/tsc --all`，三处原文是

```
--listFilesOnly
  Print names of files that are part of the compilation and then stop processing.

--listFiles
  Print all of the files read during the compilation.

--explainFiles
  Print files read during the compilation including why it was included.
```

**依据（源码）：** TS 5.6.3 的 `node_modules/.pnpm/typescript@5.6.3/node_modules/typescript/lib/typescript.js:131432-131469`，`emitFilesAndReportErrors()` 里把「跳过什么」写得很直白：

```js
131434:   const allDiagnostics = program.getConfigFileParsingDiagnostics().slice();
131436:   addRange(allDiagnostics, program.getSyntacticDiagnostics(void 0, cancellationToken));
131441:   if (allDiagnostics.length === configFileParsingDiagnosticsLength) {
131442:     addRange(allDiagnostics, program.getOptionsDiagnostics(cancellationToken));
131443:     if (!options.listFilesOnly) {
131444:       addRange(allDiagnostics, program.getGlobalDiagnostics(cancellationToken));
131446:         addRange(allDiagnostics, program.getSemanticDiagnostics(void 0, cancellationToken));
131452:       if (options.noEmit && getEmitDeclarations(options) && ...) {
```

读法：加 `--listFilesOnly` 时，**配置解析诊断、语法诊断、编译选项诊断照收**（131434 / 131436 / 131442），**全局诊断、语义诊断、声明产物诊断被整段跳过**（131443 那个 `if` 里才是它们）。同一函数 131225-131233 显示 `--explainFiles` 与 `--listFiles`/`--listFilesOnly` 是 if/else 关系，即**三者互斥，`--explainFiles` 赢了的话就不再打普通清单**。

**依据（实测）：** 在 `%TEMP%\ts-research-1020\proj4\`（一份 `strict` 项目，`src/a.ts` 里写着 `export const a: number = "not a number";`）。命令与原始输出：

```
### plain                 exit=1  stdoutlines=1  stderrlines=0
    OUT| src/a.ts(1,14): error TS2322: Type 'string' is not assignable to type 'number'.
### --listFilesOnly       exit=0  stdoutlines=46  stderrlines=0
    OUT| D:/dsh-plugin/.../typescript-win32-x64/lib/lib.es5.d.ts
    OUT| ...（46 行全是文件路径，没有任何诊断行）
### --listFiles            exit=1  stdoutlines=47  stderrlines=0
    OUT| src/a.ts(1,14): error TS2322: ...
    OUT| D:/.../lib.es5.d.ts
### --explainFiles         exit=1  stdoutlines=112  stderrlines=0
### --showConfig           exit=0  stdoutlines=20  stderrlines=0
```

三点从这组数字直接读出来：**输出走 stdout**（`stderrlines=0`）；**有类型错误时 `--listFilesOnly` 退 0**（46 行 = 46 个文件，一条诊断都没有，而 `--listFiles` 是 47 行 = 46 个文件 + 1 条诊断）；**`--showConfig` 与 `--listFilesOnly` 同时给时，`--showConfig` 赢**（两次都只有 20 行 JSON）。

**一个必须知道的例外（实测）：** `--listFilesOnly` 跳的是**语义**检查，语法错误照样报、退出码照样非 0。在 `%TEMP%\ts-research-1020\proj5\`（`src/syntax.ts` 写着 `export const a: number = ;;;`，`src/type.ts` 写着类型错）：

```
### plain ###             src/syntax.ts(1,26): error TS1109: Expression expected.    exit=1
### --listFilesOnly ###   src/syntax.ts(1,26): error TS1109: Expression expected.
                          D:/temp/ts-research-1020/proj5/src/syntax.ts
                          D:/temp/ts-research-1020/proj5/src/type.ts                  exit=1
```

注意它只报了语法那条，没报 `type.ts` 的类型错，但清单还是打全了。**所以「`--listFilesOnly` 退出码永远是 0」是错的**，正确说法是「它不因为类型错而失败，但会因为语法错或配置错而失败」。

干净项目上的对照（`%TEMP%\ts-research-1020\refs5\`）：`--listFiles` 退出码 0。

### 1.2 加 `--listFilesOnly` 时编译器会不会写出任何文件

**结论：不会，一个字节都不写。**

**依据（源码）：** 同一份 `lib/typescript.js:131461`，`emitFilesAndReportErrors()` 里这一行是决定性的：

```js
131461:   const emitResult = options.listFilesOnly ? { emitSkipped: true, diagnostics: emptyArray } : program.emit(...)
```

也就是说 `listFilesOnly` 时 `program.emit()` **根本没被调用**，`emitSkipped: true` 是硬写的，后面的诊断汇总与 `emittedFiles` 遍历因此都是空转。

**依据（实测）：** `%TEMP%\ts-research-1020\proj3\`，配置是 `{"noEmit": true, "incremental": true, "types": [], ...}`——注意 `incremental` 开着正是最容易出 `.tsbuildinfo` 的组合。命令是 `node <tsc> -p . --listFilesOnly`：

```
--- before ---   \src  \tsconfig.json  \src\a.ts
EXITCODE=0
--- after  ---   \src  \tsconfig.json  \src\a.ts
```

再加 `--tsBuildInfoFile "$p3\custom.tsbuildinfo"` 显式指定路径，跑完目录内容同样不变，`custom.tsbuildinfo` 没被创建。

关于 `noEmit` 与 `incremental` / `composite` 的组合副作用，可以这样理解（**这一段是推断**，推断依据是上面那行源码加上 `noEmit` 的语义）：既然 `listFilesOnly` 时 `program.emit()` 完全不被调用，而 `.tsbuildinfo` 是在 emit 阶段写出的，那么无论 `incremental`、`composite`、`noEmit` 怎么组合，只要命令行带了 `--listFilesOnly`，就不会产生写入。本仓六份 `tsconfig` 本来就都是 `noEmit: true` 且没有 `incremental`/`composite`，连推断都不需要——直接就是无副作用。

**顺带一个小实测：本项目里 `.js` 产物与 `.ts` 源码同目录、`.gitignore` 忽略它们，用 `--listFilesOnly` 当门禁不会碰到这些产物**（它不写文件，也就不会产生「产物比源码新」这类时间戳副作用）。

### 1.3 默认（不加 `allowJs`）与 `allowJs: true` 的清单差别

**结论：** 关闭 `allowJs` 时 `.js` 一个都不进清单；打开后进清单的 `.js` 有两类——**被 import 到的**、**`include` 通配到的且没有同名 `.ts` 的**；而**与某个 `.ts` 同名的 `.js` 永远不进**，不管它是否被 import。

42939:      }
42940:      removeWildcardFilesWithLowerPriorityExtension(file, wildcardFileMap, supportedExtensions, keyMapper);
...
43072: function hasFileWithHigherPriorityExtension(file, literalFiles, wildcardFiles, extensions, keyMapper) {
43073:   const extensionGroup = forEach(extensions, (group2) => fileExtensionIsOneOf(file, group2) ? group2 : void 0);
43078:     if (fileExtensionIs(file, ext) && (ext !== ".ts" || !fileExtensionIs(file, ".d.ts"))) {
43079:       return false;
43080:     }

### 1.4 清单里到底有什么：逐项

**（a）`node_modules/@types` 下的类型定义——这一项 TS 7 与 TS 5 的行为不一样，必须分开说。**

实测 `%TEMP%\ts-research-1020\proj2\`：`include` 只圈 `src/**/*`，`node_modules/@types/` 下放了 `foo` 与 `bar` 两个包（各含 `index.d.ts`），`tsconfig` **不写** `types` 字段。

```
TS 7.0.2 --listFilesOnly：
  D:/temp/ts-research-1020/proj2/src/a.ts          ← 只有这一条

TS 5.6.3 --listFilesOnly（同一份 tsconfig、同一份文件）：
  D:/temp/ts-research-1020/proj2/src/a.ts
  D:/temp/ts-research-1020/proj2/node_modules/@types/bar/index.d.ts
  D:/temp/ts-research-1020/proj2/node_modules/@types/foo/index.d.ts
```

TS 5.6.3 的这个行为有源码依据，`lib/typescript.js:43663-43689`：

```js
43663: function getAutomaticTypeDirectiveNames(options, host) {
43664:   if (options.types) {
43665:     return options.types;
43666:   }
43667:   const result = [];
43669:     const typeRoots = getEffectiveTypeRoots(options, host);
43671:       for (const root of typeRoots) {
43673:           for (const typeDirectivePath of host.getDirectories(root)) {
43679:               if (baseFileName.charCodeAt(0) !== 46 /* dot */) {
43680:                 result.push(baseFileName);
```

即：`types` 没写时，把 `typeRoots` 下每个目录都当成一个自动纳入的类型包。**TS 7.0.2 实测不再这么做**，但两条替代路径仍然有效（都是实测）：

```
TS7 + "types": ["foo"]                         → 列出 src/a.ts、node_modules/@types/foo/index.d.ts
TS7 + 源码里写 /// <reference types="bar" />   → 列出 node_modules/@types/bar/index.d.ts、src/a.ts
```

**关于 TS 7 为什么改掉自动纳入全部 `@types`，未找到一手依据**——官方文档与本机资料里没有明文说明；这是「TS 5.6.3 源码行为 vs TS 7.0.2 实测行为」的对照结果，只能算实测差异，不能算官方承诺。落到本仓：六份 `tsconfig` 都显式写了 `"types": []`，两种编译器下都不会自动拉 `@types`，所以这条分歧对本仓当前没有影响；但**将来谁把 `types` 删掉，行为会随编译器版本漂移**。

**（b）`lib.*.d.ts`——进清单，而且数量占绝大多数。** 实测：`proj4` 的清单 46 行里 45 行是 lib 文件，路径指向编译器自带的 lib 目录（TS 7 下是 `node_modules/.pnpm/@typescript+typescript-win32-x64@7.0.2/.../lib/lib.*.d.ts`）。开 `--explainFiles` 能看到它们被纳入的理由，原文形如：

```
../../../dsh-plugin/.../lib/lib.es5.d.ts
   Library referenced via 'es5' from file '.../lib/lib.es2015.d.ts'
```

**所以「拿 `--listFilesOnly` 的输出直接和手写源码集合做等号比较」一定会红**，必须先按后缀或按库标记过滤。TS 7 的 API 提供了现成的过滤器（见 1.5）。

**（c）`include` 匹配到但没人 import 的文件——进。** 实测 RUN 1 里 `src/c.ts`、`src/sub/deep.ts`、`types/manual.d.ts` 都进了清单，而 `c.ts` 没有任何人 import。`--explainFiles` 给的理由是 `Matched by include pattern 'src/**/*' in 'tsconfig.json'`。这也解释了一个常见困惑：**`include` 圈进来的文件无论用不用都会参与类型检查**，这正是「文件清单」与「import 图」不是一回事的原因。

**（d）被 import 进来但不在 `include` 里的文件——也进。** 实测 RUN 1 里 `D:/temp/ts-research-1020/outside/outside.ts` 进了清单，而它**在 `proj` 目录之外**（`include` 是 `["src/**/*", "types/**/*"]`，够不着它）。`--explainFiles` 对 `src/b.ts` 给出的双理由是：

```
src/b.ts
   Imported via "./b" from file 'src/a.ts'
   Matched by include pattern 'src/**/*' in 'tsconfig.json'
```

这条与 (c) 合起来说明了清单的真实定义：**`include`/`files` 匹配到的，加上从它们出发沿 import 可达的**。也顺带说明清单可以「跑出项目目录」，把它当成「本项目的文件集合」时要小心。

### 1.5 有没有官方支持的稳定清单

**分两层回答，推荐前者做机器判据、后者做人工排查。**

**（a）配置层面的清单：`tsc -p . --showConfig`。** 它打印「算完继承与默认值之后的最终配置」，退出码 0。实测 `proj4` 的完整输出：

## 二、怎么断言「一个源文件只属于一个项目」

### 结论

**编译器不会替你拦。** 同一个 `.ts` 被两个 `composite` 项目同时包含，两边都编译通过、退出码 0，没有任何诊断；坏处体现在**产物**上：两个项目会写同一个输出路径，谁最后构建谁的配置说了算。官方文档承认这件事（「otherwise the solution file will cause double compilation of files」），但给的解法是**约定**（solution 文件写 `files: []`），不是开关。

### 2.1 同一文件被两个 composite 项目包含会发生什么

**结论：静默允许，不报错。**

**依据（实测）：** `%TEMP%\ts-research-1020\refs4\` 的结构是这样：

```
refs4/
  root.ts          export const f = (o?: {a:number}) => o?.a;
  tsconfig.json    composite, target ES2020, lib ES2020, module ESNext,
                   moduleResolution Bundler, strict, types [],
                   outDir "out", tsBuildInfoFile "out/root.tsbuildinfo", include ["**/*.ts"]
  sub/
    x.ts           export const g = (o?: {a:number}) => o?.a;      ← 这一份同时落在两个项目里
    tsconfig.json  composite, target ES2015, outDir "../out/sub",
                   tsBuildInfoFile "../out/sub/.tsbuildinfo", include ["**/*.ts"]
```

父项目 `include: ["**/*.ts"]` 覆盖了 `sub/x.ts`，子项目自己也覆盖 `sub/x.ts`，且两者都满足 `composite` 的 `rootDir` 约束（父的 rootDir 推断为 `refs4/`，子的推断为 `refs4/sub/`，各自都装得下自己的文件）。逐条跑：

```
### root --listFilesOnly ###
D:/temp/ts-research-1020/refs4/root.ts
D:/temp/ts-research-1020/refs4/sub/x.ts          ← 父项目的文件清单里有它
EXITCODE=0

### sub --listFilesOnly ###
D:/temp/ts-research-1020/refs4/sub/x.ts          ← 子项目的文件清单里也有它

### root（target ES2020）构建：exit=0
--- out/sub/x.js 内容 ---
export const g = (o) => o?.a;

### sub（target ES2015）构建：exit=0
--- out/sub/x.js 内容 ---
export const g = (o) => o === null || o === void 0 ? void 0 : o.a;
```

**两个项目都退出 0，都没有任何警告，都往 `out/sub/x.js` 这同一个路径写，而文件内容随最后构建者翻转。** 这就是「一个文件属于两个项目」在今天的实际后果：没有红灯，只有产物打架。`root.ts` 那边父项目写 `out/root.js`、子项目不碰，所以只有 `sub/x.ts` 这一份受影响。

**会报错的相邻情形要分清，别把别的东西错当成「重复归属」的报错。** 实测三种：

| 情形 | 报什么 | 退出码 |
| --- | --- | --- |
| 文件不在 `composite` 项目的 rootDir 下（`rootDir` 显式写 `"."`，`include` 却圈了 `../shared/**/*`） | `error TS6059: File 'D:/temp/ts-research-1020/refs/shared/shared.ts' is not under 'rootDir' 'D:/temp/ts-research-1020/refs/a'. 'rootDir' is expected to contain all source files.` 并附 `The file is in the program because: Matched by include pattern '../shared/**/*' in 'D:/temp/ts-research-1020/refs/a/tsconfig.json'` | 2 |
| composite 项目 import 了一个不在自己文件清单里的文件（`include` 只写 `src/entry.ts`，而 `entry.ts` import 了 `./hidden.js`） | `error TS6307: File 'D:/temp/ts-research-1020/refs6/src/hidden.ts' is not listed within the file list of project 'D:/temp/ts-research-1020/refs6/tsconfig.json'. Projects must list all files or use an 'include' pattern.` | 2 |
| 同一文件落在两个 composite 项目里（本节主场景） | **什么都不报** | 0 |

TS6059 报在 `tsc -p` 单项目阶段也报在 `tsc -b` 阶段（实测 `tsc -b --verbose` 里两条都出现，都退 2）。**TS6307 才最接近「这个文件不归你管」的语义，但它管的是「你没登记」，不是「别人登记过了」**——把同一个文件在两个项目里都登记上，它就闭嘴了。

顺带记录一个实测到的危险细节：`refs` 那次 TS6059 的场景下，`tsc -b` **仍然写了产物**（`shared/shared.js`、`shared/shared.d.ts` 直接落在源码目录里），因为默认 `noEmitOnError` 是关的。（`tsc -b` 会把 `noEmitOnError` 当作打开——见 2.2 的 handbook 原文——但那次是单项目 `-p` 阶段写的。）「配置报错但照样往源码树里写文件」这件事本身值得警惕。

### 2.2 官方对「一个文件只能属于一个项目」有没有明文规则

**结论：没有一条以「禁止」措辞写的规则；只有一条对后果的间接承认。**

**依据（文档）：** TypeScript 手册 Project References 页（在线地址 <https://www.typescriptlang.org/docs/handbook/project-references.html>，其 Markdown 源在 `https://raw.githubusercontent.com/microsoft/TypeScript-Website/v2/packages/documentation/copy/en/project-config/Project%20References.md`）「Guidance → Overall Structure」一节原文：

> Another good practice is to have a "solution" `tsconfig.json` file that simply has `references` to all of your leaf-node projects and sets `files` to an empty array (**otherwise the solution file will cause double compilation of files**). Note that starting with 3.0, it is no longer an error to have an empty `files` array if you have at least one `reference` in a `tsconfig.json` file.

这句话是官方资料里唯一直接面对本问题的表述：**它承认会「双重编译」，但把它描述成「solution 文件的一种写法问题」，而不是「编译器会拦你」。** 括号里的 `otherwise` 就是官方给的解法：solution 文件把 `files` 设成空数组。

同一页「`composite`」一节还给了两条会间接限制文件归属的硬约束，原文：

> Referenced projects must have the new `composite` setting enabled. … Enabling the `composite` flag changes a few things:
> - The `rootDir` setting, if not explicitly set, defaults to the directory containing the `tsconfig` file
> - All implementation files must be matched by an `include` pattern or listed in the `files` array. If this constraint is violated, `tsc` will inform you which files weren't specified
> - `declaration` must be turned on

这两条正是 TS6059 与 TS6307 的来源：**`rootDir` 默认锁在 tsconfig 所在目录**，所以「项目外的文件」进不来；**所有实现文件必须被登记**，所以「偷偷 import」会报错。但两条都不管「两个项目都登记了同一个文件」。

同一页「Caveats」一节另有两句与基线/时间戳有关的原文，值得抄下来备查：

> For this reason, `tsc -b` effectively acts as if `noEmitOnError` is enabled for all projects.

> If you check in any build outputs (`.js`, `.d.ts`, `.d.ts.map`, etc.), you may need to run a `--force` build after certain source control operations depending on whether your source control tool preserves timestamps between the local copy and the remote copy.

**所以「一个文件只属于一个项目」在本仓要当一条自定的不变量来守，而不是指望编译器。** 官方推荐的形状是「solution 文件只有 `references` + `files: []`，叶子项目各自 `include` 自己的目录」，靠**目录不重叠**来保证文件不重叠。

### 2.3 有没有办法不自己写扫描就让编译器保证不重复

**结论：没有这样的开关。** 但**不用自己扫目录**也能拿到权威数据——用第一节 1.5 那套公开 API，逐项目取文件清单，再求交集。这不是「扫描」，是「问编译器」。

**依据（实测）：** `tsc --all` 全文搜 `unique|duplicat|overlap|owner`，只命中一个与本问题无关的选项：

```
--deduplicatePackages
Deduplicate packages with the same name and version.
```

**依据（实测）：** 把 1.5 的探针脚本分别指向 `refs3` 的父、子两个 `tsconfig`，原始输出：

```
$ node api-probe.mjs D:\temp\ts-research-1020\refs3\tsconfig.json
projects: 1
PROJECT id= d:/temp/ts-research-1020/refs3/tsconfig.json  config= D:/temp/ts-research-1020/refs3/tsconfig.json
  rootFiles= ["D:/temp/ts-research-1020/refs3/root.ts","D:/temp/ts-research-1020/refs3/sub/x.ts"]
  OWN | D:/temp/ts-research-1020/refs3/root.ts
  OWN | D:/temp/ts-research-1020/refs3/sub/x.ts

$ node api-probe.mjs D:\temp\ts-research-1020\refs3\sub\tsconfig.json
PROJECT id= d:/temp/ts-research-1020/refs3/sub/tsconfig.json  config= D:/temp/ts-research-1020/refs3/sub/tsconfig.json

`sub/x.ts` 在两次输出里都出现，`Project.id` 是 tsconfig 路径。**这十来行代码就构成了「一个文件只能属于一个项目」的判据**：把每个项目的 `rootFiles`（或滤过的 `getSourceFileNames()`）收进一张 `路径 → 项目列表` 的表，任何一条表项长度大于 1 就报错。它不需要自己遍历目录，数据源是编译器自己算出来的程序。

**替代做法（社区通行、但本节没有抓到一手来源，标为推断）：** 靠目录约定把重叠排除掉——每个项目一个独占目录，solution 文件 `files: []`，再用一条「项目的 `rootDir` 互不包含」的自检兜底。第 4.4 节的 Turborepo 明确禁止嵌套包，属于同一思路的官方版本。

**给本仓的建议：** 别自己写目录扫描器。写一个用公开 API 的小脚本（`Project.rootFiles` 或 `getSourceFileNames()` + 两个过滤器），在任何两份清单里出现同一路径就红。等本仓真的上 `composite` 时，这条也就是现成的门禁。

## 三、基线文件（baseline）的行业做法

### 结论

**三家走了三条不同的路：TypeScript 的 `.tsbuildinfo` 是「文件清单 + 每文件内容哈希」，用来回答「变了没有」；dependency-cruiser 的 known violations 是「完整名单」，一条违规一项；ESLint 的 bulk suppressions 是「每文件每规则的计数器」。**「只许缩小」在三家里都有实现，但手法不同：dependency-cruiser 用 `--baseline-mode shrink-only` 明确禁止新增，ESLint 用「多余的 suppression 会让退出码变成 2」来逼你缩。

### 3.1 TypeScript 自己：`.tsbuildinfo` 里记了什么

**依据（实测）：** 在 `refs3` 上跑 `tsc -p tsconfig.json` 得到 `out/root.tsbuildinfo`（5,528 字节，**纯 JSON**）。顶层键与值类型：

```
version : String        root : Object[]        fileNames : Object[]
fileInfos : Object[]    options : PSCustomObject    latestChangedDtsFile : String
```

`version` 是编译器版本 `"7.0.2"`。`fileNames` 是 **47 条**文件名，而且是**相对 buildinfo 所在目录**的短名（`"lib.es5.d.ts"`…`"../root.ts"`、`"../sub/x.ts"`）。`root` 是 `[[46,47]]`——**下标区间**，表示「第 46 到第 47 个是根文件」，不重复存路径。`latestChangedDtsFile` 是 `"./sub/x.d.ts"`。

`fileInfos` 与 `fileNames` 一一对应，每项是**字符串**（只有版本哈希）或**对象**，实测两种形态都在同一个文件里出现：

```json
"lib.es5.d.ts" 对应的项 → "d4306fb2e47f74835e8674ffac07d76f"
"../root.ts"   对应的项 → {"version":"147859212dab419a9f3855f70aeef048",
                          "signature":"482f41f5c9fcbf0ac1f8053e47e4e075",
                          "impliedNodeFormat":1}
```

`options` 只记与增量编译有关的选项：`{"composite":true,"module":99,"outDir":"./","strict":true,"target":7,"tsBuildInfoFile":"./root.tsbuildinfo"}`。

**同一件事在 TS 5.6.3 上（实测，同一形状的项目）** 顶层键相同——`fileNames` / `fileInfos` / `root` / `options` / `latestChangedDtsFile` / `version`——差别只在 `fileNames` 存的是从 buildinfo 出发的长相对路径（`"../../../../dsh-plugin/.../lib/lib.es5.d.ts"`），TS 7 换成了短名。

**它怎么判断「哪些文件变了」：按内容哈希，不按时间戳。**

**依据（实测）：** 在 `refs5` 上做三次受控改动，每次都读 `fileInfos` 里 `src/q.ts` 那一项：

```
--- 首次构建 ---
  {"version":"055d8f1b3db5296fc0fd3b309b9eb009","signature":"184d6c9c8c7ace231a89f8d75b048539","impliedNodeFormat":1}
--- 只改 mtime（内容不动），重新构建 ---
  {"version":"055d8f1b3db5296fc0fd3b309b9eb009","signature":"184d6c9c8c7ace231a89f8d75b048539","impliedNodeFormat":1}   ← 没变
--- 改内容（加一条注释），重新构建 ---
  {"version":"62b841040c6f5e7f5f7e818246d68685","signature":"184d6c9c8c7ace231a89f8d75b048539","impliedNodeFormat":1}   ← version 变了
```

两个结论：**`version` 是内容哈希**（`touch` 改 mtime 不动它，改内容才动它）；**`signature` 是产物的签名**，加一条注释不影响 `.d.ts` 的产出，所以 `signature` 保持不变——`version` 与 `signature` 是两层，前者管输入、后者管输出。

**依据（源码）：** TS 5.6.3 `lib/typescript.js:129868-129902` 是读 `.tsbuildinfo` 建「路径 → 版本」表的函数，第 129875-129878 行：

```js
129875:   program.fileInfos.forEach((fileInfo, index) => {
129876:     const path = toPath(program.fileNames[index], buildInfoDirectory, getCanonicalFileName);
129877:     const version2 = isString(fileInfo) ? fileInfo : fileInfo.version;
129878:     fileInfos.set(path, version2);
```

写出侧在同文件 `128975-129004`，其中 128987 行给出紧凑表示的规则：

```js
128987:       return value.impliedFormat ? { version: value.version, impliedFormat: value.impliedFormat, signature: void 0, affectsGlobalScope: void 0 } : value.version;
```

即：不需要额外元信息时，整个 `fileInfo` 压缩成一个字符串（就是 `version`）。这解释了为什么同一个 `fileInfos` 数组里既有字符串又有对象。

**另有一条「用时间戳」的路径要走清楚（实测）：** `tsc -b` 的「是否最新」判断另有 mtime 快捷路径，原文输出：

```

```

**所以准确的说法是：`tsc -b` 先用 mtime 做粗筛，再用 `.tsbuildinfo` 里的版本哈希做细判。** 这也是 handbook 那句「换机器后时间戳可能不可靠，要 `--force`」的来由。

**它要不要提交进版本库：** 官方文档没找到直接建议。**一手信号是 TypeScript 团队自己的 `.gitignore`**：`https://raw.githubusercontent.com/microsoft/TypeScript/main/.gitignore` 第 38 行是 `*.tsbuildinfo`，第 49 行是 `/built`，第 95 行是 `/lib/`——**他们把 `.tsbuildinfo` 忽略掉**。（「所以业界惯例是不提交」这一句属于**推断**，推断依据就是这条 .gitignore 加「它是本机构建状态的缓存」这一性质。）

### 3.2 dependency-cruiser 的 known violations（baseline）

**一手来源：** 官方文档在仓库里，不是独立站点：`https://github.com/sverweij/dependency-cruiser/blob/main/doc/cli.md`（核对时下载的原文是 71,513 字节，行号按该文件计）。

**`--output-type baseline` 是什么（文档，doc/cli.md:575-578）：**

> #### baseline - generate known violations
>
> Generates a list of all current violations you can use as input for the [`--ignore-known`](#--ignore-known-ignore-known-violations) option.

**注意版本变化（文档，doc/cli.md:861-864）：**

> Previously the recommended way for creating a baseline was to run `depcruise-baseline` - a separate script distributed with dependency-cruiser. As of 18.3.0 `--baseline` is the recommended way.

**`--baseline` 与 `--baseline-mode`（文档，doc/cli.md:832-872）原文：**

> ### `--baseline`: create or update a known violations baseline
>
> This option creates or updates the known violations. For example: `dependency-cruiser src --baseline`
>
> By default known violations go into `.dependency-cruiser-known-violations.json` in the root of your project, but you can pass a different filename as well. When no known violations file exists yet, it'll create one. If one does exist it'll update it, and emit a short summary of the difference:
>
> ```
> baseline  : 19 violations
>
>   new     : 1
>   same    : 18
>   stale   : 8
> ```
>
> To ensure this difference (and future features that build on it) is accurate `--baseline` implies `--no-ignore-known` and `--no-cache`.
>
> > [!NOTE]
> > In the violation comparison the _severity_ is disregarded, so raising or lowering the severity of a violation won't all of a sudden remove violations from the baseline.
>
> ### `--baseline-mode`
>
> Takes one of three values:
> - "full": makes --baseline replace the whole baseline
> - "shrink-only": makes --baseline only _remove_ existing violations, and not add any new ones.
> - "format": makes --baseline rewrite the baseline, but doesn't remove or add anything - only showing the stats.

**「只许缩小」在这里是官方档位**：`--baseline-mode shrink-only`。

**文件结构（实测）：** 本仓 `node_modules` 里装的就是 `dependency-cruiser@18.6.0`。在 `%TEMP%\ts-research-1020\dc\` 造了一个两文件项目（`src/a/a.js` import `src/b/b.js`）加一条触发的规则，跑 `dependency-cruiser src --output-type baseline` 的原始输出：

```json
[
  {
    "type": "dependency",
    "from": "src/a/a.js",
    "to": "src/b/b.js",
    "unresolvedTo": "../b/b.js",
    "dependencyTypes": [ "local", "import" ],
    "rule": { "severity": "error", "name": "no-cross-sibling" }
  }
]
```

**顶层是一个 JSON 数组，一条违规一项**，每项有 `type` / `from` / `to` / `unresolvedTo` / `dependencyTypes` / `rule{severity,name}`。`--baseline` 写出的 `.dependency-cruiser-known-violations.json` 实测内容与上面**逐字节相同**。

**新增违规时它怎么报（实测，三段连续原始输出）：**

```
$ dependency-cruiser src --baseline                       # 第一次建基线
‼ Known violations file '.dependency-cruiser-known-violations.json' does not exist yet.
  Will assume an empty current violations set and create a new one instead.

baseline  : 1 violations

  new     : 1 (running in 'full' mode => added to the baseline)
  same    : 0
  stale   : 0

# —— 这里加了一条新规则并让 b 反向 import a，制造第二条违规 ——

$ dependency-cruiser src --ignore-known

exit=1

  error no-back-edge: src/b/b.js → src/a/a.js
x 2 dependency violations (2 errors, 0 warnings). 2 modules, 2 dependencies cruised.
exit=2

$ dependency-cruiser src --baseline --baseline-mode shrink-only

  new     : 1 (running in 'shrink-only' mode => not added to the baseline)
  same    : 1
  stale   : 0

**「已知的当作已知、只有新的才失败」这句语义的实现方式在文档里有原文（doc/cli.md:888-898）：**

> #### How dependency-cruiser ignores known violations
>
> For all violations dependency-cruiser finds in the known violations file it will lower the severity to `ignore`. It depends on the reporter how these show up. E.g. the `err`/ `err-long` reporters will hide all ignored violations, but add a warning if there's violations ignored:
>
> ```
> ✔ no dependency violations found (454 modules, 1078 dependencies cruised)
> ⚠ 20 known violations ignored. Run with --no-ignore-known to see them.
> ```

**注意它不是「查表跳过」而是「降级成 `ignore` 严重度」**——所以报告里仍然会念一句「忽略了 N 条已知违规」，不会假装不存在。

### 3.3 ESLint 有没有官方基线（bulk suppressions）

**有，官方名叫 bulk suppressions。**

**一手来源：** 在线文档 <https://eslint.org/docs/latest/use/suppressions>，其源码在 <https://raw.githubusercontent.com/eslint/eslint/main/docs/src/use/suppressions.md>（本文引用行号按该 Markdown 计）。

**它解决什么（文档，suppressions.md:10-16）：**

> Enabling a new lint rule as `"error"` can be challenging when the codebase has many violations and the rule isn't auto-fixable. … To address this, ESLint provides a way to suppress existing violations for one or more rules. While the rule will be enforced for new code, the existing violations will not be reported.
>
> ::: important
> Only rules configured as `"error"` are suppressed. If a rule is enabled as `"warn"`, ESLint will not suppress the violations.
> :::

**命令行开关（文档，suppressions.md:18-36 与 command-line-interface 的选项表 136-140）：**

```
--suppress-all                   Suppress all violations - default: false
--suppress-rule [String]         Suppress specific rules
--suppressions-location path::String  Specify the location of the suppressions file
--prune-suppressions             Prune unused suppressions - default: false
--pass-on-unpruned-suppressions  Ignore unused suppressions - default: false
```

**suppressions 文件长什么样、要不要提交（文档，suppressions.md:38-46）：**

> When you suppress violations, ESLint creates a `eslint-suppressions.json` file in the root of the project. This file contains the list of rules that have been suppressed. **You should commit this file to the repository** so that the suppressions are shared with all the developers.

**它怎么处理「违规数只降不升」——这是本节最关键的一段（文档，suppressions.md:48-67）：**

> ## Resolving Suppressions
>
> You can address any of the reported violations by making the necessary changes to the code as usual. If you run ESLint again you will notice that it **exits with a non-zero exit code and an error is reported about unused suppressions.** This is because the violations have been resolved but the suppressions are still in place.
>
> ```bash
> > eslint
> There are suppressions left that do not occur anymore. Consider re-running the command with `--prune-suppressions`.
> ```
>
> To remove the suppressions that are no longer needed, you can use the `--prune-suppressions` flag.

CLI 参考里把退出码写死了（文档，`command-line-interface.md:825-827`）：

> #### `--pass-on-unpruned-suppressions`
>
> Ignore unused suppressions. **By default, ESLint exits with exit code `2`** and displays an error message if there are unused suppressions in the suppressions file. When you use this flag, unused suppressions do not affect the exit code and ESLint doesn't output an error about unused suppressions.

**所以 ESLint 的「只许缩小」不是靠「禁止新增」（新增自然会被报出来），而是靠「suppression 一旦不再命中就变红」——你修好了违规却忘了从名单里删掉，门禁就红。** 这个设计和 dependency-cruiser 的 `stale` 统计是同一个诉求的两种表达（dependency-cruiser 把 stale 只是「报个数」，ESLint 把它变成红灯）。

**文件结构（源码）：** 文档里没给 JSON 示例，但 ESLint 自己的源码给了类型定义。`https://raw.githubusercontent.com/eslint/eslint/main/lib/services/suppressions-service.js` 第 24 行：

```js
/** @typedef {Record<string, Record<string, { count: number; }>>} SuppressedViolations */
```

即 `{ "<文件相对路径>": { "<规则名>": { "count": 数字 } } }`，用 `json-stable-stringify-without-jsonify` 以两空格缩进写出（同文件第 15 行 import、第 240-242 行写文件）。

**它是计数器，不是逐条名单——这一点在源码里写得很清楚（同文件 131-133、172-174、251-255）：**

```js
131:     * For each file, counts the number of violations per rule.
132:     * For each rule in each file, compares the number of violations against the counter from the suppressions file.
133:     * If the number of violations is less or equal to the counter, messages are moved to `LintResult#suppressedMessages` and ignored.
...
172:         // Suppress messages if the number of violations is less or equal to the suppressions count
174:           SuppressionsService.suppressMessagesByRule(result, ruleId);
...
251:   static countViolationsByRule(messages) {
253:       if (message.severity === 2 && message.ruleId) {
254:         totals[message.ruleId] ??= { count: 0 };
255:         totals[message.ruleId].count++;
```

读法：抑制的判定是「**当前违规数 ≤ 记录的数**」，且只数 `severity === 2`（即 error）的消息——与文档那句「只有配置成 `"error"` 的规则才被抑制」严丝合缝。

**版本信息：** RFC 目录 `https://api.github.com/repos/eslint/rfcs/contents/designs` 下有 `2021-suppression-support`、`2025-bulk-suppressions-api`、`2026-respect-suppressions-during-autofix` 三份相关设计，说明这个能力是分批落地的。**具体在 ESLint 哪个版本首次可用，本次没有抓到一手发布说明，未找到一手依据**，不要照抄某个版本号。

### 3.4 几百到几千个成员的「只许缩小」集合：完整名单还是计数器 + 指纹

**结论：两种都有真实先例，而且分界线很干净——看「一条记录能不能稳定地指认一个成员」。** 能，就记完整名单；不能（或者说，成员的身份天然是「某个文件里的某条规则」，条数会随代码挪动而漂移），就记计数器；如果问题根本不是「允许哪些存在」而是「变了没有」，那就记哈希。

**完整名单派（依据：实测，见 3.2）。** dependency-cruiser 一条违规一项，`from` / `to` / `rule.name` 三者合起来唯一指认一条违规，天然可去重、可排序、可进 diff，所以它选了完整名单。取舍在官方文档里也能看到两处：一是「比对时忽略 severity」（doc/cli.md:856-859），因为 severity 是策略不是身份；二是 `stale`（名单里有、现在不再出现）只是统计一个数，不当失败——因为它假设你会主动跑 `--baseline` 收缩。

**计数器派（依据：文档 + 源码，见 3.3）。** ESLint 每（文件, 规则）一个 `count`。一千条违规如果落在 200 个文件 × 5 条规则里，文件里最多 1000 条记录，但如果集中在少数文件里就只剩几十条——**文件明显更小**。代价写在源码逻辑里（172-174）：判定条件是「不超过计数」。也就是说，**同一个文件里同一规则的违规从第 3 行挪到第 90 行，计数不变，门禁完全看不见**；把一条老违规修掉同时新增一条同规则的新违规，计数也不变。ESLint 接受这个代价，因为它抑制的粒度本来就是「这个文件里的这条规则」，不是「这一行」。它用「多余的 suppression 让退出码变 2」补上了收缩这一侧。

**指纹派（依据：实测 + 源码，见 3.1）。** `.tsbuildinfo` 每文件存一个内容哈希（外加一个产物签名），**不记「允许哪些存在」**。它回答的是一个不同的问题：「和上次比，什么变了」。所以它天然没有「只许缩小」这个概念——集合本身不受门禁约束，受约束的是「有没有变化」。

**给本仓的建议（这一段是推断，推断依据是上面三家的分界）：** 如果这条基线要管的成员天然是三元组（例如「某文件 import 了某文件，违反某规则」），学 dependency-cruiser 记完整名单——可 diff、可逐条审计、可对每条写理由。如果成员的天然粒度是「某文件里有几条某类问题」，学 ESLint 记计数器更省，但必须**同时**把「多余的记录会让门禁变红」这一侧做上，否则计数器只会永远不缩。**几百到几千这个量级本身不是决定因素**——dependency-cruiser 的示例里就有 19 条 tally 对应 8 条 stale，说明量级不是它选完整名单的理由；决定因素是「能不能稳定指认一个成员」。

## 四、枚举「仓库手写源码集合」的判据

### 结论

**判据本身很简单：`git ls-files -z --cached --others --exclude-standard`，读的时候必须按 NUL 切。** 但有两个会静默出错的坑：`'**/xxx'` 这样的 pathspec **匹配不到仓库根上的文件**；PowerShell 不认 NUL 分隔，`git ls-files -z` 在 pwsh 里会变成一整条字符串。至于「成熟仓库怎么保证源码集合等于被检查集合」，Bazel 走登记表，Turborepo/pnpm 走目录约定加存在性标记。

### 4.1 `git ls-files` 各种组合的语义与坑

**一手来源：** git 官方手册页 `https://git-scm.com/docs/git-ls-files`，其源码文档是 `https://raw.githubusercontent.com/git/git/master/Documentation/git-ls-files.adoc`（本文引用行号按这份 adoc 计）。

**逐条原文（文档，git-ls-files.adoc:38-108）：**

```
38: -c::
39: --cached::
40: 	Show all files cached in Git's index, i.e. all tracked files.
41: 	(This is the default if no -c/-s/-d/-o/-u/-k/-m/--resolve-undo
42: 	options are specified.)

53: -o::
54: --others::
55: 	Show other (i.e. untracked) files in the output

57: -i::
58: --ignored::
59: 	Show only ignored files in the output.  Must be used with
60: 	either an explicit '-c' or '-o'.  ...
64: 	Standard ignore rules are not automatically
65: 	activated; therefore, at least one of the `--exclude*` options
66: 	is required.

100: 	\0 line termination on output and do not quote filenames.
101: 	See <<OUTPUT,OUTPUT>> below for more information.

103: --deduplicate::

105: 	come from having multiple stages during a merge, or giving
106: 	`--deleted` and `--modified` option at the same time.

128: 	Add the standard Git exclusions: .git/info/exclude, .gitignore

```

**坑一：`--others` 单用会漏过滤。** 上面 64-66 行那句「Standard ignore rules are not automatically activated; therefore, at least one of the `--exclude*` options is required」是针对 `--ignored` 说的，但它揭示的机制是通用的：**`ls-files` 不会自动套 `.gitignore`，除非你显式要。** 所以 `--others` 必须配 `--exclude-standard`，否则 `node_modules` 之类会被吐出来。

**`--cached --others --exclude-standard` 是不是「仓库认为存在的全部非忽略文件」的正确写法？** **官方文档里没有一句话直接这么说——未找到明文表述。** 下面这条是**推断**，推断依据是上面三条各自的定义加上 `--exclude-standard` 会把「标准忽略来源」（`.git/info/exclude`、各级 `.gitignore`、全局排除文件）全加上：`--cached` 给已跟踪的、`--others` 给未跟踪的、`--exclude-standard` 把被忽略的从后者里剔掉，三者并起来正好是「存在于工作区、且没有被仓库的忽略规则排除掉的文件」。本仓实测与之吻合：

```
cached       = 1574
others-excl  = 0
union        = 1574
plain        = 1574        # git ls-files 不带参数，等价于 --cached
```

（`plain` 等于 `cached` 印证了 41-42 行那句「`--cached` 是默认」。当前工作区干净所以 `others-excl` 是 0；这恰好也说明**这份判据在干净工作区与「等于 `--cached`」重合，在有人改了没提交时才显出价值**。）

**坑二：`--deduplicate` 多数时候没作用。** 官方说得清楚（103-108）：只在「只显示文件名」且存在重复来源（merge 多阶段、同时给 `--deleted` 和 `--modified`）时才起作用。实测本仓两者都是 1574：

```
no-dedup     = 1574        # git ls-files -c -o --exclude-standard
dedup        = 1574        # 同上加 --deduplicate
```

**要看「哪些文件被 git 跟踪」这个最稳的做法，官方自己在 `-t` 选项里给了一句推荐（文档，git-ls-files.adoc:142-148）：**

```
142: -t::
143: 	Show status tags together with filenames.  Note that for
144: 	scripting purposes, linkgit:git-status[1] `--porcelain` and
145: 	linkgit:git-diff-files[1] `--name-status` are almost always
146: 	superior alternatives; users should look at
147: 	linkgit:git-status[1] `--short` or linkgit:git-diff[1]
148: 	`--name-status` for more user-friendly alternatives.
```

注意这句推荐的是「要状态标签时改用 `git status --porcelain`」，**不是**说 `ls-files` 不适合脚本——`-t` 输出的是人类看的标签，机器判据仍然该用 `ls-files`。

### 4.2 `'**/tsconfig.json'` 为什么不匹配仓库根上的 `tsconfig.json`

**结论（实测，先说结果）：确实不匹配——但要注意本仓根上根本没有 `tsconfig.json`（只有 `tsconfig.client.json` 与 `tsconfig.contract.json`），所以我拿 `AGENTS.md` / `package.json` / `*.md` 做了等价验证。**

**依据（实测，全部在本仓跑，只读）：**

```
$ git ls-files '**/package.json'
package/package.json
count=1                                   ← 根上的 package.json 不在结果里

$ git ls-files 'package.json'
package.json                              ← 不带通配的写法才拿到根上那份

$ git ls-files '**/AGENTS.md'
（空）

$ git ls-files ':(glob)**/AGENTS.md'
AGENTS.md                                 ← 加上 :(glob) 才拿到根上那份

$ git ls-files '*.md'            → 328
$ git ls-files ':(glob)**/*.md'  → 328
$ git ls-files '**/*.md'         → 323     ← 少的正好是 5 条
```

那 5 条就是根目录下的 `AGENTS.md`、`CHANGELOG.md`、`CONTEXT.md`、`README.md`、`SECURITY.md`。**328 − 323 = 5，缺口精确等于根上 `.md` 的数量**，这是本条结论最干净的证据。

**为什么（文档）：** git 的 pathspec 定义在 `https://raw.githubusercontent.com/git/git/master/Documentation/glossary-content.adoc`（`gitglossary` 的手册源），第 351-373 行原文：

```
351: [[def_pathspec]]pathspec::
352: 	Pattern used to limit paths in Git commands.
...
360: 	The pathspec syntax is as follows:
364: * any path matches itself
365: * the pathspec up to the last slash represents a
366:   directory prefix.  The scope of that pathspec is
367:   limited to that subtree.
368: * the rest of the pathspec is a pattern for the remainder
369:   of the pathname.  Paths relative to the directory
370:   prefix will be matched against that pattern using fnmatch(3);
371:   in particular, '*' and '?' _can_ match directory separators.
375: For example, Documentation/*.jpg will match all .jpg files
376: in the Documentation subtree,
377: including Documentation/chapter_1/figure_1.jpg.
```

读法：**默认的 pathspec 是「最后一个斜杠之前当目录前缀」的模型。** `'**/tsconfig.json'` 的最后一个斜杠之前是 `**/`，于是 `**` 被当成一层目录前缀，只有「至少往下走一层」的路径才会被匹配——根上的同名文件永远落在前缀之外。这也解释了 371 行那句「`*` 和 `?` **可以**跨目录分隔符」：所以不带斜杠的 `'*.md'` 反而能匹配任意深度。

**正确写法有两种，都在上面实测过：**

| 写法 | 效果 | 适用 |
| --- | --- | --- |
| `':(glob)**/tsconfig.json'` | 按 wildmatch 语义，`**/` 可以匹配零层，根上的也拿到 | 想要「任意深度、含根」时最直观 |
| `'*.md'` 这类不带斜杠的模式 | 因为 `*` 能跨 `/`，等价于任意深度 | 后缀/文件名匹配时最短 |

`:(glob)` 这个前导是 pathspec 的 magic signature（gitglossary:379-394），把匹配从默认模型切换到 wildmatch。而 wildmatch 下 `**/` 的语义有明文（同一份 gitglossary 的 418-431 行）：

```
418: Two consecutive asterisks ("`**`") in patterns matched against
...
421:  - A leading "`**`" followed by a slash means match in all
422:    directories. For example, "`**/foo`" matches file or directory
423:    "`foo`" anywhere. "`**/foo/bar`" matches file or directory "`bar`"
```

顺带一条对照：**这条 `**/foo` 的语义是 `.gitignore` 匹配规则下的**（那段在讲 gitignore 模式），不能拿来推断 `ls-files` 的默认 pathspec 行为——两者恰好相反，这正是本节两个实测结果不一致的来源。**把 gitignore 的直觉套到 pathspec 上就是 4.2 这个坑。**

### 4.3 有没有比 git 更合适的判据（路径含空格或中文时哪种写法不会出错）

**（a）路径含空格或非 ASCII：只有 `-z` 是跨环境稳定的。**

**依据（文档，git-ls-files.adoc:254-257）：**

```
254: Without the `-z` option, pathnames with "unusual" characters are
255: quoted as explained for the configuration variable `core.quotePath`
256: (see linkgit:git-config[1]).  Using `-z` the filename is output
257: verbatim and the line is terminated by a NUL byte.
```

**依据（实测）：** 本仓有 **82 个非 ASCII 路径**、**0 个含空格的路径**。取 `assets/init/1-创建新工作区-中文版.png` 试：

```
$ git ls-files assets/init/1-创建新工作区-中文版.png
assets/init/1-创建新工作区-中文版.png

$ git -c core.quotePath=false ls-files <同上>
assets/init/1-创建新工作区-中文版.png

$ git ls-files -z <同上>  → 前 31 个字节：
97,115,115,101,116,115,47,105,110,105,116,47,49,45,229,136,155,229,187,186,230,150,
176,229,183,165,228,189,156,229,140
```

字节序列 `229,136,155` 就是「创」的 UTF-8。**在本机这套环境（git 2.49 Windows、pwsh）里非 `-z` 也直接给了 UTF-8 原文，没有出现八进制转义**——但文档说的是「取决于 `core.quotePath`」，也就是**它会随环境变**。所以要一条不会因机器而异的写法，只能用 `-z`。

**（b）PowerShell 的坑（实测，这个坑会静默出错）：**

```
$ $all = & git ls-files -z
single-string-length=59564  items=1
```

`git ls-files -z` 输出的是 NUL 分隔的字节流（本仓 1574 条路径共 59564 字符），但 **PowerShell 只按换行切分记录，不认 NUL**，于是整份清单被当成**一个**字符串交给你。后果是「循环遍历」变成「只跑一次、内容是全部路径拼在一起」，如果后面接的是 `Test-Path` 之类的判断，不会报错，只会给出一个安静的错答案。正确做法是自己切：

```powershell
$paths = (& git ls-files -z --cached --others --exclude-standard) -join '' -split "`0" | Where-Object { $_ -ne '' }
```

Node 里则要用 Buffer：`execFileSync('git', ['ls-files','-z'], { maxBuffer: Infinity }).toString('utf8').split('\0')`——**注意 `execFileSync` 默认 `maxBuffer` 是 1 MiB，本仓 59564 字符还不至于，但几万文件的仓库会直接截断**。

**（c）`git check-ignore --no-index`：语义清楚，但回答不了「有哪些文件」。**

**依据（文档，`https://git-scm.com/docs/git-check-ignore` 的原文）：**

> By default, tracked files are not shown at all since they are not subject to exclude rules; but see `--no-index`.
>
> `--no-index`:: Don't look in the index when undertaking the checks. This can be used to debug why a path became tracked by e.g. `git add .` and was not ignored by the rules as expected by the user or when developing patterns including negation to match a path previously added with `git add -f`.
>
> EXIT STATUS
> `0`:: One or more of the provided paths is ignored.
> `1`:: None of the provided paths are ignored.
> `128`:: A fatal error was encountered.

**依据（实测，临时仓库）：**

```
check-ignore tracked.txt              → 无输出   exit=1     # 已跟踪，默认不参与判断
check-ignore --no-index tracked.txt   → 无输出   exit=1     # 该路径确实没被忽略规则命中
check-ignore ignored.txt              → ignored.txt  exit=0
check-ignore -q ignored.txt           → 无输出   exit=0
check-ignore nope.txt                 → 无输出   exit=1
```

**它的定位是「给一个路径，回答它是否被忽略」，所以要么为每个路径调一次（慢），要么用 `--stdin` 批量喂（文档里有 `--stdin` 与 `-z` 的组合说明）。它不能替代 `ls-files` 的枚举职责**——注意上面 `--no-index tracked.txt` 也返回 1，说明它对「已跟踪但没被忽略规则命中」的路径同样什么都不说，这两种情况在退出码上区分不开。

**（d）`git status --porcelain -z`：机器可读，但问的是另一个问题。**

它的官方手册在 `https://git-scm.com/docs/git-status`（源 `Documentation/git-status.adoc`），`-z` 段落说明用 NUL 终止并禁用路径引号。实测本仓收工时 `git status --porcelain -z` 返回 0 条，即工作区干净。**但 `status` 回答的是「工作区相对于索引有什么变化」，不是「仓库里有哪些文件」**——用它当源码集合判据会把未修改的文件整批漏掉。

**（e）推荐做法（本节结论）：**

```
git ls-files -z --cached --others --exclude-standard      # 加上自己按 NUL 切
```

- 要「只算已提交的」（例如跟一份提交进仓库的基线文件比对）→ 去掉 `--others`，只留 `--cached`。
- 要「连未提交的新文件一起算」（本地门禁更实用）→ 保留 `--others --exclude-standard`。
- **永远别用 `'**/xxx'` 这种 pathspec**；要跨深度就用 `':(glob)**/xxx'` 或干脆不带斜杠。
- **永远用 `-z`**，并且在 pwsh 里记得自己切 NUL。

### 4.4 成熟仓库怎么保证「源码集合 = 被检查集合」

挑两个做法相反、都能抓到一手文档的：**Bazel 走登记表，Turborepo（配合 pnpm workspace）走目录约定。**

**Bazel：登记表，而且官方明确反对递归 glob。**

**依据（文档）：** `https://bazel.build/build/style-guide` 的「Globs」一节原文（本文按纯文本化后的行号计）：

```
127:  Globs
128:  Indicate “no targets” with [] . Do not use a glob that matches nothing: it
129: is more error-prone and less obvious than an empty list.
130:  Recursive
131: Do not use recursive globs to match source files (for example,
132: glob(["**/*.java"]) ).
133: Recursive globs make BUILD files difficult to reason about because they skip
134: subdirectories containing BUILD files.
135: Recursive globs are generally less efficient than having a BUILD file per
136: directory with a dependency graph defined between them as this enables better
137: remote caching and parallelism.
138: It is good practice to author a BUILD file in each directory and define a
139: dependency graph between them.
140:  Non-recursive
141: Non-recursive globs are generally acceptable.
```

读法：**Bazel 的「哪些文件是一个目标的源码」写在 BUILD 文件的 `srcs` 里，是登记表**；它允许非递归 glob 当作便利写法，但**明确禁止用递归 glob 去圈源码**，理由是「会跳过含有 BUILD 文件的子目录」——也就是说，**Bazel 用「每个目录一个 BUILD 文件」这条约定，把「一个文件归谁管」变成了结构上唯一确定的**。这和第二节那个「一个 `.ts` 落在两个 composite 项目里」的问题正好是同一个问题的两种解法：Bazel 用目录边界把重叠定义成不可能。

（Bazel 的 BUILD 文件概念页在 `https://bazel.build/concepts/build-files`，本次抓到的是 297,953 字节的 HTML，未逐段引用，只作背景。）

**Turborepo + pnpm：目录约定 + 存在性标记，而且明确禁止嵌套包。**

**依据（文档）：** `https://turborepo.com/docs/crafting-your-repository/structuring-a-repository` 原文（纯文本化后按行计）：

```
turbo is built on top of Workspaces, a feature of package managers in the
JavaScript ecosystem that allows you to group multiple packages in one repository.
...
Declaring directories for packages
First, your package manager needs to describe the locations of your packages. We
recommend starting with splitting your packages into apps/ for applications and
services and packages/ for everything else, like libraries and tooling.
...
Using this configuration, every directory with a package.json in the apps or
packages directories will be considered a package. Turborepo does not support
nested packages like apps/** or packages/** due to ambiguous behavior among
package managers in the JavaScript ecosystem. Using a structure that would put a
package at apps/a and another at apps/a/b will result in an error.
...
In the directory of the package, there must be a package.json to make the package
discoverable to your package manager and turbo.
```

**三层机制叠起来：** ① `pnpm-workspace.yaml` 的 `packages:` 字段用 glob 圈出**候选目录**（pnpm 文档 `https://pnpm.io/workspaces` 说明 `pnpm-workspace.yaml` 是唯一被读的源，原文：“If the `workspaces` field later lists different patterns than `packages` in `pnpm-workspace.yaml`, pnpm prints a warning, since only `pnpm-workspace.yaml` is read.”）；② 目录里**有没有 `package.json`** 决定它是不是一个包；③ **嵌套包直接报错**——`apps/a` 与 `apps/a/b` 同时存在就失败。

**为什么这样设计（官方给的理由，就在上面那段里）：** “due to ambiguous behavior among package managers in the JavaScript ecosystem”——嵌套包在各家包管理器里的行为不一致，与其猜，不如禁止。**这和本仓要的「一个源文件只属于一个项目」是同一个诉求：与其事后检测重叠，不如让重叠在结构上不可能。**

**两者对照（本节结论）：**

| | Bazel | Turborepo + pnpm |
| --- | --- | --- |
| 靠什么界定集合 | **登记表**：BUILD 文件的 `srcs` 逐条列 | **目录约定 + 存在性标记**：workspace glob 圈目录，`package.json` 标记包 |
| 对 glob 的态度 | 非递归可接受，**递归明令禁止** | 只用单层 glob（`apps/*`、`packages/*`），**`apps/**` 直接报错** |
| 保证「不重叠」的手法 | 每个目录一个 BUILD 文件，边界由目录唯一确定 | **禁止嵌套包**，重叠结构上不可能 |
| 官方给的取舍理由 | 递归 glob 会跳过含 BUILD 的子目录；不利于远程缓存与并行 | 嵌套包在跨包管理器时行为有歧义 |

两者殊途同归的地方是：**都不靠「扫描全仓再检测重叠」，而是靠一条能让重叠不可能出现的结构约定。** 本仓如果走 project references，可用的对应约定是官方 handbook 那句——solution 文件只写 `references` 并把 `files` 设成空数组，叶子项目各自独占一个目录。

6. **`--listFilesOnly` 在 `noEmit` / `incremental` / `composite` 组合下「不会写文件」这一点，在 TS 7 上没有源码级依据。** TS 7 是原生二进制，`lib/typescript.js` 不存在；该结论在 TS 7 上只有实测（三次跑完目录内容逐条比对一致），机制解释借的是 TS 5.6.3 的源码。
