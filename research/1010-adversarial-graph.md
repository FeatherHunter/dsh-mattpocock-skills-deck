## 二、环检测

### 方法与证据

自己写的判据（不是靠 GitHub 拒收边来推断）：

1. 把 118 条边读成有向图 `blocker → blocked`。
2. **三色 DFS 枚举**所有回边：结果 `[]`，一个环也没有。
3. **Kahn 拓扑排序**：入队计数 **109 = 节点总数**，即全部节点可拓扑排序，无环。
4. 重复边 0 条，悬挂边 0 条（每条边的两端都在 109 个节点里）。

结论：**现有图无环，证据是拓扑序长度等于节点总数。**

### 但它是「差一条边就闭合」的临界图

我按维护者「严格串行」的要求试加了一条边 —— **「地图 04 的讲解 #1036 要在 地图 05 的讨论 #1038 之前」**（这正是「每张地图的讨论票等上一张地图的讲解票」这条串行规则里的一条）—— 立刻出现环：

```
1027 → 1031 → 1035 → 1036 → 1038 → 1040 → 1044 → 1048 → 1052 → 1027
```

这条环里**只有 `#1036 → #1038` 是我新加的，其余 9 条全是现有边**。把它读成人话：

> 契约的两房对齐（#1027）要等 GitHub 房开发票（#1052）；
> GitHub 房读路径（#1052）要等识别判定（#1048）；
> 识别判定（#1048）要等注册表（#1044）；
> 注册表（#1044）要等工具壳宿主侧（#1040）；
> 宿主侧（#1040）要等工具壳讨论（#1038）；
> 工具壳讨论（#1038）按严格串行要等地图 04 的讲解（#1036）；
> 地图 04 讲解（#1036）要等工具入口转完（#1035）；
> 工具入口（#1035）要等注册与装配（#1031）；
> 注册与装配（#1031）要等契约的两房对齐（#1027）。**闭环。**

同样的实验用完整串行链（13 条）跑，得到一条 **19 个节点的环**：
`1027 → 1028 → 1030 → 1031 → 1032 → 1034 → 1035 → 1036 → 1038 → 1040 → 1041 → 1043 → 1045 → 1047 → 1048 → 1049 → 1051 → 1054 → 1027`。

### 结论

**「严格串行」（`research/1010-consensus.md` 第三节）与「契约的两房 implements 等两房改造完」（`#1027` 票面、`research/1010-ticket-structure.md` §9.5/§10.3）不能同时成立。** 现有图之所以没环，只因为地图 05 的纯规则侧 #1039 没有任何出边——它是一条**断头路**，把本该闭合的圈断开在那里。谁顺着「串行」补一条边，圈就闭上。

**这不是「一处偏离」，是把两套顺序写在了一起**，正是该文件 §8「必改之三」自己撤掉的那个毛病。

### 逐边「删掉会怎样」

对 118 条边逐条做「删掉它、重算分层、看谁提前开工」：**52 条卡时间，66 条不卡时间**（完整清单在 JSON 的 `边的卡时间分析`）。不卡时间不等于可删——大多数是「本图开发票被本图讨论票阻塞」这类约定，被跨图长链的层数盖住了。但这个数字本身说明一件事：**图内那些边几乎不决定排期，真正决定谁先谁后的是那条跨图主链。**

## 四、错边清单（该删的）

### D1｜删 `1014 → 1022`（地图01讨论 → 地图01讲解）

- 理由：自家规则是「讲解票被**本图各开发票**阻塞」，#1014 是讨论票，不是开发票。`research/1010-ticket-structure.md` §12 描述这条时写的是「1015–1021 与 #1023」，也没算它。
- 删掉会怎样：**没有任何票提前开工**。#1015–1021、#1023 全都传递依赖 #1014。纯冗余边，留着会让读者以为讲解要等讨论。
- 删后谁能开工：不变。

### D2｜删 `1035 → 1039`，改成 `1039 → 1035`（方向反了）

- 理由（**代码证据**）：`src/shared/deck-tools/` 下这 10 件正是 #1039 要抽出/改造的对象；九个工具入口对它们的依赖实测是：
  - `shell` 9/9、`call-scope` 9/9、`session-resolve` 9/9、`edges` 6/9、`plan` 3/9、`key-lock` 2/9、`plan-store` 1/9。
  也就是**调用方（#1035 地图04 工具入口）依赖被调用方（#1039 地图05 纯规则侧）**，而现有边要求先转调用方、后抽被调用方。
- 危害：`docs/adr/20261011-deck-ts-rewrite.md` §6 与 `research/1010-ticket-structure.md` §10.2 要求「搬家一次做完」，搬家在 #1019。若 #1039 之后才把 `shell/` 拆成 `rules/` + `shell/`，那 9 个已经转完的工具入口的 import 说明符要**再改一遍**——正是规则 7「同一批文件不许两头改」要防的事。
- 改后谁能开工：**#1039 从第 8 层提到第 1 层**（只被自己的讨论票 #1038 阻塞），#1035 从第 7 层落到第 8 层。这样纯规则侧先立，工具入口一次改到位。
- 若维护者认为「先把对外形状定死（#1034 讨论 → #1035）再动壳」是对的，那就必须让 #1039 保证**它发布的 import 路径不变**（留再导出壳），并在票面写明；否则这条边就是错的。**这一条需要人拍板**（我倾向改方向）。

### D3｜删 `1040 → 1090`，改成 `1039 → 1090`

- 理由：#1090 票面是「建票、改票、上报三处的进度口径统一」。三处落在 `src/host/tools/deckIssueCreate.js`、`deckIssuePatch.js`、`deckIssueReport.js`（地图04 → #1035），进度区的骨架与解析落在 `src/shared/deck-tools/plan.js`（纯规则侧 → #1039）。**宿主侧 #1040 只做取会话、选后端、过闸、拼信封，不管进度口径。**
- 删后谁能开工：#1090 现在第 2 层（等 #1040），补上 #1039 → #1090 与 #1035 → #1090 后落到第 9 层——**这才是它该有的位置**（要等进度区与三处入口都成型）。

### D4｜删 `1031 → 1084`，改成 `1035 → 1084`

- 理由：#1084 票面是「上报工具补上进度自评与会话身份」，改的是 `src/host/tools/deckIssueReport.js`，属地图04 的 #1035（十个工具入口），不属地图03 的 #1031（注册选项、行模块、宿主装配、宿主代执行、额度同步、沙箱判定六件）。
- 删后谁能开工：#1084 现在第 7 层，补 1035 → 1084 后落到第 9 层（等工具入口转完）。

不逐一建议删。它们大多表达约定（本图开发票被本图讨论票阻塞），删掉不改变最早开工时间，但会让读者看不出「先对齐、再动手」。**唯一建议删的是 D1**；D2–D4 是「删旧加新」的方向修正。

## 六、第 0 层（现在就能开工的票）与评价

### 第 0 层共 57 个节点

- 28 张旧故障票（不是本次重构的工作项，见第七节）
- 15 张地图（容器，不是工作项）

也就是说：**维护者打开列表，看到的是 14 条并排的路，不是一条路。**

### 这与「严格串行」冲突

- 维护者的要求（`research/1010-consensus.md` 第三节原话）：「**严格串行**：一个单元完成（开发绿、讲解过、维护者表态）再开下一个；支线可并行，但挂在主链单元的票下。」
- 但 `research/1010-ticket-structure.md` §6 规则 7 与 §13 是**故意**这么设计的，§13 原话：「起点是 **#1014（01 号地图的讨论票）与各张地图的讨论票**」。规则 7 给的理由是「讨论票不写代码，不违反『同一批文件不许两头改』」。
- 两份书面文件对同一件事给了相反的说法，而跟踪器实现的是后者。

### 想靠加边改成串行，会撞环（第二节已证）

按「每张地图的讨论票等上一张地图的讲解票」加 13 条边 → 19 节点环。只加其中一条 `1036 → 1038` → 10 节点环。**加边这条路走不通。**

### 建议：改结构，不要加边

三个选项，我推荐第三个：

1. **保串行**：撤掉 `1027 ← 1052/1053/1054/1058/1059/1060` 这 6 条边，把「两房 implements 对上契约」移到 13 张改写图全部转完之后、收口之前。代价：`docs/adr/20261011-deck-ts-rewrite.md` §6 的「两房 implements 对上 → 再自上而下转 src/deck/」要改。
2. **保现有边**：承认讨论票并行，把 `research/1010-consensus.md` 第三节改成「开发与讲解严格串行；讨论票按地图并行，因为它不写代码」。代价：维护者一次面对 14 个选择。
3. **推荐——讨论票不再每张地图一张**：主线只放开 #1014（地图01）、#1025（地图02）、#1081（地图14）、#1089（地图15）四张讨论票（后两张要先定词汇，`research/1010-ticket-structure.md` §9.8 本来就这么要求：「能力图先定『工作状态模型』」）；其余 10 张改写图的讨论并进上游地图的收尾评论，或改成一次讨论覆盖相邻两图。这样**第 0 层缩到 4 张**，且不产生环——因为不再需要按编号串讨论票。

## 八、最严重的五条发现

1. **「严格串行」与「契约等两房」互斥，加一条边就成环。** 证据：加 `1036 → 1038` 得到 10 节点环 `1027 → 1031 → 1035 → 1036 → 1038 → 1040 → 1044 → 1048 → 1052 → 1027`，其中 9 条是现有边。现有图之所以无环，只因为 #1039 是断头路。**必须改结构，不能靠加边实现串行。**

2. **地图 05 的两张开发票被拆到排期两端，先改调用方后抽被调用方。** 证据：#1040（宿主侧）在第 1 层，#1039（纯规则侧）在第 8 层；而 9/9 个工具入口 import `shell`/`call-scope`/`session-resolve`、6 个 import `edges`、3 个 import `plan`，这些正是 #1039 要抽出的东西。边 `1035 → 1039` 的方向与代码相反。

3. **收口图可以在 11 张改写图还没转完时宣布「手写 JavaScript 归零」。** 证据：#1077 只有 4 个前置（1067/1070/1073/1074），#1078 只有 5 个。补 35 条边后 #1077 落到第 12 层、#1078 落到第 13 层。

4. **两房串行只编码了 1/6。** 证据：只有 `1054 → 1058` 一条；#1059、#1060 与 GitHub 房完全并行，与 ADR §6、「GitHub 先转」直接冲突。

5. **「旧票重叠只有十三个文件」严重低估，且文档数字本身错了。** 证据：实测 18 张旧票碰到新地图文件、横跨 9 张地图（#895 一张就碰 5 张图的 16 个文件）；子票实际 **66 张不是 68**，边实际 **118 条不是 101**，GitHub 房实际 **26 件不是 28 件**，地图13 **缺讨论票**。§10.2 承诺的那张「尾巴票」不存在。
