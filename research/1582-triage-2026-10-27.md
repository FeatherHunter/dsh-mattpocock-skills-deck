## 一句话结论

四处直调宿主属实，仓里也确实没有现成的「打开文件夹」共用件；但比「重复了四遍」更值得修的是失败处理参差：宿主对每一次 `wf.openFolder` 都会记一条结果日志，失败以 `{ok:false, error}` 回包而不抛错，四处里却只有诊断日志一处在看这个回包，Dock 的仓库芯片与子工作区图标把回包整个丢掉、什么也不提示。目录为空在正常渲染下只有 Dock 一处真的可能发生（宿主会回 `{ok:false, error:'缺少 cwd'}`），另外两处日志入口的目录是点击后才异步解析的，渲染时根本不知道，所以「空目录就禁用」这句话落到四处并不是同一件事。收敛应当共享「行为」（判空、发一次电话、看回包、把原因交给调用方去提示），外观维持四处现状；落点与验收句的范围需要维护者拍板。

### 1. Dock 的仓库芯片：只有本地 Markdown 后端会走进文件夹模式

芯片这一段在 `src/client/panel/Dock.ts:246-282`。仓库引用取 `s.repository` 或快照里的 `s.repository`（`:247`）；快照还没回来时画一条灰色骨架（`:253`），认不出仓库时画琥珀色的「未识别仓库」（`:254-257`）或红色的「无仓库」（`:258`）。开仓动作由 `:272` 的 `repositoryActionOf(s, bid)` 决定，`:273` 判 `act === 'folder'` 时才渲染成可点芯片：

- `repositoryActionOf` 在 `src/client/kernel/builtin-backends.ts:43`：`if (mm && mm.openRepository === 'folder') return 'folder'`。
- 三家后端各自的声明：本地 Markdown 是 `'folder'`（`src/tracker/rooms/markdown/index.ts:419`），GitHub 是 `'url'`（`src/tracker/rooms/github/repo.ts:102`），GitLab 是 `'url'`（`src/tracker/rooms/gitlab/index.ts:236`）。所以文件夹模式的芯片只会在本地 Markdown 后端出现。
- 同一个 `data-repo-chip` 在 url 模式与无地址时也画，但那两处分别是 `target="_blank"` 的链接（`:281`）和不可点的 `span`（`:276`），都不调 `wf.openFolder`。

点击时发的是 `host.call('wf.openFolder',{cwd: s.cwd||''})`（`:274`），整段包在 `try{…}catch(__){}` 里。这个 `catch` 抓到的东西只有「电话本身抛异常」一种；宿主正常回 `{ok:false}` 不会抛，所以什么也不会发生。

`s.cwd` 是不是可能为空：会。写它的地方在 `src/client/panel/DockSync.ts:109-117` 的 `apply`，第一行就是 `if (!cwd) return false`；`s.cwd` 只在拿到非空目录时才被赋值（`:117`）。三个来源依次是 `summaryCwd`、`detectCwd(props.session)`、`getCwdSync(sid)`（`:129-133`），都没有时再发一条 `wf.cwd` 电话，回包里带 `cwd` 才 `apply`（`:134-137`）。另有一个只在 `!s.cwd` 时补一次缓存的副作用（`:142-144`）。所以在首次同步完成之前，芯片已经可以渲染出来而 `s.cwd` 还是空串，此时 `s.cwd||''` 把空串原样发给宿主。

### 2. 子工作区图标：渲染前提已经保证目录非空

组件的入口在 `src/client/views/SubworkspaceMark.ts:192-217`：根来自 `subwsMarkRootOf(st)`（`:195`，实现在 `:77-89`，先取快照里的 `workspaceRoot`，再退到 `sessionWorkspaceRoot`，都没有就返回空串、不猜）；目录取 `(st && st.cwd) || ''`（`:196`）；显示用的行由 `subwsMarkLinesOf(root, cwd, inited)` 算出（`:216`），`isSub` 就是「有没有行」（`:217`）。没有行就 `return null`（`:310`）。`subwsMarkShows`（`:135`）的判据是根与目录都非空且折算成同一把键之后不相等，所以正常渲染出来的图标，`root` 与 `cwd` 都不为空。

点击时发的是 `host.call('wf.openFolder', { cwd: shownRoot })`（`:341`），`shownRoot` 由 `:313` 的 `subwsMarkRootShown(root, cwd)` 求出（实现在 `:101-117`）。这个函数把宿主快照里那把「折算过的键」按本会话目录的写法逐段还原；还原不出来（POSIX 上绝对路径开头那个斜杠不算一段，UNC 开头两个反斜杠同理）就原样退回折算键（`:96-100`、`:115`）。所以传下去的一般是用户写的那条路径，在 POSIX 与 UNC 上则可能是折算键（Windows 上是小写加正斜杠）。`win32` 侧 `nodePath.win32.normalize` 会把正斜杠转回反斜杠、NTFS 又不区分大小写，通常仍能打开，但它已经不是用户原先写的那一条。

`catch` 同样是空的（`:341` 那一行的 `try{…}catch(__){}`），没有提示，也没有埋点。

### 宿主 `wf.openFolder` 的契约：失败是回包，不是抛错

注册在 `src/host/index.ts:318`，转到 `src/host/pickerShell.ts:149` 的 `handleOpenFolder`（外面包了 `loggedPhone`）。实现只有 `:39-57` 这十九行：

- `:40` `let cwd = (args && (args.cwd || args.path)) || DEFAULT_CWD`。`{cwd}` 与 `{path}` 等价，`DEFAULT_CWD` 是空串（`src/host/index.ts:41`），所以「没给目录」等于「目录是空串」，没有默认目录兜底。
- `:43` 平台拿不到或没有 `openFolder` → `{ok:false, error:'当前平台不支持打开'}`。
- `:44-48` 给了 `{file}` 就用平台能力取父目录：`file` 为空回「缺少 file」（`:46`），平台没有 `path.dirname` 回「当前平台不支持解析路径」（`:47`），否则 `cwd = platform.path.dirname(file)`（`:48`）。#1557 加的就是这一段，客户端不必自己切分隔符。
- `:50` `if (!cwd) return { ok:false, error:'缺少 cwd' }`。**空目录在这里被拦下，不会走去打开任何目录**；平台层 `src/host/platform/index.ts:243-244` 那句「路径为空」对这条电话基本走不到（`win32` 的 `normalize('')` 会给出 `'.'`，但空串在 `:50` 已经先返回了）。
- `:51-53` 调 `platform.openFolder(String(cwd), DEFAULT_CWD)`；平台回包 `ok !== true` 就转成 `{ok:false, error: <平台给的原因 | '打开失败'>}`；成功回 `{ok:true, cwd, opener}`。
- `:54-56` 整段 `try/catch`，异常也转成 `{ok:false, error}`。

平台层的失败原因来自 `src/host/platform/index.ts:239-264`：没有 `shellOpen` 配方回「当前平台不支持打开」（`:242`），规范化后为空回「路径为空」（`:244`），含不可调起字符回「路径含不可调起字符」（`:245`），找不到打开器回「找不到打开器：cmd」（`:247`），`spawn` 起不来就回 `spawn` 的结果（`:254`、`:259`）。`win32` 的配方在 `src/host/platform/win32/index.ts:95-109`：`normalize` 用 `nodePath.win32.normalize`（`:97`），`allowOpen` 挡掉 `& | ^ % ! < >`（`:98`），文件夹的 `folderArgs` 是 `['/c','start','','/max',t]`（`:101`）。

日志这一半已经由宿主做完，`src/host/pickerShell.ts:143-149`：`loggedPhone('wf.openFolder','picker',handleOpenFolder)` 让每一次调用都留下一条结果——

- 成功：`info` 事件 `host.call`，字段 `{method, latencyMs, ok:true, kind}`（`:146`）。
- 回包非 ok：`warn` 事件 `host.call.fail`，字段里带 `errorHash`（`:147`），哈希的是回包里的 `error`/`errorKind`，没有整条路径。
- 抛异常：同样 `host.call.fail`，哈希异常消息（`:145`）。

所以「失败记一条打开失败的日志」在宿主侧已经成立，客户端再记一条同名的 `host.call.fail` 只是重复。`src/client/kernel/link.ts:119` 已经把这条约定写在注释里：「打开失败的日志由宿主电话统一记 host.call.fail，界面不重复记」。客户端真正缺的是「看见 `res.ok === false` 并把原因告诉人」——这是行为，不是外观。

### 仓内有没有现成可用的共用件：没有，只有两类先例

`src/client/views/shared/` 下 13 个文件：`BackendSelector.ts`、`ChainRenderer.ts`、`chips.ts`、`liquidInk.ts`、`md.ts`、`RestFallbackBanner.ts`、`stateKind.ts`、`SwitchConfirmModal.ts`、`Tabs.ts`、`tagsFit.ts`、`ticket.ts`、`truthLines.ts`、`workRouteTable.ts`；`src/client/views/primitives/` 只有 `HoverTip.ts` 与 `Tip.ts`。没有任何一个与「打开文件夹」有关，也没有通用的「调宿主并处理失败」的跳腿件。

两类先例可以借，但都不是现成答案：

- **外观层的先例**：`Tip`（`src/client/views/primitives/Tip.ts:24`）是悬停气泡的锁定预设，用法是 `h(Tip, {content}, 触发元素)`；`chips.ts:54-58` 的 `chipProps` 给药丸按钮补齐 `tabIndex`、`role`、`onKeyDown`、`data-press` 与 `data-log` 三件套。仓里「共用控件」这个词实际指向的都是这类「接 props、返回元素」的渲染件，落点是 `views/primitives/` 或 `views/shared/`（`docs/adr/20260901-reuse-g1-portal-primitives.md` 第 2 节与 `research/375-reuse-criteria.md:135`）。四处「打开文件夹」的外观恰恰是四种：芯片、图标、菜单项、按钮，语义与可访问性各不相同，没法由一件渲染件原样包住。
- **行为层的先例**：`src/client/kernel/link.ts:121-133` 的 `openTrackerTarget`。它接的是 `(st, key, host, effortId, kind)`，先用 `issueUrlFor` 取容器地址，再按后端声明分派：`'url'` 走 `window.open`，`'file'` 走 `wf.openPath`，`'folder'` 走 `wf.openFolder({file: u})`（`:128`）。**不能直接拿来开本地目录**，原因有三条：一是它要一把 tracker 的键与快照里的后端声明，本地目录没有这些；二是 folder 模式传的是 `{file: u}`，宿主会 `dirname` 到文件的父目录——把一条目录当 `file` 传进去，打开的是它的上一级；三是它自己只回一个布尔值，不区分「目录为空」「平台不支持」这些原因，调用方拿不到可提示的话。它仍然是有价值的先例：它证明「打开某物的行为」在仓里本来就住在 `kernel/`，而不是 `views/`。

### 结论：该共享的是行为，不是外观

三条证据：

1. **四处的差异全在行为与时机，不在长相。** 目录来源四个（`s.cwd`、`shownRoot`、`dswsLogEnsurePath` 的结果、`resolveLogDir` 的结果）；判空两处有一处没有；看回包一处看三处不看；提示两处有两处没有。这些没有一条能靠统一渲染件解决。
2. **外观统一会与既有语义和门禁打架。** Dock 是 `data-press="button"` 的芯片，子工作区是 `data-press="icon"` 的纯图标（`aria-label` 是三行文字的拼接，`SubworkspaceMark.ts:311`），菜单项是 `role="menuitem"` 且 `disabled` 表示「有操作在跑」，诊断日志是 `dsws-cfg-btn`。`tests/verify-ui-feedback.ts` 逐个点名这些 `data-log`（`:68`、`:81`、`:85`、`:100`），并要求全仓唯一（`:610`）；重画四处等于把这些断言全部重写，而票面要的是收敛入口。
3. **「看回包并说明原因」是一段可以单独测的纯逻辑。** 它有明确的输入（目录、宿主电话、提示函数）与输出（成功 / 失败原因），不碰 DOM，可以像 `link.ts` 那样放在 `kernel/`，也可以像 `shared/ticket.ts` 那样放 `views/shared/` 当一件纯函数叶子。这正是 #1582 真正缺的东西。

## 「目录为空即禁用并说明原因」在四处分别意味着什么

| 入口 | 渲染时知道目录吗 | 空目录会发生吗 | 今天的行为 | 这句验收要落地，只有哪几种做法 |
| --- | --- | --- | --- | --- |
| Dock 芯片 | 知道（`s.cwd`） | 会（首次同步前） | 发 `{cwd:''}`，宿主回「缺少 cwd」，用户什么也看不到 | 空 `s.cwd` 时不渲染成可点芯片（或置灰 + 气泡说明「还不知道当前目录」） |
| 子工作区图标 | 知道（`root`/`cwd`） | 正常渲染下不会 | 一定发出非空目录 | 无需新增禁用态；把 `shownRoot` 可能退化成折算键这件事在气泡里说清即可 |
| 状态栏日志菜单 | 不知道（点击后才解析） | 解析成功时不会 | 解析失败先提示并停手 | 不能「渲染时置灰」；只能保留「点了解析失败再提示」，或记住上次解析失败、下次悬停说明 |
| 诊断日志按钮 | 不知道（点击后才解析） | 解析成功时不会 | 解析失败先提示并停手 | 同上 |
