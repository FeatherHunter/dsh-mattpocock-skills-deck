## 一句话结论

现状成立：全仓没有“打开文件夹”的共用控件，四处入口各写各的直调宿主；#1557 已经把“能不能打开”修好，剩下的事确实只是收敛，外加补两种缺口——Dock 的仓库芯片与子工作区图标把失败吞掉；四处都没有“拿不到目录就置灰并说明原因”的状态。真要做，改造面不大（一个共用控件加四处替换），但先要拍板三件事，见文末。

## “做完”三条逐条核对

1. **共用控件位置与调用约定**：没有。`src/client/views/shared/` 下 21 个文件里没有文件夹或“打开”相关控件（`chips.ts`、`badge.ts`、`tooltip.ts`、`button` 一类原子件，`grep` 不到 folder/open 相关实现）。
2. **四处调用点替换为共用控件**：没有。全仓 `grep wf.openFolder`，客户端仍然只有这四处调用点（另有宿主注册处与宿主内部的 `{file}` 用法，不算客户端入口）。
3. **空目录禁用并说明原因、失败记打开失败并提示**：都没有。宿主侧失败日志已经统一（每次 `wf.openFolder` 都被 `loggedPhone` 包住，失败记一条 `host.call.fail`），但客户端四处都没有显式的可用/不可用状态，其中两处连提示都没有。

## 四处入口的现状（读源码核实）

- **Dock 仓库芯片**（`src/client/panel/Dock.ts:274`）：仓库芯片在“文件夹”模式下点击，调 `host.call('wf.openFolder', { cwd: s.cwd || '' })`。`catch` 为空，不提示；`cwd` 为空也照常发起；芯片本身渲染成 `<a href="javascript:void(0)">` 加 `Tip` 气泡，没有禁用态。
- **子工作区小图标**（`src/client/views/SubworkspaceMark.ts:341`）：点击图标调 `host.call('wf.openFolder', { cwd: shownRoot })`，`shownRoot` 由 `subwsMarkRootShown(root, cwd)` 求出。`catch` 为空，不提示；没有禁用态。
- **状态栏日志菜单的“打开目录”**（`src/client/statusbar/StatusLogMenu.ts:215-241`）：先用 `dswsLogEnsurePath()` 解析目录，失败时弹出带原因的提示（`logtoast.openFailed`）；成功则调 `host.call('wf.openFolder', { cwd: got.dir })`。这里有一处缺口：`.then` 不检查宿主回包的 `ok`，宿主回 `{ok:false}` 时菜单照样关闭、不出提示，只有调用抛错（`.catch`）才提示。
- **诊断日志页的“打开目录”**（`src/client/views/diagnosticLog/diagnosticLogActions.ts:298-329`）：先用 `resolveLogDir()` 静默解析目录；没有目录时记一条 `openDir / path-missing` 并弹提示（文案复用了导出失败那条 `cfg.dbgExportFail`，对用户来说略含糊）；有目录时调 `host.call('wf.openFolder', { cwd: dir })`，会检查 `writeOk(res)`，失败弹 `cfg.dbgOpenDirFail` 并记 `exportFail`。这里失败提示是齐的。

对照下来，验收第 3 条真正要动的是：给共用控件一个“目录能不能拿到”的输入，拿不到就置灰并在气泡里说明原因；宿主回包不是 `ok` 时统一提示。这不是新机制，四处各自零散做过一半。

## 宿主这一侧已经统一的契约（不用重做）

- 入口：`src/host/index.ts` 注册 `wf.openFolder` 电话，转给 `src/host/pickerShell.ts:149` 的 `handleOpenFolder`，再落到平台层。
- 参数：接受 `{ cwd }`、`{ path }` 或 `{ file }`；`{ file }` 在宿主侧取 `dirname`（#1557 为“第 4 颗按钮”加的）。
- 失败返回：缺 `cwd` 回 `{ ok:false, error:'缺少 cwd' }`；平台不支持回“当前平台不支持打开”；平台层非 ok 回“打开失败”。
- 日志：`loggedPhone` 已经统一记 `host.call`（成功）与 `host.call.fail`（抛错或回包非 ok），所以“失败记打开失败”这一半在宿主侧已经成立；客户端要补的是“看见失败并告诉人”，不是再记一遍原因。

## 可复用的既有机制（收敛时直接用）

- 成功/失败提示：`flash(store, msg, kind)` 这套提示，`StatusLogMenu`（`say`）与诊断日志（`deps.tell.flash`）都在用，Dock 与子工作区也能接。
- 路径解析：`dswsLogEnsurePath()`（状态栏菜单）与 `resolveLogDir()`（诊断日志）各自已经会解析“日志目录”，共用控件不必重复解析。
- 仓库动作判定：Dock 里 `repositoryActionOf` / `repoActionOf` 已经按后端 `openRepository` 声明决定“文件夹还是链接”，共用控件不需要重新判断。
- 子工作区根路径：`subwsMarkRootShown(root, cwd)` 已经算好要打开的目录。

## 落在哪、要动哪些门禁

- **落点候选**：`src/client/views/shared/` 下新增一个叶子控件（比如“打开目录”按钮/图标：输入目录来源与提示文案，内部调 `host.call('wf.openFolder')`，统一处理失败回包与禁用态）。它是 `views/shared` 的叶子模块，受现有叶子模块规矩约束：不跨叶子相对引用，登记到 `tsconfig.client.json` 的 include（`views/shared/*.ts` 已覆盖）与 `scripts/build.mts` 的叶子清单（`views/shared/chips.ts` 那一段附近）。若最终决定“只要行为、不要外观”，就落在 `src/client/kernel/` 一层（像 `link.ts` 的 `openTrackerTarget` 那样给一处打开函数），但那个文件目前没有 `wf.openFolder` 调用，引入前要确认中转层归属（见 Q2）。
- **会牵到的门禁**（gate-map 里这几份源码被这些门禁引用）：`tests/verify-666-subws-mark-root.ts`（场景 11 断言点图标会用 `{ cwd: ROOT_DIR }` 调 `wf.openFolder`）、`tests/verify-653-subworkspace.ts:180`（以源码正则断言 `wf.openFolder` 字样出现在 `SubworkspaceMark.ts` 里，收敛后要把断言改到共用控件上，否则会误红）、`tests/verify-diagnostic-log-actions.ts`（断言 `openDir` 会调 `wf.openFolder` 并报失败）、`tests/verify-ui-feedback.ts:68`（Dock 仓库芯片、子工作区图标、状态栏菜单的反馈）、`tests/verify-leaves.ts`、`tests/verify-1145-open-local.ts`（`wf.openFolder` 的 `{file}` 形态）。
- **新增叶子模块的常规代价**：`build.mts` 叶子清单、`tsconfig.client.json`、gate-map 的人工目测清单三处登记；用 `npm run verify:changed` 或全链 `npm run verify:parallel` 收口。
