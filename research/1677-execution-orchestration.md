**四条硬约定（比批次表更重要）：**

1. **一个候选、一次冻结、所有批次共用。** 候选身份是「提交 + 构建产物 tgz 的 SHA256 + 逐文件清单 + 界面显示的版本串」，不是「main 分支最新」这句话。批次只核对 <工作根>/pkg/candidate.json，不重新取 main HEAD。
2. **一批一套隔离环境。** 每批有自己的 DSH_HOME、启动目录、隔离 USERPROFILE、glab 配置文件目录、GitLab 沙箱项目和本地工作区；批次之间不共用可写数据。唯一例外是「101 张票读池项目」：它只读，跨批复用，避免重复造 101 张票。
3. **证据三层，回包不能单独证明写成功。** 批内原件（evidence/ 与 evidence.json）、归档副本（evidence-archive/ 与 SHA256SUMS.txt）、报告索引（INDEX.md 与 index.jsonl）。写场景必须有「工具回包 + 界面刷新读回 + GitLab 网页或 API 读回 + 邻字段对照」四样中的至少三样，且独立读回不能少。
4. **失败不覆盖，未测不冒充通过。** 每次尝试单独留证据；产品缺陷立即开票或重开来源票；环境问题记「未测」并写下重试条件；机时不够也记「未测」，不把没跑写成通过。

**机时结论要提前说清：** #1675 的「1-2 天机时」以第 0 阶段的工具已经就绪为前提。这台机器现在缺三样关键工具（GitLab 工作区夹具、给实例注入环境变量的入口、直接调用 deck 工具的入口），现补约 4-7 小时。四个批次的纯执行与取证合计约 5-7 小时，但每个场景要现写一段 Playwright 探针脚本并调试，按实测每场景 20-40 分钟另计，20 条约 6-9 小时；加上归档与索引 2-3 小时，整包约 2.5-3 天。若维护者不接受这个数，砍的是非核心 20 条与条件允许项，不是第 0 阶段；第 0 阶段砍掉，核心 20 条里的 4 条工具写场景就只能记未测。

## 1. 第一性推导：批次边界由什么决定

### 1.1 批次边界首先是「环境固定成本」，不是功能分类

每开一批，都要重新准备一套隔离 home、一个 GitLab 沙箱项目、一份本地工作区、一份 glab 配置、一次候选安装、一次前置巡检。这套固定成本估计 20-30 分钟。功能域的划分只决定「先跑哪条、后跑哪条」，不决定「开几个环境」。

反过来说：如果一篇功能域只为了好读就单独开一批，等于用 20-30 分钟换一个更短的标题，不划算；如果两类功能共享同一套环境而且互不污染，就应该合批。4 批是按「环境能否共用、写操作会不会污染后续读数、风险是否需要隔开」切出来的，不是按 R1 的 11 段旅程原样照搬。

### 1.2 顺序由依赖与风险共同决定

- **依赖：** 绑定与环境（B1）不通过，后面的列表、详情、写操作都没有「后端可用」这个前提。所以 B1 先做，且 B1 的 J2-01 环境检查必须真绿，不能带着红检查页往下跑。
- **读先于写：** B2 先建立「读到的票、地图、计数是可信的」基线；B3 的写操作才能判断「写完后读回的值变了」到底是写成功还是原本就读错了。
- **写先于设置与错误：** B3 会产生真实的票、评论、父子关系与阻塞关系；B4 的 J9-02（工作区总览）、J11-03（错误与空态）需要这些真实数据做对照，不需要再重复造一遍。
- **风险优先：** 超过 100 张的读全、免费档阻塞的三步降级、指派静默丢失、父子标记被挪或删，是 R2 列出的最高风险。它们分别在 B2 和 B3，且都在对应批次里先跑，不排到批尾。

### 1.3 候选必须不可变，否则结果无法归因

测试结果是对「某个确定的包」的结论。如果每批开始都取一次 main HEAD，B1 与 B3 之间代码就可能变化，同一个缺陷到底属于哪个提交、修后重验对比的是哪一版，都说不清。所以候选在 kickoff 时冻结一次，所有批次使用同一个 tgz；代码变了才产生新候选，并且只重跑受影响的场景。

「最新代码」在本方案里定义为「kickoff 时 main 分支 HEAD 指向的提交」，并记录取它的时间。报告里不能写「测了最新代码」，只能写「测了提交 X（2026-10-31 某时 main HEAD）」。如果 main 在测试期间前进，那是下一轮的事；不在本轮追。

### 1.4 每批换一套环境，是为了让失败可复现

写场景会改项目里的票、标签、评论、父子与阻塞关系。如果 B3 的写数据留在项目里，B4 读到的计数和列表就已经被污染，失败时无法判断是产品问题还是前面测试留下的状态。每批一个项目、一套 home，批次结束时整批归档并清理，下一次失败可以按 manifest 重放。

101 张票的读池是例外：造 101 张票本身要几分钟，而且只读不写，跨批复用不会污染；但一旦某批对读池做了写操作，这个项目就作废，不能继续当读池。规则写进 manifest：读池项目标记 mode: read-only，任何写操作前先检查标记。

### 1.5 证据的独立性决定结论的强度

被测代码自己返回「成功」不是证据，只是它的自述。真机测试的价值在于用另一条路径观测同一件事：GitLab 网页、GitLab API 读回、界面刷新后的显示、邻字段有没有被误伤。同一份回包既当动作记录又当结果证据，等于自己证明自己。所以第 9 节把「独立读回」写成硬要求，不满足的证据只能算「线索」，不能算「通过」。

### 1.6 失败与未测必须分开

- **产品缺陷：** 同一动作、同一环境可重复失败，且失败原因指向产品行为。
- **使用限制：** 产品按设计不提供某种能力（例如免费档没有原生阻塞写），并且有替代路径或如实提示。
- **环境限制：** 当前机器或账号做不到（例如没有第二个权限档位），不是产品的问题。
- **未测：** 没跑，或跑了但被环境打断；必须写原因与重试条件，不能写成通过。
- **测试工具问题：** 测试脚本、夹具、浏览器驱动自身出错；不计产品缺陷，但要修工具后重跑。
- **通过：** 有独立观测支持的肯定结论。

这六类与 #1675 第 2.4 节一致；批次编排只负责让每一类都有落点，不重新定义判据。

## 2. 四个批次与场景分配

### 2.0 先跑 B0 试点（不增加批次）

在 B1 的第一条场景之前，先拿 B1 的 J1-01 做一次全流程试点，叫 B0。它不另开环境、不另立批次，只把「前置巡检 → 开始评论 → 截图与诊断 → 独立读回 → result.json → 批次评论草稿 → 归档与索引」完整走一遍，检查证据流水线本身能不能用。

B0 的验收只看流程，不看产品结论：

- 一个场景的 evidence.json、result.json、observations.md、截图、page-diagnostics、日志摘录、独立读回文件都齐；
- 批次 INDEX.md 能按 9.3 的列填出来，index.jsonl 能追加一行并通过 schema 自检；
- 归档副本与 SHA256SUMS.txt 能生成，路径能在报告里引用；
- 计时：从批次开始到 B0 收尾实际用了多少分钟，用来校准后面四批的估算。

B0 不通过，先修工具与证据格式，再重跑 B0；不要带着半个证据流水线进入 B1。B0 的结果可以并入 B1 的 J1-01，不重复跑；如果 B0 后发现证据格式要改，已产出的 B0 证据按新格式重做一遍，不将就。

### 2.2 批次内部的顺序

每批内部按「先看正常路径，再看边界，最后看错误」：

1. 正常路径（D1）：界面按预期出现，数据与网页/API 一致。
2. 写后读回（D2）：写操作后，界面刷新与独立读回都看到变化，邻字段没有被误伤。
3. 异常与降级（D3）：主动制造错误，确认话术能分辨、能恢复。

同一场景内也按这个顺序，不把「错误注入」放在正常路径之前，否则恢复状态会污染正常路径的读数。

### 2.3 B3 的拆分规则（不增加环境）

B3 有 7 条核心场景，是四个批次里最重的一批。如果实际执行超过 2 小时（从批次开始评论到批次结束评论），在 J6-04 与 J6-05 之间拆成两个执行窗口：

- B3a：J6-01、J6-03、J6-04（界面读与评论写）。
- B3b：J6-05、J6-06、J7-01、J7-02（工具写与关系）。

两个窗口共用同一套环境、同一个候选、同一个项目与 home，不重新准备夹具；只是把批次开始/结束评论写成 B3a 与 B3b 两组，证据仍归在 B3 目录下。这样既不增加环境固定成本，也避免一个窗口拖太久导致证据写不完。

### 2.4 加批规则（核心 20 之后）

核心 20 条全部有结论之后，才允许开加批。加批按功能域补充剩余 20 条：

- 加批 A（读与布局）：J1-03、J2-03、J2-04、J3-02、J3-03、J3-04、J4-02、J4-04。
- 加批 B（地图、详情与在办）：J5-04、J5-05、J6-02、J7-03、J8-01、J8-02、J9-01、J9-03。
- 加批 C（条件允许项）：J10-02、J11-01、J11-02，以及 1000 张地图封顶、无权限写；能跑就跑，不能跑写未测。

加批不重新冻结候选，只核对 candidate.json；如果核心批已经发现 P0 并修了代码，加批必须用新候选并重跑受影响的核心场景。

**不要为了排满批次把核心场景往后挪。** 核心 20 条没跑完就开加批，等于用「看起来跑了很多」掩盖「最该验的没验」。

## 3. 第 0 阶段：工具与原语（批次的前置）

第 0 阶段不产生场景结论，只产生「工具可用」的结论。它任何一项不通过，对应批次不能开始；不能靠人手工点一遍来代替，因为手工步骤无法重放，也无法写进证据索引。

### 3.2 直接调用 deck 工具怎么做（两条路线）

工具写场景要的是「与产品相同代码路径上的确定性调用」，不是模型自然语言。两条路线都能做到，优先第一条：

**路线一（首选）：在隔离实例的页面里直调宿主代执行通道。** 宿主已经暴露一条给页面用的代执行入口：src/deck/registration/host-delegate.ts:68-113 的 wf.deckExec，入参 { tool, args, session: { cwd, sessionId } }，tool 必须在授权工具表内，cwd 决定工具绑到哪个工作区；执行用的是同一张工具表、同一份权限闸，回包三态 { status, text, reason }，不抛异常。页面侧通过 src/host/rpcChannel.ts:174-185 的 /api/dsws 路由发 client-request 信封，写法样板在同目录 agent-row.ts:283-313。执行时用 Playwright 在已打开的隔离实例页面里 evaluate 发这条请求（页面自带登录态），入参 cwd 指向本批夹具工作区。这比复制一套依赖装配轻，且走的正是产品给页面用的真实入口。注意：从进程外直接 POST /api/dsws 实测回 401（本轮验证），所以必须跑在页面上下文里，不能拿外部脚本硬调。

**路线二（备选）：仿 tests/verify-1559-deck-output-lossless.ts 写 deck-write 命令。** 该测试用 makeWorkspace() 造本地 Markdown 工作区，装配 gate / registry / budget / backendCtx / handleFor / decideBackend / log / now 这些依赖，然后对九个 deck 工具各调一次真实成功路径。GitLab 与 Markdown 的差别只在两处：registry.register(gitlabModule) 换成 GitLab 房（src/tracker/rooms/gitlab/index.ts 导出 createGitlabBackend）；backendCtx 里的 platform 要提供 resolveExecutable('glab') 与 exec（调 glab 子进程），cwd 指向本地工作区，handleFor 返回 { cwd, refId: '<group>/<project>' }。实现成 scripts/real-machine/commands/deck-write.mts，参数是工具名 + JSON 入参文件，回执写 tool-response.json，再用 glab api 独立读回。

第 0 阶段先用不超过 1 小时验证路线一；路线一走不通再试路线二；两条都不通，退路才是「在夹具工作区开 DSH 会话用固定代码块调 tools.deck_*」，那经过模型，只能算用户路径证据，此时 4 条工具写场景必须记未测。无论哪条路线，回执都不能单独证明写成功，必须有独立读回。

### 3.3 第 0 阶段本身的验收

第 0 阶段结束必须有一份工具验收记录（放 <工作根>/stage0/REPORT.md，不占仓内笔记）：

- 每条缺口命令能跑通，贴出命令与关键输出；
- freeze-candidate 能从干净检出构建出一个候选，candidate.json 与 tgz 的 SHA256 能对上；
- 候选装进一个隔离 home，起得来实例，界面版本串与 candidate.json 一致；
- 前置巡检在一个空批次上给出全绿（或明确指出哪一项预期为红）；
- 工具写路线至少一条跑通（路线一优先，见 3.2）：成功调用一次 deck_issue_create，并用 glab api 读回同一张票；
- 两个实例的 two-instance-smoke 跑通，证明隔离 home 与浏览器上下文可用。

第 0 阶段不通过，不开始 B1；不要用「先跑起来再说」跳过，因为后面每个批次都会重复同一套手工步骤，错误会被复制四遍。

### 4.2 每批准备的标准步骤

1. **前置巡检：** 跑第 0 阶段的 preflight-batch，确认候选哈希、home、工作区、glab、项目、票池、日志目录、屏幕状态。任何一项红，先停下修，不进场景。
2. **建沙箱项目：** gitlab-sandbox create --name dsh-gl-<批次>-<时间戳>，读回 id、path、web_url，写 manifest。项目名带时间戳，避免删除后同路径复用撞上延迟删除。
3. **造本地工作区：** make-workspace --kind gitlab --project <group>/<project>，目录放批次自己的 fixtures/workspace，不放进本仓库（否则插件可能把本仓库的 git 根当仓库身份）。
4. **种数据：** 按批次需要调用 seed-gitlab：
   - B1：5-10 张票，够验证绑定、列表和检查页即可。
   - B2：101 张票（其中 5 张已关闭）、2 张地图及子票、若干标签；读池项目标记只读。
   - B3：20-30 张票，含 1 张地图、父子关系、阻塞关系、不同标签与指派；免费档的阻塞写会走降级路径。
   - B4：设置项目 10 张票；空项目 0 张票（用于空态）。
5. **准备隔离 home：** copy-home --home <批次>/homes/instance-a --template <工作根>/homes/candidate-template --profile web，确认插件已装、版本串对。
6. **隔离设置目录：** 本批 USERPROFILE 指向批次目录下的 userprofile，DSH_HOME 指向 homes/instance-a。这样插件设置写进批次目录，不会碰真实设置。
7. **准备 glab 配置：** 把真实 LOCALAPPDATA 下 glab-cli/config.yml 复制到 <批次>/glab-config/config.yml；不复制 token（配置里本来也没有 token），登录仍走系统凭据管理器。用 GLAB_CONFIG_DIR 指过去，先跑一次 glab auth status 确认还是 FeatherHunter。
8. **起实例：** start-instance --home <批次>/homes/instance-a --dir <批次>/run-a --userprofile <批次>/userprofile --profile web --port 0 --env-file <批次>/env.txt。env.txt 里写 GLAB_CONFIG_DIR、PATH、GITLAB_TOKEN（需要时）；token 不写命令行。
9. **登记工作区：** seed-workspace --home <批次>/homes/instance-a --workspace <批次>/fixtures/workspace --title <批次>-gitlab --default，让实例一启动就能看到工作区。
10. **打开界面：** 用浏览器库打开实例 token URL，先做 browser-check 的基础断言，再进入场景。
11. **跑场景、留证据、写批次评论。**
12. **批次结束：** 停实例，跑隔离指纹对比，归档，删远端项目，清理本地夹具，更新全局索引。

### 4.3 隔离的四个面

- **DSH_HOME：** 每个实例一份，互不共享；实例的会话、缓存、日志都在里面。
- **启动目录：** 每个实例一个，插件日志写 <启动目录>/.dsh-mattskillsdeck-cache/logs/<日期>.log；两个实例的日志分开才查得清。
- **USERPROFILE：** 普通批次每批一份，避免插件设置写到真实用户目录；B4 的双实例场景刻意让两个实例共用同一份 USERPROFILE，才能验「共享设置 + 后写覆盖」。
- **glab 配置：** 每批一份 GLAB_CONFIG_DIR，但系统凭据管理器是共享的，见 4.5。这个共享是已知且可接受的：所有批次用同一个已登录账号，测试的是产品，不是账号隔离。

### 4.4 双实例批次（B4）的特别准备

J10-01 需要「两个窗口、共享设置、最多两个活跃窗口」。造法：

- 两个实例各自 DSH_HOME 与启动目录，但 --userprofile 指向同一个批次目录下的 shared-userprofile；
- 两个实例装同一个候选包，版本串必须一致；
- 用同一个浏览器开两个独立页面（newPage 两次），不要用两个 context 之外的花招；窗口身份由页面级 sessionStorage 决定，两个页面就是两个窗口；
- 验证：两个窗口都能看到同一个工作区列表；窗口 A 改设置后窗口 B 能看到（或按设计读不到，需对照预期）；开第三个窗口时按设计只保留两个活跃窗口；
- 证据：两个窗口的截图 + 设置文件 SHA256 前后 + 日志中的窗口标识行。

### 4.5 凭据怎么隔离（实测结论）

- GLAB_CONFIG_DIR 确实能把配置文件生成到指定目录，但 Windows 凭据管理器里的 token 不跟着目录走。实测：指向空目录时，glab auth status 仍然找到 keyring token，只是 API 返回 401；把真实 config.yml 复制到该目录后，认证恢复正常。结论：**每批复制真实配置到独立目录，可以隔离「配置文件」；不能隔离「系统凭据」。** 这是这台机器的测试环境限制，不冒充产品隔离。
- 正常批次：共用真实登录（FeatherHunter），不执行 glab auth logout，不动真实配置。
- 「未登录」场景：不登出真账号。用 GITLAB_TOKEN 注入一个无效值，让 glab auth status 返回 401，走与「未登录」相同的产品分支（preflight 对 code!==0 或 401/403 都判 AUTH）。报告里写「认证失败（用无效 token 模拟）」，不写「真实未登录」。如果一定要验真实未登录，需要人工在测试前临时移除一次 keyring 条目，测试后恢复；这属于人工前置，不写进自动批次。
- 「未安装 glab」：用 env.txt 的 PATH 去掉 glab 所在目录；启动前先在该 PATH 下执行 Get-Command glab 确认找不到，再起实例。不要改系统 PATH，不要卸载 glab。
- token 永不写进命令行参数、批次评论、证据文件或日志；env.txt 放批次目录，权限按当前用户可读，批次结束随目录删除；如果维护者要求更严，改用一次性专用 token，放工作根之外的只读文件。

### 4.6 清理与容量

每批结束按顺序做：

1. 停两个实例（stop-instance，按 pid 停整棵进程树），确认没有残留进程。
2. 对比真实设置文件前后 SHA256（isolation-probe 或 settings-fallback fingerprint），证明没写真实目录。
3. 把整批 evidence 复制到 evidence-archive/<批次>-<时间戳>/，复制 candidate.json，生成 SHA256SUMS.txt，写 INDEX.md。
4. 删除远端沙箱项目：gitlab-sandbox delete --project <path>，读回 marked_for_deletion_at；读回不是 404 是正常的（GitLab 延迟删除），不要重复 DELETE，也不要复用同路径新建。
5. 删除本地夹具与批次 home，但保留 manifest.json、INDEX.md 与归档；如果远端删除失败，保留整个批次目录并在批次结束评论里写项目 id 与重试时间。
6. 更新全局 INDEX.md，记录批次、候选、场景数、通过/失败/未测、缺陷票号、归档路径。
7. 容量检查：单批目录不超过 2GB，工作根总量不超过 15GB，批次目录不超过 20 个；超了先归档再清最旧的已归档批次。GitHub worktree 批次如果用到，清理后在源仓库执行 git worktree prune；GitLab 夹具是普通本地 git 仓，不需要这一步。

## 5. 候选冻结：怎么取「最新代码」

### 5.1 冻结时点

在四个批次开始之前冻结一次；不是在每批开始时取 main HEAD。冻结动作记录：

- 提交 SHA 与提交时间（git log -1 --format='%H %cI %s'）；
- 冻结时的分支（main）与「main HEAD 的时间戳」；
- 构建时间、构建命令、包版本；
- tgz 的 SHA256 与逐文件 SHA256 清单；
- 界面显示的版本串（从实例里读，不从包名猜）。

这些字段写进 candidate.json，批次开始评论只引用它的 SHA256。报告写「提交 X，冻结于 Y，包哈希 Z」，不写「最新代码」。

### 5.2 从哪里构建（这台机器有并行会话）

当前主工作区是脏的（git status 有 docs/prototype 的未提交改动，来自别的会话），不能直接 freeze-candidate：它会因为工作树不干净拒绝，或者用 --allow-dirty 把无关改动带进候选说明。正确做法：

1. 用 git clone --no-hardlinks <仓库> <工作根>/candidate-src，或 git worktree add --detach <工作根>/candidate-src <提交>；在 candidate-src 里检出冻结提交。
2. 不安装一份新依赖：在 candidate-src 下建一个 directory junction node_modules 指向主检出的 node_modules（只读使用）。依赖版本与主检出相同，构建足够。
3. 用 DECK_REPO_ROOT=<工作根>/candidate-src 与 DSH_VERIFY_WORK_ROOT=<工作根> 跑 freeze-candidate；它的 repoRoot() 支持 DECK_REPO_ROOT 覆盖（scripts/real-machine/lib/util.mts），所以命令本身不用改。
4. 只在 clone/worktree 里构建，不在主工作区构建；主工作区的未提交改动不进入候选。
5. 如果没有条件做干净检出，才用 --allow-dirty，并且必须先列出脏文件、确认它们都不在 src/、config/、package.json、构建脚本、package/ 下；有任何一个在，就停，不许冻。脏文件清单要写进 candidate.json 的说明，报告里说明「候选包含未提交的文档改动，未包含源码改动」。

### 5.3 安装到批次 home

- freeze-candidate 的 --home 指向 <工作根>/homes/candidate-template，让它把包装进模板 home；
- 每批用 copy-home --template <模板> --home <批次>/homes/instance-a 复制；不要每批重新构建；
- 每批启动后核对界面版本串与 candidate.json 的版本；不一致就停，说明装错包；
- candidate.json 与 tgz 归档到每个批次的 evidence-archive，保证日后能复现「当时装的是哪个包」。

### 5.4 什么情况下重新冻结

| 变化 | 是否重冻 | 重跑范围 |
|---|---|---|
| 只改文档、注释、测试说明 | 否 | 不重跑；报告注明候选未变 |
| 修 P0 缺陷（崩溃、数据损坏、核心写失败、绑定不可用） | 是 | 受影响批次全量重跑 + B1 的绑定/检查两条冒烟 |
| 修 P1 缺陷（显示、交互错误） | 是 | 只重跑失败场景与同判断点的邻场景 |
| 修测试工具/夹具（不是产品代码） | 否 | 重跑受工具影响的场景；候选不变 |
| main 前进但未修本报告的问题 | 否 | 不追；报告写「测的是提交 X，main 已前进到 Y，未验证」 |

新候选产生后，批次评论与索引必须写「候选切换」；不能把两个候选的结果混在同一张通过表里。报告按候选分组；最终结论只能引用最后一个候选的通过项。

## 6. 三款窗口形态用在哪

### 6.1 规则

- **wide（真全屏）：** 所有场景的基线形态。每个场景至少一张 wide 截图，布局结论必须有 page-diagnostics 的 fullscreen: true 与 viewport 读数。
- **narrow（外框宽 800、高铺满）：** 只用在矩阵里「布局=是」的 7 个场景：J3-01 页签、J4-01 胶囊与横幅、J4-03 在办票胶囊段、J5-03 地图看板、J8-01 技能页签、J9-04 标签配色、J11-03 错误与空态。做法：wide 跑完主流程后，对同一页应用 narrow 预设，只重看「是否换行、是否被裁、面板宽度是否在 300-359px、按钮是否还在视口内」，不重复整条业务流程。
- **short（宽铺满、高 600）：** 只用在垂直空间敏感的 3 个场景：J3-01、J4-01、J11-03。做法同 narrow，只重看高度压缩下的遮挡与滚动，不重跑全流程。
- 其他场景不强制 narrow/short；如果 wide 下已经出现布局疑问，再补一张 narrow，不为了凑数把每个场景都跑三遍。

### 6.2 证据要求

- 每个布局场景：wide 截图 + page-diagnostics（fullscreen、viewport、screen）+ narrow 截图与诊断；short 场景再加一张 short。
- 截图命名带形态：J3-01-wide.png、J3-01-narrow.png、J3-01-short.png，不用 screenshot1.png 这种看不出条件的名字。
- 布局结论写「在 2560×1440 主屏、wide 真全屏、narrow 外框 800 宽下，面板宽 331px，未出现横向滚动」，不写「显示正常」。
- 禁止用 setViewportSize 假装窗口尺寸；必须用工具库的 applyViewportPreset，它会同时改外框与内视口并记录诊断。

## 8. 失败、重跑与补验

### 8.1 失败之后先做什么

场景失败时，不要立刻进入下一个场景，也不要直接重跑碰运气。按顺序做四件事：

1. **冻结现场。** 保留当前截图、页面诊断、日志、工具回包、GitLab 网页或 API 读回；不要清理浏览器、不要重启实例、不要改数据。把当前时间与实例 pid 写进 observations.md。
2. **做一次最小复现。** 用同一个候选、同一套环境、同一组数据，只重放失败的那一步；如果第二步就复现，记「稳定失败」；如果两次都过，记「未复现」，再跑第三次（见 8.2）。
3. **分型。** 按六类判断：产品缺陷、使用限制、环境限制、未测、测试工具问题、通过。分型要有证据，不能因为「代码看起来不会错」就改判。
4. **处置。** 产品缺陷：立即开 bug 票或重开来源票，把票号写进结果；使用限制：写进已知限制候选，继续；环境限制：记未测，写重试条件；测试工具问题：修工具，候选不变，重跑；通过：写六元组。

不要在一个批次里连续跳过多个失败项、最后一次性处理；失败项拖到批尾，现场已经被后续写操作污染，复现不了。

### 8.2 不稳定结果怎么算

同一动作在相同条件下，三次尝试里出现「失败—通过—通过」或「通过—失败—通过」，不能算通过，也不能简单算失败：

- 记「不稳定」，保留三次证据，按产品缺陷开 P1 票（除非能证明是测试工具或环境抖动）；
- 报告里单列「不稳定项」，不计入通过数；
- 如果三次都通过但第一次失败，仍要追第一次失败的日志；可能是冷启动、首次请求慢或时序问题，这类问题在真机上恰恰最容易漏。

「重跑一次就过」是最危险的假绿：它把真实缺陷转成了通过。规则写死：失败后的第一次重跑通过，不算通过，必须再跑一次并给出解释。

### 8.3 证据目录不覆盖

每次尝试一个目录，绝不覆盖：

    evidence/
      J7-02/
        attempt-1/
          result.json
          observations.md
          shots/
          page-diagnostics/
          tool-response.json
          independent-readback.json
          logs/plugin-excerpt.log
        attempt-2/
          ...
        result.json          ← 最终结论，指向最后一次 attempt，并列出全部 attempt 的判定

最终 result.json 的字段：

    {
      "scenario": "J7-02",
      "attempts": [
        {"attempt": 1, "verdict": "产品缺陷", "evidence": "attempt-1/", "note": "..."},
        {"attempt": 2, "verdict": "产品缺陷", "evidence": "attempt-2/", "note": "..."}
      ],
      "finalVerdict": "产品缺陷",
      "defect": "#<票号>",
      "candidate": "<sha>",
      "retest": "待新候选"
    }

### 8.4 环境原因的未测与重试条件

未测必须写「为什么没测成」和「什么条件下重测」，不能只写「环境问题」。常见三类：

- **网络或限流：** 写清是 DNS、代理、429、超时中的哪一种；重试条件「等 10 分钟后、同一项目、同一场景」；同一批次内最多重试 2 次，仍失败就记未测并进补验批。
- **凭据或权限：** 写清是 keyring 读不到、token 过期、账号无权限中的哪一种；不要在现场反复登录；记未测，等维护者处理后在补验批重跑。
- **屏幕或窗口：** 写清实际分辨率与期望；如果只是屏幕尺寸不同，布局结论不能给「通过」，只能记未测或按实际尺寸给有条件结论。

### 8.5 补验批

核心 20 条全部有结论后，如果存在失败待修、未测待补，开一个补验批 S1：

- 使用当前最新候选，不复用旧候选的结果；
- 环境新准备一套，不复用旧批次 home 与项目；
- 只跑失败项、未测项、以及受修复影响的邻场景（同判断点、同数据路径）；
- 批次评论写「补验批」，并列出每条来源（原批次与原始判定）；
- 全部通过后，报告里的通过表引用补验批结果，原始批次结果作为历史保留。

补验批也要遵守同样的开始/结束评论与证据归档规则，不能因为「只是补验」就省证据。

### 8.6 候选变了，重跑范围怎么定

| 候选变化 | 重跑范围 |
|---|---|
| 只改文档、注释、测试说明 | 不重跑；报告注明候选未变，结论沿用 |
| 修 P0（崩溃、数据损坏、核心写失败、绑定不可用） | 受影响批次全量重跑，另加 B1 的 J1-01、J2-01 冒烟 |
| 修 P1（显示、交互错误） | 只重跑失败场景与同判断点的邻场景 |
| 只修测试工具、夹具、浏览器脚本 | 候选不变；重跑受影响的场景，其他沿用 |
| 只改 seed 数据或项目结构 | 只重跑依赖这些数据的场景，通常是 B2 与 B3 的写场景 |
| main 前进但没修本报告的问题 | 不追；报告写「测的是提交 X，main 已前进到 Y，未验证」 |

### 8.7 报告只引用最后一个候选的通过项

报告最终结论以最后一个候选为准。旧候选的通过项不能拼进新候选的通过表；旧结果只作为「历史记录」放附录，并注明候选哈希。这样读者不会看到一个通过表里混着两个提交的结果。

### 8.8 机时预算

| 阶段 | 估计 | 说明 |
|---|---|---|
| 第 0 阶段 | 4-7 小时 | 工具补齐与验收；并行会话做的话按实际排期 |
| B1 | 60-90 分钟 | 含准备与清理约 20 分钟 |
| B2 | 70-100 分钟 | 101 张票的种子数据约 5-10 分钟 |
| B3 | 100-140 分钟 | 写操作要等 glab 子进程与页面刷新；按 2 小时上限拆 B3a/B3b，共用环境 |
| B4 | 60-90 分钟 | 双实例准备与切换耗时 |
| 场景脚本编写与调试 | 每场景 20-40 分钟 | 20 条核心约 6-9 小时；这是历史批次实测里最容易被低估的一段 |
| 补验批 S1 | 30-60 分钟 | 只跑失败与未测 |
| 证据归档与索引 | 每批 10-15 分钟 | 复制、SHA256、INDEX 更新 |

总计约 2.5-3 天（第 0 阶段 + 四批纯执行 + 脚本编写 + 归档），不含修缺陷与重跑。如果机时只有 1 天，砍加批与非核心，不要砍第 0 阶段与核心 20 条。

## 9. 证据怎么组织、索引长什么样

### 9.1 三层结构

1. **批内原件：** <批次目录>/evidence/<场景>/attempt-N/。这是唯一可写的现场记录，写完不再改。
2. **归档副本：** <工作根>/evidence-archive/<批次>-<时间戳>/。批次结束整批复制，附 candidate.json 与 SHA256SUMS.txt；归档后不再改。
3. **全局索引：** <工作根>/evidence-archive/INDEX.md（人读）与 index.jsonl（机器读）。一行一个场景一次尝试，指向归档副本，不指向可能被删除的批内目录。

### 9.2 每个场景必须有的文件

    J7-02/
      attempt-1/
        result.json                 ← 判定、缺陷票、候选、重验状态
        observations.md             ← 六元组，人读
        evidence.json               ← 机器可读的六元组与观测字段
        shots/wide.png              ← wide 截图；布局场景加 narrow/short
        page-diagnostics/wide.json  ← fullscreen、viewport、screen
        tool-response.json          ← 工具回包原文（只作动作记录，不作独立证据）
        independent-readback.json   ← glab api / 网页读回字段
        logs/plugin-excerpt.log     ← 关键日志行，不复制整份日志
      result.json                   ← 最终结论与 attempts 列表

evidence.json 的字段：

    {
      "scenario": "J7-02",
      "claim": "在免费档、点击「标记为被 #K 阻塞」后，界面显示 Blocked by 行，GitLab 网页区块为空，正文有 DSH-BLOCKED-BY 标记。",
      "conditions": {"candidate": "<sha>", "profile": "web", "window": "wide", "project": "<path>", "tier": "free", "data": "..."},
      "steps": ["..."],
      "observations": [
        {"source": "界面", "value": "Blocked by #K", "path": "shots/wide.png"},
        {"source": "网页", "value": "Blocked by 区块为空", "path": "..."},
        {"source": "glab-api", "value": {"description": "...", "blocking": []}, "path": "independent-readback.json"}
      ],
      "inference": "免费档没有原生阻塞写，产品用正文标记表示关系；界面与正文一致，网页原生区块为空属于使用限制。",
      "verdict": "通过",
      "defect": null
    }

### 9.3 批次 INDEX.md

每批一份，列：

| 场景 | 判定 | 一句话声称 | 证据目录 | 独立读回 | 缺陷票 | 候选 | 重验 |
|---|---|---|---|---|---|---|---|
| J1-01 | 通过 | 首次选择 GitLab 后检查页三步全绿，能打开工作区 | B1.../J1-01/attempt-1 | glab auth status + 界面 | 无 | a1b2c3 | - |
| J2-02 | 未测 | 未装 glab 时给出可操作指引 | B1.../J2-02/attempt-1 | 无（起不来实例） | 无 | a1b2c3 | 补验批 S1 |

「一句话声称」直接从 evidence.json 的 claim 取，不另写；这样索引和证据不会对不上。

### 9.4 全局 index.jsonl

一行一个场景一次尝试，字段固定：

    {"batch":"B1","scenario":"J1-01","attempt":1,"candidate":"<sha>","verdict":"通过","claim":"...","evidencePaths":["evidence-archive/B1-.../J1-01/attempt-1/"],"independentSide":"glab-api","defect":null,"retest":null,"start":"2026-10-31T05:10:00+08:00","end":"2026-10-31T05:22:00+08:00"}

约定：

- verdict 只能是六类之一，不写「通过（基本）」「失败（疑似）」这类复合词；
- candidate 必须是完整提交哈希，不写 main 或 latest；
- evidencePaths 指向归档副本，不指向批内目录；
- defect 是票号字符串或 null；
- retest 是「待新候选」「补验批 S1」或 null；
- 新增行只追加，不修改历史行；更正写在独立的 corrections.jsonl，并携带被更正行的批次、场景、尝试号与原因。

### 9.4.1 条件账本（conditions.jsonl）

「有条件可用」不能只写在报告句子里，要有一份条件账本，一行一个条件：

    {"condition":"免费档不支持原生阻塞写","scope":"GitLab Free / 所有项目","scenario":"J7-02","evidence":"evidence-archive/B3-.../J7-02/attempt-1/","alternative":"正文 DSH-BLOCKED-BY 标记 + 界面 Blocked by 行","expiry":"下一版重验","owner":"#1679"}

字段约定：condition 是可判定的条件句；scope 写版本、站点档位、项目形状或窗口形态；evidence 指向归档；alternative 写替代路径（没有就写「无」）；expiry 写「下一版重验」或具体版本；owner 指向来源票或缺陷票。报告里的「条件清单」直接由这份账本汇总，不手写第二份。

### 9.4.2 报告索引脚本

第 0 阶段补一个小命令（例如 scripts/real-machine/commands/report-index.mts），输入是全局 index.jsonl，输出：

- 按 8 条支持度断言分组的场景计数（通过 / 产品缺陷 / 使用限制 / 环境限制 / 未测 / 测试工具问题）；
- P0/P1/P2 缺陷票列表与重验状态；
- 每个候选的通过率与未测数；
- 条件账本的条目数。

输出 Markdown 摘要供 #1678 直接贴进报告，不靠人肉数 JSONL。脚本本身要有单元测试或至少一次对样例 index.jsonl 的快照测试，避免统计口径漂移。

### 9.5 SHA256SUMS 与不可编辑

- 批次结束时对 evidence-archive/<批次>-<时间戳>/ 下所有文件生成 SHA256SUMS.txt（相对路径，按字典序）。
- 归档完成后目录设为只读（Windows 的只读属性即可，不是权限隔离）；要更正，写 corrections.md 与 corrections.jsonl，并在清单票评论里说明，不改原件。
- candidate.json 与 tgz 同时归档，保证日后能还原「当时装的是哪个包」。

### 9.6 保留与容量

- 每批归档至少保留到下一版发布结束；发布结束后可只保留 INDEX、result.json、observations.md 与关键截图，删掉整页截图与原始日志大文件。
- 工作根总量不超过 15GB、单批不超过 2GB、批次目录不超过 20 个；超限时先删最旧的已发布批次的大文件，再考虑移动证据到冷存储。
- 证据归档不放进本仓库，避免仓库膨胀与误提交；需要长期引用时在报告里写绝对路径或仓外路径。

### 9.7 #1678 可以直接消费什么

- index.jsonl：汇总每个结果的判定、候选、缺陷票、独立读回来源，不需要再翻目录。
- 每批 INDEX.md：人读的批次摘要，可直接改成报告里的「批次记录」章节。
- evidence.json：claim 字段就是报告「逐项能力结论」的底稿；conditions 就是作用域六元组；inference 是给作者看的推理，不是最终文案。
- result.json：缺陷票与重验状态，用于缺陷流转与已知限制。

## 10. 交棒 #1678：报告怎么接

### 10.1 前置关系

#1677 关闭后 #1678 才解锁（当前 #1678 被 #1675、#1677 阻塞，#1675 已关闭）。#1677 关闭时要在地图 Decisions so far 写一行：执行编排采用 4 批 + 第 0 阶段 + 补验批，候选一次冻结、每批一套隔离环境、证据三层与 index.jsonl。

### 10.2 报告结构建议（对应 #1678 的四问）

1. **覆盖范围与结论摘要：** 8 条支持度断言 A1-A8 的逐条结论（可用 / 有条件可用 / 不可用 / 无法判定），核心 20 条的结果计数，P0 是否为 0。
2. **环境与批次记录：** 候选（提交、版本、哈希）、操作系统与屏幕、web profile、GitLab 站点档位与账号、项目形状与数据量、每批的开始/结束时间与场景范围。
3. **逐项能力结论：** 按 8 条断言分组，每条下列场景结果与一句 claim；「有条件可用」必须写条件（版本、站点档位、项目形状、窗口形态）。
4. **已知限制：** 分三小类——产品设计取舍（例如免费档无原生阻塞）、环境限制（例如无法验真实未登录）、未测边界（例如 1000 张地图封顶）；每条写「为什么、影响谁、有没有替代路径」。
5. **缺陷与重验：** 按 P0/P1/P2 列表，票号、状态、修复候选、重验结果；未修完的写明。
6. **证据索引：** 指向 evidence-archive 的 INDEX 与 index.jsonl，不在报告正文粘大段日志。
7. **方法与局限：** 哪些是 agent 驱动、哪些人工复核，哪些结论依赖间接观测。

### 10.3 结论口径

- 「可用」：8 条断言全部通过，且核心 20 条无未测；P0=0 是必要不充分条件。
- 「有条件可用」：8 条里至少一条有条件通过，或存在未测边界；必须列条件清单。
- 「不可用」：A1-A4 任一失败（绑定、读取、写回、关系）。
- 「无法判定」：核心断言存在未测，且未测项足以改变结论。
- 报告不写「基本可用」「大体没问题」；每个结论后面跟场景编号与证据路径。

### 10.4 已知限制与 ROADMAP 的衔接

docs/ROADMAP.md 里 GitLab 标着「计划中」，报告不能写成「已支持」或「可发布」。建议写法：

> GitLab 后端在 web profile 下已具备可用的核心能力（读取、写回、关系、降级提示），但仍是计划中能力：免费档不支持原生阻塞写，超过 100 张票的项目存在列表截断风险，真实未登录状态未验证。适用于小团队、单项目、票数不超过 100 的日常使用；不建议用于大规模项目或需要原生阻塞/父子关系的团队。

具体句子由 #1678 定，本笔记只给结构与约束。

## 11. 对抗式自审：这套编排哪里最容易被推翻

### Q1：4 批是不是太少，会不会把风险挤在一起？

4 批是按环境固定成本和风险隔离切的，不是按功能域数量。B3 最重，已经给了拆分规则；如果实际执行发现 B3 仍需超过 2 小时，就按 B3a/B3b 拆窗口，不增加环境。加批只在核心 20 完成后开，避免「批很多、核心没跑完」。真正的风险不是批少，而是为了凑批把核心场景挪到加批。

### Q2：B3 里既有界面读又有工具写，工具坏了会不会整批停？

会。所以 B3 的第一条是 J6-01（打开详情），先确认界面读正常；如果 3.2 的两条工具写路线都走不通，按 3.2 的退路处理：4 条工具写场景记未测，其余 3 条界面场景照跑，不因为工具坏而整批作废。批次结果里分开写「界面部分通过、工具写未测」，不能合并成「B3 未测」。

### Q3：沙箱项目延迟删除，会不会把免费档项目额度用光？

GitLab 删除项目是延迟删除（marked_for_deletion），在保留期内仍占项目数。每批建 1 个，4 批 + 读池 1 个 = 5 个，补验批再 1 个；免费档通常允许远多于 5 个，风险低。真正要防的是「删除失败还继续建同名项目」，所以项目名带时间戳、manifest 记 id、删除后读回 marked_for_deletion_at，失败就停并报告，不复用路径。

### Q4：共用真实 keyring，会不会测出「假通过」或影响账号？

共用 keyring 是这台机器的现实：配置目录可以隔离，系统凭据不能。影响有两面：

- 好处：不用把 token 落到文件或命令行，符合凭据纪律；
- 风险一：五个批次共用一个账号，如果测试期间有人在别处撤销 token，所有批次同时失败；前置巡检能发现，批次结果记环境限制，不记产品缺陷。
- 风险二：「未登录」只能用无效 token 模拟，不能验真实 keyring 缺失；报告必须写明这是模拟，不能宣称验过真实未登录。

不接受的做法：为了隔离去 glab auth logout 再登录，可能丢真实凭据；或者把 token 复制到批次目录，违反凭据纪律。

### Q5：两条工具写路线都走不通，A3/A4 还能不能给肯定结论？

不能给「通过」，只能给「有条件通过」或「无法判定」。缓解顺序：

1. 先花最多 1 小时按 3.2 验证路线一（页面内直调）；不成再试路线二（deck-write 命令）。任一条成功就以它为主证据；
2. 走不通就用固定提示词经模型调用 deck 工具，作为用户路径证据，放报告附录；
3. 两者都不行，4 条工具写场景记未测，A3（写回真实）与 A4（关系真实）的结论降级为「有条件可用」，条件写「工具写路径未验证」。

不能拿「模型说成功了」当产品证据，也不能因为工具坏就把整个 GitLab 后端判不可用。

### Q6：主工作区脏，冻结会不会把别人的改动带进去？

会，所以默认不在主工作区冻结：clone 或 worktree 到 candidate-src，检出目标提交，node_modules 用 junction 或 npm ci，DECK_REPO_ROOT 指过去。只有实在做不了干净检出时才用 --allow-dirty，且必须先列脏文件、确认不在源码/配置/构建路径；任何一项在，就停。candidate.json 要记录构建来源与脏文件清单（如果有）。

### Q7：101 张票种子会不会很慢或撞限流？

101 张票大约 1-2 分钟（串行 API），免费档限流通常远高于这个量；但为了稳，种子命令要幂等、可断点续跑、失败重试 3 次带退避；如果 5 分钟还建不完，减到 101 张整（不能少于 101，否则验不了「超过 100」），并记录实际票数。票池建好后标记只读，任何写操作前先检查标记，避免污染只读池。

### Q8：证据会不会太大，复制和归档拖垮机时？

会有一点。单场景 3 张截图加诊断约 1-2MB，40 个场景约 40-80MB；加上日志与回包，单批 100-200MB，远低于 2GB 上限。真正大的是整页截图与浏览器 trace，规则是只留关键截图与日志摘录，不存 trace。归档复制是本地磁盘操作，每批 1-2 分钟；如果工作根在慢盘，先测一次复制速度，再决定是否只归档 result.json 与关键截图。

### Q9：agent 驱动点击，能不能替代人工看界面？

不能完全替代。agent 能稳定执行点击、读 DOM、截图、读接口；但「按钮被盖住一半」「文字重叠」「颜色对比度」「动画卡顿」这类视觉问题，DOM 断言看不出来。建议 hybrid：agent 跑步骤与收集证据，人工在批次结束时抽查关键截图（每批 10-15 分钟），发现疑点回看原始证据。报告要写清哪些结论是 agent 判定、哪些有人工复核，不能把 agent 的 DOM 断言说成「人眼确认」。

### Q10：布局结论用 2560×1440 的屏，能不能推广到别的屏？

不能。布局结论必须带作用域：屏幕分辨率、窗口形态、缩放比例。wide 真全屏在 2560×1440 下通过，只能说明这个尺寸；narrow 800 宽、short 600 高是固定条件，可以跨机器比较，但也要记录 DPI 缩放。报告里不写「布局正常」，写「在 2560×1440、100% 缩放、wide 真全屏下，侧栏 331px，无横向滚动」。

### 审查后仍然存在的四个薄弱点

1. **真实未登录无法验：** 只能用无效 token 模拟，报告必须显式标注，不能写成已验证。
2. **工具写路径依赖第 0 阶段新增入口：** 路线一（页面内直调）比路线二轻，但两条都还没有实测过；这是第 0 阶段的最大不确定性，走不通会拖累 A3/A4，必须在第 0 阶段就确认，不能等到 B3。
3. **免费档 403 与 100 张截断都是「间接可观测」：** 前者只能看话术与降级，后者只能看列表条数与 partial 提示；报告要给「有条件通过」，不能给「通过」。
4. **外部 HTTP 调 /api/dsws 回 401（已实测）：** 代执行通道必须跑在页面上下文里，所以工具写的主证据仍是「页面内调用回执 + GitLab 侧读回 + 文件侧副作用」，外部脚本无法旁路核查页面状态；报告要说明页面内读数由产品代码自证，不能把它当唯一独立观测。
