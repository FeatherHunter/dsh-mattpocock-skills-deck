## 最新 beta 还回整票吗（核心问题）

### 回执现在的形状（beta.32 与 beta.33 相同）

- 写后回读：`src/deck/tools/issue-patch.ts:426-427` 调用 `t.get(repo, key, {}, opCtx)`，不传 comments 参数，于是 GitHub 房的单票读沿用默认查询、带最多 50 条评论正文（`src/tracker/rooms/github/queries.ts:57-58` 自己注释「单票详情默认 50 条」；`src/tracker/rooms/github/issues.ts:342-347` 在没给 `comments.first` 时不加限制）。

## 修法形状（候选，尚未实施）

两条路线，正文里问维护者选哪条；两条都只动写回执，不动读工具与后端。

- **路线 A（推荐）**：写操作默认精简回执。在 `src/deck/tools/issue-patch.ts:437-447` 按参数决定 `data.ticket` 放什么：默认放三格摘要（`key/state/updatedAt`，可再加 `title`），整票只在显式传 `detail:"full"` 时放进 `data.ticket`（仍只放一份，#1273 的承诺不变）。`items` / `notes` / `touched` / `readBack` 三格保持原样。参数加在 `issue-patch-definition.ts` 的 properties。渲染层不用改（`data.ticket` 变小，自然少占预算）。
- **路线 B（最小改动）**：不新增参数，写后回读时给 GitHub 房传 `comments:{first:0}`，只去掉评论、保留正文与元数据。改一处调用即可，但长正文的票仍回整段正文，省不到报告里想省的那一半。
