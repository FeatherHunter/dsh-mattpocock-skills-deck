# 规格：deck 工具链整体改写 TypeScript

> 本规格是「把 deck 工具链改成 TypeScript」这件事的施工蓝图，与设计决议 `docs/adr/20261011-deck-ts-rewrite.md`、共识记录 `research/1010-consensus.md`、地图 #1010 配套。决议说「为什么这么定」，本规格说「谁做什么、怎么算做完」。

## Problem Statement

今天九个 deck 工具（`deck_context`、`deck_issue_get`、`deck_map_snapshot`、`deck_issue_list`、`deck_issue_create`、`deck_map_plan_create`、`deck_map_link`、`deck_issue_patch`、`deck_issue_report`）以及它们身后的两个后端房间（GitHub 房、Markdown 房）、契约层、注册表、识别判定，全部是手写 JavaScript。维护者面临的处境是：

1. 打开仓库读不到结构——同一次调用横跨五处目录，靠读注释补全，新人（包括未来的维护者自己）无法顺着一条线看懂「agent 的一次调用到底经过了什么」。
2. 语言不统一——仓库里有四个用 TypeScript 写的计算核与一批界面真源，唯独最核心的 deck 工具链是 JavaScript，类型承诺散在注释与运行时校验里（房间实现错签名，跑起来才知道）。
3. 排查靠猜——出错时日志只记两行（成功/失败），维护者无法从日志判断「坏在哪一步、为什么」。
4. 维护者是 TypeScript 新手，而这次改造正好是把这套代码读懂、并顺带入门 TypeScript 的机会；没有讲解与讨论的机制，改造就变成「别人替我改完了，我还是不懂」。

## Solution

把 deck 工具链与它底下的两个后端房间，按「一次调用的经过顺序」重排成新目录，全部用 TypeScript 重写；契约写成真正的 `interface`，两个房间用 `implements` 对上，写错编译期就报错；日志按「能不能定位 BUG」的判据大幅增密；注释按「能不能帮维护者看懂逻辑」的判据写。

开发形态是**一个改写单元一张票**：每个单元先讨论（与维护者对齐想法）、再开发、再讲解；讲解中发现的问题另开修复票，修完再讲一次。维护者全程可插话，每个单元交付时给出「讲解三看」（封装、参数、边界与失败路径）请他表态。全部做完时：旧 JavaScript 变成 TypeScript、功能行为不变、维护者读得懂并能讲回来。

## User Stories

1. 作为维护者，我想在动手前就看到每个改写单元的「打算怎么做」，这样我能在写代码之前先对齐想法，而不是事后返工。
2. 作为维护者，我想知道每个单元负责哪些旧文件、会变成哪些新文件，这样我能把「哪块代码归哪张票」记清楚。
3. 作为维护者，我想在每个单元里被明确告诉「你是 TypeScript 新手」，这样讲解会从零讲起，不假设我懂类型。
4. 作为维护者，我想在讲解里看到「这段代码用到了哪些 TypeScript 概念」（类型别名与接口的区别、可选属性、可辨识联合、泛型），并且用当次的代码当例子，这样我学得会。
5. 作为维护者，我想在每个单元交付时看到三个请我表态的点（封装、参数、边界与失败路径），这样我的意见能真正进到代码里。
6. 作为维护者，我想在我没空回复时开发仍能按票面写明的建议继续，这样进度不被我卡住，而我的意见会被记成待复核清单。
7. 作为维护者，我想一个单元一张票、且严格串行，这样我跟读不会串线。
8. 作为维护者，我想横切的小事（某单元的尾巴、门禁夹具、构建配置）能单独成票，这样我累了可以先挑一张感兴趣的小票做掉。
9. 作为维护者，我想票号按「由外向内」的阅读顺序编（注册与装配 → 工具入口 → 工具壳 → 日志 → 契约 → 注册表 → 识别判定 → GitHub 房 → Markdown 房 → 宿主接线 → 横切），而动手顺序按依赖顺序标在票里，这样我读起来顺、开发也不返工。
10. 作为维护者，我想每个单元的完成判据是死的：相关门禁全绿、行为对照有证据，这样「功能全部正确」不是一句口头保证。
11. 作为维护者，我想看到「行为零变化」的对照证据（同一输入新旧产出一致），这样我敢相信搬家没有偷偷改行为。
12. 作为维护者，我想每个单元交付时做一次日志演练（只看日志说出坏在哪一步、为什么），这样日志够不够用有实证，而不是数行数。
13. 作为维护者，我想有一份《日志导读》教我怎么读日志、哪些行连起来代表一趟流程走通，并附一个完整正确流程的样例，这样我从第一票起就能自己看日志判断。
14. 作为维护者，我想日志在出错时能直接指出环节、输入摘要、期望与实际差在哪，这样我不用复现就能定位。
15. 作为维护者，我想注释写清「这个文件在链路哪一段、什么约定不能改、一个真实反例」，这样我读代码时不用猜。
16. 作为维护者，我想源码只有一个手写真源（TypeScript），产物不进仓库，这样不会有「改了真源忘同步产物」的困惑。
17. 作为维护者，我想有一条准备命令让「拉下来 → 一条命令 → 能跑」成立，这样不入库产物不会拖累我本地开发。
18. 作为维护者，我想新写的测试用成熟测试框架，老的百来个验证脚本随对应单元分批迁移，这样测试不是一次性重写的高风险工程。
19. 作为维护者，我想测试主要挂在「工具表」这一层（喂调用、看三态回执），这样搬家不会让测试碎掉，绿了就代表行为没变。
20. 作为维护者，我想房间层也有一层测试（直接调后端对象的公开操作），这样出问题时分得清「工具错了还是后端错了」。
21. 作为维护者，我想契约层靠编译与探针把关（真按接口实现一遍两房形态、再故意写错一处看类型拦不拦），这样类型的承诺不是纸面的。
22. 作为维护者，我想有一条构建产物冒烟（构建后拿真实产物跑初始化、读一张票、改一次字段），这样「构建出来的东西还能用」有证据。
23. 作为维护者，我不想给每个函数都写单元测试，只给复杂且纯的规则函数写，这样「让参数更合理」不会每次都要改两遍代码与测试。
24. 作为维护者，我想旧的「读文件文本断言路径」那批门禁换成标准的依赖方向检查工具，这样门禁管的是真问题（依赖朝下、禁循环）而不是路径字面。
25. 作为 AI 使用方，我想九个工具在改造后行为完全不变（同样的参数、同样的三态回执、同样的必备标签与进度区自动补全），这样我的既有用法不作废。
26. 作为 AI 使用方，我想工具写得不对时回执仍然诚实（做不到就说做不到、部分成功就逐项列出），这样我不会把残缺结果当完整结果用。
27. 作为面板（消费者），我想工具与房间的改造不动行为，只跟随路径改名做轻微适配，这样界面照旧能用。
28. 作为面板，我想契约里明确哪些操作是所有房间都必须实现的、哪些是某个房间独有的扩展，这样界面不会依赖一个房间才有的能力。
29. 作为维护者，我想 GitLab 房这次只随目录改名、代码不转，并留一份迁移说明写清以后怎么按契约补齐，这样它不会拖慢主线也 不会烂在原地。
30. 作为维护者，我想旧故障票按「随重构收口」处理：开发中明确已消失的当场关闭并记录由哪一次改写解决，不确定的等开发全部完成后人机协同逐张过，这样票不会无声消失也不会被草率关掉。
31. 作为维护者，我想这次改造不碰面板行为、不碰四个已有计算核、不碰提示词文案，这样范围可控、红窗口短。
32. 作为维护者，我想在主分支上小步提交、过程中允许直接提交推送，这样不会有长分支与并发会话的冲突。
33. 作为维护者，我想提交信息用中文说清「改了什么、为什么」，这样以后翻历史能看懂。
34. 作为维护者，我想重构期间不发生「同一条边界两个写者」的冲突（要搬走的文件归重构，其他票只读引用），这样两边的工不会互相作废。
35. 作为维护者，我想每一步都能回答「我有没有改坏东西」，所以动手前先把仓库的验证基线拉回全绿，这样红灯不会新旧混在一起。
36. 作为维护者，我想那两条根本没挂进验证链的红灯脚本被挂进链里，这样红了会有人知道。
37. 作为维护者，我想知道这次改造与另外两件并行的活（配置存储改造、判定出口收口）的边界写在票面上，而不只是记在对话里，这样以后翻票就能看到。
38. 作为后续接手的人，我想 `src/deck/README.md` 一页纸就能看懂一次调用经过哪几层，这样我不用先读完五十个文件。
39. 作为后续接手的人，我想目录名与文件名各自表意（目录名说过的、文件名不再重复），这样我扫一眼目录就知道代码怎么分。
40. 作为后续接手的人，我想依赖方向由编译器保证（只能朝下，写反编译不过），这样我不会无意中造出反向依赖。

## Implementation Decisions

**范围与归属**（详见设计决议）

- 新架构按「谁用它它归谁」分三层：只有 deck 工具链用的进 `src/deck/`（工具、壳、注册与装配、日志）；面板与 deck 共用的进 `src/tracker/`（契约、注册表、两个后端房间、识别判定）；只有面板用的不动。
- 依赖方向永远单向朝下：工具 → 壳 → 契约 → 房间 → 平台能力。工具只引用契约接口，不深引用房间文件。
- 契约的家在 `src/tracker/contract/`（面板与 deck 共用，不归 deck 独有）。
- GitLab 房只随目录改名、代码不转，附一份迁移说明。
- 范围之外：客户端行为、四个已有计算核、提示词文案、部署与加载形态。

**契约**

- 契约从「注释里写的类型 + 运行时校验」升级为 TypeScript `interface`：19 条契约操作 + 新增的 `getRepoPermissions`（读写权限是工具诚实回执的通用依据）。
- 房间实现取子集是被允许的常态（注册表会给缺的方法补「做不到」的桩），所以房间对象的类型是「契约的子集 + 本房扩展」。
- 两个房间独有的能力（GitHub 房 `listSubIssues`、Markdown 房 `ensureLabelColorsFile`）与两房共有的只读辅助口（取仓库标识、产出票据链接、产出仓库身份）各有明确的类型位置，不做成索引签名糊过去。
- 房间模块对象补声明今天契约漏掉但两房实际在用的键（品牌色板、检查目录、修复知识），否则房间照原样写会编译不过。
- 契约层只放类型与数据（操作名录），不许出现运行时实现：这条由门禁强制。
- 操作名的唯一真源是名录数组，类型由它生成；迁移期由门禁断言「名录与运行时的那份清单同集」，等运行时那份退位后撤销这条断言。
- Markdown 房今日已知的语义差异（六处收了可选项不往下传、没有写前版本校验、没有写后环检）不许用可选参数藏起来，要在接口注释里逐条写明「本房不实现」。

**目录与命名**

- 新树：`src/deck/`（工具、壳、注册与装配、日志）、`src/tracker/`（契约、注册表、房间、识别判定）。目录层级按一次调用的经过顺序排。
- 命名规矩：目录名已经说清的事，文件名不再重复；文件名说清它装的是什么。
- 契约目录按读者分件：身份与枚举、实体、调用上下文、返回值、入参，另加操作层、模块对象、操作名录、统一出口。
- 注册表搬进 `registry/` 后去掉重复前缀（`core`、`shape`、`views`）。
- 房间目录统一叫 `rooms/`，文件名一个不改（它们本来就是功能名）。

**构建与工程**

- 源码只有 TypeScript；构建产物不进仓库；留一条准备命令让「拉下来 → 一条命令 → 能跑」成立。
- 按域拆 TypeScript 工程引用，依赖方向由编译器保证。
- 手写代码全覆盖（含构建脚本、测试、接缝层）；派生文件与四个计算核不动。
- 单包，不拆工作区包。

**日志**

- 判据是「BUG 发生时，日志足以定位到位置与原因」，不是行数多。
- 每个改写单元交付时做一次日志演练；配一份《日志导读》（含一趟完整正确流程的样例）。
- 事件名与字段含义稳定；新增字段先登记到对照表再写代码；可重放的凭证原文永不落盘。

**注释**

- 判据是「帮维护者看懂代码逻辑」：文件头写「这一文件在链路哪一段、什么约定不能改、一个真实反例」；导出写清语义与失败形状；非显然分支写为什么。
- 维护者是 TypeScript 新手，讲解里用当次代码讲概念，不用抽象定义。

**开发形态**

- 一个改写单元一张票（挂在地图 #1010 下），下挂讨论、开发、讲解三类子票；讲解中发现的问题另开修复票。
- 票号按阅读顺序由外向内编，动手顺序按依赖顺序标在票里。
- 严格串行；横切小事独立成票。
- 每个单元给维护者「讲解三看」请他表态；他没回时按票面建议执行并记「默认执行」。

**与别的活的边界**

- 要搬走的文件归本次重构；配置存储改造与判定出口收口对这批文件只读引用。重叠面十三个文件留作尾票，等那两件收口后再动。
- 日志事件对照表由本次重构最后统一改路径并收编新增字段。

**动手前的前置**

- 上手第一件事是把仓库验证基线拉回全绿，做法先例写在下面，照这个样子做：13 条同根因红灯（门禁夹具没给装配方传判定出口）已用「补一个共用测试桩、生产代码零改动」修好，两条根本没挂进验证链的红灯脚本（父边重读、Markdown 父边）也已挂进链里。剩下还红的那些，先逐条查清归属再动手；查不清归属就说明基线还没到位，不带病开工。

## Testing Decisions

**什么算好的测试**：只测对外可观察的行为，不测实现细节。同一个输入进去、同一个回执与后端状态出来，就是好的；把内部步骤抄一遍的测试不算。

**四条缝（自外向内）**

1. 主缝 = 工具表（宿主装好的「名字 → 定义与执行」）：喂调用、看三态回执、看必备标签与进度区是否自动补、看边落在哪一列。覆盖九个工具的全部对外行为。
2. 房间缝 = 两房产出的对象：直接调公开操作看行为，用来分清问题在工具层还是后端层。
3. 契约缝 = 编译门禁 + 实现性探针：类型检查零错误、操作名齐、契约层无运行时实现、名录与运行时同集；另有探针真按接口实现一遍两房形态（能编译），再故意写错一处（类型必须拦）。
4. 构建产物冒烟（新增）：构建后拿真实产物跑一次最小流程——初始化看工作区与后端、读一张票、改一次字段。

**单元测试的尺子（不给每个函数配测试）**：一个函数被两个以上地方调用、输入输出是纯数据不碰外部世界、分支多到读了也可能想错——三条里中两条才单独测；薄封装与私有中间步骤交给外层。先例：四个计算核（配色、刷新、版本、配置读写）各有自己的纯规则单元门禁；deck 工具这一层靠主缝。

**现有测试怎么处置**：老的百来个验证脚本随对应改写单元分批迁移语言与运行方式；新写的测试用成熟测试框架。旧的「读文件文本断言路径」检查不保留，换成标准依赖检查工具（禁循环、禁跨层深引用、单文件行数上限）。迁移期每个单元要求：相关门禁全绿 + 行为对照证据。

**日志的验收**：每个单元一次「只看日志定位」演练，做不到就补日志点。

## Out of Scope

- 客户端（面板）的行为改动：只跟随路径改名做轻微适配。
- GitLab 房的代码转换：只随目录改名，附迁移说明。
- 四个已有 TypeScript 计算核（配色、刷新、版本、配置读写）的形态统一：另有主人，将来统一另立决策。
- 提示词文案本身、脚本残余清理、部署与加载形态（把插件变成标准包加载）——各自单独立票。
- 旧故障票里「不归本次」的那些（客户端快照等待、面板刷新与显示、提示词、残余脚本等）：仍归各自的主人。
- 产物入库（已决定不入库）。
