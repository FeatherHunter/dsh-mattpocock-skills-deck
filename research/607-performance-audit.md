# #607 全量性能体检：按实测耗时排序的问题清单

这份文件是 #607 的产出。它把「哪里慢、慢多少、拿什么量的」排成一张有序清单，供后面的落地票按图施工。

**这一票只量不改**：`src/` 下任何文件都没有被改动。

## 一、这本清单是怎么量出来的

### 1.1 数字的来源分四类，每条都会标明是哪一类

| 标记 | 含义 | 能不能当真机数字用 |
|---|---|---|
| **真机日志** | 从本机正在跑的那个 DSH 实例落盘的日志里数出来的 | 能。这是唯一能当真机数字用的来源 |
| **本地可复现回路** | 在开发机上跑仓库里的脚本得到，换台机器结果会不一样 | 不能。只能搬「有没有这件事」与「改前改后的倍数」 |
| **一次性对照实验** | 为了把一件事量清楚临时做的对照，脚本在 `.scratch/` 下 | 不能。同上 |
| **没量到** | 如实写「没量到」，并写清缺什么才能量 | —— |

### 1.2 日志的落点（这一步曾经有人查错过，特别写清）

本机在用的日志目录是：

```
D:\0Tools\DSH Desktop\.dsh-mattskillsdeck-cache\logs\
```

**不是** `%USERPROFILE%\.dsh-mattskillsdeck-cache\logs\`。后者也有一份同名文件，但那是很久以前的残留，写的人早就换了落点。这一票之前有人因为查错了目录，得出过「真机没日志」的错误结论。

路径里的文件夹名带前导点（`.dsh-mattskillsdeck-cache`）。

取数时用的快照：`2026-09-12.log`，**2,797,420 字节、20,387 行、平均每行 137.2 字节、时间跨度 10.41 小时**。下面所有「真机日志」的数字都来自这一份，收口脚本 `.scratch/607-final.mjs` 一次跑完输出全部核心数字，可以重跑对照。

**注意**：这个日志文件在测量期间一直在长（每一轮命名守护都会往里写）。所以「行数」这类总量数字每次跑出来都会比上一次大一点。本报告引用的行数都以上面这个快照为准；每条结论旁边都写了它的判定方式（数哪个事件、按什么口径聚合），换一天重跑应该得到同量级的数。

## 二、按实测耗时排序的问题清单

排序依据是「这条毛病一天总共烧掉多少时间」或「单次最大等待有多长」。

### 第 1 名：命名守护每一轮都把整份 issue 索引重拉一遍（全量分页，没有增量窗）

- **现象**：只要还有会话在等编号，命名守护的循环就在跑；它每一轮都为每个在等的仓库拉一次 issue 索引。这条命令没有 `since` 参数，是整份分页拉取。
- **根因**：`src/host/namingGuardian.js:110-127` 的 `namingFetchIndex()` 拼的 URL 是
  `repos/<owner>/<name>/issues?state=all&per_page=100`，**不带 `since`**，再配 `gh api --paginate`。仓库里已经写好了带增量窗口的那套（`src/shared/tracker/indexWindow.js` 的 `scanWindow`，`src/host/issueList.js:164-169` 的 `fetchIssueIndex` 在用它），命名守护这条路没有用。
- **实测数字（真机日志，2026-09-12 快照）**：
  - 命名守护循环在快照范围内跑了 **568 轮**（判定依据：每轮结束都会落一行 `timer.schedule {name:"naming-persist"}`，见 `namingGuardian.js:67`、`:176`）。
  - 相邻两轮的间隔：**中位 69.3 秒**、p90 70.9 秒、最大 129.6 秒。这就是「一轮扫完 + 退避等待」的总节奏。
  - **540 / 568 轮**里至少起了一条外部命令；每一轮的命令条数 **中位 2、p90 4、最大 13**；每一轮的外部命令耗时合计 **中位 10.6 秒、p90 16.2 秒、最大 31.1 秒**。
  - 全天 `gh.exec` **1497 条**，单条耗时 **中位 1293 ms、p90 10044 ms、p99 14201 ms、最大 20937 ms**；其中 **542 条超过 6 秒**、626 条超过 2 秒。单条耗时相加 **6372.6 秒（1.77 小时）**。
  - 全天「至少有一条外部命令在途」的累计时长 **6054 秒 = 1.68 小时**，占 10.41 小时跨度的 **16.1%**。
  - **归属**：按「每一轮结束时刻前后 30 秒」把它们附近的外部命令归到轮上，聚合出 **6238 秒，占全天外部命令耗时的 97.9%**。**这个比例偏高有一半是窗口口径造成的**（轮与轮相隔 69 秒、窗口 60 秒，等于覆盖了大部分时间轴），所以这个 97.9% **不能当成「命名守护烧掉 97.9% 的耗时」来引**。能站的住的说法是：用 ±2 秒的紧窗口量时，**83.7% 的耗时紧贴在轮次落点附近**；两条加起来只能说「绝大部分外部命令耗时发生在命名守护的轮次节奏里」。
- **本地一次性对照实验（这条全量拉取 vs 带增量窗那条的价差）**：对同一个仓库、同一台机器、相隔几秒各跑一次：

  | 命令 | 耗时 | 返回行数 |
  |---|---|---|
  | `gh api --paginate .../issues?state=all&per_page=100`（命名守护那条） | **7807 ms** | 593 |
  | 同上加 `&since=<7 天前>`（快照校验那条用的形态） | **2745 ms** | 152 |

  **倍数：2.84 倍**。绝对毫秒数是本地一次性对照，不能当真机数字用；倍数可以搬。
- **复现方式**：`node .scratch/607-final.mjs "<日志文件>"` 一次给出轮数、轮间隔、每轮条数与归属比例；`node .scratch/607-final.mjs` 里「命名守护轮次」那一节就是这条的算法。
- **对照目标准**：**超标**。宿主单次 `gh` 调用目标准 ≤ 1.5 秒，这条路的重活单次 7.8 秒（真机 `gh.exec` 里 >6 秒的那一档全天 542 条）。
- **给落地票的接口**：把 `namingFetchIndex` 改成走 `scanWindow` 那套（带水印 + 增量合并）。命名守护持有 `indexes` 快照（`naming-guardian.json` 里已经在存），天然具备做增量的条件。

### 第 2 名：三个扫描器各扫各的，同一份索引被两处分别拉取（数据放大）

- **现象**：客户端探测（`wf.probe`）、快照校验（`wf.snapshot` / `wf.refresh` 里的 `cacheSnapshotIsCurrent`）、命名守护（全量索引）三条链互相不知道对方在干什么，各自拉各自的数据。
- **根因**（代码事实）：
  - 客户端探测：`src/client/kernel/probe-auto.js:140` 的 `setInterval(..., PROBE_MS)`（`PROBE_MS` 默认 60000），另有 `window.focus` 与 `document.visibilitychange` 两条恢复通道，共用 `FOCUS_PROBE_MIN_MS` = 60000 限流。
  - 快照校验：`src/host/issueList.js:281-293` 的 `cacheSnapshotIsCurrent` → `fetchIssueIndexWindowed`（`:230-279`，带增量窗）。
  - 命名守护：见第 1 名，全量、不带窗。
  - **没有任何「同键请求合并」**：三个入口各自调各自的取数函数，同一个仓库、同一个时刻会起多条 `gh`。
- **实测数字（真机日志，2026-09-12 快照）**：
  - 「有其它取数同时发生」的命名守护轮次：**391 / 556**（用 ±20 秒窗口量的那次；同一份文件再往下跑数字会略变）。
  - 三类取数（命名守护 + 客户端探测 + 快照/刷新）落在同一个 30 秒窗里的情形：**57 个窗**；窗内 `gh.exec` 条数 **中位 5 条、p90 12 条、最大 13 条**；窗内这些命令自己的耗时合计 **中位 17.1 秒**。
  - 把全天 `gh.exec` 按「相邻两条开始时刻相差 ≤2 秒」切成簇：**1126 个簇，其中 213 个簇有 2 条以上**（2 条 164 个、3 条 28 个、4 条 6 个、5 条 4 个、7 条 3 个、8 条 3 个、9 条 4 个、11 条 1 个）。
  - 最大并发：**7 条同时在外**。
  - 多命令簇前后 3 秒内出现最多的事件：`wf.namingPlan` 212 次、`detection.detect` 200 次、`wf.probe` 185 次、`workspaceStore.miss` 61 次。
  - 这些含 2 条以上的簇：墙钟跨度 **中位 8075 ms、p90 11483 ms、最大 20937 ms**；簇内外部命令自己的耗时合计 **1726.5 秒**（占全天外部命令耗时的 27.5%）。
- **补充观察（真机日志，09:35:09~09:35:11 逐事件时间线）**：同一秒里，`detection.detect` 连出 4 次、每次都会落一个 `snapshot.request`；`gh.exec` 在 09:35:10.364 到 09:35:11.417 之间连出 **9 条**，`cwd` 分属 3 个不同的工作区指纹。这说明同一时刻有多个工作区在各自要数据，互相不合并。
- **复现方式**：`node .scratch/607-triple.mjs "<日志文件>"`；`node .scratch/607-burst.mjs "<日志文件>" 2000`。
- **对照目标准**：**超标**。这条是第 1 名超标的放大器，也是探测一轮 ≤1 秒达不成的直接原因（见第 3 名）。
- **给落地票的接口**：地图 #604 的「宿主取数层设计」票（#608）要解决的就是它——接缝画在哪、缓存键怎么定、请求怎么合并、三个扫描器怎么收成一个。

### 第 3 名：客户端每 60 秒的探测一轮要 4.5 秒（目标准 1 秒）

- **现象**：客户端每 60 秒发一次 `wf.probe`，一次探测的中位耗时 4.47 秒。
- **根因**：**还没查到根因**。可以说清的是：`wf.probe` 在宿主侧会走探测级联（`src/host/detectChain.js`），期间会经 `ctx.exec` 起 `gh auth status`、`gh api repos/<o>/<n>`、`gh api user` 等命令；实测每一轮探测期间起的外部命令条数中位 1 条、p90 6 条、最多 9 条。但「4.5 秒里有多少是等 `gh`、多少是插件自己的活」目前分不出来——因为 `gh.exec` 现在没有「发起来源」字段（见 5.1 节），无法把命令归到具体是哪一轮探测起的。
- **实测数字（真机日志）**：
  - `wf.probe` 全天 **962 次**（收口快照），耗时 **中位 4471 ms、p90 6124 ms、最大 15938 ms**，单次耗时相加 **4355 秒**——这是全天所有宿主接口里**总耗时最大的一条**。
  - **超过目标准 1 秒的轮数：839 / 879 = 95%**（这一项在更早的那次取数上算的，样本是同一份文件的前 879 次）。
  - 每一轮探测期间的外部命令条数：中位 1、p90 6、最多 9；**30 / 879 轮期间一条外部命令都没起**——说明 4.5 秒不是全靠 `gh` 撑起来的。
- **复现方式**：`node .scratch/607-final.mjs "<日志文件>"` 里「host.call 总耗时排行」那一行；日志里数 `host.call {method:"wf.probe"}`。
- **对照目标准**：**超标**（4.47 秒 vs 1 秒）。
- **给落地票的接口**：要把它治到 ≤1 秒，先得能分解这 4.5 秒。给 `gh.exec` 补「发起来源」字段（第五节的边界一节里写明这是 #606 已裁决「等体检票量完再做」的两件事之一），或者给 `wf.probe` 加阶段计时。

### 第 4 名：客户端手动刷新一轮要 12~30 秒，而且期间有一大半时间不在等 `gh`

- **现象**：点一次刷新（`wf.refresh`）要 12~30 秒才回来。
- **根因**：**还没查到根因**。能说清的是：**这条链的耗时里有很大一部分不是花在等外部命令上**。
- **实测数字（真机日志）**：
  - `wf.refresh` 在快照范围里 **30 次**，耗时 **中位 15181 ms、p90 27200 ms、最大 29865 ms、最小 11865 ms**，单次耗时相加 567 秒。

  - 逐次分解（整条耗时 / 期间起了几条 `gh` / 这些 `gh` 自己的耗时合计）：见下表。
  - 也就是说：**「一条外部命令都没起的那几轮，照样花了 12~14 秒」**。
  - 同一条链上还有重复请求：09:36:13 与 09:36:14、09:26:22 与 09:26:23 各出现一次「同一秒内两次 `wf.refresh`」。

### 第 5 名：日志刷盘是「整份读回来 + 拼上 + 整份写回去」

- **现象**：写一行日志本身不慢，但落盘那一步每次都把整份当天日志读进内存、拼上新行、再整份写回磁盘。
- **根因**：`src/host/logStore.js:156-178` 的 `writeBatch`：
  - 第 174-175 行 `existing = await readTarget(target)` 把**整份文件**读进来；
  - 第 176 行 `writeTarget(target, String(existing || '') + text)` 把「全文 + 新行」**整份**写回去。
  - 底层文件服务没有追加原语，这是它被写成全文读改写的原因（代码注释里也写明了）。普通事件走 1000 毫秒防抖合并（`:116-124`），错误与告警当轮就写。
- **实测数字（本地可复现回路）**：照真机条件（文件撑到 2.4 MB、每行 137 字节）跑 30 次刷盘：

  | 指标 | 值 |
  |---|---|
  | 单次刷盘（全文读 + 全文写） | 中位 **11.71 ms**、p90 16.84 ms、最大 24.28 ms、最小 6.14 ms |
  | 拆开看 | 序列化/拼接的纯 CPU 部分约 0.00 ms（2.59 MB 字符串拼一行） |
  | 折算：一天 19999 行、若每行触发一次刷盘 | 读+写合计约 **68 GB**；按单次 11.7 ms 折算约 **6.5 分钟**墙钟（分散在一天里） |
- **真机佐证（真机日志）**：单行字节数中位 137、p90 145、p99 196、最大 299；一天 19999 行。
- **复现方式**：`node .scratch/607-logflush.mjs 2400000 30`。
- **对照目标准**：目标准里没有「日志落盘」这一项，所以**不能直接判超标**。判它是问题，依据是：① 它每天产生约 68 GB 的整份读写；② 单次 6~24 ms 的整份读写在事件循环上是可感知的（虽然是异步 I/O，但字符串拼接与 GC 压力落在主线程）；③ 它随当天文件增长而变慢，是**唯一一条会随「今天活动多一点」而变慢的路径**。
- **给落地票的接口**：这是「按天分文件」已经封顶之后剩下的结构性问题（代码注释里写明按天分文件就是为了把单次覆写体积封顶在一天之内）。要治得动「追加」，或者把一天再切小（按小时/按大小分片）。

### 第 6 名：工作区钥匙规整被反复调用（但代价极小，属于「量完裁决不必治」）

- **现象**：真机日志里快照范围内打了 **2464 行**「规整工作区钥匙」，其中 **946 次是同一毫秒里把同一个工作区重复规整**（同一毫秒内 2 次的时刻 997 个、3 次的 10 个、4 次的 6 个）。
- **根因**：`src/host/repoKeys.js:149-159` 的 `canonicalKey()` 每次调用都会 `await` 一遍平台层（`getPlatform()` 是惰性单例，命中之后是 `await` 一个已有 Promise）再走 `normalizeWorkspacePath` 的字符串规整。绝对路径在规整内部短路、零 `fs` 调用。**没有做结果缓存**，所以同一个工作区在同一毫秒被问三次就规整三次。
- **实测数字（本地可复现回路）**：`node .scratch/607-wskey.mjs`
  - 平台层已就绪时，规整一次 **0.0018 ms**（2000 次合计 3.6 ms）。
  - 结果**幂等**：同一份输入 200 次规整出 1 种结果。
  - 6 种写法都能归到同一把钥匙（`D:\x`、`D:\x\`、`d:\x`、`D:/x` → `d:\x`），这是这个函数存在的理由，要保住。

### 4.5 那条待验证的旧结论：宿主调用有没有被推迟（本票的定论）

旧结论是「`gh` 由同步子进程起、占住宿主事件循环」。票的验收条件要求至少有一条对它的结论。以下是本票的定论，分三块给出证据。

#### 4.5.1 结构事实：宿主这一层起进程是同步的，但同步段只有几毫秒

- DSH 宿主在 Windows 上起进程走的是自带原生绑定的 `CreateProcessW`
  （`resources/app.asar` 内 `node_modules/@deepseek-ai/dsh-win32-process/lib/index.js:614` 的 `spawnCurrentTokenJobProcess`）。**这是一个同步的 Win32 调用**，所以「起进程」这一步确实会占住调用它的那条线程。
- 但「起进程」与「命令跑多久」是两件事：子进程一旦起来就独立跑，宿主只是等它的 `exit` 事件，不占事件循环。
- 宿主起进程的写法是 `node:child_process` 的**异步** `spawn`，目标进程外面套一层 `runner.js`：入口在 `node_modules/@deepseek-ai/dsh-subprocess-local/lib/index.js:990` 的 `spawn(spec)`，真正启动在 `:493` 的 `launchWindowsJob(spec, targetEnv)`。`spawn` 同步返回 handle，启动、启动失败、退出都在 `child.on('spawn')` / `child.on('message')` / `child.on('close')` 回调里处理，**是回调式推迟调用，不是同步等结果**。

#### 4.5.2 实测：把真命令走一遍插件自己的 exec 接缝

本地可复现回路，`.scratch/607-probe-exec.mjs`。被量的对象是**真的** `src/host/platformChannel.js` 的 `detectionExec`（面板列表主取数、探测预检、取当前登录用户都走它），命令是真的 `gh`。

| 量什么 | 数字 |
|---|---|
| `subprocess.spawn` 的**同步段**（起进程这一次系统调用占事件循环的上限） | 冷启动一次 **6.62 ms**，随后 **3.57 / 2.64 ms** |
| `gh --version`（整条 46.5 ms）在途期间的事件循环漂移 | 最大 **11.08 ms** |
| `gh api rate_limit`（整条 709.4 ms）在途期间的事件循环漂移 | p50 10.75 ms、p99 11.62 ms、**最大 11.62 ms** |
| 同一进程**纯空转**对照 | p50 10.94 ms、p99 11.97 ms、**最大 12.10 ms** |

**关键读法**：命令在途期间的最大漂移（11.62 ms）**没有超过纯空转对照的最大漂移（12.10 ms）**。也就是说，一条命令跑 709 毫秒，事件循环的抖动跟什么都不干时一样。

#### 4.5.3 实测：「命令在途时宿主还能不能响应别的调用」

- **本机对照**（`.scratch/607-probe-exec.mjs` 第 3 组）：一边跑 `gh api rate_limit`（整条 914.9 ms），一边在宿主里干一件同步、纯内存的活并等它完成。期间 100 毫秒定点唤醒的实际漂移：中位 8.15 ms、p95 9.05 ms、**最大 9.05 ms**。漂移**没有出现「命令多长、漂移就多长」的量级**——命令在途期间事件循环仍在正常转。
- **阻塞对照**（同脚本第 4 组）：用 `spawnSync` 起一条 1.5 秒的命令，在它跑的那 1.5 秒里，50 毫秒的定时器**只醒了 0 次**。这才是「同步起进程占住事件循环」的样子。
- **25 条子进程连发对照**（`.scratch/607-probe-block.mjs`）：

  | 情形 | 事件循环最大漂移 | 对照 |
  |---|---|---|
  | 纯空转 3 秒 | 12.12 ms | 基准 |
  | 异步 `spawn` 连发 25 条（不等退出） | **12.72 ms** | 与基准同一档，没有恶化 |
  | 异步 `spawn` 25 条并等每条退出（整段 31.5 秒） | **12.35 ms** | 同上 |
  | 7 条 4 秒命令同时在途 | **12.14 ms** | 同上 |
  | 2 轮「2 条 6 秒命令在途」 | 12.60 ms | 同上 |
  | `spawnSync` 5 条（等退出，整段 6.3 秒） | **探针一个样本都没采到** | 事件循环整段被占住，定时器根本没机会跑 |

- **真机日志佐证**：全天日志行之间的时间空隙，中位 **799 ms**、p99 5017 ms、最大 83288 ms；**超过 10 秒的只有 1 个**（83.3 秒，跨在宿主重启的断点上，重启期间本来就没有进程在跑，且当时**在途 `gh.exec` 0 条**）。9.8 秒与 9.0 秒那两个最大的空隙，各自只有 1 条 `gh` 在途，跟那条命令自己的耗时同量级——**没有出现「多条命令在途就把日志断流很久」的形态**。
  - 这条证据的**读法要说清**：日志中位间隙约 799 ms 是「有活的时候日志自然会密」造成的，它**不是**「事件循环每 799 ms 才转一次」。这条证据能支持的结论只有一个：**没有出现与「一条命令在途时长」同量级的大断流**。

#### 4.5.4 结论

**这条旧结论在宿主这一半也站不住：宿主没有把调用推迟到命令跑完。**

- 宿主起进程那一步确实是同步的，但它只占 **3~7 毫秒**，不是那条命令的 7.8 秒。
- 命令在途期间，事件循环的抖动与纯空转无异；25 条子进程连发、7 条并发在途，都没有让漂移恶化。
- 与「真阻塞」的对照（`spawnSync`）在探针读数上差距是**数量级级别**的：真阻塞时探针一个样本都采不到。
- 另外一个结构性事实：**插件跑在 DSH Host 这个独立的节点宿主进程里**（Electron 的 `--type=utility --utility-sub-type=node.mojom.NodeService`，pid 31252；父进程是 Electron 主进程 pid 38516）。它**不是**渲染进程。所以即便宿主那一层真的卡住几毫秒，也不会直接卡住浏览器界面。

**那么为什么 `gh` 还是这么慢？** 因为它是**做了太多次**，不是**同步**。当前快照下全天 **1497 条**、单条耗时相加 **6372.6 秒（1.77 小时）**、「至少一条在途」**占全天跨度的 16.1%**，而其中绝大部分耗时归属到命名守护的定时轮次上（见第 1 名）。**要治的是次数与归属，不是把同步改成异步。**

一条诚实的边界：本节所有绝对毫秒都是**本机可复现回路与一次性对照实验**的数字，**不能当真机数字用**。可以搬的是两个结论：「宿主这一层起进程的同步段是毫秒量级」与「命令在途不阻塞事件循环」。

## 五、测点的边界与不可用之处

**这一节和上面的清单同等重要。** 后面所有落地票的「改前改后」对照都要靠这一节才读得对。以下每一条都不是猜测，是核到的代码事实或实测结论。

### 5.1 `gh.exec` 没有「发起来源」字段——最花时间的那条路归不了属

- **事实**：#606 新增的 `via` 字段只挂在 **`exec.run`**（经宿主 `ctx.exec` 起的那半边）上。**花时间最多的 `gh` 调用走的是另一条路 `runGh`，落的是常驻事件 `gh.exec`，它没有 `via`。**
- **最硬的一处**：`src/host/namingGuardian.js:113` 取整份索引用的就是 `runGh`。
- **后果**：本票查「三个扫描器各扫各的」时，**命名守护那条链用 `via` 归不了属**。本票用的替代办法是 `cwdHash` + 时间窗（借助每轮结束都会落的 `naming-persist` 行做锚点）做**推断**，并在清单里写明这是推断、不是直接归属。
- **已裁决**：给 `gh.exec` 补同样的字段是两行改动，但地图 #604 已拍板「等本票量完再做」——此刻插进去会在测量期间改变测点本身。本票照此未动。

### 5.2 有外部命令从头到尾不落任何日志行（**不要用「exec.run + gh.exec = 全部外部命令」这条等式算总量**）

- **`resolveGh()` 的 PATH 兜底探针**：`src/host/repoKeys.js:28-32` 会真的起一次 `gh --version`，它既不走 `detectionExec`（不落 `exec.run`），也不写 `gh.exec`（失败只写 `gh.resolve.fail`）。
  - **本票实测**：2026-09-11 与 2026-09-12 两份日志（新落点与旧落点各查一遍）里 **`gh.resolve.fail` 都是 0 行**，所以**这条路在观察到的两天里没有失败过**。这一点与「审查说昨天有 60 条」不一致，本票以自己的实测为准。
  - **但这不等于它可以忽略**：只要 `resolveExecutable('gh')` 失败一次、回退探针被走到，那条 `gh --version` 就**完全不会留下任何痕迹**。这是一个**盲区**，不是一个「已排除的路径」。
- **两条接缝在 `subprocess.spawn` 抛错时也落零行**（是「零行」，不是「一行带错误码」）：`platformChannel.js:196-198` 与 `repoKeys.js:104-113` 的 catch 分支直接返回/抛出，没走到落点。
- **「打开目录/文件」那一处**：`src/host/platform/index.js:133-144` 的 `spawnOpen` 会经 `subprocess.spawn` 调起系统打开器（win32 走 `cmd start`），**是 fire-and-forget、没有超时**（设计如此），而且它**不用 `exec.run` 这套字段记账**。
- **「安装更新」那一处**：`src/host/updateStore.js:282` 与 `src/host/updatePkg/store.js:308` 各自直连 `subprocess.spawn` 起安装流程，由另外的事件记账。
- **结论**：`exec.run` 行数 + `gh.exec` 行数 ≠ 全天外部命令总数。**本票清单里所有「全天外部命令」的数字都是只数 `gh.exec` 的口径**，已在第 1 节写明。

### 5.3 `click-to-painted` 在「点了但这次没渲染」时会无上界偏大

- **事实**：`panel.render` 的 `click-to-painted`（点击到画面出来，正对着地图那条 ≤300 毫秒的头号指标）在「点了面板但这一次没有发生渲染」时起点会一直挂着，被之后**任意一次无关渲染**消费，毫秒数可以差几个数量级，而且那一行还带着这次点击的 `mode` 取值，看起来像真的。
- **唯一线索**：同一批里没有配套的 `render-commit` / `render-paint`。
- **本票的取数判据**：读 `click-to-painted` 时**必须检查同批有没有 `render-commit` 与 `render-paint`**，没有就丢弃这一行。
- **本票丢弃了几条**：今天真机日志里 `panel.render` 共 **6 行、1 批**，那一批 **6 行齐全**（有 `render-commit` 也有 `render-paint`），因此**没有因为这条判据丢弃任何一行**。
- **已裁决**：给 `click-to-painted` 加守卫（本次没渲染就不发这一行）也是 #606 裁决「等本票量完再做」的第二件事。本票照此未动。

### 5.4 「开调试开关」本身会改变取证环境

- 调试开关当前是打开的（`log-switch.json` 内容 `{"enabled":true,"sampleRate":1}`）。**打开与关闭的日志量差别很大**：常驻事件一直在落，按需事件（`exec.run`、`panel.render`、`host.call` 的 debug 档、`workspaceKey.canonical` 等）只在打开时落。
- 后果：本条清单里所有「某事件多少行」的数字，都是**开关打开状态下**的数字。**开关关着时的实际落盘量与内存压力会小很多**。拿这些行数去推断「平时系统有多忙」是不对的——行数反映的是「记录了多少」，不是「干了多少活」。
- 判断办法：任何一条结论如果建立在「某事件行数」上，先问一句「这条事件在开关关着时还落不落」。

### 5.5 「改前基线」有时间断层：宿主进程在 #606 落地之后还没重启过

- **事实**：#606 的改动已经同步到已装插件目录（`profiles/desktop/node_modules/dsh-mattpocock-skills-deck` 的文件时间戳是 **2026-09-12 10:00:37**），但**宿主进程是 00:39:56 启动的，比这次同步早 9 个多小时**。宿主侧的插件代码要重启才生效。
- 后果：**真机日志里 `exec.run` 目前 0 行**，而且**不是**「这条测点不可用」，是「新代码还没被加载」。这一天里 `panel.render` 有 6 行（客户端包换页就生效，不吃重启），`exec.run` 0 行。
- **本票写的结论口径**：只能说「尚未观察到，因为宿主未重启」。**不许写「`exec.run` 真机不可用」。**

### 5.6 重启之后 `exec.run` 能不能落盘：核过开关链路，能

读代码核过一遍，结论是**能**，但**踩到过一处容易误判的地方**，写在这里：

- `src/host/platformChannel.js:187` 与 `repoKeys.js:102` 都靠 `logCtx.isEnabled('debug')` 决定要不要取时钟、要不要落行。
- `logCtx.isEnabled`（`src/host/index.js:74`）读的是宿主自己缓存的那个布尔 `logSwitchCache`，而它**只在 `fireLog` 执行时才被刷新**（`index.js:73`）。
- 所以：**宿主重启后，必须有「至少一行 info 档的常驻事件」先落过一次，`logSwitchCache` 才会变成 true，之后 `exec.run` 才会开始落行。**
- 真机上是满足的：客户端每 5 秒一次 `wf.namingPlan`，而 `namingGuardian.js:346` 给它的档位是 `debug`——**但 `host.call` 这个事件本身也有 info 档的落点**（`sessionLifecycle.js:60`、`workspaceData` 等同形写法），面板一打开就会有。所以第一行 info 落盘之后，链路就通了。
- **结论**：重启后 `exec.run` 会落盘，但**前几秒钟可能采不到**。取数时以「重启后第一行 info 之后」为起点。
