### 为什么 WSL 的错误很可能是固定名自己造成的

这是本次分诊最重要的新证据。

- 本机已装宿主 `@deepseek-ai/dsh-fs-local@0.2.1-rc.3` 的 `lib/index.js`：`:864` `async writeText(target, content, expected, signal)`；`:866` `const existing = await probe(target.targetKey)`；`:873` `await writeFileAtomic(target.targetKey, content, existing?.mode, signal, this.internals, ...)`；`:512` `async writeFileAtomic(absolutePath, content, mode, signal, internals = {}, createIfAbsent)`；`:536` `if (platform === "win32" && mode !== void 0) await copyFileDacl(absolutePath, tempPath)`；`:59` `async function readFileDaclWin32(path)`；`:64` `if (needed[0] === 0) throw win32Error("GetFileSecurityW", api.getLastError(), path)`。
- 也就是说：**只有目标文件已经存在（`existing?.mode` 有值）才会走 `copyFileDacl`，才会调用 `GetFileSecurityW`；新建文件跳过 DACL 复制，走临时文件 + rename 发布。** 作者看到的错误原文是「GetFileSecurityW EIO (Win32 1)」，这恰好说明写探针时 `.scratch/.dsh-write-probe`（或仓库根的同名文件）已经存在。
- 固定名探针因此不只是「可能覆盖用户文件」：它还会让 WSL 上「替换既存文件」这条 DACL 路径被触发，把探测误判成不可写。若改成随机唯一名，第一次探测是新建文件，不会走 `GetFileSecurityW`；大概率能在 WSL 上真实测出可写（本机没有 WSL 发行版，无法复现，必须由作者在 WSL 上验证）。
- Microsoft 文档：`ERROR_INVALID_FUNCTION = 1` 的文案是「Incorrect function.」，`ERROR_ACCESS_DENIED = 5` 才是「Access is denied.」；`GetFileSecurityW` 失败时返回 0，需要读 DACL 时要求 `READ_CONTROL` 或调用者是 owner。9P 共享对 `GetFileSecurityW` 返回「功能不正确」，这是「这个操作不支持」，不是「目录没有写权限」——把它判成 `pending`「未验证」比判成 `fail`「不可写」准确；但这只支持「窄分类」，不支持「全平台删除探测」。
- 外部二手材料也指向同一方向：`dsh-plugin.org/zh/tutorials/fix-wsl-unc-workspace-eio`（2026-10-20）说编辑已存在文件会报 `GetFileSecurityW EIO (Win32 1)`，新建文件走另一条 hardlink 路径；GitHub 上 `Big-Dao/dsh-plugin-wsl-env` 的 `docs/root-fs-routing.md` 也描述 UNC 9P 写会撞 `GetFileSecurityW` / `ReplaceFileW` / 硬链接。这两份材料没有版本与复现细节，只作旁证，不作为裁决依据。
