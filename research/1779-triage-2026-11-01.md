## 根因链

1. **预检第 2 步问错了问题。** `preflight.ts:75-95` 的第 2 步是「登录了没有」，它执行裸 `glab auth status`（`:81`），把「glab 认为所有已配置主机都健康」当成「当前仓库主机已登录」；只要退出码非零或输出命中 `/not logged in|no token|unauthenticated|401|403/i`（`:82-84`，stdout 与 stderr 合并后判断），就返回 AUTH 并**立即早退**（`:86`）。它问的是一条与房间实际操作不同的命令：房间所有读写都是 `glab api …`，`auth status` 是另一套多主机聚合语义。
2. **能回答真正问题的第 3 步永远不跑。** `:97-132` 的第 3 步是仓库作用域探活 `glab api projects/<refId>`（`:110-113`），它成功就说明当前仓库主机的 token 可用、仓库可达——这正是用户关心的事实。但第 2 步一失败就 return，第 3 步没有机会执行。
3. **glab 的语义决定了第 2 步不是仓库作用域的。** 1.41–1.78 的 `auth status` 遍历全部已配置主机、任意一台失败整体非零；1.79 起虽然会按上下文主机收窄，但仓库主机恰为 gitlab.com（或 glab 解析不出仓库主机）时，`hostname` 保持为空、仍回落到「检查全部」（glab 源码注释自称 backward compatible）。版本细节见下一节。
4. **链上把 coarse 的 AUTH 判成红牌并给错引导。** `chain-env-map.ts:259-270` 的 `glabAuthVerdict` 对 `kind: 'auth'` 直接判 fail，文案是「glab 登录状态已失效（重新执行 glab auth login）」；GitLab 房没有 GitHub 房 #916 那样的自证核对（`github/read/preflight.ts:184-196`），所以这个错误分类原样传到界面。
5. **同源的第二类误判。** 第 2 步的 catch（`:88-95`）把超时、进程起不来等网络/环境失败也一律判成 AUTH；链上靠 `looksLikeTransportFailure`（`chain-env-map.ts:225-228`）的正则兜底把它们降成 pending，这是「碰巧对」，不是分类正确。#916 的注释（`github/read/preflight.ts:105-120`）记的正是同一件事：`auth status` 会把「连不上」写成「token 无效」。

## glab 一手事实与版本分界

以下都核对过 glab 源码与官方文档，URL 见文末。

- **1.14.0–1.40.0**：`commands/auth/status/status.go` 逐台打印，失败只打印文本（如「x <host>: api call failed: 401 Unauthorized」「x No token provided」），命令自身最后仍 `return nil`（v1.40.0 的 `:147`），退出码是 0。但插件把 stdout 与 stderr 合并后跑正则（`preflight.ts:82-84`），这些失败文本照样命中 `no token`/`401`，所以**这些版本也可能误判**（按源码推断，没有逐版本真机复核）。
- **1.41.0–1.78.0**：引入 `failedAuth` 汇总（v1.41.0 的 `:81`、`:153`），任意一台已检查主机失败即整体非零；仍遍历全部已配置主机。
- **1.79.0 起**：`auth status` 增加了按上下文主机收窄的逻辑（v1.79.0 的 `:85-92`）：`--hostname` 优先，其次是 `--all`，否则用 `defaultHostname`（来自 `GITLAB_HOST` 或 git remote）；**只有 `defaultHostname` 不等于 gitlab.com 时才把 hostname 设成它，否则保持空、仍检查全部主机**（源码注释自称 backward compatible）。所以自建主机仓库在 1.123.0 上只查当前主机（实测），gitlab.com 仓库或认不出仓库主机时仍全查（夹具 B 实测）。
- **`--hostname` 的历史**：从 v1.14.0 就有（`commands/auth/status/status.go:47`）；v1.68.0 与 v1.123.0 都接受 `host:port`（实测）；主机不在配置里时命令会报「X has not been authenticated with glab」并退出 1（实测）。
- **`glab api` 的主机选择**：官方文档说「在 git 目录里用当前目录对应的已认证主机，否则用 gitlab.com」；源码（v1.68.0 `internal/commands/api/api.go:491-504`）是先看 `--hostname`，否则用 `baseRepo` 的 `RepoHost()`。注意 `glab api --hostname` **不接受端口**（1.68.0 与 1.123.0 实测报 invalid hostname），所以「用 `api --hostname` 显式指定主机」这条路对带端口的自建实例不可用；`auth status --hostname` 可以。
- **版本日期**：v1.68.0 发布于 2025-09-04（报票人版本）；v1.79.0 发布于 2025-12-05（commit 3f08782「feat: support GITLAB_HOST in auth status」）；v1.123.0 发布于 2026-10-13（本机版本）。`--all` 从 1.79.0 起有，`--all --output json` 从 1.122.0 起有，但任一主机失败时整体仍退出 1。
- **官方文档原句**（https://docs.gitlab.com/cli/auth/status/）：「By default, this command checks the authentication state of the GitLab instance determined by your current context (git remote, GITLAB_HOST environment variable, or configuration). To check all configured instances, use `--all`. To check a specific instance, use `--hostname`.」

## 修法候选与真实 glab 实测矩阵

读法与结论：

- **P4 修好了所有假 AUTH 场景**：多主机里无关主机失效、缺 token、hang，P4 都判 ok；1.68.0 与 1.123.0 一致。原因是它问的 `glab api user` 只走当前上下文主机，不聚合其它主机。
- **P4 没有把真失败放过去**：当前 token 失效、当前没有 token、断网、仓库 404 四种真失败，P4 的结论与今天逐条一致（fail/auth、fail/auth、fail/auth→链上 pending、authed pass / repo fail）。
- **P4 把等待时间降下来了**：无关主机 hang 8 秒时，现行 8.2 秒、P1 8.6 秒、P4 0.4 秒；断网时现行 12.5 秒、P1 12.2 秒、P4 0.16 秒。成功路径调用次数不变（两次：登录 + 仓库探活），失败路径一次。
- **P1 也修正确性，但保留了等待**：它先跑 `auth status`，hang 与断网要等完才核对，所以最坏情况仍是 8–12 秒。
- **PA 在两个真实场景里更差**：仓库主机没配进 glab 时把今天能用的仓库判死；remote 带端口而配置键不带端口时，它的错误原文不含网络词，链上从 pending 变成红牌。原因是主机名必须与配置键逐字一致，端口、别名、大小写都会让它对不上。
- **PAB 把 PA 的误判救回来，但仍要先付 `auth status` 的等待**。

夹具隔离失败、不作为依据的场景：`168-no-config`、`123-no-config`（没有配置时 glab 回落到真实 gitlab.com，被真实网络的 401/429/超时污染）、`168-host-mismatch`、`168-no-repo`（同样回落到真实 gitlab.com）、`123-single-no-token-real`（glab 从本机 Windows 凭据库读到了真实 token）。这些只说明「glab 的主机解析失败时会静默回落到默认主机」，不能用来比较候选优劣。

**自证端点为什么必须是 `glab api user`，而不是项目探活**：同一夹具里，当前主机没有 token、仓库是公开项目时，`glab api projects/<refId>` 会匿名成功（退出码 0），而 `glab api user` 返回 401。拿项目探活当登录判据会把「没登录」判成「已登录」。这也说明第 3 步的探活不能替代第 2 步：它回答的是「仓库能不能读」，不是「登录有效吗」。

P4 的残余限制（诚实列出，本票不修）：

1. **仓库主机没配进 glab 时**，`glab api` 可能静默用默认主机（1.123.0 实测：仓库主机 gitlab.example.org 未配置，`api user` 打到 gitlab.com 并成功），P4 与今天一样识别不出来。要根治得把主机显式传给 glab（PA 的方向），但那会带来上面两个更糟的误判，超出本票范围。
2. **glab 1.68.0 + 带端口自建仓库**：glab 解析仓库主机时丢掉端口，`repo view` 失败、`glab api` 回落到 gitlab.com；这种组合下房间本来就所有 API 操作都不可用（glab 旧版限制），P4 会判 auth 失败，文案不够准，但不是本票要修的东西。
3. **失败文案变了**：第 2 步失败时交给链上的是 `glab api user` 的原文（例如 `401 Unauthorized`），不再是 `auth status` 的多主机汇总。链上分类口径不变（kind=auth → fail，网络原文 → pending），只是原文更短、更贴近当前主机。

## 建议的修法形状：首选 P4（第 2 步换成 `glab api user`）

改动只在 `src/tracker/rooms/gitlab/preflight.ts` 第 2 步（`:75-95`）：

1. 把 `exec('glab', ['auth','status'], …)` 换成 `exec('glab', ['api','user'], …)`，超时仍用 `GITLAB_PROBE_TIMEOUT_MS`。
2. 退出码非 0 即 `return fail(AUTH, 原文, 原文)`；抛异常同样回 AUTH（与今天一致）。
3. 删掉输出正则（`:84` 的 `/not logged in|no token|…/`）：`glab api user` 成功就说明当前主机 token 可用，失败由退出码表达，不需要再从原文猜。
4. 第 3 步（`:97-132`）与文件头的三步约定保持不动，只把文件头注释里第 2 步的说明从「glab auth status」改成「glab api user」。

为什么这是第一性原理的答案：**预检应该探测房间真正依赖的那条能力。** GitLab 房间的所有读写都是 `glab api …`（`src/tracker/rooms/gitlab/client.ts:109-119`），主机解析、token 选择、错误分类都走这一条路；`glab auth status` 是另一套语义（多主机聚合、随版本变、1.79 起才有上下文收窄），拿它当代理判据既会误伤（本票），也会误报（把网络失败写成凭据失效）。`glab api user` 与第 3 步的 `glab api projects/<id>` 是同一条命令类的两个问题——「我是谁」与「这个仓库我能读吗」——正好对应界面上「已登录」与「仓库可达」两行。

`glab api user` 在这个房间里不是新东西：取当前登录用户本来就跑它（`src/tracker/rooms/gitlab/identity-ops.ts:192`、`src/tracker/rooms/gitlab/init-project.ts:255`），没有新增依赖面。

与 GitHub 房 #916 的关系：同一课——`auth status` 会骗人，要用一次 API 调用核对。P4 把它推到底：既然 API 调用是权威判据，就直接问它，不必先问那个会骗人的。GitHub 房保留 `gh auth status` 作主判据有它的理由（#916 场景四：auth status 本地超时时要少问一次接口；GitHub 也没有多主机聚合语义），这两条理由在 GitLab 这边都不成立。

成本：成功路径两次调用（与今天相同）；真失败一次；假失败一次（P1 要两到三次）。矩阵里 hang 与断网场景的耗时从 8–12 秒降到 0.2–0.4 秒。

备选（都在矩阵里量过）：

- **P1 自证（最小改动）**：保留 `auth status` 作主判据，失败后用 `glab api user` 核对。正确性与 P4 相同，但 hang/断网仍要等 8–12 秒，且多一条命令的维护成本。
- **PA 收窄**：需要先补主机传递管线，而且在「仓库主机没配进 glab」「remote 带端口」两个场景里比今天更差。
- **PAB**：PA 的误判能靠自证救回，但仍付 `auth status` 的等待。
- **wontfix**：写 `.out-of-scope/1779-gitlab-preflight-multi-host.md`。

### 回归门禁

推荐扩展 `tests/verify-1187-gitlab-chain-predicates.ts`（不新建文件，就不用登记 `tests/gate-map.json`）。P4 下这扇门要改的地方：

- **④（装了没登录）**：夹具从「`auth status` 返回 not logged in、其余命令一律 0」改成「`glab api user` 返回 401」；断言登录行 fail、仓库行 pending 不变。
- **⑥（网络超时）**：夹具从「`auth status` 抛 timeout、其余命令 0」改成「`glab api user` 抛 timeout」；断言两行 pending 不变。
- **⑦（全过）**：调用次数仍是 2，但第一次从 `auth status` 变成 `api user`；`:308` 断言第二次仍是 `api projects/group%2Fproj`，`:306` 的次数不变。

## 对抗式复核

我尝试推翻过六个说法（前四条针对「问题是否成立」，后两条针对「推荐修法是否安全」）：

1. **「这只是老版本 glab 的问题，最新版已经好了。」** 不成立。1.79.0 起自建主机仓库确实收窄了（1.123.0 实测只查当前主机），但仓库主机是 gitlab.com（最常见的部署）或 glab 认不出仓库主机时仍回落到全查；夹具 B 用 1.123.0 实测复现了完整误判链（裸 status 退出 1、真实 preflight 返回 auth 失败、同环境探活成功）。
2. **「`auth status` 在 git 目录里本来就只看当前仓库主机，所以不是 bug。」** 不成立。官方文档与源码都写的是「按上下文」而不是「按仓库」；1.41–1.78 明确遍历全部；1.79 起的收窄条件里 gitlab.com 是例外。
3. **「主机拿不到，没法修。」** 不成立。`RepositoryRef.host` 已有（#435），`repo.ts` 进程缓存也有 `gitlabOriginOf(cwd)`；缺的是把主机交给 glab（或者干脆用不依赖主机的 `glab api user`）。
4. **「这会把所有 GitLab 操作都卡住，很严重。」** 不成立。没有任何硬闸：链上是一行红牌 + 一行 pending + 一条 deck_context note；真正的读写仍然执行。严重性在于误导（让人以为要重新登录，可能去动 token/配置），而不是中断。
5. **「`glab api user` 会不会把没登录判成已登录？」** 不会。`/user` 永远要求认证，实测当前主机没有 token 时返回 401；项目探活才会匿名成功。矩阵里「当前没有 token」场景五个候选全部 fail/auth，P4 没有例外。
6. **「换掉 `auth status` 会不会丢掉有用信息，或者让真失败变绿？」** 丢掉的只有「本机没有 token」这种本地检查，真实 GitLab 上 `api user` 会 401 覆盖它；多主机汇总信息对当前仓库没用，反而是病根。矩阵里当前 token 失效、当前没有 token、断网、404 四类真失败，P4 与今天逐条一致；成功路径调用次数也没变。

反例维度（什么情况下不复现）：只配了一台主机；无关主机健康；`auth status` 输出里没有失败文本；或者仓库认不出（此时 `deck_context` 路径仍可能误判，但只影响一条 note）。这些反例都不覆盖夹具 A/B 与矩阵里的多主机场景，所以不改变结论。

**test-the-test（反查门禁为什么会放行）**：`verify-1187` 的 ④/⑥ 夹具把「`auth status` 失败即终局」写成了期望，所以只要实现保持早退，门禁就是绿的；新场景缺失，多主机误判在门禁里根本不存在。P4 实施时这两节要跟着换判据改夹具语义（见「回归门禁」），否则会按旧命令的期望变红——这不是回归，而是旧夹具写错了语义。这条要在 Agent Brief 里写清楚，避免实施者用改断言的方式「修绿」。
