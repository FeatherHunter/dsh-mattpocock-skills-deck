## 根因链

1. **预检第 2 步问错了问题。** `preflight.ts:75-95` 的第 2 步是「登录了没有」，它执行裸 `glab auth status`（`:81`），把「glab 认为所有已配置主机都健康」当成「当前仓库主机已登录」；只要退出码非零或输出命中 `/not logged in|no token|unauthenticated|401|403/i`（`:82-84`，stdout 与 stderr 合并后判断），就返回 AUTH 并**立即早退**（`:86`）。
2. **能回答真正问题的第 3 步永远不跑。** `:97-132` 的第 3 步是仓库作用域探活 `glab api projects/<refId>`（`:110-113`），它成功就说明当前仓库主机的 token 可用、仓库可达——这正是用户关心的事实。但第 2 步一失败就 return，第 3 步没有机会执行。
3. **glab 的语义决定了第 2 步不是仓库作用域的。** 1.41–1.78 的 `auth status` 遍历全部已配置主机、任意一台失败整体非零；1.79 起虽然会按上下文主机收窄，但仓库主机恰为 gitlab.com（或 glab 解析不出仓库主机）时，`hostname` 保持为空、仍回落到「检查全部」（glab 源码注释自称 backward compatible）。版本细节见下一节。
4. **链上把 coarse 的 AUTH 判成红牌并给错引导。** `chain-env-map.ts:259-270` 的 `glabAuthVerdict` 对 `kind: 'auth'` 直接判 fail，文案是「glab 登录状态已失效（重新执行 glab auth login）」；GitLab 房没有 GitHub 房 #916 那样的自证核对（`github/read/preflight.ts:184-196`），所以这个错误分类原样传到界面。
5. **同源的第二类误判。** 第 2 步的 catch（`:88-95`）把超时、进程起不来等网络/环境失败也一律判成 AUTH；链上靠 `looksLikeTransportFailure`（`chain-env-map.ts:225-228`）的正则兜底把它们降成 pending，这是「碰巧对」，不是分类正确。#916 的注释（`github/read/preflight.ts:105-120`）记的正是同一件事：`auth status` 会把「连不上」写成「token 无效」。

## glab 一手事实与版本分界

以下都核对过 glab 源码与官方文档，URL 见文末。

- **1.14.0–1.40.0**：`commands/auth/status/status.go` 逐台打印，失败只打印文本（如「x <host>: api call failed: 401 Unauthorized」「x No token provided」），命令自身最后仍 `return nil`（v1.40.0 的 `:147`），退出码是 0。但插件把 stdout 与 stderr 合并后跑正则（`preflight.ts:82-84`），这些失败文本照样命中 `no token`/`401`，所以**这些版本也可能误判**（按源码推断，没有逐版本真机复核）。
- **1.41.0–1.78.0**：引入 `failedAuth` 汇总（v1.41.0 的 `:81`、`:153`），任意一台已检查主机失败即整体非零；仍遍历全部已配置主机。
- **1.79.0 起**：`auth status` 增加了按上下文主机收窄的逻辑（v1.79.0 的 `:85-92`）：`--hostname` 优先，其次是 `--all`，否则用 `defaultHostname`（来自 `GITLAB_HOST` 或 git remote）；**只有 `defaultHostname` 不等于 gitlab.com 时才把 hostname 设成它，否则保持空、仍检查全部主机**（源码注释自称 backward compatible）。所以自建主机仓库在 1.123.0 上只查当前主机（实测），gitlab.com 仓库或认不出仓库主机时仍全查（夹具 B 实测）。
- **`--hostname` 的历史**：从 v1.14.0 就有（`commands/auth/status/status.go:47`）；v1.68.0 与 v1.123.0 都接受 `host:port`（实测）；主机不在配置里时命令会报「X has not been authenticated with glab」并退出 1（实测）。
- **`glab api` 的主机选择**：官方文档说「在 git 目录里用当前目录对应的已认证主机，否则用 gitlab.com」；源码（v1.68.0 `internal/commands/api/api.go:491-504`）是先看 `--hostname`，否则用 `baseRepo` 的 `RepoHost()`。注意 `glab api --hostname` **不接受端口**（1.68.0 与 1.123.0 实测报 invalid hostname），所以「用 `api --hostname` 显式指定主机」这条路对带端口的自建实例不可用；`auth status --hostname` 可以。
- **版本日期**：v1.68.0 发布于 2025-09-04（报票人版本）；v1.79.0 发布于 2025-12-05（commit 3f08782「feat: support GITLAB_HOST in auth status」）；v1.123.0 发布于 2026-10-13（本机版本）。`--all` 从 1.79.0 起有，`--all --output json` 从 1.122.0 起有，但任一主机失败时整体仍退出 1。
- **官方文档原句**（https://docs.gitlab.com/cli/auth/status/）：「By default, this command checks the authentication state of the GitLab instance determined by your current context (git remote, GITLAB_HOST environment variable, or configuration). To check all configured instances, use `--all`. To check a specific instance, use `--hostname`.」

## 建议的修法形状

### 首选 B：照 GitHub 房 #916 的做法，用仓库作用域探活作权威判据

改动落在 `src/tracker/rooms/gitlab/preflight.ts` 的第 2、3 步之间：

1. 第 2 步 `auth status` 判失败（退出码非零或输出命中正则）时**不立即 return**。
2. 若 `probeId` 存在（链上路径总是有 refId），继续执行第 3 步 `glab api projects/<encoded>`：
   - 探活成功 → 说明当前仓库主机的 token 可用、仓库可达，`return { ok: true }`；
   - 探活失败 → 交出**探活那一份**错误并按现有口径分类：401/403/unauthorized/forbidden/no token/not logged in → AUTH；404/not found → NOTFOUND；其余 → NETWORK（`:115-124` 已有这套分类，可直接复用）。
3. 若 `probeId` 不存在（`deck_context` 那条路径），维持现状（判 AUTH 并返回），因为手上没有能证明「当前仓库主机可用」的权威检查。

与 GitHub 房对照：`github/read/preflight.ts:184-196` 就是「`auth status` 失败且错误是 AUTH 时，跑 `gh api user` 自证；成功就继续，失败就交出核对那份 error」；`crosscheckGhAuth` 在 `:121-123`。GitLab 这边更简单：核对就是已有的第 3 步，不需要新增命令。

成本与收益：

- 成功路径调用次数不变（今天成功也是 `auth status` + 探活两次）；只有「`auth status` 失败」的路径会多跑一次探活，单次上限是中央配置的 `gitlabProbeMs` 15 秒，实际真失败（401/403/404）通常很快返回。
- 同时修掉「网络/超时被写成认证失败」这类同源误判：探活抛错或不可达时按 NETWORK 返回，链上 `glabAuthVerdict` 会把它降成 pending（`chain-env-map.ts:259-270` 对 `kind: network` 或 transport 文本给 pending），不再误导用户去重新登录。
- 不依赖 glab 版本：不用判断 1.79 分界，也不用维护「哪些版本会全查」的清单。

### 备选 A：给 `auth status` 加 `--hostname <仓库主机>`

- 可行：`--hostname` 从 1.14.0 起就有，接受 `host:port`（实测）；能直接修掉多主机误判，且不依赖 refId。
- 代价：需要先拿到主机并传给 preflight。主机来源有两处：`RepositoryRef.host`（#435 已有，但链上 `ChainRepoHandle` 目前只带 `cwd/backend/refId`，没带 host）或 `gitlabOriginOf(cwd)`（`repo.ts:182`；链路径里 `getRepoKey` 在 preflight 之前跑过，缓存是热的；`deck_context` 路径可能没跑过，缓存可能是冷的）。取到的是 `scheme://host[:port]` 形式，还要去掉 scheme 再交给 `--hostname`。
- 局限：只修多主机误判，不修「网络失败被写成认证失败」；主机拿不到时仍回落到裸调，误判仍在。因此不建议单独做，可作为 B 之后的硬化（B 修好后，A 的边际收益主要是让错误文案更贴近当前主机）。

### 备选 B2（只作为记录）：有 refId 时直接跳过 `auth status`

第一性原理上最干净——既然仓库作用域探活是权威判据，有 refId 时第 2 步本来就不必要，可以直接探活；没有 refId 时才问 `auth status`。但这会改动文件头声明的「三步探活」契约（`preflight.ts:1-16`、`chain-env-map.ts:354-372` 的调用形状）、界面文案与更多门禁夹具，超出本票范围，不建议这次做。

### 回归门禁

推荐扩展 `tests/verify-1187-gitlab-chain-predicates.ts`（不新建文件，就不用登记 `tests/gate-map.json`）：

- 新增场景「无关主机失败 + 当前仓库探活成功 → 两行全绿」：execHandler 让 `auth status` 返回 `{code:1, stderr: 含「could not authenticate to one or more」+ 当前主机成功文本}`，让 `api projects/group%2Fproj` 返回 0；断言 `glab:authed` 与 `glab:repoAccess` 都 pass、`exec.calls` 里确实有 `api projects/group%2Fproj` 这一次。
- 改 ④ 的夹具语义：现在它让 `auth status` 返回 `not logged in`、其余命令一律返回 0，于是探活会成功、断言却要求失败——这正好是「旧行为」的期望。修法 B 后应改成「探活也返回 401」，才代表真的未登录；仍断言登录行 fail、仓库行 pending。
- 改 ⑥ 的夹具语义：现在它让 `auth status` 抛超时、其余命令返回 0（探活会成功），断言却要求 pending。修法 B 后应改成「探活也抛超时/返回网络错误」，才代表真的连不上；仍断言两行 pending、不许出现红牌。
- ⑦ 的调用次数断言（`:306` 两次、`:308` 第二次是 `api projects/group%2Fproj`）在 B 下仍然成立，不用改；⑧（没有 refId 时只跑一次 `auth status`）也不变。

## 对抗式复核

我尝试推翻过四个可能让本票不成立的说法：

1. **「这只是老版本 glab 的问题，最新版已经好了。」** 不成立。1.79.0 起自建主机仓库确实收窄了（1.123.0 实测只查当前主机），但仓库主机是 gitlab.com（最常见的部署）或 glab 认不出仓库主机时仍回落到全查；夹具 B 用 1.123.0 实测复现了完整误判链（裸 status 退出 1、真实 preflight 返回 auth 失败、同环境探活成功）。
2. **「`auth status` 在 git 目录里本来就只看当前仓库主机，所以不是 bug。」** 不成立。官方文档与源码都写的是「按上下文」而不是「按仓库」；1.41–1.78 明确遍历全部；1.79 起的收窄条件里 gitlab.com 是例外。
3. **「主机拿不到，没法修。」** 不成立。`RepositoryRef.host` 已有（#435），`repo.ts` 进程缓存也有 `gitlabOriginOf(cwd)`；缺的是把主机交给 glab（或者干脆用不依赖主机的仓库作用域探活）。
4. **「这会把所有 GitLab 操作都卡住，很严重。」** 不成立。没有任何硬闸：链上是一行红牌 + 一行 pending + 一条 deck_context note；真正的读写仍然执行。严重性在于误导（让人以为要重新登录，可能去动 token/配置），而不是中断。

反例维度（什么情况下不复现）：只配了一台主机；无关主机健康；`auth status` 输出里没有失败文本；或者仓库认不出（此时 `deck_context` 路径仍可能误判，但只影响一条 note）。这些反例都不覆盖夹具 A/B 的场景，所以不改变结论。

**test-the-test（反查门禁为什么会放行）**：`verify-1187` 的 ④/⑥ 夹具把「`auth status` 失败即终局」写成了期望，所以只要实现保持早退，门禁就是绿的；新场景缺失，多主机误判在门禁里根本不存在。修法 B 实施时，如果只加新场景、不改 ④/⑥，这两节会因为探活成功而变红——这不是回归，而是旧夹具写错了语义。这条要在 Agent Brief 里写清楚，避免实施者用改断言的方式「修绿」。
