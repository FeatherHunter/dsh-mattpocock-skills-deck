# #1926 分诊：切换会话时整列闪黄，以及「上次已知／只读显示」两句

> 本文件由 AI 在分诊 #1926 期间写成。分诊只查清问题、判断分流，不改业务代码，也没有实施修复。行号与结论以 HEAD `00e1a53f`（2026-11-06）为准；本机安装的插件是 `1.9.0-beta.34`（2026-11-05 04:41 构建），与 main 在这几处同形。

## 一句话结论

整列闪黄成立，是两条独立缺陷叠加：同一张票的 `updatedAt` 有两种 ISO 写法（在线秒级、库回放毫秒级），而差异判据按原始字符串比；再加上闪烁标记按会话各存一份、清除计时器全局只有一个，除被计时器捕获的那一份外，其余会话的标记不会被清。用本机快照库真实 911 行复算，仅换写法就让 `diffSnapshots` 把 911 行全判成变了。「上次已知／只读显示」两句的事实没错，但把本机快照库的单写者写锁说成了「面板只读」，产品层面是错的；它和闪黄是两个互不相干的根因，都要改。

## 一、闪黄成因一：两种时间写法撞上原始字符串比较

**两条来源给同一张票的 `updatedAt` 不同。** 在线取数把后端原样的秒级 ISO 交上来，例如 `2026-08-24T01:33:13Z`（真实样本 `tests/tracker-contract/fixtures/github-real/normalized-list.json:10`；GitHub 的列表行原样透传，`src/tracker/rooms/github/model/normalize.ts:280`）。本机快照库回放把毫秒数转成 ISO，例如 `2026-08-24T01:33:13.000Z`（`src/refresh/rooms/host/snapshot-view-projection.ts:57-59` 的 `isoOf`，`:82` 用它填 `updatedAt`）。

**差异判据按原始字符串比。** `diffSnapshots` 对地图子票与顶层票都写 `String(a.updatedAt || '') !== String(b.updatedAt || '')`（`src/refresh/rooms/client/snapshot-sync-helpers.ts:82`、`:96`）。同一时刻的同一张票因此被逐行判成「变了」。

**两条来源会在同一个工作区里交替。** GitHub 的 `wf.snapshot` 在库里有回放且不是强制刷新时，直接交付库回放（`src/refresh/rooms/host/session-snapshot-cache.ts:389` 读库、`:400` 选回放，在线组装是同一行冒号后的另一支）；`wf.refresh` 一律走在线组装（`src/refresh/rooms/host/session-refresh-schedule.ts:208`），库空首屏也走在线组装并写库。版本推进时（另一个窗口在写、或这一趟刷新确实写了库）差异就会出现；版本相同会被 `diffSnapshots` 的短路挡掉。

**复现数字。** 用仓里 `diffSnapshots` 真源 + 本机真实 911 行，构造两份内容完全相同、只有时间写法不同的快照：`online(秒级) -> 回放(毫秒级)` 得到 `changed = 911, added = 0, removed = 0`；`online -> online` 与 `replay -> replay`（只换版本）都是 `changed = 0`。

## 二、闪黄成因二：全局清除计时器与每会话一份的闪烁标记

**闪烁标记按会话各一份，清除计时器全局只有一个。** `scheduleFlashClear` 用模块级 `_flashClearPending` 保证「一次只排一个 timer」（`src/refresh/rooms/client/snapshot-sync-helpers.ts:102-116`；停留时长 2600ms 见 `config/ttl.yaml:112`）。第一个调用者把旗子置真后，2.6 秒内其它会话的调用直接返回，那一份 `rowFlash` 再没人清。

**手动刷新的同工作区扇出正好会踩到它。** `refreshAll` 对 group 里每个会话先算差异、写 `st2.rowFlash`，再逐个调 `scheduleFlashClear(st2)`（`src/refresh/rooms/client/refresh-timer.ts:404-424`，清除在 `:421`）。扇出期间全局只可能有一个计时器在跑，它只清它捕获的那一份（通常是发起刷新的当前会话），其余会话的标记要等各自下一次安装才被清。

**复现。** 把 `timer.timeout` 换成记录回调，对两个会话依次调 `scheduleFlashClear`：只排上 1 个计时器（2600ms）；回调触发后 A 的 `rowFlash` 清空、B 仍留 2 条。之后切到 B 会话，`ListTabRow` 会按 `st.rowFlash` 给这些行挂 `.dsws-row-changed`（`src/client/views/ListTabRow.ts:316`），动画定义在 `src/client/kernel/styles.ts:304-307`；切走再切回、类名再挂一次，又跑一次。

**这一条与成因一的关系。** 成因二单独就能解释「来回切换时每次都闪」——只要那份标记还留着；成因一把它从「少数行」放大成「整列」。两条都要满足验收第 1 条（来回切 5 次不整列闪）。

## 三、「上次已知／只读显示」两句：事实成立，但「只读」的说法在产品层面是错的

- **来源**：`truthNoticeLines` 按顺序往列表上方那一行拼句子；`truth.replayLastKnown` 在快照带 `diskReplay.lastKnownAtMs` 时出现（`src/client/views/shared/truthLines.ts:292-296`），`truth.snapshotReadonly` 在开库诊断有 `lease-held-readonly` 时出现（同文件 `:297-311`）。词条在 `config/copy/pages.yaml:39`、`:43`（英文在 `:131`、`:135`）。
- **事实**：快照库对同一工作区只允许一个进程写；抢不到写租约的进程用只读方式打开这个文件（`src/workspace-snapshot/runtime/lease.ts:1-8`；`src/workspace-snapshot/runtime/open.ts:143` 与 `:317` 给出 `lease-held-readonly`）。这把锁按进程算，不是按会话算——同一个窗口里的所有会话共用它。
- **它不限制什么**：右侧面板的操作、AI 工具调用、对 GitHub 后端的写操作都不受这把锁影响。报告人的原话是「我们所有会话的右侧面板都不是只读的，都是当前AI调用工具可以修改的」；这一点成立，所以「这里以只读显示」在产品层面是错的。
- **真实后果**：没拿到写锁的进程，写回执落库会回 `readonly`（`src/refresh/rooms/host/snapshot-library.ts:431-448`），`write-event-fetch` 这一趟因此补不进快照（`src/refresh/rooms/host/thin-row-fetch.ts:170-180`）；这个窗口的面板可能要到写锁持有者下一次写库才看到刚改的那一行。手动刷新仍能把后端的新数据交给界面，但不会落库（`src/refresh/rooms/host/session-refresh-schedule.ts:150-165` 把 readonly 当已知降级，不按失败处理）。同一次运行里多数时候不是退回，是没更新；重启或新窗口第一次读库时才会看到旧的（客户端带库版本时 `wf.snapshot` 回 304，不会拿旧回放盖新视图）。按现在的实现，它不改 AI 工具调用的成败：改票走 GitHub，工具结果以 GitHub 的返回与写后读回为准；评论写回执失败只多回 `stored:false`（`src/refresh/rooms/host/comment-thread-fetch.ts:459-465`），不把工具判失败。
- **为什么会有**：由 #1869 真机演练补入（提交 `01c3efae`），理由是：不说的话，界面会静默把另一个窗口写的数据当成自己的，事后也说不清「为什么我这边写不进去」。
- **门禁**：`tests/verify-1692-disk-replay-eviction.ts:101`（回放时刻）、`:107`（不是回放时不说）、`:109`（时刻为 0 时不说）、`:112`（中英词条都在）、`:119`（只读租约时说这句）。要换形态得一起改这些断言与两份词条。
- **与闪黄的关系**：不是同一个根因。修好闪黄，这两句照样出现；换掉这两句，闪黄照样发生。所以可以拆成两张票。
- **修法（2026-11-06 更正）**：推荐 C——只放开行级写回执，让任何窗口都能把改完的结果写进库；全量刷新仍由写锁持有者做。A（只改视图）不能让库更新，不再推荐；B 是全面放开。详见 #1929。
- **维护者的产品判断（2026-11-06）**：写锁是数据库为了保证安全用的，属于实现细节，UI 不展示；用户只该看到数据和结果，底层由代码处理。界面上的删改归 #1928，非持有窗口的视图一致性归 #1929。
