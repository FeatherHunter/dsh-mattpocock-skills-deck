## 1. 目标（一句话）

把「工作区所有 issue 及其周边数据」从现在的「可回放的缓存」改成「本地 SQLite 文件是唯一根基」：进入工作区只读这份库就能画首屏，网络只用来补新；界面显示的每一个值都来自这份库。

## 2. 范围

- 包含：列表页签里的所有 issue 及其周边数据（父票、阻塞、被阻塞、标签、指派、评论、评审、合并信息、子票计数、正文、详情），单位是一张一张 issue；三端 GitHub / GitLab / 本地 Markdown。
- 不包含（Q-G）：通知事件、工作条目、版本控制页、设置、技能清单、检查链。
- 不做：旧 JSON 迁移——旧文件原地不动，新库从空开始（m00281 用户明确）。

## 3. 沿用已有的行为契约

- ADR `docs/adr/20261030-panel-snapshot-single-source.md`：三态合并（有值/明确为空/不知道）、未知≠空、只有完整来源能清空、版本门、TTL 只决定新鲜度不决定显示、失败保留上次数据、跨重启先画磁盘再后台校准。
- 首屏口径：只装开放工作集、开放容器子票、已关闭地图容器行（`docs/design/677-issue-pool-completeness-spec.md` §6.3），不预装整仓已关闭历史。
- 视野模型与请求预算不变。
- 单一入口：所有写经一个合并入口，界面不直写。

## 5. 数据模型（12 张表）

| 表 | 职责 |
|---|---|
| `meta` | 库级身份（后端、仓库、工作区根）、schema 版本、合并版本、写者租约 |
| `actor` | 参与人（作者、指派、评论作者、评审人共用） |
| `issue` | 票骨架：身份 + 能成列的字段；取不到的列留 NULL，是否知道看 `issue_group` |
| `issue_body` | 正文单独一张表，列表查询不碰 |
| `issue_group` | 每组数据知道到什么程度（complete / truncated / unknown），决定「空」的含义 |
| `label` | 标签定义（名字唯一、颜色、说明） |
| `issue_label` | 票与标签的关联，带顺序 |
| `issue_assignee` | 票与指派人关联，带顺序 |
| `issue_edge` | 父子与阻塞两种边，一行一条，只存一个方向 |
| `comment` | 评论独立表，按位置排序，后端 id 可为空 |
| `review` | 评审独立表，按顺序整组替换 |
| `fetch_cursor` | 按页取的组（评论等）的下一页游标 |

关键约定：

- 票的唯一身份是 `(effort_id, key)`；本地 Markdown 的 `effort_id` 是工作单元目录名，GitHub/GitLab 写 `''`。
- 边表方向：`kind='parent'` 时 subject 的父票是 object；`kind='blocks'` 时 subject 被 object 阻塞。三个查询方向（父是谁、谁阻塞我、我阻塞谁）都有索引。
- 所有表 `STRICT`；时间存 UTC 毫秒整数；只有「日期」语义的字段保留 `YYYY-MM-DD` 文本。
- 开放形状、不参与查询的字段用 JSON 列：里程碑、自定义字段、本地 Markdown 的状态冲突记录。
- 「引用骨架」：别的票的依赖边提到、但自己没被完整取过的票，存在一行最小信息；没有 `row` 组记录，列表/详情查询必须排除。

## 6. 三态怎么落（Q-J 的 B）

| 库里的样子 | 含义 | 界面 |
|---|---|---|
| 有行，`complete`，值为空/无子行 | 完整查过，确认没有 | 显示「没有」 |
| 有行，`truncated`，有值 | 只拿到一部分 | 显示已有部分，标「不全」 |
| 有行，`unknown` + 原因 | 明确记下不知道（不适用 / 读不懂 / 没表达） | 显示「不适用」或「未知」 |
| 没有行 | 从来没取过 | 显示「未知」，带上次已知时间 |

## 7. 行为契约

- **一轮刷新一个事务**：合并、写库、递增合并版本都在一个事务里；提交成功才通知界面刷新（Q-A：界面只显示已提交的数据）。
- **组替换规则**：完整来源才能覆盖或清空整组；截断来源只补空缺、不删旧值；没表达或说「不知道」的来源不许删。
- **版本门**：本趟表达的组里，凡写入版本大于起读版本的，整批丢弃。
- **单写者租约**（Q-C）：一个工作区同一时刻只有一个逻辑写者；其他会话只读；抢不到租约就退回只读并明示。租约心跳 5 秒、过期 15 秒；接管前重读最新状态。
- **失败处理**（Q-F）：写失败什么都不改，界面保持旧值并明示；库不可用时降级到内存并明示，提供手动重建入口。
- **冷启动**：进入工作区先读库铺首屏，再后台校准；不允许先发在线探测、等整份重建（现状约 25 秒，`src/host/tracker/issue-list-fetch.ts:239-254`）。
- **详情**（Q-D）：本地优先，过期后台刷新。
- **库文件位置**：`<工作区根>\\.dsh-mattskillsdeck-cache\\snapshot\\<后端>.sqlite`（加 `-wal`、`-shm` 伴生文件）；工作区根按 `workspace.yaml` 向上逐层找（ADR 20261103），不认 `.git`。回退链：工作区根 → 进程 cwd（仅同一工作区根内）→ 只留内存并明示。网络盘 WAL 不可靠时回退 `journal_mode=DELETE`。
- **重建**：显式「重建快照」= 关连接、删三件套、重开；不做旧 JSON 迁移。

## 8. 并发与恢复

- WAL 下一写多读；读连接 `query_only`；写连接 `BEGIN IMMEDIATE`。
- 心跳租约解决「谁做逻辑合并」；SQLite 自身保证写入串行。
- 崩溃：WAL 自动回滚未提交事务；`synchronous=NORMAL` 下最多丢最后一条已提交事务（数据可重取）。
- 损坏：开库 `PRAGMA quick_check`；坏了整库重建并记诊断日志；备份用 SQLite 的 `backup()`。
- 演进：`PRAGMA user_version` + `meta.schema_version`；第一版只认 1，升级走显式迁移或整库重建。
