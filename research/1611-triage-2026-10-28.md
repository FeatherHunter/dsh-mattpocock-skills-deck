## 三扇门禁的根因与修法

### verify-pagination-limits：共享表多一项、EXPECTED 少一项，GitLab 房还留着两个分页裸数字

红字有三条：共享表 github 组多出 mapListMaxPages（EXPECTED 里没有）、src/tracker/rooms/gitlab/maps.ts:38 的 `const PAGE_SIZE = 100` 是 named-constant 裸数字、同一文件用了 PAGINATION 却没有从 contract/pagination.js 导入。

根因：这三件事都出自 #1603/#1605 的地图薄查。GitHub 房新增分页上限时把它收进了共享表（src/tracker/contract/pagination.ts:61 `mapListMaxPages: 10`），但没有同步 tests/verify-pagination-limits.ts 的 EXPECTED（:37-53）。GitLab 房照着写了一份独立常量（src/tracker/rooms/gitlab/maps.ts:38 `PAGE_SIZE = 100`、:40 `MAX_MAP_PAGES = 10`），文件头注释还明确写着「分页常量住本文件，不碰共享分页表」—— 这正是门禁要拦的「同值第二份拷贝」。门禁这次只逮到 `PAGE_SIZE` 的写法，`MAX_MAP_PAGES = 10` 的形状没被 RULES 正则匹配，但两者都是同值第二份，修的时候两处都该收进共享表。契约文件头（pagination.ts:26-28）本来就要求「改这里的数字必须同时改 EXPECTED」。

修法（值不变、行为不变）：pagination.ts 的 gitlab 组新增 `mapListMaxPages: 10`；EXPECTED 的 github 与 gitlab 各补这一项；gitlab/maps.ts 改为导入 PAGINATION，`PAGE_SIZE` 取 `PAGINATION.gitlab.maxPerPage`（100，per_page 上限的语义），`MAX_MAP_PAGES` 取 `PAGINATION.gitlab.mapListMaxPages`。门禁文件头 :20-21 也写明：新写法应「收进共享表并把新形状加进 RULES」，而不是绕开。

### verify-file-granularity：tracker-session.ts 351 有效行，超了上限 1 行

tests/verify-file-granularity.ts:30 的上限是 350 有效行（注释与空行不计，口径来自 scripts/lib/effective-lines.mts），:31 的严重线是 500。src/deck/tools/tracker-session.ts 现在 472 物理行 / 351 有效行，超 1 行。

增长来自 #1603 的提交 623d3341：这个文件被加了 11 行 —— :262 的 ADAPT_OPS 加入 'listMaps'，:270-275 的 adaptSession 里让 listMaps 缺席时回 unsupported 而不是抛错。这是「加功能时把文件顶过线」，不是基线冻结项：tests/file-granularity-baseline.json 里没有这个文件，所以门禁判「新增超标」。

修法方向：按门禁「超了要拆」的规矩真拆出模块，不是删注释或压掉一行。最小的一刀是把 #1603 新加的那段适配层整块搬走 —— src/deck/tools/tracker-session.ts:261-283 的 ADAPT_OPS 与 adaptSession（其中 :262 加了 'listMaps'、:270-275 是缺方法时回 unsupported 的分支）抽到新文件 src/deck/tools/tracker-session-adapt.ts、导出 adaptSession，抽走 19 有效行后原文件 351→332，新文件约 30 行；原文件只剩 :262/:264/:267/:403 几处引用，没有测试直接引用它。另外两个也可行的候选：额度回执组（BudgetFacts 接口、NOTE_READING_UNKNOWN / NOTE_OFF_NETWORK 两条说明、quotaPart、openedBackendIdOf，:313-381 共 51 行，抽走后到 300）与 fallbackAdmit（:82-103，21 行，抽走后到 330）。推荐最小那刀，因为超出的 11 行正是 #1603 新加的这一块，搬走它等于把「谁把它顶过线」当场结清。

拆完的登记（实测核对过，原来想当然的两处不用改）：src/deck/tsconfig.json:42 是 include ["**/*.ts"]，scripts/build.mts:1081-1091 的 MOVED_TREE_MAP + collectMovedTs 递归扫 src/deck，都会自动纳入新文件，不用另登记。真正漏的是 tests/verify-1106-deck-surface.ts:803 的精确 20 项 EXPECTED_FILES（要加 tracker-session-adapt.ts 变 21 份），同文件 :804 的文案「三个内部模块」「二十份」要改成「四个」「二十一份」，:786-802 追加一句 #1611 拆分说明；以及 tests/gate-map.json 必须用 node scripts/gate-map.mts 重新生成（tests/verify-gate-map.ts:51-70 逐字节比落盘表、:395-411 要求覆盖面文件数等于磁盘 src 文件数，592→593），否则 verify-gate-map 会红。新文件在 src/deck/tools 下已有目录级门禁覆盖，不会 ungated。不要跑 --record-baseline：它会把当前所有超标重录，反而掩盖新超标。

### verify-golden-receipts：本地地图薄行的 url 从文件地址变成了空串

差异只有一处：夹具 tests/tracker-contract/fixtures/golden-receipts/01-deck_context.golden.json:38 记的 url 是 `"<ROOT>/.scratch/demo/map.md"`，实测是空串。基准 2892 字、实测 2865 字，差 27 字正好是这个路径的长度，首差在第 1856 字符；其余 11 项比对（10 份工具回执加两房形状对照）逐字节一致。归一化只抹工作区根、工作区钥匙、时间三样（tests/verify-golden-receipts.ts:18-32），所以这是行为实差，不是夹具噪音。

行为链：旧路径是 markdown 房枚举地图容器时 parseMd(..., url: mapPath) 带上文件地址（src/tracker/rooms/markdown/issues-read.ts:120，另有 :404/:424），deck_context 再经 src/deck/tools/context.ts:85-87 的 mapRow 投影 url: issue.url || ''，于是回执里有路径；#1142 也确立本地票的地址就是文件地址。新路径是 #1605 的 src/tracker/rooms/markdown/maps.ts:80 写死 `url: ''`（:17 注释「本地 url 诚实回空串（契约 MapRow 注明）」），而 context.ts:202-205 在薄查成功时直接用薄行、不再过 mapRow，于是空串直达回执。

这里有一个需要维护者拍板的语义选择，两条路都能让门禁回绿：

- (a) 承认空串是 #1603 契约（src/tracker/contract/results.ts:303 注释「票的地址（远端是网址，本地诚实回空串）」）的既定含义，用 `node tests/verify-golden-receipts.ts --update` 重录基准。代价是本地地图行永远没有地址可点。
- (b) 回到旧行为：markdown/maps.ts:80 改 `url: String(row.url || '')`，让薄行带上同一个文件地址，基准一行不动。依据是 #1602 的「契约只增不改，老列表语义一行不动」和 #1142：src/tracker/contract/index.ts:136 说的「诚实回空串」只针对 issueAddress（按编号算地址的定位口）；票的地址从 #1142 起就由票自己的 url 字段带出，src/tracker/rooms/markdown/index.ts:190-191、:420 也是这个口径。需要同步改 results.ts:303 与 maps.ts:17 的注释、docs/tracker/capability-markdown.md:31 的「本地 url 诚实回空串」一句，并把 tests/verify-1605-markdown-map-list.ts:98 的说明文案改成断言地址非空/含 map.md。

推荐 (b)：薄查换的只是取数路径，同一批列表数据在两套路径下应当同形；空串会让「同一个列表，走老路有地址、走薄查没地址」这种只在性能优化后才出现的行为漂移固化进冻结基准。这一条已有实测：临时把 :80 改成 `url: String(row.url || '')` 后，12 项比对全部逐字节一致（deck_context 回到基准的 2892 字），随后已还原；而 (a) 要动的 --update 会把这个回归写死，且与 #1602/#1142 的既定口径相反。正因如此，这条仍属用户可见语义，按维护者拍板为准。
