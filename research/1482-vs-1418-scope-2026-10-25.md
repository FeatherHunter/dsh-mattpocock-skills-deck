# #1482 与 #1418 的问题关系（2026-10-25 调查）

一句话：**不是同一个问题**。用户看到的症状相同（deck 工具被「额度的一个桶已经见底」拒），但病灶分三层：#1482 是记账口径错（已随 beta.17 生效），#1418 是探测真实需求超量 + 闸把一族见底放大成整轮停（代码已在 main、未发版）。唯一「同一个问题」的角落是 #1482 的同类残留：gh CLI 子命令里的 GraphQL 写仍被账本记成 REST 请求（量级很小，建议单独立小票）。

## 1. 两票各自的问题

### #1482（已发 beta.17，等真机复核）

- 记账口径：#1482 之前，`gh api graphql` 的每一页被账本记成 **1 条 REST 请求**（判 GraphQL 只看 argv[0] 是否含 `graphql`，而真实命令的 argv[0] 是 `api`）。于是本地 rest 桶被 GraphQL 调用虚增，先到写保底，deck 工具被整轮拒掉——而 GitHub 上真实的 REST 配额几乎没动。
- 修法：判档看完整 argv；GraphQL 只记点数、不记请求条数；点数按回包 `rateLimit.cost` 补差；`gh.exec` 日志补 `points` 与 `pointSource` 两格。
- 交付：`3710cc58`、`984ea3f7`、`5cce28dc` → 已随 **v1.9.0-beta.17** 发布。剩 1 小时真机复核（看日志里 bucket 落点）就可以关票。

### #1418（P0 + P1 + 两轮复核整改都在 main，未发版）

- ① 需求侧：探测按「客户端记住的每一个工作区」全量扇出，每一拍都做全仓翻页 → 真实 GraphQL 点数被探测烧穿。P1 改成只探「人正在看的那一个工作区」+ 连续无变化退避（后台 60 秒拍与面板开着的 5 秒拍各按自己的基数拉长）。
- ② 准入侧：任一桶 remaining ≤ 写保底 → 拒掉全部 deck 工具（连只用另一族的操作也停）。P1 改成按族判断、文案写清缺的是哪种额度 / 约几点恢复 / 还剩多少。
- ③ P0（过程中发现）：探测索引扫描单页要 200 条，超过 GitHub 连接上限 100 → 每一拍整页被拒、失败又看不见。已修。
- ④ 复核又修：写操作按真实出站通道分族（含建票的前置幂等锚回查）、活跃探测拍退避、闸拒绝文案、日志附录。

## 2. 为什么说不是同一个问题：今天（2026-10-25）的真机证据

用本机已装 beta.17（含 #1482）的插件日志，取最近 2 小时：

- **#1482 的修正在生效**：`quota.spend` 里 graphql 6,939 行 / 7,036 点；rest 只有 87 行（plugin 82 条、ai-tool 5 条，都是真实 REST 命令）。`gh.exec` 带 `points` / `pointSource` 两格。旧症状「GraphQL 被记成 REST 请求」已经看不到。
- **但 deck 工具仍然被拒**：本地账本 `remaining=0` 在 2 小时里出现 5,199 次（13:40–15:40）；同一时刻真实 GitHub 的 GraphQL 还有 1,647/5,000，15:40 配额重置后是 4,761/5,000。也就是说：本地见底不是账本虚增，是**插件自己那一份额度被真实花光了**。
- **花光的来源是探测**：`host.call` 的 `wf.probe` 2 小时 7,993 次（中位 79 次/分、p95 98 次/分、同一秒最多 24 条多工作区齐探）；GraphQL 记账约 3,500 点/小时，而插件份额上限是 1,750 点/小时——**超额约 2 倍**。这正是 #1418 的 ①。
- 结论：#1482 修好之后现场仍然堵，堵因是 #1418 的 ①② 还没装上新版，而不是记账又坏了。

## 3. 唯一的交叉点：同类的记账残留

- `gh issue edit / close / reopen / comment` 这几条 gh 子命令内部发的都是 `POST /graphql`，但账本的判档只认 `gh api graphql`，所以这些写操作仍被记成「1 条 REST 请求、0 点」。#1482 修的是同一条判档函数的另一段（api graphql），这是它没盖到的另一条出站路径。
- 量级：写操作低频，今天两小时只有 2 笔写（1 条 comment 走 REST、1 条 setAssignees 走 cli），对 rest 桶的影响不到 10 条，不足以造成误停。
- 与 #1418 的关系：这是同一事实（写操作真实走 GraphQL）的两个用途。#1418 已经让**准入**按真实通道判（update / close 等只看 GraphQL），但**记账**没改；要不要改记账建议单独立小票（先定 gh 子命令的 GraphQL 写怎么估点数——gh CLI 不回 `rateLimit.cost`）。
- 顺带一个真机复核提醒：今天日志里 `gh.exec.pointSource` 全是 `estimate`（首报按 1 点估），补差走 `noteOutboundCorrection` 另一条路、不体现在 `pointSource` 上；#1482 的「点数等于回包 cost」要看 `quota.spend` 与回包 cost 对账，不能只看 pointSource。

## 4. 建议

- #1482：先不关；它的 1 小时真机复核可以和 #1418 的 2 小时 soak 合并做（同一轮安装后）：看 ①GraphQL 只进 graphql 桶、②rest 桶只在真实 REST 命令上下降、③用 `.scratch/1418-soak/collect-soak.ps1` 的判定表核对 bucket 落点。
- #1418：等发版、安装后做 2 小时 soak；装上新版后探测需求降下来，graphql 桶不再见底，deck 工具应恢复正常。
- 建议新立两张小票：①gh CLI GraphQL 写的记账口径（#1482 同类残留）；②异常现场按需日志（是否落 stderr 原文，先定脱敏与保留期）。
- 关票顺序：同一轮 soak 同时覆盖两票的验收项，数据齐了两票一起关。
