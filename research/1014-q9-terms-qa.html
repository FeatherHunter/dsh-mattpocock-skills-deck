GitHub issue #1014（地图 #1013 的子票）· 问题 Q9 的名词讲解

Q9 里的五个词：产物、落点、根两份、_dev、ARTIFACT_FILES、点名

2026-10-12 · 写给 TypeScript 新手 · 只讲你点名的五件事

一句话：产物＝构建跑一遍、机器写出来的文件；落点＝这些文件被写进磁盘的哪个目录；根两份＝仓库根目录下的 client.js 与 host.js；_dev＝构建的一档输出目标（给「在仓库里直接跑」的那份，相对的是发布包那份 _pkg）；ARTIFACT_FILES＝构建脚本里那份「哪些文件是我写的」名单；点名＝写规矩时把这些路径一条条写进文字里，让规矩能被机械核对。

1「产物」是什么？「落地」是什么意思？

产物＝构建（node scripts/build.mjs）跑一遍以后，机器写出来的那些文件。它跟手写的那份相对：手写的源码住在 src/ 等目录里，产物是机器照着它生成的。tests/verify-build-artifacts.js:10 用一句话概括过这件事：产物＝机器炒好的菜，菜谱＝src/。

落地（落点）＝这些文件被写到磁盘上的哪个目录。所以「产物落点规则」就是一句话：机器写出来的东西，只允许出现在哪几个目录里——这条规矩要解决的问题是「别让产物和手写源码混在一起」。

今天这个仓库里，产物实际散落在八处（实测）

落点里面装什么进发布包吗进 git 吗
根 client.js、host.js界面与宿主的「开发态」产物（scripts/build.mjs:105 点名的那两份）不进不进（已忽略）
package/lib/**宿主那棵树的逐文件产物，加一个打包出来的 client.js（今天 169 个文件）进不进（已忽略）
package/shared/**src/shared 整棵树的逐文件产物（今天 79 个文件）进今天错在进了，要移出
scripts/generated/*两个派生脚本的产物不进部分已忽略
src/host/logPkg/*上游日志包 dsh-log 的镜像（4 个文件，由派生脚本原样拷来）随 package/lib 进在（唯一要先讲清定性的例外）
src/ 里像素风那 34 个同名 .js每个 .ts 旁边生成的同名产物（与真源并排躺在一起）不进在，要出库
src/shared/<核名>/*.js四个计算核转译出的产物（35 个，落在 src/ 里）进（被 package/shared 收走）在，要出库
packages/*/dist两个子包自己构建出来的产物不进主包不进（已忽略）

为什么这条规矩值得写清楚：前两行和后两行的区别，就是「产物有没有跟手写源码混在一个目录里」。混在一起时，测试 import './X.js' 读到的是今天刚写的真源、还是昨天生成的产物，要靠人记；13 号收口要核「手写 .js 归零」时，也没法用一个目录扫描判出来。

2「根两份」是哪两份？

「根」＝仓库根目录（也就是 D:\dsh-plugin\dsh-mattpocock-skills-deck\ 这一层，不是 package/ 子目录）。「两份」＝client.js 与 host.js。它们就是 scripts/build.mjs:105 那一行里点名的前两个文件。

它俩与「包内那两份」是同一份源码的两个形态（构建脚本开头 :9-11 写着「一源出两物」）：

开发态（根）发布态（包内）是什么
client.jspackage/lib/client.js界面那份闭包
host.jspackage/lib/index.js宿主那份插件入口

谁在读它们：tests/ 里对这两个名字的命中 333 处，其中上百条门禁拿「根产物」与「包内产物」互相比对（叫「双源一致」）——例如 tests/verify-kernel.js:10、tests/verify-ctx.js:14、tests/verify-client-no-undef.js:27、tests/verify-handoff-latest-sort.js:34。

这就是 Q9 的由来：Q4 那句「产物只落三处」没把这两份点进去。照字面执行的人，第一个动作就会把它们搬进构建缓存目录——然后上面那上百条门禁一起红，换来的只是「仓库根少两个文件」。

3_dev 是什么东西？

它不是文件后缀、不是环境变量、不是目录名，而是构建的一档「输出目标」——同一份源码，构建可以产出两种形态，脚本用 _dev、_pkg 这两个后缀给它们命名。scripts/build.mjs:8-11 的原文：

规范方言 = 动态版方言（src/client/index.js / src/host/index.js …）
一源出两物：
  _dev → 根 client.js / host.js（cordis_define 函数体形态，须过 precheckCode）
  _pkg → package/lib/client.js / package/lib/index.js（ModuleLoader / ESM 形态，pkg entry 提供 shim）
  • _dev 取「development」：给「在仓库里直接跑、被门禁读文本」的那份（形态是 cordis_define 函数体，构建时会做一次包装编译校验，见 :18）。
  • _pkg 取「package」：给安装这个插件的人用的那份（形态是 ModuleLoader 工厂壳 / ESM，另过三关：vm 编译、__ModuleLoader__ 特征、单组件单声明，见 :19）。
  • 怎么选：node scripts/build.mjs 两份都出；--dev-only 只出根那份、--pkg-only 只出包内那份（:22、:989-990）。发布包里 package/package.json:16 的 prepare 用的就是 --pkg-only。

顺带一条相关的事实：根产物有「降级声明」——scripts/build.mjs:944-953 的 gateBuildArtifacts() 会看根 client.js／host.js 开头有没有 // AUTO-GENERATED 横幅；没有就警告「可能是手改产物，下次构建会被覆盖」。这条就是「产物不许手碰」的现场提示。

4ARTIFACT_FILES 是什么？

它是 scripts/build.mjs:105 的一行常量——构建脚本自己那份「哪些文件是我写的」名单：

const ARTIFACT_FILES = ['client.js', 'host.js', 'package/README.md']

它跟下一行的 ARTIFACT_DIRS（:108）是一对：一个列单文件，一个列整目录。目录那份列了五个：package/lib、scripts/generated、src/host/logPkg、package/scripts、package/bundled-skills。

它被用来干什么

  • :161-170 的 listOutputs() 把两者合成一份完整的产物清单（文件部分来自 ARTIFACT_FILES，目录部分来自 ARTIFACT_DIRS）。
  • :242-247 拿这份清单逐个算 sha256，记进构建缓存 node_modules/.cache/dsh-build.json——构建靠它记住「上次我写了哪些文件」。
  • :227 还会把清单里每个产物的修改时间提一档，让外部工具（编辑器、监听器）知道「这次构建动过它」。

它本身就是一个「手写清单」的例子：要构建记住哪些是产物，作者手写了 3 个文件名加 5 个目录名。这类清单的典型毛病是「漏一个，缓存和自检就看不见它」——这正是本次讨论里「能算出来的就别手写」那条原则要治的病。

5「点名」是什么意思？

点名＝写规矩的时候，把具体的路径或者名字一条条写进文字里，而不是笼统一句「其余的不管」「其他的照旧」。

为什么非要点名

因为规矩要能被机械核对：核对的人拿着这条规矩，应该能对每个文件给出「算例外」还是「算违规」，不需要猜。Q4 那句「产物只落三处」就是一次漏点名——packages/*/dist、根 client.js/host.js、scripts/generated/* 都没被点进去。等到 13 号收口核「手写 .js 归零」时，没人知道 packages/*/dist 里那些文件到底算合理的例外、还是算违规。

点名写出来是什么样

一句话里既有路径、也有它的性质，例如：

packages/*/dist：两个子包各自构建出来的产物；已被 .gitignore 忽略、不进主包、本次不动。

这样写的好处是：以后任何人（包括 AI）核这条规矩时，照着念就能判。

我的建议（等你定）：Q9 的规则照四类点名写——发布包内产物、仓库根 dev 产物、构建缓存、子包自己的 dist，其中 packages/*/dist 单独写一句如上。
