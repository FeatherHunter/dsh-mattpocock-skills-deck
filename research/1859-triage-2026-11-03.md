### A. H3 的「3 条」是怎么来的

- **干净票直接写 H3**：读回 **2 条**，不是 3 条。精确数组：

```json
[
  {"login":"probe-actor","body":"先给结论。","createdAt":"2026-11-03T15:52:46.680Z"},
  {"login":"这段是三级标题","body":"后面还有内容。","createdAt":""}
]
```

- **同一张票先写 H2 评论，再追加 H3 评论**：读回 **3 条**，正好是票面的 `["先给结论。", "先给结论。", "后面还有内容。"]`。精确数组：

```json
[
  {"login":"probe-actor","body":"先给结论。","createdAt":"2026-11-03T15:52:46.697Z"},
  {"login":"probe-actor","body":"先给结论。","createdAt":"2026-11-03T15:52:46.704Z"},
  {"login":"这段是三级标题","body":"后面还有内容。","createdAt":""}
]
```

落盘顺序是：

```text
## Comments

### probe-actor — 2026-11-03T15:52:46.697Z
先给结论。

### probe-actor — 2026-11-03T15:52:46.704Z
先给结论。

### 这段是三级标题

后面还有内容。

## 这段是二级标题

后面还有内容。
```

- 结论：票面的 3 条**可以复现**，但复现步骤少了一个前置——必须先写那条含 H2 的评论。第二条「先给结论。」是第二次真实写入的评论，不是读侧复制出来的；伪评论只有末尾那条作者为「这段是三级标题」、时间戳为空的。票面把「换成 H3 时」写成孤立步骤，读者会以为干净票也读到 3 条，这是**复现描述不完整**，不是数字造假。第 2 节的 2 条/3 条对照仍然成立，但要把前置写进回归用例。

### B. 地图路线不是「未受影响」，而是另一种重复

- 代码路径：`issues-status.ts:260-267` 的 `answerTextOf` 用 `/^##\s*Answer\s*$/` 找段、用 `/^##\s/` 当段尾；`:284` 在 `answerTextOf(out) !== reason.trim()` 时用 `appendSectionBlock(out, 'Answer', reason)` 追加。原因正文里出现 `## 附注`，Answer 段在第一次写入后就被读短；第二次关闭读到的不等于完整 reason，于是再追加一遍。
- 实测同一张地图票、同一段 reason `第一步做完了\n\n## 附注\n\n还有下文` 连关两次，两次都返回成功，落盘变成：

```text
## Answer

第一步做完了

第一步做完了

## 附注

还有下文

## 附注

还有下文
```

- `getIssue().body` 是整份原文，能看到两份；这不是评论切分，但根因同属「正文里的 H2 被当成结构边界」。第 4 节原句「地图子票……本轮没有发现同型截断」应以此为准：地图分支不经过评论切分，但关闭原因含 H2 时 `## Answer` 段内正文会重复、后续假 H2 也会重复，修评论切分时要一并处理 `answerTextOf` 与 `appendSectionBlock`。

### C. 描述里的假 `## Comments` 会让整个评论区锚错位

- 夹具：手写一张实施票，描述里先放一个假 `## Comments`（后面还有真的 `## Comments` 与一条旧评论）。`addComment` 之前 `listComments` 已经把假评论区读成一条评论：

```json
[{"login":"描述里的假评论区，不是真的。","body":"","createdAt":""}]
```

- 追加一条新评论后，文件里的顺序是「描述 → 假 `## Comments` → 描述里的假评论区 → 新评论 → 真 `## Comments` → 旧评论」；`listComments` 只读到假评论区那条与新评论，**真评论区里的旧评论完全消失**。
- 这比评论正文里的 H3 更严重：不是把一条评论读短，而是整段评论区换成了另一个锚。只改 `commentBlockOf` 不够，读侧选锚和写侧 `appendSectionBlock` 必须使用同一个「真锚」判据；当前 `parse.ts:302` 的 `cmAnchor` 与 `original-fields.ts:288-314` 都取第一个 `## Comments`。

### D. 票面转义方案的边界（补第 6 节）

按票面文字实现「行首 `## `/`### ` 加反斜杠、读侧先双后单还原」，在隔离探针里逐项跑过：

| 评论正文 | 结果 |
| --- | --- |
| 普通正文 / H2 / H3 / H4 | API 读回逐字相同；H2/H3 落盘为 `\##` / `\###` |
| 裸 `##`、裸 `###` | 写侧不转义；裸 `##` 截断，裸 `###` 造出伪评论（作者为「后面还有内容。」） |
| `##\t制表符标题` | 写侧不转义；读侧仍截断 |
| 行首两个空格 / 四个空格的 `##` | 写侧不转义；读侧仍截断；两个空格的 `###` 反而完整往返（`###` 正则不认前导空格） |
| `- ## 标题`、`> ## 标题` | 完整往返（行首不是 `##`） |
| 用户本来写 `\## 标题` | 写侧再加一个，读侧还原，往返正确 |
| 用户本来写 `\\## 标题` | 写侧不变，读侧把双反斜杠去成一个，**丢一个反斜杠** |
| 围栏代码块里的 `## 标题` | API 读回正确，但落盘的代码块变成 `\## 标题`；人或其他 agent 复制代码会看到反斜杠 |
| 围栏代码块里的 `---` | 仍被 `parse.ts:330` 截断，读回只剩「示例：」、一个空行和开围栏 |
| 正文中间单独一行 `---` | 仍被截断，读回第一段 |

- 结论：票面方案只覆盖「行首恰好一个空格分隔的 `##`/`###`」。要让它真正可逆，至少还要：① 与读侧共用「什么算标题行」的判据（裸 `##`/`###`、tab、前导空白）；② 按行首连续反斜杠个数 k 做写 k+1、读 k-1，而不是只分「双/单」两档；③ 围栏内不转义、但读侧要围栏感知；④ `---` 只去掉评论块末尾的分隔线（保留正文中间的水平线）；⑤ 收紧 `## Comments` 锚点（当前 `\s*` 允许 `##Comments` 也当锚点）。这已经超出「parse.ts 只留一行调用」的范围，需要新模块或拆文件，并补 ADR/格式映射，因为落盘可见正文多出了反斜杠。
- 另一条路是**只读严格解析**：不改文件，围栏按长度遮罩；评论区只认已知段名（`## Answer`、`## 进度`、`## Decisions so far`）作结束；评论头只认 `^### <actor> — <ISO>` 形状；正文只去掉末尾 `---`。已知段名清单应从 `src/tracker/rooms/markdown/format/original-skills.yaml` 真源生成，不能手抄；下面这个原型只有手写清单，未接真实 API。隔离原型在 control/H2/H3/H4/裸 H2/裸 H3/tab/缩进/列表/引用/单双反斜杠/围栏内标题/围栏内 `---`/正文中间 `---`/正文里的 `## Comments` 上都能逐字读回，也能在描述假锚点里选到真评论区。残留歧义：正文若出现 `## Answer` 这类已知段名，仍会被当段尾；正文若出现与真实评论头一模一样的 `### 名字 — ISO`，仍会被切开；评论头只认带 ISO 的形状，手写的无 ISO 旧评论（实测 `### 手工写的旧评论` 当前会被读成一条评论）会被并进上一条正文或读不到，旧手写票若有这种写法要单独定兼容规则。若旧文件已经被后续写入插坏（新评论插在旧评论的假 H2 之前），读侧只能把旧尾部归到新评论，无法可靠还原原归属。
- 取舍：只读严格解析改动最小、不改可见格式、能修「还没被插坏」的旧文件，但它只能降低歧义，不能保证任意正文（正文里出现 `## Answer` 这类已知段名、或与真实评论头一模一样的 `### 名字 — ISO`）都逐字往返；转义能保证新数据、但改文件、需要 ADR，而且修不了旧数据；HTML 注释分隔符/评论 id 最无歧义，但直接撞 ADR 决定三「插件自己的信息只放文件头隐藏注释、可见正文只放原文有的内容」，要先改 ADR 与 `original-skills.yaml`。本次分诊建议先把只读严格解析 + 写侧共用同一段边界判据作为第一段，转义或结构化标记留作后续；不要只做票面的「两行调用」就收口。

### E. `body` 与空白

- `getIssue().body` 是整份文件原文（`parse.ts:413` 的 `body: raw`），不是票面描述。H2 例里 `addComment` 前后 `body` 从 199 字变成 283 字，`bodyChanged=true`；要求「票面正文不被污染」若指 `body` 不变，则不成立。合理的验收口径是「`## Comments` 之前的票面前缀不变」，不是整个 `body`。
- `commentBlockOf` 的 `String(body || '').trim()` 会去掉评论正文首尾空白，这是既有行为，不属本 bug。实测输入 `"   开头空白   \n\n结尾空白   "` 读回 `"开头空白   \n\n结尾空白"`：行首行尾空白被去掉，行内空格保留。若要逐字保真，这条也要单独立项，不要混进本次修复。
