## 缺陷 A：Status 原值读不出来

### 代码与运行时事实

- 解析：`src/tracker/rooms/markdown/parse.ts:240-244`——`statusRaw` 取可见 `Status:` 行（允许 `**Status:**`）或文件头 `DSH-STATUS` 隐藏注释；`:243` 的 `closedSet` 只认 `resolved` / `completed` / `closed` / `done`，`:244` 其余一律 `state=open`。
- 返回对象：`parse.ts:407-423` 只有 key / effortId / type / title / state / body / url / 时间 / parentKey / blockedBy / comments / labels，没有 `status`。`:429-434` 是 `statusRaw` 的唯一用途——认领兜底（`statusNorm === 'claimed'` 时给 `[{login:''}]`，否则 `[]`）。
- 契约：`src/tracker/contract/entities.ts:163-215` 的 `Issue` 没有 `status`；`docs/architecture/tracker-backend-normalized-model.md:62` 定义 `type State = 'open' | 'closed'`，`:76` 明说「frontier/claimed/blocked 由 deck 推导，不进形状」，`:213-214` 把 `Status→state` 的映射归给 #115，只约定两态。
- 运行时复现（Node v24.19.0，临时探针，仓库零改动）：

| 文件里写的 | 读回的 state | 有 status 键吗 | assignees |
| --- | --- | --- | --- |
| `Status: claimed` | open | 否 | `[{login:'', kind:'user'}]` |
| `Status: needs-triage` | open | 否 | `[]` |
| `Status: ready-for-agent` | open | 否 | `[]` |
| `Status: wontfix` | open | 否 | `[]` |
| `Status: resolved` | closed（reason=`completed`） | 否 | `[]` |
| 没有 Status 行 | open | 否 | 字段整个省略（MISSING） |
| `<!-- DSH-STATUS: resolved -->` 在文件头 | closed | 否 | —（隐藏注释只认文件头，放在第一个可见标题之后就认不出） |

### 对票面的两处修正

1. **「原值在 API 侧完全看不见」不准确。** `deck_issue_get` 的正文摘录默认回前 2000 字（`src/deck/tools/issue-get.ts:261-267`，`:276` 把 `issueBrief.body` 换成摘录），Status 行在票首，所以正文里看得到。真正丢的是结构化字段：`issueBrief`（`issue-get.ts:114-131`）只有 `state`；`issue-list` 的行（`issue-list.ts:354-365`）与 `map-snapshot` 的子票行（`map-snapshot.ts:64-71`、`:79`）连状态原词和正文都没有。按状态筛票、扫地图时才真的失明。
2. **根因不只是「少一个字段」。** 随包模板 `package/bundled-skills/setup-matt-pocock-skills/issue-tracker-local.md:10` 明写「Triage state is recorded as a `Status:` line near the top of each issue file (see `triage-labels.md` for the role strings)」，且这份模板会被逐字复制成工作区 `docs/agents/issue-tracker.md`（`src/host/skillDoc.ts:80` 的 `CHOICE_REFS`；`src/client/kernel/locale-data.ts:1990` 的 `setup.markdown.backendNote`；`src/deck/tools/context.ts:67` 的 `LOCAL_HOWTO_SUFFIX`）。实现却把 triage 角色放进隐藏注释 `DSH-LABELS`（`src/tracker/rooms/markdown/format/original-skills.yaml:164-168`、`:197-200`；写侧 `create-render.ts:268`、`issues-patch.ts:491-496`），读侧不认 `Status:` 里的角色词。两条口径在同一个工作区里并存：使用者按模板手写 `Status: needs-triage`，deck 读成 open、没有标签；deck 自己建的票又走隐藏标签。

### 新查到的一处加重情形：同一个文件两套状态

本地 Markdown 建一张 bug 票，`renderTicket` 的结果同时有：

```markdown
<!-- DSH-LABELS: bug, needs-triage -->
...
# 01: T

**What to build:** ...

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent
```

可见 Status 是 `ready-for-agent`（实施票模板的默认值），隐藏标签是 `bug, needs-triage`。复现方法：`node --import ./scripts/ts-hook.mts` 直接调 `renderTicket('issue', …)`（本轮在内存里跑过，仓库零改动）。原因在 `create-render.ts:235-241` 的 `statusFor`：正文里的 Status 行 > 调用方给的 status > 格式默认值；`original-skills.yaml:154-162` 的 `plain-issue` `reuse: implementation-ticket`，于是普通票/bug 票继承了实施票的可见 `**Status:** ready-for-agent` 默认值。`src/deck/rules/object-kind.ts:81-84` 给 bug 的 triage 标签是 `bug` + `needs-triage`，两处没有对齐。

### 设计口径上的既有张力

- `docs/adr/20261025-markdown-format-original.md` 决定三第 37 行说「标签、状态、认领人…一律写成文件头的隐藏 HTML 注释」，第 39 行又说「状态、类型、依赖这些技能原文要求的行内字段照原文写（`Status:`、`Type:`、`Blocked by:`…）」。同一份 ADR 对「状态写哪里」本身有张力，实现选了前者。
- `docs/architecture/tracker-backend-normalized-model.md:211-217`（第 4 节）还写着「本地 Markdown 无 labels，用行内字段表达语义；`Issue.labels` 为 MISSING」，与今天实现（`parse.ts:291-306` 读可见 Labels 行或 `DSH-LABELS`）和契约夹具（`tests/tracker-contract/fixtures/markdown.ts:81` 把 `labels` 列为已实现字段）都对不上。
- 测试钉住现状：`tests/tracker-contract/fixtures/markdown.ts:137` 断言 `claimed→open`；`:152` 断言没有 Status 行时 assignees 整个省略。
- 已关闭的 #134 留下过口径「其余 Status/Type 保留于 body」（历史答案），但那条答案没有回答「按模板手写的 triage 状态要不要参与 deck 的筛选与前沿」。
- 折中选项（未定）：`entities.ts:68-75` 的 `CustomField` 允许任意 name 且写明「说明性元数据，绝不驱动 deck 逻辑」；parse 已把 `Type` 提升进 `customFields`（`parse.ts:267-269`、`:423`），Status 可以照做而不动 Issue 形状——但它同样不解决「按模板写的 triage 状态不生效」。

## 缺陷 B：失败回执顶层 reason 恒 backend-unsupported

### 三处同型，不是两处

- `src/deck/tools/issue-patch.ts:435-441`：`status = statusOfItems(items)`；`:440` `reason: status === DECK_STATUS.OK ? '' : REFUSAL_REASONS.BACKEND_UNSUPPORTED`；`:441` `text` 只有「票 key：这次点了 N 步，成了 M 步。」。
- `src/deck/tools/map-link.ts:249-273`：同一行 reason（`:265`）；text 自 #790 起已带失败摘要（`:251-261`）。
- `src/deck/tools/map-plan-create.ts:483-496`：同一行 reason（`:495`）；`:485` 还会把 items 全成但没建完的情况改成 partial，text 不提第一处失败。
- 另有 partial 同型两处：`map-snapshot.ts:194-195`、`context.ts:221-225`。
- 锁冲突误报：`map-plan-create.ts:262` 对「同一个计划标识正在另一次执行里跑」也回 `backend-unsupported`（文案说「等它做完再来」，与「后端做不到」正相反）。

### 真实原因的去向

- `issue-patch.ts:161-164` 的 `fail()` 只取 `result.error.message` 并截 200 字进 items，丢掉 `error.kind`。正文改写路径 `:374` `t.update` → `:381` `fail('text', r)`，此时 `r.error.kind === 'parse'` 就在手上。模板守卫拒绝的出处是 `src/tracker/rooms/markdown/issues-patch.ts:124` 的 `failAs(ERROR_KIND.PARSE, refusal, …)`；本轮用临时探针直接调守卫，拒绝文案 225 字，deck 层截到 200 字。
- 「恒为」不准确：整笔传输超时已走 `backend-timeout`（`issue-patch.ts:170-178`）。恒错的是「有逐项失败」的收尾支。整体三态由 `src/deck/shell/edge-landing.ts:260-270` 的 `statusOfItems` 合成：全成 ok、全没成 unsupported、部分成 partial。票面实测那次是 1 步全失败，`status=unsupported` 本身没错，错的是把 PARSE 说成「后端做不到」；partial 的案例里顶层 reason 也写成 backend-unsupported，语义更不对。
- 「现有原因码够用」不成立：`REFUSAL_REASONS` 只有 8 码（`src/deck/shell/call-shell.ts:52-61`：no-session-context / ai-tool-refused / no-backend / gate-defer / backend-threw / backend-timeout / backend-unsupported / bad-args），没有 parse、没有 conflict；文档语义是「下一步怎么办」（`docs/agents/issue-tracker.md:50` 四档）。后端自己的 `ErrorKind`（`src/tracker/contract/identity.ts:79-87`：env / auth / rate-limit / conflict / unsupported / not-found / network / parse）是另一套词表，注释明写「不许新增取值」；本地 Markdown 确实会产 `parse`（`issues-patch.ts:124`）与 `conflict`（`issues-locate.ts:271`、`write-guards.ts:68`），但 items 的 `status` 只有 ok / failed，分不出这两类。
- map-link 这边更缺料：`EdgeItem`（`edge-landing.ts:45-64`）只有 op / target / landing / evidence / ok / key / role / status，没有 kind；写失败时 kind 还被强制成 `'unsupported'`（`edge-landing.ts:149-152`、`:197-204`）。多数失败是 deck 层本地判断（锁、额度、读回未确认、环预检），没有后端 kind 可分类。
- 门禁与文档钉住现状：`tests/verify-1106-deck-surface.ts:100` 冻结 8 码、`:534` 断言非 ok 回执的 reason 必在表内、`:698` 甚至把 map-plan-create 的并发锁拒绝断言成 `backend-unsupported`；`tests/verify-deck-tools.ts:382` 对 map-link partial 只查 items、不查顶层 reason；`docs/tour/deck-call-end-to-end.md:668` 写「reason 七值之一」，实际是八码（既有文档漂移）。
- 同型实例：#1785 的记录 `tests/verify-1785-assign-unknown.ts:5` 是「票 20：这次点了 1 步，成了 0 步。」，真实 kind 为 `not-found`（`:162`）。
- 历史：这行 reason 自 `405bd676fd`（#713 七工具落地，2026-09-23）起就是这个写法；#790 只给 map-link 的 text 加失败摘要，没碰 reason；没有测试钉住这两处聚合 reason 的正确性。
