# 研究：地图 699 下面的老问题在当前主干是否还存在（427 / 428 / 429 复核）

调查范围是地图 [699](https://github.com/FeatherHunter/dsh-mattpocock-skills-deck/issues/699) 下面的三张老问题票：[427](https://github.com/FeatherHunter/dsh-mattpocock-skills-deck/issues/427)（新电脑已装 gh 仍报找不到命令）、[428](https://github.com/FeatherHunter/dsh-mattpocock-skills-deck/issues/428)（仓库已就绪仍显示未识别仓库）、[429](https://github.com/FeatherHunter/dsh-mattpocock-skills-deck/issues/429)（上面两起现象是否解决的待定票）。[702](https://github.com/FeatherHunter/dsh-mattpocock-skills-deck/issues/702) 是 699 建图之后派生的新讨论，不是当初的老问题，这里只在边界处提一句，不计入存废结论。

老票基于 v1.7.10（427 与 428 的正文里写明了实测版本与版本对照）；本次复核的代码是当前主干 v1.7.46（`package/package.json:3` 写着 `"version": "1.7.46"`）。

**一句话结论：427 的 A 项（gh 假阴性）还存在，代码里的根因一处没动，只多了一次同环境的兜底探测；427 的 B 项（技能随包可用）已经不存在，当初的疑问被后面的版本解决了；427 的 C 项（git 与 pnpm 是否进检查链、登录指引是否换形态）还存在，都没有进检查链；428 的三级解析结构还存在，失败仍然静默，面板上的警示芯片还在、另多了一块独立触发的红卡；429 的待定还挂着，维护者还没有拍板。**

下面每节一条结论，每条结论后面跟一手来源。只交事实与边界，不写产品结论。本报告 v2 补记：428 一节按第二路并行核查的 7 条硬证据订正过，第一版里两处说法（默认值位置搬家、芯片搬家）以本版为准。

## 2 427-A（gh 假阴性）：还存在

程序找 gh 的办法还是两段式，没有新增第三段去读系统里的最新值。来源是 `src/host/platform/index.js:111-129`：先试子进程解析（第 114 行），命中就直接返回（第 118 行）；只有名字正好是 gh 时才读系统变量兜底并用文件系统校验存在才返回（第 119-127 行），否则返回空（第 128 行）。

三个系统的底座都是直透，没有自己加料。Windows 在 `src/host/platform/win32/index.js:62-65`，别名表里只有终端命令那一项，gh 不进表，直接调子进程解析；macOS 在 `src/host/platform/darwin/index.js:45-48`，注释写明找不到时抛错交给通用层转空，平台层不叠加兜底；Linux 在 `src/host/platform/linux/index.js:47-50`，注释写明原来自带的兜底已于 2026-08-29 移除，单一真源在通用层（第 42-45 行）。

环境变量的来源还是进程启动那一刻的快照。通用层在 `src/host/platform/index.js:107` 取注入对象或进程环境，第 80-89 行的构造只是只读包装；Windows 适配器在 `src/host/platform/win32/index.js:22-34` 按注入对象、测试挂载、最后进程环境的顺序取；另一条兜底通道 `src/host/platformChannel.js:105` 同样取进程环境，第 151 行的视图也是只读包装。

全仓库搜不到读新鲜环境变量的代码。macOS 适配器在 `src/host/platform/darwin/index.js:8` 明确声明平台层不硬编码常见安装目录；登录终端、用户注册表、新鲜环境变量这类取法在源代码目录下没有命中（Windows 注册表读数、登录终端起新终端打印环境变量、已知目录枚举都没有对应的实现代码）。

系统变量兜底还在，但读的是同一份旧快照。拥有点仍在通用层，注释在 `src/host/platform/index.js:108-110`（2026-08-29 统一，三个系统行为一致）；读取点在第 120 行，读的是上面那份环境来源；另一条通道在 `src/host/platformChannel.js:135-148`，第 140 行同样读兜底变量再做文件校验。

检查链判定 gh 是否安装还是走同一条路。检查目录在 `src/host/tracker/backends/github/checks.js:25-30`，装没装这一项就是存在性检查；原语实现在 `src/host/tracker/predicatePrimitives.js:53-59`，经解析命中算通过、否则算失败；门禁预检在 `src/host/tracker/backends/github/preflight.js:44-53`，第一项同样经平台解析，拿不到就返回环境类错误。链快照与门禁同源，都受进程快照影响。

唯一的新增是一次同环境的存活探测，不是新鲜环境变量修复。在 `src/host/tracker/backends/github/client.js:99-113`，平台找不到 gh 之后会再起一次 gh 看版本（第 107 行），命中就按找到了算（第 108-111 行）。注释在第 102-103 行写明了目的只是绕开子进程解析与终端环境变量不一致导致的那类建票拉不到的问题；这次探测没有传自定义环境变量也没有起登录终端，继承的还是宿主进程的环境，所以装完 gh 但进程没重启的那种快照滞后它覆盖不了。

文案搬过家，但根因链没变。修复知识现在在 `src/host/tracker/backends/github/index.js:39-49`，装没装的提示还是说没安装并给安装指引与重新检查两个动作；安装指引的那句话在第 136-139 行，是维护者给的原话（用向导帮用户装 gh 并附官方地址）；第 17-18 行与第 133-135 行注释写明这句话是按 716 从共享清单挪回本模块的；第 144-146 行注释写明原来按系统分平台的那段长文已按 664 退役。共享清单在 `src/shared/tracker/guide-steps.js:26` 只留注入哪条提示词的键名，第 66-72 行的安装步骤仍指向它。所以 427 原文里引用的两段长文名字已经对不上现在的文件，但找不到 gh 就判失败、失败就给安装指引这条路还在。

## 5 428（三级解析全失败）：结构上还存在

解析还是三层，顺序与失败处理都没变，而且有两套同源实现并存。后端能力位那套在 `src/host/tracker/backends/github/repo.js:92-154`：第一层用 git 问远端地址再解析（第 98-122 行），第二层直读相对路径配置文件里的远端地址再解析（第 124-141 行，另在第 135-139 行多一段行级地址的兼容回退），第三层用 gh 问仓库全名再拆分（第 143-152 行）；三层各自吞错，全挂才返回空（第 153-154 行）。宿主实际调用走第二套同源实现，在 `src/host/repoKeys.js:254-294`（第 258-261 行注释写明方案同源）：第一层在第 264-272 行，第二层在第 273-284 行，第三层在第 285-293 行。接线在 `src/host/index.js:90`（仓库键委托内部实现）与后端装配文件第 123 行（把后端那套挂为后端能力位）。

失败还是静默的，埋点只记层号。来源是后端那套第 83-90 行的层级埋点，只记第几层、是否成功、耗时；成功时在第 107、117、132、138、150 行各记一行，全挂在第 153 行记第三层失败一行，不记哪一段掉的原因。第二套同纪律：`src/host/repoKeys.js` 第 270 行记第一层成功一行、第 281 行记第二层成功一行、第 287 行记第三层失败一行、第 292 行记第三层成功一行，字段同样只有层号、成败、耗时。调用方只能看到空结果，例如快照组装在拿不到仓库键之后直接走无仓库分支。

工作目录拿不到就回落的写法还在，默认值仍是进程启动目录。定义在 `src/host/index.js:32`（默认值等于进程当前目录，第 31 行注释写明默认工作区就是进程当前目录）。回落链：`src/host/workspaceCwd.js:13-14` 收到目录为空就用默认值，`src/host/repoKeys.js:256` 同样收到目录空就用默认值再算键、第 263 行再按仓库根与键定出本次执行目录。唯一不一致的是后端那套在 `src/host/tracker/backends/github/repo.js:94` 写的是空时直接用空串，不吃默认值，两套回落口径不一致仍然存在。

第二层的目录用法是相对路径加本次目录转发，解析权在文件服务，插件不判沙箱根。两套都是解析相对配置文件路径并把本次执行目录传过去（后端那套第 127 行，第二套第 276 行），插件侧没有拼接绝对路径、没有沙箱根白名单，文件服务来自上下文透传。如果沙箱把本次目录判到界外，读抛出的异常会被上面的空异常捕获吃掉，直接落到第三层或空结果，链路上无法区分文件不存在还是沙箱拒绝。

面板上的琥珀色警示芯片还在，另有一块全屏红卡是独立触发，不要混为一处。芯片触发在 `src/client/panel/Dock.js:194-196`（远程型后端已选但仓库引用缺失时显示琥珀色警示，第 193 行是快照没回来时的灰色占位骨架，不算未识别）。全屏红卡是另一条触发，在 `src/client/views/NoRepoCard.js:22-24`（判仓库缺位改从链快照的远端失败派生）。所以 428 的现象链（三层全失败得空、面板显示未识别）在代码层面仍然可达。第一版报告里写芯片搬家是说法不准，以本段为准。

## 7 还没确定的事

1. 本次是代码静态复核，没有在 v1.7.46 的真机上重跑 427 与 428 的复现步骤（全新电脑、用快捷方式启动、在用户级环境变量补丁生效前启动），真机上是否还是三处红与未识别仓库仍需实测。
2. 四个分叉点的运行时值（宿主进程环境里有没有兜底变量、子进程里的环境变量实际是什么、宿主收到的工作目录是真实目录还是回落值、文件沙箱的可写根实际是什么）都要真机转储才能定，代码只能对应到位置，给不出值。
3. 地图雾里的 winget 提权交互（当场失败还是先弹一个要人按的框）仍只到官方资料，没有真机验过。
4. 本次没有重验 DSH 本体（子进程服务与文件沙箱）的版本变化，子进程清理规则与沙箱根的结论沿用 699 前两份研究的实测。
