## 人话总览（300字以内）

地图08要把 GitHub 后端与本地 Markdown 后端从旧语言转成 TypeScript，并补齐日志。契约是指仓库里描述后端必须实现哪些操作的那一份类型与数据。契约之前只被两样东西检查过，一样是类型探针，一样是契约门禁，从来没有被真实的读写操作完整地运行过。地图08是第一次让契约面对真实后端的完整读写与关系操作，所以转写过程中发现的形状不一致，就是契约第一次被真实后端检验的结果。检验发现三类事实，一是探针里有三处诚实的弱化，二是创建操作的返回在三个深层位置被写宽了，三是两个后端各有一些契约之外的扩展成员。本文把这三类事实逐条讲清，把证据指到文件行号与票号，最后列出留给人类决策的事项清单。

## 1. 地图08是什么，为什么说契约第一次被真实后端检验

人话结论：地图08是把两个真实后端转成 TypeScript 的开发工作。契约是描述后端必须实现哪些操作的类型与数据。契约之前只被类型探针与契约门禁检查过，没有被真实的读写操作完整运行过。地图08第一次让契约面对两个真实后端的完整读写与关系操作，所以转写中暴露的形状差异，就是契约第一次被真实后端检验的记录。

人话补充：类型探针是指只做类型检查、不运行、不改后端的检查文件。契约门禁是指检查契约目录形状与探针结论的脚本。真实后端是指真正读写 GitHub 远端与本地文件的两套实现。检验在这里的意思是让契约的形状与真实后端的形状逐条对照，形状对不上就记录下来。

证据：

- 地图议题 #1050 是地图08的地图票，开发工作拆成三张开发票，分别是读路径 #1052、写路径 #1053、关系与边 #1054。

- #1053 的票面写明目的为建票、改票、评论、标签配色、初始化、幂等锚这一串写路径转 TypeScript，边界只改写路径，写前校验与写后读回语义不许变。
- #1054 的票面写明目的为父子边、阻塞边、环检测、边修复、调用内名册这五件转 TypeScript，边界只改关系与边这一组。
- 三张开发票的票面都写明，本图的结论在讨论票 #1051 的评论与地图 #1050 的相应章节，本票边界与讨论结论冲突时以讨论结论为准，并把冲突写进本票评论。

## 2. 后端模块形状与探针形状的区别，三处弱化是什么、为什么弱化、风险是什么

人话结论：后端模块形状是指契约里描述一个后端模块对象必须长什么样的类型。后端模块对象是指进程启动时注册的那一份静态描述，包含身份、显示名、创建函数、识别函数与若干只读的界面描述数据。探针形状是指探针文件里为了让旧语言实现通过类型检查而诚实放宽的形状。探针形状与后端模块形状有三处弱化，分别是创建操作只断存在不断深层、开仓库方式只断存在不断字面量、检查目录只断存在不断种类。弱化的原因是后端的实现还是旧语言，修形状要改实现面，而讨论结论定下探针票不碰实现面。风险是缺成员抓不住体现在可选成员上，增成员只能靠运行时键快照发现。

人话补充：创建操作是指契约里创建一个能干活的后端实例的那个函数。开仓库方式是指界面打开仓库时用浏览器打开网址还是打开本地文件夹。检查目录是指每个后端自己的环境检查条目列表。缺成员抓不住是指契约里要求有但后端没有实现的可选成员，类型检查不会报错。增成员只能靠运行时键快照是指后端多出来的成员，类型检查不会报错，只能靠门禁在运行时把成员名字列出来做快照比对。

证据：

- 后端模块形状的必填四件套为身份、显示名、创建函数、识别函数，其余字段全部可选，见 `src/tracker/contract/backend-module.ts:146-180`。
- 注册表只校验五件事，缺字段不是错误，缺显示描述时有回退，见 `src/tracker/contract/backend-module.ts:14-19`。
- 探针形状的定义见 `tests/contract-probe-github.ts:44-48`，写法是从后端模块形状里去掉创建操作、开仓库方式、检查目录三格，再把这三格分别放宽为任意参数函数、未知值、未知值。
- 本地 Markdown 后端的探针形状同样写法，见 `tests/contract-probe-markdown.ts:45-51`。
- 三处弱化的理由写在探针文件头，见 `tests/contract-probe-github.ts:9-24`：创建操作的返回深层要动后端实现面所以只断存在，开仓库方式的字面量被旧语言加宽成字符串所以静态不断字面量，检查目录是数组还是工厂要另起专票定所以只断存在。
- 开仓库方式的契约形状为网址与文件夹二选一，见 `src/tracker/contract/backend-module.ts:214-219`。
- 检查目录的契约形状为条目数组，见 `src/tracker/contract/backend-module.ts:233-234`。
- 创建操作的契约形状见 `src/tracker/contract/backend-module.ts:165-167`，返回类型为操作集合与房内扩展与只读辅助口的交叉。
- 探针编译用宽松开关，关闭了隐式任意类型的报错，后端文件内部自己的报错另行计数，见 `tests/contract-probe-github.ts:26-28` 与 `tests/verify-contract-types.js:84-93`。
- 宽松开关的基线为 200 条，见 `tests/verify-contract-types.js:84-88`。
- 快照键集合的期望值见 `tests/verify-contract-types.js:102-107`，运行时腿把模块对象的键列出来比对，键集合变了要先确认增减的成员有没有契约覆盖，见 `tests/verify-contract-types.js:490-497`。

## 3. 反面证明现状与缺少的第二条是什么

人话结论：反面证明是指故意把探针里一处签名改错，门禁必须变红，用来证明门禁真的有检查能力。现状是只有一条反面证明，即故意去掉识别函数时类型检查必须失败。缺少的第二条是指开关不一致与目标不一致没有补齐，即探针平时用宽松开关编译，反面证明用严格开关编译，两次编译的目标文件也不完全一致。

人话补充：开关是指传给类型编译器的严格程度选项。目标是指被编译的文件是探针本身还是后端实现。两处不一致会让反面证明的说服力打折，因为证明用的条件与平时用的条件不是同一套。

证据：

- 探针平时编译用宽松开关，见 `tests/verify-contract-types.js:93`，其中关闭了严格模式。
- 反面证明用严格开关编译，见 `tests/verify-contract-types.js:447`，其中开启了严格模式。
- 运行时腿用进程内求值读取模块对象的键、开仓库方式真值、检查目录种类，见 `tests/verify-contract-types.js:473-476`，输出包含键个数、开仓库方式真值、检查目录种类。
- 快照比对断言键集合、真值、种类三者一致，见 `tests/verify-contract-types.js:490-497`。
- 讨论记录承认开关不一致与目标不一致是已知差距，缺少的第二条反面证明就是把这两处对齐，现状见议题 #1026 的收尾评论与 `research/1026-adversarial-claims-verification.md` 的相关章节。

## 4. 创建操作返回深层的三处加宽是什么，为什么今天运行时无害

人话结论：创建操作返回深层的三处加宽是指后端实例的形状在三个深层位置比契约写得宽。第一处是操作结果的成功标志被加宽成布尔值，契约要求成功与失败是二选一的字面量联合。第二处是检查目录在契约里是数组，而 GitHub 后端实际带的是零参数函数，调用一次返回一份新数组。第三处是开仓库方式在契约里是网址与文件夹二选一的字面量，而旧语言文件里的字面量被加宽成字符串。今天运行时无害的原因是调用方枚举与消费方只做分流，即今天没有调用方去调用检查目录，消费开仓库方式的地方只做分支选择，不依赖字面量的编译期收窄。

人话补充：操作结果是指每个操作返回的成功或失败的包装。成功标志是指包装里表示成功的那一格。零参数函数是指不需要传入参数、调用一次返回一份新数组的函数。调用方枚举是指全仓搜索调用位置。消费方只做分流是指使用该值的地方只按取值走不同分支。

证据：

- 探针文件头如实记录创建操作的成功标志被加宽成布尔值，按契约的字面量联合算是不合，见 `tests/contract-probe-github.ts:10-16`。
- 探针文件头如实记录开仓库方式的字面量被加宽成字符串，真值由门禁的运行时腿断，见 `tests/contract-probe-github.ts:17-19`。
- 探针文件头如实记录检查目录的种类差异，数组还是工厂要另起专票定，全仓搜索今天没有任何调用方，真种类由门禁运行时腿如实记录，见 `tests/contract-probe-github.ts:20-24`。
- GitHub 后端的开仓库方式真值为网址，见 `src/tracker/rooms/github/repo.ts:73`，模块装配时原样带上该值，见 `src/tracker/rooms/github/index.ts:218-224`。
- GitHub 后端的检查目录真值为零参数函数，见 `src/tracker/rooms/github/checks.ts:53`，模块装配时原样带上该函数，见 `src/tracker/rooms/github/index.ts:224`。
- 本地 Markdown 后端的开仓库方式真值为文件夹，模块对象里写明该值，见 `src/tracker/rooms/markdown/index.ts:87-153` 的模块装配段。
- 门禁运行时腿如实记录两房的真值，GitHub 房记录为网址与函数，本地房记录为文件夹与缺席，见 `tests/verify-contract-types.js:473-497` 的输出断言。
- 契约里操作结果的成功与失败为二选一，错误种类为封闭集合，见 `src/tracker/contract/results.ts` 与 `src/tracker/contract/index.ts:33-57` 的形状注释。

## 5. 契约外扩展有哪些，各自是谁在用

## 6. 装配残留与调用上下文只读约定未冻结是怎么回事

人话结论：装配残留是指装配层留下来的三处历史痕迹，一是仓库标识补全等待上限没有被装配层传入，二是双命中保护已经退役但装配层还传一个空函数，三是计划存储没有注入所以批量建图的中间态退回进程内存。调用上下文只读约定未冻结是指单次调用上下文的形状已经写成契约，但只读冻结没有落实，调用方每次都是复制一份再加字段，没有任何地方把它冻住。

人话补充：装配层是指把闸、注册表、额度、后端上下文组装成工具依赖的那一层。仓库标识补全等待上限是指补全仓库身份时等待的最长毫秒数。双命中保护是指自动识别出多个后端时的人工确认保护。计划存储是指批量建图时可续跑的中间态的落盘位置。单次调用上下文是指每次调用时带工作区目录、中止信号、调用方、沙箱策略、会话标识的那一份上下文。

证据：

- 仓库标识补全等待上限的注释与缺席默认值见 `src/deck/shell/call-shell.ts:81` 与 `src/deck/shell/call-shell.ts:218`，读的是传入依赖里的该字段，缺席时取 8000 毫秒。
- 双命中保护的装配残留见 `src/deck/registration/host-assemble.ts:93-96` 与 `src/deck/registration/host-assemble.ts:134`，装配层构造一个返回空的保护函数并传给工具。
- 双命中保护已退役的证据为测试断言传了也忽略，见 `tests/verify-957-workspace-writer.js:163-165`，范围基线把该传递记为旧兼容残留，见 `research/1010-deck-contract-surface.md` 的装配表相关行。
- 计划存储没有注入的注释见 `src/host/refresh/wiring.js:305`，工具侧在没有注入时退回按工作区分区的进程内存，见 `src/deck/tools/map-plan-create.ts:127`，文件头写明落盘与缺席两条路，见 `src/deck/tools/map-plan-create.ts:7`。
- 进程级能力的形状见 `src/tracker/contract/contexts.ts:125-149`，单次调用上下文为进程级能力的超集，见 `src/tracker/contract/contexts.ts:156-174`，其中包含工作区目录、中止信号、仓库标识、路径运算、文件服务取值五格。

## 7. 边：契约对外票号，GitHub 原生端点要内部数据库编号，换号责任在谁

人话结论：边是指父子关系与阻塞关系。契约的设置父票与设置阻塞关系对外只认票面编号，即用户在界面上看到的那一串数字。GitHub 原生端点要的是内部数据库编号，即 GitHub 内部给每张票的另一串数字。把票面编号换成内部数据库编号的责任在 GitHub 后端内部，不在契约，也不在工具层。

人话补充：票面编号是指议题列表里显示的数字。内部数据库编号是指原生接口传参时要求的那一串数字。换号是指调用原生接口之前先把票面编号查成内部数据库编号。责任在后端内部的意思是换号的查询与传参都在后端的边实现文件里完成，调用方只传票面编号。

证据：
