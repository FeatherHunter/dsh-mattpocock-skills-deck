#1051 本票
三张票动手前先读的结论源

三张动手票的票面里都写着一句话：「本票边界与讨论结论冲突时，以讨论结论为准，并把冲突写进本票评论。」所以这张票的结论不是参考意见，是它们要遵守的规矩。

「压」这个字是票面里的比喻

票面写的是「契约第一次被真后端压」，听着像试验压力。仓库的术语表 CONTEXT.md 里没有这个词，本文一律换成大白话：契约与真实后端对不上的地方。查清这些地方，再定每一处怎么改。

两个词的准确定义

契约：仓库里描述「一个后端必须实现哪些操作」的类型与数据，真源在 src/tracker/contract/，操作名录共 19 个名字。

真实后端：真正干活的实现——GitHub 那套真的读写远端仓库，本地 Markdown 那套真的读写本地文件。

小提醒：早期的调研文档 research/1010-deck-contract-surface.md 里记的是旧文件路径，那棵目录树已经搬过家。本文引用的都是搬家后的新路径，旧文档只看结论、不看路径。

03

八个事实：契约和真实后端到底哪里对不上

每条都是「人话先说结论，证据指到文件和行号」。行号可以直接打开对应文件核对。

Ⅰ

探针有三处诚实的放宽

探针是一种只做类型检查、不运行代码的检查文件。它检查「后端模块对象长什么样」时，有三格故意放宽了：创建操作只检查「存在、能调用」，不管返回的东西对不对；开仓库方式只检查「存在」，不管值是网址还是文件夹；检查目录只检查「存在」，不管它是数组还是函数。

为什么放宽：后端实现还是旧语言写的，要收紧就得动实现面，而那属于开发票的活，探针票不碰。放宽本身是诚实的，理由写在文件头里。

代价：被放宽的成员如果少了，探针看不见；后端多带了成员，探针永远绿的。多带成员这件事，只能靠门禁在运行时把成员名字列出来、跟一张快照逐字比对才能发现。

证据：放宽定义 tests/contract-probe-github.ts:44-48、tests/contract-probe-markdown.ts:45-51；理由 tests/contract-probe-github.ts:9-24；契约本来的要求 src/tracker/contract/backend-module.ts:214-219（开仓库方式二选一）、:233-234（检查目录是数组）；运行时快照 tests/verify-contract-types.js:102-107 与 :490-497
Ⅱ

反面证明缺了第二条

反面证明是这么个东西：故意把一处签名改错，看门禁会不会变红。会变红，才证明门禁真的有检查能力。现在只有一条——去掉「识别函数」时必须编不过。

缺的那条在于：探针平时是用宽松开关编译的，反面证明却用严格开关编译。证明用的条件和平时用的条件不是同一套，说服力就打了折扣。地图02 关票时把这件事移交过来，要求补上「用探针同款开关，去断那个放宽后的形状」这第二条反面证明。

证据：宽松开关 tests/verify-contract-types.js:93；严格开关 :447；移交原文见 #1051 现有评论 与 research/1026-adversarial-claims-verification.md 的 P2 一节
Ⅲ

创建返回有三处写宽了，但今天不影响运行

后端实例在三个位置比契约写得宽：成功标志被写成「是/否」两个值都能收，契约要求成功与失败是二选一的字面量；检查目录GitHub 实际给的是「调用一次、返回一份新数组」的函数，契约写的是数组；开仓库方式旧代码里被放宽成普通字符串，契约要求「网址」或「文件夹」二选一。

为什么今天不出事：全仓没有任何地方真的去调用那个检查目录；用开仓库方式的地方只做「是网址就开浏览器、是文件夹就开目录」的分流，不靠编译期的严格取值；成功标志在运行时的真值仍然是真或假，宽类型不改变运行结果。

结论：丢的是静态检查的精度，不是运行时的对错。但这件事不能无声无息——要么在开发票里收敛掉，要么在票面写明「故意不收敛，理由是什么」。

证据：三处自述 tests/contract-probe-github.ts:10-24；GitHub 检查目录真值 src/tracker/rooms/github/checks.ts:53；GitHub 开仓库方式真值 src/tracker/rooms/github/repo.ts:73；门禁运行时腿记录真值 tests/verify-contract-types.js:473-497；调用方枚举见 research/1026-adversarial-claims-verification.md 的 P4 一节
Ⅳ

契约之外有四个真实成员

两个后端各带了一些契约 19 个操作名里没有的成员，四个都有真实的调用方，不是死代码：

① 子票列表——按父票取全部子票，唯一调用方是宿主侧「打开地图」那条电话。

证据：操作名录 19 名 src/tracker/contract/operations-catalog.ts:37-57；子票列表 src/tracker/rooms/github/sub-issues.ts:36-44 与 :9-10；权限查询 src/tracker/rooms/github/backend.ts:129-137、调用方 src/deck/tools/context.ts:87-88；配色入口 src/tracker/rooms/markdown/index.ts:148；归一化与解析 src/tracker/rooms/markdown/parse.ts:79；契约承认「创建返回里带房内扩展是有意的」src/tracker/contract/backend-module.ts:159-163
Ⅴ

装配层留了三处历史痕迹

装配层是把闸、注册表、额度、后端上下文组装成工具依赖的那一层。那里留着三处旧痕迹：仓库标识补全的等待上限没有被传进去（代码里写死了缺席时用 8000 毫秒）；双命中保护已经退役，但装配层还在传一个空函数（测试里明确写着「传了也忽略」）；计划存储没有注入，所以批量建图的中间态退回进程内存，重启就丢。

新接口要不要继承这三处，是这张票要定的。

Ⅵ

单次调用的上下文没有冻结

每次工具调后端，都会带上一份「这次调用的上下文」：工作区目录、中止信号、调用方标识、沙箱策略、会话标识。形状已经写进契约了，但只读这件事只是口头约定——每次调用都是复制一份新的再加字段，全仓没有任何地方把它冻住，契约里也没有「只读」的字样。

冻不冻、怎么冻，是这张票要定的。

证据：形状 src/tracker/contract/contexts.ts:125-149 与 :156-174；每次复制一份 src/deck/shell/call-shell.ts:280-288
Ⅶ

边的换号责任在后端内部，不在契约

边指父子关系和阻塞关系。契约和工具层对外只认票面编号——就是你在议题列表里看到的那串数字。但 GitHub 的原生接口要的是内部数据库编号，是另一串数字。

换号的活全在 GitHub 后端内部完成：先查号、再用内部编号调原生接口、出错时降级。工具层只管传票面编号。本地 Markdown 后端不需要换号。

证据：契约签名 src/tracker/contract/index.ts:46-47；工具层只传票面编号 src/deck/shell/edge-landing.ts:153-189；后端内部换号 src/tracker/rooms/github/graph.ts:35-42、:139-142、:272-311；本地房 src/tracker/rooms/markdown/graph.ts:11-28

04

七个板，等你拍

每题给出选项、我的推荐、理由，以及「选另一个会付出的代价」。你回复时可以直接说「Q3 换成 A」，也可以说「先跳过」——跳过的我记下来，不替你猜。

Q1

检查目录：定「数组」还是定「调用一次返回新数组的函数」？

契约写的是数组，GitHub 实现给的是函数。两边必须统一成一种，开发票照做。

A定数组。改实现侧：GitHub 那边把函数改成直接给出数组。
B定函数。改契约：允许「数组或函数」两种写法。
我的推荐：B，把契约改成接受函数

检查链的推进原则是「每次重新求值才算数」。函数每次调用返回一份新数组，正好符合这个语义；反过来把实现改成数组，等于把一份随时可能过期的快照固定在内存里。而且改契约比改实现面的牵连小。

选 A 的代价：GitHub 那边的检查条目要在模块装配时就算好并冻结，环境变化后需要重启才能刷新。
Q2

另两处写宽（成功标志、开仓库方式）放进哪张开发票？

成功标志收回「成功与失败二选一」，开仓库方式收回「网址与文件夹二选一」。这项活归读路径 #1052、写路径 #1053，还是另立一张跟随任务？

A归 #1052 读路径，随读路径一起收。
B归 #1053 写路径。
C另立一张跟随任务，本图四张票变五张。
我的推荐：B，归 #1053 写路径

成功标志是「创建操作」的返回值问题，开仓库方式是模块装配时透传的问题——两件都不属于「只读查询」。#1052 那张票的验收标准写的是「读相关的回执与今天逐字一致」，往里塞类型收敛会破坏它原本干净的边界。

选 A 的代价：#1052 的验收口径要跟着改，否则「逐字一致」和「类型收敛」两件事会互相打架。
Q3

第二条反面证明归谁做，按移交原文的做法做吗？

地图02 移交时给了具体做法：把放宽后的形状从探针文件里导出，门禁里加一条「用探针同款宽松开关、去断这个形状」的反面证明。

A归本图（08），按移交原文的做法做。
B退回契约图去做，本票只写下「欠一条」。
C归本图，但换一种做法（比如把探针开关直接对齐成严格）。
我的推荐：A，归本图并按原文做法做

这是「契约第一次被真实后端检验」的门面。如果这里不把证明补上，开发票里做的每一处收敛都没有门禁守着，等于白收敛。按原文做法最省事，因为做法已经写死、不需要重新论证。

选 C 的代价：把探针改成严格开关会让旧语言实现当场爆出一批类型错误，等于把实现面的活提前塞进探针，与本图「先讨论清楚再动手」的顺序反了。
Q4

四个契约外成员：哪些升进契约，哪些永远留在房里？

子票列表、仓库权限查询、配色文件放置入口、归一化与解析——四组都有真实调用方。

A全部升进契约，19 个操作名扩成更多。
B四个都留房里，只在契约注释里写明它们是自愿扩展。
C分开处理：需要跨后端统一语义的升，只服务某一个后端的留。
我的推荐：C，分开处理

逐项看：仓库权限查询留房里——本地 Markdown 后端根本没有远端权限这回事，升进契约等于逼它长一个假实现；子票列表留房里——它是「打开地图」那条电话的实现细节，操作名录里已经写明这类读路径细节不进名录；配色文件放置入口保持现状——契约里本来就有它的形状；归一化与解析永远留本地房内部——它们是文件格式的解析工具，不是后端对外能力。

选 A 的代价：契约会为「只有某一个后端才有的能力」承担形状义务，Markdown 房被迫长出四个空壳，后面每个新后端都要跟着长。
Q5

装配层三处历史痕迹：删、补，还是继承？

等待上限没人传、双命中保护已退役还在传空函数、计划存储没注入导致中间态退回内存。

A三处一起在这张图收掉：补上等待上限、删掉空函数、把计划存储的注入另立一张跟随任务。
B三处都留着，新接口原样继承，等以后再清。
C只删退役的空函数，另两处原样保留。
我的推荐：A

三处的性质不同，处理也不同：退役的空函数该删——测试已经证明「传了也忽略」，新接口继续传就是骗后人；等待上限该补传入方——它现在是「文档写了、消费方读了、接线从来没给」的半截状态，不补就会一直靠 8000 毫秒的兜底；计划存储的注入是独立的一件事（批量建图的落盘），塞进这三张转写票会撑破它们的边界，另立跟随任务最干净。

选 B 的代价：三处都是「没人知道为什么还在」的痕迹，新接口继承之后，后人更不敢删。
Q6

单次调用的上下文：冻住，还是只加「只读」类型？

现状是每次调用复制一份新的、彼此不共享，但没有冻结，契约里也没写「只读」。

A类型上标只读，运行时也真冻住（改动就报错）。
B只在类型上标只读，运行时保持现状。
C维持现状，什么都不加。
我的推荐：B，类型标只读，运行时不冻

「每次复制一份」已经保证了调用之间不会互相改写，运行时冻结并不会多挡住一类真实故障，反而会在开发期制造一堆「不能赋值」的报错噪音。类型上标只读成本极低、收益明确：写代码的人和 AI 都不会再去改它。真有人踩到互相改写，再补运行时冻结不迟。

选 A 的代价：需要逐个排查现有代码里所有对这份上下文的写操作，属于本票边界之外的实现改动。
Q7

边的换号：把「责任在后端内部」定死吗？

契约与工具层永远只传票面编号，把票面编号换成 GitHub 内部数据库编号的活永远在 GitHub 后端内部。

A定死，写进结论，开发票不用再议。
B不定死，留给开发票按实际情况处理。
我的推荐：A，定死

这已经是代码今天的样子（换号查询、传参、降级三段都在后端内部完成）。定下来不是新增约束，只是把现状写成结论——省掉开发票里的一次重复论证，也让「工具层只认票面编号」这条边界有明文可依。

选 B 的代价：开发票可能各自理解不同，出现「工具层顺手换了一次号」这种越界写法。

术语小抄

词一句话意思
契约仓库里描述「一个后端必须实现哪些操作」的类型与数据，操作名录 19 个名字。

  6. 对抗式审查——对本次执行的所有任务做一次对抗式审查，确认无误后关闭 #1051。
