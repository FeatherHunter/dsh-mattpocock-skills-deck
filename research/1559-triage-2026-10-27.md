# #1559 分流诊断：deck_issue_list 为什么整笔失败（2026-10-27）

调查范围：票 #1559 正文（无评论；标签 `bug`、`needs-triage`）；仓库 main（调查时 HEAD 从 `6f823f84` 移到 `2bfe6b59`，期间其他会话在提交，版本号仍是 `1.9.0-beta.26`）；`src/deck/tools/issue-list.ts`、`src/deck/tools/tracker-session.ts`、`src/deck/registration/agent-row.ts`；相关门禁与金标准回执；本机 DSH 宿主包 `D:\DeepseekHarness\resources\app.asar` 里接收工具返回值的那段校验；本机安装的插件（`1.9.0-beta.25`，含编译后的同一段代码）；提交 `4f5ba7aa` 及其改动；相邻票 #1553、#1556–#1562；`.out-of-scope/`；`research/` 下既有笔记；以及 2026-10-27 凌晨在本机对 `deck_issue_list` 的现场调用。本次只做诊断，没有改业务代码、没有开始实施。

## 一句话结论

`deck_issue_list` 在“后端正常回了列表”这一支把 `data` 里的 `fallback` 与 `fallbackReason` 两个键写成了 `undefined`；DSH 宿主收工具返回值时要求它必须是“无损 JSON”，碰到 `undefined` 就整笔判成 `invalid output: value is not lossless JSON`。这是提交 `4f5ba7aa`（2026-10-26 13:13，给 deck 工具补操作编号与降级原因）引入的回归：报告时本机插件是 `1.9.0-beta.25`（已含该提交），main 到 `1.9.0-beta.26` 仍是同一写法，没有修复。

## 错误从哪来（代码链路）

- 仓库这一侧：返回值在 `src/deck/tools/issue-list.ts:239-248` 拼装，关键是 `:243`：

  ```ts
  data: { total, returned: sliced.length, truncated, issues: sliced,
    fallback: backendFallback ? 'rest' : undefined,
    fallbackReason: backendFallback ? (fallbackReason || 'other') : undefined,
    opId: opId || undefined },
  ```

- 接线层原样并进信封、不清洗：`src/deck/tools/tracker-session.ts:375-460` 的 `callDeckSession` 在 `:450` 执行 `out.data = v.data !== undefined ? v.data : null`。
- 插件把整份信封交回 DSH 宿主（工具执行入口见 `src/deck/registration/agent-row.ts:314-380`）。宿主包 `app.asar` 里 `snapshotToolValue` 调 `snapshotJsonValue`，后者即 `walkJsonValue(value, true)`：对象自己的可枚举键会逐个访问；如果某个值是 `undefined`，会落到 `typeof current !== "object"` 这一支并直接返回 `void 0`。于是 `snapshotJsonValue` 返回 `undefined`，`snapshotToolValue` 抛 `ToolOutputError(toolName, ['value is not lossless JSON'])`，报错原文与票面逐字相同。
- 什么时候必炸：后端主路正常回列表时 `backendFallback` 为假，`fallback` 与 `fallbackReason` 两个键存在、值都是 `undefined`，必被拒收。什么时候能过：这次列表走了 REST 降级（`fallback = 'rest'`，`fallbackReason` 也有值）时，这两个键不再为空，同一道检查就放过。也就是说这条故障看起来“时好时坏”，实际只取决于有没有降级。

## 现场复现（2026-10-27 凌晨，本机）

- 直接调用 `deck_issue_list`，参数 `{state:"open", limit:1}`，连续 3 次都整笔失败，报文是 `tool "deck_issue_list" returned invalid output: value is not lossless JSON`，与报告人一致。
- 早先另一次 `{state:"all", limit:5}` 回到 `status:"ok"`（“共 500 行符合”）；按代码，只有走了 REST 降级那一支的三个键才都有值、能过同一道检查，这个成功与上面的解释相容。那次没有留下回执的 `notes` 供核对，所以只当相容解释，不当证据。
- 报告人给的复现步骤（GitHub 后端，调用 `deck_issue_list`）成立。触发条件不是某个参数组合，而是“后端正常回了列表、且没走 REST 降级”；参数只决定查什么，缺省参数同样触发。

## 为什么既有门禁全是绿的

- `tests/verify-1106-deck-surface.ts` 已经用本地 Markdown 后端把九个工具的“成功”支各跑了一遍（“列票：成功”在点数表 `POINTS` 里），但它只断言信封字段清单、状态、原因码与记账数；它直接调 `entry.run`，不经过宿主那道无损 JSON 校验，也没有 JSON 往返断言。本次现场复跑：187 项全过、退出码 0，而同一台机器上调真工具就炸。
- 金标准回执 `tests/tracker-contract/fixtures/golden-receipts/03-deck_issue_list.golden.json:25-56` 是序列化后的文件：`opId` 在（`"1700000000000-3"`），`fallback` / `fallbackReason` 两个键根本不在文件里（`undefined` 被 `JSON.stringify` 丢掉了）。也就是说“序列化后的正确形状”早就躺在门禁里，但没有谁拿它反过来校验运行时的原对象。
- 既有带 JSON 往返断言的只有渲染层那一扇 `tests/verify-deck-render-detail.ts:137-170`（#1273/#1303 那批），它测的是渲染函数，不是工具原值。
- 票面验收第 3 条要的“所有 deck 工具返回值必须能 JSON 往返”这道门禁目前不存在：`tests/` 里搜 `JSON.parse(JSON.stringify` 只命中渲染、配置等别的用途，搜 `lossless` 没有工具输出相关的命中。

## 对抗式复核（2026-10-27，第一性原理重审）

### 把“推断”补成“实测”

- 用仓库真实的工具工厂 + 真实本地 Markdown 后端（照 `tests/verify-deck-tools.ts` 的夹具方式）跑了一次 `deck_issue_list` 成功路径探针（临时脚本，不入库）：回执 `status:"ok"`，`data` 的自有键里 `fallback` 与 `fallbackReason` **存在且值为 `undefined`**；对整份回执做 `assert.deepStrictEqual(JSON.parse(JSON.stringify(r)), r)` 失败。这与宿主 `walkJsonValue` 的拒收判据对得上，原结论从推断升级为实测。
- 九个工具用同一套夹具各跑一遍：只有 `deck_issue_list` 的回执带 `undefined`（`data.fallback`、`data.fallbackReason`），其余八份都能过同样的检查。范围结论（“目前只有列票坏”）也从静态阅读升级为实测；局限是只覆盖代表性成功路径，不是所有分支与三种后端的所有组合。
- 现场调用 3/3 整笔失败、以及“REST 降级支能过”的解释仍成立（降级时这两个键都有值）。

### 重审修法：只修源头，但理由要换

- 结论不变：**只在源头修**（缺省的键不出现、`opId` 改成恒为字符串）。但支撑它的第一性理由是：**宿主的无损 JSON 规则是唯一一份运输契约**。在插件出口再做一份清洗/校验，只有三种结局：照抄宿主规则（多一份会漂移的契约）、写近似规则（有盲区）、或者做 `JSON.stringify→parse` 影像化（数据会悄悄变样，而且门禁从此看不见这类错误）。仓库的保证机制是“提交前本地全链”，所以该补的是门禁，不是运行期清洗。
- 题面验收第 2 条（任何参数组合都不再 invalid output）对 `deck_issue_list` 可以结构性证明：`data` 形状固定，只有“降级/不降级”两支；修后两支都不出现 `undefined`。另外，`opId: opId || undefined` 本身就是一处同类潜在写法（若 `opId` 为空会再制造一个 `undefined`），应一并改成 `String(opId || '')`。

### 重审门禁：题面点名的检查方法有盲区

- 实测 `JSON.parse(JSON.stringify(v))` 等值检查会漏掉**不可枚举自有属性**（宿主 `walkJsonValue` 会拒收，而往返比较相等）；`BigInt`、循环引用、顶层 `undefined` 在往返这一步会直接抛。照题面字面写“`parse(stringify(v))` 与 `v` 等值”会得到一扇有盲区的门禁。
- 建议的检查器判据照宿主 `walkJsonValue` 写：只允许 null / 布尔 / 字符串 / 有限数（不是 -0）/ 纯对象与数组；对象的自有键必须全是可枚举字符串键；数组不许稀疏、不许额外自有属性；不许循环。题面要求的往返等值断言照留，作为显式对照。
- 落点：新开 `tests/verify-1559-deck-output-lossless.ts`，用本地 Markdown 夹具跑九个工具的真实成功路径，逐份回执过检查器；再放检查器自己的“坏值矩阵”单测与一条“旧写法必红”的回归。另外建议把同一行检查挂进既有 `tests/verify-deck-tools.ts` 的 `callTool()` 与 `tests/verify-1106-deck-surface.ts` 的 `run()`（各一行），覆盖它们已经跑到的几十次调用，而不只是新门禁的九条正例。

### 修订后的推荐答案

- **Q1：A（只修源头）**，不加运行期兜底/清洗。若要做“任何情况下都不再整笔失败”的可用性兜底，那是一次会改变所有工具失败语义的契约变更，应另开票，且必须显式记录，不许静默。
- **Q2：新建一扇门禁**，但检查器按上面“宿主规则”写，并挂到两个既有九工具门禁的中心调用点；不要只写往返等值。
- **Q3：A（缺省不出现）**，不改 `null`：金标准本来就按“缺省不出现”生成、仓里没有消费方读这两个键，`null` 只会多一次金标准重建。
