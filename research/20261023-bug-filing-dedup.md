# 新增BUG单为什么还是重复建单：一次只读调查

调查时间：2026-10-23 晚。仓库 FeatherHunter/dsh-mattpocock-skills-deck，后端 GitHub。
调查方式：读源码与配置、用 `gh` 与 `deck_issue_list` 实数核对、抽读相关票的正文。没有改代码，没有跑测试。

**一句话结论：注入文本里的「## 查历史」没有丢，它从 v7 起就在，v12 还在，而且被门禁逐字钉死；问题出在它拿到的那份清单本身就是残缺的——列表默认只看 open，后端又是「先取 500 条再在内存里筛」，已关闭的 1304 张票里有 858 张根本进不了 AI 的视野；同时这段文字自己的裁决规则写的是「拿不准就新建、默认关联不关闭」，于是「看见了也不确定」的情况天然倾向再建一张。只改措辞解决不了，改 prompt 这条路此前已经走过五轮，其中 #882 就是这次同一个诉求。**

下面七节对应七个调查问题，每节先给结论，再给证据。文件路径都带行号，票都带编号。

## 1. 面板按钮到底注入了什么文本

**结论：最终注入的文本只有两段——`config/prompts/ticket-creation.yaml` 里 `newBugWayfinder` 的正文（中文版 6-33 行，版本号 12），加上同文件 `newBugFields` 的四字段片段（153-171 行）。两段直接拼接，中间没有别的模板，也不经过 `bodyFormat`。** 「## 查历史」确实在这一版正文里（22-25 行），不是漏了。

按钮到文本的接线有三处，两条入口最后落到同一个函数：

- 面板「+ 新增BUG单」：`src/client/views/shared/Tabs.ts:98`，点击后调 `openTextInNewSession(s, newBugWayfinderText(s), newSessionTitleNew('bug'))`，埋点 `panel.newbug`。
- 状态栏 BUG 悬停菜单「新增」：`src/client/statusbar/StatusBar.ts:409`，同一句调用，埋点 `status.menu.bug.new`。
- 拼装：`src/client/kernel/router.ts:204`：

  ```ts
  export const newBugWayfinderText = (st: any): string => promptText('newBugWayfinder', { repo: repoUrlFor(st) }) + NEW_BUG_FIELDS_BODY();
  ```

  第 201-203 行的注释说明第二段自带开头两个换行，所以拼接处不会粘在一起。

- 四字段片段：`src/client/kernel/prompts.ts:370` 的 `NEW_BUG_FIELDS_BODY` 直接取 `promptFragment('newBugFields')`，内容在 yaml 153-171 行。

`bodyFormat` 不在这条链路上：全仓搜索只命中 `src/client/kernel/prompts-backend.ts:4` 与 `:16`，那是后端声明的 `prompts.subIssue / bodyFormat`，给 wayfinder 建图用的，和这个按钮无关。

「## 查历史」四行的原文（yaml 22-25 行，一字未改）：

```text
## 查历史

- [ ] 从实际抽 2 到 3 个关键词，按当前后端方式搜已打开与已关闭的单子（优先 deck_ 工具），初筛看前 20 条标题，疑似点开正文
- [ ] 撞到疑似再用 /research 深查，结论写回新单正文
- [ ] 新增则建；重复则复用不重建，写明原单号与理由；回归则注明原单号；拿不准则新建并关联疑似单标待确认；默认关联不关闭
```

同一段正文里还有：「## 澄清」13-14 行、「## 调查（建议先查后问）」16-20 行、「## 自查」27-28 行、「## 工具」30-33 行；标签要求在第 10 行（必带 `bug`，未诊断再带 `needs-triage`，并区分远端原生标签与本地 `Labels` 行）。

这句话不是「大概写了」，而是被门禁钉死的。`tests/verify-bug-entry.ts` 逐字断言：

| 行号 | 断言 |
| --- | --- |
| 112 | 中文正文必须含 `## 查历史` |
| 115 | 必须含 `前 20 条标题` |
| 116 | 必须含 `回归则注明原单号` |
| 117 | 必须含 `拿不准` |
| 118 | 必须含 `默认关联不关闭` |
| 120/123/124 | 英文版必须含 `## Check history`、`top 20 titles`、`default link, never close` |
| 163-164 | 四字段片段必须以两个换行开头 |
| 246 | `openTextInNewSession` 的接线至少两处（面板与状态栏） |
| 272 | 拼接必须正好是 `promptText('newBugWayfinder', …) + NEW_BUG_FIELDS_BODY()` |

所以「AI 不知道要查历史」这个假设可以排除；要改措辞，必须先动这扇门禁。

## 2. AI 建单时能用的数据面

**结论：AI 调用 `deck_issue_list` 时，看到的库比真实的库小得多，而且小在哪里它自己也不完全知道。三层叠加：① 不传 state 就只看 open；② 后端把 open 与 closed 按「最近更新」倒序一起取，取到 500 条就停，再在内存里按状态筛——于是越老的开放票越容易被一起截掉；③ 截断这件事只写在回执的提示行里，数据字段里的 `truncated` 只表示「被 limit 截断」，不表示「后端没取全」。**

### 2.1 工具这一侧

- 状态缺省值：`src/deck/tools/issue-list.ts:128-129`。只认 `closed` / `all` 两个值，其它（含不传）一律回落成 `open`。
- `query` 的匹配方式：同文件 205-207 行，把标题、换行、正文拼成一串，整体转小写后做**子串**匹配。大小写不敏感；包含正文；不是分词，也不是相似度。
- 过滤放在内存：165-168 行先拼 `filter.state`，再交给 `t.list`；标签、认领人、query 都在内存里再过一遍（189-208 行）。
- `limit` 上限 200，缺省 50（135 行）。
- `truncated` 的含义：224 行 `truncated = total > sliced.length`，只说明「结果被 limit 切过」。后端自己的截断只进 `notes`（约 234 行），原话是「后端这次只翻到自己的上限就停了（工单 500 条、拉取请求 1000 条），这份清单可能不全：收窄过滤再查一次」。

### 2.2 后端这一侧

- `src/tracker/rooms/github/queries.ts:37` 的注释直接写着「filter 在内存完成」；38-45 行的 `LIST_QUERY` 把 `states:[OPEN,CLOSED]` 写死，排序是 `UPDATED_AT DESC`，不接受把状态下推到查询里。
- `src/tracker/rooms/github/issues.ts:206-231` 是分页循环，230 行 `if (all.length >= 500) { issuesTruncated = true; break }`；拉取请求另走一路（232-257 行），到 1000 条才停；两路并进同一份清单。
- 状态下推缺失的后果在 147-172 行的 `applyIssueFilter`：它是在「已经截断的那 500 条」上再筛 `state === want`。
- 这不是没人提醒过。`docs/design/677-issue-pool-completeness-spec.md:104` 的表格里明确写着：「`list({state:'open'})` 必须把状态下推——查询里写 `states:[OPEN]`，不许『先取一页再内存过滤』——今天 500 条窗口一截，旧开放票就被过滤没了」。106 行说 500 上限可以保留，但后果必须被说出来（`deck.partial`）。今天的代码没做到这一条。

## 3. 真实的重复例子

**结论：能坐实「几乎一样」的重复有两类，但没有一类是「AI 完全没看见旧单」：一类是工具重试造出来的同名子票（4 对，标题逐字相同，创建时间只差几分钟）；一类是同症状 BUG 由人隔天再报（#1395 与 #1436），而第二张其实读到了第一张，只是判断成「同源不同症」，最后被报告人推翻。真正「看不见」的，是 500 条窗口外的 7 张 open 票和 858 张已关闭票。**

### 3.1 工具重试造出的同名子票（4 对，与 prompt 无关）

| 对 | 标题（逐字相同） | 状态与时间 |
| --- | --- | --- |
| #1121 / #1127 | 红门禁治理：隔离名单带票号与期限，每扇门禁写明守护的票号 | closed / closed，均 2026-10-13，20:18:52 与 20:22:15 |
| #1122 / #1125 | 门禁自动发现与分阶段顺序：名单从 package.json 的长串改成目录约定加显式排除表 | closed / **open**，20:18:52 与 20:21:26 |
| #1123 / #1128 | 等待口收敛成一个共用件：九份工具的超时钳制与壳里五处等待合成一处 | closed / closed，20:18:52 与 20:22:40 |
| #1124 / #1126 | 归属从依赖图推导：手写声明降级为覆盖，生成物退出「必须入库」 | closed / closed，20:18:52 与 20:21:53 |

第一批四张是在同一秒建出来的（20:18:52），三分钟后第二批四张又建了一遍。两批的幂等锚不同（#1122 是 `deck-plan-verify-chain-shape-2026-10-14-child-discover`，#1125 是 `deck-plan-1119-discover`）。这正对上 #1245 正文的记录：`deck_map_plan_create` 超时后重跑换了新锚，多建了内容相同的子票。也就是说，这 4 对重复与「新增BUG单」的提示词无关，是建计划工具在超时重试时换了身份。

### 3.2 同症状 BUG 隔天再报：#1395 与 #1436

- #1395（open，2026-10-22 13:10）「BUG：重启 DSH 或长时间运行后，胶囊状态栏的工作路线入口偶发整段消失，工作路线存档里却有本会话记录」，带 `bug` + `needs-triage`，四字段齐全，锚 `bug-capsule-workroute-entry-missing-b111bd35-20261022`。
- #1436（open，2026-10-23 09:17）「BUG：打开会话时胶囊状态栏的工作路线入口不立刻出现，要等一阵才显示或干脆不显示」，同样带 `bug` + `needs-triage`，四字段齐全，锚 `bug-capsule-workroute-first-open-latency-20261023`。

看起来是标准的「隔一天又报一次」，但 #1436 的正文里有大段对 #1395 的引用，说明它查到了：

> 同症状既有票：暂未找到。最接近的是 #1395……与本单共享「水合剥表 → 缺表 → 补拉」同一段链路；区别是本单的落点是「第一次打开要等一阵/等不到」，#1395 的落点是「显示过之后消失」。

> 处理方式：新建本单；#1395 经复核判定为「同源不同症，不是重复单」……默认互相关联、不合并、不关闭；已在 #1395 留下这条结论评论。

后来报告人补了一句「#1395 也是这个问题」，同一条正文的后面又追加：

> 报告人本轮补充：**#1395 也是这个问题**。……本单作为总修……验证通过前该单保持打开，通过后按重复关闭并写明指向本单。

所以这一对的教训不是「看不见」，而是：**看见了，凭症状与链路的差别判成两张票；判断本身错了，而当时的规则允许这种判断，还默认「不合并、不关闭」。**

### 3.3 对照组：查到了、也关联了

- #995（open，2026-10-10）标题里就写着「（#891 同类根因）」，正文引 #891，两张都 open，但关联关系是明确的。
- #1435（open，2026-10-23）正文有「与既有票的关系（不是重复）」一节，逐条区分 #1418、#1006、#998——这三张它都读到了。

### 3.4 「承接」造成的两张 open 票

- #1008（open，2026-10-10）「落地：闸的裁决日志补上『当时连续失败几次、上一笔真失败是谁』」。
- #1218（open，2026-10-16）「承接#1008：闸裁决日志补连续失败数与上一笔真失败」，正文开头「承接 #1008（转，2026-10-16 收口结账）……本票把那件活接过来」。
- #1001（open，2026-10-10）「清理 `gh:labels` 死项……」与 #1223（open，2026-10-16）「承接#1001：清理gh:labels死项」同理。

这两对不是「没查到」，是「把活转给新票、旧票不关」。从查重角度看，它们仍然是两张 open 票在说同一件事；从工作流角度看，缺的是一条「承接后旧票怎么收口」的规则。注入文本里没有这条规则，工具侧也没有。

### 3.5 小结

在最近这批 BUG 票里，我没有找到「AI 完全没看见旧单、闭着眼建了第二张」的干净例子；找到的是三种别的形态：工具重试换锚（3.1）、看见但判错且规则允许不合并（3.2）、承接后旧票不收口（3.4）。**视野的缺口是真实的，但它落在窗口外的 7 张 open 与 858 张 closed 上；而这次的导火索恰好不在缺口里——#1395 是被看见的。**

## 5. 工具侧查重的先例

**结论：`deck_issue_create` 没有任何「建前查相似票」的动作；它只有一道幂等锚——同会话 + 同标题 + 同标签，5 分钟内重复调用复用同一张票。这能挡住「同一次会话里手抖点了两次」，挡不住「人隔一天又报一次」，也挡不住「另一个会话报了同一件事」。全仓没有按标题查重的实现。**

- `src/deck/tools/issue-create.ts:167`：

  ```ts
  const anchor = a.idempotencyKey ? String(a.idempotencyKey) : anchorKeyFor({ tool: 'deck_issue_create', sessionId: s.sessionId, workspaceKey: s.workspaceKey, title: title, labels: ensured.labels, now: now })
  ```

  锚的实现真源在 `src/deck/rules/anchor.ts:84`（`src/deck/shell/minimal-spec.ts:54` 是壳里的同名入口）。

- 回执自己把边界说清楚了（`issue-create.ts:235` 附近）：「这次用的是自动幂等锚（同会话 + 同标题 + 同标签，5 分钟窗口内重复调用复用同一张票）」。11 行的注释同义。
- 有先例可借的是 `deck_map_plan_create`：`src/deck/tools/map-plan-create.ts:239` 用 `'auto-' + anchorKeyFor({ … now: 0 })`，把时间窗固定成 0，所以同一个标题无论隔多久重跑都落在同一个计划上；236 行的注释写明理由：「自动计划标识必须稳定（不带时间窗），否则重试跨过 5 分钟窗口就会变成新计划、按新锚建重复票」——这就是 #1245 的教训。但它仍然是「查自己上次建的那张」，不是「查库里有没有相似的票」。
- 全仓搜索「同标题 / 标题相同 / already exists」只命中三处：`issue-create.ts:235` 的注释、`blocked-by-write.ts:302`（错误文本去重）、`init-project-error-kinds.ts:40` 与 `github/index.ts:179`（仓库已存在）。没有任何一处按标题查库。
- 顺手发现一处可疑代码（未实测，列为线索）：`src/deck/tools/map-plan-resume.ts:86` 写 `tracker.list(repo, { state: 'all' }, opCtx)`，而契约注释 `src/tracker/contract/inputs.ts:32-36` 明确说「`state: 'all'` 这种写法在列出票上会把所有行都筛掉，不要用它表达『全部』——省略才是全部」。按这段话，这一行列不出任何票；如果续跑今天还能用，说明中间有人特判过 `'all'`，值得单独确认。

**回答「工具侧加一道查重闸今天有没有可复用的做法」**：有半件——固定窗口的幂等锚（map-plan-create 的 `now: 0` 写法）可以复用，用来防「同一次操作重试」；但没有「按标题或关键词查相似票并提示」的现成实现，这一层要从零写。

## 6. 注入侧加数据的可行性（只查事实）

**结论：点击那一刻，客户端手里已经有工单池，同步就能取「当前池子里的 open BUG / needs-triage 标题清单」，不需要新发请求；但这份池子就是后端那份被 500 条窗口截过的清单（85/93），而且完全不含已关闭票。要更全，必须新发请求，而今天的 `deck_issue_list` 也只能给到 88 行——换条路请求，拿到的还是同一份残缺数据。**

- `newBugWayfinderText` 是同步函数（`router.ts:204`），文本在点击那一刻就定型；`openTextInNewSession`（`src/client/kernel/api-new-session.ts:45`）内部是 then 链，但函数体本身同步返回，因此「点击时把池子里的标题拼进文本」在时序上做得到。
- 草稿的传递方式是 `incomingDraft`：`api-new-session.ts:226/230/233/316` 把文本写进目标会话自己的 store；`src/client/kernel/api-naming.ts:142-174` 的 `mountDraft` 也是写 `storeOf(sid).incomingDraft = text`。新会话界面取一次就清空。全仓没有 `pendingDraft` 这个名字。
- 池子的来源：`src/client/kernel/store-derived.ts:162` 的 `openIssuesOf` 从 `st.snapshot.issues` 里筛 `state !== 'CLOSED'`；`src/client/views/ListTab.ts:188` 用 `ticketRowsOf(...)` 把 `issues` 与 `maps[].tickets` 拼在一起。规格 `docs/design/677-issue-pool-completeness-spec.md:37` 把这份集合定义为「池子」，148 行说明池子被截断时置 `deck.partial`。
- 权威计数已经单独存在：`store-derived.ts:151-158` 的 `deckCountsOf` 读 `st.snapshot.deck.counts`，那是后端自己数的全量（open/closed/total），不受 500 条窗口影响。

所以事实是：**加「池子里的标题」零成本，但加进去的是同一份看不见 7 张 open、看不见 858 张 closed 的清单；加「全量标题」必须新请求，而今天的后端给不出全量。** 这两件事要分开谈，不能把「注入时带上清单」当成「AI 就能看见全库」。

## 7. 仓库约定里与建单/查重有关的条款

**结论：约定只规定「用哪些工具、带哪些标签、正文怎么写」，没有一条要求建单前查重；唯一相关的是「工具回执会如实说这份清单可能不全」，而那句话今天只出现在提示行里。**

- `docs/agents/issue-tracker.md:7`：「这个仓库的票，用插件自带的工具来读写，不要手敲跟踪器命令。」——所以「用 `gh issue list` 搜全库」本身就违背约定，AI 只能走 `deck_` 工具。
- 同文件 10-14 行：工具回执分三段，其中「本次调用的提示」是「工具对这次拿得全不全的如实警告」，并说「总量超过上限时压掉的是尾部条目并在原地写明『还有几项未带回』」。这是既有设计，缺的是把它抬到能让调用方停下来的位置。
- 同文件 115-123 行：三枚必备标签 `bug` / `needs-triage` / `wayfinder:grilling`，建票时由 `deck_issue_create` 一并补上。
- `docs/agents/triage-labels.md:27-33`：同一套必备标签的另一份说明；45 行的表只讲标签含义，没有查重流程。
- 在 `docs/agents` 下搜「查重 / 重复 / 相似 / 撞」，命中的全是无关句（验证链不重复跑、并行会话不重复构建之类）。**仓库层面没有「建单前先查重」的成文规则。**

## 对讨论最关键的五条事实

1. **「## 查历史」不是漏了。** 它在 v12 里（`config/prompts/ticket-creation.yaml:22-25`），而且被 `tests/verify-bug-entry.ts:112-124` 逐字钉死；这个 prompt 为同一个诉求已经改过（#882，v7）。
2. **它拿到的清单是残缺的。** `deck_issue_list` 默认 `state:'open'`（`issue-list.ts:128-129`），后端先取 500 条再内存筛（`issues.ts:230` + `queries.ts:40`）。实测 open 只看见 85/92，closed 只看见 446/1304；7 张 open 票与 858 张 closed 票对 AI 不可见。
3. **规格 #677 第 104 行早就写明「状态下推」，今天没做。** `queries.ts:40` 仍是 `states:[OPEN,CLOSED]`。这不是 prompt 能修的；不修它，再好的查重话术也只能在半份库上工作。
4. **注入文本自己的裁决规则偏向新建。**「拿不准则新建并关联疑似单标待确认；默认关联不关闭」（yaml:25）。#1436 就是照这条建的，而它其实读到了 #1395——看见了、判成「同源不同症」，直到报告人说「这也是这个问题」才改口。
5. **工具侧只有 5 分钟幂等锚，没有相似票查询。** 同名重复的 4 对子票（#1121/#1127、#1122/#1125、#1123/#1128、#1124/#1126）来自建计划工具超时重试换锚（#1245 有记录），与这个按钮的提示词无关；「隔天再报」这一类，今天没有任何一道闸。
