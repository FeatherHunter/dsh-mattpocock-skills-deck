## 二、票面两个数字的核实

**返回体为什么能到 15KB。** 当前一份缺省回执同时装：整篇正文（`data.ticket.body`）、再一份前 2000 字摘要（`data.excerpt`）、最多 50 条评论正文（`data.comments`），再加标签、URL、关系与落点字段。渲染层还有两道兜底上限：单个字符串 8000 字符、整份明细 60000 字符（`src/deck/registration/register-options.ts:117-118`），所以最坏一份回执能到六万字符量级。

本仓一张规格票即可量：票 #1259《地图14规格单》正文 9,702 字符、2 条评论共 1,770 字符（`gh issue view 1259 --json body,comments`）。正文本身已超过单串 8000 的上限，实际会截到 8000 再加截断说明；加上 2000 字摘要与 1,770 字评论，按字段折算已是 12KB 量级，讨论多几条就是票面说的 15KB+。**这条成立。**

**「额度花掉 6 点」不是返回体造成的。** 6 点是本地账本按「读票 + 读反向阻塞边」两次后端调用记的固定价（`src/refresh/kernel/tool-call-budget.ts:88-104` 的定价表：固定开销 3 点 + 读一张票 3 点）。本次分诊调用 `deck_issue_get 1562` 的活回执也印证：`estimated 6 点 / 3 条请求`，`actual 2 条请求 / 6 点`。thin 之后这两个调用还在，账不会变成 3 点；它省的是模型上下文（以及渲染层 60,000 字符上限的压力），不是 GitHub 额度。真要省网络额度，得另立票改查询片段（正文仍必须完整取回，才能做摘要与进度/原话解析）。

一句话给实施票：**这是「省上下文」的改动，别按「省额度」验收。**

## 三、边界：不能重演 #809 的静默降级

`deck_issue_patch` 的 `body` 是「新的正文」，一次整份替换（`src/deck/tools/issue-patch-definition.ts:22`；`tests/verify-1091-original-words.ts` 第⑧组实测整份改写）。#809 正文里记过一次真实事故：没读到全文，把一张 3,922 字的票覆盖成空正文，靠临时副本恢复。

默认 thin 之后，AI 只看摘要就整份替换正文的风险会明显变大。所以实现时必须同时做两件事，不是可选项：

1. thin 回执的摘要与 `notes` 里明写「正文这次只给了摘要/前 N 字；改正文前先传 detail:'full' 读全文」；
2. `docs/agents/issue-tracker.md` 里把这条约定写清楚（:10-14 讲回执三段与「要更小就调参数」，:139 现在还写着「读那张票（连同它的评论与标签）」，默认不再带评论后这句必须改）。

## 八、对抗式复核与最终方案（2026-10-27 上午，本节取代第七节）

> 维护者 2026-10-27T10:52 回复「按照你推荐的来」，确认按本节方案执行并把票转 ready-for-agent。

### 1. 上一轮漏掉的三件事实

- **今天所谓「全文」本来就是截断的。** 用真实的详情渲染函数实测：9,702 字正文进模型只剩 8,000 字 + 「本段已截断，原长 9702 字符」标记（单串上限 8,000 在 `src/deck/registration/register-options.ts`）。所以原验收「显式要全文时行为与今天一致，一句不少」按字面不可满足；正确的验收是「分块交付、逐字节一致、完整才给 digest」。
- **`comments: 0` 今天等于 50。** `src/deck/tools/issue-get.ts` 的 `Number(a.comments) > 0 ? … : 50` 把 0 与缺省并在一起，显式要 0 条做不到；翻默认前必须修语义。
- **评论总数几乎免费。** 实测 GitHub GraphQL `comments(first:0){totalCount}` 可用（本票返回 `totalCount:1, nodes:[]`，不拉评论正文）；GitHub REST 回包里 `comments` 本来就是数字；Markdown 房解析后本来就有全量数组。原第七节「暂不报总数」的建议作废，纳入本票。

### 2. 安全设计：完整交付才给 digest

原第七节的边界只写在回执提示里，不够。最终方案把它做成机器判据：

- `deck_issue_get` 的 `body: 'full'` 分块返回整篇正文，拼起来与后台原文逐字节相同，并附 `digest`；**只有分块完整交付时才给 digest**，给不全就明确失败。
- `deck_issue_patch` 的整份正文替换必填 `bodyDigest`：先读现正文算指纹比对，不匹配或缺失就一个字不动地拒绝。这样 #809 那类「没读全文就覆盖」在写侧直接失败，顺带能发现读后被并发改过。
- 已知限制：GitHub 没有条件更新，预读与写入之间仍有极窄的 TOCTOU 窗口；本方案防的是「没读全」与「读后已变」，不是原子 CAS。

### 3. 最终方案（与第七节的差异）

- 参数：**不再用二元的 `detail` 开关**，改成 `body: 'excerpt' | 'full'`（缺省 excerpt）与独立的 `comments: N`（缺省 0、显式 0 生效）两个轴；`section` / `blocking` 不动。
- 回执：缺省只回票面元数据 + 正文摘要（前 2000 字或 section 那一节）+ `commentCount`（可得时），不再重复整篇正文；full 模式回 `data.body`（mode / chunks / length / digest）。
- 契约：票实体加可选 `commentCount`（能力字段，拿不到省略），三个落点各自填。
- 验收改写为：10KB 正文 + 5 条评论的票缺省 ≤ 3KB；full 拼起来逐字节一致且带 digest；patch 缺 digest / digest 不符整笔拒绝；评论数如实；门禁与文档全同步。
- 实施顺序：先闸与取全（分块 + digest、patch 凭证、comments 0 语义、commentCount），再翻默认与去重，最后金标准回执与文档收尾。
