# 研究 #613：不发 npm 包的插件内置 TS——落点、构建与门禁的最小改动路径

调查对象：本仓库（`FeatherHunter/dsh-mattpocock-skills-deck`）现有构建链与门禁。
本次调查只读：没有改任何构建脚本、没有新增包、没有改任何被跟踪文件，除本文件外没有新建文件。
每条结论都指到「文件路径 + 行号」或「命令 + 输出」；没有核实的写法，文中会明说「未核实」。

## 0. 一句话结论

**仓库里已经有一个「不发 npm 包的内置 TS」，就是根级的 `update-core/`**：TS 源码放在仓库根的独立目录里，用 esbuild 一对一转译成 `src/shared/update/*.js` 并提交进 git，另有 `tests/verify-update-freshness.js` 这条门禁钉住「TS 改了、JS 没跟上」并顺带跑 `tsc --noEmit`。

所以这次要的不是从零发明形态，而是**照抄 `update-core/` 这一套，再补上它缺的那一小步**——它没有被并进任何自动流程（根 `package.json:15` 的 `prepare` 里没有它），所以改一行 TS 要跑两条命令。把它并进 `scripts/build.mjs` 之后，开发循环与今天写 JS 完全一样长。

## 1. 现有构建链逐段拆解

### 1.1 入口命令（根 `package.json:9-20`）

- `build` = `node scripts/build.mjs`（`:10`）：把 `src/` 拼成根 `client.js` / `host.js` 与 `package/lib/client.js` / `package/lib/index.js`。
- `build:dsh-log`（`:11`）/ `build:dsh-plugin-update`（`:13`）：两个**已发布包**的 TS 编译。

### 1.4 派生脚本为什么存在（决定了内部形态能不能省掉它）

`scripts/derive-log-from-package.mjs:9-15` 与 `scripts/derive-update-from-package.mjs:9-16` 写明两个落点：宿主半边把 `packages/<包>/dist/{…}.js` **原样复制**到 `src/host/logPkg/`（update 侧是 `updatePkg/`，8 个文件，`derive-update-from-package.mjs:40-41`）；客户端半边把 `packages/<包>/src/client.ts` 用 esbuild **打包成单文件**落到 `scripts/generated/logKernel.derived.js` / `updateClient.derived.js`（`derive-log-from-package.mjs:61-127`、`derive-update-from-package.mjs:107-199`）。

这两个脚本里还有一批**只为「两份副本要一致」而存在**的步骤：引号归一（`derive-log-from-package.mjs:85-89`）、注释路径归一（`:78-80`）、改名避开顶撞（`derive-update-from-package.mjs:151-162`）、零变化断言字面（`:182-188`）。内部形态下这些**全都不需要**——因为不存在第二份副本（`update-core` 就是直接落进消费点的，一行这类代码都没有）。

跟踪状态已核实（`gh api` 只读查询，不是 git 命令）：

```
repos/…/contents/scripts/generated        → logKernel.derived.js, updateClient.derived.js
repos/…/contents/src/host/logPkg           → config.js, host.js, phones.js, store.js
repos/…/contents/packages/dsh-plugin-update/dist → 404 Not Found
```

即：**派生出来的运行时代码提交进仓库**，`packages/*/dist` 不入库（`.gitignore:35,42`）。`src/shared/update/*.js` 同样是提交进仓库的生成物（`update-core/README.md:31`）。

### 1.5 `scripts/build.mjs`：两种消费形态

- 客户端：`src/client/index.js` 里留标记，构建时按 `KERNEL_MODULES`（`scripts/build.mjs:221-254`）、`SHARED_SPLICE`（`:264-275`）、`LEAF_MODULES`（`:282-327`）三张清单，把每个文件「去掉行首 export」后文本拼回标记处（`extractModuleBlock` `:328-330`、`wireModules` `:331-370`），最后包成 `client.js` 与 `package/lib/client.js`（`buildClient` `:373-406`）。产物里不许留标记（`tests/verify-kernel.js:83-86`）。
- 宿主：`src/host/**` 与 `src/shared/**` **整树原样复制**到 `package/lib`、`package/shared`（`scripts/build.mjs:435-466`），并校验 `package/lib/index.js` 与 `src/host/index.js` 逐字节一致（`:467-474`）；`src/host/updatePkg` 走同一套（`:476-491`）。复制后跑 `node --check` 全树加 `import` 入口冒烟（`:518-553`）。
- 同步：构建结束默认把所有装了本插件的 profile 的 `lib`、`shared`、`scripts` 三棵树同步过去并做 hash 校验（`:649-703`）。
- 客户端只有一个入口：`package/package.json` 的 `exports["./client"] = ./lib/client.js`，产物里只有一处 `window.__ModuleLoader__.load({ id, factory })`（`scripts/build.mjs:387-399`）。

### 1.6 由此得到的两条硬约束

1. **宿主运行时能拿到的代码，必须落在 `src/host/` 或 `src/shared/` 里**（或随包的 `package/scripts/`，但那份清单写死在 `scripts/build.mjs:495` 的 `SHIPPED_SCRIPTS`，只有两条消费者脚本）。因为只有这两棵树会被复制进 `package/lib`、`package/shared`，而 `package/package.json` 的 `files` 白名单是 `["lib","shared","cordis.patch.yml","bundled-skills","scripts/"]`。
2. **客户端只有一个闭包**，没有第二份客户端 bundle 的先例，也没有加载第二入口的机制。

## 2. 内置形态的落点

### 2.1 直接抄 `update-core/` 的形状（推荐）

新开一个根级目录（例如 `<名字>-core/`），内含 `src/*.ts` + `build.mjs` + `tsconfig.json` + `README.md` 四件套，全部照 `update-core/` 抄；产物一对一落进 `src/shared/<名字>/*.js` 并提交进 git；宿主用相对 import 直接消费（照 `src/host/update.js:13-14` 的写法）。这套形态的既有理由都写在 `update-core/README.md` 里，可以直接引用：

- `:21-25` 「给第二家的三条保证」：输出目标定死 ES2020、核心里不碰 Node 或浏览器专属能力（跑腿全在适配器）、类型只用标准写法不依赖特殊编译选项。
- `:37` 「文件之间不互相引用，同层互引门禁天然能过」——这条纪律直接让第 3.1 节第 3 条那道门禁不用动。
- `:47` 「成品包 `files` 白名单不动（共享层整树进包、宿主整树复制）」——产物落在 `src/shared/` 下就自动随包发布，不用改任何发布配置。

**与其他落点的差别**：这条路不用新建 `packages/<名字>/`（不进 pnpm workspace `pnpm-workspace.yaml` 的 `packages: ['packages/*']`、不产生「要发布的包」的假象），也不用碰两个已发布包。

### 2.2 宿主半边：走相对 import 的派生副本（两套先例都可用）

- `update-core` 路径（推荐）：产物落 `src/shared/<名字>/*.js`，宿主侧直接 `import … from '../shared/<名字>/xxx.js'`。先例 `src/host/update.js:13-14`。
- `logPkg` / `updatePkg` 路径：产物落 `src/host/<名字>Pkg/*.js`，另写一个 `src/host/<名字>FromPackage.js` 做接线，入口优先动态 import、失败回退旧实现（`src/host/index.js:315-317`、`:325-327`）。这条路是为「已发布的包 + 插件自带一份」设计的，内部形态用不到那层回退。

两条都会被 `scripts/build.mjs:435-447` 自动带进发布包，不用改构建脚本。

### 2.3 客户端半边：两条路，各有先例

| | 路 A：拼进闭包的派生分块（先例 #564 / #586） | 路 B：当普通叶子拼进闭包（先例：现有 45 个叶子） |
| --- | --- | --- |
| 落点 | `scripts/generated/<名字>Client.derived.js`（esbuild `bundle:true` 打成一个文件） | `src/client/views/.../X.js`（逐文件转译产物） |
| 登记 | `scripts/build.mjs` 的 `KERNEL_MODULES`（`:221-254` 里的 `log`、`updateClient` 两项就是这样）+ `src/client/index.js` 加 `// ==== kernel:<名> (spliced by build) ====` 标记 | `scripts/build.mjs` 的 `LEAF_MODULES`（`:282-327`）+ `src/client/index.js` 加 `// ==== leaf:<id> (spliced by build) ====` 标记 |
| 门禁代价 | 要改「同名冲突」门禁（见 3.1 第 2 条）；**不受** 350 行上限与中文串门禁（两者都只扫 `src/`） | 必须在 `tests/verify-leaves.js:16-50` 的 `LEAVES` 里登记（文件名 + 导出名 + 哪些是组件）并 ≤350 行（`:82`）；文件里不能有 CJK 字符串字面量（`tests/verify-locale-completeness.js:114`），否则要在 BASELINE（`:65-90`）登记条目 |
| 反查机制 | 无（`scripts/build.mjs:348-365` 的反向检查只覆盖 `src/client/views|panel|statusbar|floating`） | 有：这四个目录下任何 `.js` 没登记就构建失败（`scripts/build.mjs:348-365`） |

怎么选：客户端半边会带中文文案、或合并后容易超 350 行 → 走路 A（放 `scripts/` 而不是 `src/client/` 的理由写在 `scripts/derive-log-from-package.mjs:14-15`：`src/client` 下会被中文基线门禁误拦）；客户端半边是纯逻辑（色值解析、规范化、校验），文案由调用方传入走词条 → 路 B 更省事，还自带登记反查保护。

**没有第三条路**：`package/package.json` 只有 `./client → ./lib/client.js` 一个客户端入口，另发一份 bundle 没有消费机制（未核实 DSH 侧是否支持多客户端入口；本仓库内没有任何用法）。

### 2.4 TS 源码放哪：一个必须避开的坑

`scripts/build.mjs:435-447` 是**整树递归复制** `src/host/**` 与 `src/shared/**`。所以如果 TS 源码直接放进这两个目录，**`.ts` 源文件会一起被复制进 `package/lib`、跟着进 npm tarball、再同步进用户机器上的 `node_modules`**（不会报错：`node --check` 只查 `.js`，但等于把源码当死文件一路发出去）。能放的地方有两类，都不用改门禁：

- **仓库根的独立目录**（`update-core/` 就是这么做的）。
- **`src/` 之内但避开 `host`、`shared` 两层**（例如 `src/builtin-ts/<名字>/*.ts`）。可行性已核实：`tests/verify-strict-module-syntax.js:55-67` 与 `tests/verify-file-granularity.js:31-46` 都只看 `.js`；`tests/verify-no-same-layer-import.js:41-48,135` 对不属于 platform / backends / host / shared / seam 五层的文件直接跳过（`return 'other'` → `if (!LAYERS.includes(fromLayer)) continue`）。

## 3. 门禁清单

### 3.1 会被碰到的门禁

1. **TS 与产物的一致性（内置 TS 的专属门禁）**——`tests/verify-update-freshness.js`：`:3-4` 是规则，`:21-25` 是 UNITS 对照表，`:33` 复用编译脚本导出的同一个 `transpileUnit`，`:56` 逐字比对，`:72` 跑 `tsc --noEmit`。新开一个 core 目录就要**照它抄一条门禁**（或把新 UNITS 并进这条），否则「TS 改了 JS 没跟上」没有任何机器在看。顺带一提：这是全仓**唯一**在 `verify` 链里跑 tsc 的地方；两个已发布包的 tsc 只写在各自的 `build.mjs` 里，`scripts/build.mjs` 不编 TS。
2. **生成物同名冲突**——`tests/verify-generated-no-shadow.js`：`:21-47` 取 `scripts/generated/` 两份派生文件的顶层声明名集合求交集，非空即红；`:49-86` 按真实拼接顺序拼成一份闭包跑一遍，断言五个日志电话名与三个更新电话名没被顶掉；`:88-95` 还断言打包产物里带着改名后的 `updBuildPhoneNames`。**新增第三份派生客户端分块必须把这份门禁扩成三份**——该文件 `:3-8` 说明了漏掉的后果：函数声明被提升、后拼的顶掉先拼的、电话名变 `undefined`、界面永远弹「开关保存失败」且一条日志都发不出去（静默坏功能）。构建期还有一条同口径守卫 `scripts/derive-update-from-package.mjs:69-85`。若客户端半边走「普通叶子」而不是派生分块，这条门禁同样不用动——但同一种顶撞风险依然存在（函数声明提升对任何拼进闭包的模块都成立），既有门禁本来就没覆盖手写叶子，这是既有空白、不是本次引入的。
3. **分层 import 基线**——`tests/verify-no-same-layer-import.js`：`:130-151` 扫 `src/host`、`src/shared`、`src/seam` 下所有 `.js` 的相对引用边，同层即违规；`:244-250` 用 `tests/same-layer-baseline.json` 白名单过滤，**不在基线里的新增边直接红**（`:264` 的失败文案：「新增同层引用须先拆分消边，或确认后记进基线（只许减不许增，新增须写理由与归属拆分票）」）。该基线现在 84 条，其中约 22 条正是 `logPkg` / `updatePkg` 内部的边。**照 `update-core/README.md:37` 的纪律让新 core 的产物文件之间零引用，这条门禁一条基线都不用加**；反之每多一条内部 import 就多一条基线条目。
4. **共享层文件计数**——`tests/verify-build-artifacts.js:139-140`：硬断言 `src/shared 23 文件` 与 `package/shared 23 文件`。产物落进 `src/shared/<名字>/` 就要把这个数字改成 23 + N，并按 `:126-138` 的既定格式补一行来历注释（那里已经有一串「#540 …总数 +2 到 20」「#542 … +1 到 21」「#589 … 到 22」「#600 … 到 23」）。**这是落 `src/shared/` 一定会碰的门禁**。
5. **import 卫生**——`tests/verify-build-artifacts.js:142-157`：`src/host/**` 与 `src/shared/**` 里每条相对 import 都必须带 `.js` 扩展名，缺了就红（`import\s+['"](\.[^'"]+)['"]` + `!spec.endsWith('.js')`）。转译会原样保留说明符，所以 TS 里也必须写成 `./xxx.js` 形式——`update-core` 的 `commands.ts` 就是「自包含零引用」加上「类型引用只用 `import type`」（`update-core/README.md:14`）。不用改门禁，但写错就红。
6. **单文件行数上限**——`tests/verify-file-granularity.js:18-19`（`LIMIT = 350`、`SEVERE = 500`）+ `:31-46`（只扫 `src/**/*.js`）+ `:24-29` 的豁免名单 `DERIVED_DIRS = ['src/host/logPkg/', 'src/host/updatePkg/']`（注释写明理由：那是原样复制来的编译产物，人手不能拆、拆了会被下次派生覆盖）。**落进 `src/shared/` 的转译产物没有豁免**，所以每个产出的 `.js` 不能超 350 行；超了要么拆 TS 源文件，要么把新目录加进 `DERIVED_DIRS`（后者会削弱「人手可维护」的含义，建议优先拆）。基线文件 `tests/file-granularity-baseline.json` 现在是空的 `{"version":1,…,"files":{}}`，改动会立刻显形。另有一处同口径但只针对叶子的上限：`tests/verify-leaves.js:82`。

### 3.2 因为「不发包」而不需要动的门禁与步骤

- `package/package.json` 的 `exports` / `files` / `version` / `publishConfig` / `repository.directory`：只有独立发布的包才需要。产物落在 `lib/`、`shared/`、`scripts/` 三棵树里时，`files` 白名单（是目录，不是文件清单）不用改——`update-core/README.md:47` 已经把这句话写下了。
- `tests/verify-release-contract.js:187-232`（`npm pack --dry-run` 白名单）、`tests/verify-release-template.js`、`tests/verify-t1-initpublish.js`：针对插件包本身，不点名内部 TS。

- 根 `package.json` 的 `dependencies`（`dsh-log`、`dsh-plugin-update`）：那是两个**已发布包**的依赖，内置 TS 不需要。
- 没有任何既有门禁把两个 TS 包当集合点名（`grep -r 'dsh-log|dsh-plugin-update' tests/` 只命中 `verify-file-granularity.js:27-28` 的注释与 `verify-update-migration.js:103,231,234`），所以不新建 `packages/<名字>/` 就碰不到「包集合」类断言。

## 4. 备选方案对比

### 方案 A：复用现有两个包的管线骨架，跳过发布相关步骤

新增 `packages/<内名>/tsconfig.json`（抄 `packages/dsh-log/tsconfig.json`，16 行）、`packages/<内名>/build.mjs`（抄 `packages/dsh-log/build.mjs`，79 行）、`scripts/derive-<内名>-from-package.mjs`（抄 `scripts/derive-update-from-package.mjs` 214 行，删掉改名与零变化断言那几段）；根 `package.json` 的 `prepare`（`:15`）追加一段；另写一条逐字节一致性门禁（照 `verify-update-migration.js:101-117`）。
教训是：这条路**比现状倒退**——仓库已经有一个不带包骨架的内置 TS（`update-core/`），再起一个带包骨架的，等于把「为发布服务」的那部分步骤请回来，还要长期维护第二份副本与它的门禁。

### 方案 B：照 `update-core/` 的形状，把转译口径并进 `scripts/build.mjs`（推荐）

**改动面**：新增一个根级 core 目录（`src/*.ts` + `tsconfig.json` + `README.md`，不要单独的 `build.mjs`）；把 `transpileUnit()`（照 `update-core/build.mjs:32-43`）与类型检查（照 `:45-60`）放进 `scripts/build.mjs` 并导出，在 `main` 开头调用——该文件 `:25` 已经 `import * as esbuild`，`:24` 已经会用 `spawnSync(process.execPath, …)` 跑子进程；产物一对一写进 `src/shared/<名字>/*.js`。
**长期维护成本**：最低。没有第二份副本、没有新包目录、没有 pnpm workspace 变化；开发循环与今天写 JS 完全一样长（见第 5 节）。
**一处与现状的差异要写进 ADR**：`update-core` 是「自己一个 build.mjs、要手工跑第二条命令」，本方案是「口径住在主构建脚本里、一条命令搞定」。要么接受这点分叉，要么顺手把 `update-core` 也并进去（那是改既有结构，建议另开票，不要塞进本次）。

### 方案 C：不引 TS，全部写普通 JS（对照基线）

**改动面**：0 个新构建步骤、0 个新产物落点、0 处构建脚本改动。新代码直接写在被门禁天然覆盖的位置：宿主写 `src/host/<名>.js`，客户端写 `src/client/views/.../X.js` 并登记 `LEAF_MODULES` + 标记 + `tests/verify-leaves.js`。
**放弃的东西**（这是它真实的代价）：编译期的类型约束（色值的 6 位十六进制规范化、宿主与客户端两半共享的类型、端口与适配器分开的边界——正是 `update-core` 的 `ports.ts` / `runtime.d.ts` 那一套）；换来的是每个文件都要自觉 ≤350 行（`tests/verify-file-granularity.js:18`）与客户端文件零 CJK 字符串字面量（`tests/verify-locale-completeness.js:114`）——这两条在 `scripts/generated/` 或 `src/shared/` 之外的落点下都躲不开。本仓库现在的补偿手段是运行时门禁（`node --test`、`tests/verify-*`）与 `npm run test:smoke`，不是类型检查。

### 推荐

**方案 B。** 三条理由：

1. **它是既有决定，不是新发明**：`update-core/README.md:3` 写着 538 落点决议「独立 TS 模块的源码家：以后独立成包时整个目录拎走」。照抄这套，长期认知负担最小，也最容易被后来人看懂。
2. **开发循环不长**：今天写 JS 是「改 `src/` → `node scripts/build.mjs` → 刷新 / 重启」；方案 B 完全一样。而**照 `update-core` 现状不改**的话是两条命令（先 `node update-core/build.mjs` 再 `node scripts/build.mjs`），这正是要补上的那一小步。
3. **不制造「又一个包」的假象**：#613 的核心区分是「这是插件内置能力，不是 `dsh-log`、`dsh-plugin-update` 那种对外发布的包」。不新建 `packages/<内名>/`，就不碰 pnpm workspace、发布契约与版本号。

## 6. 还没确定的事

1. **新 core 目录叫什么、要不要就并到 `update-core/` 旁边**（仓库根级的新目录，还是 `src/` 内避开 `host`/`shared` 的新目录）。两条都不用改门禁；取舍是「仓库里允许几棵源码树」与「会不会被误认成要发布的包」。留给 #616 定版。
2. **客户端半边走「派生分块」还是「普通叶子」**，取决于该功能客户端代码的规模与是否带中文文案：带文案或超 350 行 → 派生分块（`scripts/generated/`）；纯逻辑、文案走词条 → 普通叶子（`src/client/`）。
3. **要不要顺手把 `update-core` 也并进 `scripts/build.mjs`**，让全仓只有一条「改代码到见效」的命令。这是改既有结构，建议另开票，但如果不改，全仓就会长期并存两种节奏。
