## 六、dsh-log 埋点方案（本阶段只写方案，不改代码）

本票是死代码清理，不是运行期故障；日志不能证明「该不该删」，只能回答「运行时是否还在丢弃这个项」。按任务要求仍给出一版精确方案，作为实施后回归的旁证。

### 落点与事件

- 文件与行：`src/host/detectChain.ts:386`。就在这句过滤之后、`items` 被使用之前记一行。这里只有后端为 github/gitlab/markdown 且走进链求值时才执行。
- 事件名：`chain.catalog`，按需（debug）级。现有同族事件是 `chain.predicate`、`chain.cache.hit`、`chain.cache.miss`、`chain.preflight.reuse`，命名风格一致。
- 写法沿用 `:240`、`:243` 的既有形状：

  `try { if (logCtx && logCtx.isEnabled('debug')) logCtx.fire('debug', 'chain.catalog', function () { return { backend: String(backendId), declaredCount: n, runtimeCount: m, droppedIds: ids, reason: 'backend-catalog-filtered' } }) } catch (eL) {}`

- 去重：按「每进程每后端只记一次」处理，避免每次链求值刷屏。做法是在模块级加一个 `Set`（放在 `:167` 附近 `chainInflight` 那一带），键用后端标识；命中就跳过。这是高频不判开关的典型，必须靠开关加一次性去重两层。

### 字段（只收能排除一种故障的信号）

- `backend`：`github` / `gitlab` / `markdown`，短字符串。
- `declaredCount`：`catalogFor()` 声明的后端项数（今天 github 是 5）。
- `runtimeCount`：过滤后真正进入运行视图的条数（今天 github 是 4）。
- `droppedIds`：被过滤掉的 id 数组（今天应为 `['gh:labels']`）。只允许枚举 id，不记路径、标题、用户名、工作区原文，凭证不落盘。
- `reason`：固定原因码，取 `backend-catalog-filtered`。

不记：工作区路径原文、完整目录项对象、locale 文本。

### 这条日志落盘后怎么判

- 出现 `chain.catalog` 且 `droppedIds` 含 `gh:labels`：死项仍在真源声明、仍被运行时丢弃，故障存在。
- 出现 `chain.catalog` 且 `droppedIds` 为空、`declaredCount == runtimeCount`：过滤已没有对象，死项已清理（此时过滤本身也该删）。
- 没有 `chain.catalog` 但同窗口有 `chain.predicate`：说明链确实求值过，但本事件没发——可能是过滤被删、事件被删或构建未含本改动，单靠日志分不清，需要对照构建与源码。
- 没有 `chain.catalog` 且没有 `chain.predicate`：该后端当天没走链求值，日志不能判定。
