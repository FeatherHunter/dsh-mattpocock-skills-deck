## 六、设计规则：为什么这么切（写下来供以后的人照着判断）

1. **只做三层，不往下加第四层**：#1010（总图）→ 地图 → 任务票。任务票还是太大时的正确做法是**在同一层拆成两张并列的开发票**，而不是再挂一层子票。理由：每多一层，读者就多一次「我该看哪张」的判断；而执行端（AI）一次只领一张票，第四层不会带来任何执行上的好处，只会让「做完没有」变得说不清。
2. **一张地图 = 一句话能说清、且这句话里不出现「和」的边界**：一个源码目录、一个契约面、一条链。说不清就说明切错了位置。
3. **地图张数守在 12–14 张**：切成三十张会让维护者在票海里导航；切成三四张则会出现「GitHub 房 28 件」这种一个上下文窗口吃不下的巨票。目标是「一天能讲完一张」。
4. **两种判据不混**：改写单元地图的完成判据是「同一输入、同一回执、零变化」；能力地图的完成判据是「新行为可用、有验收证据」。判据不同就不同图，因为混在一张图里两条判据会互相打架，讲解时也说不清「这行为是搬来的还是新加的」。
5. **编号＝阅读顺序，动手顺序只在少数处偏离**：把纯前置（基建、契约接口）排在最前，其余按请求走一遍的顺序排，于是列表顺序本身就是执行顺序，读者不用换算。唯一允许的偏离用 blocked-by 标出（例：契约的「两房实现对齐」要等两房开发票）。**不要造出两套完整顺序**——那会逼读者每次先做一次换算。
6. **地图内部的票不是「固定三张」，而是「固定的认知阶梯 + 按需修复」**：讨论（先对齐做法）→ 开发（搬、转、补日志注释、门禁）→ 讲解（带维护者读代码、用当次代码讲 TypeScript、请他给「讲解三看」表态）。讲解单开一张票，是为了保证「代码写完了」不会顺带把「他学会了没有」也当成完成。修复票只在真发现问题时开，不预留——预留的票会变成僵尸票。
7. **同一批文件不许两头改**：能力地图的开发票要 blocked-by 它要动的改写单元地图。之所以允许「能力地图的讨论票现在就开」，是因为讨论票不写代码，不违反这一条。
8. **一张开发票何时再拆（同一层并列）**，两个尺子任选其一：一是「一个上下文窗口吃不吃得下」（GitHub 房 28 件、Markdown 房 23 件必须拆）；二是「改完之后讲解票能不能一次讲完」。讲不完就说明开发票太粗。
9. **旧票不搬进新结构**：旧 27 张票的判据是「故障好了没」，与改写单元的判据不同；搬进来还会破坏「同一条边界同一时间只允许一个写者」。它们留在 #1010 下，按「随重构收口」处理。
10. **每张票的正文都要能独立读懂**：开头写清「我在哪张地图下、上游是谁」，进度区由动手的 AI 写一行带时间的实况，而不是只放一个百分比。

## 七、待维护者拍板的 4 条（建票前必须问清）

1. **讨论票要不要按地图开**：每张地图一张（13 张讨论票），还是按阶段合并（比如「入口与壳」一张、「三房」一张，共 5 张）？合并省票数，代价是讨论时混着几个单元。
2. **讲解票什么时候建**：我倾向**不提前建**——等对应开发票收尾时由 AI 开，因为讲解的对象是已经写完的代码，提前建只会挂在那里。你要的是不是「列表里一眼看到还有讲解这一环」？如果是，那就提前建、正文写明「等开发票收尾后认领」。

4. **标题格式**（见第八节末）：确认「地图03工具壳：共用壳转TypeScript」这种紧凑写法，还是要更短。

## 八、对抗式审查（2026-10-12）：三处必改、两个方案被否掉

我拿维护者的五项目标当尺子，逐条攻击自己的切法，查出三处真问题（已按上面的新清单改掉），并把站不住的自我说法撤掉。

**必改之一：漏了整层「最底层」。** 证据：`research/1010-deck-chain-dirs.md:79-88` 列的第 7 层是起 `gh` 进程的 `src/host/repoKeys.js`（超时 30000）、平台三底座、`platform/deckExec.js`、`refresh/gate.js`、`ledger.js`、`src/shared/refresh/budget.js` 与 `tool-cost.js`、Markdown 的 `.scratch/` 写入队列、宿主快照四件。而我原来列的 W11「宿主接线 6 件」只是**引用点**（谁 import 了被搬走的文件），不是底层。维护者的第三条目标写明「deck 工具加底层 GitHub 加底层 Markdown 全部在内」，漏掉这一层等于目标没落票。修正：新增 11 号地图，并把 ADR §3.4（`docs/adr/20261011-deck-ts-rewrite.md:82`）那句「闸、账本、注册表只转被 deck 调到的行」写成它的边界规则。

**必改之二：日志是横切关注点，不该占旅途上的一段。** 日志的事件常量与字段表是机制，可以集中；但**每段旅途的埋点必须写在该段的开发票里**——不在现场的人写不出正确的日志点。修正：日志机制归 01 号基建地图，埋点变成每张开发票的验收项。注释同理，全部落在开发票里，不单开地图。

**必改之三：撤掉「编号给人看、依赖边给执行看」这个说法。** 它等于告诉读者有两套完整顺序，每次读票都要先换算一次。修正：编号就是阅读顺序，把纯前置排到最前，于是它同时是执行顺序；只允许一处偏离（契约的两房对齐），用一条 blocked-by 标出。

**站不住的说法，一并撤掉**：①「按源码目录切地图」——第一性原理的单位是「一次请求走完的一段路」，目录只是这段路的落点；目录是**核查手段**，不是切分判据。②标题里用字母（W/C）和「·」做速记——违反本仓「人类第一次阅读就能懂」的规矩。新格式：地图 `地图03工具壳：共用壳转TypeScript`；子票 `地图03工具壳讨论：做法与失败路径怎么定`、`地图03工具壳开发：转TypeScript并补日志注释`、`地图03工具壳讲解：带你读共用壳`。全角冒号是标点、不算空格；不用「·」，不用半角空格。

**审查中想过、最后否掉的两个方案**（留个记录，免得以后有人再提一遍）：
- **不要地图层，13 张票平铺**：这样 #1010 下会有 13 张新票 + 27 张旧票并列，阅读顺序消失；而且讨论、开发、讲解是三次不同的对话（各自有认领人、状态、评论流），塞进一张票里没法分别推进。省下的只是一次点击。
- **只按阶段切 5 张地图**（入口与壳 / 契约与识别 / 三房 / 最底层与宿主 / 基建与收口）：层数更少、列表更短，但每张地图的「已定决策」区混着三四个单元，单元边界只能藏在标题里；维护者要的是**按单元吃透**，所以否掉。

**剩下的攻击，我承认成立、但接受代价**：13 张改写地图 + 2 张能力地图，每张至少三张子票，总量在 45 张左右，对一个个人项目是重的。砍法只有一处值得砍——讨论票按阶段合并（4–5 张），其余不建议砍：开发票是交付单位、讲解票是学习单位，都不能省。

## 九、第二轮：以架构师视角重看一遍（2026-10-12，查证后重写）

**先纠正三条我记错的仓库事实**（都亲手核过）：
1. **构建产物今天就不入库**：`.gitignore` 里明确写着 `/client.js`、`/host.js`、`/package/lib/`、`/package/scripts/`；`git ls-files lib` 为 0。四个 TypeScript 核「提交同名 `.js` 产物」是另一套并存形状（它们转译进 `src/shared/<核名>/`，由新鲜度门禁核对）。所以「产物出仓」不是新决定，是把并存的两种形状统一到已经存在的那一种。
2. **运行时吃的是 esbuild 打出来的两个产物**（`host.js` 与 `package/lib/*`），而 esbuild 原生吃 `.ts`。所以让 `.ts` 上运行不需要「编译到 dist + 工程引用」那套重武器，只需要改入口解析与测试装载。
3. **客户端从不 import 跟踪器那一层**：全仓 `tracker/...` 的 55 处命中里，`src/client/` 的三处（`locale-labels.js:14`、`link.js:111`、`labelColorErrors.js:13`）**全是注释**。ADR §3.2 注里「契约是面板与 deck 共用的承诺」这个理由站不住——准确的说法是：契约是跟踪器这个模块**对外发布的接口**，deck 与宿主刷新都是它的消费者，按深模块的说法接口就住在模块边界上。**结论（放 `src/tracker/contract/`）不改，改的是理由那句话。**

**据此给出九条优化（前四条改变执行方式，后五条改变交付物）**：
1. **按「纯度」在每张改写地图内部再划一条线**：纯规则（最小规范、幂等锚、边落点、超时余量、进度与区块解析）与摸宿主的部分（取会话、起进程、读写文件、查时钟）分目录放；纯规则那一侧**不许 import 宿主能力**，由一条门禁保证。收益：单测不用模拟宿主就能跑；将来客户端能复用这些规则；讲解时能清楚指出「哪部分是算、哪部分是碰世界」——这正是今天 `shell.js` 最大的问题（它同时算规则又取会话）。
2. **依赖方向从约定升级为会红的门禁**：`src/deck/**` 只许 import 跟踪器的契约与注册表，不许碰房间与识别判定；房间只许 import 契约。今天这类边界靠扫文本的三条门禁，转 TS 后改成按依赖图判。
3. **「行为零变化」从承诺变成机器判据**：新增金标准回执夹具——把今天九个工具的代表性调用回执（去掉时间戳与路径后）落成基准，之后每个单元转完重跑比对，逐字相等才算过。
4. **「搬家」与「转换」分两笔，搬家一次做完**：91 处引用改动属于机械操作，一次做完（门禁全绿 + `git diff -M` 全是相似度 100% 的重命名），之后每个单元只做「转 TypeScript + 日志 + 注释」，diff 干净、可单独回滚，也不会出现「改坏了分不清是搬家还是转换」。注意：这一步要等 #1003/#1012 那 13 个重叠文件收口，或先把它们排除在外。
5. **两房串行，GitHub 先转**：把 GitHub 房当成契约的第一次真实压力测试，契约该改的地方在 08 就暴露；Markdown 房排在它之后，避免同一处契约被改两遍。
6. **竖直薄片先行**：01 号地图里加一张只读的票「一次真实调用的全程走查」，产出 `docs/tour/00-一次调用全程.md` 与基准回执，不写任何产品代码，给后面 13 张地图当模板与尺子。
7. **每个单元留一份讲解文档与一段提交区间**：`docs/tour/<号>-<单元>.md`，文件头写「对应提交 `<sha>`」（过时一眼可见）；开发票收尾评论记录本单元的提交区间，任何一段都能单独回滚。
8. **能力图先定「工作状态模型」**：C1（在办可见）与 C2（正文进度与原话）共用一张讨论票先定词汇——有哪些状态、字段叫什么、谁写谁读、留多久、哪些绝不落盘，避免两张图各造一套词。
9. **测试跑法定为 `node --test` + 一个约三十行的 esbuild 装载钩子**，不引 vitest（避免把 vite 全家桶带进来；界面侧已有 jsdom 与 playwright）。旧的 243 条 `verify-*` 脚本按单元分批迁到新跑法，不一次性重写。

## 十、第三轮：把构建链读到底之后，方案定稿（2026-10-12）

**四条硬事实（亲手核过，它们决定了整个改造的技术路径）**：

1. **宿主树没有打包，是逐文件原样拷贝**：`scripts/build.mjs:814-845` 用 `cpSync` 把 `src/host/**` 拷成 `package/lib/**`、把 `src/shared/**` 拷成 `package/shared/**`（注释原话「零打包」）；`scripts/build.mjs:863-867` 还立了一条不变量：`package/lib/index.js` 必须与 `src/host/index.js` **逐字节一致**。→ 所以「编译到 dist + 工程引用」确实不需要；但 `.ts` 必须**逐个转译成 `.js`** 才能进运行时，运行时不会自己认 `.ts`。
2. **逐文件转译的先例已经在仓库里**：`scripts/build.mjs:1029-1053` 处理客户端像素系列的 `.ts` 真源——`esbuild.transformSync(source, {loader:'ts', format:'esm', target:'es2020'})`，产物带 AUTO-GENERATED 头；四个核也是同一形状。→ deck 改造复用这条既有管线，**不发明新机制**。
3. **产物今天就不入库**：`.gitignore` 里写着 `/package/lib/`、`/client.js`、`/host.js`。像素系列那套「生成的 `.js` 提交在 `src/` 里」是旧形状，**不扩展到 deck**：新代码只留 `.ts`，转译产物只出到 `package/lib`。
4. **源码之间的引用写成 `./x.js`，而磁盘上将来是 `x.ts`**：测试侧用一个 ESM `resolve` 钩子把 `.js` 映射到同名 `.ts` 双胞胎（约三十行，零新增依赖）。因此 91 处引用里**只有跨树搬家那些**需要真的改路径，其余原样不动——机械搬家的规模比原先估计的小。

1. **纯度划线做**：`src/deck/` 下新增 `rules/`（纯规则：最小规范、幂等锚、边落点、超时余量、进度与区块解析），与 `shell/`（摸宿主：取会话、选后端、过闸）分开；纯规则那侧不许 import 宿主能力，由一条门禁守。**理由是现成的证据**：这一轮 13 条门禁变红，根因正是 `src/shared/deck-tools/shell.js:176-180` 硬要一个夹具没递进来的 `d.decideBackend`——规则与外部依赖缠在一起，谁都得陪它一起造桩。

## 十一、每张地图的目的定稿（计划层 / 项目经理层 / 总工程师层，2026-10-12）

这一节只回答一件事：**每张地图为什么必须单独存在、它守护哪条边界、做到什么算完、交给下一环什么**。票怎么写、依赖边怎么连，是下一层的事，不在这里。

### 11.1 整个工程的三条线

同一次改造里同时发生三件事：**换语言**（手写代码只剩 TypeScript）、**立架构**（边界能用一句话说清并被门禁守住）、**留证据**（日志、注释、讲解文档，让维护者能复述每一段为什么这么写）。三条线对应三类地图：地基（01 基建、02 契约）、改写单元（03–12）、收口（13）；两张能力图（C1、C2）是另一条线，完成判据不同（新行为可用，而不是行为零变化）。

图的顺序就是**一次调用走一遍的顺序**。理由只有一个：读懂代码的最短路径是跟着一次真实调用走，而不是跟着目录清单走。每张图都配三种票——对齐（讨论）、交付（开发）、传承（讲解）——因为这三件事任何一张图都逃不掉。图与图之间只通过三样产物交接：**能跑的东西**、**能量的尺子**（门禁与金标准回执）、**能读懂的文字**（注释、讲解文档、索引、日志导读）。

### 11.2 地基两张

**01 构建与测试基建**
- 目的：让后面每一张图都能「改完立刻看见效果、坏了立刻知道」。它是唯一一张不改变产品行为的图，却是其他图敢动手的前提。
- 守护的边界：源码与运行时之间那道转译线——`.ts` 怎么变成 `package/lib/*.js`、测试怎么加载 `.ts`、门禁怎么读 `.ts`。
- 做完的标志：随手写一个 `.ts`，一条命令就能被构建、被测试、被类型检查、被门禁看见；发布探测仍通过。
- 交给下一环：一条可复制的流水线，外加一把量尺（金标准回执夹具）。

**02 契约**
- 目的：把「上层敢对后端一无所知」从口头承诺变成编译期事实——谁写错签名，编译就报错。
- 守护的边界：工具与后端之间唯一的书面承诺（19 个操作加旁路扩展）。
- 做完的标志：两房 `implements` 全绿、`getRepoPermissions` 升进契约、契约门禁收尾。
- 交给下一环：房间改造时不需要再谈判的接口。
