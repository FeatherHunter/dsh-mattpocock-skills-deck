## 四、根因链

1. **每个窗口只向宿主读一次设置文档。** `settings-view.ts:411` 的注释写明「惰性读一次文档：第一次有人读或写时才问宿主，只问一次」，`:412-414` 在状态不是 idle 时直接返回。所以一个窗口活多久，它的内存文档就可能是多久以前的快照。
2. **窗口把这份内存文档当长期真源。** `settings-view-state.ts` 的 `viewFlagState.doc` 保存文档，`viewFlagOfRoot` / `viewFlagOf` 只读内存，不感知别的窗口刚写了什么。
3. **任何一格改动都会送整份文档。** `settings-view-write.ts:375-400` 的 `viewFlagWriteNow` 在有本窗待写格时，先 `viewFlagFreshDocFor` 重读、把本窗 journal 合并进重读结果，然后 `:359-373` 的 `viewFlagSendDoc` 调用 `host.call('wf.setSettings', { value: snap })`，送出去的是整份文档快照。
4. **重读失败时退回内存旧文档。** `:392` 的 `const value = fresh || viewFlagState.doc`：重读失败、只读、形状不对时，拿内存里的旧文档整份写回。这是覆盖风险最高的一条路径。
5. **宿主直接整份覆盖。** `settingsPhones.ts:196-233` 的 `handleSetSettings` 在进程内串行队列 `serialWrite`（:168-172）里先读一次文件，但这次读只用来判只读/更高版本（:203-211），随后 `:214` 用客户端传来的整份文档覆盖；`:220` 只把快照 publish 给 deck 工具闸门。`serialWrite` 只保证同一宿主进程内的写不交错，不提供版本判据，也不合并。
6. **覆盖写的触发动作没有闭环。** 日志第 6028-6029 行是两条 `settings.toggle ... listed=true ... reason=queued`，同一毫秒（ts 1793541072628）、同一条 trace（35575694e83404d5），值与「从 hide/on 点两下开关得到 show/off」吻合；但同一毫秒两笔不符合人手点击的间隔，驱动脚本 `j10-01-run.mts` 对 A2 只做了开设置页、展开工作区组、只读读色、截图、关闭，没有点开关。全仓传 `listed=true` 的地方只有 `SettingsWorkspaces.ts:364-365` 的开关按钮，所以来源写口确定；**具体是哪一下带出这两笔写，本轮没有找到**。
7. **写成功后没有跨窗口/跨进程广播。** 客户端只 emit 本窗口；读侧又只读一次，所以别的窗口永远看不到新值。这是与写侧独立的第二个缺陷。
8. **两台实例共用 profile 时，连 `serialWrite` 都不共用**（它是进程内队列），只剩文件系统一层；要防两台实例互相覆盖，需要文件级版本号、条件写或锁文件。

## 五、修复落点与实施注意（写给动手的人，不含代码）

1. **宿主加一个按字段写的电话。** 只接收「本窗这次改动的格」，宿主在 `serialWrite` 内读最新文件、只合并这几格、写回、再 `publishSettingsSnapshot`。`settingsPhones.ts:235-289` 的 `writeDebugSwitchEnabled` 已经是「宿主读、只改一格、写回」的现成先例，说明机制不用新造，工作量可控。
2. **客户端设置页的开关只送改动格，不再送整份文档。** 现在的 `viewFlagSendDoc` 是整份快照，改完之后状态栏开关与 deck 工具开关只送 `{ statusBar }` / `{ deckTools }` 这样的单格；`settings.toggle` 日志格式保持不变。
3. **设置页每次打开都重读。** 去掉 `settingsViewLoad` 的 `status !== 'idle'` 早退；重读后先把本窗未落盘的 journal 与本窗临时记录合并进去，再覆盖内存文档，避免重读把本窗还没写成功的东西冲掉。
4. **跨进程需要文件级版本号或条件写。** 只在客户端做「写前重读合并」缩不到零：`settings-view-write.ts:33-38` 的注释自己写明，重读之后、写回之前别人写进去的格，照样可能被这一趟整份顶掉（实测）。要覆盖两台实例共用 profile，必须在文件层加版本判据，或者在写入口排队（锁文件）。
5. **补一扇双客户端门禁，再重跑 J10-01 真机。** 门禁用真 `settingsPhones` + 真 `configStore` + 临时 home 真文件，起两个客户端实例：A 把 `statusBar` 写成 hide；B 拿它那份旧文档再写一格；断言文件里的 hide 还在、B 重读能读到 hide。门禁绿了之后重跑 J10-01 真机，把新证据回填票面。

实施时注意：

- 不要只改客户端重读。`settings-view-write.ts:33-38` 已经写明那样仍会丢数据，只改读侧会让票面验收看起来过了，而覆盖写还在。
- 设置页「列出但还没打开」的临时记录（`listed`、`unopened`，见 #1640、#1641）走的是同一条写路径，改单格写口时要把这条路径一起兼顾，不要把它退回整份写。

## 七、分诊新发现

1. **读侧与写侧是两个缺陷，验收要分开写。** 「重新打开设置页应看到新值」验的是读侧；「后写的一方不覆盖先写的一方」验的是写侧。只做前一半会让票面判据通过而数据仍可能丢。
2. **宿主已经具备单格读改写能力**（`writeDebugSwitchEnabled`），所以按字段写口不是大改，主要工作在客户端把「整份快照」换成「改动格」，以及跨进程的版本判据。
3. **B4 那两笔写的触发动作未闭环。** 两笔 `listed=true` 同一毫秒入队、值与「从 hide/on 点两下」吻合，但不符合人手点击；驱动脚本里也没有对应动作。实施第一步建议先补一条能钉住「这次 `setViewFlag` 由哪个界面动作发起」的日志（现有 `settings.toggle` 记了 flag/value/listed/reason，缺的是发起动作），再复现一次。
4. **票面混用了两趟运行的时间戳**（14:03:12.117 与 13:41:08.827），不影响结论，但引用时按 `observations.md` 与日志为准。
5. **幂等键注释在正文里重复了两行**（第 1、2 行完全相同），是小瑕疵。
6. **独立快照文件名没有抓取时刻。** `independent/settings-before.yaml`、`settings-after.yaml`、`settings-now.yaml` 能证明「文件从 hide 变成 show」，但不能用来给某一次点击定时。
7. **1e 观测与文件快照一致**：文件里三行 `statusBar` 全是 show，说明覆盖写确实落到了文件，不只是界面问题。
