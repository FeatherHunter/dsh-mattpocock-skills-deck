## 四、根因链

1. #1693（2026-10-31）把通知中心的事件库落成四类事件（`notification-events.ts:29`），只接了宿主刷新这一路：`session-refresh-schedule` 失败时调 `noteRefreshFailure`。没有「探测失败」「取数失败」的位置。
2. #715 / #1418 把「失败必可见」做在客户端：探测失败写 `snapFail={kind:'probe-failed'}`（`refresh-timer.ts:126`），快照取数失败写 `fetch-failed` / `quota-exhausted`（`snapshot-sync.ts:291`），界面据此画头部小标识。可见性做到了，留痕没做。
3. 通知中心历史只读事件库（`wf.notifications` → `store.read`）；客户端失败态是会话内存，不进历史。当前状态又按 ADR 只从快照降级标记派生（`notificationCenterModel.ts:283-287`），所以通知中心里没有失败位。
4. 频率与上限让「简单记一条」不成立：活跃探测固定 5 秒一拍（`config/intervals.yaml:17`），瞬时事件按「类型+仓库」60 秒去重（`config/intervals.yaml:61`、`notification-events.ts:203`），窗外新起一条；保留 7 天（`config/ttl.yaml:149`）、上限 500 条（`notification-events.ts:33`）。按现有去重窗简单记录，持续失败约每分钟一条，估算约 8 小时就会把 500 条上限被这一类事件占满。
5. 事件库的合并语义还会丢环节：`appendInstant` 窗内合并只加 `count` 与 `updatedAt`，`code`/`params` 保留第一条（`notification-events.ts:205`）；若探测失败与取数失败复用同一 type 且同窗发生，后到那条的环节信息不会更新。
6. 界面侧：说明只按机器码 `code` 取词条（`notificationCenterModel.ts:144-156`）。现有 `refresh-failed` 的 code 只说「刷新没成功」，不区分探测/取数；没有 code 的旧事件会落到「旧版记录：没有记录失败细节」，所以新增环节必须同时配 code 映射与词条。
7. 写入侧：事件库的 store 方法自己用 `getRepoKey(cwd)` 解析仓库（`notification-store.ts:93-95`），宿主 `probe-handler` 与 `session-snapshot-cache` 都拿得到 cwd，所以宿主补记不需要客户端提供 owner/name，也不需要新 RPC；但 `noteRefreshFailure(cwd, error)` 现在只收两样东西，要带环节与原因类别得扩参数并同步门禁。
