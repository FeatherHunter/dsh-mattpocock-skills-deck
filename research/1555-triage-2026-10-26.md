# #1555 分流诊断：“这个工作区的只读会话没开成”在什么场景下出现、这次是哪一种（2026-10-26）

调查范围：票 #1555 的正文、图片与评论（作者 q4452542007，2026-10-26 创建，无评论、无标签）；仓库 main（调查时 HEAD `b79bbc4c`，提交信息称版本已推进到 1.9.0-beta.26）；本仓库里与只读会话、后端认领、详情与评论读路径有关的源码、门禁与提交；`research/` 下相关的既有笔记；相邻票 #1444、#1533、#1505、#1519。本次只做诊断，没有改业务代码、没有开始实施。

## 一句话结论

这句话是“面板要读一张票的正文或评论（或要发评论），于是去开这个工作区的 Tracker 只读会话，但会话没开成”时的统一失败文案；图里这次的具体原因是 `multi-match`（多家后端同时认领）。它和升级的关系在代码上可以核对：v1.9.0-beta.12 的提交 `e31124e1`（#1444）把详情与评论的读路径从“先走统一判定定下后端、再直接读那个后端”改成“开一个 Tracker 只读会话”，但开会话时没有把统一判定的结论带过去；会话层看到“多家同时认领”就拒绝，于是同一批子票在升级前能读正文与评论、升级后只剩一条红条。

## 这句话在哪儿产生，界面怎么显示

- 唯一的出处是 `src/refresh/rooms/host/comment-thread-fetch.ts:73-77`（只读会话；`:117-121` 是同一句话的写会话版本，文案把“只读会话”换成“写会话”）。
- 三个宿主电话会走到它：`wf.issueDetail`（详情，`:132-133`）、`wf.issueComments`（评论首屏与加载更多，`:203-204`）、`wf.commentIssue`（发评论，`:246-247`）；接线在 `src/host/index.ts:290-292`，开会话的装配口在 `src/host/index.ts:104` 与 `src/refresh/rooms/host/session-opener.ts:148-202`。
- 界面方面：`src/client/views/IssueDetail.ts:368-381` 把失败回包画成顶部红条（主行是 `err.message`，小标签是 `kind`，可展开的“原始说明”是 `raw`，旁边有“重试”和“（显示快照降级）”）；`src/client/kernel/api-io.ts:216-224` 把宿主回包归一成 `{kind, message, raw}`。宿主这条失败只带 `kind:'env'` 与 `message`，所以“原始说明”里重复的就是同一句话。
- “重试”会再打一次同样的电话（`IssueDetail.ts:96`），原因没变就会得到同一句话；“（显示快照降级）”表示详情没拿到，标题/标签/所属地图这些轻量字段来自列表快照，正文与评论只能写“还没拿到”。

## 什么场景下会出现（这句话后面括号里的原因）

会话开不成的结局都会拼进这句话。按代码把全部取值列出来（`src/refresh/rooms/host/session-opener.ts` 与 `src/tracker/session/open-tracker.ts`）：

- `multi-match`：两个或更多已注册后端同时认领这个工作区（`open-tracker.ts:110-113`）。图里就是这一种：`markdown、gitlab`。
- `no-backend`：问过一圈，没有任何后端认这个工作区（`open-tracker.ts:108`）。
- `pending`：认领还没定（有后端超时没回话，`open-tracker.ts:106`；或选出来的后端刚被卸载、没有预算声明、开工中途炸了，`open-tracker.ts:114-126`、`:170-172`）。
- `no-registry`：后端注册表还没就绪，这一趟拿不到任何后端（`session-opener.ts:153-155`）。
- `open-threw`：开会话这一步自己抛了异常（`session-opener.ts:200-202`）。
- `not-wired`：宿主没有注入开会话的装配口（`comment-thread-fetch.ts:68` 与 `:94`）。正常安装不会出现，测试或装配不完整时才会。

其中只有 `multi-match` 会明确写出“多家后端同时认领：谁、谁”。这句话里的“等会话可用后再试”对多命中不成立：等多久认领名单都不会变，重试还是同一个结论。

## 这张图属于哪一种

图片里的文案是：

> 这个工作区的只读会话没开成（multi-match）：多家后端同时认领：markdown、gitlab，等会话可用后再试。

也就是这个工作区同时被 markdown 与 gitlab 两家认领。两家的认领判据分别是：

- Markdown（`src/tracker/rooms/markdown/index.ts:88-157`）：工作区根有 `.scratch/map.md`、`.scratch/spec.md` 或 `.scratch/issues`，或者 `docs/agents/issue-tracker.md` 里写着 Local Markdown。
- GitLab（`src/tracker/rooms/gitlab/index.ts:131-178`）：仓库标识里含 gitlab；或 `.git/config` 的 `[remote ...]` 段里有 gitlab 地址；或 `docs/agents/issue-tracker.md` 里出现 gitlab 字样；或 `git remote get-url origin` 的输出里有 gitlab。

所以图上这个工作区最常见的情形是“代码托管在 GitLab 的仓库，同时用本地 Markdown 管票与地图”：GitLab 由远端地址认领，Markdown 由 `.scratch` 里的地图或声明文件认领。另一种可能是：工作区其实只用本地 Markdown，但声明文件里出现了“gitlab”字样（GitLab 那一处只做了不区分大小写的文本搜索，见 `:158-161`），把 GitLab 也拉了进来。#1533 已经把 `.git/config` 从“全文找 gitlab”收窄成“只看 remote 段的 url”，但文档文本这处没有跟着收紧。

能确认图里这一次是“多命中”而不是别的结局，是因为括号里直接写了 `multi-match` 与两家名字；但“为什么这两家会同时命中”要靠报告人的工作区文件才能定，见本文末尾“还没核实的事”。

## 补充（2026-10-26 晚）：为什么图上是绿色 markdown 芯片、底层却报两家

图不是“GitLab 偷偷变成了当前后端”，而是两套判定各答各的：

1. 头部那枚仓库芯片的颜色取 `sel.backendId`（`src/client/panel/Dock.ts:246-262`），颜色由各后端的 `presentation.color` 派生：markdown `#1a7f37`（绿，`src/tracker/rooms/markdown/index.ts:385-390`）、github `#0969da`（蓝，`src/tracker/rooms/github/index.ts:206-208`）、gitlab `#c25100`（橙，`src/tracker/rooms/gitlab/index.ts:397-402`）。绿色 = 判定层的结论是 markdown。
2. 判定层这一次没有多命中：如果 `selection.multiHit` 有两家，`Dock.ts:317-337` 会在标签行上方画一条黄色「检测到多个可用后端：… — 建议显式绑定」。图上没有这条黄条 → 判定层给的 selection 不带 multiHit → 结论来自“工作区文件 / 声明文件”这一级（那一级命中时自动识别整段被跳过），不是来自自动识别。
3. 红条来自另一条路：`wf.issueDetail` 开只读会话时没有复用判定层的结论（`comment-thread-fetch.ts:67-70`、`:132-133`），会话入口直接调 `registry.select`，把每家后端的 `matches` 从现场重跑一遍；两家都举手就判 `multi-match`（`open-tracker.ts:110-113`）。

也就是说，同一个问题“这个工作区用哪个后端”在代码里有两套答法：面板、快照与工具走“工作区文件 > 声明文件 > 自动识别”（`docs/adr/20260921-tracker-choice-precedence.md` 第 2、3 节定的优先级）；详情与评论的只读会话只问自动识别。图就是这两套答法打架的现场。

### GitLab 会在什么情况下认领（以及哪一条容易误认）

现行判据在 `src/tracker/rooms/gitlab/index.ts:131-178`，四条任一成立就认领：

1. `handle.refId` 里含 `gitlab`（不区分大小写）。正常探测只给 `cwd`，这一条基本走不到；只有调用方拿仓库标识当句柄时才会。
2. `.git/config` 里任一 `[remote "..."]` 段的 `url` 含 `gitlab`。**远端名字不限 origin**（`tests/verify-1533-git-remote-claim.ts:117-123` 明确写着“远端名字不限 origin”），所以“origin 是 GitHub、另加了一个 GitLab 镜像 remote”也会被认领。
3. `docs/agents/issue-tracker.md` **全文**含 `gitlab`（不区分大小写）。这一条没有区分“声明用它”与“只是提到它”：标题写的是 GitHub 或 Local Markdown，正文里只要出现一次 GitLab 字样（例如“GitLab 的 MR 不参与分诊”、迁移说明、留下的一行旧注释），GitLab 就认领。`:158-161` 就是这一条。
4. 兜底跑一次 `git remote get-url origin`，输出含 `gitlab`。

对比一下同一件事在“声明层”的口径：`src/tracker/detection/parseIssueTracker.ts:33-68` 是**结构化解析**——先看 `# Issue tracker: GitLab` 这种标题行（high），标题都不命中才把正文关键词当 low 兜底，并且 markdown 的正文关键词明确不参与判定（#277）。`matches` 的第三条却退回到整篇文本扫一遍 `gitlab`，把“提到”当成“声明”。这是两个口径不一致，也是误认领最可能的入口。

### 一个很可能被踩中的现场：切换后端后锚文件没改

`docs/adr/20260921-tracker-choice-precedence.md` 第 3 节第 5 条写明：插件自己不写用户的仓库文件；“把文件对齐”交给初始化那只 AI（切换时注入一条 prompt 让它去改）。所以如果用户在面板里从 GitLab 切到 markdown、但那段对齐 prompt 没有真正跑完，`docs/agents/issue-tracker.md` 里仍会留着 GitLab 模板的内容。之后：

- 判定层：工作区文件 `docs/agents/workspace.yaml`（markdown）优先，锚文件只算“冲突证据” → 绿色芯片、没有 multiHit 黄条；
- 自动识别：GitLab 那一路读到锚文件里的 GitLab 字样，仍然认领；markdown 那一路读到根级 `.scratch` 标记或 Local Markdown 声明，也认领 → 两家；
- 详情/评论开会话时正好只问自动识别 → `multi-match` 红条。

### 最小复现（临时脚本，未入库）

用仓库真实模块（`explicitDetector`、`gitlabBackend.matches`、`markdownModule.matches`、`githubMatches`）在临时目录里拼三种工作区，结果如下：

| 现场 | 判定层（芯片/黄条看它） | 自动识别（会话看它） |
| --- | --- | --- |
| A：锚文件遗留 GitLab 模板 + 工作区文件选 markdown + 根级 `.scratch/map.md` + 非 GitHub/GitLab 远端 | `{backendId:'markdown', source:'explicit'}`（无 multiHit） | `{markdown:true, gitlab:true}` → 与图一致 |
| B：锚文件正确写 Local Markdown + 远端真是 GitLab | `{backendId:'markdown', source:'explicit'}`（无 multiHit） | `{markdown:true, gitlab:true}` → 同样的红条，但 GitLab 不是误认 |
| C：GitHub 远端 + 名字带 gitlab 的分支 | `{backendId:'github'}` | `{github:true, markdown:false, gitlab:false}` → #1533 之后这一类已不会误认 |

A 与 B 在界面上长得一模一样（绿芯片 + multi-match 红条），区别只在“GitLab 是不是真的该认领”。要知道报告人属于哪一种，仍然需要他那边的两个文件（锚文件与工作区文件）和 `.git/config` 的远端地址。

## 升级前后的差别（为什么 beta.8 能读、beta.24 读不了）

- 旧路（v1.9.0-beta.8 时的 `src/host/commentThreads.ts`，也就是现在 `comment-thread-fetch.ts` 的前身）：`handleIssueDetail` 先调 `selectEarly({cwd, backendId})` 拿统一判定的结论，`isComposerSelection(sel)` 判过之后直接 `reg.get(sel.backendId)`，再调 `tracker.get(...)` 读票。统一判定会把多家认领按明文顺序（GitHub > Markdown > GitLab，`src/tracker/detection/backendDecision.ts:349`、`:558-581`）裁成一个后端并如实带出名单；**读操作本身不会因为“多家认领”被拒绝**（当时的判定笔记也写着“两条读用途的电话照常能走，multiHit 只在写用途上被拦”，见 `research/1047-detection-cost-and-write-facts.md`）。
- 新路（v1.9.0-beta.12 起，提交 `e31124e1`）：同一条电话改成 `openReadSession(cwd)` → `deps.openSession(cwd)`（`comment-thread-fetch.ts:67-70`、`:132-133`），开会话时**没有把统一判定的结论带过去**，走的是注册表原始认领（`session-opener.ts:176` 的 `matchContext` 分支）；而会话入口对多命中是硬拒绝（`open-tracker.ts:110-113`）。
- 用 `git show e31124e1 -- src/refresh/rooms/host/comment-thread-fetch.ts` 可以看到旧代码里的 `selectEarly` 与 `tracker.get` 被整段删掉，换成 `openReadSession` 与新的失败文案；这次提交就是 beta.12 的“刷新后台六条读路径改走 Tracker 只读会话”。
- 结论：**同一批子票，在 beta.8 上走统一判定能读，在 beta.24 上走“不带判定结论的会话”会被多命中挡掉**。升级跨越的正是 beta.12，不是 beta.24 本身新增的哪一条。
- 为什么面板其他部分还能显示：列表与地图的快照路径会把判定结论交给会话（`src/refresh/rooms/host/snapshot-build.ts:303-335` 取判定，`:430-432` 开会话时传 `resolveSelection`），工作区文件或声明文件已经定了后端时，那一份结论不带多命中名单，会话能开；详情与评论这条路径没有这一步，所以只有它失败。反过来说，如果这个工作区只靠“自动识别多命中”而没有工作区文件或声明文件，那么快照也会失败，图里能看到的列表就只可能来自磁盘缓存——两种情况都指向同一个缺口：详情与评论没有复用统一判定。
- 这里还有一个会让人白等的细节：即使人在面板里“切换后端”选定一次（写进 `docs/agents/workspace.yaml`），详情与评论这条路径仍然不会读那份选择，因为会话是从注册表的原始认领重新选的。也就是说，今天这条路径在多命中工作区上是死路，重试与换后端都救不了。这是本次核对到、值得当成修复主线的一条事实。

## 还没核实的事（需要报告人补充）

1. 这个工作区的 `docs/agents/issue-tracker.md` 与 `docs/agents/workspace.yaml` 各写了哪个后端。
2. `git remote -v`（或 `.git/config` 的 remote 地址）里有没有 gitlab；这是不是真的一个 GitLab 仓库。
3. 工作区根 `.scratch/` 下有没有 `map.md`、`spec.md`、`issues/`，地图是不是在 `.scratch/<地图名>/map.md`。
4. 打开调试日志后搜 `read.session`，最近几条的 `reason` 是不是都是 `multi-match`（这个事件是调试级，要在设置里打开调试日志才会记；它只记 `ok` 与 `reason` 两格，定义见 `research/489-appendix.md:413`）。
5. 升级前（beta.8）在同一批子票上，正文与评论能不能正常显示——用来确认“升级前后读路径不同”这个判断在报告人的机器上成立。

## 建议的分流

- 分类：`bug`。这是读路径不读统一判定结论造成的功能缺陷，不是报告人的用法问题。
- 状态：建议先 `needs-info`（向报告人取上面五项证据），证据齐后再转 `ready-for-agent`。如果维护者认为“详情/评论必须复用统一判定”这条已经足够明确，也可以直接 `ready-for-agent`，但修法的边界要一起定。
- 可能的修法（留给实施时拍板）：
  - A. 最小改动：`comment-thread-fetch.ts` 开会话时用宿主仍在注入的 `selectEarly` 拿统一判定结论（这个依赖今天还在接口上，只是没被用），把定下来的后端交给会话；和快照、工具那条路一致。
  - B. 把“复用统一判定”下沉到 `session-opener` 或 `openTracker`，让所有没显式传选择的读路径都先问一次判定；影响面更大，但能顺带覆盖刷新探测这些同样会踩多命中的路径。
  - C. 只改文案（告诉人去面板选定后端）不行：今天选定后端也救不了这条路径，见上文。
- 另外建议单独评估 GitLab 的认领判据，不要和读路径的修复混成一票（`src/tracker/rooms/gitlab/index.ts:158-161`）：`matches` 现在把“锚文件里出现 gitlab 字样”当成认领依据，与 `parseIssueTracker` 的结构化口径不一致；且切换后端后锚文件可能仍是旧模板（ADR 20260921：插件不写用户仓库文件，靠注入 prompt 让 AI 对齐）。修法有两档：A. 把 `matches` 收回“现场事实”（只看远端地址，把声明文件交给声明层），最小、与 ADR 对自动识别的定义一致；B. 至少改成结构化解析，不拿整篇文本扫 `gitlab`。无论哪档，都建议再加一条“判定层发现用户选择与锚文件冲突时如实显示出来”，别只落日志。
