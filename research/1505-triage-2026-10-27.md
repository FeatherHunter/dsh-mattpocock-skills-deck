# #1505 分流诊断：环境检查「已登录 GitHub」在「已选 github、目录还没有 .git」时为什么恒为 pending（2026-10-27）

调查范围：票 #1505 的正文与唯一一条评论（作者 TangSuann，2026-10-25 创建，无标签）；仓库 main（调查时 HEAD `6f823f84`，`package/package.json` 版本 1.9.0-beta.26）；`src/` 里检查链求值、环境探针、会话装配、注册表选择与三个后端认领判据的源码；`tests/` 里相关门禁；`package/` 与 `.build/` 里同一文件的产物；git 全分支历史与 `research/` 下既有笔记。本次只做诊断，没有改业务代码、没有开始实施；唯一的新文件是本笔记与 `.scratch/1505-repro/repro.ts`（临时复现脚本，被 `.gitignore` 的 `.scratch/` 忽略，不入库）。

## 一句话结论

最新 main 上这条缺陷仍在，而且可以用当前源码原样复现：判定层已经从 `docs/agents/workspace.yaml` 读出「用户选了 github」，但检查链在造环境探针时没有把这份选择交给只读会话；会话入口只拿目录去问注册表的 `matches` 认领，一个还没有 `.git` 的新目录没有任何后端认领，于是回 `no-backend`，探针落到 `stage:"none"`，两个环境谓词共用报告里那句「读会话还没接上」的 pending。报告人的根因分析与真机证据在源码上逐环成立；本条与 #1468 不是同一处，#1468 修的是「会话交来的操作上下文被丢掉」，本条的会话根本没开出来。

## 当前源码上的这条链（逐环）

1. 判定层：`detectionService` 读 `docs/agents/workspace.yaml`（`src/tracker/detection/detectionService.ts:218`），显式层把 `backendId: github` 认成 `selection: {backendId:'github', source:'explicit'}`（`src/tracker/detection/explicitDetector.ts:58-77`）。检查链在 `check-chain-evaluation.ts:296-310` 拿到 `selDetected`，`backendId` 因此是 `github`。
2. 探针：`check-chain-evaluation.ts:314` 调 `createChainEnvProbe(cwd, backendId)`；`:143` 只把 `{backendId}` 交给 `probeChainEnv`；链求值里已经算出的 `selConsistent` 在 `:344` 才出现，没有交给探针（顺序上探针先生成）。
3. 探针开会话：`chain-env-map.ts:240-248` 的 `openOnce` 只调 `openSession(probeCwd)`，一个 `opts` 都不传；`ChainEnvProbeOptions`（`:215`）也只有 `backendId` 一格。
4. 会话装配：`session-opener.ts:176` 只有在调用方给了 `resolveSelection` 时才交给 `openTracker`，否则传 `matchContext`；`open-tracker.ts:99-101` 的缺省实现就是 `registry.select`。
5. 注册表选择：`registry/core.ts:164-208` 只并行问各房 `matches()`，没人认领就回 `{backendId:null, source:'fallback'}`，不读工作区文件、不复用判定结论。
6. GitHub 的认领判据：`src/tracker/rooms/github/backend.ts:67-96` 要 `.git/config` 的 remote 段指向 github、或 `git remote get-url origin` 指向 github、或 `handle.refId` 含 `/`；三者都没有就 false。报告现场正是三者都没有。
7. 结局：`openTracker` 回 `no-backend`（`open-tracker.ts:103-109`）→ `openSession` 回 `{ok:false, reason:'no-backend'}` → 探针 `preflightOnce` 回 `{stage:'none'}`（`chain-env-map.ts:304`）→ `ghAuthVerdict` 落到 `:154` 的兜底 pending，`repoAccessVerdict` 落到 `:130` 的兜底 pending。
8. 对照（同仓其它开会话的调用点都做对了）：`snapshot-build.ts:236-239` 与 `:430-432` 会把判定结论当 `resolveSelection` 传下去；`workspaceCwd.ts:80` 与 `workspaceLabelColors.ts:238` 也各传了一份。只有检查链这只探针漏了这一格。

## 对抗式复核（2026-10-27 第二次）：原建议要改两处

按「一次链求值只有一个后端决定」这条公理重新审了候选修法，并用当前源码实测了几条关键分支（脚本 `.scratch/1505-repro/repro-fix.ts`，未入库）：

1. **报告人建议的「把 selConsistent 原样交给探测」不能直接采纳**：`selectionFromOutlet` 会把 `multiHit` 与 `pending` 原样带出（`src/tracker/detection/backendDecision.ts:387-400`），而 `openTracker` 拿 `resolveSelection` 的结论后仍会按这两格否掉会话（`src/tracker/session/open-tracker.ts:110-117`）。实测：选择里带 `multiHit:['github','markdown']` → `ok:false reason:"multi-match"`；带 `pending:true` → `ok:false reason:"pending"`。照原建议写，只有「显式/声明层」这类不带仲裁字段的选择能被修好；自动识别多命中的工作区仍会恒 pending（与 #1555 同族）。正确的传递物是「链已经定下的那个 backendId」本身，不是判定层的整份选择对象。
2. **修在调用点，不修在 `session-opener`**：`session-opener` 手里没有判定层（依赖只有注册表、账本、后端上下文），要把判定塞进去就得新增依赖，并在每次开会话时重复跑一次判定；这既重复成本，也让「谁做的决定」变模糊。同族缺口（#1555 的详情/评论路径）更适合另开一张「开会话必须带上判定结论」的审查票，逐调用点清单化，而不是在会话入口里自动兜底。
3. **不改 `githubMatches` 去读工作区文件**：注册表的职责是「本地认领」，人选那一层明确归唯一判定出口（`src/tracker/registry/core.ts:177-180` 的注释）；把选择塞进认领等于在注册表里重造一套判定。
4. **修好以后，面板 tooltip 那条大概率不用单独立票**：报告人说 tooltip 指向「红牌」而卡住的是黄牌（登录行）。修好后登录行转绿、红牌正是「已关联仓库 / 仓库可访问」两行，指向反而正确了。等修完复核一次，再决定要不要动文案。

### 建议的修法（A′，改在 `check-chain-evaluation.ts` 的 `createChainEnvProbe`）

链求值里 `backendId` 已经定下（`:296-310`）。在造探针时，把传给 `probeChainEnv` 的 `openSession` 能力包一层：`backendId` 非空时调用 `openSession(cwd, { resolveSelection: async () => ({ backendId }) })`，为空时维持原样。只传 `backendId` 一格，不传 `multiHit`/`pending`/旧 ref。`probeChainEnv`、`openTracker`、`session-opener`、注册表与三个后端都不用改。

实测这条修法的效果（假外部世界：gh 已登录、仓库不存在）：

```text
openSession(no-git, selection=github) = {"ok":true,"backendId":"github"}
probeChainEnv.preflightOnce = {"stage":"repo","kind":"not-found",...,"refId":""}
ghAuthVerdict = {"status":"pass","detail":"已登录（仓库可达性由下一项判断）"}
repoAccessVerdict = {"status":"fail","detail":"GitHub 上访问不到该仓库（可能还没创建，或你没有权限）"}
```

这正是票面期望：登录行转 pass，仓库两行红；`stage` 不是 `none`，不再落「读会话还没接上」。

**代价（实测）**：这一状态下每次链求值会打 1 次 `git remote get-url`（开会话补仓库身份）、2 次 `gh repo view`（开会话补身份 1 次 + 预检第 3 关 1 次）、1 次 `gh auth status`。其中 2 次 `gh repo view` 是重复的（都因为缺 refId），量不大、状态也主要在「建仓库之前」出现；先接受，若日志或账本上看出明显浪费，再另开票给开会话口加「这次不用补仓库身份」的开关，不塞进本票。

### 验收与门禁（建议写进 agent brief）

1. 无 `.git` + `docs/agents/workspace.yaml` 写明 `backendId: github`：探针 `preflightOnce()` 不得回 `stage:'none'`；假 gh 为已登录时 `ghAuthVerdict` = `pass`（「已登录（仓库可达性由下一项判断）」）。
2. 同一目录补 `.git` + github 远端：行为不比今天差（`stage` 走到 `pass` 或 `repo`，登录行 pass）。
3. 没有后端结论（判定层空、`args.backendId` 也为空）：维持现状，不凭默认 `github` 伪造会话（探针仍回 `stage:'none'`）。
4. 反向门禁：把 `openSession` 换回「只给 cwd 的实现」时，第 1 条断言必须变红 —— 保证门禁测的是接线，不只是文案。
5. 既有门禁 `verify-916-ghauth-crosscheck`、`verify-1475-predicate-budget`、`verify-chain-env-e2e`、`verify-1444-chain` 全绿。
