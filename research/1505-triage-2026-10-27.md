# #1505 分流诊断：环境检查「已登录 GitHub」在「已选 github、目录还没有 .git」时为什么恒为 pending（2026-10-27）

调查范围：票 #1505 的正文与唯一一条评论（作者 TangSuann，2026-10-25 创建，无标签）；仓库 main（调查时 HEAD `6f823f84`，`package/package.json` 版本 1.9.0-beta.26）；`src/` 里检查链求值、环境探针、会话装配、注册表选择与三个后端认领判据的源码；`tests/` 里相关门禁；`package/` 与 `.build/` 里同一文件的产物；git 全分支历史与 `research/` 下既有笔记。本次只做诊断，没有改业务代码、没有开始实施；唯一的新文件是本笔记与 `.scratch/1505-repro/repro.ts`（临时复现脚本，被 `.gitignore` 的 `.scratch/` 忽略，不入库）。

## 一句话结论

最新 main 上这条缺陷仍在，而且可以用当前源码原样复现：判定层已经从 `docs/agents/workspace.yaml` 读出「用户选了 github」，但检查链在造环境探针时没有把这份选择交给只读会话；会话入口只拿目录去问注册表的 `matches` 认领，一个还没有 `.git` 的新目录没有任何后端认领，于是回 `no-backend`，探针落到 `stage:"none"`，两个环境谓词共用报告里那句「读会话还没接上」的 pending。报告人的根因分析与真机证据在源码上逐环成立；本条与 #1468 不是同一处，#1468 修的是「会话交来的操作上下文被丢掉」，本条的会话根本没开出来。

## 当前源码上的这条链（逐环）

1. 判定层：`detectionService` 读 `docs/agents/workspace.yaml`（`src/tracker/detection/detectionService.ts:218`），显式层把 `backendId: github` 认成 `selection: {backendId:'github', source:'explicit'}`（`src/tracker/detection/explicitDetector.ts:58-77`）。检查链在 `check-chain-evaluation.ts:296-310` 拿到 `selDetected`，`backendId` 因此是 `github`。
2. 探针：`check-chain-evaluation.ts:314` 调 `createChainEnvProbe(cwd, backendId)`；`:143` 只把 `{backendId}` 交给 `probeChainEnv`；链求值里已经算出的 `selConsistent` 在 `:344` 才出现，没有交给探针（顺序上探针先生成）。
3. 探针开会话：`chain-env-map.ts:240-248` 的 `openOnce` 只调 `openSession(probeCwd)`，一个 `opts` 都不传；`ChainEnvProbeOptions`（`:215`）也只有 `backendId` 一格。
4. 会话装配：`session-opener.ts:176` 只有在调用方给了 `resolveSelection` 时才交给 `openTracker`，否则传 `matchContext`；`open-tracker.ts:99-101` 的缺省实现就是 `registry.select`。
5. 注册表选择：`registry/core.ts:164-208` 只并行问各房 `matches()`，没人认领就回 `{backendId:null, source:'fallback'}`，不读工作区文件、不复用判定结论。
6. GitHub 的认领判据：`src/tracker/rooms/github/backend.ts:67-96` 要 `.git/config` 的 remote 段指向 github、或 `git remote get-url origin` 指向 github、或 `handle.refId` 含 `/`；三者都没有就 false。报告现场正是三者都没有。
7. 结局：`openTracker` 回 `no-backend`（`open-tracker.ts:103-109`）→ `openSession` 回 `{ok:false, reason:'no-backend'}` → 探针 `preflightOnce` 回 `{stage:'none'}`（`chain-env-map.ts:304`）→ `ghAuthVerdict` 落到 `:154` 的兜底 pending，`repoAccessVerdict` 落到 `:130` 的兜底 pending。
8. 对照（同仓其它开会话的调用点都做对了）：`snapshot-build.ts:236-239` 与 `:430-432` 会把判定结论当 `resolveSelection` 传下去；`workspaceCwd.ts:80` 与 `workspaceLabelColors.ts:238` 也各传了一份。只有检查链这只探针漏了这一格。

## 复现（临时脚本，未入库）

脚本：`.scratch/1505-repro/repro.ts`。它用当前 `src/` 的真装配跑：真注册表 + 真三个内置后端（经 `src/tracker/registry/builtins.ts` 装配）、真 `createSessionOpener`、真 `probeChainEnv`，判定层用真 `detectExplicit`；只把「外部世界」换掉（平台文件服务读本机临时目录，`exec` 一律按「不是 git 仓库」失败，不联网、不起真 gh）。临时工作区里写的是插件自己会写的 `version: 2 / backendId: github / source: user`，没有 `.git`。

运行（Node v24.19.0）：`node --import ./scripts/ts-hook.mts .scratch/1505-repro/repro.ts`

输出原文：

```text
registered backends: github,markdown,gitlab
detectExplicit.selection = {"backendId":"github","source":"explicit","ref":{"backend":"github","refId":"","name":"ws-no-git","url":""}}
openSession(no-git, no opts) = {"ok":false,"reason":"no-backend","detail":"本地认领问过一圈，没有后端认这个工作区"}
openSession(no-git, resolveSelection=github) = {"ok":true,"backendId":"github"}
probeChainEnv.preflightOnce(no-git) = {"stage":"none","message":"no-backend","refId":""}
ghAuthVerdict(no-git, zh) = {"status":"pending","detail":"读会话还没接上，暂时无法确认登录状态"}
repoAccessVerdict(no-git, zh) = {"status":"pending","detail":"读会话还没接上，暂无法确认仓库可访问"}
openSession(with-git, no opts) = {"ok":true,"backendId":"github","repoRef":{"backend":"github","refId":"acme/demo","name":"acme/demo","url":"https://github.com/acme/demo"}}
```

读法：同一个目录，选择结论是现成的（第一行），但生产开会话口不传它时开不出来（第二行）；把选择显式交给会话就能开（第三行），说明缺的就是这一格；检查链拿到的就是「开不出来」这一种结局（第四、五行），与报告里的 pending 文案逐字相同。补上 `.git` 里的 github 远端后同一份代码自己就能开会话（最后一行），与报告人「建仓库后自愈」的现场一致。

## 建议的分流

- 分类：`bug`。缺陷可复现、根因与修法边界都清楚，不是用法问题。
- 状态：建议 `ready-for-agent`。修复动作小而明确（把链求值已经算出的选择交给探针开会话），验收可以机械核对（无 `.git` + 显式 github 时必须走到 preflight，而不是 `stage:'none'`），适合 AFK agent。
- 修法（留给实施时拍板）：
  - A（最小）：`probeChainEnv` 多收一格「这次求值的结论」，`openOnce` 调 `openSession(probeCwd, { resolveSelection: async () => selection })`；`check-chain-evaluation` 把 `selConsistent` 交给它。注意当前源码里探针在 `:314` 生成、`selConsistent` 在 `:344` 才算出来，要么把归一提前，要么用一个持有器（报告人的本机补丁就是后者），实施时别把顺序写反。
  - B（更稳）：`session-opener` 在 `openTracker` 回 `no-backend`/`pending` 时回落到判定层再开一次；影响所有开会话的调用点，建议另开票，不与本票混。
- 顺带项别混进主修：兜底文案带出 `reason`（`no-backend` / `pending` / `open-threw` 不该压成同一句）与面板黄标 tooltip 指向纠正，建议各拆一张小票；回归门禁建议并进本票（同一个探针、同一条验收链），加在 `tests/verify-916-ghauth-crosscheck.ts` 一类探针级门禁里或新建 `tests/verify-1505-*.ts`。
