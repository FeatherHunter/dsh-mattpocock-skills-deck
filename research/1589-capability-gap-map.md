# 1589 能力差距表：162 条 git 能力对到版本管理页原型

这张表只做一件事：把 `research/1588-git-full-capability-surface.md` 第 2 章里的 162 条用户向能力，逐条对到 `docs/prototype/vc-redesign/` 现在这份可点原型上，说清每条是已经走通、还差流程、只能看、还是完全没有。不改代码，不改文案，也不改术语，只给规格票 #1586 当底稿。

## 1. 结论

162 条里，**已有完整闭环 17 条，有入口但缺流程 35 条，只有只读展示 15 条，完全没有 95 条**。

缺口按「需要新建界面或流程」的口径算（35 + 95 = 130 条）最重的是三个域：**11 仓库维护与迁移（15 条全空）、6 合并变基与冲突（14 条缺口，能点的只有一颗「合并到当前分支」，而且它不判冲突）、8 远端与同步（14 条缺口，能点的只有更新、拉取、推送三颗按钮）**。

17 条闭环集中在三条线上：改动页的暂存与丢弃、提交、拉取与推送，加上工作树的清理与移除。越往历史改写、配置、诊断走，原型越接近空白：12 配置与钩子、10 子模块、14 平台相关都是 8 条全空，11 仓库维护是 15 条全空。

## 2. 怎么读这张表

四类的判定只看原型**现在**的样子，不看 README 里列的计划。

- **A 已有完整闭环**：有可点的入口，并且「预检（禁用加原因，或确认卡写清后果与范围）→ 确认（危险动作）→ 结果贴触发点」三段都在。
- **B 有入口但缺流程**：入口在，但上面三段缺一段，或者这个入口只做了这条能力的一部分（粒度更粗、只做其中一档、少一个选项）。
- **C 只有只读展示**：没有任何可执行入口，但这条能力自己的读数在某个视图里看得见。
- **D 完全没有**：既没有入口，也没有展示位置。

下面五条判例是这次实际卡过的地方，重数时照这五条走，数字就能对上：

1. **读级能力只记 C 或 D**，不记 A 或 B。搜索框、展开、筛选都算「展示手段」，不算执行入口。所以「按说明搜提交」是 C（列表里能筛），不是 A。
2. **同一条 git 命令的其它档位记 B**，不记 D。提交按钮在，`--amend`、`-a`、`--no-verify` 这些档位没有，就是「有入口缺流程」；同理合并的三个档位、拉取的两个档位、变基的五个档位。这是本表 B 数量偏多的主要原因。
3. **动作只做了一半记 B**：新建分支只建不切（4.2）、工作树只能解锁不能加锁（9.6）、解决冲突只有整文件选边且不随变基换方向（6.6）。
4. **信息哪里都看不到记 D**，哪怕同族有控件。分支浮层里没有说明字段，也没有只读展示，所以「分支说明」是 D，不是 B。
5. **C 要求「这条能力自己的读数」可见**，不是「相关的东西」可见。「为什么这个文件被忽略」只看到「已忽略」四个字、看不到命中的规则行，记 D；「领先 / 落后」这两个数直接印在同步带上，记 C。

一个能力被多个入口覆盖时，落点列会把每个入口都写出来，不合并成一句。

### 4.1 工作区与暂存（13 条：闭环 7，缺流程 1，只读 1，没有 4）

| 编号 | 能力 | 级 | 归类 | 原型落点 | 缺口或备注 |
| --- | --- | --- | --- | --- | --- |
| 1.1 | 看工作区状态 `git status --porcelain=v2` | 读 | C | 改动页三组计数与文件行、页签数字、三个筛选 chip | 读级，全部自动展示 |
| 1.2 | 逐块暂存 `git add -p` | 写 | B | 文件行「暂存」只到整文件；行主体展开整份补丁（只读） | 缺块清单、行号与逐块选择，文件内多个改动拆不开 |

| 1.8 | 删除未跟踪文件 `git clean -fd` | 毁 | A | 行菜单「删除这个文件」→ 确认卡 | 缺文件体积与「其中多少条被忽略」 |

| 1.12 | 加进忽略清单 `gitignore` + `check-ignore -v` | 写 | A | 行菜单「加入 .gitignore」→ 确认卡 → 结果条 | 预检不写命中哪条规则、会影响哪些同级文件 |
| 1.13 | 查这条路径为什么被忽略 `git check-ignore -v` | 读 | D | 只有「已忽略」这个归类结果 | 规则文件与行号没有展示位，所以记 D 不记 C |

缺口里最痛的三条：

1. **1.2 逐块暂存**。这是「把一堆改动拆成几条能评审的提交」的唯一手段。原型只能整文件暂存，想拆就得回终端；2.4（fixup 提交）和 5.6（交互式变基）也因此都没有起点。
2. **1.9 删除已跟踪文件**。未跟踪能删、已跟踪反而没有入口。日常「删掉这个文件并记进这次提交」是最常见的提交内容之一，现在只能绕到终端；1.10、1.11 是同一族，三条一起缺。
3. **1.13 查为什么被忽略**。1.12 刚把文件加进忽略，下一步「它为什么还是不出现」就没有答案。`check-ignore -v` 给出的规则文件与行号是排障的第一手证据，面板里只有「已忽略」四个字。

### 4.2 提交（8 条：闭环 1，缺流程 7）

| 编号 | 能力 | 级 | 归类 | 原型落点 | 缺口或备注 |
| --- | --- | --- | --- | --- | --- |
| 2.1 | 提交已暂存内容 `git commit -m` | 写 | A | 提交区说明栏 + 主按钮「提交 N 个文件」，结果条贴提交区，历史首行跟着变 | 预检有（无暂存 / 有冲突 / 没写说明三种都给了原因），但清单不判 merge、rebase、cherry-pick 进行中（`COPY.block` 里备了这三个词却没用上） |
| 2.2 | 提交全部已跟踪改动 `git commit -a` | 写 | B | 提交按钮 | 没有「连未暂存一起提交」这一档 |
| 2.3 | 修订上一条提交 `git commit --amend` | 改写 | B | 提交按钮 / 说明栏 | 没有修订入口；只能走 5.1 撤销再重提 |
| 2.4 | 生成 fixup / squash 提交 `git commit --fixup` | 写 | B | 提交按钮 | 没有目标提交选择，也没有历史行标记 |
| 2.5 | 跳过提交钩子 `git commit --no-verify` | 写 | B | 提交按钮 | 钩子失败时没有任何出口，也看不到哪个钩子失败 |
| 2.6 | 签名提交 / 追加签名行 `git commit -S` | 写 | B | 提交按钮 | 没有签名开关，历史行也不显示「已签名」 |
| 2.7 | 用编辑器写完整说明 `git commit` 不带 `-m` | 写 | B | 提交说明栏（替代方案的一部分） | 只有一栏纯文本，没有标题 / 正文分栏，也没有模板预填 |
| 2.8 | 套用提交说明模板 `commit.template` | 写 | B | 提交说明栏 | 读不到模板路径，也没有预填 |

缺口里最痛的三条：

1. **2.3 修订上一条提交**。提交完发现漏了文件或说明写错，这是最高频的补救。原型只有「撤销这次提交」（5.1）一条路：撤销再重提多一次往返，reflog 上多两条记录，已推送时还会让本地落后远端一步，和「修订」完全不是一回事。
2. **2.5 跳过提交钩子**。钩子失败时提交被卡住，面板连哪个钩子失败、退出码多少都看不到，更别说跳过一次；用户只能去终端加 `--no-verify`。12.5、12.6 也一起缺，钩子整块是黑箱。
3. **2.2 提交全部已跟踪改动**。只暂存了一部分时想「剩下的也一起提交」，得先逐个暂存，或者先「全部暂存」再撤掉不想交的，步骤比命令行多。签名（2.6）对合规仓库同样硬，但影响面比这条窄。

缺口里最痛的三条：

1. **3.5 行级追溯 blame**。读代码时「这行为什么变成这样」是历史页之后最高频的一问，现在连入口都没有；它也直接决定诊断页要不要存在。
2. **3.4 单文件历史**。改过的文件想回看它这几版怎么变，只能逐条打开提交翻 diff，成本随提交数线性上涨，300 到 520 宽的面板里尤其难受。
3. **3.10 版本名 describe**。顶部身份条只有短号，没有版本名；发布、对版本、贴给别人看都缺一个稳定标签，而它本来只是身份行上的一行读数。

缺口里最痛的三条：

1. **5.6 交互式变基**。把一串「改一下」「再改一下」整理成几条能评审的提交，是版本管理页的核心价值。原型只有「变基到这里」一种整体重放，没有提交清单、改说明、压缩、丢弃、重排；2.4 生成的 fixup 提交也会无处安放。
2. **5.3 硬重置**。毁级动作，需要「会丢哪些未提交改动」的预检和不可逆确认。提交行菜单本该是它的位置，现在没有这一项；用户会退而用「撤销」再加丢弃，路径更危险也更绕。
3. **5.2 撤销提交并取消暂存**。撤销只有 soft 一档（改动回暂存区）。想「改动回工作区、重新挑着暂存」做不到，而这一步正好接 1.2 的逐块暂存。

2. **8.1 远端列表**。8.2、8.3、8.4 三条全挂在它上面。没有远端列表，就没有「这是哪个远端、地址对不对、远端还有哪些分支」这些判断依据；克隆（8.16）与凭据（8.15）的失败也因此无从排查。

缺口里最痛的三条：

1. **9.2 新建工作树**。整个「多开」页签只能看和清理，不能开。想并行做两件事（一边跑测试、一边改代码）的人，第一步就得回终端；9.3 跟着一起缺。
2. **9.3 用已有分支建工作树**。这是工作树最常用的用法：把远程分支或旧分支摊到另一个目录。「新建」只能从当前提交开新分支，等于绕开了工作树的主要价值。
3. **9.6 加锁**。只有解锁，没有加锁。锁的意义是「别动这个目录」，界面却只在你已经锁上之后才认识它；状态词「已被占用」也没说清是锁还是别的原因。

## 5. 改名对照表：原型的叫法对不上能力名的地方

这张表只做对照，供规格取舍用。术语先不落地，代码里的名字和文案一个字都不改。

分两种不一致：**同一个动作两个叫法**（能力名一个、界面另一个，或者界面自己就有两套），**一个叫法覆盖多条能力**（一颗按钮或一个词同时被几条能力引用，界面上分不开）。表中间一列写清是哪一种。

| 原型叫法 | 出现在哪 | 对应能力 | 不一致在哪 | 规格要定的事 |
| --- | --- | --- | --- | --- |
| 更新 | 同步带 | 8.5 抓取 | 一个动作两个叫法：能力名「抓取」，git 叫 fetch；「更新」还会和「重新读取」混 | 只留一个叫法，并把「重新读取」（本地重读）与「抓取」（连远端）彻底分开 |
| 撤回 / 全部撤回 | 已暂存行尾、已暂存组头 | 1.5 撤回暂存 | 一个动作两个叫法；单独一个「撤回」容易被读成「撤销提交」 | 统一成「从暂存区拿回」，别和 5.1 的「撤销」共用词根 |
| 丢弃修改 / 丢弃全部 | 改动行菜单、未暂存组头 | 1.6、1.7 丢弃工作区改动 | 一个叫法覆盖两个范围（单个文件 / 全部），而且和贮藏的「丢弃」同词不同后果 | 先说清丢的是什么（工作区改动），再说清范围 |
| 丢弃 | 贮藏行 | 7.9 删贮藏记录 | 同一个词，1.6 丢的是工作区改动、这里删的是一条记录 | 两个「丢弃」必须能区分：丢改动 / 删记录 |
| 删除这个文件 | 未跟踪行菜单 | 1.8 删除未跟踪文件 | 「删除」一词覆盖 1.8、1.9、4.6、7.9、8.11、9.4、10.7 七条能力 | 说清删的是磁盘文件、git 记录、还是登记 |
| 撤销这次提交，改动留在暂存区 | 提交行菜单 | 5.1 撤销上一条提交 | 与下一行的「回退这次提交」只差一个字，后果完全相反（丢提交 vs 新增反向提交） | 「撤销」「回退」「还原」三个词只留一个给 reset，另一个换掉 |
| 回退这次提交 | 提交行菜单 | 5.4 反向提交 | 同上；中文里「回退」常被理解成 reset | 换成能看出「新增一条反向提交」的说法 |
| 拣选到当前分支 | 提交行菜单 | 5.5 拣选提交 | 一个动作两个叫法：能力名「拣选提交」，git 叫 cherry-pick；方向词倒是对的 | 保留「到当前分支」这半句，它是唯一把方向说清的部分 |
| 变基到这里 | 分支详情 | 5.6 交互式变基（最简形态） | 「到这里」指目标分支，但被搬的是当前分支；「变基」一词在 5.7–5.10 四条里共用 | 写明「把当前分支的提交搬到 X 之上」，并说清提交号会变 |
| 合并到当前分支 | 分支详情 | 6.1 合并分支 | 方向与能力名相反（能力名以被合进来的分支为主语） | 统一成「把 X 合进当前分支」这一种句式 |
| 新建分支 | 分支列表头 | 4.2 新建并切换 | 能力名说「新建并切换」，实际只建不切；结果条自己承认「还没有切换过去」 | 要么补上切换，要么把名字改成「只新建」并说清下一步 |

## 6. 复核方法：怎样重数一遍得到同样的数字

按下面六步走，任何人拿这份笔记和 `research/1588-git-full-capability-surface.md` 都应得同一组数。

1. **先数条数**。1588 里十四个域的表格行数依次是 13、8、13、13、13、15、10、16、8、8、15、8、14、8，相加 162；本文 §4 十四张表的行数应与之一一对应，合计也是 162。两边对不上，先查是不是漏抄或重抄了某一行。
2. **数分类**。把 §4.1–§4.14 每张表「归类」列数一遍，应得闭环 17、缺流程 35、只读 15、没有 95，合计 162。再看 §4.0 的并排表：四列各自相加也应是这四个数，逐域那一行也要和对应小节一致。
3. **遇到边界行照判例走**。§2 的五条判例是：读级能力只记「只读」或「没有」；同一条 git 命令的其它档位记「缺流程」；只做一半的动作记「缺流程」；信息在任何位置都看不到记「没有」（哪怕同族有控件）；「只读」要求这条能力自己的读数可见。容易判错的几行是 1.13、4.4、4.7、6.8、9.6，复核时优先看它们。
4. **缺口口径跟着数字一起引用**。本文的「缺口」= 缺流程 + 没有（要新建界面或流程），只读算轻缺口。按这个口径排：域 11 是 15，域 6 与域 8 各 14，域 5 是 12，域 13 是 10，域 3 是 9，域 4、10、12、14 各 8，域 2、7 各 7，域 1、9 各 5。若只按「没有」排，前三名会变成域 11（15）与域 3、8、13（各 10，并列），结论会变——所以引用结论时必须带上口径。
5. **三条交叉核对**。（a）闭环的 17 条必须都能在 §3 索引一的「覆盖能力」一列里找到至少一个控件；（b）「没有」的 95 条不应出现在这一列，出现了就说明其实有入口，归类要改（注意别用整段文本搜编号：13.11 里含「3.11」，1.12 的备注里含「1.13」，按列看才准）；（c）「只读」的 15 条必须能在 §4 的落点列找到具体展示位置，落点写「无」的不能算只读。
6. **分歧要登记**。有些行是「控件族在、这条能力项没有」，例如 4.7（分支行显示上游）与 6.8（行尾显示暂存），落点写的是控件族而不是某个具体动作。这类行在规格里要单独确认，不能当成「已有入口」直接跳过。
