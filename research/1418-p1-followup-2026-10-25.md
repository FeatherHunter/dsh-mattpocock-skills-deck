# #1418 P1 复核整改与验收口径（2026-10-25）

一句话：P1 首版提交 `1a5b7308` 之后的两轴评审指出四处缺口（写操作通道判错、退避没盖住面板开着的活跃拍、拒绝文案只改了一半、日志附录没同步）。本文记的是逐条复核结论、改动依据与剩下的真机验收口径，供下一轮接手的人直接对照。

## 1. 写操作到底走哪条通道（本轮的硬证据）

用 `GH_DEBUG=api` 对 gh CLI 2.x 逐条实测了写子命令的 HTTP 落点（2026-10-25 本机）：

| 操作 | 房间里的实现 | 实测请求落点 | 判定 |
|---|---|---|---|
| create | 幂等锚回查 `gh search issues` / `gh issue list`（`idempotency.ts`）→ `gh api repos/<o>/<n>/issues --method POST`（`issues-write.ts` 主路） | 回查 GraphQL、写 REST | 两族都要 |
| update | `gh issue edit --title/--body` | `POST https://api.github.com/graphql` | 只看 GraphQL 点数 |
| setLabels | `gh issue edit --add-label/--remove-label` | 同上（graphql） | 只看 GraphQL 点数 |
| setAssignees | `gh issue edit --add-assignee/--remove-assignee` | 同上（graphql） | 只看 GraphQL 点数 |
| close | `gh issue close` | 同上（graphql） | 只看 GraphQL 点数 |
| reopen | `gh issue reopen` | 同上（graphql） | 只看 GraphQL 点数 |
| comment | 先 `gh api repos/.../issues/<n>/comments`，失败回落 `gh issue comment` | REST 先、GraphQL 兜底 | 两条路任一可用即可 |
| setParent | 先 `gh issue edit --parent`；REST 退路只在 gh 不认 `--parent`（unknown flag）时走 | GraphQL（前置读与写都在 GraphQL） | 只看 GraphQL 点数 |
| setBlockedBy | 先 GraphQL mutation，失败回落 REST `dependencies/blocked_by` | GraphQL 先、REST 兜底 | 两条路任一可用即可 |

结论：`familiesOfOp` 原来「写一律算 REST」是错的，`update / setLabels / setAssignees / setParent / close / reopen` 在 REST 见底时本来就能做。

**不能只看「最后那条写命令」**（复核第二轮补）：一次操作里还有前置读。建票的写那一步是 REST，但建前必跑幂等锚回查（`gh search issues` 与 `gh issue list`，都是 GraphQL），所以它同时依赖两族；setParent 的前置读与写都在 GraphQL 上，REST 退路只用于老版本 gh 不认 `--parent` 的场景，配额耗尽不会换路，所以它只看 GraphQL。据此分三组：两族都要（create）、只看 GraphQL（update / setLabels / setAssignees / setParent / close / reopen）、两条路任一（comment / setBlockedBy）。

## 2. 条件请求（ETag / If-None-Match 304）这一条现在怎么算

票面原始验收里写的是「ETag / If-None-Match，没有变化时 304 不计入 REST 配额」，那是**探测还在走 REST 时**的说法。P0 之后探测的索引扫描只发 `gh api graphql`（POST /graphql），GraphQL 没有文档化的条件请求机制；REST 才有「304 不计入配额」（GitHub 文档：https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#use-conditional-requests-if-appropriate ）。

等价效果由 `since` 窗口承担：2026-10-24 22:14 用同一查询实测「带 since、0 条变化」时只有 **1 页、cost=1 点、hasNextPage=false**。也就是说「没有变化时探测花多少」这条验收改成「稳态每拍 1 页 1 点」，用真机日志里的 `gh.exec` points 直接核对，不再要求 304。这条改动是 AI 按维护者「技术细节由 AI 拍板」的口径定的。

## 3. 记账口径的遗留差口（不属本票范围，记一笔）

本仓账本目前把「`gh issue edit` 这类 gh CLI 子命令」记成 1 条 REST 请求（`outbound-tiers.ts` 的 `isGraphqlGhArgs` 只认 `api graphql`），但它们实际花的是 GraphQL 点数。对真机影响的量级很小（写操作一条一次、低频），不影响「按族准入」的正确性；要修得给 gh 子命令判 GraphQL 并估点数，属于记账口径新一轮的事，建议单独立小票，不在 #1418 里顺手改。

## 4. 真机 2 小时验收要看什么

- 探测节拍与退避：`probe.loop`（常驻）。`reason=scheduled / no-timer` 是排没排上；`backoff` 是连续无变化拉开一档；`backoff-reset` 是探到变化 / 人回到前台 / 换了工作区后复位。`intervalMs` 是当时那一档的间隔。
- 每族用量：`quota.spend`（调试级，字段 `bucket requests points remaining`）按桶记；`gh.exec` 记每一条外部命令的 `points` / `pointSource`。真机验收可以直接看 REST/GraphQL 两族有没有被探测无产出地推到底。
- 面板新鲜度：`snapshot.built` 与界面「上次更新」的时间戳推进。
- deck 工具被误停：`refresh.skipped` / 工具回执里的 defer 文案（现在会写出缺的是哪种额度、约几点恢复）。

## 5. 这一轮改了什么（提交见票面进度）

1. `budget-admission.ts`：写操作按上表分 `all`（缺一不可）/ `anyOf`（任一条路）两组判；文案改成「额度见底：REST 请求额度不够了（约 HH:MM 恢复），这次先不执行。」，不再用「族 / 桶 / 保底」这类内部叫法。
2. `refusal-messages.ts` + `refresh-gate.ts`：闸自己的拒绝文案补上「缺的是哪种额度、约几点恢复、还剩多少」，额度短名与「点/条」单位从桶上取。
3. `client-attention-heartbeat.ts` + `refresh-timer.ts`：退避基数可传。后台 60 秒拍按 60/60/120/300/600 秒拉长；面板开着、宿主说 5 秒档的活跃拍按 5/5/10/25/50 秒拉长，有变化或人回到前台立刻回 5 秒。
4. `admission-policy.ts`：删掉过时的「含二级限流的 Retry-After」说法（生产路径没有二级限流信号来源）。
5. `tracker-session.ts`：deck 工具开会话前的预检按「读数里余量更多的一族」选桶，不再让一族见底把另一族还能做的写挡在门外；真正按操作拦截在每次操作过管线时做。
6. 日志附录第 1 章 #123 probe.loop 同步两档新 reason 与落点。
7. 门禁 `verify-1418` 扩到 99 条断言（新增：写操作按通道放行/拦截、两条通道见底的文案、活跃拍退避基数、复位日志、闸拒绝文案）。

## 6. 没做的（有意留下）

- 真机连续 2 小时 soak：要有装了本轮改动的 beta 版本 + 人按日常方式使用，只能由人做（票面人工档位 = 需人工测试）。
- P0 第 4 条「`client.ts` 失败分支把 stderr 原文落日志」：不做。日志契约明写上游报错原文不记（`read.degraded` / `gh.exec` 的登记口径），现在失败原因已有判档（`kind` / `errorKind`）与脱敏散列，定位够用；真要原文另立「异常现场按需日志」小票，先定脱敏与保留期。
