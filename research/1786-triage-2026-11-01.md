## 根因链（逐环节，带出处）

### 一、守卫在哪判、判什么

- `template-guard.ts:30` 定义四段名：Parent、What to build、Acceptance criteria、Blocked by。
- `template-guard.ts:39` `remoteTemplateSections(body)`：非字符串给空数组；逐行扫描，遇到三反引号围栏跳过；只收二级标题；空白折叠、转小写；按段名去重（`:53`），保持出现顺序。
- `template-guard.ts:85-98`：`REFUSAL_BUILDERS` 按票形选文案，`remoteTemplateRefusalFor(kind, sections)` 生成人话。
- `template-guard.ts:118` `remoteTemplateRefusalForLocalFile(container, form, sections)`：spec / map 容器直接返回空串（不拦）；否则按 `form` 分派地图子票文案或普通票文案。
- 全仓只有两处调用：新建 `issues-create.ts:68-70`；改写 `issues-patch.ts:124`。

### 二、为什么「写回自己」会把旧段重新递进去

- markdown 房的 `getIssue` 返回的 `data.body` 就是盘上整份文件。
- deck 的进度与维护者原话是 first-class 动作：`src/deck/tools/issue-patch.ts:329-350`。先读旧正文（`:342`），`planBodyWrite`（`src/deck/shell/body-write.ts:42`）把进度记录/原话拼进整份正文，`:361-364` 把结果当 `patch.body` 整份递交。
- 后端两条写正文路：整份（`issues-patch.ts:125-127` `mergeWholeBodyForPatch` + `moveLeadingSectionBelowTitle`）与片段插入（`:128-156`）。`isWholeIssueBody` 的判据在 `parse.ts:76`，规则层有一份逐字副本在 `src/deck/rules/minimal-spec.ts:133`，两处注释互指，改一处必须同步另一处。
- 进度模型本身也从正文读：`src/tracker/deck-derive.ts:267-298` 的 `progressOf` / `parseProgress` 读正文进度区，快照与收口都用它；所以不能用「发一条 comment」顶替进度——comment 没有 `percent / note / updatedAt` 语义。

### 三、为什么 comment 没事

- `src/tracker/rooms/markdown/comments.ts:64` `addComment` → `:71` `addCommentInner` → `locateForWrite` → `withFileWriter` → 读文件 → 追加到 `## Comments` → `publishTextFile`；全文没有 import 模板守卫。
- 只改标题、只改标签、关票也不经过 body 守卫。

### 四、拒绝语长度

- 实测 `remoteTemplateRefusalFor('issue'|'spec-ticket', 单段)` = 172 字，四段 = 225 字；`'map-ticket'` 单段 = 157 字，四段 = 210 字。
- deck 在 `src/deck/tools/issue-patch.ts:161-162` 用 `slice(0, 200)` 截断 `reason`，不补省略号，所以四段场景用户看到半句；票面遇到的单段场景完整，不是主诉。

### 五、第二条独立缺陷：legacy 形状票的进度写后核对必然假失败

- `src/tracker/rooms/markdown/original-fields.ts:94-106` 的 `ticketFormOf`：没有加粗字段行、没有 `## Question`、没有「# NN:」加裸 `Type`、没有 `DSH-FORMAT` 的文件判为 `legacy`。
- `src/tracker/rooms/markdown/patch-body.ts:158-171`（`originalLayout` 判断在 `:163`）对 legacy 形状补 `## Comments` / `## Answer` 骨架——这是旧行为的兼容，本身是有意的。
- 于是落盘 ≠ deck 的计划：deck 的写后核对 `src/deck/shell/text-write-verify.ts:24` 用 `bodyWriteReadbackProblem(plan, body)` 按整份比对，legacy 形状必然报 `src/shared/issue-file/src/progress.ts:495` 那句话：「进度写进去了，但进度区以外的正文跟写前对不上：这次可能顺手动到了别的区块，别当成已经写好，先读一次复核。」
- 实测：纯函数层面 `mergeWholeBodyForPatch(plan.next, oldLegacy)` 在文末补出 `## Comments` / `## Answer`，merged 与 plan.next 不等；room 级 `updateIssue` 返回 `ok:true` 但盘上内容 ≠ 计划；impl-ticket 与 map-ticket 两种形状不触发。
- 与守卫无关：带远端段的 legacy 票就算被守卫放行，也会卡在写后核对。现实可达性待核——旧扁平布局的工作区根 `issues/` 写路径已按 ADR 20261025 改成如实失败（`issues-locate.ts:354-356`，读兼容、不写），所以「legacy 形状且可写」的票在今天的现实文件里可能很罕见；但缺陷路径真实存在。
- 建议单独立 bug 票，不要混进 #1786。

## 门禁为什么拦不住

- `tests/verify-1509-update-strict.ts:244-275` 的存量用例盘上只带 `## Parent` 一个远端段，整份改写成「四段全带」时被拒；断言只到「被拒 + 盘上不变」，不检查拒绝语点名的是旧段还是新段，所以把判据改成「新旧块差集」后这条仍然绿——现有门禁不区分「旧段被拒」与「新段被拒」，而 #1786 要的正是这个区分。

## 提案评估（票面的「段名白名单」 vs 其他做法）

票面建议：用盘上旧正文已有的二级标题做白名单，只对「新旧差集里新出现的远端段名」报错。方向对，但有四个可复现的洞：

1. **旧票已带全四段时 identity 写回被放行**，而 `#1509` 验收①字面是「整份正文替换时带远端四段模板被拒绝」——语义与验收冲突，必须先改验收文字，否则实现的人会照字面判红。
2. **在旧段名下继续加内容**（段名不变）会被放行：差集只看段名，看不见块内容变化。
3. **同名段被去重漏掉**：`remoteTemplateSections` 按段名去重（`template-guard.ts:53`），旧票已有 `## What to build` 时再插第二个内容不同的同名段，集合不变、被放行。
4. **位置放错会回退 #1506 的修复**：如果把差集判据放在 `issues-patch.ts:124`（片段与整份共用），旧票已有同名段时片段写也会被放行，等于重新打开 #1506 两轴评审点 1 修掉的片段旁路。差集必须只作用 `isWholeIssueBody` 分支。

推荐做法 C5：**远端段整块逐字比对，只作用整份路径。**

- 按二级标题切块；新正文里每个远端段块，若能在旧正文里找到逐字相同的同名块，就视为存量、不算新增；块内容被改动、或出现旧正文没有的远端段，就拒绝，拒绝语仍点名是哪一段；旧段被删掉不算新增（允许把票改干净）。
- 行为核对：identity 写回 → 通过；追加进度 → 通过；新增一个旧票没有的远端段 → 拒绝；改动旧段内容 → 拒绝（#1509 的存量用例仍然成立）；删除旧段 → 通过；规格 / 地图容器 → 不变（今天本来就不拦）；新建路径 → 保持全量拦（没有旧正文可白名单）。
- 实现要点：白名单不能塞进 `remoteTemplateSections` 本身（新建路径没有旧正文），要新增一个「拿新旧两份正文比对」的纯函数，住在 `template-guard.ts`；`issues-patch.ts` 只在整份分支调用它，片段分支保持原判据。

其他方案：

- **C1 迁移存量票**：治本但会改动历史文件，与 #1506「存量不自动搬、不自动改，只读」正面冲突，代价最高，不推荐。
- **C2 给 markdown 后端加「只追加进度 / 原话」写路径**：语义最干净、不会撞 legacy 骨架，但要动 tracker 写正文契约（`src/tracker/contract/inputs.ts:117-122` 现在只有 title / body / milestone / customFields）和三个后端、deck 分支与门禁，工程量大；建议另立票评估，不在本条扩大范围。
- **C7 维持只读**：零代码，与 #1509 收口评论一致，但必须在 `.out-of-scope/` 或 ADR 留下「存量票只读」的决定与理由，否则下一个人会把它当 bug 重开。
- **C8 用 comment 顶进度**：不成立，进度是规范化模型，见根因链第二节。
