# #1560 分诊调查：读操作把排队时间算进 12 秒预算（2026-10-27）

调查范围：票 #1560 的正文、标签、评论与实施痕迹；`src/tracker/rooms/github/client.ts`、`src/refresh/rooms/host/outbound-admission.ts`、`src/refresh/rooms/host/gh-execution.ts`、`src/refresh/rooms/host/gh-queue-race.ts`、`src/tracker/kernel/outbound-tiers.ts`、`src/tracker/rooms/github/preflight.ts`；`config/timeouts.yaml`；相关门禁与旧笔记；关联票 #1007、#1101、#1475。这次只做诊断，没有改业务代码。

## 结论

- 现象成立，而且能在源码上稳定复现：读档的房内计时器在拿名额之前就起，排队与命令共用同一份预算；排队把预算吃掉之后，命令才起来，随后被同一只表掐断。
- 这是同一类缺陷在两条出口上的不一致：宿主 `runGh` 那一路已经改成「排队单独上限 3 秒 + 拿到名额后另起本档计时」（#1007 复核那次落地的），房间客户端（`deck_*` 工具走这条路）还是旧口径。
- 本票没有任何实施痕迹：没有评论，没有对应分支、工作树、提交或 PR，工作区里也没有相关未提交改动；main 上仍是旧行为。所以按「未实施」诊断，不按已实现收口。
- 这次还查出一条票面没写的影响放大路径：排队占满预算的到点因为进程已经起来，被判成 transport 级失败并设 30 秒冷却，随后一串读在 1 毫秒内被「通路不通」挡回，一次进程都没起。

## 复现（临时探针，未入库）

用真 `ghClient`、真准入闸、假执行器（永不回话）做最小复现：读桶只留 1 个名额，先占住 300 毫秒；这一笔 `execGh` 的预算设成 500 毫秒。结果：

- 回执原文：「gh 在 500 毫秒内没有回话（命令 api:graphql；到点掐断这一笔的是房内分档表……总共已等 500 毫秒，其中排队 302 毫秒；……）。这一笔已经中止。」
- 实际时间：总 500 毫秒，排队 302 毫秒，命令只跑了 199 毫秒。把 500 换成生产读档的 12000、把 302 换成票面的 10105，就是票面那一次的形状。
- 下一笔读：1 毫秒内返回「到 GitHub 的通路现在不通……上一笔连续第 1 次超时失败，冷却还剩约 60 秒」（探针把冷却缩成 60 秒；生产是 30 秒），起进程 0 次。

概率量级不是猜的：2026-10-21 的本机日志里读桶 64 个名额全满，排队中位数 35 位、最长 338 位，等名额 90 分位 14.8 秒、最长 15.1 秒（见 #1101 的核查记录与 #1007 的 triage 评论四），正好覆盖读档的 12 秒。

## 验收标准逐条对照

1. 「回执能分开给排队多久 / 命令跑了多久」：部分满足。现状给「总共已等 X / 其中排队 Y」，命令耗时可以相减推出，但主句仍写「gh 在 N 毫秒内没有回话」，没有直说命令跑了多久；票面的误解正来自这句主句。
2. 「排队不再挤占网络档位预算；或排队到点回排队中」：不满足。只有排队超过整档预算才会回「还在排队」（`phase=queue`）；票面这种排队 10.1 秒（小于 12 秒）的情形会先拿到名额、再被掐断。
3. 「既有超时门禁保持绿色，新增覆盖排队占满预算的场景」：不满足。`tests/verify-969-tiered-timeout.ts:205-215` 今天仍断言「排队段也算进房内的表」；`tests/verify-1475-predicate-budget.ts` 的算式依赖房间侧排队算在本档之内（`research/1536-triage-2026-10-26.md:47`）；没有「排队占满预算」的断言。

## 修复形状与代价（2026-10-27 首轮；晚对抗式复核后推荐改为乙，见文末，甲降为后续）

方案甲（两条都做，和宿主 runGh 一个口径）：排队段单独上限（本档与 3 秒取小），到点回「还在排队、没跑起来」；拿到名额后重起本档计时；回执分别写排队与命令两段。

- 代价一：预检一条命令的最坏等待变成「本档 + 排队上限」，内层串行最坏从 54 秒变 66 秒（`preflight.ts:63-78` 现算），外层 60 秒不再够，`predicateTimeoutMs` 要抬到至少 72 秒（66 + 余量 6），`tests/verify-1475-predicate-budget.ts` 与 `config/timeouts.yaml` 的注释要一起改。已实跑该门禁确认今天内层是 54000 毫秒、外层 60000 毫秒、全部通过；改后这条算式必然变红。
- 代价二：缓存命中后按会话补算那条路复用同一档预算，60 秒变 72 秒会连带变长（#1536 的诊断笔记已经提过这一点，当时建议另开窄票，这张票会提前碰到）。
- 代价三：排队上限的算式今天住在 `src/refresh/rooms/host/gh-queue-race.ts:53`，房间侧不能 import 宿主（`src/tracker/contract/outbound.ts` 与 `outbound-tiers.ts` 头注释写了这条边界）；要按甲做，得把这条纯算式挪进 `src/tracker/kernel/outbound-tiers.ts` 由两边共用，并同步 `tests/verify-1007-transport-cooldown.ts:228-232` 里对 `gh-queue-race.ts` 的静态断言。

方案乙（只做排队上限与回话）：排队超过 3 秒回「还在排队、没跑起来」，但不重起本档计时，拿到名额后还剩多少预算就用多少。

- 不动预检算式与 `predicateTimeoutMs`，改动面小。
- 代价：短暂排队（小于 3 秒）仍会占掉一部分网络预算，只满足验收第二条「或」的那一支，不满足「排队不再挤占预算」的字面要求。

两个方案的共同点：排队段到点不设 transport 冷却（现在排队段到点本来就不设，靠 `processStarted` 判断）；票面这种「排了 10 秒才拿到名额、命令跑 1.9 秒被掐」的形状，甲、乙都不再出现，连带误设冷却也消失。

## 尚未核实

- 3 秒排队上限对房间侧读工具是否合适：#1101 实测的 14.8 秒是「已经排上队的人等多久」；改成 3 秒后这些人会在 3 秒时收到「稍后重试」，对 `deck_issue_get` 这类读是不是更好的取舍，需要维护者按使用感拍板。
- 方案甲把 `predicateTimeoutMs` 抬到 72 秒会不会撞上别的外层上限：`PER_OP_TIMEOUT_MS` 60 秒只夹单次远端调用，`toolTimeoutMs` 300 秒是工具整趟预算；这次没有跑全链，只实跑了 verify-1475 本身。

## 对抗式复核（2026-10-27 晚，推荐由甲改为乙）

第一性原理拆开看，这是一个契约定义问题：

- 时间档位今天是「一次尝试进门到放弃的总墙钟」，不是「命令的网络时限」；票面的期望把它读成后者。换定义要重算所有依赖它的算式与上限。
- 准入队列是并发保险丝；它的结局只有「等到名额」或「明确说还在排队」两种。
- transport 冷却全桶生效（读冷却会挡住所有读 30 秒），设它的证据必须是「命令拿到了它该有的时间还是没回话」；排队挤占预算的到点不提供这个证据。
- 回执的职责是告诉人下一步做什么：排队归「稍后重试」，网络才归「查网络」。

按这个框架重审甲（排队独立上限 + 重起本档计时）：

- 甲多买到的只有「排队 0 到 3 秒时命令仍有完整本档时间」这一个区间；报告里的 10.1 秒排队在甲下同样在 3 秒时回「还在排队、没跑起来」，和乙的用户体验一样。
- 代价是把「一次尝试 ≤ 本档」改成「≤ 本档 + 排队上限」：预检内层 54 → 66 秒、外层 60 → 72 秒，缓存命中补算跟着变长。这是预算契约变更，应有测量依据、单独走预算审查。
- 未核实的外层上限（客户端 host.call 桥接、per-op 钳制是否覆盖链求值）可能把 72 秒静默截断；没核实前推荐甲等于拿刚合入的 #1475 预算去赌。
- 宿主 runGh 的调用方没有预检这种内层串行预算，房间客户端有；口径一致是手段不是目的。

修订后的推荐（乙 + 三条补丁）：

1. 房间侧加排队上限 min(本档, ghQueueWaitTimeoutMs = 3000)，排队到点回「还在排队、一次没跑起来」；总墙钟仍是本档，不给预检与外层预算加账。
2. 被排队挤占过的到点（排队等待 > 0 的房内到点）不设 transport 冷却——它证明不了通路坏；排队段到点本来就不设。
3. 回执措辞改成「排队 X 毫秒 / 拿到名额后又等了 Y 毫秒」，不把 Y 说成「命令跑了 Y 毫秒」（Y 含解析执行器的时间）。
4. 实现必须处理「排队到点后迟到的名额归还」，复用宿主 gh-queue-race 的赛跑与归还逻辑（或下沉到共用层），不能只写裸计时器。
5. 3 秒沿用宿主的值（同一问题一份答案），但按可调参数对待，用 gh.lane.wait 与 gh.timeout 的 waitedMs 分布回填。

甲降为后续：等有数据证明「排队 0 到 3 秒导致的提前掐断」有可感知损失，且外层上限核实完，再单独立预算变更票。
