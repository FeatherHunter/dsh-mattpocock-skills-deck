# #1136 对抗式审查·第一性原理（2026-10-14）

审查对象：issue #1136「房间纪律门禁起点仍指旧目录，一条边都没命中（假绿）」。
审查路线：第一性原理。结论不引用其他审查员的文件，全部判据都由我自己在钉住 `474602bd` 的临时工作树上跑出来；主工作树（今天有 67–70 处未提交的 gitlab 房 `.js`→`.ts` 迁移）全程只读。

---

## 0. 一句话结论

门禁假绿的根因不是「有人忘了改一行路径」，而是**判据的形状错了**：今天这道门禁检查的是「规则在不在」与「有没有违规」两件事，而这两件事在「规则完全没生效」时给出的输出与「代码完全干净」时**逐字相同**——我实测过两种情形都打印同一行「房间纪律与禁循环零违规」；因此本票真正的交付物不是「把起点改对」这件机械动作，而是一条**能被证伪的判据**：作用域非空用**磁盘**判，规则有牙用**注入的违规边**判；triage 提议的「起点在图上至少命中一个模块」既防不住最省事的那种假修法（我实测：起点改对 + 白名单放宽两行 → 规则照样命中 65 个房间模块、判据全绿、真跨房边被吃掉、整道门禁 exit 0），又会误伤「只约束未来文件」的合法规则（`^src/client/`：磁盘 208 个源码文件、图上 0 个模块）。

## 1. 不变式：防的是什么、怎么判定

### 1.1 要防的真实故障（三个场景，都不是风格问题）

**场景 A：一间房的实现被另一间房当自己的部件用。**
`src/tracker/rooms/github/` 里的东西直接 `import` 了 `src/tracker/rooms/gitlab/` 里的东西。此刻发生的是：github 房的加载链把 gitlab 房的文件一起拖进来；gitlab 房后来把 `client.js` 拆成 `createWorkbench`（今天正在发生的迁移就在动这些文件），github 房那条引用变成静默的解析失败或行为漂移，而 github 房自己的测试夹具不认识 gitlab 房，测试可能照样绿。更硬的后果在「摘除」这个动作上：`src/tracker/rooms/README.md` 与 `src/tracker/registry/core.ts` 把三房描述成三个可注册、可摘除的后端实现；只要有一间房静态引了另一间，**「删掉一间房」就不再是删目录**——它得先把别房里的引用清干净，而没有任何工具会告诉你漏了哪条。这是「搬家/摘除」类改动会踩到的真实故障，也是 #1019 把小半个树搬完之后最该担心的事。

**场景 B：一间房引了一个 npm 包。**
房间的运行环境由宿主进程提供（启动链在 `src/host/index.ts`）。房间自己引包意味着：该包被钉进插件根 `package.json`，所有用户都要装，哪怕只有一间房用；包的版本从此由插件根决定，房间没法表达「后端 A 要 v2、后端 B 要 v3」；包若带平台差异或原生扩展，失败现场出现在宿主启动路径上，而根因在房间的 import 行。ADR `docs/adr/20260913-builtin-ts-shape.md` §2.9 记的就是这个谱系的第三类：房间要引共享件时，白名单是唯一入口（#629 label-color、#711 refresh、#1012 config-store 三次开口）。

**场景 C：房间引共享件，但没登记。**
这一类看上去无害，实际是把「共享件的公开面」这件契约偷偷扩大：共享件的一次内部重构会同时打断三间房，而三间房的测试互不相干，谁也拦不住。它与场景 A 是同一个病：**依赖方向没有被声明**。

### 1.2 可判定的不变式陈述

设某次提交的源码树中，`R = {位于 src/tracker/rooms/<房名>/ 下的源码模块}`（`.ts` 源文件，以及在钩子 `scripts/ts-hook.mjs` 打开时按同名 `.ts` 解析的 `.js` 说明符），「同房」= 解析后的目标仍落在同一个 `<房名>/` 目录内。

> **I1（禁跨房）** 任取 r ∈ R，r 的每一条静态依赖（`import` / `export ... from` / `require` / 动态 `import()` 的字面量说明符）解析出的目标 t，必须落在「同房 ∪ 白名单」内。
> **I2（白名单只能是两类东西）** 白名单 = 契约层（`src/tracker/contract/**`）∪ 登记在册的共享件；每一项都必须指向**磁盘上存在的源码路径**，并且必须带着引入它的票号登记（今天是一串裸正则，没有票号、没有一致性检查）。
> **I3（禁第三方）** 房间不得直接依赖 npm 包；`node:` 内置模块不算 npm 包。
> **I4（方向）** 只允许 `房间 → 契约层/共享件`、`房间 → 同房`、`装配层（src/tracker/*.ts、registry、detection、host、client、deck）→ 房间`；禁止 `房间 → 别房`、`房间 → 装配层`、`房间 → 宿主层`、`房间 → 产物路径`。

### 1.3 边界：逐条判、逐条给理由

**房间引 `src/tracker/contract/**` —— 不算跨房，但要有配套判据。**
理由：契约层是三房唯一被允许的公共面（`src/tracker/contract/operations.ts`、`vocabulary.ts` 等只放常量与类型，没有运行期状态）。它要能名正言顺地当白名单的第一条，否则三房之间就只剩「复制粘贴」这一条路。**配套判据（今天没有）**：契约层自己不得引房间、不得引 `src/host/**`、不得引 npm 包——否则「契约层」会慢性长成「实现层」，白名单第一条就成了万能开口。我实测今天契约层是干净的（不引房间），但这条没有门禁守着。

**房间引 `src/tracker/preflight.ts`、`error-rules.ts`、`identity-keys.ts`、`src/tracker/detection/workspace-ownership.ts` —— 按今天的目录结构算跨房（违规）。**
理由：它们在 `src/tracker/` 根下，是「装配/共用」部件而不是契约层；而且它们自己引房间（`preflight.ts` 引各房自己的 preflight 实现），于是「房间引它们」会形成 `房间 → 装配 → 房间` 的环——正是 `src/tracker/rooms/README.md` 说要防的运行期成环。
**但这不是能纸上决定的事**：我实测这 4 类今天正被三房引用，共 22 条边（`preflight.ts` 19 条、`identity-keys.ts` 1 条、`detection/workspace-ownership.ts` 1 条、`error-rules.ts` 1 条；其中 19 条来自 `src/tracker/preflight.ts`）。所以本票落地时必须二选一：**要么**把它们搬进契约层/登记为共享件，**要么**承认房间可以引它们并把理由写进 ADR。这个选择直接决定本票要改多少代码：起点重指、白名单原样时，整道门禁 exit 1，62 条跨房违规里 38 条指向 `contract/`（本应被白名单放行）、19 条指向 `preflight.ts`。

**房间引 `src/host/outbound/tiers.ts`（2 条边）、`src/host/refresh/chain-ride.ts`（1 条边）—— 算跨房（违规），而且最该判红。**
理由：`src/host/**` 是宿主层，装配顺序与启动路径由宿主进程决定，房间静态引宿主件既让房间不再可摘除，方向也反了（I4）。**但判定必须按解析后的源码模块，不能按写下来的路径字符串**：`chain-ride` 今天同时存在源码位 `src/host/refresh/src/chain-ride.ts` 与产物位 `src/host/refresh/chain-ride.js`，而产物位在 `.gitignore` 里被手工放行（注释写着 #671，因为 `src/host/index.ts` 静态引它）。只看字符串会把同一件事判成两件事。

**判定的材料下限**：判据必须建立在「解析后的依赖图」上，而不是文本扫描。理由：同一个共享件今天有两种落点写法（`<包>/x.js` 是产物、`<包>/src/x.js` 是源码），`src/tracker/rooms/gitlab/idempotency.ts` 一个文件里就同时用了这两种；文本判据分不清它们，解析器分得清。

| 方案 | 防住了什么 | 没防住什么 | 新维护负担 | 我的实测证据 |
| --- | --- | --- | --- | --- |

### 2.1 逐案展开

**① 重指起点 + 手抄白名单。** 它是必要的第一步，机械、可验证，我按图推导重列后跑通了：真跨房边判红、同房不误伤、白名单覆盖到了三房今天实际用到的全部共享件（`contract/vocabulary.js` 等）。它的致命处不是「能不能做对」，而是**做错的时候不响**：白名单只能压制、不能补充，多写一行就是永久静默放行。我做了那个最可能发生的错法——起点改对，白名单顺手加 `^src/tracker/` 与 `^src/host/` 两行（因为 62 条违规里 19+1+1+1+2+1 条指向房外共享件，最容易的「修法」就是把前缀整段写进去）——结果：规则名仍叫 `cross-room-import`、severity 仍是 `error`、`EXPECTED_RULES` 仍齐全、规则仍命中 65 个房间模块，而整道门禁 **exit 0**，末行照旧「房间纪律与禁循环零违规」，我注入的那条真跨房边安安静静地合法了。**这是本次审查的核心发现：假绿有第二种形态，triage 的防复发判据抓不到它。**

**② 白名单机器推导。** 「从图推导」这个词有两种截然不同的含义，必须分开：
- 从**依赖图**推导（今天的边）→ 会把现状洗白。今天三房正引 `preflight.ts` 等 22 条边，推导出来的白名单会把它们写成「合法」，等于用机器把违规冻结成规则。
- 从**声明的清单**推导（契约层的公开入口 + 一份 `SHARED_INVENTORY` 登记表，每条带票号）→ 这才是我支持的方向。此时机器做的是「清单 ↔ 图」的一致性核对：图上有、清单里没有的边必须判红（是新开口子），清单里有、图上没有的条目应当提示清理。
我的实测支持后者可行：把白名单按「机器可核对的结构化条目」重列一遍，就能让真跨房边判红且无遗漏——也就是说，**清单只要写全，判据就有牙**；不确定性只在「谁来声明清单」这一步，而那一步本来就是人的职责（ADR §2.9 的每次开口都是人拍的）。

**③ 起点从注册表派生。** 先问「今天有没有这样的单点真源」：**没有**。房间名今天散落在至少四处，而且互相不一致：`src/tracker/rooms/README.md` 的表格（三房）、`.dependency-cruiser.cjs` 的两条规则字面量（三房）、`scripts/matrix-full.js:110-112`（三个入口文件）、`tests/verify-no-mixed-session.js:21` 的 `BACKENDS`（**只登记了 github 与 gitlab 两间房**）。所以「从注册表派生」这个方案要先造注册表。
但我在实测里发现一条更省的路（③-lite）：**规则根本不需要知道房间名**。把 `from.path` 写成 `^src/tracker/rooms/([^/]+)/`，`to.pathNot` 写 `^src/tracker/rooms/$1/`，行为与写死三个房名完全一致（我实测：违规集合相同、同房误伤 0）。这样「房间集合」这个字面量从规则里彻底消失，只剩**一个**字面量 `^src/tracker/rooms/`——房间根目录。它仍然会腐烂（根目录也可能被搬），但腐烂面从「3 个房名 × 2 条规则 × from/pathNot 两半」缩到「1 条路径」，而且这条路径正好可以用「磁盘存在 + 图上至少一个模块」这一个判据守住（见 §3）。
**③ 的边界**：捕获组写法依赖「一间房 = 一个目录」这个前提。哪一天某间房的内容横跨两个目录（例如 `rooms/github/` 与 `rooms/github-actions/` 合起来算一房），捕获组写法就表达不了，必须回到显式清单。写进 ADR，作为将来改回显式清单的触发条件。

**④ 换执法层。** 我不主张换，但要把它里面的「断言」这个想法吸收进来。理由：本仓今天真正在执法的是「CI 跑门禁脚本」这条链（`scripts.verify` 里 239 条，含 `verify-dependency-rules.ts`），换工具的边际收益远小于「让现有判据有负控」的收益。tsconfig project references 在本仓是明确不可行的：构建走 esbuild + `noEmit`，Node 的类型剥离钩子直接跑源码，没有 `tsc -b` 这个环节，references 拦不到任何东西；而且它对 `.js` 里的 `require` 和动态 `import()` 无能为力，房间昨天还全是 `.js`。生成式 allowlist（配置由脚本生成）值得做，但它属于 ②，不属于「换执法层」。

### 2.2 我的取舍

**③-lite（起点去掉房名）+ ②（白名单改成带票号的结构化登记表，人声明、机器核对）+ ①（只作为把登记表落到配置里的机械步骤）+ §3 的判据（作用域用磁盘判、有牙用注入边判）。** ④ 的内容只保留「CI 断言」这一件，即把判据写进 `tests/verify-dependency-rules.ts`。

## 3. 防复发判据：原提案的攻击面与我的改法

### 3.1 原提案的原文与它想解决的问题

Agent Brief 的 desired behavior 写着：**「门禁增加一条机器判据：每条规则的起点在图上至少命中一个模块，命中 0 个就判红」**。它针对的是「起点指空目录」这一类，方向对，判据选错了对象。

### 3.2 它会误伤的场景（尽力找全）

1. **合法的空作用域规则（只约束未来文件/尚未进图的树）**。我实测：`src/client` 有 208 个源码文件，而根清单只扫 `src/host`、`src/shared`、`src/seam`、`src/deck` 四棵树，所以一条 `from: '^src/client/'` 的规则**命中 0 个模块、违规 0**——它不是坏规则，它是「client 一旦进图就该被管」的规则。按原判据，这条规则要判红，逼人删掉它或把 client 塞进根清单（后者会让图上多出一大批今天没被判过的边）。**这是最现实的误伤**：本仓的扫描域是 4 棵树的字面量，任何管第 5 棵树的规则都会踩到。
2. **可选树/可选依赖没装齐的检出**。房间的第三方边在 `node_modules` 不全时解析不到，规则命中数会掉；极端情况下房间自己不进图（今天房间 65 个磁盘文件只有 56 个进图，就是因为那 9 条边解析不到）。
3. **规则起点写在单个文件上、而文件改了名**。此时该判的是「这个文件不存在了」（磁盘事实），而不是「图上没命中」（解析/引用事实）。两者语义不同：文件存在但今天没人引它，规则是**合法地**空着的；文件不存在，规则是**死**的。原判据把这两件事合并成一条红字，维护者分不清该删规则还是该改路径。
4. **依赖没装齐 / 只扫部分树 / 规则包在 `--include-only` 之外的运行**：命中数为 0 是环境态，不是规则态。我实测同一提交换构建态：文件 176→212、模块 364→396、`unknown` 类依赖 12→3。
5. **它抓不到真问题**（不是误伤，是漏报，但决定了这条判据值不值得加）：我实测「起点改对 + 白名单放宽两行」时，规则命中 65 个房间模块——**判据全绿**，而真跨房边已经被白名单吃掉。原判据防的是「起点指空目录」这一种假绿，而更危险的假绿是「规则有作用域、没有牙」。

### 3.3 更根本的问题：真正该判的是什么

对一条 forbid 规则，图上的模块集合是它的**定义域**，不是它的**效果**。「命中 ≥1 个模块」只证明配置被解析了两次（起点正则和根清单都没写错到完全落空），不证明这条规则还能判红任何东西。所以：

- 「起点在磁盘上存在至少一个匹配路径」与「起点在图上命中至少一个模块」，**哪个才对**？→ **前者是必要条件，后者既非必要也非充分**。原因：`图上命中 = 磁盘存在 ∧ 解析成功 ∧ 根清单覆盖 ∧ 依赖装齐`，右边四项里三项是环境态。用环境态当判据，会把「本地没装包」「没构建」「根清单没覆盖」误报成「规则坏了」，也会把「规则被白名单架空」漏过去。而「磁盘存在」只判一件事，且正好是这次坏掉的那件事：`src/host/tracker/backends/` 这个目录今天**在磁盘上不存在**。
- 但「磁盘存在」也不充分（它挡不住白名单架空），所以判据必须是**两条腿**：作用域用磁盘判（必要条件），规则有牙用**注入边**判（充分条件）。

### 3.4 我推荐的判据原文（可直接抄进 `tests/verify-dependency-rules.ts`）

> 对配置里每一条 `severity: 'error'` 的 forbid 规则 R，同时满足以下五条才算通过：
> (1) **作用域非空（磁盘判）**：R 的 `from.path` 必须匹配到至少一个**磁盘上存在的源码文件**（用 `git ls-files` 或 `existsSync` 判，不依赖依赖图）。匹配 0 个判红，红字里写明「起点可能仍指向搬家前的旧目录」，并打印 `from.path` 原文。
> (2) **正控（有牙）**：向图里注入一条**确定违规**的边（不改工作区文件：用临时配置文件 + 探针树，或仓内固定的 `tests/fixtures/`），断言 R 判红，且判红的 from/to 与注入的边一致。注入边的**目标**必须选在「R 允许的所有合法目标类之外的一个具体目标」上——房间规则要选一条别的房间的**源码模块**（例如 `src/tracker/rooms/gitlab/index.ts`），这样白名单一旦被放宽到 `^src/tracker/`，正控立刻红。这条是本判据的关键，没有它，(2) 只是重复「规则名在不在」。
> (3) **负控（不误伤）**：注入一条**确定合法**的边（同房互引、或白名单内的引用），断言 R **不**判红。
> (4) **白名单可核对**：R 的每条白名单条目必须是结构化登记（目标路径 + 引入票号 + 是否允许产物路径），且其目标路径在**磁盘**上必须匹配到 ≥1 个存在的路径；匹配 0 个判红。**边界**：允许产物路径的条目（如 `^src/shared/labels\.js$` 这类指向构建产物的名字）只在「构建后」的检出上判，未构建的检出上列为提示不判红——否则本地干净检出会被产物缺失误伤（我实测：未构建树上房间的三方规则会多出 9 条假违规，构建后降到 0）。
> (5) **规则集合不缩水**：`ruleSetUsed` 的规则名集合 == 期望集合，且 `severity === 'error'`（今天已有，保留）。
> 另加一条**不判红但必须打印**的诊断：每条规则在图上命中的模块数、房间进图数/磁盘数（今天 56/65，补根清单后 65/65）。数量进日志、不进判据，因为它是环境态。

### 3.5 我这条判据自己的误伤边界

1. **(1) 会误伤「只约束未来文件」的合法规则**（`^src/client/`）。所以 (1) 的判据必须建立在「**声明过的**起点」上：允许规则带 `intentionalEmptyScope: true` + 一段理由（写明哪张票会把它接上），登记在配置里；不允许静默空着。这样 `^src/client/` 这类规则能留住，(1) 也不会变成「逼人删规则」的工具。
2. **(4) 会误伤「产物路径条目」**：见 (4) 的边界，产物类条目按构建态分档。
3. **(2)/(3) 依赖一条注入机制**。我实测可行（临时配置 + 探针树），但门禁脚本要么自己造临时树，要么在仓内放固定夹具（`tests/fixtures/room-discipline/`）。后者更稳（不依赖 git 状态），代价是仓里多两个只为门禁存在的文件——我推荐后者，因为它让判据在任何检出上都能跑。
4. **(2) 的注入边如果选在「白名单已覆盖的目标」上，正控会假绿**：所以注入边的目标必须跟着 §1.3 的边界决定走（本票落定后写进注释），否则这次能过、下次白名单一改就失效。
5. **(1) 只判「存在」，不判「该不该存在」**：起点指到一个真实存在但**语义已变**的目录（例如房间整体搬走后旧目录被别的东西占用）时，(1) 会绿。这条我认了——机器判不了语义，只能靠 (2)/(3) 兜住效果。

## 4. 为什么这个洞能活这么久，还有哪些同类洞

### 4.1 病根（机制层，不追责）

1. **判据写在两处，而真值只写在不会被检查的地方**。规则的起点是一次性写下的**字面路径**（`.dependency-cruiser.cjs:96` 的 `from.path`、`:100` 的 `pathNot`），而它指向的东西在另一个 PR 里被搬家；`tests/verify-dependency-rules.ts:58-69` 的 `EXPECTED_RULES` 与 `:546-554` 的核对逻辑检查的是规则的**身份**（名字在不在、`severity === 'error'`），**从不检查规则的作用域**。「规则存在」与「规则生效」之间没有任何机器联系。
2. **零违规是默认状态，且与「没看」同形**。forbid 规则的输出集合为空，既可以是「代码干净」，也可以是「规则没看」；两者打印同一行绿字。我实测了两种假绿：(a) 起点指旧目录（今天的状态）；(b) 起点正确、白名单放宽两行吃掉真违规。**任何只报违规的门禁都有这个盲区**，除非它有正控。
3. **同一份知识抄了两份，却没有一致性检查**。`src/tracker/rooms/README.md:44-49` 的白名单与 `.dependency-cruiser.cjs:31-41` 的 `ROOM_WHITELIST` 是两份人工清单，CONTEXT.md:36 只写了「两处一起改」的规矩。今天它们**已经不一致**：README 列的是 `src/tracker/contract/canonical-labels.ts` 与 `src/tracker/preflight.ts`（#1019 已把文档改到新路径），配置里还是 `^src/shared/labels\.js$` 与 `^src/host/tracker/preflight\.js$`（旧路径）。也就是说：**搬家的人改了文档、漏了机器判据，而没有任何东西因此变红**。
4. **分层设计让「底层机制全绿、上层语义失效」成为可能**。`verify-dependency-rules.ts` 只核对规则名与 severity 就宣布「房间纪律与禁循环零违规」；链上另一道真正走全仓剖析的门禁 `verify-gate-map` 今天自己是红的（见 4.2 第 4 条），所以它提供不了交叉验证。
5. **验收标准写的是「绿」，不是「有牙」**。本票需求里写着「改动之后整道门禁在真实仓库上判绿」——在一个「零违规」与「没看」同形的门禁上，「判绿」不是证据。这条把假绿制度化了。

### 4.2 今天仍然敞开的同类洞（都用一手材料证过）

1. **`src/tracker/**` 整棵树今天没有任何「同层互引」判据**。`same-layer-import-host` 的起点只写 `^src/host/`（`.dependency-cruiser.cjs:62`）。搬家前 `src/host/tracker/**` 在它的作用域内；搬家后 `src/tracker/**`（磁盘 99 个文件、图上 84→99）掉出了**所有**同层规则。我实测这棵树里「非房间件互相引」的边有 **22 条**：`registry` 5、`index.ts` 5、`detection` 4、`contract` 2、`deck-derive.ts` 2、`preflight.ts` 2、`error-rules.ts` 1、`label-names.ts` 1——今天一条也没人判。同一个词「tracker」今天横跨两棵树：`src/host/tracker/`（5 件：capability / generic / predicateCore / predicatePrimitives / snapshot，仍受同层规则管）与 `src/tracker/`（99 件，不受任何同层规则管）。
2. **规则的作用域是「图」，而图是 `解析成功 ∧ 根清单覆盖 ∧ 依赖装齐` 的函数**。`.dependency-cruiser.cjs` 的扫描域只写 4 棵树（`src/host`、`src/shared`、`src/seam`、`src/deck`），`src/tracker` 与 `src/client` 都不在里面。我实测：房间 65 个磁盘文件只有 **56** 个进图；`src/client` 208 个源码文件在图上 **0** 个模块。triage 的修复（根清单补 `src/tracker`）只补这一次——**根清单本身仍是一处会腐烂的字面量**，下一次搬家（比如 `src/seam`）会重演同一幕。而且补根清单不是中性动作：我实测补上 `src/tracker` 后模块数 364→420，`circular-dependency` 的判域跟着从 364 涨到 420——新进图的树要单独过一遍别条规则。
3. **规则的判据随构建态变化**。同一提交：构建前 176 文件 / 364 模块 / 12 条 `unknown` 类依赖；构建后 212 文件 / 396 模块 / 3 条 `unknown`（`src/shared` 下生成 59 个 `.js`）。原因是三房把 9 条共享件的引用写成了**产物路径**（`../../../shared/refresh/idempotency.js`、`.../label-color/colors.js`、`.../config-store/labels.js`），而钩子 `scripts/ts-hook.mjs` 只把**同目录**的 `./x.js` 改指 `./x.ts`，不管 `<包>/x.js` → `<包>/src/x.ts`。于是这些边在「没构建过的检出」上根本解析不到，而它们正是房间规则要判的对象。CI 先 build 再 verify（`.github/workflows/verify.yml`），所以 CI 看得见、人本地干净检出看不见。顺带一个没有门禁守着的现象：同一份共享件今天有两种落点写法，`src/tracker/rooms/gitlab/idempotency.ts` 里「值用产物路径、类型用源码路径」并存。
4. **另一道走全仓剖析的门禁今天是红的**（`verify-gate-map`）：干净检出上 6 条 FAIL（`200 guards 路径不存在`、表里 534 vs 磁盘 462、`guardedFiles 多 72`、底层共享模块 `budget.js` 缺、场景三漏 7 扇），构建后剩 1 条 FAIL，另有 freshness INFO（链长 238 两处一致；落盘 `attributedGates` 210/`buildOutputOnly` 20 vs 推导 205/5）。一条长期红的门禁不会给任何信号——「路径存在性」这一类断言在这个仓里**已经部署过，并且已经失效**。triage 第 4 条把它列成「判绿的验收条件」方向对，但必须明确：**它红的原因与本票根因无关**（是产物/推导口径差），把它算进本票验收，本票会被拖成永不开绿。
5. **配置里那条「反方向」规则被有意留空**（`.dependency-cruiser.cjs:147-152` 的注释）：今天允许任何东西引房间（`src/host/index.ts` 等 5 处按后端名相对引房间），注释写着复查条件——「等 12 号收口、契约层公开入口立起来之后」。今天 `src/tracker/contract/` 已经存在、`deck-deep-import`(:135) 已经管住 deck→rooms，**注释里的前提已经成立、注释里的路径也过期了**。这是「已知、有意留、但复查条件已到」的同类洞。
6. **同一条规则体系里还有别的旧路径字面量**：`same-layer-import-host` 的 `pathNot` 里 `^src/host/tracker/backends/`（:62）今天是不存在的目录。它是「反方向」那条规则的配套豁免；写在这里意味着将来若有人把房间搬回去、或在 `src/host/tracker/backends/` 下新放文件，这条豁免会**静默生效**（今天它是空转的，所以不响）。

## 5. 我推翻或修正了哪些通行说法

1. **修正 triage 的防复发判据**（「起点在图上至少命中一个模块，命中 0 个就判红」）：它会被最省事的那种修法骗过——我实测「起点改对 + 白名单放宽两行」时规则命中 65 个房间模块、判据全绿，而真跨房边已被吃掉、门禁 exit 0；它还会误伤「只约束未来文件」的合法规则（`^src/client/`：磁盘 208 文件、图上 0 模块）。改法见 §3.4。
2. **修正「三房」这个说法被到处复述的前提**：`tests/verify-no-mixed-session.js:21` 的 `BACKENDS` **只登记了 github 与 gitlab 两间房**；`scripts/matrix-full.js:110-112` 又写了一份三个入口文件。今天不存在「房间目录注册表」这种东西，③ 要新建。这一点很重要：若把判据写成「拿注册表比对」，得先确认注册表存在且完整——今天它不存在。
3. **修正「白名单抄错只是抄错」的轻描淡写**：白名单是**单向**的（只能压制、不能补充），所以抄写偏差在「判绿」的前提下不可观测。我用两行放宽就让一条真跨房边合法化、门禁 exit 0。注意它与规则的错误方向相反：规则指空目录是「漏判」，白名单抄宽是「错放」，两者的噪声都是 0。**同一种病（判据不可证伪）的两个方向。**
4. **修正「根清单补 src/tracker 就够了」**：补根清单让房间图完整度 56/65→65/65，但它让「根清单」这个字面量继续存在（4.2 第 2 条），并且顺带扩大别条规则的判域（364→420 模块）。票面上要写成「补根清单会影响所有规则，需单独复查新进图的树」。
5. **修正「verify-gate-map 判绿是本票验收」**：那 6 条 FAIL 与本票根因无关，应改成「本票不新增 FAIL，并记录它今天的红」。
6. **修正「README 与规则两处一起改」的口径**：今天已经不一致（README：`src/tracker/contract/canonical-labels.ts`、`src/tracker/preflight.ts`；配置：`^src/shared/labels\.js$`、`^src/host/tracker/preflight\.js$`）。这条「规矩」从未被执行过；要么变成机器检查（白名单结构化 + 一致性断言），要么承认文档过期、以配置为准并在 README 里指向配置。
7. **补一条 triage 没提的既有事实**：`^src/client/` 这类规则在今天的图上是**完全死掉**的（磁盘 208 文件、图上 0 模块、违规 0），而它不是坏规则。这说明「规则作用域」这件事在整个配置里只有房间规则被怀疑过，其余规则的「空」从未被检查——判据要按规则逐条落地，不能只补房间那两条。
