## 一、票面症状摘要

GitHub issue #1006（open，标签 bug / ready-for-agent / wayfinder:task，父票 #1010，无评论）要求「修复：剩余额度读数的失败冷却按工作区分开，并把它从工具关键路径上挪走」。票面记录 2026-10-10 深查量到的三件事：

1. 冷却起点固定不滑动：旧实现 `ensureReading` 的失败分支「锚是 0 才盖戳」，导致 60 秒后每次调用都真起一次注定失败的 `gh`。这一块已经单独修好（提交 a6c7e4c1「剩余额度读数同步的失败冷却改成滑动锚」，随 1.8.0-beta.5 发布），票面明确说本票做后面两块。
2. 冷却变量全进程一份、不按工作区分：旧 `src/host/refresh/wiring.js` 的 `quotaSyncOf` 只建一个闭包。A 工作区同步失败会让 B 工作区也被认成失败，A 成功又会清掉所有工作区的失败锚。
3. 硬失败与软失败共用 60 秒：`repoKeys.js` 的五档失败（env / spawn / auth / timeout / 解析不出）被混成 `sync-empty` / `sync-threw` 两种结果，冷却时间一样。

期望五条：① 冷却锚改成「下次允许尝试的时刻」，失败越久等得越久，有上限；② 冷却按工作区键分开存，表有上限与淘汰；③ 硬失败（无 gh、没登录）等得久、软失败（超时、解析空）等得短，粗分两档，不加随机抖动；④ 关键路径不等：账本不差直接过；差但有旧读数就先让调用走、同步放后台；完全没读数就不挡路、诚实推迟、后台刷；⑤ 后台刷新失败要在界面说得出来。

验收六条：过期后连调只放一笔（扩 `tests/verify-deck-quota-sync.js` 冷却段）；A 工作区连续失败不影响 B 工作区；失败越久等待越长的序列有上限；有旧读数时工具调用不再等同步（假时钟加慢 `runGh` 断言不等）；慢读数回来不覆盖更新读数；不新增日志事件名、`npm run verify` 全绿（含 `verify-log-*` 三道）。

## 六、dsh-log 埋点方案（本阶段只写方案，不改代码）

原则：按票面验收第 6 条，不新增日志事件名；只复用已有的 `host.call.fail`、`gh.exec`、`host.call`。凭证与 `gh` 错误原文不落盘（沿用 `src/host/git-process.ts:254` 注释里「只记 signal 枚举」的口径）；高频点必须加开关，按 `docs/design/335-logging-contract.md` 第 3 章的分层做法。

### 落点 A：同步失败的结论（必需）

* 位置：`src/deck/registration/quota-sync.ts` 的 `doSync` 里，`:105-107` 处保存 `runGh` 失败时的 `kind`；在 `:128`（`sync-empty`）与 `:129`（`sync-threw`）两个失败出口发一行；`:150` 的 `ensure-threw` 同样处理。
* 事件与字段：复用 `host.call.fail` 既有白名单（`tests/verify-log-fields.ts:190`；`research/489-appendix.md:254` 第 27 条）：`method: 'deck.quotaSync'`、`kind: 'deck-tool'`、`errorKind` 枚举、`errorHash: hash8(原因 + 类别)`、`cwdHash: hash8(cwd)`。字段集不扩，只扩 `errorKind` 的取值。
* `errorKind` 取值（每个值只用来排除一种故障）：`env`（gh 不在 PATH 或 `DSH_GH_PATH` 没配）、`auth`（没登录或凭据失效）、`network`（超时或连接失败）、`exit`（其它非零退出）、`parse`（gh 成功但读数解析不出）、`missing-dep`（接线没给全依赖）、`sync-threw`（意外抛出）。前两个是票面期望③说的硬失败，中间三个是软失败。
* 节流：只在「首次失败」与「失败类别发生变化」时记一行（进程内记住上一次类别）；成功恢复用既有 `host.call`（`:87-89`）表示。这样 gh 不在的机器上不会每次工具调用都刷一行。
* 这条日志落盘后：看到 `errorKind=env/auth` 说明冷却被硬失败触发；看到 `network/exit/parse` 说明是软失败；`cwdHash` 说明是哪一个工作区失败。若同一条失败之后 60 秒内另一个 `cwdHash` 的工具调用没有任何自己的同步尝试行，配合落点 B 就能证明「冷却不分工作区」还在。

### 落点 B：冷却挡下的那一次（按需 debug，推荐）

* 位置：`src/deck/registration/quota-sync.ts:145` 的冷却分支。
* 做法：仅在 `logCtx.isEnabled('debug')` 为真时记一行 `host.call.fail`（`level: 'debug'`），字段 `{ method: 'deck.quotaSync', kind: 'deck-tool', errorKind: 'cooldown', errorHash: hash8('cooldown'), cwdHash: hash8(cwd) }`。`logCtx` 的接口里已有 `isEnabled`（`src/host/refresh/wiring.ts:120` 的注释、`src/host/refresh/gate.ts:138-139` 的接口定义）。
* 为什么要开 debug：常驻会在坏 gh 的机器上每次工具调用刷一行，违反 AGENTS.md 的垃圾四条；开 debug 只在排查时打开。
* 这条日志落盘后：若工作区 A 失败后 60 秒内出现 `cwdHash` 属于工作区 B 的 `cooldown` 行，而 B 自己没有失败或尝试行，就说明 B 被 A 的失败连坐——这就是票面问题②的日志判据。如果修复后 B 在 A 失败后仍能出现自己的尝试行，就说明冷却已经按工作区分开。
