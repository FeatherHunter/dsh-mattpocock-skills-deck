## 二、今天的实现锚点（以 2026-10-21 工作树为准）

### 2.1 宿主侧：令牌是唯一能绕过退避的钥匙

- `src/host/refresh/chainBackoff.ts:107-109` 的头注释写明了约定：「人亲手点的那一次（trigger 为 'user-recheck'）永不降档」。
- `src/host/refresh/chainBackoff.ts:124` 取出 trigger；`:127-130` 是唯一旁路：当 trigger 严格等于 'user-recheck' 时直接返回 `{needed:true, reason:'user-recheck-bypass', waitMs:0}`，只在 debug 级记一行 `chain.backoff {keyHash, decision:'user-recheck-bypass'}`，**不经过下面那条常驻 info 记录**。
- 其余触发条件（事件名、action-done、write-done、插件自己补一次）都走纯函数 `chainRefreshVerdict`，按 8 秒 / 30 秒 / 2 分钟 / 5 分钟四档退避；`:136-140` 落常驻 info 级 `chain.backoff {keyHash, decision:recompute|defer, reason, waitMs, step, trigger}`。
- `src/host/detectChain.ts:218-246` 是链入口 `handleChain`：`:220` 取 force，`:222` 取 trigger，`:227` 把 trigger 归成刷新来源；`:236-238` 调退避；`:239-241` 被挡下时记 debug `chain.cache.hit {deferred:true, reason, waitMs}` 并直接把缓存回包交回去。**关键点：force=true 本身并不绕过退避**——只有 trigger='user-recheck' 能绕。
- 反过来，`tests/verify-709-no-self-continuing-timers.ts` 也把这条口径守住了：「挂载时主动调 force 刷新（force=true，客户端不带 trigger）：闸把它归成 background 并放行」「人亲手点重新检查（trigger=user-recheck）：闸把它归成 user-action 并放行」。

### 2.2 客户端三条「人亲手点重查」的活路，今天都带令牌

1. `src/client/kernel/probe-auto.ts:300-318` 的 `refreshAll`：`:309` 调 `chainEventRefresh(st, 'user-recheck')`。它的三个调用点都是人点的按钮：`src/client/views/ChecksTab.ts:222`（检查页「重新检查」）、`src/client/panel/Dock.ts:307`（面板刷新）、`src/client/statusbar/StatusBar.ts:352`（状态栏刷新）。
2. `src/client/views/ChecksTab.ts:118-125` 的动作分发器 `ctx.refresh`：`:123` 用 `chainEventRefresh(st, whyRecheck)`，而 `:46` 的 `whyRecheck` 就是 `CHAIN_EVENT_REASONS.userRecheck`（'user-recheck'）。检查页行内动作走这个分发器。
3. `src/client/statusbar/bannerChain.ts:246-261`（#916 新按钮的「查不到→只重查」）：`:257` 调 `chainEventRefresh(st, 'user-recheck')`，`:258` 兜底 `loadChain(st, true, 'user-recheck')`。

`src/client/kernel/probe-chain.ts:121-127` 的 `chainEventRefresh(st, why, force)` 会把 reason 同时写进 debug 日志 `chain.event {reason}`，再以第三个参数 trigger 调 `loadChain`；`:158` 把 trigger 拼进 `wf.chain` 参数，`:164` 发出去，`:165` 记 `host.call` 或 `host.call.fail`。所以「带没带令牌」从代码和日志两头都能看出来。

### 2.3 票面点名的「老路」今天已经不可达（死代码）

票面说的「横幅动作分发里的 refresh 一路」是 `src/client/statusbar/bannerChain.ts:184-214` 的 `runAction`：它建了一个动作分发器，`:197-204` 的 `ctx.refresh` 回调里 `:200` 先 `wf.detect {force:true}`，`:202` 再 `loadChain(st, true)`——第三个参数 trigger 缺省，确实不带 user-recheck。

但这条路今天没有入口，三道证据合起来说明它走不到：

1. `runAction` 在整个文件里只有一个调用点：`bannerChain.ts:270`，传进去的 action 来自 `firstFixesActionOf`（`:173-181`）。这个函数只在当前步骤的 actions 里挑两类：先挑 form / wizard，再挑 inject-prompt / rpc，**从来不会返回 type='refresh' 的动作**。
2. 动作分发器 `src/client/kernel/actions.ts` 里，只有 `t === ACTION_TYPE.REFRESH` 的分支（`:200-205`）会调 `ctx.refresh`；rpc（`:91-120`）、form（`:121-158`）、wizard（`:159-199`）成功后都不会调 `ctx.refresh`。
3. 唯一会走到 `runAction` 的步骤是引导链里的「已关联仓库」（`src/shared/tracker/guide-steps.ts:32-33` 的 `repoRemoteFix` 用 FIXES_ACTION），今天只有 GitHub 后端声明这个能力（`src/tracker/rooms/github/repo.ts:91`）。它在这一步声明的修复动作是「一个 wizard + 一个 refresh」（`src/tracker/rooms/github/index.ts:67-95`），wizard 的提交动作是 rpc（`:92`），不是 refresh。所以 `firstFixesActionOf` 选中的是 wizard，提交后 dispatch 的是 rpc，走不到 `:197-204`。

换句话说：票面描述的「点了老路按钮不带令牌」这件事，在今天的数据与分发口径下没有可触发的组合；那段回调留着，但没有任何一条路径能把它叫起来。另外从时间线上看，`firstFixesActionOf` 的过滤是 2026-09-19 的提交 d8327c06（#663）加进来的，早于本票 2026-10-08 的立案时间——立案时的审查看到的是「代码里有这么一段没带令牌的写法」，没有继续核对它是否可达。

## 五、判定：不存在

判定理由：

1. 票面点名的「横幅动作分发里的 refresh 一路」`bannerChain.ts:197-204` 今天没有任何可达调用方：唯一调用 `runAction` 的 `:270` 只接收 `firstFixesActionOf` 的返回值，而后者不会返回 refresh 类型；分发器里也只有 type=refresh 的动作才触发 `ctx.refresh`，今天的修复动作里没有这种提交动作。机制在树上还在，但触发不了。
2. 今天所有「人亲手点重查/刷新」的活路都带 user-recheck 令牌（refreshAll 三处按钮、检查页行内分发器、#916 横幅重查），宿主侧的令牌旁路与 force 不旁路都由 verify-709 的 34 条断言守住了。
3. 真机日志同向：10-17 至 10-21 每天都有 user-recheck-bypass，10-21 当天 3 次都配上 `chain.event {reason:user-recheck}`；defer 全部来自后台事件。

边界（不等于票面机制完全消失）：那段没带令牌的回调是死代码，如果将来某个后端给 form/wizard 的 submitAction 声明成 refresh，或者有人改动 `firstFixesActionOf` 的挑选规则，它会在没有令牌的情况下复活，且不会有任何测试变红。这属于「埋着一颗哑弹」，建议另开一张小加固票处理（删除这段回调，或在 `runAction` 入口断言 action.type 不可能是 refresh 并加一扇门禁）；它不是今天能复现的 #918 故障，不改变本票「不存在」的判定。
