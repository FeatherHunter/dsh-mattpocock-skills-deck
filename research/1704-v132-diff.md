## 一、范围与核对方法

- 上游两个 tag 之间的全部改动是 51 个 commit、72 个文件（[compare](https://github.com/mattpocock/skills/compare/v1.3.1...v1.3.2)）；落在随包两个目录里的只有 19 个文件，全部是 modified，合计 `96 insertions(+), 58 deletions(-)`，没有新增、删除、改名。这个数字用 `git diff --stat v1.3.1 v1.3.2 -- skills/engineering skills/productivity` 实测，与开工前给的已知事实一致。
- 核对步骤：`git clone --filter=blob:none --no-checkout` 到临时目录（不碰本仓库），用 `git diff v1.3.1 v1.3.2 -- skills/engineering skills/productivity` 取逐行 diff，用 `git show v1.3.2:<路径>` 取原文行号；frontmatter 用「首行 `---` 到下一个独立 `---`」的整段做逐字比对；目录集合用 `git ls-tree` 对比两个 tag。

- 引用上游原文时，行号都是 v1.3.2 里的行号；每处只引 1-3 行，完整原文看同一条目里的 blob 链接。

#### issue-tracker-github.md（+13 -8，提交 [59db609](https://github.com/mattpocock/skills/commit/59db609)、[ed0de59](https://github.com/mattpocock/skills/commit/ed0de59)、[5b7cade](https://github.com/mattpocock/skills/commit/5b7cade)、[c07714b](https://github.com/mattpocock/skills/commit/c07714b)、[9e2abf8](https://github.com/mattpocock/skills/commit/9e2abf8)、[8e67db2](https://github.com/mattpocock/skills/commit/8e67db2)、[cffab50](https://github.com/mattpocock/skills/commit/cffab50)、[e0efb6e](https://github.com/mattpocock/skills/commit/e0efb6e)）

这是 19 个文件里改动最密的一个，逐条列：

- 第 8 行「Read an issue」从「`gh issue view <number> --comments`」换成显式字段清单：`gh issue view <number> --json number,title,body,labels,comments`。行为变化：读票只取需要的字段，不把整张票的所有内容倒出来（省上下文）。
- 第 10 行新增「Make an issue a sub-issue of a parent」：`gh issue create --parent <parent> ...`，或事后 `gh issue edit <parent> --add-sub-issue <child>`（`gh` 2.94+）；旧版走 `gh api --method POST repos/<owner>/<repo>/issues/<parent>/sub_issues -F sub_issue_id=<child-db-id>`；没有子票能力时在子票正文第一行写 `Part of #<parent>`。
- 第 11 行新增「Blocking」，并把这件事从 Wayfinding 一节搬进 Conventions：「GitHub's **native issue dependencies**, the canonical, UI-visible representation.」命令是 `gh issue create --blocked-by <n>,<n> ...` 或 `gh issue edit <child> --add-blocked-by <blocker>`（`gh` 2.94+）；旧版走 `/dependencies/blocked_by` API，要传的是阻塞票的数字 database id（`gh api repos/<owner>/<repo>/issues/<n> --jq .id`，不是 `#number` 也不是 `node_id`）；拿不到原生能力才退回正文顶部的 `Blocked by: #<n>, #<n>`。
- 第 12 行新增「Count open blockers」：`gh api repos/<owner>/<repo>/issues/<n> --jq .issue_dependencies_summary.blocked_by`，并提醒 `--json blockedBy` 连已关闭的也列，得过滤 `select(.state == "OPEN")`。
- 第 15 行「Close」改成两步，并给出理由：「post the explanation with `gh issue comment <number> --body "..."`, then `gh issue close <number>`. On an already-closed issue, `gh issue close --comment` drops the comment and still exits 0.」行为变化：先评论再关闭；在已经关闭的票上，`--comment` 那种写法会把评论丢掉却仍然返回 0，所以不能靠一条命令做完。

### 4.6 「全新上下文窗口」对 DSH 的含义

上游这轮把「派子代理时用全新上下文窗口、不要 fork 当前对话」写进了 7 个随包文件（清单见 2.1），发布说明给的理由是「有些 harness（Codex）默认 fork 当前对话，而那会把子代理存在的意义——干净上下文——丢掉」（[PR #1341](https://github.com/mattpocock/skills/pull/1341)）。

本仓库这边的事实：

- 全仓没有任何一处引用 `subagent_fork`（grep 过 `*.ts`、`*.mts`、`*.md`、`*.yaml`）；「全新上下文」这个词目前只出现在 `package/bundled-skills-zh/to-tickets/SKILL.md:33`「每个切片的大小要能放进一个全新的上下文窗口」，那是 to-tickets 原有的切票尺子，不是派子代理的规则。
- DSH 有两种派子代理的方式：`subagent` 是独立的新上下文，`subagent_fork` 会把当前对话的已完成回合喂给子代理。上游这句要求对应的正是 `subagent`。
- 随包原文没有点名任何 DSH 工具名，所以「用哪一种」取决于代理自己怎么选，技能文本本身不构成强制。可能的冲突有四处：
  1. **默认用 fork 就违反这句**。如果代理习惯用 `subagent_fork`（例如觉得任务依赖当前对话），就与「全新上下文窗口」直接冲突；这是唯一一条真正的行为冲突。DSH 是否默认 fork，**未证实**——本会话没有被这样配置过，也没有仓内文档说明默认值。
  2. **`code-review` 的「前台」语义**。上游要求两路评审「Issue both sub-agent calls together, in the foreground」。DSH 的 `subagent` 调用会立刻返回一个 id、报告稍后由通知送达，父代理必须等两份报告都到了再汇总；如果派完就往下走，就会只汇总一路。要跟的是「同一条消息里派两个、等两份回执再汇总」这个做法，不是工具本身。
  3. **`research` 说的「后台代理」**。DSH 最接近的是 `subagent`（父代理继续干活、完成时收通知），而不是 `job_*`——`job_*` 是命令后台任务，不是代理。译文与本地说明里不要把「后台代理」写成 `job`。
  4. **子代理层数上限**。DSH 允许把子代理再派子代理的层数限死（本会话就被限成「当前 1 层、最大 1 层、剩余 0 层」，因此在子代理里不能再派）。`code-review`、`wayfinder` 建图、`implement-spec` 这类会派子代理的技能，如果是在一个已经没有剩余层数的子代理里跑，就会派不出去。这个上限是不是 DSH 的默认配置，**未证实**；但它是真实存在的运行条件，写本地说明时值得提一句。
- 要改哪里：随包的英文原文与中文译文都只照译，不要加 DSH 专属说明——英文树被哈希钉住（多一个文件或改一个字就红），中文树要跟英文逐字对应结构。真要给本地代理一句「用 `subagent`，不要 `subagent_fork`」，合适的落点是 `docs/agents/` 下的说明或插件的提示词数据，不是 `package/bundled-skills*`。

## 八、未证实与局限

- 本轮**没有跑任何门禁**（任务不允许跑构建与改仓库），所以「哪扇门禁会红」都是按判据源码推的；实际红绿要在升级动手时用 `npm run verify:parallel` 验证。
- `tests/bundled-skills-upstream-hashes.json` 是手工维护的：仓库里找不到写它的脚本，`sync-matt-skills.mts` 只写 `LICENSE`、`VERSION`、`README.md`；这次升级之前要先定下重算方式，**未证实**原作者当时是怎么生成的。
- DSH 是否默认用 `subagent_fork` 派子代理，**未证实**；本会话只看到自己的层级上限（1/1），没看到默认配置。
- 「子代理层数上限」在本会话里是 1 层，但这是本会话的配置，**未证实**它是 DSH 的默认值。
- 上游发布说明里的 `chief-of-staff` 不在随包范围，本节没有核对它在 `skills/in-progress/` 里的具体改动。
- 各 PR 与 commit 的对应关系取自发布说明与 `git log v1.3.1..v1.3.2 -- <路径>`；个别 commit（例如 wizard 的两笔修复 #1237 / #1198）没有逐笔拆分到具体行，只按文件归属列出。
