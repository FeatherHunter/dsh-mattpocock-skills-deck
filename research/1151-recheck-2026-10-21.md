## 0. 结论摘要

- **判定：不存在。** 针对票面主诉的因果链「磁盘缓存落点按进程工作目录算、沙箱栅栏按会话工作区算，所以切回 workspace-write 档后缓存写不进且没有任何信号」——这条链在今天的源码与运行时上不成立。原因不是「证据不够」，而是这条写入路径根本不经过会话的沙箱政策（见第 3 节）。

## 3. 关键证据：为什么票面机理不成立

### 3.1 插件写缓存时根本不传会话的沙箱政策

- `src/host/git-process.ts:444` 是真正写盘的那一句：
  `await fs.writeText(t, JSON.stringify(Object.assign({}, snap, { cacheFormat: 3 })))`
  —— 只有「目标」和「内容」两个实参，没有第 5 个参数 `sandboxPolicy`。
- `src/host/index.ts:27` `const fs = ctx.get('fs')`；`src/host/platform/index.ts:200` 同样是 `ctx.get('fs')` 透传，`platform.fs` 就是同一个沙箱文件服务，没有再包一层白名单。
- DSH 沙箱的实现里，第 5 个参数缺省时取 `this.ctx.sandboxPolicy.resolve()`（不带参数），见 `.asar 内 dsh/node_modules/@deepseek-ai/dsh-fs-sandbox/lib/index.js:153-154`：
  `async checkedTarget(target, sandboxPolicy) { const policy = sandboxPolicy ?? this.ctx.sandboxPolicy.resolve(); ... }`
  —— 也就是说，插件这条写路径**拿不到会话的工作区**，它拿到的是部署默认政策。

### 3.2 「没有会话」的调用取部署默认政策，而部署根就是 process.cwd()

- `.asar 内 dsh/node_modules/@deepseek-ai/dsh-sandbox-policy/lib/index.js:143-147` 的 `resolve()` 逐字是：
  ```
  return {
    mode: request.mode ?? (session === void 0 ? void 0 : this.overrideOf(session)) ?? this.defaultMode,
    workspaceRoot: resolveWorkspaceRoot(session?.header.cwd ?? this.workspaceRoot),
    ...session === void 0 ? {} : { sessionId: session.id }
  };
  ```
  没有 session 时：`mode` 取部署默认值，`workspaceRoot` 取部署根 `this.workspaceRoot`。这和票面引用的那行代码是同一行，票面引对了；票面漏掉的是「插件调用时没有 session」这一点。
- 部署默认值来自 `.asar 内 dsh/node_modules/@deepseek-ai/dsh-base/cordis.patch.yml:240-247`：
  ```
  - id: sandbox-policy
    name: '@deepseek-ai/dsh-sandbox-policy'
    config:
      mode: !!js process.env.DSH_PERMISSION_MODE ?? 'workspace-write'
      workspaceRoot: !!js process.cwd()
  ```
- 本机 `DSH_PERMISSION_MODE` 在进程、用户、机器三处环境变量里都为空（复核时 15:21 再查仍为空）；整个 app.asar 里只有 dsh-base 这一份配置引用这个变量名；桌面 profile 的 `cordis.patch.yml` 没有覆盖 `sandbox-policy`。所以**今天的部署默认政策就是 workspace-write + 进程 cwd**，票面第 6 条说的「躲在 danger-full-access 后面」并不准确——danger-full-access 只是**会话权限预设**的默认值，不进入这条无会话写路径。
- 桌面版宿主进程的 cwd 从启动起就是 profile 目录：`.asar 内 lib/main.js:3799、3803、3804` 里，宿主进程由 `spawn(this.node, [...], { cwd: this.projectDir, env: desktopNodeEnvironment(...) })` 启动，`this.projectDir` 在 3779 行赋值，取自桌面路径（`resolveDesktopPaths()` 得到的 profile 目录，即 `C:\Users\辰辰洋洋\.dsh\profiles\desktop`）。
- 插件缓存目录在 `src/host/git-process.ts:408-416`：
  `const cwd0 = (typeof process !== 'undefined' && process.cwd) ? process.cwd() : DEFAULT_CWD` → `platform.path.join(cwd0, '.dsh-mattskillsdeck-cache')`。
  同一进程、没有 `process.chdir`（在 asar 里全文搜 `chdir`，只命中子进程运行器对子进程 cwd 的设置，不是进程自己改目录），所以它和部署根是同一个字符串。
- 可写根的推导在 `.asar 内 dsh/node_modules/@deepseek-ai/dsh-sandbox/lib/index.js:166-173`：workspace-write 的可写根 = 政策里的 `workspaceRoot`、`/tmp`、系统临时目录（都先规范化）。缓存目录正好在 `workspaceRoot` 之下，`dsh-fs-sandbox/lib/index.js:158-165` 的 `isPathUnder` 会判为 contained（Windows 下大小写不敏感），写入放行，不会走到 `FS_SANDBOX_DENIED`。

**把这两段接起来就是票面的漏洞**：票面证据 ② 抄的 `session?.header.cwd ?? this.workspaceRoot` 是对的，但它同时说明「没有 session 时用部署根」；而插件这条写路径恰恰没有 session。票面把「会话内的工具写」的规则套到了「插件的无会话写」上。

### 3.3 会话权限档的切换只改会话投影，不改部署政策

`.asar 内 dsh/node_modules/@deepseek-ai/dsh-permission-presets/lib/index.js` 里，切换预设的 `apply()` 在 350 行，实际动作是 `setSandboxMode(session, spec.sandbox)`（356 行；新会话在 381 行同样写法）。这些写的是 **session 的投影状态**（会话自己的 sandbox 记录），不会改部署默认的 `sandboxPolicy` 配置，也不会改 `SandboxedFileSystem` 实例上缓存的 `defaultMode`。所以「把会话权限档切到 workspace-write」不会进入插件这条无会话写路径，也不会改变它的判定。

### 3.4 票面的实验依据不是生产形状（最关键的一条）

票面证据 ④ 引的是 `research/1150-plan-store-injection-verification.md` 第 6.5 节的实验，原始脚本在 `.scratch/1150/exp3-cache-fence.mjs`（53 行）。今天重读该脚本：

- 第 25 行：`const pol = { mode: 'workspace-write', workspaceRoot: SESSION_WS }`，其中 `SESSION_WS = 'D:/dsh-plugin/dsh-mattpocock-skills-deck'`；
- 第 32 行：`sbx.writeText(target, '{"probe":"workspace-write"}', undefined, undefined, pol)` —— 把上面这个「按会话工作区算」的政策**手工当第 5 个参数传进去**；
- 第 40-43 行是对照组：把可写根换成 `PROC_CWD`（进程 cwd）后写入成功。

也就是说，被拒的那一组是**人为构造的政策形状**；生产代码（3.1）从不传这个参数。而对照组「可写根换成进程 cwd」恰好就是生产实际行为（部署根 = 进程 cwd），那一组是成功的。所以票面 ④ 说明的是「如果插件把会话政策传进去会怎样」，推不出「插件缓存写不进」。

同理，`research/1150` 第 6.5 节与第 8 节据此得到的「沙箱那条没修，躲在 danger-full-access 后面」也需要按今天的运行时更正：这条无会话写路径在部署默认政策下运行，部署默认今天是 workspace-write（不是 danger-full-access），而它并不拦当前这个缓存目录。

## 5. 仍然属实的两件事（不属于票面判定，但建议处理）

### 5.1 写失败确实没有任何信号

- `src/host/git-process.ts:435-446` `writeDiskCache`：写入整体包在 `try` 里，`catch (e) { /* 写失败不影响主流程 */ }` 把错误吞掉；函数不返回任何值，调用方在代码层面无法知道写没写成功。
- `src/host/git-process.ts:420-433` `readDiskCache`：读失败（包括解析失败、格式版本不对）一律 `return null`，与「文件不存在」不可区分。
- `src/host/refresh/wiring.ts:444-447` 的 `writeSnapshot`：外面还有一层 `try { ... } catch (eD: any) {}` 空 `catch`。
- `src/host/sessionRefresh.ts:360-361` 与 `src/host/sessionSnapshot.ts:369-370`：`await writeDiskCache(snap2.repo, snap2)` 之后无条件 `return adoptSnapLog(snap2, cwd)`，失败不会回传。
- 全仓 grep `cache.disk` 之类事件 0 处；7 天日志里也没有任何磁盘缓存写入的痕迹（见 3.5）。所以「盘上没写」时，现场区分不出是没拿到文件服务、缓存目录算不出来、被沙箱拒、写抛错，还是写成功但读回解析失败。

**今天不在票面条件下、但会让它真的发作的触发条件**（供以后立票或加固参考）：

1. 部署默认被改成 read-only：例如把环境变量 `DSH_PERMISSION_MODE` 设为 `read-only` 再重启桌面版（或以后 dsh-base 的默认值改成 read-only）。这时所有写入都会被拒，缓存写失败且依然没有信号。
2. 部署 `workspaceRoot` 与进程 cwd 脱钩：dsh-base 现在写的是 `workspaceRoot: process.cwd()`，如果以后被改成固定目录、会话目录或其它根，而插件仍按 `process.cwd()` 拼缓存目录，两者就可能不同根。
3. 插件以后改成把会话政策传给 `writeText`、或改用 DSH storage 服务但没处理失败——那会变成另一条链，需要另做验证。

### 5.2 文档与注释把「部署根 = process.cwd()」说成了「沙箱只允许 process.cwd() 下写」
