# #1566 分诊调查：环境检查为什么认不出「origin 不是 GitHub、GitHub 是第二个远端」的工作区（2026-10-27）

调查范围：票 #1566 的正文与评论（2026-10-26 创建，无评论、无标签）；仓库 main（HEAD `6f823f84`，`package.json` 版本 `1.9.0-beta.26`）里与仓库定位、检查链、开会话有关的源码与门禁；`research/` 下相关既有笔记；gh CLI 自己选远端的那段源码。本次只做诊断：没有改业务代码，也没有开始实施。

## 一句话结论

现象成立：环境检查里「已关联 GitHub 仓库」（判定函数 `backend:github:repoRemote`）与「仓库在 GitHub 上可访问」（`backend:github:repoAccess`）用的是宿主那份只读 `origin` 的仓库定位；而工具面（deck 工具、详情与评论读取那条路）走的是会话的仓库定位，带 `gh repo view` 第三层。于是同一个工作区，工具面能报出 `owner/repo`，检查页这两行却恒红。票面写的三条口径不一致属实；另外还有两点值得写进修法：会话开会话时其实已经在补 GitHub 的仓库身份，需要扫全部远端的解析器仓库里也已经有了。

## 复现（跑的是 main 的真源码，只把外部环境换成临时目录与真 git / gh）

做四套临时目录，`git init` 后按需要加远端，然后跑两样东西：宿主这一侧的 `createRepoKeys().getRepoKey(目录)`（`src/refresh/rooms/host/git-execution.ts` 里的工厂，起真 git、读真 `.git/config`），以及工具面同一条路会用到的 `gh repo view --json nameWithOwner -q .nameWithOwner`。

| 夹具 | `origin` 指向 | 第二个远端 | 宿主的 `getRepoKey` | 同目录的 `gh repo view` |
| --- | --- | --- | --- | --- |
| 甲（本票现场） | 自建 GitLab 镜像地址 | `github` → `https://github.com/FeatherHunter/dsh-mattpocock-skills-deck.git` | `null`（git 可用与只读 `.git/config` 两条路都是） | `FeatherHunter/dsh-mattpocock-skills-deck` |
| 乙（对照） | `https://github.com/FeatherHunter/dsh-mattpocock-skills-deck.git` | 无 | `{ owner: 'FeatherHunter', name: 'dsh-mattpocock-skills-deck' }` | 同上 |
| 丙 | `https://github.com/FeatherHunter/dsh-mattpocock-skills-deck.git` | `upstream` → `https://github.com/cli/cli.git` | `FeatherHunter/dsh-mattpocock-skills-deck` | `cli/cli` |
| 丁 | `https://github.com/cli/cli.git` | `github` → `https://github.com/FeatherHunter/dsh-mattpocock-skills-deck.git` | `cli/cli` | `FeatherHunter/dsh-mattpocock-skills-deck` |

读法：

- 甲证明本票现象：`origin` 不是 GitHub 时，宿主两层都拿不到仓库；同一个目录 `gh repo view` 能拿到（它会把不是 GitHub 的远端过滤掉，只留 `github` 那个远端）。
- 乙证明缺的只是「非 origin 的远端」，不是整个定位逻辑坏了：`origin` 本来就是 GitHub 时，两层都正常。
- 丙、丁证明票面建议的「`origin` 命中 GitHub 优先」与工具面并不一致：两个远端都指向 GitHub 的不同仓库时，宿主今天报的是 `origin` 那个，`gh` 报的是名字分数更高的那个（`upstream` > `github` > `origin`，见下文）。

另外用真 `probeChainEnv`（`src/refresh/rooms/host/chain-env-map.ts`）在甲的目录上跑了一次：`backendId=github` 时它交给 preflight 的 `refId` 是空串（它根本没问会话的仓库定位）；`backendId=gitlab` 时 `refId` 是假会话答的 `session/side`。票面说的第三处口径不一致，在真实代码上可以稳定复现。

## 代码里的三处口径不一致（以及各自的出处）

1. **宿主那份只读 `origin`。** `git-execution.ts:336-373` 的 `getRepoKey`：Tier 1 起 `git -C … remote get-url origin`（`:346-354`）；Tier 2 用正则 `\[remote\s+"origin"\][^[]*url\s*=\s*([^\r\n]+)` 直读 `.git/config`（`:355-366`）。两层都只认名字叫 origin 的远端。没有第三层，因为 #1453 把 `gh repo view` 那一级从这里删了（`:367-372` 的注释写明「需要 gh 的那一级属于出站，改由会话补」）。
2. **环境检查两条谓词直接用宿主这份。** `check-chain-evaluation.ts:354-362` 的 `backend:github:repoRemote` 只调 `getRepoKey`，拿不到就 fail「未找到 GitHub 仓库关联（git remote 未指向 GitHub）」；`:363-373` 的 `backend:github:repoAccess` 在问会话 preflight 之前也先调同一份 `getRepoKey`，拿不到就 fail。所以两行一起红。
3. **探针的 GitHub 分支退回宿主这份，GitLab 分支才问会话。** `chain-env-map.ts:279-294` 的 `repoRefOnce`：非 github 后端走会话的 `getRepoKey` 能力（`:281-290`），github 后端直接调宿主传进来的 `getRepoKey`（`:291`）。而 GitHub 房间自己的 `getRepoKey` 有第三层 `gh repo view`（`src/tracker/rooms/github/repo.ts:119-190`，Tier 3 在 `:170-188`）。

另外两点是修法可以直接借力的：

- **会话开会话时已经在补 GitHub 的仓库身份。** `src/refresh/rooms/host/session-opener.ts:114-147` 的 `resolveRepoRef`：判定出口没带 `refId` 时先用 `describe` 补，仍缺且后端是 GitHub 就问会话自己的 `getRepoKey`（`:129-146`），按操作管线先裁决、再记账（#1453）。这个结果挂在开会话回包的 `repoRef` 上（类型 `OpenedSession` 在 `:55-67`，字段在 `:62`）。检查链的探针类型 `OpenedChainSession`（`chain-env-map.ts:44`）只声明了 `ok`/`backendId`/`call` 三格、没有把 `repoRef` 读出来——要复用它只需要补一格类型，不需要新出一笔 gh。
- **扫全部远端的解析器已经有了。** `src/tracker/kernel/git-remote.ts:30-46` 的 `remoteUrlsOfGitConfig` 只读 `[remote "…"]` 段里的 `url`，远端名字不限 origin（#1533 上线）。把甲的真 `.git/config` 喂给它，两条地址都读得出来。`git-execution.ts` 本来就引 `src/tracker/kernel/` 的文件（文件头 `:17-19`），复用不新增层级依赖。

## 多远端时的选择口径（是拍板材料，不是结论）

gh CLI 给远端排队的规则在 `context/remote.go` 的 `remoteNameSortScore`：`upstream` 3 分、`github` 2 分、`origin` 1 分、其余 0 分；它先把不是 GitHub 的远端过滤掉，再按这个分数排、取第一个（源码：https://raw.githubusercontent.com/cli/cli/trunk/context/remote.go ，2026-10-27 抓取）。夹具丙、丁的实测与这条规则一致：`upstream` 压过 `origin`，`github` 也压过 `origin`。

这条口径与票面建议的「`origin` 命中 GitHub 优先；多个 GitHub 远端判歧义并如实报错」有两处会打架：

- 「`origin` 命中 GitHub 优先」：`origin` 与另一个远端都指向 GitHub 的不同仓库时，宿主会说 `origin` 的仓库、工具面会说名字分数更高的那个仓库——两边又对不上，而票面的目的正是「与工具面口径一致」。
- 「多个 GitHub 远端判歧义」：今天「`origin` 是 GitHub、另加一个 GitHub 远端」的工作区判 pass；按这条会改判红，与票面验收里「既有 `origin` 即 GitHub 的工作区结论不变」冲突。

## 追加（2026-10-27，对抗式复审后）：修法改为「只报工具面的答案」

上一节的修法材料是按票面的「建议修法」整理的。按第一性原理复审之后，原来的两条推荐要改，原因与改用后的规则如下。

### 上一轮的两处误读

1. 我把「工具面口径」当成了裸 `gh repo view` 的选法（upstream > github > origin）。这不是插件实际用的口径：工具面读的是会话的仓库定位能力（`getRepoKey`），先看 `origin`（`git remote get-url origin` → `.git/config` 的 origin 段），只有 origin 不是 GitHub 时才问 `gh repo view`（`src/tracker/rooms/github/repo.ts:119-190`）。所以 **origin 优先恰恰就是工具面口径**；gh 的名字排序只在「origin 不是 GitHub」的分支里生效，并没有和 origin 优先打架。
2. 我把「接会话」当成可拆的补充项。实际上检查链每次求值本来就会开这个会话（`gh:authed`／`repoAccess` 两行要问 preflight），而会话开会话时已经算好仓库身份并随回包返回（`src/refresh/rooms/host/session-opener.ts:226-241` 的 `repoRef`）。检查链只是没去读这一格——不是缺一条新通路，也不是多一笔出站。

### 复审后补进证据的事实

- 带着 refId 问 preflight，会省掉它自己的一次 `gh repo view`（`src/tracker/rooms/github/preflight.ts:201-215` 缺 refId 才跑那一笔）。所以「读会话身份」不但不多花请求，反而少一笔。
- `git remote -v` 会展开 `url.<base>.insteadOf` 别名（2026-10-27 本地实测：配置里写 `gh-work:`，`git remote -v` 打出 `https://github.com/...`）；裸 `.git/config` 文本里仍是别名。所以「本地扫全部远端」必须走 git 命令才和 gh 看到的地址一致，直接扫配置文本会漏。
- gh 选远端只看各远端的 fetch 地址（`context/remote.go` 的 `TranslateRemotes`：先 FetchURL，取不到才看 PushURL）。本地推导因此也只看 fetch 行。
- 链条状态语义有个陷阱：`pending` 会被当成「没过」，并把后端的 onFail 展示与动作一起挂上（`src/shared/tracker/chain-evaluate.ts:237-245`）；对 `gh:remote` 这一步，动作就是「创建并发布」。所以仓库关联这一行不能随便改成 pending，否则会在仓库明明存在时冒出建仓向导。

### 复审后的修法（取代上一节的修法建议）

一条不变量：这两行报的仓库身份，必须等于工具面（会话 `getRepoKey`）实际会用的仓库身份。宿主只允许做「能证明与工具面答案相同」的本地推导，其余一律取会话已经算好的 `repoRef`，不另立规则：

1. `origin` 的地址解析得出 GitHub 仓库 → 就是它（工具面 Tier 1 同一条，必然一致）。
2. 否则，本地远端里**恰好只有一个** GitHub fetch 地址 → 就是它（gh 过滤后只可能选它，必然一致）。远端列表用 `git remote -v` 取（带 insteadOf 展开）；git 不可用时退回读 `.git/config`，此时只能做「有没有」的分类，不推导身份。
3. 否则（多个 GitHub 远端、别名、gh 才认得的形态）→ 读开会话回包里的 `repoRef`（工具面的答案；这次求值本来就开了这个会话）。
4. 还是拿不到 → 红，但按本地证据分两种话术：本地没有 GitHub 远端（去加远端／建仓）／本地有 GitHub 远端（点名是哪个）但工具面没认出（先看 gh 登录与网络那两行）。

配套：

- `repoAccess` 不再在「本地认不出」时提前判红：有身份就带 refId 问 preflight（省掉它自己的 repo-view）；没有身份且本地确有 GitHub 远端时判「暂时确认不了」（pending，诚实未知；这一行不在首开引导链里，不会挂建仓向导）；本地确实没有 GitHub 远端才判红。
- 判定与文案合成一份，两条行共用，避免一处改一处漏。
- 不改宿主 `getRepoKey` 的解析规则（它还被别处用作缓存键与兜底；把「扫全部远端」塞进去等于给别的路径也换一套口径，超出本票边界，且制造第二份定义）。
- 「多个 GitHub 远端判歧义」这条验收要改：宿主不猜，但结果取工具面答案；只有工具面也问不到时才报歧义。否则会把今天工具面明明能用的工作区判红。

### 复审后的三个答案

- Q1：本票一次做完「身份来源 + 文案分类 + 门禁」，不拆会话补位票；不改宿主 `getRepoKey`。
- Q2：origin 优先；单一非 origin GitHub 远端用它；多个非 origin 远端取会话 `repoRef`；工具面也没有答案时才红并点名远端。
- Q3：合并（同一身份来源 + 同一分类函数 + 同一份双语文案）。

## 追加（2026-10-27，第三轮）：报告者想要的与修订方案能给的，以及面板顶「未识别仓库」的同源路径

### 报告者按票面「期望 + 验收」真正要的效果

1. 环境检查「已关联 GitHub 仓库」变绿，detail 与 `deck_context` 给出的 owner/repo 一致；「仓库在 GitHub 上可访问」不再被前置判断拖红。
2. 红的时候文案把人引对方向：没有 GitHub 远端 → 去加远端/建仓；有 GitHub 远端但工具面没认出 → 先查 gh 登录与网络，并点名是哪个远端。不要让人以为该去改 origin。
3. 面板顶部不再显示「未识别仓库」（这条写在「实际」，没有写进期望/验收）。
4. origin 即 GitHub 的工作区结论零变化。
5. 不回归 #1453 的纪律：宿主不新增直连 gh。
6. 验收四种形态：原状 / 单一非 origin / 多远端 / 无远端。

### 修订方案逐条对照

- 第 1 条：完全一致。身份取开会话回包里的 repoRef（工具面 getRepoKey 的同一份答案，`deck_context` 也是同一条能力）；两条谓词共用；preflight 带上 refId 还会省掉它自己一次 repo view。
- 第 2 条：方向一致，但失败边界更窄。单一非 origin GitHub 远端在本方案里直接 pass（不再算失败），第二句文案留给「有 GitHub 远端但工具面没认出」（多远端、别名、gh 不可用），点名远端并指向登录/网络。这是「能认就认」，不是把失败的句子写圆。
- 第 3 条：不一致，本轮新查出来的。面板顶「未识别仓库」不走检查链，走另一条宿主路径（证据见下）；只改两谓词，这块不会变，修完反而自相矛盾。
- 第 4 条：一致。origin 即 GitHub 走同一条 Tier 1，行为不变。
- 第 5 条：一致。不新增宿主直连 gh；本地推导只用 `git remote -v`（fetch 行，含 insteadOf 展开），不出站；全量门禁要等实施后跑 `npm run verify:parallel`，现在是诊断，不能提前说绿。
- 第 6 条：部分一致。多远端不判歧义红：取工具面（会话）已经给出的答案，工具面也问不到才红并点名远端。理由：gh 的 upstream > github > origin 排序只在 origin 不是 GitHub 时生效；报歧义会把今天工具面明明能用的形态判红，是回归。验收措辞需要按此改。

### 面板顶「未识别仓库」的路径证据（同一个根因的第二条消费路径）

- `src/refresh/rooms/host/session-snapshot-cache.ts:307-311`：先 `reg.describe({ cwd }, backendId)`；GitHub 的 describe 即使拿不到身份也返回非空对象（refId 空），所以进入「`!refId`」分支，`:309` 调注入的宿主 `getRepoKey`（只读 origin）。
- `:313-328`：宿主 `getRepoKey` 拿不到时，`buildSnap` 不传 repository 直接返回空快照（selection 仍带 backendId）。
- `src/refresh/rooms/host/snapshot-build.ts:414`：另一条快照组装也先取宿主 `getRepoKey` 再 `pickBackend`。
- `src/host/snapshotEnvelope.ts:82`：`buildSnap` 的 repository 缺省为 null。
- `src/client/panel/Dock.ts:247-256`：repoRef 为空且 `selection.backendId` 存在 → 画琥珀「未识别仓库」。
- `src/client/statusbar/bannerChain.ts:89-102` 的注释也记了同一个观感（「右侧面板还写着未识别仓库」）。
- 结论：只改环境检查两谓词，面板顶不会变；要一致，需要把「origin → 单一 GitHub 远端」这条本地可证推导抽成共享函数，快照路径也走它（不新增出站、不扩会话开销）。

## 第四轮定稿（2026-10-27，自选方案 · 对抗式审查后）

背景：用户要求「从第一性原理出发。对抗式审查。选择你自己认可的方案。」——不再逐条等 Q1-Q4 拍板，由我定稿。本轮补查了面板路径与会话房间的 `describe`，结论是第三轮「不改宿主 `getRepoKey`、检查链取会话 `repoRef`」被推翻：面板没有会话结果可用，只改检查链会留下「检查绿、面板仍琥珀」的自相矛盾。

### 新证据（为什么改）

- GitHub 后端的 `describe` 是同步纯函数（`src/tracker/rooms/github/repo.ts:50-64`）：只认 `handle.refId` 或 cwd 形如 owner/name；`refId` 为空时返回 `refId` 空、name 为 cwd basename 的对象，**不解析 remote**。因此 `src/refresh/rooms/host/session-snapshot-cache.ts:307-329` 在报告现场必然进入宿主 `getRepoKey` 回退；拿不到就产出没有 repository 的快照（`:313-328`）。
- 该文件 `SnapshotDeps` 有 `openSession`，但只交给 composer（约 `:340`），身份解析读不到会话结果；为了面板身份开会话 = 每次快照多一次会话/网络，否决。
- GitHub 房间的认领层 `githubMatches`（`src/tracker/rooms/github/backend.ts:67-97`）早就用 `remoteUrlsOfGitConfig` 扫全部远端；只有身份解析死守 origin，是同一后端内部的不一致。
- 宿主 `getRepoKey` 的缓存只在成功时写（`src/refresh/rooms/host/git-execution.ts:352`、`:363`），负结果不缓存；保留这个语义，用户补好远端后下一次检查能变绿。

### 定稿（与第三轮的不同）

宿主 `getRepoKey` 从「只读 origin」升级为「本地可证身份」：Tier1 `git remote get-url origin`、Tier2 `.git/config` 的 origin 段不变；新增 Tier3 只在两级都拿不到时扫全部远端（git 可用读 `git remote -v` 的 fetch 行，含 insteadOf 展开；git 不可用退回 `.git/config` 全部 `[remote …]` 段，复用 `remoteUrlsOfGitConfig`），用现有 `parseGithubRepo` 解析、按 owner/name 去重；恰好一个身份→采用，两个及以上→不猜返回空身份并保留候选，零个→空身份。同处出富证据口 `getRepoIdentity`（identity / ambiguous(候选) / none），`getRepoKey` 继续返回 `{owner,name}|null` 以兼容现有六个调用点。检查链两条谓词共用这份证据：`repoRemote` 有身份→pass detail owner/name；ambiguous→fail 点名候选并说明把 canonical 设为 origin 或去掉多余远端；none→fail「本地没有指向 GitHub 的远端」；`repoAccess` 有身份才问会话 preflight，无身份用同一文案 fail、不发 preflight。面板快照不改代码，靠同一个 `getRepoKey` 自动修复。不做负缓存。

### 对抗式审查：被否的替代方案

| 替代方案 | 否决理由 |
|---|---|
| 检查链直接用会话 `repoRef` | 仓库关联是本地事实，gh 不可用/未登录时也应能答；面板快照读不到会话结果，仍矛盾 |
| 宿主新增直连 gh 兜底 | #1453 明令移除；宿主层不应新增网络出站 |
| 永远按 gh 的 upstream > github > origin 排序 | 该排序只在 origin 不是 GitHub 时生效；套到「origin 即 GitHub + 另有 GitHub 远端」会把身份改错 |
| 面板另开一张票 | 同一根因、共享函数后几乎零成本；只修检查链会留着「检查绿、面板未识别」的自相矛盾 |
| 面板快照改为开会话拿 `repoRef` | 每次快照多一次会话/网络，只为本地事实不值得 |
| 多个 GitHub 远端时直接报歧义红 | 今天「origin 非 GitHub + 多远端」本来就红，判歧义不是新回归；票面验收明确要求「不猜（明确报歧义）」；面板无法为 gh 猜出的仓库背书，检查若绿会再次矛盾 |
