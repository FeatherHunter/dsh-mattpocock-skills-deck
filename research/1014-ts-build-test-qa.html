让 TypeScript 进构建与测试：结论草案

2026-10-12 · 状态：待维护者逐条表态，未落盘

目标复述：01 号地图不改任何产品行为，只把「源码与运行时之间那道转译线」立起来，让后面每张图「改完立刻看见效果、坏了立刻知道」。做完的标志：随手写一个 .ts，一条命令就能被构建、被测试、被类型检查、被门禁看见，且发布探测仍通过。

二、八个问题与最终推荐

Q101 的验收证据算哪一条

  • 甲：新增类型检查命令 + 一条自检门禁（临时写 .ts，正确版全绿、错误版各自变红）推荐
  • 乙：真挑一个小文件转成 .ts 留在仓库当活样板
  • 丙：只要求 npm run build + npm test 跑通，不新增门禁

✅ 推荐甲（加强版）：新增 npm run check 当那条「一条命令」（构建 → 类型检查 → 测试 → 门禁）。自检门禁分两段：快段进默认链（临时 .ts 走同一条转译函数、断言产物落位、断言 tsc 看见它、断言装载钩子能 import 它）；慢段（真的跑一次完整构建往返）交给发布门禁——它本来就是 build → test。临时文件用唯一名、try/finally 清理、结束断言该路径 git status 为空、目录名进扫描排除表。理由：验收必须是机器判据，但 30 秒冷构建不该塞进 231 条门禁的日常链。

Q2「引用只能朝下」靠编译器还是靠检查工具

  • 甲：照 ADR 上 TypeScript 工程引用（代价：被引用的域必须产出 .d.ts，多一个声明产物目录 + 增量状态，入口换成 tsc -b）
  • 乙：不上工程引用，用依赖图检查判方向
  • 丙：两条都要，分阶段 推荐

✅ 推荐分阶段的丙（已按「讨厌门禁」修订）：现在引一个社区依赖检查工具（dependency-cruiser，npm 上 18.6.0，自述支持 JavaScript/TypeScript），规则写在它的配置里——禁循环、禁跨层深引用、方向表；它一次替掉现有两条老门禁（verify-no-same-layer-import.js、verify-no-cross-import.js），并且同时能看 .js 与 .ts。终态（域边界稳定后）上工程引用，方向由编译器接管，同时把工具配置里那条方向规则删掉，不许两套并存。工程师自己写门禁这条路取消。

Q3混存期里 .ts 引 .js 怎么算

  • 甲：开 allowJs: true、checkJs: false，配一把只降不升的尺子 推荐
  • 乙：不开 allowJs，靠「契约先行 + 自上而下转」保证 .ts 只引 .ts
  • 丙：给 348 个还没转的 .js 手写 .d.ts

✅ 推荐甲 + 棘轮：先否掉乙——计划是自上而下转（03 注册 → … → 12 宿主接线），转上层时下层还是 .js，乙在这套顺序下做不到。实测：开了 allowJs 之后 .js 侧是不检查的 any，收益只是「能过」。因此配棘轮：把「.ts 直接 import 的 .js 边数」与「手写 .js 文件数」做成基线文件（仓里已有两份基线先例），只降不升，基线外新增 .js 判红。最重要的缝（契约）本来已是 .ts；个别重要的房内扩展缝，手写一份 .d.ts 顶到转换完成。

Q4「产物不入库」这次收到哪一步

  • 甲：只清 package/shared
  • 乙：三处一起清，并把产物落点收敛干净 推荐
  • 丙：一处都不清，留给 13 号收口图

✅ 推荐乙：package/shared 的 79 个 .js、像素风 34 个同名 .js、四个核在 src/shared/<核名>/ 的产物全部出库；再加一步终态——产物只落 package/lib、package/shared 与一个构建缓存目录，src/ 下不再生成 .js（四个核的输出目录要挪出 src/）。理由：入库产物是第二真源，逼出了四条 verify-*-freshness.js 当永久税；而 src/ 里不再有生成物，13 号那句「手写 .js 归零核对通过」才可能用目录扫描判。落地：git rm --cached 只动索引、文件留在盘上；单独立票、单独一次提交；把 tests/verify-build-artifacts.js:132-155 的守门对象改成「构建会生成、且不入库」。这条超出 01 原边界，单独成票、单一写者。

Q5新树的 .ts 怎么登记进构建与类型检查

  • 甲：目录扫描 + 一条「不漏不重」门禁（顺手补 locale-cards.ts）推荐
  • 乙：继续按 AGENTS.md 现行做法手工登记进 tsconfig include 与 build.mjs 清单

✅ 推荐甲（加强版）：按域目录通配收集要转译的 .ts；客户端闭包的拼接顺序仍用手写有序清单（顺序是信息，扫不出来）；再加一条「不漏不重」门禁把三者对齐——每个 .ts 恰好属于一个域、恰好被一个转译集合覆盖、闭包清单里没有多余项；构建时打印「本域收录 N 个 .ts」，让扫描结果可见。

Q6测试跑法与 231 条旧门禁怎么退场

  • 甲：node --test + 约三十行装载钩子；旧长串按条迁移；新测试一律 .ts 推荐
  • 乙：一次性把 231 条全部改成新跑法
  • 丙：长串保留，新测试另走一套，不设退场期限

✅ 推荐甲 + 棘轮 + 两条细则：钩子定优先级——同名 .ts 存在就加载 .ts，否则加载 .js（同时解决「陈旧产物冒充真源」）；默认串行跑（--test-concurrency=1，或把有状态门禁标 serial，因为现有门禁里有动夹具、动 git 索引、占端口的）；未迁移测试数只降不升。乙会一次性拆掉后面每张图都依赖的「行为零变化」尺子；丙会让两套跑法永久并存。

Q7要不要写 Node 版本下限

  • 甲：写 engines.node + 一条会报错的门禁 推荐
  • 乙：不写，只在文档里说明

✅ 推荐甲，但只写在根 package.json：package/package.json 的 engines 是给用户侧的，不动；Node 下限属于开发者工具链，建议 >=22（module.register 最低 20.6，但 Node 20 的维护期 2026 年 4 月已结束）。注意 engines 默认只警告不拦人，真正的拦截是那条门禁；下限同时写进 AGENTS.md。

Q8类型检查要不要进阻塞发布链

  • 甲：新增 npm run typecheck 并挂进 npm run verify 推荐
  • 乙：只做 npm run typecheck，不进 verify

✅ 推荐甲 + 防「绿而没检查」：typecheck 用 glob 发现全部 tsconfig（不手写清单），跑完断言「发现的份数与文件数」达到预期下限。理由：tsc -p 只检查它 include 到的文件，include 漏了照样绿（locale-cards.ts 是活证）；实测成本亚秒级，不进阻塞链则「写错编译就报错」这条收益只在本地生效。

三、Q2 深挖（给 TypeScript 新手）

1. 「依赖图门禁」是什么

把「哪个文件引用了哪个文件」全部读出来，画成一张图（点 = 文件，线 = 引用），再按目录规则看这张图上有没有不该有的线。

例子：src/deck/shell/xxx.ts 里若写着 import ... from '../../host/tracker/backends/github/yyy.js'，图上就多出一条「deck → GitHub 房」的线，规则说这条线不许有，它报红。它跟现在的 tests/verify-*.js 一样挂在 npm run verify 里，非 0 阻塞发布。

仓里今天有两条这种门禁，判据是「读文件文本 + 正则」：tests/verify-no-same-layer-import.js（同层内部不许互引）、tests/verify-no-cross-import.js（三座房间之间不许跨房）。你提到的第三条 tests/verify-file-granularity.js 数的是「每个文件多少行」，不是依赖图，只是同样靠读文本。

2. 「用 TypeScript 编译器 API 解析 import」是什么

不用正则去猜，而是把源码交给 TypeScript 自己的解析器，让它读成一棵语法树，再从树上读「这条 import 指向哪」。

仓里已有现成例子：tests/verify-client-no-undef.js:24 就是 const ts = require('typescript-ast')，接着 ts.createProgram(...)、ts.getPreEmitDiagnostics(program) 拿诊断——那就是在调用编译器。

为什么比正则好：注释里的 import、字符串里的 import 字样、import type、export ... from、import(变量)，正则要一条条写规则还容易漏；编译器给的就是「代码实际会怎么解析」。老门禁为了绕开这些，注释里专门写了「先去掉块注释与行注释，JSDoc 里的 import() 不算数」，那都是要还的债。

3. typescript-ast 是什么

就是根 package.json:36 那一行："typescript-ast": "npm:typescript@5.6.3"。这是 npm 的别名写法：把 typescript 这个包再装一份，名字叫 typescript-ast，版本 5.6.3。

为什么这么干，tests/verify-client-no-undef.js:12-15 写清了：主包 typescript 升到 7.x（Go 重写）之后不再导出可以在代码里调用的编译器接口（createProgram 这类取不到），而构建与类型检查用的是 7.x 的 tsc 命令行本体，不受影响。所以凡是要在脚本里调用编译器的地方，就 require typescript-ast。

结论：这套「解析 import」的能力不需要新增任何依赖，仓里已经装好了。

4. 那三条规则怎么管到、为什么能管到

  • 引用只能朝下：每条线的两头各落在哪个域（deck / tracker 契约 / 内核 / 三座房间），把允许的方向写成一张表；表外的线出现就报红。
  • 禁循环：A 引 B、B 引 A，或绕一圈回到自己，这是图上的「环」，工具自带判定。
  • 禁跨层深引用：把「允许连到谁」收窄成白名单——deck 只许连到 src/tracker/contract/ 的公开入口，连到 src/host/tracker/backends/**（房间实现）或 src/host/tracker/detection/**（识别判定）即违规。
  • 为什么能管到：这三条的判据都只是「线的两头是谁」，而线的两头在源码里是静态写死的，不需要运行程序就能读出来。
  • 管不到什么：路径是算出来的看不见，例如 await import('./' + name + '.js')。今天老门禁对此的口径是「一律算违规」，新工具要沿用同样的严格度，否则这里就是一个洞。

5. 「终态（12 号收口后）」是什么

指地图 #1010 里排在最后的几张图做完之后的局面：12 号「宿主接线」做完的标志是全仓没有指向旧路径的活引用、面板读数与今天一致；13 号「收口」是全域索引加手写 .js 归零核对。在它们之前还有 1019 那次机械搬家（91 处引用一次改完）、08/09 两房改造、11 号最底层。

为什么工程引用要等到那时候：工程引用要求「每个文件固定属于哪个工程」。在此之前文件还在搬（三座房间要搬进 rooms/、契约刚挪过家、91 处引用要一次改完）。此刻立工程图，等于一边搬家一边改门牌，编译器报的错会把真问题埋在噪声里。

6. 「把方向从检查升级成编译期事实」——这样对吗

对，但有三个细节必须补上：

  • 它只管编译器看得见的文件（.ts）：过渡期那 348 个手写 .js 不在任何工程里，所以现在只能靠检查工具。
  • 它有实测代价：被引用的域必须真的产出 .d.ts（实测报 TS6310），类型检查入口从 tsc -p 换成 tsc -b，多一个声明产物目录。
  • 它的边界：编译器保证「不许引用没被 references 的域」（实测写反方向导入报 TS6059/TS6307），但同一工程内部随便引，「只许走契约入口」这条它管不了——深引用这条规则即使上了工程引用也要继续由工具管。

大白话：检查工具是「交卷前有人替你核对一遍」，编译器是「写错当场不让你编译过」。前者可能漏，后者不会漏，所以终态那一步值得做。

7. 你讨厌门禁 → 推荐改成这样

先站你这边：你讨厌的大概是「自己写的、读文件文本钉写法」的那类，而仓里已经按你的意思删过一批——tests/verify-build-artifacts.js 里三条读文本钉形状的断言被删掉了，注释还留在文件里（第 4-8 行、156-161 行）。ADR 也早写了「换成社区的」。

  • 引社区标准工具：dependency-cruiser（npm 当前 18.6.0，自述支持 JavaScript/TypeScript），规则写配置文件：禁循环、禁跨层深引用、方向表。
  • 一次替掉两条老门禁，且同时能看 .js 与 .ts，过渡期不用另写一套。
  • 终态删掉方向规则：工程引用上线后，方向归编译器，配置里那条删掉，不许并存。同一条规则两个判据，迟早不一致，最后没人知道哪个说了算——那就是「假绿」的来源。

一句反向的话供你驳：问题不在「有门禁」，而在「自己写的、读文本钉写法、一条规则两个判据」。这三样都该消掉；但完全没有检查等于靠自觉，这次要跨十几张图和多个会话，靠自觉的东西一定退化。建议口径：能交给编译器的不写检查；非写不可的用社区工具；自己写的检查只留「只有这个仓库知道」的规则，且每条都要能说出它防的是哪一次真实事故。

8. 为什么这张票挂 13 号、写死触发条件与「上线即删」

  • 挂 13 号：13 号本来就是「收口」，工程引用的判据是终态。放这里，既不会被提前做（提前做与搬家打架），也不会被忘（收口图就是清账的地方）。
  • 写死触发条件：跨会话的工作里「以后再说」基本等于「永远不做」。条件必须可判定，例如：12 号收口 + 手写 .js 归零核对通过。
  • 「上线即删」：第 7 条那条原则的落地方式，防止两套判据并存。
  • 优点：① 过渡期不付工程引用的代价（声明产物目录、搬家期 tsc -b 的噪声）；② 终态拿到最硬的保证（编译器级，不是脚本级）；③ 删掉的是「检查」，不是「判断力」——规则交给了更硬的那一方。

四、建议写进票里的结论骨架

I1 一份真源

源码树只有 .ts；生成物只落 package/lib、package/shared 与构建缓存目录，永不入库。

I2 一种写法

源码里的相对引用一律写 ./x.js（TS 会解析到同名 .ts，产物正好就是 .js——实测成立）。

I3 一条命令

npm run check = 构建 + 类型检查 + 测试 + 门禁；发布门禁另跑完整链。

I4 两把棘轮

手写 .js 数、.ts 引 .js 的边数，只降不升，基线入库。

I5 空集合判红

任何门禁扫到的输入集为空时必须红，不许绿。
