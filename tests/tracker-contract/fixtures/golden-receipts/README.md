# 金标准回执夹具（#1015，硬化版）

把「行为零变化」从口头承诺变成机器判据：九个 deck 工具的代表性回执，归一化后逐字节比对，差一个字符就红。

## 跑法（自挂钩子，裸跑即正确）

```sh
node tests/verify-golden-receipts.ts            # 比对（只读基准，不写盘）
node tests/verify-golden-receipts.ts --update   # 重建基准（只在有意改行为且已评审时用）
```

不需要命令行再挂钩子：夹具启动第一件事就是自己导入 `scripts/ts-hook.mjs`（与生产线 `npm test` 挂的是同一个）。此后一切产品模块导入都走同一解析路径——同名 `.ts` 存在就量 `.ts`，不存在就量 `.js`。混存期量不错文件。

比对全绿 exit 0；任何一个字符不一致 exit 1，并指出第一个不一致的字符位置与前后片段。`--update` 会逐个报告"新建／不变／已更新（旧字数→新字数＋首个差异位置）"，最后汇总有几个文件内容变了——重建基准必须是有意改行为且已评审，顺手跑的不算。

## 基准内容（10 个文件）

- `01-deck_context.golden.json` … `08-deck_issue_patch.golden.json`：
  前八个 deck 工具各一次代表性调用的完整归一化回执。
  调用顺序本身就是基准的一部分（写操作有先后）：
  context → issue_create（建「金标准演示票」）→ issue_list →
  issue_get（key 01）→ map_snapshot（key 00 底图）→
  map_plan_create（planId golden-1，建「金标准地图」+ 两张子票；原文布局下地图是 00，
  子票编号接着已有的 01 号票往下排成 02/03）→
  map_link（03 blockedBy 02）→ issue_patch（加一条评论）。
- `09-deck_issue_report-retired-progress.golden.json`：
  上报带已退役的 `progress` 时那份拒绝回执：`bad-args`，不选后端、不花点数、不写盘。
- `10-deck_issue_report-without-progress.golden.json`：
  上报的快乐路径（不带 `progress`，文件名沿用历史）；回执与工作条目里都不出现进度自评这一格。
- `two-room-shape.golden.json`：
  同一张最小票在本地 Markdown 房与 GitHub 房 normalize 之后的字段形状对照。
  只比「有哪些字段」与「已知差异」，不比具体值。

## 确定性设计（基准为什么可复现）

- 固定工作区：每次运行新建临时目录，底图 `map.md` 内容固定（标题「金标准底图」）。
  原文布局下一个目录只允许一份 `map.md`：底图先让 05 快照量完，建图场景开始前撤掉，
  再由建图工具写出自己的 `map.md`（旧扁平布局把地图放成 issues/ 里的普通票，不必撤）。
- 固定会话：`session id = s-golden`（幂等锚由会话 + 标题 + 标签算出，会话固定锚就固定；会话号出现在回执里但每次都一样，故不归一化）。
- 固定时钟：`now = 1700000000000`（幂等锚的时间窗口号固定）。
- 固定配额账本：同步 5000 点剩余额度，本地后端零花费，`cost.actual` 每次一样。
- 真实链路：用的就是产品代码里的 gate + ledger + registry + Markdown 后端，
  不是 mock——行为变了基准一定变。
- 解析自证：每个模块记录实际解析到了 `.js` 还是 `.ts`（跑起来第一行就打印，如"16 个模块，0 个走 .ts"）；
  若磁盘上有 `.ts` 兄弟却解析到 `.js`，说明钩子没生效，直接报错退出——含糊时宁可红，不要绿。

## 归一化口径（基准里看不到的东西，只有三样）

1. 绝对路径：本次运行的工作区根一律换成 `<ROOT>`（posix 与反斜杠两种写法都换）。
2. 工作区钥匙：本次运行的精确钥匙值换成 `<WSKEY>`（它由工作区根算出，根变它就变）。
   不用通配正则——通配会把票正文里恰好长得像钥匙的内容也抹掉，那是假绿。
3. 时间戳：`Z` 结尾的 ISO 时刻一律换成 `<TIME>`（文件修改时间是墙上时钟，两次运行必然不同）。
   别的时刻形状若出现，让它红（红比悄悄抹掉对），再按需把新形状列进来。

其余原样比对：幂等锚、票号、标签、回执形状、花费预估，一个字符都不放过。
对象键递归排序后再比（JSON 键顺序永不承载语义，排了之后重构式改动不再误红）；
数组顺序不动（列表输出本来就按 key 排过，是确定性的）。

约束：金标准演示票的标题、正文、评论里不许出现日期样子的字符串，否则归一化会把它当时间戳抹掉。

## 守卫边界（本夹具不是全部，请勿误读）

每个工具一次最小调用，只守快乐路径回执。错误分支与集成级错误包络由
`tests/verify-deck-tools.js` 的 86 条守着，后端契约由
`tests/verify-tracker-contract.js` 守着。夹具绿不等于行为全等；
夹具红则一定是有东西变了（表示抖动或真漂移，按下一节分拣）。

已知缺口（离线量尺的原理边界，不是疏漏）：GitHub 房特有的回执措辞
（evidence 文案、landing 落点描述）只有真机联网能走到；playback 固件守的是
后端契约层的形状，不是这九个工具在 GitHub 房里的回执原文。
已知约束：按修改时间倒序的那处列表在时间粒度粗的文件系统上可能抖动，
同机同文件系统可忽略，跨机器红了先查这一条。

## 分拣指南（红了先看这里）

- `cost.actual.remaining` 是具名常量（`src/refresh/kernel/host-budget.ts` 的
  `PLUGIN_HOURLY_CAP`），变了先看是不是调过配额。
- `<TIME>` / `<ROOT>` / `<WSKEY>` 不可能出现在差异里（已归一），
  若出现说明归一化漏了新形状，按上一节第 3 条处理。
- 其余差异逐个看：键少了/多了是真漂移，值变了是真漂移。

## 与 #1014 讨论结论的衔接

- Q1 活样板：本夹具就是它的量尺。以后任何改动如果改了九个工具任一回执，
  夹具这一关会先红；契约与 playback 守各自那层，三层分工不同，不互相替代。
- Q5 闭包拼接顺序：手写有序清单仍然保留，改顺序会改变构建产物；
  本夹具守的是工具回执层，拼接顺序的量尺由构建产物守。
