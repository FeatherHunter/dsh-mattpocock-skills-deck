Q1 帖子由谁发出去

背景：帖子要发在公开仓库，署你的名字，发出去就有人看到，删掉也会留下记录。你的 gh 已经登录，权限也够，技术上一行命令就能发。

选项利弊

  • A 我用你的账号直接发，发之前把最终全文渲染成网页给你看，你点头我才发（推荐）。利：一步到位，排版、图片、换行都不会在手工搬运时出错，你只需要看一遍。弊：账号动作由我代做，这一步需要你信任。
  • B 我把最终文本给你，你自己粘贴发布。利：发布时机和账号动作完全在你手里。弊：你多一道手工活；长文粘贴容易丢换行；图有没有显示对还得你自己确认。
  • C 只给草稿，不发布。利：最保守。弊：事情只做了一半。
我的推荐：A。前提是"预览"这一步不能省。
对抗式审查后：仍是 A，但补一条硬规则。预览必须是浏览器里渲染出来的效果，不能是 Markdown 源码——源码里看不出图片多大、段落有没有挤在一起。另外把动作拆成两步：我先把预览给你并写明"你说可以我才发"，你不回话我就不发。只有在你不想让任何工具替你操作账号时，B 才更好。
从头想起后：仍是 A。这件事唯一不可逆的是"发出去"那一下。所以原则是：不可逆的一步留给能做最终判断的人，但不必为了这一下让整篇手工搬运。预览确认加我来发，刚好卡在这个点上。

Q2 帖子写多长

背景：你给的素材有 5 个功能点和 4 张截图。我读了那个分类里最近反响不错的几篇，长度大致在英文 300–600 词，写法都是"我遇到什么麻烦、我做了什么、想听你的意见"。讨论区不是说明书，读者是刷到的，不是来查文档的。

选项利弊

  • A 短：中文 300 字左右，只讲最亮的两三件事。利：读完率高。弊：放不下 5 个功能点，4 张图也铺不开。
  • B 中：中文 500–700 字，5 个功能点讲全，配 3–4 张图（推荐）。利：讲得清又不拖，和图的数量匹配。弊：要砍掉次要功能，写到后面得克制。
  • C 长：完整功能清单加安装步骤，像一篇文档。利：信息最全。弊：讨论区里没人读完，图片会把页面拉得很长，重点被淹没。
我的推荐：B。
对抗式审查后：仍是 B，加两条约束。一是图必须限宽——那几张截图原始宽度 3833 像素，不限宽会把页面拉得极长；二是中英双语等于篇幅翻倍，所以中文正文控制在 600 字内、英文控制在 350 词内。真正的风险不是"写少了"，而是"读者滚了两屏还没看到重点"，所以开头三句必须把"这是什么、解决什么麻烦"讲完。
从头想起后：仍是 B。帖子只有两个任务：让人看懂、让人想试。字数不是目标，"读者在两屏内能记住三件事"才是，按这个标准反推篇幅就落在中档。

Q3 要不要交代背景和身份

背景：那个讨论区的读者大多用 Claude Code，不一定知道 DeepSeek Harness（DSH）。你这个插件只对 DSH 用户有用，而且是个人作品，跟 mattpocock/skills 没有官方关系。

选项利弊

  • A 开头一句话说明 DSH 是什么，第一次提到插件时顺带写明是个人作品、与作者没有官方关系，结尾向 Matt 道谢（推荐）。利：不会让人误会成官方插件，也解释了"为什么只在 DSH 里能用"。弊：多三句话，开场稍慢。
  • B 不提，直接讲功能。利：开场干脆。弊：多数读者会困惑这是什么环境，甚至以为是官方周边。
  • C 把"非官方"声明放在开头。利：最不容易误解。弊：像免责声明，读者还没看到价值就先看到声明。
我的推荐：A。
对抗式审查后：仍是 A，但位置调整。"这是什么"放开头一句；"与作者无官方关系"不要单列成声明，而是在第一次出现插件名时用半句话带过（例如"我自己做的、跟 Matt 没有官方关系的插件"）；道谢放结尾一句。这样该说的都说了，又不打断阅读节奏。
从头想起后：仍是 A。读者翻开帖子先问"这跟我有什么关系"。开头必须先回答这个问题（用 Matt 的技能干活时，重复的琐事太多），再一句交代环境与身份。

Q4 安装信息放多少

背景：能装这个插件的只有 DSH 用户。安装其实是两步：先装 DSH，再装插件；插件还分桌面版和网页版两种 profile，装错等于没装——这是你仓库 README 里专门提醒过的坑。

选项利弊

  • A 一行命令加仓库链接。利：想试的人马上动手，看不懂的人也不被挡住。弊：桌面版用户可能照抄网页版那条命令，装错地方却以为插件坏了。
  • B 完整安装块（先装 DSH、再装插件、重启说明）。利：几乎不会装错。弊：占掉帖子近一半篇幅，非 DSH 用户会觉得啰嗦。
  • C 只放仓库链接。利：最短。弊：想试的人还要多点一层，动手的人会变少。
我的推荐：A。
对抗式审查后：仍是 A，但命令由一行改成两行。桌面版和网页版各一行，再加一句"装错 profile 等于没装"。理由是"装错 profile"是你自己踩过并写进 README 的坑，对读者伤害最直接。两行命令换掉一次踩坑，划算。
从头想起后：仍是 A 加两行命令。标准是"想试的人一分钟内能装上、看不懂的人不被挡住"，两行命令刚好满足，完整教程留在仓库里。

Q5 讲哪几个功能

背景：你列了 5 条：① 技能操作变成面板；② 当前会话在处理哪个工单、处理过哪些；③ 预置按钮，长会话快满时一键交接；④ 右侧面板按工单状态给不同按钮，一键点；⑤ 新会话自动改名。仓库 README 里还有：任务板按可接/阻塞/已关闭分组、底部状态栏、工单详情与评论、新会话预填指令、27 个技能快捷入口、多后端切换。

选项利弊

  • A 只讲你列的 5 条。利：忠于你的原意。弊：第①条是总纲（"变成面板"），和第④条重叠，实际只有 4 个独立点。
  • B 讲 4 个独立点，其余一句带过（推荐）。利：每一条都是别人也能感同身受的麻烦。弊：舍掉一部分工作量展示。
  • C 把 README 里的都讲。利：展示完整。弊：变成功能清单，读者一条也记不住。
我的推荐：B。
对抗式审查后：仍是 B，但顺序按"读者能感同身受的程度"排，不按你的列表顺序：先讲"工单多了记不住状态"（对应②④），再讲"会话快满、上下文要丢"（对应③），最后讲"二三十个会话同时开、改名很枯燥"（对应⑤）；第①条改成标题和开头的引子。另外，4 张图里那张"预置 prompt 按钮"的图可以并进③一起讲，不必单列一段。
从头想起后：仍是 B。帖子不是功能清单，读者只会记住"他也有这个麻烦"的条目。按痛点排序、只留 4 条，是唯一站得住的标准。

Q6 标题用什么语言

背景：正文你已定"先中文后英文"。但那个讨论区读者以英文为主，标题是所有人都会看到的一行。

选项利弊

  • A 英文标题一行（推荐）。利：主要读者一眼看懂，也容易被搜到。弊：中文读者要靠正文第一段才明白。
  • B 中英各一行标题。利：两种读者都照顾到。弊：标题区重复、占地方，英文读者会觉得奇怪。
  • C 中文标题。利：中文读者亲切。弊：多数读者看不懂，等于没有标题。
我的推荐：A，插件名放最前面，例如 MattSkillsDeck: a task board for the Matt Pocock skills workflow in DeepSeek Harness。
对抗式审查后：仍是 A，加一条提醒：标题里不要出现只有中文用户才懂的直译词（"工单""面板"之类），用最普通的英文说清"这是什么"。中文版是正文开头整段，标题不必再照顾一次。
从头想起后：仍是 A。标题只有一个职责：让目标读者判断要不要点开。目标读者以英文为主，所以用英文；中文读者进了正文就都懂了。

Q7 图片怎么放

背景：你贴的 4 张截图都存在 GitHub 上、可以直接引用（我测过，都能打开）。原始尺寸最宽 3833 像素，不限宽会占满整屏、把文字挤得很远。

选项利弊

  • A 分散放，讲到一个功能就放对应的图，并统一限宽（推荐）。利：图就是那段话的说明，读起来顺；限宽后滚动长度可控。弊：每张图要配一句说明，写起来稍费事。
  • B 全部集中在开头或结尾。利：写起来省事。弊：读者看图时不知道在讲什么，图白放。
  • C 不放图，只放文字。利：帖子短。弊：界面类工具没有图，很难让人相信好看又好用。
我的推荐：A。
对抗式审查后：仍是 A，但由 4 张减到 3 张：开头一张整体界面，中间一张"按状态给按钮"，末尾一张"会话自动改名"。第③张很窄（1192×78），并进"长会话交接"那段当插图；如果放不下，宁可不放也不凑数。
从头想起后：仍是 A。图的作用是替文字解释界面，所以必须紧挨着需要解释的那句话；张数由"读者要记住几件事"决定，不由手上有几张图决定。
