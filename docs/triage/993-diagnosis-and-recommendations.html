三个决定答案形状的事实

事实证据对答案的影响
1. 仓库里已经有「认不出来」这一档，只有出错的那一头没在用 向导弹窗的代码写的是「有分类就用，没有就用 unknown」（client.js:11223）；panel.noRepoErr.unknown 的中英文文案也早就在（src/client/kernel/locale-panel.js:144 与第 309 行） 改成 unknown 不是发明新东西，是让出错的那一头对齐客户端已经在用的值
2. 只改兜底，用户仍然看不到 git 的原话 把界面取文案的函数抠出来实跑：分类改成 unknown 后显示「创建失败，请查看错误详情」，原文一个字不显示；现状显示「权限不足，请检查登录账号 · fatal: detected dubious ownership…」 「兜底改诚实」和「让用户看见真实原因」必须一起做，缺一个都不算修好
3. 修法那行命令今天到不了用户眼前 三道截断叠加：出错那头先把错误文本截到 400 字（src/host/repoKeys.js:196），向导弹窗再截到 120 字，红卡截到 160 字。报告那条原文的修法命令正好落在截断之外 修法必须由分类器自己产出一句短文案，不能指望原文捎带

Q4　兜底改成哪个取值？

背景

出错分类函数认不出来时，最后一行直接返回「没权限」。所以磁盘满、git 身份没配、提交钩子拒绝，全被说成「权限不足，请检查登录账号」，报告人因此先查登录、再查令牌范围，白花一个多小时。可选值有两个：新增一个 unknown，或者沿用契约层「认不出来就归网络」的写法。

推荐答案

改成 unknown。同时必须做两件事，缺一件都不算修好：① 后端文案表补一条 unknown 的中英文；② 红卡那条界面路在 unknown 档下也要把原始错误文本显示出来。

优点
  • 下游（界面文案、取值判断）早就按 unknown 写好了，不用新增词汇
  • 不再把「不知道」说成「没权限」，用户不会再去查登录和令牌
  • 「仓库名已存在」这类被故意改写成 permission 的旧写法可以一并拆掉
缺点
  • 是出错那一头的输出变更，下游所有消费这个取值的地方都要跟着核对一遍
  • 只改取值不改界面，用户会看到「创建失败，请查看错误详情」这种没有信息量的话
对抗式审查

反对一：错误类别枚举里没有 unknown，这不是既有词汇。成立，但不决定性。这个流程的取值从「没装 git」「没装 gh」开始就不是那套枚举，它是另一套字符串。决定性的是客户端已经按 unknown 写了。

反对二：改输出就是改契约，风险大。方向反了。现在的 permission 是一个被下游当真值使用的猜测，它会变成错误码去驱动「没登录」那类自动引导。改掉它是在收回一个错误承诺，不是新增契约。

反对三：那不如只在界面兜底，不动出错那头。不成立。出错那头说的是 permission，界面无从分辨这是真权限问题还是猜的。只有出错那头知道自己是猜的。

反对四：unknown 和 permission 不都是一句话吗？差别在把用户引向哪里：permission 让人去查登录和令牌，unknown 加原文让人直接看到 git 说了什么。报告人的一小时就是这两者的差价。

从第一性原理出发

这个分类函数的输出被当成两样东西用：出了什么错，和用户该去做什么。这是两个不同的轴，被压成了一个值。一旦压成一个值，凡是认不出来的错误，就必须借一个错误的「该做什么」——这就是「兜底归权限」的真正来源。

所以 unknown 不是「第九种错误类别」，它是「分类器承认自己不知道」这件事的合法表达。它同时是一个契约承诺：取值是 unknown 时，界面必须把原始错误文本显示出来。

Q4 结论：改成 unknown，并且把「显示原文」写进同一张票的验收标准。

Q5　本票和 #994 的分工怎么划？

背景

#994 说的是「发布流程没有提前检查工作区能不能用 git」，它已经切到 ready-for-agent，并且自己就引用了本票，建议里包含「把属主不一致单独成一档，并给出修法提示」——这和本票的修法建议是同一件事。两票各做各的会写出两套识别。

推荐答案

两票都留，但分工写死：

  • 本票（#993）：兜底改 unknown、后端补文案、红卡在 unknown 档显示原文、属主不一致单独成一档并给一句短修法、补 git 侧失败的回归测试。不碰提前发现、不碰自动修。
  • #994：提前发现（动手前就拦住）、自动补 safe.directory 再重试一次，以及这个识别函数本身的归属。
  • 唯一真源：「属主不一致」的判据和修法提示只写一处，放在三个后端都能引用的共享目录下（src/shared/tracker/，仓库里已有同类先例）。不要让发布流程去引用某个后端房间的文件，那会同时撞上仓库的两道分层门禁。
优点
  • 两票各自都能独立验收，不会互相等
  • 判据只有一处，不会出现「提前发现说属主问题、兜底说权限不足」的自相矛盾
  • 共享目录是仓库既有做法，不需要新开分层例外
缺点
  • 本票要动到「属主不一致」这一档，和 #994 有一小块重叠，需要靠文档把边界钉住
  • 两票都动同一个出错分类函数，谁先合并谁的改动会被另一方撞到
对抗式审查

反对一：既然 #994 会提前拦住并给出修法，本票的专门档就是重复的。一半成立。#994 确实认领了这一档。但本票仍然需要它——理由是事实三：光改兜底，用户看到「创建失败，请查看错误详情」，修法一个字看不到。

反对二：那本票干脆只做兜底，别管属主问题。我原本也这么想，被事实三推翻了。至少要让这一档带出一句短修法文案。

反对三：#994 的探针能覆盖报告人的现场吗？这是本次审查最值钱的产出，单列为 Q7。

反对四：把识别放共享目录会不会绕过门禁？不会。跨后端房引用共享目录是白名单允许的，仓库里已有同类先例（三个后端共用一份「这张票是不是我建的」判断）。

从第一性原理出发

这里有两件不同的事被混在一起谈：动手前主动确认工作区可用（预防），和失败后解释发生了什么（归因）。预防能减少失败，但永远不能消灭失败——磁盘会满、文件会在检查之后被人改掉。所以两者不是二选一，是两层。

但两层必须共用同一个事实来源，否则同一个「属主不一致」会在两条路上被说出两种话。这就是「唯一真源」不是洁癖、而是必要的原因。

Q5 结论：两票都留、分工写死、判据只写一处。

Q6　契约层同类毛病要不要单独开票？

背景

「认不出来就借一个真实档位」这个毛病一共有三处，不是一处：

位置认不出来时用户能看到的后果
发布流程的错误分类（本票）说成「没权限」「权限不足，请检查登录账号」，排查方向跑偏
契约层的通用错误分类 src/host/tracker/preflight.js:57说成「网络」未知错误被说成网络问题（影响面待证）
重试推送失败的界面兜底 src/client/kernel/slotRenderer-repo-sync.js:102 与 :107说成「网络」取值被填成网络，只在半成功那条路影响副文案
推荐答案

开一张票，但把范围砍小：只收「用户能看到的错误分类」，先修两处界面兜底（各一行，零成本），再单独论证契约层那一处。不要把「给错误类别枚举新增 unknown」塞进来。

优点
  • 同一个毛病集中在一张票里，不会散成三张没人管的单子
  • 砍掉枚举改造，避免动到所有后端和它们的消费方
  • 两处界面兜底是零成本修复，可以立刻落地
缺点
  • 契约层那一处的实际影响我还没证实，票里必须写明是「同类毛病、影响待证」
  • 只修界面兜底不修契约层，同一类错误在不同界面上的说法仍可能不一致
对抗式审查

反对一：错误分类里返回 unknown 是既有做法，所以契约层那处不算毛病。这句是错的，已核实：那个 unknown 只是写日志用的原始档位标签，不是分类结果；契约层的错误类别八个值里没有 unknown。

反对二：三处一起修，票据范围太大。成立，所以砍掉枚举改造。要动枚举得改所有后端和每一处消费方，成本与收益不成比例。

反对三：契约层那处的影响被夸大了。这一条我承认。它在很多调用点只用于日志和分支，不直接产文案。票里不能写成「已确认的用户可见缺陷」。

反对四：本票顺手修了不就行了。不行。本票的验收标准是「git 侧错误不再被说成权限不足」，塞进契约层会让验收边界糊掉，而 #994 正在同一片区域动刀。

从第一性原理出发

错误分类的输出如果既要给日志看、又要给用户看，就必须回答两个问题：我们知道多少，和这个信息给谁用。只给日志看时，猜一个最可能的档位代价很小；要给用户看时，猜错会把人的时间引到错误的方向——报告人的一小时就是这么花掉的。

所以正确的切法是按受众切，不是按代码位置切：凡是要变成用户眼前那句话的分类，认不出来就必须说认不出来；只给日志用的，维持现状即可。这也正是把契约层那一处先列为「影响待证」的原因。

Q6 结论：开票但砍小范围，先修两处界面兜底，契约层那处单独论证。

Q7　#994 的探针能抓到报告人的现场吗？（审查中新增）

背景

#994 建议用 git rev-parse --is-inside-work-tree 做提前检查，用来发现「属主不一致」。但两处证据对不上：

  • #994 的正文说：git init 成功，从 git add 才开始报属主不一致。
  • 报告人在本票正文里给的实测输出是：git rev-parse --is-inside-work-tree 就已经报了属主不一致。

如果 rev-parse 在属主不一致时能成功，那用它做探针就抓不到这个现场，探针必须换成真正碰索引的命令（例如 git add -n . 或 git status）。

推荐答案

把「rev-parse 在属主不一致时到底会不会失败」列为 #994 动工前必须核实的第一件事，核实前不要按 rev-parse 做探针。本机无法定论：Windows 上造不出「属主不同」而不改系统权限。

优点
  • 避免 #994 交付一个「看起来做了检查、实际抓不到报告人这个场景」的探针
  • 核实成本很低：在真机上跑两条命令即可
缺点
  • 属于 #994 的范围，本票只能提出，不能替它决定
  • 核实需要报告人那类环境（Android 真机 + 属主不一致），本机替代不了
对抗式审查

反对：这不就是两份描述里有一份记错了吗，值得单列？值得。这不是措辞出入，而是决定探针选哪条命令的分叉点。选错的结果是：检查通过了，流程照样在下一步死掉，而用户又回到「看不懂的报错」。

反对：既然本票的兜底改成诚实的，探针选错也不致命。半对。兜底诚实只是让失败时说的话是真的，不能让流程成功。#994 的价值恰恰在于让这个场景直接跑通，所以探针必须真的抓得到。

从第一性原理出发

「提前检查」的有效性只取决于一件事：检查用的那条命令，是否覆盖了后面真正会失败的那条命令的前提。如果后面失败在「写索引」这一步，那么只检查「能不能读到仓库」就不构成覆盖。选探针时应该从「哪一步会先失败」往回推，而不是挑一条看起来最轻的命令。

Q7 结论：动工前先核实，探针按「哪一步先失败」往回选，不要默认 rev-parse 够用。
