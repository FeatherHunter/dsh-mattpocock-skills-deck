# #640 修复说明：状态栏容器宽度跟住输入卡，并补一道量几何的门

这份记录说清三件事：修的是什么、为什么这么修、用什么证明修好了。

## 一、修的是什么

**症状**：在未初始化的工作区里，输入框上方出现一条橫跨输入区的背景带，它的左右边比输入卡的左右边各宽出约 98 CSS px；提示条、状态栏胶囊、输入卡三者左右边互相对不齐。

**根因**：宿主把输入区做成一个纵向列，列里每一项各自声明自己的宽度。宿主自己的三个输入区商品（待办 / 目标 / 队列）都写着同一条算式：

```
width: calc(100% - 2 * var(--dsh-composer-side-clearance) - 4 * var(--dsh-composer-dock-inset));
max-width: calc(var(--dsh-composer-card-max-width) - 4 * var(--dsh-composer-dock-inset));
margin: 0 auto;
```

（出处：`@deepseek-ai/dsh-client-ui-conversation/lib/client.js` 的 `.uj7T0q_root`（待办，第 16265 行）、`.gtDvpa_bar`（目标，`dsh-client-ui-goal/lib/client.js:127`）、`.gm5e9a_dock`（队列，第 13959 行））

本插件挂在同一个槽位（`conversation.input.dock`，见 `src/client/panelAssembly.js:79-81`），但那三支外层容器原来什么都没写：没 `width`、没 `max-width`、没 `box-sizing`。它是那一列里唯一不设宽度约束的孩子，于是横向铺满整列（实测 1428 CSS px），比输入卡（约 1231）宽出约 197。

宿主给这个槽位做的定位锚点是 `<div data-slot="conversation.input.dock" style="display:contents">` —— `display:contents` 不产生盒子、画不了任何东西，所以那块多出来的地方露出来的就是宿主的输入区底色。

**顺带查清的另一半**：维护者截图里那块 `#030303` 的矩形，是页面底色被 65% 黑压暗之后的样子（`#0a0a0a` 亮度 10 × 0.35 = 3.5 ≈ `#030303`），不是某个元素画的底色；压暗只到输入卡上沿为止。插件自己有一个这样的遮罩（`StatusBar.js` 里那条选后端窗口用的 `rgba(0,0,0,.65)`），它的定位祖先是同一个外层容器 —— 容器多大，遮罩就压多大。容器宽度收窄之后，这个放大效应也一并消失。

## 二、改了什么

1. **`src/client/statusbar/StatusBar.js`**：新增模块级函数 `dswsStatusDockGeom()`，把外层容器的几何收到一处，三支渲染分支（收起态 / 无横幅 / 有横幅）统一用 `Object.assign(..., dswsStatusDockGeom())` 取它。原来那两支写法不对称（一支写了 `width:'100%' + boxSizing + overflow`，另一支三样都没有）的毛病随之消失。

   容器的算式照抄的是**宿主输入卡**那一条，不是宿主自己那三个输入区商品那一条：

   ```
   width:    calc(100% - 2 * var(--dsh-composer-side-clearance, 0px))
   maxWidth: var(--dsh-composer-card-max-width, 100%)
   marginLeft/Right: auto     boxSizing: border-box     padding: 3px 0 0
   ```

   **为什么要区分这两条**：宿主输入卡是「`p_FcLG_root` 留一个侧距、`p_FcLG_card` 用卡宽上限夹住」，成品是 `min(列宽 − 2×侧距, 卡宽上限)`；而宿主自己的待办/目标/队列用的是**再各内缩 2×内距**的另一条算式（比卡片窄 32px）——它们是宿主要给卡片让位的挂件。本插件要的是「横幅/胶囊/输入卡三者左右边对齐」（#640 的达成判据），所以取卡片那条。这一条我踩过坑：先写成宿主挂件那条算式，被独立复核量出「容器比卡片各内缩 16px」，已改正。

   **横向 padding 不放在容器上**（放 `3px 8px 0` 会让胶囊再往里挤 8px，与卡片又差 16px），改由胶囊自己带。

   **兜底为什么是 0**：宿主那两条规则里 `--dsh-composer-side-clearance` **没有兜底值**（`padding:0 var(--dsh-composer-side-clearance) 8px`）。变量缺失时那条 padding 整条作废，卡片的左右边就是列的两边。所以这里也只有退回 0 才对得上卡片；退成 16 会让容器在旧宿主上比卡片窄 32px（浏览器量尺实测左右各差 16）。

2. **`src/client/kernel/styles.js`**：胶囊的宽度上限从自编的 `min(100%,1400px)` 改成宿主那一个变量 `var(--dsh-composer-card-max-width, 100%)`；第一条规则里并列的那个 1400px 兜底一并删掉（两条上限并存容易改错一条），并清掉一条描述早已删除规则的注释和它留下的空规则槽。

   这里要把话说准：**改造前的实测并没有证明「那个 1400 上限正在生效」**。按宿主算式反推，改造前胶囊宽 = `min(列宽 − 2×侧距, 卡片上限)`，在报告者那一档下正好等于卡片宽 1231 —— 也就是说旧写法在某些档位下本来就是对的。真正的问题在于**它把「对齐」交给了一个自编的数**：1400 与卡片的真实宽度无关，宿主换主题、换列宽偏好、换版本，它都可能变成比卡片宽或比卡片窄的那一个。改成与卡片同一个变量后，这个数不再存在。

3. **没碰的东西**：宿主产物、其它插件、状态栏里的按钮行为、`applyFold` 折叠逻辑、日志接口。本次改动只动样式与几何，没有新增跨边界调用、缓存或定时器，因此按日志纪律不需要新增日志点。

## 三、怎么证明修好了

**新增门（`tests/verify-640-dock-width-browser.js`，已挂进 `scripts.verify` 链第 69 道）**

在真实 Chromium 里量几何，判据只有一条：状态栏容器的左右边必须落在输入卡的左右边上（容差 1px），且胶囊不得比卡片宽。十一例全部通过（实测左右差恒为 0）：

| 用例 | 检验什么 | 容器左右 | 卡片左右 |
|---|---|---|---|
| host-formula-col1428 | 报告者那档列宽，卡宽按宿主公式算出来 | 262.05..1207.95 | 262.05..1207.95 |
| host-formula-stored-userWidth | 用户拖过列宽（存档宽度偏好 1199） | 259..1211 | 259..1211 |
| cardMax-binds-1120 | 卡宽上限成为约束项 | 175..1295 | 175..1295 |
| narrow-960 / narrow-700 | 窄窗口 | 145..857 / 37..705 | 同左 |
| wide-clearance-24 | 侧距、内距被改大 | 76..1476 | 76..1476 |
| no-vars | 宿主变量全缺（旧宿主） | 21..1449 | 21..1449 |

反证用例必须「不对齐」——实测容器比卡片宽 **197px**，说明这一页真量得出问题，不是假绿。

**量尺是外部的**：fixture 里「卡片那一侧」用的不是插件自己的公式，而是**宿主产物原文**——`scripts/gen-fixture-640.js` 从 DSH 桌面包里读 `.p_FcLG_root` 与 `.p_FcLG_card` 两条规则（`padding:0 var(--dsh-composer-side-clearance) 8px` 与 `width:100%; max-width:var(--dsh-composer-card-max-width)`），并对插件的几何算式加多道哨兵：必须引用宿主那两条变量、必须三支都调它、几何自带的 padding 必须是无横向内边距的 `3px 0 0`。读取失败或哨兵不过就直接报错，不会悄悄退化成「两边同一个公式」的恒真测试。被测那一侧才用插件的几何。

**这道门是我自己先写错、被独立复核揪出来的**：第一版把「卡片那一侧」也写成 `calc(卡宽 − 4×内距)`（插件当时那条错算式），两边同公式、必然相等，于是**恒真**——宿主怎么变都绿。复核用「宿主真卡」重搭量尺，立刻把钳住的错位量出来（旧算式在真卡下左右各差 16px）。现在卡片侧从宿主产物读，这道门才真的在量东西。

**变异实验（改坏源码 → 重建产物 → 看门红不红）**：

| 变异 | 门 68 | 门 69 |
|---|---|---|
| 删掉容器的 `maxWidth` 一行 | 红 | 红（生成期哨兵） |
| 容器宽度退回内联 `100%`（改造前写法） | 红 | 红（几何量出 ±98.5） |
| **只让「有横幅」那一支停止调用几何** | 红（该支结构断言） | 绿 |
| 胶囊上限改回 `min(100%,1400px)` | 红 | 红（宽列那一例量出胶囊比卡片窄） |
| 容器加回横向内边距 `3px 8px 0` | 红 | 红（几何量出 ±8） |

「只让一支停止调用几何」这一格是刻意留的分工：fixture 是从源码生成出来的，把某一支的 helper 调用换成字面量后，fixture 会照样生成成正确形状，**几何量尺看不出差**；挡住这类改动的是门 68 那三条「每一支各自调用几何」的结构断言。两道门分管两件事：**门 68 管三支写法同源，门 69 管同源之后的几何确实落在输入卡上。**

**修好的旧门（`tests/verify-capsule-narrow.js`）**

它原来有三条断言写的是改造前的外层容器形状（内联 `width:'100%'` + `boxSizing` + `overflow` 连在一起），本次改造前就已经在主干上红着，而且它一直没挂进门禁链（见 `docs/research/640-背景横带实测.md`）。现在改成断言真源关系（几何收敛到一处、宽度取宿主变量、不带横向内边距、三支都调它），像素级对齐交给上面那道浏览器门；同时把它挂进链的第 68 道，以后它会真的拦住回归。

**回归面**：`node scripts/verify-all.mjs` 全链 120 道通过 / 1 失败 —— 那 1 道是上面那道刚改写、当次产物还是旧的，重建产物后重跑为 121 道全绿（见提交说明）。

## 四、真机上还要确认的一件事

本席进不去真机页面（`http://127.0.0.1:43120/` 直接打开回 401，令牌只在桌面版进程里），所以上面所有几何结论来自：真实宿主产物的 CSS 原文 + 两张截图的逐像素实测 + 真实 Chromium 里的量尺。**真机上只需要看一处**：右键那条带里没被内容盖住的地方，读三个变量

```js
const seat = document.querySelector('[data-composer-seat]')
const cs = getComputedStyle(seat)
console.log(cs.getPropertyValue('--dsh-composer-card-max-width'),
            cs.getPropertyValue('--dsh-composer-side-clearance'),
            cs.getPropertyValue('--dsh-composer-dock-inset'))
```

再把状态栏容器与输入卡各自的 `getBoundingClientRect()` 打出来对一下。两者左右边相等即确认；不等就把这两组数发回来，按数再调一次算式。
