# #640「输入框上方的横向背景带」：两张截图逐像素实测 + 正主判定

这份记录只做一件事：把两张真实截图量到底，说清「输入区上方那条横向色块」是什么形状、多大、谁在画，以及插件这一侧到底有没有画它。数字全部来自图片字节，不靠肉眼估。

## 四、乙图里那块「近黑色横带」到底是什么：是「被压暗的页面」，不是「画上去的一块板」

这是本记录里最要紧的一条，先把结论放前面：**乙图里那块 `#030303` 的矩形不是某个元素画的底色，而是页面底色被一层 65% 黑遮罩压暗之后的样子。**

三条量化判据（全部来自乙图字节）：

| 判据 | 实测 | 判读 |
|---|---|---|
| 带内颜色 = 页面底色 × 0.35 ？ | 页面底色 `#0a0a0a`（亮度 10）；带内 `#030303`（亮度 3）；10 × 0.35 = 3.5 | 吻合 |
| 带外（输入卡）有没有一起被压暗？ | 带内是 `#03`，紧挨着它的输入卡上是 `#141414`（原色，没被压暗） | 压暗只发生在那一带，不是整页遮罩 |
| 带子的上圆角有多大？ | 逐行量首个近黑像素：y294 起、到 y306 收敛到 x=67，半径约 12 设备px ≈ 6 CSS px（约 8 CSS px 量级） | 与 `borderRadius:8` 那一类小圆角吻合 |

插件里唯一的 `rgba(0,0,0,.65)` 遮罩就在 `src/client/statusbar/StatusBar.js:273`：`{position:'absolute', inset:0, background:'rgba(0,0,0,.65)', … borderRadius:8}`，它声明在 `position:'relative'` 的那个外层容器里面（`:269`，也就是带警告条的那一支）——**颜色、圆角、以及「只压住输入区上方、压不到输入卡」这一点，三者都对得上**。

另外顺带纠正一条更早的说法：本记录前面几节把那一带叫「深色板子」「填充色 #030303」，那个说法是错的 —— 它不是填充，是压暗。乙图里那一带里其实**有插件的黄色警告条**（带内找到 134 个琥珀色像素，集中在设备 x≈730–760、y≈333–337，与插件 `.dsws-banner.warn` 的 `rgba(245,158,11,…)` 一脉相承，只是被压暗了 65%），只是被压得几乎看不出黄色。

**这一条的确定性边界**：能确证的是「那一带＝页面底色被 65% 黑压暗、且压暗范围只到输入卡上沿为止」；**不能**从静态文件确证的是「压暗它的那个遮罩到底住在插件的状态栏容器里，还是住在宿主的某个弹窗容器里」——插件自己有这么一个遮罩（`StatusBar.js:273`，那条蓝色的「请选择 Tracker 后端以继续」窗口正是它开的，两张图都是这个窗口开着时截的），宿主那一侧本席在它全部产物里**没有搜到**同样的 `.65` 遮罩写法。要钉死这一条，需要在真机上看那个遮罩元素的 `class` 与它的父元素。

下面这一节讲的是**甲图**（没有弹窗、没有遮罩）里同一块地方的样子 —— 那里看到的是真正被画出来的底色。

## 五、甲图里那块底色是谁画的：宿主铺的底，插件占的位置

**先纠一处前面的错**：甲图里那条黄色警告条（「该工作区尚未初始化　帮我执行初始化 /setup-matt-pocock-skills ×」）**不是宿主的提示条，是插件自己的横幅**。它在插件源码里：`src/client/kernel/locale-panel.js` 的 `'banner.setup'` / `'banner.setupBtn'`，渲染成 `div.dsws-banner.warn`。把整个桌面端产物（`resources/app` 下全部 `.js/.json/.css/.html`）按 UTF-8 逐字节搜「初始化」三个字，只命中两个桌面端自己的文件（恢复助手、托盘文案），**任何一个 `@deepseek-ai/dsh-client-ui-*` 包里都没有这句话**。所以甲图红框里的两行 —— 黄色警告条、状态栏胶囊 —— **都是插件画的，是兄弟节点**，一起住在插件状态栏那个最外层 div 里。

**宿主那一侧的真相（从产物里读出来的 CSS 原文）**：

```
._0cyzDW_root{background:var(--dsw-alias-bg-base); --dsh-composer-card-max-width:calc(var(--dsh-chat-content-width) + 32px); --dsh-composer-side-clearance:16px; --dsh-composer-dock-inset:8px; …}
._0cyzDW_composerStack{gap:var(--dsh-composer-stack-gap,6px); …}          ← 没有底色
._0cyzDW_root[data-phase=active] ._0cyzDW_composerSeat{z-index:7; background:linear-gradient(…, var(--dsw-alias-bg-base) 36px); position:sticky; bottom:0}
.p_FcLG_card{width:100%; max-width:var(--dsh-composer-card-max-width); …}  ← 输入卡被这条 max-width 夹住
```

出处：`…\node_modules\@deepseek-ai\dsh-client-ui-conversation\lib\client.js` 第 14652 行、15757 行。**座位（seat）铺满整列，输入卡被单独夹窄** —— 这个不对称就是「那一带比输入卡宽」的机器原因。

而且宿主给自己那三个输入区商品（待办 `todo` / 目标 `goal` / 队列 `queue`）**都写死了同一条宽度公式**，例如待办：

```
.uj7T0q_root{width:calc(100% - 2*var(--dsh-composer-side-clearance) - 4*var(--dsh-composer-dock-inset));
             max-width:calc(var(--dsh-composer-card-max-width) - 4*var(--dsh-composer-dock-inset)); margin:0 auto}
```

**插件没有跟这条公式。** 插件挂在同一个槽位（`conversation.input.dock`，插件注册见 `src/client/panelAssembly.js:79-81`，order 40），但它的外层容器只声明 `display:flex; flex:none; flexDirection:column; alignItems:center; padding:'3px 8px 0'`，**没有 `width`、没有 `max-width`、没有 `box-sizing`**。它是 flex 列里的一个不设约束的孩子，于是横向铺满整列。

**另外一处关键机制**：宿主给这个槽位做的定位锚点是 `<div data-slot="conversation.input.dock" style="display:contents">`（`dsh-client-ui-renderer\lib\client.js:767,771-775`，注释写明「`display:contents` keeps the wrapper out of layout … the anchor is purely addressable surface」）。`display:contents` **不产生盒子、不可能画任何底色**。

**一句话**：甲图里那块底色是**宿主铺的**（宿主的座位），位置是**插件占的**（插件那个没设宽度约束的外层容器）。四张仓库里更早的截图（08-21 到 09-19）里都没有这样一块全宽Panel，当时胶囊的宽度和输入卡只差 1–6 px —— 也就是说**这是后来的版本才出现的偏差，不是一直如此**。

## 六、插件这一侧真正该改的，是三条能自证的偏差

正主（底色）在宿主，不等于插件没问题 —— 让那块底色露出来的就是插件的容器。实测里插件侧有三处和它自己写下的规矩不符：

**偏差 1：状态栏外层容器宽度不跟输入卡。** 乙图（CSS px）：压暗矩形 51.9…1479.1（宽 1428），胶囊内芯 77.4…1453.5（宽 1377），而输入卡约 131…1362（宽 1231）—— 那一带比卡宽约 197，左右各多出约 98。甲图（全屏 1510 CSS px 宽）里胶囊约 100…1460，卡在它下方另起一块。两张图都说明同一件事：**那一带的宽度来自槽位，不来自输入卡**。宿主给同槽位另外三家写的是 `width:calc(100% - 2*侧距 - 4*内距)` ＋ `max-width:calc(卡宽 - 4*内距)` ＋ `margin:0 auto`，插件要跟这条。

**偏差 2：有警告条 / 无警告条两个分支的外层容器写法不对称**（#640 正文的候选 B，静态可证）：
- 无警告条分支 `src/client/statusbar/StatusBar.js:244`：`{display:'flex', flex:'none', flexDirection:'column', alignItems:'center', gap:2, width:'100%', boxSizing:'border-box', padding:'3px 8px 0', overflow: RDOM?'hidden':'visible'}`
- 有警告条分支 `src/client/statusbar/StatusBar.js:269`：`{display:'flex', flex:'none', flexDirection:'column', alignItems:'center', gap:4, padding:'3px 8px 0', position:'relative'}`

后者**没有写 `width`、没有写 `boxSizing`、没有写 `overflow`**。这正是「关掉初始化提示条后剩下的状态栏仍应与输入框对齐」这条验收要求的落点。另外那一支还同时是 `rgba(0,0,0,.65)` 遮罩（`:273`）的定位祖先 —— 它的盒子多大，遮罩就压多大。

**偏差 3：胶囊的宽度上限比输入卡宽。** 插件给胶囊写的上限是 `min(100%,1400px)`（`styles.js:124`），后来那条改成 `var(--dsh-composer-card-max-width, min(100%,1400px))`（`:127`）。实测容器内容宽约 1409，胶囊实测 1377 —— 也就是**上限根本没起作用，胶囊是被 100% 撑满的**；而宿主那三家用的是「卡宽 − 32」这种比卡更窄的上限。上限选错，就算容器修对了，胶囊也咬不住卡的边。

## 七、还差最后一下（要人在真机上看一眼）

甲图里那块底色是宿主铺的（宿主的座位 `._0cyzDW_composerSeat[data-phase=active]` 用 `--dsw-alias-bg-base` 铺满整列，输入卡单独被 `--dsh-composer-card-max-width` 夹窄），锚点是 `display:contents` 不可能画东西。乙图里那块是**被压暗**而不是被画出来，压暗它的是插件自己那个 `.65` 遮罩还是宿主弹窗的遮罩，从静态文件还不能定 —— 插件有这么一个遮罩（`:273`，那条蓝色选后端窗口正是它开的），宿主那边本席没搜到同样写法。所以真机上看一眼要分两件事：

**A. 定「谁把那一带压暗」**（乙图那种状态下）：
1. 让那条蓝色选后端窗口开着，右键那块暗色里没被窗口和胶囊盖住的地方 → 检查。
2. 看它的 `class`、`background-color`（是否 `rgba(0,0,0,0.65)`）、`border-radius`（是否 8px），以及它的父元素是谁 —— 父元素是插件那个状态栏容器（`dsws-` 打头），就归插件；是宿主类名（如 `_0cyzDW_…`），就归宿主。

**B. 定「谁把那一带铺成一块宽底」**（甲图那种没有弹窗的状态下）：
3. 同一位置再右键一次，看 `class` / `data-slot` / `data-composer-seat`、`background-color` 与 `background-image`（宿主座位是 `background-image: linear-gradient(...)`，不是纯色，容易被漏看）、以及 `width`。
4. 顺手在控制台读三个数，用来验算要套的公式：
   `getComputedStyle(document.querySelector('[data-composer-seat]')).getPropertyValue('--dsh-composer-card-max-width')`，以及 `--dsh-composer-side-clearance`、`--dsh-composer-dock-inset`。

另外 #640 的 Q2（把插件禁用后横带还在不在）在干净环境里跑一次即可，这一步与上面的读数相互独立。
