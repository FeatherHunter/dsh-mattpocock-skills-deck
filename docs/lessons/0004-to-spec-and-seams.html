Lesson 04 · 12 min

从对话到规格：/to-spec
不访谈，只综合；先定 seams，再写正文

拷问已把“做什么、为什么、边界在哪”磨清楚了。/to-spec 的任务是一口气把它压成可交付的 spec。

铁律： /to-spec 不再提问拷问，只综合已有的对话与代码上下文。

Spec 的形状（模板即契约）

## Problem Statement      — 用户视角的痛
## Solution               — 用户视角的解
## User Stories           — As an <actor>, I want <feature>, so that <benefit>  （要极其详尽）
## Implementation Decisions — 动了哪些模块、接口怎么变
## Testing Decisions      — 什么算好测试、在哪些 seams 测
## Out of Scope
## Further Notes

例外：若 /prototype 产出的某段状态机比文字更精确，可内联其“决策精华”。

关键一步：先定 seams，再动笔

  • 优先复用既有 seams，选尽可能高的 seam
  • 若需新增 seams，提议“能放多高就多高”，越少越好——理想是 1 个
  • 先跟你确认 seams，再写正文
// 高 seam（好）— 贴近用户行为
await saveSnapshot(mapId); expect(loadSnapshot(mapId)).toEqual(expected)
// 低 seam（脆）— 贴近实现细节
expect(writeToIndexedDB).toHaveBeenCalledWith(key, bytes)

落盘形态

写完即发 issue tracker，打 ready-for-agent。

gh issue create --title "沉淀快照：定版与落地" --body-file spec.md --label ready-for-agent
