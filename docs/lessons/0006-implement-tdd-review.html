Lesson 06 · 15 min · Build

按票开建：/implement + /tdd + /code-review

一张票，一个新上下文，用 red→green 单步推进，做完即审再合。

/implement 的纪律

  1. 每票起一个新上下文（/clear），只读该票与 spec。
  2. 在已约定的 seams 上跑 /tdd：一次一测、一次一实现。
  3. 定期跑 typecheck，单测频繁、全量收尾各一次。
  4. 收尾固定跑 /code-review（双轴并行），再 commit。

/tdd：什么算好测试

好测试
  • 测接口行为，不测实现细节
  • 读起来像规约：“用户可用有效购物车结算”
  • 测于 seam 上
expect(checkout(validCart)).toEqual(success)
三条反模式
  • 实现耦合：mock 内部协作
  • 同义反复：用代码重算期望值
  • 水平切片：一口气写完所有测试再实现
expect(add(a,b)).toBe(a+b) // 永远绿
seams 事前约定： “在哪个公共接口上测？”——写下来并与人确认。

/code-review：双轴并行

固定点 → 两个子 agent 并行：

  • Standards：是否合乎本仓编码规范
  • Spec：是否忠实实现 origin issue/spec

先写全量实现再补测试
红（写会失败的测试）→ 绿（刚好通过的最简实现）→ 重复
先重构再写测试
✓ 重构属于 review 阶段。
3/4 · 测试应断言：
内部私有方法的调用次数
通过公共接口可观察的行为
数据库里是否写入了某行
✓ “查询库”而非“走接口”是侧通道。
4/4 · /code-review 的两轴是？
性能 vs 安全
Standards（规范/异味） vs Spec（是否做对）
覆盖率 vs 行数
✓ 两轴并行跑，互不污染。
