查票的后半程：从 run 走到最底层

上一讲讲到你懂了 run。这一讲跟着查票这笔调用，从 run 一路走到真正读票的那一层，再走回来。

先划界哪部分是地图01的

把话说在前面，免得你以为这些代码是我们图改的：

地图01 负责的：scripts/ts-hook.mjs（装载钩子）、tests/gate-map.json（归属表）、金标准回执夹具、搬家（133 个文件按新树落位）、构建与类型检查入口。这就是「你这张图讲什么」的边界。

下面这条链上的每一站代码，属于别的图（工具壳、注册表、房间各图）。地图01 做的是把这条链记录准确（#1094 那份 721 行走查文档），并让它跑得起来、改得动、坏了看得见。所以我讲它，但每站都标清楚它归谁。

第1站run 进门那几步

查票的 run 在 src/deck/tools/issue-get.ts:84（createDeckIssueGet，它返回 { definition, run }；definition 在 :30-45，就是给 AI 看的那份说明书）。它做完九步就交给预算壳：

行干什么失败长什么样
:86把 key 去空白—
:87先估算这笔花多少—
:88取会话的工作区目录:89 回 no-session-context
:90判 key 有没有回 bad-args：「要读哪一张票」
:92选后端（哪个仓库、哪种跟踪器）:93 回 no-backend 等
:94拼出仓库身份—
:97comments 夹进 0..200，缺省 50—
:99blocking 缺省要；只有显式 false 才跳过—
:100-106取沙箱策略，5 秒上限，拿不到按空走不算失败，只是不限权
:108进预算壳 shell.call后面几档
记一句：会话判不过就不往下走，而且这一步排在参数校验之前。取会话是「能不能干活」的前置，票号写没写是「活干什么」。

有一处例外：deck_context 是反过来（先取会话再估算），因为它要回答的正是「这个工作区该在面板上选哪个后端」，会话拿不到也得如实告诉 AI。

第2站预算壳里的四件事

shell.call（src/deck/shell/call-shell.ts）是每笔调用真正动手的地方，顺序固定四件：

  1. 硬顶：先问闸「这笔允许吗」。五个数写死在预算表里——单笔 600 点 / 400 请求，每小时 2000 点 / 1500 请求，单笔最多 60 张子票。顶住了回 ai-tool-refused，而且文案是闸自己的原话（会告诉你预计花多少、本小时已用多少、建议分几次），工具不许自己编一个数。
  2. 记账：过闸时把这一笔记上。
  3. 干活：调工具自己那段 work。它拿到的上下文里带着会话、选出的后端与仓库、闸、注册表选出的跟踪器。
  4. 收口：把结果并进统一信封；写过的票要让宿主那侧的快照缓存作废，否则面板显示旧数据。

为什么还有第二层壳

一笔调用内部可能发好几笔远端请求，所以 work 里再包一层：单笔最长 120 秒、留 10 秒余量、单次操作 30 秒。它们管的是超时与中止；额度不够会停止发下一笔。

这层壳顺手给读操作带记忆：同一笔调用里，同一个操作 + 同一把钥匙第二次要，就直接拿表里那份，不再问后端。只记成功的——失败结果不记，下一笔老实再问。这里的取舍很直白：同一笔里重复读是浪费，跨笔缓存是骗人。

第3站真正读票那一层

壳里最终调的是 t.get(repo, key, …)。这个 t 是按后端 id 从注册表里选出的那座「房间」：GitHub 房、GitLab 房、本地 Markdown 房，各在 src/tracker/rooms/ 下。

run  →  shell.call（预算壳）  →  withCallScope  →  tracker.get
                                                     ↓
                                    注册表按后端 id 选房
                                                     ↓
                     GitHub 房 → gh 子进程 ／ Markdown 房 → 磁盘文件

再往下就是地图01 边界之外的事了：那一步真的去敲 gh 命令或读文件。一句话记牢：上三层只决定「准不准做、算谁的账」，最后一层才决定「去哪拿」。

房间拿回来之后，工具做三件收尾：把票的关系算出来（父子、阻塞边）；如实注记读不到的东西（例如 blocking=false 时明说「上面记空不是 0 条」）；按实际读数报账（一次读就是 1 请求 3 点，跳过反向边那一大段全仓扫描也是这个数）。

读路径有个诚实的降级：读回来的字段只能说明「契约里有这条关系」，分不出后端把父子放在原生层级还是平级链接，所以返回里如实标「降一档，看写操作的记录」。宁可说不知道，不假装知道。

第4站回来后去哪

结果并进统一信封，回到 AI 眼前就是你可能见过的那一行：

票 1022 读回来了：状态 open，父票 1013，被阻塞 9 条，阻塞别人未取（blocking=false）。

这句不是模板拼的，是刚才那一路的读数拼的：状态来自票、父票和阻塞边来自关系计算结果、括号里那句来自你传的参数。你看到的每句话，都能倒推回某一层的某个判断——这正是走查要练的本事。

看三看封装 / 参数 / 边界失败

票面要求你对这三看逐条表态，这一讲刚好三样都摸到了：

  • 封装：九个工具都长同一个形状——进门九步、进预算壳、调房间。差异只在各自那段 work。这种「外壳一份、内芯九份」是好是坏，你怎么看？
  • 参数：key 必填、comments 夹范围、blocking 缺省要——参数校验排在取会话之后。这个顺序你认不认？
  • 边界失败：失败不是一句「出错了」，而是分档的（没会话、参数不够、后端没选定、闸顶住、后端自己抛错），每档配一句人话文案。分这么细值不值？

这一讲的过关线你回答两个问题

不用背书，用你自己的话说就行：

  1. 查票的 run 在哪个文件？它后面依次经过哪三站（预算壳 → ？→ ？），每站各管什么？
  2. 为什么「取会话」要排在「判票号」前面？

答完这两问，下一讲就接「三座房间各自怎么落地」——那一讲会讲到地图01 是怎么把搬家后的文件位置记录下来、又怎么用金标准保证搬家没改行为的。
