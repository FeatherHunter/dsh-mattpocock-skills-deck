这张规格 issue（{url}）下面的实施 issue 已经全部关闭（{closed}/{total}）。先核对，再决定能不能关。关规格是向以后的人保证：这批改动已经在仓库长期保留的那条分支上、在你写下的提交上可复现地全绿、遗留都已处置——不只是子票都关了。

## 一、先认这次是怎么做的
- [ ] 读仓库自己的说明（例如 AGENTS.md、docs/agents 下的约定）和近期同类规格的收尾记录，认这次属于哪种做法：每张实施票分别用 /implement 实现；直接对这张规格跑过 /implement-spec（会产出集成分支，可能还有草稿 PR）；这个工作区没有版本库。
- [ ] 找到这次的分支、工作区副本和提交：散在多处的改动先合到同一条分支再往下核对；找不到、或改动只在临时目录里，先问用户改动在哪，不要假定已经交付。
- [ ] 确认要交出去的代码：每张实施票的改动是不是都已合进同一条长期分支（通常是 main，以仓库自己的叫法为准）。走 PR 的仓库，只认已合并且提交落在长期分支；草稿、待评审、合进别的分支都不算。实施票当初在集成分支上验完就关，是正常做法；规格不一样，要等集成分支也进了长期分支（本仓库的惯例是与 main 同一提交）才算交付完成。
- [ ] 读不到分支或 PR 状态时，判不了就不关，把情况交回用户。

## 二、核对（三种做法都要做）
- [ ] 逐张打开实施 issue，对照验收判据看代码、测试或运行结果，确认真的做到；只看关闭状态和票面自述不算数。
- [ ] 在最终交给仓库的那份代码上跑仓库规定的测试、类型检查和构建，记下分支名与提交号。在没含这些改动的主分支、有未提交改动的树、或别人的分支上跑出的绿不算数。
- [ ] 多张票改同一模块或接口时，合起来再核一遍：各自绿不等于一起绿。
- [ ] 收干净实施过程留下的临时物：实施工作区副本、已合并的临时分支、未提交改动、临时文件。没合并的分支不要删，把里面独有的提交列给用户。
- [ ] 规格正文与评论里的「待定」「后续再说」逐条处置：这次做完；转成新票并写下票号；用户确认不做。只把字眼找出来不算处置。

## 三、把改动交给仓库（没有版本库就跳过这一节）
- [ ] 按仓库自己的落地方式走，不要为了关票硬造 PR：用 PR 合入的仓库，没有 PR 就建（标题用一句中文说清这次交付了什么，引用规格与实施票），草稿改成可评审；正文用 /pr 技能写（Summary / Evidence / Merge Danger），写清逐票结论与检查证据。/pr 只写正文，不建 PR、不合并 PR。
- [ ] 等 PR 合入长期分支后再关；只建了 PR、只改成可评审都不算。需要人合并就停下来，把 PR 链接和结论交给用户，并说明合入后再点「完成」。这是等待，不是失败；未经用户当场授权不要替人合并。
- [ ] 不用 PR 的仓库（本仓库的常态）：把这条分支合入长期分支并推送，确认长期分支包含这次的全部提交。PR 不是结案方式；只有长期分支里真的有了这些提交，才算交付完成。
- [ ] 改动还没提交就先提交并推送，只提交这次动过的路径，提交信息按仓库规范写清改了什么、为什么。
- [ ] 合入后拉回长期分支的最新提交，在上面重跑第二遍检查：合入会带进交叉影响，合入前的绿不能当结论。
- [ ] 不要让合并 PR 的关闭引用替你把票关掉（有的后端会按关键词自动关）；票一律走 deck_issue_patch 的核对评论后关闭。
- [ ] 长期分支还没含改动、PR 没合、只合了一部分：不关闭，写清差哪条与下一步，不要为这件事重开实施票。

## 四、没有版本库的工作区
- [ ] 没有分支、提交历史和 PR 可做：以当前工作区为要交出去的代码，确认改动确实在这里（不是只在临时目录或子代理的副本里），检查照跑。
- [ ] 关闭评论注明「本工作区没有版本库，以上结论以当前工作区文件为准」，并写清检查命令与结果、改了哪些文件。

## 五、关闭规格（核对与交付都通过之后）
- [ ] 全部通过 → 在同一次 deck_issue_patch 调用里带 comment 和 close:true：评论写清逐票核对结论、这次是怎么做的、分支名与提交号（或 PR 合并提交、没有版本库的说明）、跑了哪些检查与结果、遗留项的新票号；工具会先发评论再关，缺评论或还有实施 issue 没关都会被挡下来。
- [ ] 有任何一条没通过 → 不关闭：改动还没交出去就说卡在哪一步、下一步由谁做（如「等 PR #N 合并」）；验收没做到就说缺什么、建议重开哪张实施 issue 或补一张。
- [ ] 没有「实施 issue 都关了顺手关」的旁路：关规格只有上面这一条路，先核对、再带核对评论关。
- [ ] 人随时可以重开这张规格；重开只能由人在后端做，AI 的工具面上只允许关、不允许重开。

## 工具
- [ ] issue 相关操作优先使用 deck_ 开头的工具处理
- [ ] 及时使用 deck_issue_report 工具上报处理过、处理中的 issue 编号

先把尺子立起来

这个动作的本质是把一句断言写进仓库历史——「这张规格承诺的东西已经做完、交付、可复核」。由此推出六条判据，下面的每张卡都按它们量。

1真值只能来自交付物

长期分支上的提交 + 在该提交上复现的检查 + 规格承诺真的实现。票的关闭状态是过去的人写下的断言，拿它推结论是循环论证。

2成本不对称

误关是沉默的（票从在办列表消失，没人再看；AI 不能重开，纠正要人动手）；该关没关是可见的、一点就关。所以判不了就不关。

3断言要带指纹

分支、提交、命令、结果。没有指纹的收尾评论 = 无法复核 = 等于没核对。

4绿只对跑它的那棵树有效

干净树、明确提交、合入后重跑；合入会带进交叉影响。

5分解有固有缺口

逐票满足判据 ≠ 合起来满足规格承诺——判据是拆票时写的局部条件。

6有些动作是人的

评审门上的合并、重开、丢弃工作，不能替人做。

四处硬伤（按价值排）

  1. 缺整体验收。三节核的都是「逐票有没有做到」，没有一处回到规格正文看整体——而「不只是子票都关了」正是这张提示词的立身之本。→ 增A
  2. 「与 main 同一提交」是事实错误。本仓库的交付是合并提交：bf4e88c3（#1460 的交付）两个父提交，一个是 main 3304e1f0、一个是集成分支 e0d6f1d2——合并后必然不在同一提交。按字面判，本仓库最常见的形态反而判不出来。→ ⑥
  3. 「收干净未提交改动」与仓库安全规定冲突。AGENTS.md 明令不许 reset --hard / checkout . / clean -f；工作区里还可能有别的会话的活。→ ⑪
  4. 收尾评论只要求「写清」，而闸不验内容。闸只检查评论存在且非空（spec-close-guard.ts:96），「已核对、通过」能过闸。→ ㉒

结构上再收一刀

  • 开头第③句扩成四条编号谓词后，第五节「全部通过」才有明确的指代对象——现在它指的是前面挑着做的结果。
  • 第四节不是并列的第五节，是第三节的第三条路：交付只有三态（PR / 直接合 / 无版本库），判据相同；29 张卡可以压到 20 条左右。
  • 第二节标题「三种做法都要做」容易被读成「三种流程全做」，其实那三种只是交付形态，改「不管哪种做法都要做」。
  • 顺序「核对 → 交付 → 合完再跑 → 关」是立的，别动。
