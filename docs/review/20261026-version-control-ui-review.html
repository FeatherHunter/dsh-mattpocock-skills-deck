先把尺子立起来

版本管理页本质上只回答三个问题。先定判据，再逐场景量，避免把「看着不顺眼」当成结论。

问一我现在改了什么哪些是我要的、哪些是垃圾。判断依据是体积、类型、来源和差异，不是文件名猜。
问二下一步做什么暂存、提交、丢弃、同步；一屏一个主操作，每个写操作都有对称的撤销。
问三做完怎么确认结果落在触发点旁边，写清对象、数量与时间；没发生的事不说「完成」。
1可判定

决定「要不要写进历史」之前，先看得到体积、类型和差异入口。

现在：未跟踪的 21.8 MB 视频与 1 KB 脚本同列，唯一动作是「add」。
2可逆

写操作有对称的撤销；代价高的动作二次确认，代价低的不要拦。

现在：只有逐行「撤回」；没有丢弃、忽略、删除，「add 全部」也没有「撤回全部」。
3可归因

结果必须贴住触发点，说清对象、数量、耗时，否则用户无法判断是否重试。

现在：结果固定在整页末尾，与按钮隔整张列表；无时间、无远端名、无提交号。
4一致口径

数字、文案、状态使用同一口径；口径不同的数字并排放，就是在制造误读。

现在：12 是条目数、50 是已加载数、14 是其他工作树棵数，并排展示成同一种计数。
5可达

鼠标、键盘、读屏、触摸四路都要能完成同一件事，并收到同样的状态通知。

现在：文件行不可聚焦，禁用原因只在鼠标悬停里，结果与忙态没有 aria-live。
6诚实

按钮可用就等于「点了有意义」；报告结果必须真的发生过。

现在：超前 0 时「推送」仍亮绿可点，成功后统一说「推送完成」；脏工作区拉取可点，提示却写「请先提交再拉取」。
结论先行：如果只改三处，就把力气花在这三处——① 结果回到触发点旁边；② 三类文件分开，并补上「丢弃 / 忽略」；③ 无提交可推与拉取风险做成按钮状态，而不是句子。 这三处改完，这页才配叫「提交前的检查台」。
