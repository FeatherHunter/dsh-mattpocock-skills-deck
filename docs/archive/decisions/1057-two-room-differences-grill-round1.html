01这张票在干什么

一句话：同一个工具在两个后端跑，有些地方结果不一样；把每一条的「补」或「不补」定死，并写明理由。

票面原文：

目的：把已知差异（可选参数被丢、没有写前版本校验、没有写后环检）逐条定掉：补齐还是明确记为差异。
边界：只讨论。
做完：每条差异都有去留与理由，写进本票评论。 来源：GitHub issue #1057 正文

这件事不是可做可不做：地图 09 的「做完的标志」里明写了一条「两房语义差异逐条落定或明确记为已知差异」（来源：research/1010-ticket-structure.md:223，地图 #1056 正文同句）。所以这张讨论票的结论，是地图 09 能不能往下走的门。

02背景：两房与地图 09

两房是什么

GitHub 房本地 Markdown 房
票存在哪远端 GitHub 仓库本工作区磁盘上的 Markdown 文件（.scratch 目录下，一张地图一份 map.md，每张票一个文件）
怎么读写经过本机装的 gh 命令发网络请求直接读文件、改内容、整份写回，不经过网络
能不能离线不能能
来源src/tracker/rooms/github/backend.ts:8、graph.ts:80src/tracker/rooms/markdown/index.ts:29、issues-status.ts:41-43

两个后端物理隔离：一个动远端仓库，一个动本地磁盘，互相不引用、也不同步数据。跨房间不许引用是写在注释里的纪律（src/tracker/rooms/github/cycle-check.ts:7）。

地图 09 要证明什么

证明「上层对后端无知」不是一句空话——换一个完全没有 gh 的后端，同一套 deck 工具全部照样跑（来源：research/1010-ticket-structure.md:223）。

这句话的现实含义：工具层不应该知道底下是谁在存票。要做到这一点，两个后端的对外行为必须一样，或者差异必须是写在明面上、调用方看得见的。

为什么这类差异要靠讨论定，编译器抓不到

契约（工具和后端之间唯一的书面承诺）给这些操作声明了可选项参数。本地房在门口把参数收下、进屋就丢了——声明了参数却不用，在 TypeScript 里是合法的，编译一声不响。所以这一类差异只能靠人对着接口逐条定，或者靠注释写明。

已经定下的一句口径：本地房已知的差异不许用可选项藏起来，要在接口注释里逐条写明「本房不实现」（来源：specs/1010-ts-rewrite-spec.md:81）。

一句话总结背景 GitHub 房是「远方真源」，本地房是「离线可用」。今天的现实是：本地房有几处对外说着和 GitHub 房一样的话，做起来少做了几步。这张票要定的就是：这几步该补，还是该明说。

你实际会看到什么

  • 同一个关闭原因，同时关两张票，都显示成功。GitHub 那张读回能看到原因；本地那张读回原因只能是空。同一个「成功」，含义不一样。
  • 同一个批量取依赖调用，都显示成功。GitHub 返回多张票的结果；本地只返回第一张票的结果。
补齐要动哪批量键：本地取依赖函数加接收位置，多张逐个读再合并；或者明确拒绝批量、回「做不到」。关闭原因：本地关票函数加接收位置，并定好写在文件哪一行、从哪一行读出来（文件格式有没有预留原因行，尚未核实）。
记成差异的代价最贵的是静默：调用方收到成功，以为原因记下了、批量取全了，盘上并没有。上层每个用到这两个字段的地方都要先问「现在在哪个后端」。

桶二 · 写前版本校验，本地房整类缺席

会丢改动

期望更新时间是什么：一种乐观并发控制。你上次读票时拿到一串更新时间，下次写时原样交回去；后端拿它和当前存的比对，对不上就回「冲突」，不让你盖掉别人的改动（来源：src/tracker/contract/inputs.ts:116-123）。冲突是显式的失败分类，不是靠错误文本猜的。

GitHub 房本地 Markdown 房
认不认4 处都认：改标签、改认领、改父地图、改阻塞关系，写前先读当前票比对全房搜索「期望更新时间」零命中，4 个本地写函数签名里没有收它的位置
对不上时回冲突，不往下写——（根本没有比对这个动作）
来源github/labels.ts:99-106、github/issues-write.ts:288-293、github/graph.ts:60-67、github/graph.ts:251-258markdown/issues-patch.ts:327,199,244,183、markdown/index.ts:138-141

你实际会看到什么

甲乙两人同时打开同一张票，读到的更新时间是同一串。甲先改标签并成功，更新时间变成新串。乙接着改同一张票，交回的还是旧串：

  • GitHub 房：乙收到冲突，盘上保持甲改完的样子，乙的改动没落盘。
  • 本地房：乙显示成功，文件被整份改写，甲的改动被整份抹掉，两次调用都成功，盘上只剩乙的版本。

本地已有「按文件排队」的单写者队列（markdown/issues-patch.ts:24-34），它解决的是同时写同一份文件互相踩，不解决先后写后写盖先写——这是两个不同的并发层次。

顺手发现的一处契约内部不一致（需要你决定，见 Q5） 契约的关票注释写着「带期望更新时间时对不上就回冲突」（src/tracker/contract/operations.ts:135），但关票选项的类型里今天只有关闭原因，没有期望更新时间（inputs.ts:99-103）；改票操作今天根本没有可选项参数位（operations.ts:145）。所以按今天的类型，能做版本校验的只有那 4 个操作。
补齐要动哪本地 4 个写函数各加一个接收期望更新的位置，写之前先读当前文件的更新时间（或等价的文件版本标记），对不上就冲突且不写文件。本地文件今天有没有可靠的更新时间可比，尚未核实。
记成差异的代价本地房永远后写盖先写。凡是靠「冲突」提醒人先合并再写的上层流程，在本地会静默丢改动，而且两次都返回成功，没有日志能指出谁盖了谁。将来在本地房上做协同编辑，这个会第一个变成丢数据故障。

桶三 · 写后环检，只有 GitHub 房有

图会打结

契约给「改阻塞关系」写了两条硬规矩：自己阻塞自己回冲突；写完成环回冲突且不落盘。注释还多写了一句：环检是写路径的一部分，不许省，省了图会变成一团，而且再也解不开（来源：src/tracker/contract/operations.ts:174-177）。

GitHub 房本地 Markdown 房
自环当场回冲突也挡：读、写两边各有一个自环分支
成环落盘前用全图邻接表判一次（深度优先搜索），成环就不写不判。直接改文件的阻塞行并落盘
来源github/graph.ts:249,260-261、github/cycle-check.ts:55-73markdown/issues-patch.ts:186（只此一处）

一处措辞差别如实说明：契约写「写完之后成环」，GitHub 房实现是写之前预判（github/graph.ts:259 注释「成环检测（写前，不落盘）」）。效果一致，都是成环的边不落盘，不是先写再回滚。

你实际会看到什么

已经有一条「甲等乙」，你再把乙设成「等甲」，两条边凑成一圈：

  • GitHub 房：第二次写入回冲突，盘上保持原样。
  • 本地房：第二次写入成功，两个文件各记一条，下次读依赖时两张票互相出现在对方的阻塞列表里，留下一圈解不开的等待。
补齐要动哪在本地写阻塞边函数里加一次写前判环：把同一工作单元内所有票的阻塞关系读出来组邻接表，把拟写入的边套进去做深度优先搜索，成环就冲突且不写文件。判环算法可参考 GitHub 房那份。判环范围要不要含跨工作单元的边，尚未核实——本地阻塞关系今天只在同一工作单元内成立（markdown/graph.ts:3-5）。
记成差异的代价本地图可以长期带环运行。环一旦落盘，后续排序、展示、自动化推进都可能在环上打转；解环要人逐条拆边，机器判不出该先拆哪条。等于接受「本地图可能要人手工修环」。

按讨论聚焦的五项各归一句，不多扩散。

目标8 处差异逐条有去留与理由：补齐，或明确记为已知差异并在接口上写明。

05待你定夺 Q1–Q6

每题的推荐都写清了理由和影响，你只回选项字母、或者直接说你的第三种做法都行。

Q1

完成判据与边界，认不认

票面写着「边界：只讨论」，收尾要写三处：本票评论（结论）、地图 #1056 的决定区、受影响的开发票正文或评论。三处都写完才算讨论完毕，只写第一处下游票看不到。另外票面有一条默认：贴出后 48 小时没人回话，就按票面默认方案往下走。

A认：三处都写；48 小时默认也认。
B三处认，但 48 小时默认不认（你要亲自看完再定）。
推荐 A三处不齐下游看不到；48 小时那条是防止讨论票把开发票卡死，认了不等于你不看，你随时可以推翻重定。
Q2

桶一这 6 处，一起定还是拆开定

6 处里其实是两种性质：关闭原因与批量键（本地文件写一行就能记、多读几个文件就能办，代价小、用户看得见）；4 处期望更新时间（远端并发才需要，本地单机串行，属于桶二）。

A拆开定：前两处单独作为「有意义的字段」，跟桶二分开拍。
B6 处一起定，统一口径（全补 / 全记差异）。
推荐 A绑一起会让「便宜又有用」的两处被「贵又未必需要」的四处拖下水，或者反过来被一起补掉。分开拍更准。

如果选 A，前两处各自还有一个子问题：关闭原因，补进本地文件（要定写在哪个位置），还是明确记为「本地房不记原因」？批量键，补成批量（多张逐个读再合并），还是明确拒绝批量调用回「做不到」（比静默只回一张诚实）？这两处可以等你先答完 Q2 再进入下一轮。

Q3

写前版本校验：本地房补，还是明确豁免

A补：本地 4 个写操作加期望更新时间比对，对不上回冲突不写。代价是本地票文件要有可靠的更新时间或版本标记，且每次写前多读一次文件。
B豁免：明确写「本地房长期是后写覆盖先写」，上层协同流程按此避开；契约注释加一句本地房不实现。
推荐 A这是三桶里唯一会静默丢数据的：两张票都回成功，改动却没了，事后无从追查。本地读一次文件比对，成本远低于远端再拉一遍。而且「本地单机不会并发」这个前提，在同一个工作区开两个会话时就不成立了。

如果选 B，请一并定：豁免写在契约注释里，还是也在本地房的接口说明里写一遍？

Q4

写后环检：本地房补，还是接受带环

A补：本地写阻塞边前判环，成环回冲突不写。范围建议先定「只看同一工作单元」（与今天本地阻塞关系只在该单元内成立一致）。
B接受带环：保持只挡自环，写明本地图可能带环、由人手工拆。
推荐 A环检是契约里唯一被写明「不许省」的一条，理由也说得通：图一旦成环就再也解不开。本地组一次邻接表比远端拉全仓便宜得多，代价小、风险大，不值得豁免。

如果选 A，还要定判环范围：只看同一工作单元，还是看整个工作区的所有票？（本地今天阻塞关系只在同一工作单元内成立，跨单元暂时不在语义里。）

Q5

关票与改票，要不要也加版本校验

顺手核出来的契约内部不一致：关票注释说带期望更新时间就比对（operations.ts:135），但关票选项类型里只有原因（inputs.ts:99-103），改票更是连可选项参数位都没有（operations.ts:145）。这不是两房差异，是契约自己前后不一。

A补齐契约：给关票与改票都加上期望更新时间位置，桶二按 6 个操作一起算。
B改注释：注释跟着类型走，明确「今天只有 4 个写操作支持版本校验」。范围小、今天不做。
C本票不定，另立一张小票处理（本票先聚焦两房差异）。
推荐 B本票的题是「两房差异」，这处是契约自己的笔误级不一致；按类型为准改注释，成本最小，也不会把本票范围撑大。若你更看重「关票也该防并发覆盖」，那就选 A。
Q6

结论落盘的形式

结论必须先写进这张票（正文/评论），这是票面判据。问题是要不要另立长期留存的地方。

A只留本票 + 地图 #1056 决定区。
B本票 + 地图决定区，另外对「选择豁免」的条目各写一条决策记录（ADR）。
推荐 B（视结果而定）如果 Q3/Q4 里选了豁免，那是一条「以后别人会问为什么」的长期决定，值得一条 ADR；如果都选了补齐，选项 A 就够，不必为对称而写。

06结论落到哪 · 收尾动作

讨论完毕时，结论写三处

  1. 本票 #1057：逐条写结论与理由，不写「已讨论」这种空话。
  2. 地图 #1056 的「Decisions so far」：要动手的人先读这里，没写进这里的结论等于没定。
  3. 受影响的开发票：只影响某一张就写进那一张的正文或评论。

讨论定案之后的收尾

  • 全部讨论完、意图对齐时，走一次 /to-spec，把结论固化成规格文档。
  • /to-spec 产出的规格单，挂到同一张地图 #1056 下成为子票。
  • 按你的指示执行完 /to-spec 后，对本次执行的所有任务做一次对抗式审查，确认无误再关闭本票。
