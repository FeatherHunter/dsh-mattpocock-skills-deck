# 对抗式第一性原理审查：deck 工具链 TypeScript 化方案

审查对象：《#1010 下的 13 张改写单元地图 + 2 张能力地图、共 66 张子票》（票面、`research/1010-ticket-structure.md`、`specs/1010-ts-rewrite-spec.md`、`docs/adr/20261011-deck-ts-rewrite.md`、`research/1010-deck-chain-dirs.md`、`CONTEXT.md`）。
审查方式：只读。所有数字都是我这一次亲手量的，量不到的一律标「猜测」或写进最后一节。
审查立场：我是反方。下面每一条先给「最强的反方论证」，再给裁决。裁决不等于反方赢——有三条我量完之后判反方输了。

## 一句话结论

**小改，不动 TypeScript 这个大方向。**

理由一句话：范围实测只有 109 份文件 / 16309 行（不是 417 份大爆炸），所以「转 TypeScript」这件事本身是可负担的；真正站不住的不是语言选择，而是三处落地细节——范围与判据没对齐（地图 13 承诺全仓手写 `.js` 归零，而方案自己声明了范围外）、搬家票与开发票会同时改同一批文件（实测 9 份）、以及「让人吃透」的那份文字被排在整个改造的最后一张地图。

## 问题 1：「全面 TypeScript」是不是达到那五个目标的最省路径？

### 最强反方论证

先把反方要用的量摆出来（全部实测，命令见最后一节）：

| 口径 | 文件 | 行数 |
| --- | --- | --- |
| `src/` 下手写 `.js`（扣掉 `logPkg`、`generated` 两个派生目录） | 417 | 59613 |
| `src/` 下 `.ts` / `.mts` | 46 | 3349 |
| `src/` 下手写 `.js` 中的薄文件（<80 行） | 162 | 6882 |
| **本次范围内的文件**（迁移映射表 `modules` 去重、只数 `.js`） | **109** | **16309** |
| 范围内的薄文件（<80 行 / <60 行） | 36 / 20 | — |
| 范围内纯转发壳（只有 re-export） | 1 | — |

反方的论证有三步：

1. **范围的真实大小是 417 份，方案只覆盖 109 份**，所以「全面 TypeScript」这个词描述的事情（全仓 417 份）和方案实际做的事（109 份）不是一件事。
2. 如果目标只是「架构清晰 + 类型安全 + 看得懂」，那么给现有 `.js` 加 JSDoc 类型注释、`tsconfig` 开 `allowJs` + `checkJs`，是**不搬家**的路线：不动 109 份文件的位置、不动 91 条 import 字符串、不动 22 个导入方、不动构建脚本、不动 231 条门禁链的路径。
3. 我实测了 `checkJs` 到底要写多少类型（同一把尺子，把范围内的文件当种子让 `tsc` 顺着 import 走）：

| 档位 | 报错数 | 报错文件数 | 主要错误码 |
| --- | --- | --- | --- |
| 壳层种子（9 个工具 + 10 份共享壳，实际拉进 27 份报错文件）`strict` | 689 | 27 | TS7006×503、TS2339×67、TS7053×41 |
| 同上，关掉 `noImplicitAny` | 158 | 20 | TS2339×77、TS18047×36、TS2322×24 |
| 同上，`strict` 全关 | **6** | 3 | TS2591×4、TS2694×1、TS2810×1（全是缺 `@types/node` 的环境错） |
| 全部 109 份范围内文件，`strict` + `checkJs` | **5502** | 220 | TS7006×3362、TS2339×870、TS7053×309、TS2345×184、TS7005×184 |

反方读完这张表说：`strict` 全关的情况下，今天这批 `.js` **只报 6 个环境错**——也就是说「加 JSDoc + 开 checkJs」这条路，第一天就能全绿，成本是一份 `@types/node` 和一次 `tsconfig` 改动。要更严一点，关掉 `noImplicitAny` 是 158 处；只有当你非要和转 TS 一样的严格度时，才会变成 5502 处。

### 裁决：反方的结论输，但反方量出来的东西赢了一半

**反方输在哪：** `checkJs` 不产出可运行代码，而运行时这一头方案里有硬事实挡着——宿主树是**逐文件原样拷贝**，不是打包（`scripts/build.mjs:814-845` 用 `cpSync` 把 `src/host/**` 拷成 `package/lib/**`），并且立了一条不变量（`scripts/build.mjs:863-867`：`package/lib/index.js` 必须与 `src/host/index.js` 逐字节一致）。运行时永远不认 `.ts`，所以**必须逐份转译**；`checkJs` 只能当过程中的网，不能当终点。反方把「终点」偷换成了「过程中的网」，这一步不成立。

**反方输的第二个地方：** 5502 这个数字说明「严格档的类型工作省不掉」。它比逐份转 TS 只多不少——同样要给 3362 个参数写类型，只是把类型写在 JSDoc 注释里；而且 JSDoc 表达不了 `interface` / `implements` / 联合类型收窄，而契约那条线（`docs/adr/20261011-deck-ts-rewrite.md:75-76`、票 #1027「两房用 implements 对上契约」）恰恰靠这个。所以「几分之一」这个说法没有实测支撑。

**反方赢在哪（必须承认）：** 逐份重写真正贵、真正有风险的不是打字，是**搬家**——110 份文件换位置、91 条 import 字符串改写、22 个导入方跟着改（实测：`research/1010-migration-map.json` 的 `specifiers` 有 91 条，`from` 去重后是 22 份文件）。这条路线的风险是「搬到一半，全仓 import 断」，而且是**全仓同时断**，不是一处一处断。

**再给一条反方没提、但方案也说错了的：** 方案自己承诺的东西被范围否掉了。`AGENTS.md:46` 写的最终目标是「项目里手写代码只有 TypeScript……直到清零」，地图 13 的开发票 #1078 的「做完」原文就是「归零核对通过」。但 `research/1010-migration-map.json` 的 `outOfScope` 与 `docs/adr/20261011-deck-ts-rewrite.md:27` 都写明「只有面板用的不动，不在本次任务内」——`src/client/**` 与 `src/shared/**` 的剩余部分这次不转。**两句话不可能同时为真**：范围内的 109 份归零之后，全仓手写 `.js` 仍有三百多份。这一条我在问题 5 里还会用到。

**最少改动的处方：** 把 #1078 的「做完」从「手写 JavaScript 归零核对」改成「范围内 109 份归零核对 + 全仓新增文件只写 `.ts` 核对」，并把这句话写进地图 13 与 #1010 正文；`AGENTS.md:46` 那条「最终目标」保留为长期口径，不当作本次的验收项。改动量：两张票的正文，两句话。

## 问题 2：切分依据对不对？

### 最强反方论证

反方要证的是：**方案嘴上说按「一次调用走完的一段路」切，手上做的是按「源码目录」归堆。** 我手里有三份实测证据。

**证据一：两个独立方法都查出「无主件」，而且各漏各的。**

我从 deck 的入口（9 个工具 + 10 份共享壳）出发做 import 闭包，得到 55 份可到达文件；其中 **29 份（4871 行）不在迁移映射表的 109 份里**。扣掉一份生成物（`src/shared/refresh/idempotency.js`，由 `refresh-core` 生成），还有 28 份手写件。这 28 份逐条拿票结构文档去对，只有 10 份被点名，**18 份（2612 行）在整份票结构文档里一个字都没提**：

- `src/host/refresh/attention.js`（242 行）、`src/host/refresh/writeEvents.js`（387 行）
- `src/host/platform/namingSummary.js`（276 行）、`src/host/platform/refreshAssembly.js`（26 行）
- `src/shared/naming-tracking.js`（327 行）、`src/shared/config-store/workspace.js`（156 行）
- `src/shared/refresh/attention.js`（218 行）、`delta.js`（123）、`failure-window.js`（26）、`page-budget.js`（37）、`policy.js`（128）、`refusal-text.js`（32）、`write-detect.js`（260）
- `src/shared/refresh-workspace-key.js`（40）、`src/shared/step-cost.js`（32）
- `src/shared/tracker/constants.js`（130）、`src/shared/tracker/indexWindow.js`（146）、`src/shared/tracker/backendWritePermissions.js`（26）

本项目里另一份审查（`research/1010-adversarial-lead.md` 第 2.1 节）用另一种方法（「口径里点名、地图里没有」）另查出 10 份，两边**交集只有 3 份**（`constants.js`、`deck-derive.js`、`refusal-text.js`），并集 **25 份**。两个方法各漏各的，这件事本身就是「按目录归堆查不全」的直接证据：目录清单是人工列的，漏掉的那些文件没有一处机制能提醒你。

**证据二：两张票会同时改同一批文件，而且实测是 9 份。**

地图 01 的 #1019「目录归位机械搬家一次做完」要改 91 条 import 字符串，落在 22 个导入方上（实测清单在 `research/1010-migration-map.json` 的 `specifiers.from`）。这 22 份里，**9 份就是 `src/host/tools/*.js`**——也就是地图 04 的开发票 #1035「十个工具入口文件转 TypeScript」的全部工作对象。

我按 118 条阻塞边算了传递闭包，实测这两张票的关系是：

- #1019 的直接前置：#1014、#1017、#1020、#1021、#1023、#1026
- #1035 的直接前置：#1034、#1031
- **#1019 不是 #1035 的祖先，#1035 也不是 #1019 的祖先**（两边的祖先集合里都没有对方）

也就是说，只要地基那几张票一关，这两张票**同时进入可开工状态**，然后两张票各自去改同样的 9 份文件。101 条（实测 118 条）边在这里一条都挡不住。

**证据三：「编号＝阅读顺序，动手顺序写在依赖边上」这句话不被任何机制保证。**

`research/1010-ticket-structure.md:24` 写「编号＝阅读顺序，由外向内；动手顺序写在依赖边上」。我把 118 条边做成传递闭包，逐对检查 12 张调用链地图的开发票，实测结果：

```
相邻两号逐对检查（后一号是否被前一号的开发票强制阻塞）
  03 -> 04: 强制     04 -> 05: 强制     05 -> 06: **未强制**
  06 -> 07: 强制     07 -> 08: 强制     08 -> 09: **未强制**
  09 -> 10: **未强制**  10 -> 11: 强制  11 -> 12: **未强制**
跨号抽查
  03 与 06/07/08/09/10/11/12 之间：全部没有强制顺序
  04、05 与 06/07/08/09/10/11/12 之间：全部没有强制顺序
```

12 张调用链地图里的动手顺序，实际上只有 5 处被边钉住，其余靠「编号」这个**没有任何机器约束**的约定。并发三个会话时，谁先谁后完全看人记不记得。

### 裁决：切分依据本身是对的，落地成了目录归堆，必须动

按「一次调用穿过八层」切（`docs/adr/20261011-deck-ts-rewrite.md:14`），第一性原理上是对的——目录只是这段路的落点。但落地之后出现三处漏：25 份底路件无主、9 份文件双写、编号顺序不被边约束。这三处都不是「注释能补」的问题，是结构问题。

**更抗冲突的切法，两档：**

- **档一（小改，够用）**：给「搬家票」和「以那 22 个导入方为对象的开发票」之间加一条双向阻塞（或者干脆让 #1019 成为 03–12 全部开发票的前置）。一行操作，消掉 9 份文件双写。再把 #1019 的票面补上那 22 份清单——今天这份清单只存在于 `research/1010-migration-map.json`，而实测 81 份票面里只有 4 份（#1013、#1017、#1021、#1023，全在地图 01）提到过任何路径。
- **档二（大改，只在维护者真要三会话并发时）**：先冻结接口再分片——把契约（#1027、#1028）提到房间改造**之前**，再给每一对跨目录 import 写一条「接口冻结」票，上层按接口写、下层按接口实现，两边都对着同一份 `.ts` 类型做事，谁先谁后都不冲突。但这档有个前提：契约今天还不能描述真实行为。`research/1010-adversarial-lead.md` 第 2.6 节实测：`src/` 下没有任何文件 import 契约目录，契约是一座只被自己的门禁检查、还没约束任何真实代码的孤岛，且刚立起来就被改了两轮。所以档二要先补上那节建议的「房间照契约实现的贴合探针」。

我的裁决是**档一**。理由：维护者现在要的是吃透和推进，不是把并发做到极致；档二的收益（真并发）在契约还不准之前拿不到。

## 问题 3：一次性建 66 张票对不对？

### 最强反方论证

反方要证的是：后面 60 张票的边界建立在前面 12 张的结果上，前面一动后面票面就要重写，而执行者会照着错的干。

我先把「票面重写的成本」量出来（实测，`.scratch/adv-1010/t/` 下 81 份票面）：

- 子票正文**平均 174.4 字符（约 8.8 行）**，最长 716 字符、最短 251 字符。
- 81 份票面里，只有 **4 份**提到过任何路径；
- 「零变化」这个词在 81 份票面里总共只出现 **2 次**。

所以反方最弱的一环在这里：**票面返工的成本极低**（一张三句话的票，改一次五分钟）。真正贵的不是票面，是**依赖边**：118 条边里有 32 条跨图，前面一改，后面的次序就失效，而**边失效没有任何门禁能发现**——我复核时只能自己写传递闭包去算，仓库里没有一条命令会告诉你「#1031 的前置少了一条」。

### 现在建 vs 到点再建：代价清单

| | 现在建（已建） | 到点再建 |
| --- | --- | --- |
| 票面返工 | 便宜：一张票三句话 | 便宜，但写票时要用一次「回头读前面结果」的时间 |
| 维护者浏览 | 贵：`#1010` 下 43 张直接子票，含 28 张旧票；全批 81 个节点 + 28 张旧票 = 109 行列表 | 便宜：列表短 |
| 依赖边 | 一次建对，但改一张票的前置要人记得去动边（GitHub 不提醒） | 可以按真实结果连，边不会失效 |
| 建造成本 | 已付 | **要重付，而且不便宜**：`research/1010-ticket-structure.md:267` 记着三个坑——插件的 `deck_map_plan_create` 一次调用建不完一张地图（120 秒上限）、GitHub 的父子边与阻塞边端点编号口径不一致会全部 404、编号记错接错边 |
| 全貌 | 现在就有（能开工的第 0 层 29 个节点） | 看不到，且维护者明确说过想「挑感兴趣的」 |

### 裁决：现在建是对的，但必须给票面加一条「这会变」的规则

判据是：**重建造的成本 > 改票面的成本**。重建要再踩一遍上面那三个坑，而且 118 条边要重连；改票面只是改三句话。

但有一条必须补：哪些票的边界会随前面的结果改写，票面上要写出来。按我的实测，是这三类：

1. **地图 03/04/05/06/07 的全部开发票**——它们的边界引用契约，而契约今天还没被任何真实代码用过（见问题 2 的档二）。契约第一次被真后端压是地图 08（#1050 的目的原文：「把契约第一次真正压一遍——契约的问题要在这张图暴露」）。在 #1050 之前，契约随时可能改。
2. **地图 11 的 #1068/#1069/#1070**——它们的边界是「只转被 deck 调到的行」（`docs/adr/20261011-deck-ts-rewrite.md:82`、`research/1010-ticket-structure.md:38`）。而「被 deck 调到」这件事今天**没有机器判据**：我把票结构、规格、ADR、迁移映射表都搜过，没有一条命令能算出「哪些行被 deck 调到」。判据票是 #1067（讨论票），在它们前面——但在 #1067 出结论之前，这三张票的边界是空的。
3. **地图 08/09 的开发票**——边界是「两房语义差异」（#1057 讨论票定），清单今天在 `research/1010-room-conformity-checklist.md`：13 处编译器能抓的不一致（少方法、参数个数不对、返回类型不对）+ 8 处房内旁路键会因为多余属性报错（GitHub 的 `create()` 带 5 个、Markdown 带 3 个）。这些数字会随 #1057 的结论变。

另外建议在 #1010 正文加一句规则：「票面只保证目的与做完，边界以本图讨论票的结论为准」。把「票面会变」写成规则，而不是让执行者以为是意外。

## 问题 4：「讨论 → 开发 → 讲解」这套仪式对吗？

### 最强反方论证

先把成本摆出来（实测）：

- 需要维护者出场的票：**14 张讨论票**（地图 13 没有讨论票）+ **15 张讲解票** = **29 张**，占 81 个节点的 36%。
- 15 张讲解票里，**13 张的「做完」是同一套「封装 / 参数 / 边界失败」三看问答**（实测「三看」在 81 份票面里出现 13 次），其中 **11 张逐字完全相同**（#1032、#1036、#1041、#1045、#1049、#1055、#1061、#1071、#1075、#1087、#1093 都是「做完：维护者能复述，并对『封装 / 参数 / 边界失败』三看逐条表态。」）；#1022 与 #1028 是同一套的变体（分别写成「能用自己的话复述这条链」「能复述契约管什么、不管什么」）；#1065 只写「维护者能复述」；#1079 写「维护者确认全域可读，本次改造收口」。
- 最长依赖链 10 层。而第 0 层（无前置、可开工）是 15 张地图 + 14 张讨论票 = 29 个节点——**开工前就有 14 次对话要发生**，不是边做边问。

时间与注意力估计（**猜测，不是我量的**）：按讨论票每张 2 个往返、讲解票每张 3 个往返（提问 → 维护者答 → 再确认），是 `14×2 + 15×3 = 73` 个往返；按每天能承受 5 个往返算约 15 个工作日，全花在仪式上，还不含开发票返工。我没量过维护者的往返速度，这个数字只能当量级参考。

反方还指出一件更实质的事：**同一套问题要被问 13 遍**。13 张讲解票的「三看」（封装 / 参数 / 边界失败）是同一套通用问题，不是每张图特有的问题。同一个问题问 13 遍，答案会趋同，注意力会磨掉——而维护者的目标恰恰是「吃透」，不是「复述 13 遍」。

### 替代方案

- **甲（最小改动）**：讲解票从 15 张合并到 3 张（地基一次、调用链中段一次、收口一次），讨论票从 14 张合并到 5 张——`research/1010-ticket-structure.md:124` 自己就列过「按阶段合并 5 张」这个选项。29 张人票降到 8 张，往返从约 73 降到约 20。
- **乙（维护者提过的方向）**：讲解不做每图一次，改成整条链做完后走一次全程；每张地图只留一段「本图做了什么」的文字记录，不请人表态。

## 问题 5：验收口径自相矛盾吗？

### 先看票面是怎么写的（按维护者的要求读了票面原文）

- **#1013（地图 01 构建与测试基建）**原文：「这张地图不改任何产品行为……做完的标志：随手写一个 `.ts`，一条命令就能被构建、被测试、被类型检查、被门禁看见；发布探测仍通过。」→ 它只说**基建自己**不改行为，**没有给 03–12 定零变化的判据**。
- **#1050（地图 08 GitHub 房）**原文：「做完的标志：28 件转 TypeScript、门禁全绿、金标准回执逐字一致、真仓回放通过。」→ 「金标准回执逐字一致」是唯一一条可判定的零变化表述，而且它只落在一张地图上，不是全部 13 张。
- **#1066（地图 11 最底层）**原文：「边界：只转被 deck 调到的行，不整文件扫荡——这些文件另有主人。做完的标志：被 deck 调到的每一行都是 TypeScript、**每笔外部调用都有日志与耗时**、**额度与快照行为不变**。」→ **矛盾就在这一句话里**：一半是加法（每笔调用加日志与耗时），一半是零变化（额度与快照行为不变）。

### 最强反方论证

1. **两份仓库文件直接对撞。** `AGENTS.md:60` 原文写「纯重构注释类型迁移**免演练**」；而 `specs/1010-ts-rewrite-spec.md:140` 原文写「每个单元一次『只看日志定位』演练，做不到就补日志点」，票 #1016 的「做完的标志」也写「每张改写地图的开发票都带一句『本段日志点已加、对照表已更新』的验收项」。一个说免演练，一个说每张票都必须加日志点。**要么每张票不是纯迁移（那它就不是零变化），要么它是（那就该免演练）**——必须二选一，现在是两条同时挂着。
2. **尺子必须被改造本身改掉。** 今天的验证链里有 `verify-log-count` 与 `verify-log-fields`，它们拿代码里的日志事件与 `research/489-appendix.md` 第 1 章对照表对齐。计划要求每张地图加日志点，就必然要动这份对照表——**同一条门禁既是判据，又是被改的对象**。所以「用今天这 231 条链量到底」这句话在日志这一维上是假的。
3. **尺子本身今天就是残的（实测）。**
   - `scripts.verify` 今天实测 **231 条**（方案文档写 240 或 243），`tests/verify-*.js` 实测 **283 份**（52 份不在链里）。
   - `research/1010-verify-baseline.md` 点名当天为红的三条门禁，我实跑**三条全绿**（`tests/verify-deck-tools.js`、`tests/verify-log-count.js`、`tests/verify-669-switch-visible.js`，exit=0）——并行会话已经修掉了。所以「今天 14 条红」这个说法已过期。
   - 更要紧的是：那份基线文档自己写明有 **13 条链今天是红的，而红的原因正是重构要动的地方**（夹具各自手拼依赖对象，等新的装配口做好后应当一次全绿）。也就是说：**在重构落地之前，这 13 条链测不出「行为零变化」**——尺子恰好在要量的那个位置是坏的。
4. **「大量日志」与「行为零变化」在同一个文件里对撞。** `src/host/logStore.js` 的调试开关问题（#1012 报的：真源搬到本机设置文件后，宿主仍拿旧副本当闸门，日志被静默丢掉，`handleLogBatch` 还回 `dropped:0`）正落在日志地图 #1016 的地界里。加日志点会经过这道闸——加完之后「每笔外部调用都有日志」这句话是真是假，取决于这道闸修没修。这不是口径问题，是会让人误判的事实问题。

### 一个能同时容纳两者的验收定义（可判定，三条）

1. **对外回执**：同一份输入对每一个 deck 工具各跑一次，回执 JSON **逐字节相同**。这条靠 #1015 的金标准夹具。注意：#1050 已经把它写进「做完」，而 #1015 今天还没建——所以 **#1015 必须先落地，否则地图 08 的「做完」是不可判定的**。
2. **可观测面**：日志的**事件名集合只许增不许改**（沿用 #1016 的「不新增同义事件」）；新增事件必须在同一次提交里登记进 `research/489-appendix.md`；并把 `verify-log-count` 的判定从「事件总数一致」改成「已登记事件全部有落点、且没有未登记事件」——把计数改成对照，这样加日志和零变化才能共存。
3. **注释与体积**：注释不算行为，但要有一条上限兜着（`specs/1010-ts-rewrite-spec.md:138` 已经写了「单文件行数上限」这条依赖检查工具），否则「大量注释」会把那条门禁顶红。

### 裁决：自相矛盾，且矛盾在最关键的一处

矛盾不是我推出来的，是 #1066 自己一句话里写着的，加上 `AGENTS.md:60` 与 `specs/1010-ts-rewrite-spec.md:140` 两份文件对撞。不改这一条，三个执行者遇到「加日志会不会破零变化」会拍出三种答案。

**今天的材料够不够支撑这个验收定义：不够。** 三处缺口：金标准夹具（#1015）还没建；231 条链里有 13 条今天红、且红的正是重构落点；日志门禁的判定口径还是计数（三个执行者之一改了对照表，另外两个人看不到）。
