Q4 深挖：产物出库，以及产物今后落在哪

2026-10-12 · 写给 TypeScript 新手 · 只讲你点名要知道的七件事

一句话总结：手写的源码只留 .ts 一份；机器生成的 .js 只落三个地方——package/lib、package/shared、一个构建缓存目录；src/ 下不再出现生成的 .js；这件事不单独成票，在 1014 敲定后并入 01 号地图的范围。

1「三处一起出库」是哪三处

「出库」＝从 git 里移除（git rm --cached，只动索引、文件留在盘上，不删文件）、写进 .gitignore、改由构建负责生成。

哪一处是什么今天的状态
package/shared/ 构建把 src/shared/ 整棵树原样拷过来的一份镜像（scripts/build.mjs:847） 79 个 .js 全被 git 跟踪。注意：.gitignore 只忽略了 /package/lib/，漏了它
像素风 34 个同名 .js 每一个 .ts 旁边生成的同名 .js（cards 16、pixel 8、skillDetail 7、views 1、kernel 2） 34 个全部被 git 跟踪（与 34 个 .ts 并排放在 src/ 里）
四个核的转译产物 35 个 四个 xxx-core 把 .ts 转译出的 .js，落在 src/shared/<核名>/（label-color 3、refresh 14、version-control 14、config-store 4） 35 个全部被 git 跟踪

别把两组数字搞混：src/shared/refresh/ 与 src/shared/version-control/ 里另外还有 3 个 .js 是手写源码，不属于上面那 35 个生成物；它们要靠后面的迁移票转成 .ts，不在这件事里删。

为什么要把它们请出库：入库的产物就是第二份真源——改一边忘另一边就会漂移。为了防这次漂移，仓里现在养着四条「新鲜度门禁」当永久税：tests/verify-label-color-freshness.js、verify-refresh-freshness.js、verify-version-control-freshness.js、verify-config-store-freshness.js（做法是重转一遍、逐字比对）。产物不入库，这四条就没有存在理由，可以删。

2「产物只落三处」是什么意思

意思是一句分类原则：手写的那一份永远只有 .ts；机器写的那一份只允许出现在下面三个地方，别处（尤其是 src/ 里）不许有。

落点装什么进发布包吗进 git 吗
package/lib/宿主那份逐文件产物（src/host/** 整树 + 一个 esbuild 打出来的 client.js）。今天 169 个文件进（files 白名单里有 lib）不进（已被忽略）
package/shared/纯逻辑那份逐文件产物（对应 src/shared/**）。今天 79 个文件进（files 白名单里有 shared）今天错在进了，要移出
构建缓存目录（新增，例如 .build/）客户端闭包拼接要用的逐文件 .js；今天这批产物写在 src/ 里与真源并排（就是第 1 节那 34 个）不进（只是构建中间品）不进（写进 .gitignore）

为什么必须有第三个地方：客户端那份界面代码不是逐文件发布的，它是构建时把几十个文件按顺序拼成一个闭包（scripts/build.mjs 里的 KERNEL_MODULES、SHARED_SPLICE、LEAF_MODULES 三张清单）。拼接读的是逐文件产物，所以这些产物必须落到磁盘上某个目录；今天它们落在 src/ 里，于是 src/ 混着「手写真源」和「昨天生成的产物」——这正是要消掉的那种混乱。

3package/lib 是干什么的？传统用法是这样吗？

先说结论：名字不是 TypeScript 的约定，位置也跟传统项目不一样；它是本仓发布包的布局。

  • 本仓的 npm 包根目录不是仓库根，而是 package/ 这个子目录。
  • package/package.json 的 main 就是 lib/index.js：安装这个插件的人，入口文件是它。
  • 它的 files 白名单是 lib、shared、cordis.patch.yml、bundled-skills、scripts/、CHANGELOG.md——发布包里只有这些。
  • 里面装的是宿主那棵树的逐文件产物：src/host/** 被整树原样复制过来（构建注释原话「零打包」），再加一个 esbuild 打出来的 package/lib/client.js（客户端那份闭包）。

传统 TS 项目怎么放产物

最常见是 dist/（也有 build/、out/，老式的库会用 lib/）：源码在 src/，编译产物整棵进 dist/，dist/ 写进 .gitignore，package.json 里写 "files": ["dist"]、"main": "dist/index.js"。

对照：「产物集中放一个目录、只发布那个目录、不发布源码树」这套做法，本仓已经在用；不同的只是名字叫 lib 而不是 dist，而且发布包整体住在 package/ 子目录里。所以 package/lib 不奇怪，它就是「这个包的代码目录」，恰好叫 lib。

4package/shared 是干什么的？传统用法是这样吗？

它是第二棵逐文件产物树：对应源码 src/shared/**，同样是整树原样复制（scripts/build.mjs:847），今天 79 个文件。

它装的东西是「宿主与客户端闭包两边都要用的纯逻辑」——例如契约形状、标签、工作区键这类不带宿主能力（不起进程、不读文件系统）的代码。宿主用 require('../shared/xxx.js') 直接加载它，客户端那份闭包则由构建把它拼进去。

「shared」这个名字不是 TypeScript 或 npm 的约定，它是本仓自定的语义（两边共用的纯逻辑）。传统项目里同类的做法是「一个 workspace 包（例如 packages/shared）各自产出自己的 dist」；本仓没有拆成多个 npm 包，而是在同一个发布包里用两个目录把「宿主那份」和「共用那份」分开：lib 与 shared，两个都进 files 白名单。

5src/ 下不再生成 .js——经典 TS 项目会落到哪里

经典 TS 项目：源码只有 src/**/*.ts；编译产物落 dist/**（或 build/、out/），整棵进 .gitignore；测试与编辑器直接吃 src/ 里的 .ts，不需要先产出 .js。src/ 里永远不会出现同名 .js。

本仓的现状：像素风那 34 个文件是「产物与真源并排同名」（源码 PixelCardHead.ts 旁边躺着生成的 PixelCardHead.js，都入库）。这是本仓早期为客户端闭包留下的形状，带来两个具体麻烦：

  • 分不清读的是谁：测试或门禁 import ./PixelCardHead.js 时，读到的是昨天生成的产物还是今天的真源，要靠人记；真源改了没重跑构建，检查照样绿。
  • 「手写 .js 归零」没法机械判定：13 号收口票要核「手写 .js 归零」，但 src/ 里混着生成物时，任何自动核对都得先学会区分「哪份是手写的、哪份是生成的」。

改法：客户端闭包拼接用的那批逐文件产物挪进构建缓存目录（第 2 节第三行）；src/ 下只剩手写文件——将来只剩 .ts。宿主那棵树的逐文件产物本来就只在 package/lib，不落 src/，不受影响。

一个容易误解的点：Node 侧没有打包，宿主的代码是逐文件同名加载的（因为要动态 import 模块），所以「产物集中到一处」不等于「打成一个 bundle」。前两个落点依旧是逐文件、同文件名、同相对路径，只是整棵树挪了位置；构建缓存目录也一样。

7四个 xxx-core 是什么，为什么要动它们

你的理解是对的。就是仓库根目录下这四个目录：

核TS 源码产物落点新鲜度门禁
label-color-core/3 个 .tssrc/shared/label-color/*.js（3 个）verify-label-color-freshness.js
refresh-core/14 个 .tssrc/shared/refresh/*.js（14 个生成 + 2 个手写）verify-refresh-freshness.js

每个核的构成完全一样：src/ 下是手写 .ts、一份自己的 tsconfig.json、一份自己的 build.mjs（逐文件转译成同名 .js），产物提交入库，另有上面那条新鲜度门禁守着「产物必须与真源一致」。它们是本仓已有的 TypeScript 先例，也是现行那种折中形状：源码已经是 TS 了，但产物还在库里、还要靠门禁看着。

「让它们向我们学习」＝这次讨论给 deck 工具定下的规矩（源码只有 .ts、产物只落那三处且不入库、新文件靠目录扫描自动收录、一条命令跑完检查、没有新鲜度门禁），定下来之后就是全仓的统一规范；四个核按同一套改，那四条新鲜度门禁随之删除。仓库 ADR 里已经写着「四核形态统一另立决策」——本次讨论正好把这套规范写清楚，剩下的只是「什么时候改、由哪张票改」。
