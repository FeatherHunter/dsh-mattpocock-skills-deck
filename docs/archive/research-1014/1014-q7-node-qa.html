Q7 深挖：要求哪个 Node 版本，这件事到底在管什么

2026-10-12 · 写给 TypeScript 新手 · 只讲你点名的六个知识点

一句话总结：package.json 是 Node 与 npm 世界的包裹清单，不是 TypeScript 的配置文件；engines.node 是它里面的标准字段，不是我们自造的名字；我们写 22.15 不是因为「版本越高越好」，而是因为测试侧那只装载钩子用到的同步接口从 22.15 才有；装插件不会替用户装 Node；最新的 Node 确实能直接跑 .ts，但它不做类型检查、也不把 ./x.js 映到 x.ts，所以替不掉那只钩子，也替不掉 tsc。

1package.json 是 TypeScript 规定的配置文件吗？

不是。TypeScript 自己的配置文件是 tsconfig.json；package.json 属于 Node 与 npm/pnpm 的世界。两者的分工：

文件回答什么问题谁认它
package.json这个包叫什么、什么版本、依赖谁、入口文件是哪个、怎么安装、有哪些脚本Node 与包管理器（npm / pnpm / yarn）
tsconfig.json检查哪些文件、用什么严格程度、要不要产出文件TypeScript 编译器 tsc

TypeScript 只是借用了 package.json 里几个字段来表达自己：types（指向类型声明文件 .d.ts）、exports 里的 types 条件。没有 package.json，tsc 照样能编译一个 .ts 文件；反过来，没有 tsconfig.json，tsc 会用一套默认参数，几乎什么都不检查。

本仓实例：根 package.json 的 scripts.build 拉起 node scripts/build.mjs（构建入口）；tsconfig.client.json 决定客户端那一域检查哪些文件。两份文件各管一件事，互不替代。

2engines.node 是 TypeScript 规定的，还是我们自己取的名字？

都不是 TypeScript 的东西，也不是我们自造的名字：engines 是 npm 包清单里的标准字段，node 是它规定的标准引擎名之一（另一个是 npm）。写法就是一句版本范围：

"engines": { "node": ">=22.15" }

顺带分清本仓已有的那个：

  • package/package.json:10 的 "engines": { "dsh": ">=0.2.0-rc.2" }——dsh 不是标准引擎名，是 DSH 自己定的约定：npm 不认识它（只照旧检查 node 和 npm），DSH 认识它。
  • 所以「node 与 dsh 并列写在同一段」完全合法：一个给包管理器看，一个给 DSH 看。

要记住它的性质：engines 默认只警告、不拦截——版本不满足时 npm 打印一条 EBADENGINE 提示，包还是照装（除非使用方自己打开 engine-strict）。所以它是一句「声明」，不是一道「闸」；真想拦住，得靠脚本自己在启动时检查版本并报错。

3为什么是 22.15？——下限由「用到的那条 API 从哪版才有」决定

不是「越高越好」，而是我们依赖的最新一条 Node 接口的引入版本。相关的那条接口，正是 Q6 里讲的那只装载钩子：

接口从哪个版本才有它管得到 CJS 的 require() 吗
module.register()（异步）Node 20.6管不到——只加异步钩子的话，那条 require(.../guide-steps.js) 会在文件改名当天就断
module.registerHooks()（同步）Node 22.15管得到，正是我们要用的那只

本机实测（Node v24.19.0）：registerHooks=function、register=function、typescript=strip（原生跑 .ts 的能力默认已开）。所以 22.15 这个数字不是拍的，是「同步钩子 + 我们那 7 处 CJS require」算出来的最小充分值。

4版本高对插件使用者意味着什么？越高性能越好吗？

先把两件事分开：① 仓库与开发链的下限（我们写进根 package.json 的那个）；② 使用者那一侧的要求（由 DSH 决定，不由我们决定）。

  • 发布包今天只要求 dsh >= 0.2.0-rc.2（package/package.json:10），因为那只装载钩子只在仓库的测试与开发链上跑，不随包发布；发布出去的是普通 .js 产物，能被 DSH 跑起来的 Node 都能跑。
  • 「越高越快」只在大方向上成立：新版 Node 换了新版 V8，常见场景会快一些。但版本下限存在的理由不是快，而是「这条接口有没有」。
  • 抬高下限的代价很实在：把还在旧版本的同事、CI 和使用方一起挡在外面。

所以本仓的 22.15 是「刚刚够」，不是追新。真要抬高，得先说清抬到哪一版、为哪条接口抬；说不出来就不该抬。

5用户没装最新 Node，装我们的插件会替他装吗？

不会。npm 与 pnpm 只装「包」，从不安装或升级 Node 本身。Node 是用户自己装在机器上的运行时（官方安装包，或 nvm / fnm / Volta 这类版本管理工具）。包管理器在这件事上能做到的，最多是：

  • 照 engines 打印警告（默认），或在使用方开了 engine-strict 时拒绝安装；
  • 注意别和 Corepack 搞混：本仓 package.json 里的 packageManager: pnpm@11.22.0 管的是包管理器（Corepack 能按它下载 pnpm），不是 Node。

另外，用户装到的是我们发布时就已经构建好的包：package/package.json:16 的 prepare 在我们这一侧跑（发布时的 npm publish 会再触发一次构建），不会在用户机器上编译一遍源码。

6用最新 Node 就能直接「编译」TypeScript 吗？

能跑一部分，但它和「编译」是两件事。新 Node 的做法是擦掉类型再把代码交给 V8 执行（type stripping）：

  • 不产出 .js 文件，也不做类型检查——类型写错了它不报错，那是 tsc 的活。
  • 不改写引用路径：源码写 import './x.js'、而磁盘上只有 x.ts 时，直接报错退出（本机 v24.19.0 实测 exit 1）。
  • 有些依赖类型的语法用不了：enum、带运行时代码的 namespace、参数属性、装饰器（全仓今天一处都没有）。
  • 这份能力还要看使用者那一侧的 Node 版本，而我们控制不了别人的机器。

本仓为什么不靠它：两条发布产物是逐文件被加载的（src/host → package/lib、四个核 → package/shared），源码里的相对引用写 ./x.js 是为了让产物里的路径正确。靠 Node 原生就得把源码改成 ./x.ts，等于把风险搬到发布产物上——所以自己写约三十行装载钩子，只在测试与开发链上把 ./x.js 映到同名 .ts。

一句话：Node 原生跑 .ts 让「单测直接跑 .ts」这条路更近，但它替不掉钩子，也替不掉 tsc——三件事各归各：Node 负责跑，钩子负责找文件，tsc 负责挑错。
