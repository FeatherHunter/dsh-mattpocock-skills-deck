Q2 深挖：「引用只能朝下」到底怎么管住

2026-10-12 · 写给 TypeScript 新手

一句话总结：过渡期用一个社区标准的依赖检查工具看着（不自己写门禁），终态把「方向」交给 TypeScript 编译器保证，两条规则各有唯一判据、不许并存。

1「依赖图门禁」是什么

把「哪个文件引用了哪个文件」全部读出来，画成一张图：点 = 文件，线 = 引用；然后按目录规则看这张图上有没有不该有的线。

具体例子：如果 src/deck/shell/xxx.ts 里写着 import ... from '../../host/tracker/backends/github/yyy.js'，图上就多出一条「deck → GitHub 房」的线；规则说这条线不许有，它就报红。

它什么时候跑：跟现在 tests/verify-*.js 一样，挂在 npm run verify 里，非 0 就阻塞发布。

仓里今天已经有两条这种门禁，只是判据是「读文件文本 + 正则」：

  • tests/verify-no-same-layer-import.js —— 同一层内部不许互相引用（host / platform / shared / seam 四层，各层内部禁引）。
  • tests/verify-no-cross-import.js —— 三座后端房间之间不许跨房引用。

顺带说清：你提到的第三条 tests/verify-file-granularity.js 其实不是依赖图，它数的是「每个文件多少行」，只是同样靠读文件文本。票里把三条归成一类，是因为它们的判据都是「读 .js 的文本」，换成 .ts 之后全都看不见。

2「用 TypeScript 编译器 API 解析 import」是什么

不用正则去猜，而是把源码交给 TypeScript 自己的解析器，让它把文件读成一棵语法树，再从树上读「这条 import 指向哪」。

仓里已经有现成例子：tests/verify-client-no-undef.js:24 就是 const ts = require('typescript-ast')，紧接着 ts.createProgram(...)、ts.getPreEmitDiagnostics(program) 拿诊断结果 —— 那就是在调用编译器。

为什么比正则好：注释里写的 import、字符串里出现的 import 字样、import type {...}、export ... from '...'、import(变量) 这些情况，正则要一条条写规则，而且很容易漏；编译器给出的答案就是「这段代码实际会怎么解析」。

老门禁为了绕开这些，注释里专门写了「先去掉块注释与行注释，JSDoc 里的 import() 不算数」—— 那些都是正则方案自己要还的债。

这条路仓里已经能走通，不需要新增依赖。但我们最终不自己写这套检查，改用社区工具（见第 7 条）；理解它是为了看懂「门禁到底在做什么」。

3typescript-ast 是什么

就是根 package.json:36 的那一行：

"typescript": "7.0.2"
"typescript-ast": "npm:typescript@5.6.3"

第二行是 npm 的别名写法：把 typescript 这个包再装一份，名字叫 typescript-ast，版本 5.6.3。

为什么要这么干，tests/verify-client-no-undef.js:12-15 写得很清楚：主包 typescript 升到 7.x（Go 重写）之后，不再导出可以在代码里调用的编译器接口（createProgram 这类取不到），而构建与类型检查用的是 7.x 的 tsc 命令行本体，不受影响。所以凡是要「在脚本里调用编译器」的地方，就 require typescript-ast（5.6.3）当解析器；将来解析器也能用新版了，把那行换回去即可。

一句话：它是同一个包的第二份安装，专门给需要调用编译器的脚本使用。

4那三条规则怎么管到、为什么能管到

  • 引用只能朝下：每条线的两头各落在哪个域（deck / tracker 契约 / 内核 / 三座房间……），把「允许的方向」写成一张表 —— deck → tracker 契约 允许，契约 → deck 没写就是不许。出现表外的线就报红。
  • 禁循环：A 引 B、B 引 A，或者绕一圈回到自己。这在图上就是「环」，工具自带这个判定，不需要你写规则。
  • 禁跨层深引用：把「允许连到谁」收窄成白名单 —— deck 的文件只许连到 src/tracker/contract/ 里的公开入口；连到 src/host/tracker/backends/**（房间实现）或 src/host/tracker/detection/**（识别判定）就算违规。

为什么能管到：这三条的判据都只是「这条线的两头是谁」，而线的两头在源码里是静态写死的（import ... from './x.js'），不需要运行程序就能读出来。它就是「照着一张表逐条核对」，没有玄机。

它管不到什么（这条你必须知道）：路径是算出来的就看不见，例如 await import('./' + name + '.js')。今天老门禁对此的口径是「一律算违规」（verify-no-same-layer-import.js 的注释里写着这条），新工具要沿用同样的严格度，否则这里就是一个洞。

5「终态（12 号收口后）」是什么

指地图 #1010 里排在最后的几张图做完之后的局面：

  • 12 号「宿主接线」做完的标志：全仓没有指向旧路径的活引用、面板读数与今天一致。
  • 13 号「收口」：全域索引 + 手写 .js 归零核对通过。
  • 在这之前还有：1019 那次机械搬家（91 处引用一次改完）、08/09 两房改造、11 号最底层。

为什么工程引用要等到那时候：工程引用要求「每个文件固定属于哪个工程」。而在此之前，文件还在搬 —— 三座房间要搬进 rooms/、契约刚挪过家、91 处引用要一次改完。此刻立工程图，等于一边搬家一边改门牌，编译器报的错会把真问题埋在噪声里。

6「把方向从检查升级成编译期事实」——这样对吗

对，但有三个细节必须补上，不然会把它想成万能：

  • 它只管编译器看得见的文件（.ts）。过渡期那 348 个手写 .js 不在任何工程里，所以现在只能靠检查工具 —— 这就是「分阶段」的原因。
  • 它有实测代价。被引用的域必须真的产出 .d.ts（实测报 TS6310），类型检查入口从 tsc -p 换成 tsc -b，多一个声明产物目录。
  • 它的边界。编译器保证的是「不许引用没被 references 的域」（实测写反方向的导入，报 TS6059 / TS6307）；但同一个工程内部随便引，「只许走契约入口」这条它管不了。所以「深引用」这条规则即使上了工程引用，也要继续由工具管。

大白话：检查工具是「交卷前有人替你核对一遍」，编译器是「写错当场不让你编译过」。前者可能漏（脚本写得不好就漏），后者是解析器自己说的，不会漏。所以终态那一步值得做。

7你讨厌门禁 → 推荐改成这样

先站你这边。你讨厌的大概是「自己写的、读文件文本钉写法」的那一类，而仓里已经按你的意思删过一批：tests/verify-build-artifacts.js 里三条读文本钉形状的断言被删掉了，注释还留在文件里（第 4-8 行、156-161 行）。你们自己的 ADR 也早写了这条方向：「今天约三十个按路径文本断言的旧门禁，换成标准依赖检查工具……工具换成社区的。」

所以改后的做法是：

  • 引一个社区标准的依赖检查工具。dependency-cruiser 是这一行的主流（npm 当前 18.6.0，自述就是「Validate and visualize dependencies. With your rules. JavaScript, TypeScript……」，昨天还在更新）。规则写成它的配置文件：禁循环、禁跨层深引用（白名单）、方向表。
  • 它一次替掉现在两条老门禁（verify-no-same-layer-import.js、verify-no-cross-import.js），而且同时能看 .js 与 .ts，过渡期不用另写一套。
  • 终态上了工程引用之后，把「方向」那条规则从配置里删掉，不是并存。

为什么坚决不许并存：同一条规则有两个判据，迟早不一致，最后没人知道哪个说了算 —— 那就是「假绿」的来源。

关于「讨厌门禁」我说一句反向的话，你可以驳：问题不在「有门禁」，而在「自己写的、读文本钉写法、一条规则两个判据」—— 这三样都该消掉。但完全没有检查等于靠自觉，这次要跨十几张图和多个会话，靠自觉的东西一定退化。建议口径定成：

能交给编译器的不写检查；非写不可的用社区工具；自己写的检查只留「只有这个仓库知道」的规则，而且每条都要能说出它防的是哪一次真实事故。

8为什么这张票挂 13 号、写死触发条件与「上线即删」

  • 挂 13 号：13 号本来就是「收口」。工程引用的判据是终态（全仓 .ts、目录不再动），放在收口图里，它既不会被提前做（提前做会和搬家打架），也不会被忘（收口图就是清账的地方）。
  • 写死触发条件：跨会话的工作里，「以后再说」基本等于「永远不做」。条件必须是可判定的，例如：12 号收口 + 手写 .js 归零核对通过。
  • 「上线即删」：就是第 7 条那条原则的落地方式 —— 防止两套判据并存。

优点：① 过渡期不付工程引用的代价（声明产物目录、搬家期 tsc -b 的噪声）；② 终态拿到最硬的保证（编译器级，不是脚本级）；③ 删掉的是「检查」，不是「判断力」—— 规则交给了更硬的那一方，没有能力损失。
