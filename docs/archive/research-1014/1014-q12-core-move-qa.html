Q12：把四个核的源码搬进 src/shared/<功能名>/

2026-10-12 · 写给 TypeScript 新手 · 只讲 Q12 要动的那些东西

一句话：四个核的源码从顶层 xxx-core/src/ 搬进 src/shared/<功能名>/，与它们现在的产物目录同名同位置；引用点一个字不用改；搬完顶层四个目录、四份子构建、四份 tsconfig、四条新鲜度门禁一起退场。

0维护者本次的两条表态（原话）

「认可甲，但是目录名会变不会再是 xxx-core 这种命名而是非常规范的符合这个核的功能的命名」

「那句『不用单独成票』我理解只覆盖『产物出库与落点』——是的，未来肯定会有 ISSUE 的」

两条都记在下面：第 4 节回答命名，第 8 节写清哪部分留给未来的票。

1先弄清「核」是什么

核＝一块纯逻辑：只算数、不碰宿主能力（不起进程、不读文件、不起定时器）。今天的四个核各是一个顶层目录，里面固定四件套：

件作用
<名>-core/src/*.ts手写真源（TypeScript）
<名>-core/tsconfig.json只给这个核做类型检查
<名>-core/build.mjs把它逐文件转译成 .js
产物 src/shared/<功能名>/*.js给宿主运行时与界面闭包读

四个核与它们的产物目录：label-color-core → src/shared/label-color/（3 个）、refresh-core → src/shared/refresh/（14 生成 + 2 手写）、version-control-core → src/shared/version-control/（14 生成 + 1 手写）、config-store-core → src/shared/config-store/（4 个）。

为什么会有这种「源码住楼上、产物住楼下」的形状：因为核当初是按「独立子包」造的——自带一份构建脚本，把产物写回共享层。搬进来之后它不再是子包，只是一个域目录，那四件套就没有理由继续存在。

2为什么必须搬：三条要求今天凑不齐

  • ① 源码树要能直接跑：宿主代码与测试都是直接读 src/ 下的模块（例：src/host/configStore.js:18-20 引 ../shared/config-store/labels.js，src/host/versionControl.js:17-24 引 ../shared/version-control/*.js，tests/verify-969-tiered-timeout.js:69 直接 import src/host 的模块）。
  • ② src/ 下不要有生成物（Q4 定的口径）：否则分不清读到的是昨天的产物还是今天的真源，13 号「手写 .js 归零」也没法机械核对。
  • ③ 产物只落发布包：package/shared/<名>/*.js，由根构建统一产出。

今天这三条只能同时满足两条。装载钩子只会把 ./x.js 解到同名的 x.ts——它做不到「跳到另一个顶层目录里的核源码」。所以只要核源码留在楼上、产物又搬走，第 ① 条就断。

搬进来之后三条同时成立：引用点写的是 ../shared/refresh/budget.js，磁盘上是 src/shared/refresh/budget.ts——钩子按同名规则解析，一个字都不用改；src/ 里不再有生成物；产物只落 package/shared/。

3装载钩子在这里干的那一件事

Node 本身跑不了 .ts。测试与开发链要在源码树上直接跑，就挂一只小钩子（本次已定：同步的 module.registerHooks()，约三十行，零新增依赖），规则只有一条：

import('./x.js') → 磁盘上有同名 x.ts 就加载它，没有才加载 x.js。

它的能力边界＝同名。举例：

  • 搬完之后：src/host/refresh/gate.js 里的 '../../shared/refresh/policy.js' → 命中 src/shared/refresh/policy.ts ✅
  • 不搬：那个说明符会去找 src/shared/refresh/policy.ts，而源码此刻还在 refresh-core/src/policy.ts ❌（钩子不会跨目录猜）

4目录名叫什么：-core 消失，名字沿用功能名

-core 是「我是一个自带构建的核」的记号，不是功能描述。子构建退场，这个记号自然没有存在的理由——这一点与你的要求完全一致。

但要说清一条硬约束：搬进去的目录名不能自由取。它由那几十处引用点钉死——引用写的是 ../shared/refresh/budget.js，所以磁盘上必须真的叫 src/shared/refresh/。现有四个名字（label-color、refresh、version-control、config-store）本来就是功能名，已经符合「不带实现史、按功能命名」的口径。

顶层旧名（消失）搬进去之后功能
label-color-core/src/shared/label-color/标签配色：颜色归一与调色板文本
refresh-core/src/shared/refresh/刷新机制的纯逻辑：闸判据、账本预算、写判定
version-control-core/src/shared/version-control/版本管理：命令拼装、解析、写前判定
config-store-core/src/shared/config-store/配置读写：三份 schema 的校验与模板

若你要换更准确的名字（例如给 refresh 换个说法），代价会翻倍：要同时改几十处引用、产物路径、客户端闭包拼接清单（scripts/build.mjs:586-596 有 4 条指向核产物）。建议把「改名」单独一张票，不要混进这次机械搬家——混在一起，git diff -M 就不再是「清一色改名」，回滚也分不清是哪件事出的问题。

5搬家后各件去哪（一张表看完）

东西搬家后
核的源码 <名>-core/src/*.ts（35 个文件）移到 src/shared/<功能名>/*.ts；引用点一个字不改
核的产物由根构建统一转译到 package/shared/<功能名>/*.js（今天各核自己写 src/shared/<名>/，根构建再整树拷进 package/shared/，见 scripts/build.mjs:847）
顶层四个 <名>-core/ 目录删（子构建不再存在）
四份 build.mjs删（逐文件转译交给根构建）
四份 tsconfig.json移进域目录（src/shared/<名>/tsconfig.json），由 glob 发现——「域自带配置」是本次定的默认形状
四条 verify-*-freshness.js删（产物不再入库，一致性由构建保证；删它们的前提见第 6 节）
客户端闭包那 4 条拼接项路径不变，取文本改走同一条「.ts 优先」规则

6删「新鲜度门禁」的前提：构建必须不可能给出过期产物

这四条门禁的做法是「把产物重转一遍、与已入库的产物逐字比对」。产物一出库，这条就没有对象了。但今天「产物与真源一致」还有另外两条检查，它们在源码变 .ts 之后物理上不可能再成立：

  • tests/verify-build-artifacts.js:132-155 的 package/shared ↔ src/shared 逐文件 sha256 双向比对（字节相等的前提没了）
  • scripts/build.mjs:867-874 的「package/lib/index.js 与 src/host/index.js 逐字节一致」（同上）

于是「产物一定新」只剩一个支点：构建的内容指纹缓存。而它的输入清单今天是手写的（scripts/build.mjs:103-104），漏一个目录就会静默给出过期产物。

所以要绑在一起做：把输入集合改成「扫描出来的域目录 ＋ glob 发现的所有 tsconfig」，并加三条断言——域目录不重叠、每个域至少 1 个输入、扫到 0 个就判红。这不是新增门禁，是构建脚本自己的事。

7怎么算搬对了（三条判据）

  • git diff -M 显示这一提交全是重命名，行为零变化（不改一个字符的代码）
  • src/ 下没有生成的 .js（唯一被点名的例外是上游包镜像 src/host/logPkg/）
  • 发布包里 package/shared/ 四份文件数不变：label-color 3、refresh 14、version-control 14、config-store 4；故意改坏一个域里的一个文件，类型检查必须红

8哪些留给未来的票（本次不解决）

  • 子构建的存废（删四份 build.mjs、删四条新鲜度门禁、四核 tsconfig 并进 glob 发现）：本次只确认「产物出库与落点」并入 01 号地图，这一块未来另有 ISSUE（你的原话已确认）。
  • 改名（把 refresh 等换成别的功能名）：要动引用点与产物路径，单独一张票。
  • 两个手写 .js 还躺在 src/shared/refresh/ 与 src/shared/version-control/ 里（共 3 个）：它们是真源、不是产物，靠后面的迁移票转 .ts，本次不动。
  • 工程引用上线（把「引用方向」交给编译器）：挂 13 号收口图，写死触发条件。

9术语小抄

  • 说明符：import ... from '写在这里的那段路径'；本仓约定写 ./x.js，哪怕磁盘上是 x.ts。
  • 装载钩子：挂在 Node 模块解析上的一小段代码，只在加载时改「去哪找文件」，不改代码内容。
  • 逐文件转译：一个 .ts 产出一个同名 .js；不做打包，因为宿主是按路径动态加载模块的。
  • 域：一块代码分区，决定「谁检查它、它允许引用谁」；域目录自带一份 tsconfig.json。
  • 新鲜度门禁：过去用来核对「入库的产物与真源一致」的检查脚本，产物出库后可删。
  • 派生件：不是人手写、也不是本仓源码转译来的文件（例：从已装 dsh-log 包原样拷来的 src/host/logPkg/）。
