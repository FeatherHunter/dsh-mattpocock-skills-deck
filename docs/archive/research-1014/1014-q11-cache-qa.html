Q11 深挖：为什么要先修好「构建怎么判断该不该重跑」，再删掉四个守门脚本

2026-10-12 · 写给 TypeScript 新手 · 只讲你点名的两件事

问题一（Q11 在决定什么）：仓库里有一份「构建缓存」，跑过一次构建之后，只要没改东西，下次就跳过整个构建（省约 30 秒）。它判断「有没有改东西」，靠的是一张手写的输入清单。今天另有四条脚本，专门核对「盘上的产物和源码是否一致」。产物要从 git 里取出来（不入库）之后，那四条脚本就没有存在理由了，要删。Q11 要你定的只有一件事：删它们之前，要不要先把那张手写清单换成自动收集的，并且两件事放在同一张票、同一批交付里完成。

问题二（缓存输入集合结构化）：把「哪些目录算改动」从手写清单改成让构建自己去发现——src、scripts 两棵固定大树，加上「凡是含 tsconfig 的顶层目录」（自动发现），再加上所有 tsconfig 文件本身；并加一条断言：如果一个域目录一个输入都没收到，构建当场失败，而不是安静地跳过。

1先把三个东西讲清，Q11 就不用猜了

构建缓存

跑 node scripts/build.mjs 时会先算一个「总指纹」：把所有输入文件逐个算内容摘要（sha256），拼在一起。指纹和上次一样，就认为「没改东西」，整个构建跳过；不一样才重新构建。缓存文件在 node_modules/.cache/dsh-build.json，不进版本库。

手写输入清单

算指纹之前，得先知道「哪些文件算输入」。这份名单是手写的两行：

  • scripts/build.mjs:103 的 INPUT_ROOTS：src、scripts 和四个核的目录，共六项；
  • scripts/build.mjs:104 的 INPUT_EXTRA：package.json、package/package.json、README.md、tsconfig.client.json、tsconfig.contract.json，共五项。

四条新鲜度门禁

指 tests/verify-label-color-freshness.js、verify-refresh-freshness.js、verify-version-control-freshness.js、verify-config-store-freshness.js。它们的做法是：把四个核的 TypeScript 源码重新转译一遍，和盘上已有的产物 .js 逐字比对。它们存在的唯一理由是「产物今天提交在 git 里，怕产物和源码对不上」。

2Q11 到底要你决定什么

要你决定的是顺序和范围，不是技术细节。两条路：

选法做法后果
甲（我推荐） 同一张票、同一批交付里，先把「输入清单自动化 + 域目录断言 + 修好构建里那条会静默变绿的旧检查」做完，再删那四条新鲜度门禁。 多约 10～30 行构建脚本改动，不新增任何门禁脚本；删门禁那一刻，剩下的保证已经站得住。
乙 分两张票：先删四条门禁，以后再补输入清单的自动化。 中间这段时间里，「产物过期」没有任何东西看得见——构建跳过、门禁也没了，谁都不会报错。
丙 只删四条门禁，输入清单的手写名单长期不动。 等于长期留一个看不见的坑：将来新开一个顶层域目录、或新增一份根上的 tsconfig，忘了补名单，改代码不会触发重建。

需要你决策吗：需要。因为「删四条门禁」听起来像一件独立的小事，很容易被当成顺手清理做掉；而它其实是「把唯一的独立核对手段拿掉」。你只需回答一句话：照甲绑在一起，还是走乙／丙。（如果你觉得这属于实现细节、不想逐条过，也可以直接说「按推荐来」，我就按甲记。）

3为什么删门禁之前必须先修好缓存（这条是 Q11 的核心理由）

今天「盘上的产物与源码一致」这句话，由三条互不相干的检查撑着：

检查在哪产物出库、源码变 .ts 之后
四条新鲜度门禁：重转一遍再逐字比对四个核各自的 tests/verify-*-freshness.js按 Q4 的决定要删掉（它们的存在理由消失了）
package/shared 与 src/shared 逐文件摘要双向比对tests/verify-build-artifacts.js:132-155做不到：一边是 .ts 源码、一边是 .js 产物，摘要不可能相等
「package/lib/index.js 与 src/host/index.js 逐字节一致」scripts/build.mjs:867-874同样做不到：字节相等的前提是两边都是 .js

三条里两条物理上失效、一条要删，最后只剩下一条：「构建刚跑过，所以产物一定是新的」。而这句话能不能成立，全部押在「算指纹的那份输入清单是否完整」上——名单漏了谁，谁的改动就不触发构建，产物就一直旧着，而且没声音。

所以顺序不能反：先把「缓存不可能过期」这件事做成结构性的（名单自己发现，漏了就报错），再删那四条门禁。反过来做，就是先拆保险、再谈修车。

4「缓存输入集合结构化」是什么

今天它是手写的，两个具体漏法

  • 新开一个顶层目录（例如将来可能叫 deck-core/ 的那种），忘了加进 INPUT_ROOTS：改它的文件，指纹不变，构建跳过，产物是旧的，且不报错。
  • 新增一份根上的 tsconfig（例如 tsconfig.deck.json），忘了加进 INPUT_EXTRA：同上。

今天没出事的原因：src/ 与 scripts/ 是整棵树遍历的，绝大多数改动都落在它们里面；四个核也都逐个列了。风险面窄，但一旦踩到，症状是安静的。

改成什么样（这就是「结构化」）

  • 固定两棵大树：src、scripts 整树算输入（今天已经这样）。
  • 自动发现域目录：凡是含 tsconfig 的顶层目录，都算输入根——不再手写「四个核」这样一份名册；将来新开域目录，只要它自带一份 tsconfig，就自动进入输入集合。
  • 自动收 tsconfig 文件本身：不再手写 INPUT_EXTRA 里的两份配置。
  • 加一条断言：输入集合不许为空；每个域目录至少要收到 1 个输入；不满足就让构建当场失败。这条不是新门禁脚本，是构建脚本自己的一句检查。

一个类比：今天像门口保安照一张手写名单认人——名单忘改，人进去了他也不认识。改完之后是「住在小区里的住户都认」，再加一条「如果发现一个住户都没认出来，立刻报警」。

和 Q5 是同一个原则的两次应用：Q5 解决「.ts 文件怎么被构建和类型检查看见」（目录通配 + 目录扫描），Q11 解决「构建怎么知道该不该重跑」（自动发现的输入集合）。两处都是同一句话——能自动数出来的，不许手写。

顺手要修的一条旧检查：scripts/build.mjs:748-768 早就有个「有叶子文件却没登记」的反向检查，但它只认 .js、只扫四个写死的目录，而且外层把异常吞掉。这次迁移把叶子文件改成 .ts 之后，它会扫到空集合还判绿——正是第 3 节说的那种「没声音的错」。修它不用新写门禁，是这条旧检查自己的漏洞。
