Q6 深挖：测试怎么跑 .ts，旧的 231 条门禁怎么办

2026-10-12 · 写给 TypeScript 新手

一句话总结：源码里照旧写 ./x.js（发布产物本来就要这个写法），测试侧加一个约三十行的 Node 装载钩子，把 ./x.js 领到同名 .ts；旧测试不一次性重写，谁被迁移谁退场，13 号收口时清空。

1「写 ./x.js + 三十行钩子」是保留了 js 门禁、不改造了？为什么？

先分清两样东西 —— 它们在这一条里被写在一起，但不是一件事：

东西它管什么它是门禁吗
装载钩子
（约三十行，新增）		 测试怎么把 .ts 加载起来 不是。它不判任何规则、不会红不会绿，是运行环境的一部分
旧测试文件
（tests/verify-*.js，现有 231 条挂在链上）		 判定不变式，红了阻塞发布 是。它们这次不一次性重写，按条迁移

不一次性重写的三个原因

  1. 它是尺子。后面每张改写单元图都要用「转完行为零变化」来判自己有没有改坏，判据就是这 231 条。一次性重写等于把尺子拆了再量。
  2. 零新增依赖。钩子约三十行，转译复用仓里已有的 esbuild，不引测试框架（不引 vitest 那类全家桶）。
  3. 生产链路零改动。./x.js 是发布产物本来就需要的写法（产物是逐文件加载的 .js），源码跟着写 .js，产物一个字不用改。

那旧门禁怎么退场

谁被迁移，就从那条长串里删一条、登记进新跑法；未迁移的数量只降不升；13 号收口时长串清空。新写的测试一律 .ts。

为什么不干脆用 Node 原生跑 .ts

本机 Node v24.19.0 确实能直接跑 .ts（node --test 会连同 .test.ts 一起发现），但 Node 不做 ./x.js → x.ts 的映射：import './b.js' 而磁盘上只有 b.ts 时会直接失败。

若把源码改成写 ./x.ts，这个写法会一路带进发布产物 —— 而产物是宿主与四个核逐文件直接加载的 .js，等于把风险从测试搬到线上。所以：源码保持 ./x.js，测试侧用钩子补上那一步映射。

另一条要记住：Node 原生的类型剥离不支持 enum、带运行时代码的 namespace、参数属性、装饰器（报 ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX）。本仓全仓扫描目前一处都没有，属于「现在不用，但要知道这条线在哪」。

2为什么是 package/lib？符合权威 TS 项目的思路吗？

它是什么：package/ 是发布出去的那个 npm 包（用户装到的是 package/package.json 那一份），package/lib/ 是它的运行时目录 —— 包的 main 就是 lib/index.js，exports 指向的也都是 lib/ 下的文件。

构建怎么填它：src/host/** 原样拷贝成 package/lib/**（零打包），再写入面板入口的打包产物 lib/client.js。

名字权威吗：lib 是 npm 生态沿用几十年的产物目录名（与 dist、build 同族），不是本仓自造词。

和主流 TS 项目比本仓
相同源码在 src/；产物不与源码混放；产物不入库；发布包只装产物（靠 files 白名单）
不同主流常见的是仓库根的 dist/、由 tsc 产出；本仓把「发布包」做成了子目录 package/，产物落在包内的 lib/

为什么不同（不是口味问题）：这是插件形态决定的 —— 宿主按路径逐个加载模块，例如 src/host/platform/deckToolsAssembly.js:104 写的是 await import('../tracker/detection/parseIssueTracker.js')。打成一个大文件之后，这类路径就不存在了，所以宿主那一侧必须逐文件保留。

一句话：目录名是常规的；目录位置由「发布包是一棵可以逐文件被加载的树」这条物理事实决定。

3为什么是 package/shared？符合吗？

它是什么：src/shared/ 是宿主与面板都要用的那部分代码（四个独立计算核的产物也落在这里）；发布包里它是 lib/ 的兄弟目录。

为什么必须和 lib 一起进包：package/lib 里的代码是用相对相邻目录引用它的 —— 例如 src/host/configStore.js:18 写 from '../shared/config-store/labels.js'；拷进包之后，同一条路径正好指向 package/shared/config-store/labels.js。所以 package/package.json 的 files 白名单同时收了 lib 与 shared。

名字权威吗：shared 是主流命名，表示「跨层共用、不属于任何一层」。大仓库里常把它做成独立包（packages/shared/），本仓这个规模做成一个目录就够。

一句话：名字常规；位置同样是发布形态决定的 —— 它是 lib 的相对邻居，两个目录一起构成可运行的包。

4esbuild 是什么技术？权威的 TS 项目用它吗？

一句话：用 Go 写的打包 / 转译器；它只做「把源码变成能跑的 JS」这一件事，不做类型检查。

谁在用：Vite（前端构建的主流工具）底层就是它；Vitest、tsx、Deno 等也在用。属于当红工具，不是冷门自造件。

TS 世界里的常见分工：tsc（TypeScript 官方编译器）负责类型检查，esbuild 负责快速转译与打包。很多项目就是「tsc --noEmit 检查 + esbuild 出产物」。

本仓正是这个分工：esbuild（^0.28.2，已经是仓里的开发依赖）做逐文件转译（scripts/build.mjs:1057）；tsc（仓里版本 7.0.2）只用来做 --noEmit 类型检查。这条改造路线不新增依赖。

5「逐文件转译」是什么行为？

一个 .ts 进去，一个同名 .js 出来：文件个数不变、目录形状不变、相对引用原样保留。

做什么本仓哪里在用
逐文件转译一个文件对一个文件宿主树、共用树、四个计算核、客户端像素系列
打包把很多文件合成一个 .js只有面板入口 lib/client.js

宿主那侧为什么必须逐文件：宿主按路径动态加载模块（见第 2 条的 await import('../tracker/detection/parseIssueTracker.js')）；另外发布包里还有一条老约定「package/lib/index.js 与源入口逐字节一致」，源码换成 .ts 之后，这条要改写成「与转译结果一致」。

好处：报错里出现的路径与源码一一对应；改一个文件只影响一个产物。

6「说明符」是什么？

说明符（specifier）就是 import ... from '这里' 引号里的那个字符串；import('...') 这种动态导入里的字符串也算。

本仓的规矩：源码里一律写 ./x.js（写 .js，不写 .ts，也不省掉扩展名）。两个原因：

  1. 为了产物：发布产物是 .js，Node 的 ESM 要求把扩展名写全，所以产物里的说明符必须是 ./x.js；源码写 .js，转译时原样保留，产物就不用改。
  2. 能编译过：TypeScript 检查时会把这个 ./x.js 解析到磁盘上的同名 x.ts（本仓 moduleResolution: "Bundler" 下实测成立）。

一句话：写 .js 是为了产物；写得通，是因为 TypeScript 认识这种写法。

7「钩子」是什么技术？

它是 Node 的模块加载钩子（ESM loader hooks，用 node:module 的 register() 注册）：Node 在「找到底是哪个文件」和「这个文件怎么读进来」这两步上，允许你插一段自己的代码。

为什么需要它：Node 不认识 .ts；测试想直接 import .ts 源码，又不想先整棵树编译一遍。

计划中的形状（约三十行，落在 1021 那票）分两步：

  1. 解析那一步：看到 ./x.js，磁盘上没有 x.js、只有同名 x.ts 时，就把它指向 x.ts。
  2. 读取那一步：把 .ts 用仓里已有的 esbuild 转成 JS，再交给 Node 执行。

细则一条：同名 .ts 优先于 .js —— 防止一份陈旧的生成产物冒充真源。

它不是什么：不是门禁、不改任何产品代码、不进发布包；只在「跑测试」那条命令里生效。

配套两件：它跟 Node 版本有关（register() 需要 Node 20.6 以上），所以要写下限（见 Q7）；钩子本身要有一条测试，确认 ./x.js 真能加载到 .ts。

8为什么「钩子」能让旧的 200 多条门禁一个字都不用改？

先把它说准：钩子保证的是那些门禁的文本一个字都不用改，不是「这些门禁以后不用管」。分三层说清。

8.1 门禁是怎么取源码的

主流写法是「按路径拼一个 URL，再动态 import」，全仓有 175 处：

await import(pathToFileURL(path.join(ROOT, 'src/host/detectChain.js')).href)

在这行里，x.js 只是一段文本；「这段路径最终指向磁盘上哪个文件」是 Node 在解析阶段决定的。文件从 x.js 改成 x.ts 之后：文本没变，解析结果变了 —— 而钩子挂的正好就是解析阶段，把那一步补上。

所以省掉的是「去 200 多个文件里把 .js 挨个改成 .ts」这件事：改一处解析规则，抵 200 多处文本改动。

8.2 实测：钩子要用「同步那一种」

本机 Node v24.19.0，两条路各跑一次，结果不同：

钩子 动态 import('./x.js')
（磁盘上只有 x.ts）		 CJS 的 require('./x.js')
module.register()
（异步，老 APIs）		 ✅ 拿到值 ❌ 找不到模块
module.registerHooks()
（同步，Node 22.15+）		 ✅ 拿到值 ✅ 拿到值

结论：钩子要用 registerHooks 这一种。因为门禁里确实有几条直接用 CJS require 取产品源码，例如 tests/verify-subdir-first-frame.js:170 写着 require(path.join(root, 'src/shared/tracker/guide-steps.js')) —— 只用异步钩子，这几条会在文件改名当天就断。

8.3 两个「看着不用动、其实要动」的分清

  • 读文本的门禁（数行数、扫 .js 文本抓 import，如 tests/verify-file-granularity.js、tests/verify-no-same-layer-import.js）：文件改名后它们不会崩，但会扫不到文件还判绿 —— 这是空集合假绿，归 1017（门禁换轨读 .ts）与 Q2（方向类换成社区工具）处理，不是钩子能解决的。
  • 写死旧路径/目录的门禁：文件搬家之后必须改（1019 那次 91 处引用、三房改叫 rooms/），ADR §7 已经点名约三十个脚本。

8.4 顺带一条底气

283 个 verify-*.js 里，相对 require 的目标只有 7 个，全部落在 tests/ 自己的辅助件（tests/lib/*.js 等）和 scripts/ 一件脚本上，没有一件指向产品源码；这些辅助件不会跟着转成 .ts，所以那条路不受影响。

一句话收口：钩子把「文件改名」这件事从 200 多处门禁里一次拿走 —— 路径照旧写 .js，解析时领到 .ts。
