3 · 根因：到底卡在哪一步

面板打开 → 前端先用水合好的本地缓存立刻画出来（164 ms，这部分没问题） ↓ 前端随后向宿主问一句：给我最新的（wf.snapshot） ↓ 宿主：我手上有缓存 → 那我先联网核对一下「有没有变」 ↓ ★ 就是这里在等：冷的时候 4.4 秒，热的时候 1.1 秒 ★ ↓ 核对结果绝大多数是「没变」→ 于是把那份旧缓存原样返回 ↓ 前端拿到 → 和手上那份一样 → 界面根本不用变

要害：宿主在交出手上那份数据之前，非要先把联网核对做完。「取数据」和「把数据交出去」被绑成了一件事。

3.1 你设想的流程，我们做到哪一步了

你提的是：先读磁盘缓存 → 放到内存缓存 → 请求网络 → 网络回来更新内存 → 再更新磁盘。逐条对照：

你设想的步骤现状说明

放到内存缓存有宿主与前端各有内存表
只读缓存就返回给前端缺必须先 await 联网核对，才肯返回

再更新磁盘有重建后写盘

你设想的那套流程，我们只缺其中一步：「先把手上的缓存交出去，核对放后台」。其余六步全都有，而且都在正常工作。

5 · 你的三个问题

Q1为什么要把缓存标记为「脏」？这样发现新数据和老数据没区别，岂不是有问题？

先纠正一个误解：标脏不是「把新数据当成旧数据」，恰恰相反——它是为了区分新老。

这里有个绕不开的硬约束：宿主没法自己去重画界面，那是前端的事。所以探测器发现「远端变了」之后，它唯一能做的就是留下一个记号，说：我这份缓存可能过期了。等界面下次来取时，看到这个记号就会去重新拿一份。

标脏是「作废通知」，不是「数据内容」。

用生活里的例子说：

这就像冰箱上贴的一张便签，写着「牛奶可能过期了」。便签本身不是牛奶，它也不会把新鲜牛奶变成过期的。它的作用是：你下次打开冰箱时，会想起来看一眼日期。

如果没有这张便签，你会以为冰箱里那盒是刚买的，直接喝了。

「发现新数据和老数据没区别」这个担心其实点到了真问题，但方向反了：真正的情况是——标脏让两者有了区别。有记号 = 这份可能旧了，去重拿；没记号 = 这是新鲜的，直接用。

你说的「岂不是有问题」，暴露的是另一件真事：如果只依赖标脏，而标脏这一步本身失败了（网络断了、限流了），那记号就永远不会被贴上，界面就会一直以为手上那份是新鲜的。这正是我下面决定一担心的事。

Q2决定一里的「校验／核对」是在做什么？

核对 = 问 GitHub 一句「自上次以来，这个仓库的票有没有变化」，然后拿答案和手上那份比。

它拿不到任何新数据，只回答一个问题：变没变。

为什么要有它：面板上显示的是快照。这份快照可能是几分钟前生成的。直接给用户看，用户可能在看过期的东西。所以宿主想先确认一句「还是最新的吗」，是的话就直接用，不是的话就去重建。

问题在于：核对这件事，本身就贵得离谱。

你这个仓库有 505 条票。核对要把它们整个扫一遍才能回答「变没变」。所以出现了荒谬的局面——

花 4.4 秒去核对，核对完的答案是「没变」，然后把手上那份原样还给界面。这 4.4 秒什么都没换来。

这正是本次卡顿的全部来源。而第一笔修复做的事就是：把「整个扫一遍」换成「只问变了什么」，于是同样的核对从 4.4 秒降到 1 秒上下。

Q3「探测一直失败会无限期显示旧数据」——我认为没问题：都拿不到新数据了，不显示旧的还能怎么办？

你说得对，是我那句表述有问题。

拿不到新数据的时候，显示旧的确实是对的。空白或者报错都比旧数据更糟——你连历史都看不到了。这一点你的判断没有错，我接受。

我真正担心的不是「显示旧的」，而是「显示旧的、同时让用户以为它是最新的」。

能看到内容用户会不会被误导评价
空白／报错看不到不会体验最差
旧数据 + 不说明看得到会。他会以为看到的是最新的最危险
旧数据 + 标明「未核对」看得到不会最佳

所以差别不是「能不能看」，而是「用户会不会基于过期信息做决定」。比如你看到某张票还是「可接」，于是点了开始，结果它其实已经被别人认领了——这类误判才是我想避免的。

结论：你的核心判断（宁可显示旧的）我完全接受，只需要加一件事——把「这份没核对上」说出来，而不是安静地当成最新的。

6 · 三个待定决策

先说这三件事的共同点：决定一和二是这次改动的安全前提——没有它们，「先返回」会引入一个安静出错的故障。决定三是后台成本，不挡你，可以晚点再说。

1校验长期失败时，要不要设个上限？

要解决的问题：如果改成「先返回、核对放后台」，而核对一直失败（断网、限流），那份缓存就永远不会被判过期，界面会一直显示旧数据。

选项 A：设上限（例如 5 分钟）
  • 超过上限就明确标出「这份没能核对」，不会安静地骗人
  • 行为可预测、好排查
  • 要多一个计时状态，代码多一点点
选项 B：不设上限，一直用旧的
  • 实现最省事
  • 永远不会因为「太旧」而打扰用户
  • 故障时是安静地给旧数据，最难查
  • 用户无从知道手上的数据是三分钟前还是三小时前
选 A，上限用 5 分钟。代价极小（一个计时状态），换来的是「故障时不会安静骗人」。
5 分钟这个量级怎么来的：手动刷新随时可用，你随时能自己触发一次真拿数据；而 5 分钟远小于「会让人误判」的尺度，又足够长到不会因为一次网络抖动就跳出提示。

2要不要让用户看见「这份数据没核对上」？

选项 A：可见（在面板上标出来）
  • 用户能区分「看到的就是最新的」和「这是旧的」
  • 面板里本来就有新鲜度状态位，不用新造
  • 多一个视觉元素
选项 B：完全透明，什么都不显示
  • 界面干净
  • 你无法判断手上的数据是不是最新的
  • 配合决策一，等于白设了上限
选 A，但要克制：只在「确实没核对上」时显示，正常情况一个字都不加。
理由：平时不打扰，出问题时你看得见。这样它才不会变成常驻噪音。

3后台每 15 秒一趟的全量扫描，要不要一起收？

选项 A：一起收（短时间内的重复核对复用同一份结果）
  • 省时间、省 GitHub 配额
  • 动的是探测那条路，与本次卡顿无关，属于扩大改动范围
  • 一旦写错，影响的是「发现变化」这条正确性链路
选项 B：先不动，单独观察
  • 本次改动的风险面保持最小
  • 它不挡界面，不影响你的体感
  • 配额与后台开销继续存在
选 B，先不动。先把面板这条路的收益拿稳，再单独谈后台优化。
一次只改一件、单独验证，是这次能把根因找准的原因。上一次我同时怀疑三个方向（渲染、状态栏、数据），结果两处猜错了。

7 · 如果按推荐走，我会怎么做

核心改动（一处）：面板数据这条通话，在「手上有缓存」那条分支上，立刻返回，把核对挪到后台。

  • 前端拿到就画 → 秒开
  • 后台核对若发现真的变了 → 走既有的静默重建链（这条链已经存在，而且我给它补过留痕）
  • 核对长期失败 → 按决定一的上限标记出来（决定二决定它可不可见）

为什么这是安全的（我自己先挑过刺）：

  • 你机器上本来就有一条每 60 秒的自动探测负责发现变化。改成「先返回」之后，最坏是显示最多 60 秒前的数据——而这正是这套设计原本就已接受的容忍度。没有降低任何保证，只是把「用户要等」换成「用户先看旧的」。
  • 唯一的风险就是决定一那个洞：核对一直失败会安静地用旧数据。堵上它需要决定一与决定二。

配套：给这条改动配门禁（断言「有缓存时必须先返回，不许 await 核对」），避免以后有人改回去。这次的两笔改动都配了门禁，共 38 项断言。

预期收益，以及它可能达不到的地方：

第二次重启后实测，你有货的那条路应该从 4.4 秒 降到 接近 0。

但如果你的体感里，那 7~8 秒大部分是「手上真的什么都没有、必须去拿」（比如刚重启、内存和磁盘都空），那部分属于硬成本，这次改动帮不上——那种情况要靠第二笔修复（重启后立起点）去把「整扫」变成「只问增量」。两笔是一套，缺一不可。
