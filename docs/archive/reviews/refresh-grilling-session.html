第一部分背景：这些问题为什么会被问出来

不铺垫前情，后面的问题会像天书。这一节用大白话把来龙去脉说清，三分钟读完。

为什么"刷新"这件事值得这么大费周章

  • 有两只独立的额度桶，各 5000/小时，而且跟你的 AI 共用同一份额度。一只按"请求次数"算（REST），一只按"点数"算（GraphQL）。插件多花的每一次，都是你的 AI 少掉的每一次。
  • 你同时开着很多工作区（十个量级），但同一时刻只有一块屏幕在亮。旧的做法是"每个工作区都定时去问远端有没有变"，等于把九成的预算花在你看不见的地方。十个工作区、环境检查还没做完的情况下，最坏能烧到 5000 的 4.9 倍。
  • 现在每次"重建"一次面板数据要 25 点，因为它把每张票的正文和 50 条评论一起拖了回来——而列表要画一行，一个字都用不到它们。

那份定稿架构做了什么（一句话版）

界面只说一件事——"我在看哪个工作区"；宿主据此把工作区分成"正在看的"（有节拍）和"其余的"（一次都不发，切回来才补）；所有去 GitHub 的调用都从同一道闸过，闸把请求分成"用户动作（永远放行）／生命周期（切进来那一次）／后台（超出预算就推迟，不失败）"，并且每小时最多用掉剩余额度的 35%，剩下的留给你的 AI。

你问的三个场景，各自炸出了什么

场景结论暴露的缺口
一、会话里 close 一张票，面板要立刻变 定稿当时只能做到最坏 90 秒 真缺口文档只从"预算"倒推节拍（30 秒探测、60 秒合并），从没为"你写完东西多久看到"定过目标。补法是两个：只补变的那几条行（1~2 点，而不是整池 13 点）+ 变化探测加快。
二、一直切来切去会不会堆积请求 不会堆积，全局在途请求有硬上限（≤4 个） 两处要钉紧强制刷新今天不进"在途合并"表（狂切会各发一份）；额度紧张时可能出现"永远旧下去"且没有出口。
三、父子工作区来回切，数据能不能复用 能，而且是全链路复用 基本没有缺口。只有一个边界：工作区"根"还没识别出来之前先切进去，会多建一个桶。

"父子工作区"指的是同一个 git 根下的两个会话（仓库根 + 子目录）：插件认的是"根"，所以它们天然是同一个工作区、同一份缓存、同一个探测节拍——来回切零请求、秒显。

为什么要专门查"插件能不能看见 agent 写操作"

因为"close 完立刻看到"这件事，理想情况下不该靠"每几秒去问一次"，而该靠"你写的那一刻我就知道"。如果插件能在 agent 执行 gh issue close 的瞬间收到通知，那次刷新就是零延迟、零浪费。所以这个问题决定了体验能做到"2 秒"还是只能做到"5 秒"。

第二部分术语表：后面会反复出现的几个词

词大白话解释
探测花 1 次请求问一句"这个仓库自上次以来有没有变化"。便宜、不带内容。
整池重建把整个仓库的票重新拉一遍（现在 25 点、改造后 13 点）。贵，但一次到位。
行级增量只把"变了的那几条"重新拉回来，合并进现有列表。1~2 点，快。本次要新增的机制。

闸所有去 GitHub 的调用都要过的唯一一道门。它分类、记账、决定"放行 / 降级 / 推迟"。
档位（绿黄红）额度用得少叫绿（正常跑）、用到六成转黄（放慢）、八成五或撞过限流转红（自动刷新全停，只留你手动）。
写事件"刚刚有一次写操作发生了"这条通知。拿到它 = 不用等探测就知道要刷新。

tool/call上面那条广播里的一类事件：模型调用了哪个工具、参数是什么。对执行命令的工具，参数里就带着那行命令。
presetDSH 里"会话以哪套能力启动"。不同的 preset 会改变工具调用的形态，这会影响我们能看见什么。

第三部分三路事实核查：查到了什么

这三路都是只读调查（没有修改任何代码），每条结论都标了出处。命令只在侧边栏终端里跑过只读的 git 查询与读文件。

第一路：插件今天能看见什么

问题结论证据
插件能看见 agent 在会话里跑的 gh 命令吗 从来没有过。它只看得见"自己启动的 gh"（六处进程入口），没有会话内容读取，也没有文件监听。 src/host/repoKeys.js:28,46,105、platformChannel.js:190、platform/index.js:138；仓库里早有同结论：docs/research/session-rename-failure-paths.md:5,10
那"写后事件"（gh-create 等词汇）是谁产生的 是插件自己跑写命令时记的（比如面板里的认领），不是 agent。而且这条链已经在 #345 被整块删除（提交 6c51e71，13 个文件 +54/−606）。 src/shared/tracker/sync.js:23-26（词汇表今天无生产者）；tests/verify-issue232-sync.js:95,114-116 直接断言那条路不存在
插件今天从 DSH 拿到什么 宿主侧：subprocess / timer / fs / sessions / platform / connection 等服务，加一个自建的"电话簿"（约 38 条 wf.*）。客户端侧：面板槽位、状态栏、语言、工作区列表。 src/host/index.js:18,20-35、package/package.json:13,18-23,48-57

第二路：DSH 给插件的能力（这条是好消息）

  • 能注册工具：注册之后模型就能看见并调用（harness.defineTool + harness.registerTool，或普通插件的 ctx.tools.register）。证据：dsh-cordis-host-runner/lib/types/sandbox.js:28-35,117-133、guard.js:560-563。
  • 能订阅会话事件：ctx.on('session/event', (session, event) => …)。事件类型有 56 种（本机 2.0.10 这一版；此前写 57 是旧数），含 tool/call（模型调了哪个工具）、tool/result（结果）、command/run（人打的斜杠命令）等。证据：dsh-tool-cordis/lib/index.js:5412-5425、第一方先例 dsh-session/lib/types/invariant.js:176-184。
  • 能拦、能包，但不能改写命令：tools/pre-execute（放行/拒绝/询问）、tools/execute（包住派发）、tools/post-execute（改结果）——但明确不允许改写命令参数（dsh-tools/README.zh.md:224）。也就是说"把裸 gh 偷偷换成我们的工具"做不到，只能"要么放行、要么拒绝"。
  • 人类打的斜杠命令拦不住：只有跑完之后的事件日志（command/run / command/done）。
  • 顺带发现：我们的宿主侧自建了一个 const harness 遮蔽了 DSH 注入的真 harness，对外走自建的 /api/dsws 通道（src/host/index.js:29-35、rpcChannel.js:90-113）。要用原生能力不必碰这条通道——订阅和注册都通过 ctx。

第三路：我们这种插件到底能不能真订到事件（结论：能，但要实测）

  • 事件对所有会话都播：真播点在"会话每追加一条事件"那里（dsh-session/lib/index.js:1195-1202），与"是不是某个 preset"无关。子代理的写操作也走同一个存储，所以我们一样看得见。
  • 我们的插件拿到的是普通 Cordis 上下文，on 没被冻结也没被包装（加载路径：dsh-app-boot/lib/index.js:862-877 → cordis-plugin-loader/lib/index.js:537 → cordis/lib/index.js:1053,1070）。第一方在同类位置订阅会话事件的先例有好几个。
  • 订阅时建议显式写 { global: true }：未打作用域标的监听器本来就全局放行，写上更稳（dsh-scope/lib/index.js:327-338 的 332 行）。
  • 事件里带什么：tool/call 带工具名与参数，参数是模型给的原始 JSON 串——JSON.parse(arguments).command 就是那行命令，够认出 gh issue close。成功与否看 tool/result 的 message.content[0].isError；结构化退出码不在 session/event 里（只在正文文本的 [exit code: N]），要结构化得改用 tools/result 事件的 result.value.exitCode。
  • 注意别用错事件：command/run 是人打的斜杠命令，不是 shell 命令，不能拿来认 gh。

必须实测才能确认的六件事

  1. 运行期我们的上下文是否确实未打作用域标、监听器是否真的被调用（读代码只能证明"未打标就放行"）。
  2. { global: true } 到底必需不必需（依赖上一条）。
  3. 运行时生效的是哪个 profile（web 还是 desktop）与哪个 preset；若是 ptc，内层工具调用会以另一种形态送达，只订 tool/call 会漏。（2026-09-24 已查清：跑的是 Web 系档案，预设默认 standard；但进程级环境变量 DSH_TOOLS_MODE=ptc 会让 standard 会话也变内层形态。见 research/dsh-platform-facts-2026-09-23.md）
  4. Windows 上实际生效的 shell 工具叫 bash 还是 pwsh（读代码推不出）。（2026-09-24 已查清：是 pwsh，bash 那一行在 win32 上被显式关掉）
  5. 插件加载之前发生的历史事件收不到（事件是即时推送），补历史只能读会话日志。（2026-09-24 已查清补课接口：ctx.sessionQuery 的 listSessions() 与 readSession(id)，读取不会把会话变活）
  6. 子代理会话的工具调用是否真被我们看见（代码路径指向同一个存储，但属结构性推断）。

2026-09-24 补记：上面这六件事里，第三、四、五条已经查清（读 DSH 安装目录的打包代码得出，证据见 research/dsh-platform-facts-2026-09-23.md，对应票据 #717）。第三、四条的结论与这份记录里的说法一致，第五条补上了具体接口。另外查出两处需要更正的说法：会话事件里叫 tool/result（单数），tools/result 是另一套 Cordis 运行时事件（它反而是更省事的订阅点，一次给全工具名、已解析参数与结构化结果）；本机这一版会话事件共 56 条，不是 57 条。还剩第一、二、六条要在插件落地时实测。

A 组 · 目标与节拍（Q1–Q6）

Q1

"及时"到底写几秒，以及为它常态花多少额度

问什么

(A) 常态探测 5 秒一次（每小时 720 条 REST，占 REST 配额 14%），目标写成"别处发生变化 ≤10 秒落到界面"；(B) 常态 15 秒、只有你刚写过东西后的 60 秒内加速到 5 秒（每小时约 240 条，5%），目标只能写"≤20 秒"。

为什么

目标延迟一旦写进文档，就决定了常态探测频率——两者是同一件事。差别只体现在"别人（你的 AI、网页、手机）改的那张票，多久出现在你眼前"。

推荐

选 A。额度账算得过来（REST 14% + 行级增量后 GraphQL 约 4%，闸是 35%），而"及时"是你这次的第一诉求；B 省下的额度换来的正是你最不想要的那种迟钝。

答完解锁

探测节拍、闸的份额分配、以及"体验目标"那一节的所有数字。

Q2

额度紧张（红档）时，你亲手写的那一次要不要也停

问什么

牺牲顺序是"先降别处变化的灵敏度 → 再降后台对账 → 最后才动本地写入的即时性"。但"最后动"有两种解释：① 永不降档——给"用户写入触发的刷新"留固定 10% 保底额度（500 点），红档也照做；② 红档全停，连你刚写的也不刷，等你手动点。

为什么

这决定"额度用完时这个面板还有没有用"。

推荐

选 ①。你亲手做的动作看不到结果，这个面板就失去存在意义。500 点按整池重换算约每小时 38 次、按行级补行算几百次，足够。

答完解锁

闸的保底份额与降档顺序的写法。

Q3

整池重建还剩哪些用途；切进工作区要不要做一次对账

问什么

有行级增量之后，整池重建只剩"冷启动"和"对账"。对账触发条件：① 定时兜底（10 分钟一次）；② 数量与计数对不上；③ 出现没见过的票号、或有票号消失；④ 每次切进工作区都做一次。

为什么

④ 是唯一有代价的：做了最稳（能发现"票被删掉"这种增量看不见的事），代价是每次切开一个工作区最多 13 点。

推荐

①②③ 都做，④ 不做。切进来只做"一次探测 + 补变的那几条"（最坏 1~2 点，秒开），"票被删了"交给 10 分钟兜底。

答完解锁

行级增量与整池对账的分工、切工作区的最坏花费。

Q4

写入之后、数据回来之前的那一秒，界面显示什么

问什么

① 什么都不显示（可能让人以为没点到，重复操作）；② 给那一行加一个"更新中"的淡标记，不改状态；③ 先按你的意图把那行画成新状态，等远端确认。

为什么

仓库既有纪律是"不做乐观更新"（动作不承诺结果）。③ 直接违背它。

推荐

选 ②。不违背纪律，又让你知道点到了。③ 明确否决——那是"面板说已关闭、其实没关"这类谎话的来源。

答完解锁

界面在写入窗口期的表现。

Q5

切回一个后台工作区：先出旧数据，还是等新的

问什么

① 先用手上那份旧数据铺满（≤100 毫秒）+ 标"更新中" + ≤5 秒补齐；② 显示加载态，等新的到了再画。

为什么

"切工作区"是你最高频的动作；两条路的差别是"秒开但可能先看到旧数据"还是"绝不显示旧数据但每次都慢一下"。

推荐

选 ①。秒开比"绝不显示旧数据"重要得多；旧数据配一个诚实标记就够了。

答完解锁

切换时的界面行为与"更新中"标记的用法。

Q6

文档形态与范围

问什么

定稿要新增两章（体验目标与降档顺序、行级增量刷新）、一节（前提与待确认项）、以及落地清单与门禁。做成一份单页，还是拆成"架构"与"落地规格"两份？

推荐

一份单页。门禁清单必须跟架构规则放在一起读——规则和它的自动检查一旦分开，迟早对不上，而这次整套设计的价值恰恰在于"规则有自动检查兜着"。

文档改稿的结构。

B 组 · 看见写操作（Q7–Q9）

Q7

"看见 agent 写操作"是必须满足的前提，还是可选的加速项

问什么

最坏情况下（平台不给事件、也不给注册工具），能不能接受定稿的最终形态是"agent 写的票最多 5 秒被探测发现"？另一个选项是把它当必须满足的前提——平台不给就改用"把 gh 包一层、要求 agent 必须走我们的工具"来换取"看得见"。

为什么

这决定定稿是"自己就能成立"还是"吊在一个外部能力上"。

推荐

把"≤5 秒探测发现"做成定稿自身的能力（不依赖平台），把"看得见写操作"当成可选加速项（有就 ≤2 秒）。任何"必须经过我们的工具"的强约束，只要被绕过一次（你自己开终端、换个 agent、手机上改），面板就会静默过期——而那正是这次要根治的病。

答完解锁

"前提"那一节怎么写，以及它跟平台能力的关系。

Q8

要不要明说"不复活 #345 删掉的那条路"

问什么

#345 删掉的 issuePath 链（状态栏胶囊 + 提及识别 + 4 秒轮询 + 事件队列）与本次要做的事不是同一件——那张票关心的是"给我看这张票的链接"，我们要的是"远端变了要刷新"。但实现的人翻开 sync.js 会看到同一套词汇，很可能误以为该把它复活。

推荐

写一句明确的边界：本次重建的是"写后刷新"，与 issuePath 那条路无关，旧链的删除维持现状。

答完解锁

落地清单里"别碰什么"的说明。

Q9

合同层那批"有常量没人产生"的死词汇怎么处置

问什么

sync.js 的四个事件源常量今天没有任何生产者（只有测试引用），日志契约文档里两条 issuePath.* 事件的落点也已不存在。① 一并删干净（常量、文档表、测试断言）；② 保留词汇表，由新架构接管命名；③ 先不动。

推荐

答完解锁

落地清单里"清理项"的范围。

C 组 · 机制选择（Q10–Q13）

Q10

"看见写操作"走哪条路

问什么

(A) 订阅会话事件，从工具调用参数里认出 gh 写命令（被动、不需要任何一方配合、不改变 agent 的工作方式）；(B) 注册我们自己的 gh 读写工具，让 agent 走它（主动，但靠提示词纪律，绕过就看不见）；(C) 加一道守卫，拒绝裸 gh 写命令，逼 agent 走我们的工具（最强也最侵入，而且不能改写命令，只能放行/拒绝/询问）。

为什么

平台三条路都能走（证据见第三部分），所以这是纯取舍。

推荐

只做 A，B 留作以后有明确需求时的可选加速项，明确否决 C。A 不需要任何人配合；C 会把插件变成"必须经过的关卡"——一旦换 preset、换 agent、或你在终端里直接跑，它要么炸要么形同虚设，而且它连人类斜杠命令都拦不住。代价要认：A 是尽力而为的加速项（脚本里绕一层就认不出），所以探测兜底不能取消。

答完解锁

落地清单里"写事件源"的形态。

Q11

认哪些算"可能改变了远端"

问什么

① 只认 gh 的写子命令；② 再加 git push；③ 再加我们自己的工具调用；④ 成功判定：命令一发出就刷新，还是只认成功（看 tool/result）？

推荐

①②③ 都认，并且只认成功。命令发出就刷会在命令失败时白花一次重建；等结果是零成本（都在同一条本地事件流里）。

答完解锁

Q12

"能订到会话事件"要不要先实测再写进定稿

问什么

机制证据齐了，但我们的插件（bundle 形态）实际能不能收到事件没有实测过。定稿里写成"待确认的未知依赖"，还是"已确认的前提 + 落地第一步就验"？

推荐

写成后者：定稿的底线能力仍是不依赖平台的那条（≤5 秒探测），事件命中时升级到 ≤2 秒。这样即使实测不通，架构一个字都不用改，只是少了一格加速。

Q13

要不要顺势改回 DSH 原生链路

问什么

我们的宿主侧今天遮蔽了真的 harness、走自建的 /api/dsws 通道。要用原生能力，是否顺手把整条跨进程通话链路换回原生？

推荐

不换。订阅事件用 ctx.on、注册工具用 ctx.tools.register，两者都通过 ctx，与通道无关；为了一个加速项去翻新整条通话链路，风险远大于收益。

D 组 · 覆盖范围（Q14–Q15）

Q14

订阅范围与用法

问什么

事件免费（纯本地，不花配额），所以可以订所有会话：(a) 只订当前活跃工作区的会话——事件只用于"立即刷新"；(b) 订所有会话——活跃的立即刷新，后台的只标脏、不取数（切回来时优先取数）。

推荐

选 (b)。它不花配额、不违反"后台不烧钱"（标脏是零成本的本地状态），但把"切回一个刚被 AI 改过的工作区"从"先旧数据、5 秒后补齐"变成"先旧数据、立刻补齐"。

答完解锁

订阅的注册范围与"脏标记"的用法。

Q15

要不要把覆盖面做到最大

问什么

只订 tool/call 会漏两种情形：跑 ptc preset 时（形态是另一种事件）、以及拿不到结构化退出码时。(a) 只订 tool/call，命中即刷；(b) 订三种事件（tool/call + 内层派发 + tools/result），合并判定，并用结构化退出码判断成功；(c) 只订两种工具调用，不看成功与否。

推荐

选 (b)。判定逻辑稍复杂（三种形态归一到同一个"看到一次写操作"的结论），但换来"不管你跑哪种 preset、不管命令是 bash 还是 pwsh，插件都看得见"，而且不会在命令失败时白花一次重建。
2026-09-24 补记（读源码所得）：还有一条更省事的路——只订运行时事件 tools/result 这一条，它同时覆盖原生调用与 ptc 内层派发，且直接给出工具名、已解析的参数对象、是否出错与结构化结果；代价是它不落盘、插件加载之前的调用收不到。另外更正：会话事件里叫 tool/result，tools/result 是 Cordis 运行时事件，两者不是同一个东西。落地时在 (b) 与这条之间定。见 research/dsh-platform-facts-2026-09-23.md。

答完解锁
