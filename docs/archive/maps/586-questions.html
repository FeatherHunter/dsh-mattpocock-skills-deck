4需要你拍板的问题

问题一 新包怎么送进插件？（这就是「切引用」的具体做法）

为什么必须定这件事

「切引用」这句话落到代码上就一行：插件从「自己源码里的旧更新代码」改成「引用新包」。 但 新包从哪来、以什么形式被插件拿到，有三条完全不同的路，三条路各自的 「今天能验到什么」和「会不会做不可逆的事」差很多。

牵扯到的两个硬约束：

  • 打包白名单：插件发布时只带 lib / shared / cordis.patch.yml / bundled-skills / scripts/。 别人装了插件以后，插件要能 import 到新包——所以新包必须真的存在于 「插件所在的使用范围」里，不能只存在于我的开发目录。
  • 运行版本是反查出来的：新包靠「反查目标包名所在的包目录」来确定 「当前跑的是哪个版本」。如果新包是从开发目录链进去的，它可能在你的仓库里找到那份清单， 而不是使用范围里那份——这会直接影响「有没有新版 / 能不能装」的判断。
关键信息：发布这条路今天卡在哪
发布需要 npm 登录态。我刚查过：npm whoami 失败，本机 ~/.npmrc 里 npmjs.org 的令牌是打码状态、用不上。也就是说选 A 的话，你得先 npm login 一次， 我才能真的发出去。
A 真的发布到 npm，然后插件按版本号依赖它 最接近票面原意

把 dsh-plugin-update@0.1.0 发到官方源，插件根目录 package.json 里加一条 "dsh-plugin-update": "0.1.0"，重新装进使用范围。之后任何人装这个插件， 更新能力都来自 npm 上那个包。

利
  • 票面原话（切引用、发布前复查包名、回滚即 git 回退）得到完全满足
  • 「别人装这个插件能得到完整更新能力」当场成立，不是将来才成立
  • 网页端的 npm 侧验证是真实安装，不是本地假装
  • 包名当场占住，不用再担心被抢注
弊 / 代价
  • 发布是不可逆的公开动作：0.1.0 一旦发出去就在 npm 上留下永久的版本记录
  • 今天需要你先 npm login，多一道人工前置
  • 0.1.0 是「还没被任何真实宿主用过」的初版，先发后用，风险顺序不理想
  • 发出去后如果包内有缺陷，只能发 0.1.1 修，不能撤版本
B 先用工作区链接（workspace / link）接上，发布留作明确的发布步骤 推荐

插件 package.json 里把它指到本仓的 packages/dsh-plugin-update，让它在使用范围里以真实包的形式存在、能被 import 到、能被反查到。今天不发任何东西；等你决定发布时，把这条链接改成 确切版本号再发一次插件版本即可。

利
  • 今天零不可逆动作，你不用先登录，我可以一口气做完并验证
  • 双宿主都能真跑：新包真的在使用范围里被 import 到，不是假件
  • 零变化证明更干净——代码换了，但行为和发布物形态都没有额外变量
  • 先验后用：等真机验过再发布，风险顺序正确
  • 回滚依然只是 git 回退一条
弊 / 代价
  • 「别人装插件就有更新能力」这件事要等发布才成立，本票只能验到「本机可用」
  • 多一条待办（发布 + 改回版本号），需要一个明确的发布动作收口，否则容易忘
  • 链接形态下，运行版本反查指向开发目录的行为需要我专门断言，我会补一条门禁覆盖它
C 把新包编译产物拷进插件源码树，完全不依赖 npm 我判断不该选

把新包 dist 下的文件复制进插件仓库当成自己的源码，插件不带任何依赖。

利
  • 没有任何外部依赖，安装最不容易出岔子
弊 / 代价
  • 直接否掉整张地图的目的：地图要的就是「抽成独立包、别人能复用」，拷一份就等于回到原点
  • 两份副本长期漂移，以后修 bug 要改两处
  • 第二家插件没有可依赖的对象，集成文档也随之作废
为什么我推荐 B 而不是 A（想看我的推理就展开）

两条路最终都会走到同一个终点（插件按版本号依赖 npm 上的新包），区别只在顺序。 A 是「先公开、再验证」，B 是「先验证、再公开」。而这一票的全部意义就是验证—— 把包先发出去，反而让「零变化」这件事多背了一个不可逆的变量：万一真机点按暴露了问题， 代码能 git 回退，npm 上那个版本却回不来了。

反过来，B 的代价只是「一条待办」：发布。而这条待办本来就属于地图里明确的发布环节， 不会丢。所以顺序风险低、代价小的是 B。

如果你更看重「本票结束即对外可用」，那就选 A，我照做，只是需要你先登录一次 npm。

问题二 「零变化」要不要连面板（客户端那一半）一起改？

为什么会有这个问题

新包有两个入口：宿主侧入口（插件后端调用）和客户端入口 （面板界面那一半调用）。客户端入口里装着「电话名怎么拼」「轮询间隔是多少」 「手工兜底命令长什么样」这几样东西，供面板照着用。

现在面板 SettingsPage.js 里是硬编码的：三个电话名 wf.updateStatus / wf.updateCheck / wf.updateInstall， 以及每秒一次（1000 毫秒）的轮询间隔。

而新包自己的客户端入口注释里明确写着：本仓当前插件这一次不切拼接源， 默认前缀 wf 下行为零变化，拼接形态留给第二个插件验证。

所以问题其实是
「零变化」的证明范围，是只包到宿主侧（后端），还是连面板（前端）也一起换成新包推导出来的值？ 两边取值完全一样（wf.* 与 1000 毫秒都不变），区别在改不改代码。
A 面板这一票不动：电话名与轮询间隔保持原样 推荐

面板代码一行不改，仍写 wf.* 与 1000 毫秒。理由不只是省事： 这一票的证明题是「换了包，行为零变化」，面板不动，客户端这一半就真的是字节级零变化， 没有「改了但值一样」这种需要解释的地方。

强化面板的活本来就排在下一票 #587（它阻塞于本票，票面写着「迁后做，不污染零变化证明」）。 到那一票再把面板接到新包客户端入口上，顺手把弹窗和待重启横幅一起做掉，是同一处代码只动一次。

利
  • 零变化证明最干净：客户端零改动，无可争议
  • 与新包自己的注释、与 #587 的排期都一致
  • 本票改动面小，红了的门禁更容易判断是谁引起的
弊 / 代价
  • 严格说「客户端入口」在这一票没被真实使用过，只能说被文档和测试覆盖
  • 新包的客户端入口要到 #587 才第一次真正上岗
B 面板也一起改：电话名与轮询间隔改从新包推导 更彻底，但改动面更大

把面板里的硬编码电话名和 1000 毫秒改成「从新包客户端入口取」，取值保持不变， 于是「切换引用」这件事在前端后端都真的发生了一遍。

利
  • 「切引用」覆盖完整，两个入口都被真实使用
  • 以后改前缀或轮询间隔只改一处
弊 / 代价
  • 改动落进 SettingsPage.js，会牵动断言「每秒轮询」「电话名写在客户端」的现成面板门禁， 需要同步改门禁，而改门禁本身就是「零变化证明」里最容易被质疑的一步
  • 与 #587 要做的事重叠：同一段面板代码两票各动一次
  • 与新包客户端入口自己写的「本次不切」注释相矛盾
如果你选 B，我会怎么把风险压住（展开看）
  • 只替换取值来源，不改任何取值：电话名仍是 wf.*，轮询仍是 1000 毫秒，逐项断言相等
  • 门禁的修改单独成一个提交，并写清「改的是取值来源的断言，不是行为断言」
  • 面板行为相关的断言（每秒轮询、只在安装中轮询、清理只停定时器）保持原样不动
