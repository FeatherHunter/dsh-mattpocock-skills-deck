地图 503：GitHub 后端拉取请求入口实现

这份手册只讲一件事：在主线版本上，如何一步一步确认拉取请求页签真的做好了。拉取请求就是别人在 GitHub 上请求把代码合并进来的那张单子。

整份手册分三层。第一层是机器自动检查，第二层是不联网的内存桩检查，第三层是连真实仓库的人工目视检查。三层都通过，才算验收通过。

第一层：全链自动门禁（机器替你跑完所有检查）

这一层的目标是：只记一条命令，机器把所有检查跑完，退出码是 0 就算通过。如果中间某一步变红，不要急着改功能，先按每一步下面的“不绿先补什么”去补。

第 1 步：跑全链检查，退出码必须是 0
全链检查就是把仓库里所有的自动检查按顺序跑一遍。退出码 0 表示全部通过，非 0 表示至少有一处失败。
npm run verify
通过标准：命令从头跑到尾不停下，最后退出码是 0，屏幕上没有出现 FAIL 或者“存在失败”字样。
日志追溯：屏幕输出本身就是证据。失败时会打印是哪个检查文件失败，例如 tests 开头的某个检查文件名。
不绿先补什么：先看是第几步失败，就去看下面对应的那一步说明，不要直接改业务代码。
第 2 步：契约检查，525 项通过加 4 项预期失败
契约检查是确认工单形状没有被写坏的检查。工单就是跟踪系统里的一张票，拉取请求复用了工单的形状，只是多了三个可选字段。
node tests/verify-tracker-contract.js
通过标准：最后一行显示 525 项通过，4 项失败，并且最后一行写“骨架自洽”。这 4 项失败是故意放进去的坏例子，用来证明检查真的能抓住坏数据，不是摆设。
日志追溯：坏例子都以 violating 开头。好例子以 compliant、demo、github、gitlab 开头。拉取请求相关的好例子包含是否拉取请求、合并时间、评审细分三个字段。
不绿先补什么：如果通过数少于 525，先看是不是改了工单形状文件而没有同步改检查；如果 4 项预期失败变成了通过，说明检查被绕过了，先把检查恢复原样。
第 3 步：GitHub 房间拉取请求专项，40 项全绿
房间是指负责和某一种后端打交道的代码分组。这里是 GitHub 房间，负责把 GitHub 的拉取请求数据拿回来并整理成统一形状。

日志追溯：降级相关的日志事件名是 graphql.fallback、issues.fallback、fallback.chain。坏节点计数复用已有的调试事件 error.normalize，不新增事件。
不绿先补什么：先补注释和分类函数。常见原因是查询片段里多写了父子边或者阻塞边，或者失败原因没有分成通用、超时、限流、企业版主机四类。先把注释写诚实，再谈数据对不对。

第 10 步：指纹反查（看到日志能找回是哪一步）
指纹就是日志里用来证明走过哪条路的固定事件名和字段。反查就是拿着日志去附录里找到对应的编号。
反查路径：先打开 research 目录下的 489-appendix.md 第 1 章对照表，再去本地诊断日志里搜事件名。
本层用到的指纹：双路降级用 graphql.fallback、issues.fallback、fallback.chain；快照三态用 snapshot.cache.miss；界面、只读、空态三组复用快照链路，不新增事件；契约组是纯形状，没有日志。
通过标准：每个失败现场都能在日志里找到对应的原因枚举和通道名，数字和附录对得上。
第 11 步：脱敏要求（日志里不许出现隐私原文）
脱敏就是只记能定位问题的最少量信息，不记隐私原文。
只允许记：失败原因枚举、通道名字、计数、算出来的短指纹。一律不记：令牌原文、登录状态原文、工作区原始路径、仓库地址原文、标题原文。标题太长只留前一段并注明已截断。检查方法是把日志字段转成文本后搜令牌形状和路径形状，搜不到才算通过。
通过标准：离线桩里的 B3 用例通过，即转成文本后没有令牌形状和路径形状。
不绿先补什么：先找到是哪个日志点把原文带进去了，把那个字段换成枚举或者短指纹，再重跑 B3。

docs/prototype/293-pr-tab-dynamic.html

第 13 步：显隐验收（有能力才显示页签）
只有后端返回了拉取请求能力，才显示拉取请求页签，不是写死后端名字。
通过标准：选 GitHub 时有拉取请求页签；切到 GitLab 或者本地 Markdown 时页签消失；如果当时正停在拉取请求页，要自动回到列表页；切回 GitHub 时恢复。
不绿先补什么：先查页签显隐是不是只读能力标记，有没有误写后端名字。
第 14 步：折叠验收（窄屏时按优先级收起）
折叠是指面板变窄时，页签从文字收成纯图标，不换行，不出现横向滚动条。
通过标准：把宽度从 640 拖到 280，页签按优先级从大到小逐个收起。优先级是列表 4、拉取请求页签 5、技能 6、环境检查 7。动作按钮最后才收。拖回宽屏时逐个恢复。
不绿先补什么：先查页签组装是不是复用了统一的折叠机器，有没有单独写一套。
第 15 步：空态与失败态验收（入口永远保留）
空态是指没有数据时的占位界面。要求是不管哪种坏情况，入口都不许消失，更不许白屏。
通过标准：空结果显示还没有拉取请求；加载失败显示加载失败并带重试按钮，重试可以重新拉数据；加载中显示转圈加文案。三种状态都不隐藏入口。
不绿先补什么：先查失败分支有没有保留重试按钮，空分支有没有保留占位文案。
第 16 步：后端切换验收（切换时自动回列表，不白屏）
后端切换就是换一个工作区或者换一种后端类型。
通过标准：在拉取请求页切到无能力后端时，自动回到列表页，全程无白屏，日志里有一次显隐记录。
不绿先补什么：先查容器侧的回退逻辑有没有写，有没有只藏了页签却忘了切页面。
第 17 步：列表五个字段验收
拉取请求列表每一行必须显示五个字段，缺一个都不行。
通过标准：每一行都能看到标题、作者、状态、标签、更新时间五个信息。排序是按更新时间从新到旧，同时间按编号排。
不绿先补什么：先查列表组件是不是只取了过滤后的拉取请求，有没有误把普通工单混进来。
第 18 步：详情基础加评论只读验收（拉取请求隐藏输入框）
详情是指点开一行后看到的右侧详情。基础是指标题、正文、状态等基本信息；评论只读是指只能看评论，不能写评论。
通过标准：点开拉取请求能看到基本信息和评论列表，但是没有评论输入框；点开普通工单时输入框行为保持原样；输入框被替代时才出现只读提示。
不绿先补什么：先查详情里的是否可评论判断，有没有兼容数组和图两种评论形状，有没有任一来源标拉取请求就隐藏。
第 19 步：确认已知留尾（这次故意不做，以后做）
留尾是指已知但本次不做的缺口，已经在源码里留了字说明，不是漏掉的缺陷。
同号码的普通工单和拉取请求会进同一个详情，评审合并展示留给以后做。悬浮面板本来就没有详情分支，点行后详情走右侧停靠的同一机制。前端判断函数已经具名，分类和身份函数按名字可以查到。
通过标准：能在源码注释里找到上面这段话，界面上不会静默吞掉任何一张票。
三层小结：十九个方框全部勾选，地图 503 才算验收通过。
