## 1 双侧统一 logger 接口与守卫约束

### 1.1 形态总览

- 宿主是唯一的落盘者。客户端自己不写盘，只把日志批量转发给宿主。
- 宿主新增 `src/host/logStore.js` 日志库（工厂函数，接收文件服务、计时器、取缓存目录函数，行数不超过 350 行，与现有拆分文件体量纪律一致）。它只做五件事：内存队列、级别判断、按天文件名、单写者刷盘、失败计数。
- 客户端新增 `src/client/kernel/log.js` 日志模块：开关读写、内存批量队列、按批量转发、丢弃计数。文本组装只在守卫通过后做。

### 1.2 统一 logger 接口字面（两端同名同参）

```
isEnabled(level)        // 读当前级别是否允许产生日志；关闭时调用处直接返回
log(level, event, fields) // fields 为已按白名单挑好的字段对象；函数体内仍先判断一次再写
flush()                 // 仅宿主有效：取消本次防抖等待，本轮事件循环末写当天文件
getDroppedCount()       // 读累计丢弃数（写盘失败与通道丢弃都只计数不抛错）
```

- 级别只有四个：`error`、`warn`、`info`、`debug`。
- 落盘规则：`error` 与 `warn` 始终落盘；`info` 中第 3 章常驻 29 条落盘，其余 `info` 与全部 `debug` 只在调试开关打开时落盘。
- 惰性参数：参数组装本身贵（跨多行或含循环）时才用函数包裹延迟执行，且该函数只在外层判断通过后才执行，不作为默认写法。默认不全量使用惰性工厂（每个高频调用点都分配函数违背关闭时零分配，沿用 #330 客户端结论）。

### 1.3 开关信号

- 全局整机一个开关，默认关闭；设置页的主开关为主；开发自用与用户现场同一套语义，不设开发者模式。
- 客户端存一份：本地存储新键 `dsws.debug`，形状为 `{ enabled 布尔, sampleRate 数字, rev 版本号 }`，不动 `dsws.cfg` 现有字段（沿用 #330 客户端结论）。启动读本地值秒显，再向宿主读开关对账，对账前不产生调试日志。
- 宿主持一份：缓存目录下 `log-switch.json`（与命名守护 `naming-guardian.json` 同例，全文覆写，失败不抛错）。
- 对账以宿主为准，重启后保持；设置页保存后向全组广播新开关值（沿用 `broadcastCfg` 同构）；转发失败时客户端保持本地值并提示，不回退为开启。
- 状态栏小入口只做导出与跳转，不做显眼开关（#329 已澄清约束）。

### 1.4 守卫纪律（外层判断为主、体内兜底）

1. 高频调用点外层先判断：`if (!isEnabled(level)) return` 走原逻辑，不碰日志参数。关闭时直接返回，不分配行对象，不拼接字符串，不做对象转文本，不进队列，不排定时器，不写盘。
2. `log` 函数体内仍判断一次并直接丢弃，做漏加外层判断的兜底。但兜底拦不住调用前已求值的拼接，所以外层判断不许省略。
3. 高频路径手法（按 #330 客户端第 7 节分工）：按事件限量为主（有变化才记，无变化不记）；采样为辅（缓存命中类按次数采样或时间窗口首条）；节流为辅（定时器只记调度与跳过原因，不记每次心跳；在途复用只累加计数，窗口到才记一次）。
4. 错误与告警走直通（见 2.3），但调用处仍只进内存队列就返回，不等写盘完成。

### 1.5 渲染路径禁令

- 渲染函数体内禁止为日志做对象转文本与字符串拼接。需要记行状态时只记编号与计数，不记整行对象。
- 反例（不可搬进日志）：`src/client/views/ListTabRow.js` 每次渲染对标签名数组做对象转文本的写法；`src/client/views/SettingsWorkspaces.js` 先对象转文本再解析取样的写法。
- 正例（沿用）：错误文本截断 120 字、详情错误截断 160 字、标题留前 80 字的现有榜样；结构化参数先按白名单挑字段再转文本，转文本带异常捕获与长度上限。
- 门禁对应第 4 章断言二与断言三：高频路径无外层判断即红，渲染函数体内出现日志用对象转文本即红。

## 2 落盘导出契约

### 2.1 落盘位置与文件命名

- 落点为宿主进程当前目录下缓存目录中的独立日志子目录：`.dsh-mattskillsdeck-cache/logs/`（解析办法沿用 `src/host/repoKeys.js` 缓存目录惰性解析；建目录方法存在才调用，不存在也不报错，真正的建目录由写文件内部自动完成）。
- 每个自然天一个文件，命名 `YYYY-MM-DD.log`（如 `2026-09-06.log`）。只分桶，不自动清理，不做自动轮转（地图范围外）。
- 不按工作区分桶：日志是整机一份按天记录的运行轨迹（沿用 #330 宿主假设 6）。
- 每次启动在日志头写入进程标识、启动时间与实际目录，事后能区分哪几行来自哪个进程；目录漂移时写实际目录头、不迁移旧日志（沿用 #489 第 3.3 节）。

### 2.2 异步单写者覆写

- 调用处只进内存队列就返回，另起链路写盘（只用异步，文件服务本就没有同步写法）。
- 防抖窗口 1000 毫秒：窗口内多次调用合并为一次读改写（文件服务无追加原语，任何追加都是全文读改写，按天分文件把单次覆写体积封顶在一天之内）。
- 单写者队列加繁忙守卫：宿主一次只写一份，队列正忙时新写入合并等待；写失败只计数不抛错（沿用命名守护已验证形态：1200 毫秒防抖、15 秒常驻节拍、失败留到下一轮）。
- 双进程同写以后写为准，不加锁，审计行可能少记（与快照缓存一致，本轮不解决）。

### 2.3 错误与告警直通刷盘

- `error` 与 `warn` 入队后立即触发一次刷盘（取消本次防抖等待，本轮事件循环末就写当天文件），崩溃窗口只剩毫秒级，致命日志不因等批量而丢失。
- 常驻 29 条信息走 1000 毫秒批量；按需 16 条只在调试开关打开时进批量。
- 调用处等待写盘完成即违规（门禁断言四）。

### 2.4 脱敏字段清单引用

- 字段白名单以 `research/489-appendix.md` 第 1 节为执行清单，本设计不再复抄：45 事件逐条允许字段、截断代号（T80 标题留前 80 字、T120 错误留前 120 字、T160 详情留前 160 字并标注已截断）、散列代号（H_CWD 路径只记散列、H_TITLE 标题只记散列或截断、H_ERR 错误原文只记散列、B_TOKEN 令牌只记有无与类别）、具名正则第二道网（R_TOKEN_BEARER、R_GH_TOKEN、R_PASSWD_KV、R_AUTH_HEADER、R_WIN_ABS、R_HOME_PATH、R_REPO_URL、R_EMAIL，命中只记规则名不记原文）。
- 脱敏责任划分：客户端组装侧按白名单挑字段、自由文本先截断再过正则（#333 终选记名加截断，可读优先，安全底线由字段清单承担）；宿主侧信任写入，照原文写盘，不再二次解析。
- 红线（门禁断言一）：出现工作区原始路径、仓库地址原文、令牌原文、模板正文、快照全文即红。

### 2.5 记录与导出与清空三电话形状（本设计定版字面）

电话统一 `wf.` 前缀登记（宿主用内存表登记，去掉前缀后为真正的电话名，打包产物 `host.call` 同理去前缀）。

- 记录 `wf.logBatch`：入参 `{ entries: [{ ts 时间戳, level 级别, event 事件名, fields 白名单字段对象 }], droppedCount 客户端累计丢弃数 }`；回参 `{ ok, accepted 接收条数, dropped 宿主侧累计丢弃数 }`。批量上限见 #489：每批最多 50 条、每 1000 毫秒发一次、单包 128KB 或 100 条先到先截并在包尾记截断标记；失败降级为丢弃并计数（不背压等待，不无界缓冲）。
- 导出 `wf.logExport`：入参 `{ date: YYYY-MM-DD（缺省当天）, format: 'zip' }`；回参 `{ ok, fileName, bytes, fallback 是否走了回退 }`。内容为当天日志加系统信息摘要（摘要初版字段：插件版本、操作系统、宿主进程当前目录、开关值、日志头进程标识）。
- 清空 `wf.logClear`：入参 `{ date: YYYY-MM-DD 或 'all' }`；回参 `{ ok, removed删了几个文件 }`。手动清空，客户端先弹窗确认，成功与失败都给反馈（沿用 #334 原型 toast 与路径展示）。
- 开关读 `wf.logGetSwitch`：入参无；回参 `{ ok, enabled, sampleRate }`。开关写 `wf.logSetSwitch`：入参 `{ enabled, sampleRate }`；回参 `{ ok, enabled 生效值 }`（#330 客户端第 8 节通道需求的字面落实）。
- 目录打开与跳转复用现有的打开目录电话，不新增（沿用 #330 宿主第 6 节）。

### 2.6 导出包格式与 zip 能力验证项加回退

- 首选 zip 单包，一个附件发走：包名 `dsws-logs-YYYY-MM-DD.zip`，内含当天日志文件与 `system-summary.json` 系统信息摘要。
- zip 能力验证项（第 5 批落地前实测，结论回填 #333 第 4 项）：宿主进程内可用压缩手段在 Windows 与 Linux 与 macOS 是否一致；一次打包耗时与内存增量初测；失败时是否只计数不抛错。验证不过即走回退，不阻塞前四批。
- 回退：直接返回当天日志原文件加摘要文本文件（多文件），客户端照常提示用户补交跨天缺文；回参 `fallback: true`，并在包里附目录清单（多日期目录并存时提示用户一并打包，不静默只导当前目录，沿用 #489 第 3.3 节）。

## 4 双源镜像影响

### 4.1 改哪几个 src 文件

新增（3 个）：

修改（6 处）：

## 5 落地顺序与真机门禁

### 5.1 分房分批顺序（一次会话只改一房）

- 第 1 批 host 底座（房外，1 个会话）：`src/host/logStore.js`、5 个电话、`log-switch.json` 持久化、启动头写入、门禁骨架（断言四、七、八先行）。验收：`verify` 全绿；关闭时零分配零写盘；错误与告警直通；双产物含 5 个电话名；宿主侧开关默认关、重启保持。
- 第 2 批 client 底座（房外，1 个会话）：`src/client/kernel/log.js`、开关双端同步（对账以宿主为准）、外层判断纪律、体内兜底。验收：对账 winner 为宿主；通道失败保持本地值不回退为开启；批量数量符合 50 条与 1000 毫秒与 128KB。
- 第 3 批常驻 29 条埋点（房外公共区 1 个会话起；落点进入房间文件的事件按 github 房、markdown 房、gitlab 房各 1 个会话）：逐条按第 3.1 节表落地。验收：计数 29 断言过；字段白名单扫描过；脱敏抽查（路径散列、令牌掩码、标题截断）。
- 第 4 批按需 16 条埋点（1 个会话）：开关开时路径、采样率初值按第 3.2 节表。验收：关闭时高频路径零调用（外层判断全覆盖）；打开时采样率符合设计值；采样初值真机调参回填 #489 假设 6。
- 第 5 批开关导出界面（1 到 2 个会话：设置页分组 1 个，状态栏入口与导出清空 1 个）：沉底调试分组、四按钮、常驻小灰点、四键菜单、清空确认、toast 与路径反馈、zip 打包与回退分支。验收：#334 三问回放（不过显、找得到、文案清）；zip 能力验证有结论（有则 zip，无则回退并记录）；双系统真机通过。

### 5.2 真机门禁

- 手法用地图指定的 dsh-plugin-ui-debug 技能，真机验证开关与导出：默认关无写入、开有关闭有、重启保持、对账 winner 为宿主、四键菜单每键可用、清空有确认有反馈。
- 真机矩阵至少双系统（Windows 加 Linux 或 macOS 其一，口径沿用 `verify-platform-linux` 门禁）。
- 端到端判据：用户把导出的包发给维护者即可复现定位——至少用导出包定位一次已知问题走通全链路。
- 熔断：门禁不过阻塞发布；计数变更未同步更新附录对照表阻塞发布（断言六）；项目经理对控制台规则的一票否决随时生效，喊停即改。
