# 677 工单取数规格：数字从哪来、列表装多少、历史怎么按需取

出处：缺陷票 #677「右侧面板的「已关闭」票数不准确（工单池被 500 条上限截断 + 10 条拉取请求被算成已关闭票）」。
写这份的时间：2026-09-22。维护者 2026-09-22 的要求：**先把方案从上到下制定完整，再谈执行。**

这份文档是 #677 方案的**权威版本**；票里的「最终方案」与「分层账」两节是这份文档的推演过程与摘要，两边不一致时以本文为准。

---

## 1. 结论（一页纸读完）

**问题出在数据面，不在界面。** 面板上「已关闭」的数字偏少，是因为面板手里的那份工单清单被后端悄悄截断了，而界面拿残缺当全量用。

根因一句话：**契约的 `list` 返回的是一个数组（`OpResult<Issue[]>`），里面没有任何位置能表达「这份清单是不是全量」**，于是三个后端各自静默截断、互不知情：

| 后端 | 今天的截断 | 出处 |
| --- | --- | --- |
| GitHub | 最多 500 条（按更新时间倒序取到 500 就停） | `src/host/tracker/backends/github/issues.js:186-187` |
| GitLab | 一页 100 条，而且**不翻页** | `src/host/tracker/backends/gitlab/issues.js:72`（只设 `per_page=100`，没有 `page`） |
| 本地 Markdown | 读全部票文件，不截断 | `src/host/tracker/backends/markdown/issues-read.js` |

修法三句话（这三句是整份规格的骨架）：

1. **数字由后端算**：契约新增 `counts`，让每个后端自己回答「打开多少、关闭多少、一共多少」。宿主把这三个数写进快照的 `deck`，界面只读 `deck`，不再自己数池子。
2. **工作集拉全**：面板每次打开都要用到的那些票（全部开放票、加上开放地图的全部子票，含已关闭子票），必须完整拿到；做不到时不许假装，要标 `partial`。
3. **历史按需取**：已关闭票的行、以及已关闭地图的子票，只在用户真的要的时候按页取（契约新增 `listPage`），界面写清「已加载多少 / 共多少」。

另外两条口径，贯穿所有改动：

- **凡是要说「工单」的地方，只认 `isPullRequest !== true` 的票**（主列表、KPI、状态栏那几枚计数都是「工单口径」；快照池子本身与拉取请求页签保持原样）。
- **凡是被截断，界面必须自己说出来**（`deck.partial` 为真时显示一句「这份清单不全」）。

## 2. 词表（先统一叫法，后面不再解释）

- **池子**：快照里那份票的集合（`snapshot.issues` + `snapshot.maps[].tickets` 合起来）。
- **行数据**：池子里每一条票记录（列表要画成一行的那种）。
- **数字**：面板顶部那一行要显示的三个数（可接 / 阻塞 / 已关闭），以及状态栏那几枚。
- **全量 / 部分**：全量 = 这份行数据包含了后端里所有符合条件的票；部分 = 只包含一部分。
- **工作集**：面板每次打开都必须完整拿到的那部分票 —— 全部开放票，加开放地图的全部子票（含已关闭子票，因为地图行上的进度环与「完成」判定需要它们）。
- **历史**：已关闭票的行、已关闭地图的子票 —— 只在用户主动要时取。
- **工单口径**：只数 `isPullRequest !== true` 的票。
- **一页**：一次向后端要的一批票（`listPage` 的一次调用结果）。

## 3. 必须遵守的架构事实与硬约束

这些是设计边界，方案不能越过：

1. **界面只经契约拿数据**：「UI/宿主只通过本接口访问 tracker，不知道后端是谁」（`src/host/tracker/contract.js:13`）。
2. **快照不是契约操作**：`snapshot` 是宿主编排（`list` 组合出来的），不在 `OPERATIONS` 里（`contract.js:10`）。
3. **数字本来就是宿主算的**：`snapshot.deck = deriveDeck(snapshot)`（`src/host/tracker/snapshot.js:163`）。后端从不产出 `deck`。
4. **`list` 的返回形状没有位置表达全量性**：`OpResult<Issue[]>`，一个数组。
5. **G5 红线**：能力是事后的事实 —— 不做能力表、不做能力缓存、不做运行期内省；能力位只许驱动引导入口，永不被数据路径读取（`contract.js:5-6`、`:118-119`）。界面要判断「这个后端能不能翻页」，只能**去调一次**，按真实返回（`{ok:false,error:{kind:'unsupported'}}`）退化。
6. **拉取请求与工单同池**（#294 / #505 的裁决，写在 `tracker/snapshot.js:16-19`）：不按类型分片、不新增集合；**界面按类型过滤**（#506）。维护者 2026-09-22 确认：主列表要过滤掉拉取请求，因为我们有专门的拉取请求页签。
7. **`deck` 已经有两个读者**：`labelColorPatch.js:83` 读 `snap.deck.labels`；契约测试 `tests/tracker-contract/sections/deck.js` 断 `deck` 形状。改 `deck` 要同步这两处。
8. **缓存与版号**：快照按「后端 + 仓库键（含 effort）」进 LRU（上限 20），TTL 5 秒；带 `ifNoneMatch` 时可以回 304（`tracker/snapshot.js:94-168`）。**版号必须覆盖新加的字段**，否则数字变了也可能被 304 糊过去。
9. **日志纪律（#502 总纲）**：新增跨边界调用必须同步加日志点；常驻还是按需按 `docs/design/335-logging-contract.md` 第 3 章判定；事件增删要同步 `research/489-appendix.md` 第 1 章的对照表与条数（现为常驻 31 条、按需 27 条、自监控 5 条），并让 `tests/verify-log-count.js`、`verify-log-fields.js`、`verify-log-guards.js` 保持绿。
10. **文件粒度门禁 ≤350 行**：`sessionRefresh.js` 334、`issueList.js` 348、`github/issues.js` 335、`MapDetail.js` 336、`store-derived.js` 333 —— 几乎顶格，新逻辑必须按既有做法拆文件。
11. **界面文字走词条**，中英各一份；渲染代码里不许写死中文。
12. **契约测试与桩机制**：加进 `OPERATIONS` 的操作，注册表会自动给没实现的后端补「做不到」的桩（`registryShape.js` 的 unsupportedStub，出处见 `contract.js:62-64`），所以新增操作不需要兼容层、不会碰坏现有后端。

## 4. 契约层：加两条操作

### 4.1 `counts(repo, filter, ctx) -> OpResult<{open: number, closed: number, total: number}>`

- **语义**：这个后端里符合条件的票有多少张。**只数工单**（不含拉取请求）—— GitHub 的 `issues` 连接天然不含拉取请求，GitLab 的 issues 接口也不含合并请求，本地 Markdown 没有这个概念。
- **effort（工作单元）由 `repo.effortId` 带**（编排层的快照键已经含它），所以多工作单元的后端（本地 Markdown）能按工作单元分别数。
- **filter 复用现有 `ListFilter`**（`state` / `labels` 之类），只支持 `state` 与 `labels` 两项即可，其余字段忽略并写进注释。
- **失败语义**：`unsupported`（这个后端没实现）/ `rate-limit` / `network` / `auth` / `parse`。返回里带 `errors` 或数据不完整时**一律失败**，不许猜一个数出来。
- **不许缓存判定**：`unsupported` 的结果不进缓存（G5 红线，与 `getDependencies` 同例）。

### 4.2 `listPage(repo, filter, {cursor, limit}, ctx) -> OpResult<{items: Issue[], nextCursor: string|null, total: number}>`

- **语义**：按页取票，供界面按需浏览历史用。
- **排序键固定为「创建时间倒序」**（`CREATED_AT DESC`）。理由：翻页期间如果有别的票被更新，按更新时间排序会让票在页与页之间挪位、可能漏掉一张；创建时间不会变，翻页稳定。
- **cursor 是不透明字符串**，调用方只负责原样回传（GitHub 用 GraphQL 的 `after`；GitLab 用它自己的页码；本地 Markdown 用票文件列表的下标，编码成字符串）。
- **limit 默认 50、上限 200**（超上限按上限处理，并在返回值里如实反映实际条数）。
- **`total` 是同一口径下的总数**（供界面写「已加载 x / 共 N」）。
- **失败语义**同 `counts`。特别地：游标失效（后端数据变了、进程重启）返回 `parse` 或 `not-found` 并在消息里说清「游标已失效，请重新加载」，界面据此回到第一页。

### 4.3 连带改动

- `OPERATIONS` 加两个名字；`registryShape` 用既有机制补桩（不需要新代码，只需契约测试断言桩的行为）。
- `CONTRACT_VERSION` **不升版**：这次是纯新增操作，缺实现的后端由桩兜住，形状没有改。理由写在契约里，免得以后有人问。
- `contract.js` 补两个 typedef（`Counts`、`PageResult`）与上面这些语义；`ListFilter`、`Issue` 形状不动。
- `tests/tracker-contract/sections/` 加一节（文件名建议 `counts-page.js`）：三后端 fixture 各断一次「实现了就回数、没实现就回 unsupported 桩」，再断 `listPage` 的游标回传与 `total` 一致。

## 5. 三个后端各自怎么做

### 5.1 GitHub

| 操作 | 实现 | 代价 |
| --- | --- | --- |
| `counts` | 一次 GraphQL：`issues(states:[OPEN]){totalCount}` + `issues(states:[CLOSED]){totalCount}` | 1 点额度（实测），不翻页 |
| `listPage` | GraphQL `first:$limit, after:$cursor, orderBy:{field:CREATED_AT, direction:DESC}` + **薄片段**（编号/标题/状态/时间/标签/指派人/链接，不带正文与评论） | 一页约 2 点、0.02 MB（实测 200 条 4 点） |
| 地图子票拉全 | `issue(number:n){subIssues(first:100, after:…)}` 循环到底，用 `totalCount` 核对 | 每 100 张一页，只在打开该地图时付 |
| **`list({state:'open'})` 必须把状态下推** | 查询里写 `states:[OPEN]`，不许「先取一页再内存过滤」—— 今天 500 条窗口一截，旧开放票就被过滤没了 | 开放票全量的前提 |

`list` 的 500 条安全上限**保留**（它当初是为「一次拉太多在部分网络下会断」加的），但它的后果必须被说出来：编排层据此把 `deck.partial` 置真，数字由 `counts` 兜住。以后要不要抬上限，是另一个决定，不在这份规格里。

拉取请求仍然与工单同池（裁决不改）；主列表、KPI、状态栏按工单口径过滤，拉取请求页签照旧从池子里取 `isPullRequest === true` 的那些。

### 5.2 本地 Markdown

| 操作 | 实现 |
| --- | --- |
| `counts` | 数票文件（本来就是全量读出，天然准） |
| `listPage` | 票文件列表切片（cursor = 下标） |
| 地图子票 | 地图文件（`map.md`）里列出的票 |

它今天没有截断问题，实现这两条是为了让**界面代码一条路**：界面不需要知道后端是谁。

### 5.3 GitLab

| 操作 | 实现 |
| --- | --- |
| `counts` | 两条候选：`X-Total` 响应头（`per_page=1` 取一次）或 `issues_statistics`。**落地时二选一并把实测结果写进实现注释**（这一轮没有 GitLab 环境，未实测） |
| `listPage` | 现成的 `per_page` + `page`（今天只设了 `per_page=100` 且不翻页，顺手把「只取 100 条」这处同族截断一起收掉） |
| 地图子票 | 走 `links`/父票关系，按页取 |

### 5.4 第三方 / 没实现的后端

注册表自动补的桩会回 `unsupported`。界面据此显示「这个后端只能在它自己的网页上看全部」，其余照旧（数字退回按池子派生 + 标 `partial`）。

## 6. 宿主编排层：数字与首屏

### 6.1 改后的 `composeSnapshot` 流程

1. 取工作集：`list({state:'open'})`（后端必须下推状态）+ 开放地图的子票（每张地图循环 `subIssues` 拉全，见 6.4）。
2. 取历史首页：`listPage({state:'closed'}, {limit:100})`。
3. 取数字：`counts({})`。
4. 组装：`assembleSnapshot`（不动）→ `deriveDeck` → **用 `counts` 覆盖 `deck` 里的数字**（拿不到就保留派生值）→ 置 `deck.partial`。
5. 版号：`snapshotVersionOf` **必须把 `counts` 与 `partial` 算进去**（否则数字变了可能被 304 糊过去）。
6. 缓存与 304 照旧（LRU 20 / TTL 5 秒 / `ifNoneMatch`）。

### 6.2 `deck` 增两个字段

- `deck.counts = {open, closed, total}`：来自 `counts` 的真实数字；拿不到时省略。
- `deck.partial = true|false`：**手上这份行数据是不是被截断过**。三种情况置真：`list` 触到后端上限、历史只装了首页、大仓库降级（见第 9 节）。
- 界面只读这两个；`deck` 的其余字段（`total/open/closed/frontier/claimed/blocked/levels/levelOf`）保持现在的含义与消费者（`sections/deck.js`、`labelColorPatch.js`）不变。

### 6.3 首屏装哪些行

- 全部开放票（工单口径与拉取请求都在池子里，界面自己过滤）；
- 开放地图的全部子票（含已关闭子票 —— 地图行上的进度环、「完成」判定需要）；
- 已关闭票的最近 100 条（工单口径），作为折叠行的第一屏；
- 已关闭地图的**容器行**（不带子票）。

### 6.4 地图详情按需

- 打开一张地图时（不论开还是关），抓它的全部子票：`subIssues(first:100, after:…)` 循环到底，用 `totalCount` 核对「拉到的张数 == 总数」；对不上要把差额说出来，不许静默少几条。
- 硬上限 1000 张子票（超过就明说「只加载了前 1000 张」）。
- 已关闭地图的子票不在首屏抓（实测 39 张里 35 张是已关闭，那一块今天要 105 点、2.93 MB）。

### 6.5 失败与降级

- `counts` 拿不到（不支持 / 配额 / 网络）→ 数字退回 `deriveDeck` 的派生值，并且 `deck.partial = true`；界面明说「数字可能不全」。
- `listPage` 拿不到 → 界面只给「在网页上看全部」的出口，不显示假的行。
- 任何情况下**不许显示一个漂亮的大数字骗人**。

## 7. 电话层与客户端

### 7.1 新电话 `wf.issuesPage`

- 入参：`{cwd, state, labels, cursor, limit, effortId}`；回参：`{ok, items, nextCursor, total, error}`（错误形状与现有电话一致）。
- 走 `registry` → 后端的 `listPage`；后端回 `unsupported` 时原样透出去，界面按它退化（G5 纪律：不做能力表）。
- 在途去重：同一「仓库 + 视图 + 筛选 + 游标」的并发请求合并成一次（照 `probe-stale.js` 那套在途复用的做法）。

### 7.2 翻页结果放在哪

- 键 = 「后端 + 仓库键（含 effort）+ 视图 + 筛选条件」。**不塞回快照**（快照仍是首屏那一份），单独一份页数据。
- 按票身份去重（同号票以「后到的那份」为准）。
- 刷新（含静默探测）时：只更新其中已有条目的内容，**不清空已加载的页**（否则用户翻了半天，一次静默刷新全没了）。
- 内存上限：最多保留 10 页（约 500-2000 行）；超出从最旧的页开始丢，并让界面知道「再往上滚要重新加载」。
- 不落磁盘（历史随时可再取，不做第二份缓存真源）。

### 7.3 KPI 改读 `deck`

- `ListTab` 的顶部三个数字从「自己数池子」改成读 `deck.counts`（拿不到再退回现在的算法），并按工单口径。
- 状态栏那几枚（可接 / 占用 / BUG / TRIAGE）同样改工单口径 —— 它们今天是数池子的，池子被截断时会跟着错。

### 7.4 三个触发点

1. 展开列表底部那行「已关闭 N」；
2. 状态筛选「已关闭」；
3. 已加载区滚到底。

三者都走 `wf.issuesPage`，共用同一份页数据与游标。

### 7.5 日志点

- `wf.issuesPage` 是新跨边界调用 → **记常驻**（用户主动触发、低频）：事件名建议 `issues.page`，字段按白名单取 `state`、`labelsCount`、`returned`、`total`、`latencyMs`、`ok`、`errorHash`（路径只记散列）。
- `counts` 随每次重建发生 → **不新增事件**，把 `open`/`closed`/`partial` 三个字段加进既有的 `snapshot.built`（常驻）里，避免条数膨胀。
- 同步：`research/489-appendix.md` 第 1 章对照表与条数（常驻 31 → 32）、`tests/verify-log-count.js` / `verify-log-fields.js` / `verify-log-guards.js`。

## 9. 边界与异常：逐条说清会怎样、怎么办

| 情形 | 会发生什么 | 怎么办 |
| --- | --- | --- |
| 新仓库 / 没有已关闭票 | `counts` 回 0；折叠行不出现 | 不显示 0 行，照旧隐藏折叠行 |
| 正好 100 / 500 / 1000 条 | 边界处容易少一条 | 判定用 `>= 上限` 而不是 `> 上限`；验收里各测一次 |
| 翻页期间有人关票或改票 | 按创建时间排序不会挪位；按更新时间会漏 | 排序键固定 `CREATED_AT DESC`；客户端按 key 去重防重复 |
| 游标失效（后端重启、数据大改） | 后端报错 | 返回 `parse`/`not-found` 并说清「游标失效」，界面回到第一页 |
| 配额耗尽 / 部分 `errors` | 可能返回残缺数据 | 一律失败不猜；数字退回派生值 + `partial`；界面提示稍后再试 |
| 网络中断 / 超时 | 请求失败 | 不改变已有页；提示可重试 |
| 翻页途中切后端或切工作区 | 可能串台 | 页数据按「后端 + 仓库 + effort + 视图 + 筛选」分开存；切了就换键，旧键数据不显示 |
| 多工作单元（本地 Markdown） | 数字可能跨工作单元混算 | `counts` 按 `repo.effortId` 作用域；KPI 的筛选维度保持现状 |
| 子工作区会话（#647） | 同仓库不同目录 | 沿用工作区键分桶，本规格不改这条 |
| 已删票 / 归档仓库 / 权限不足 | 数字与行都在同一权限下 | `counts` 与 `list` 走同一授权，天然一致；不额外处理 |
| 自建 GitLab / GHES | 接口形状相同 | 沿用现有 gh/glab 通道，失败如实报 |
| 大仓库（开放票 > 1000） | 工作集太大 | 只取最新 1000 张开放票，置 `partial`，界面明说「只加载了最近 1000 张开放票」 |
| 地图子票 > 1000 | 层网格画不全 | 硬上限 1000，明说「只加载了前 1000 张」 |
| 地图没有子票 | 环为空、按钮空 | 沿用现有空态（`mapEmpty`） |
| Markdown 票文件被手改坏 | 解析失败 | 后端如实报 `parse`，不静默丢票 |
| 两个会话同时翻页 | 互相干扰 | 页数据是会话私有；宿主只在途去重，不共享可变状态 |
| 静默刷新撞上已加载的页 | 页被清空 | 刷新只合并更新，不清空（见 7.2） |
| 面板很窄 | 文案放不下 | 文案按现有窄面板收缩规则收（图标 + 悬停显示全句） |

## 10. 验收判据

1. 面板顶部「已关闭」等于同一时刻 `counts` 给的数字（本仓库对 `gh issue list --state closed` 核对）。
2. 折叠行说的数与展开后的行数自洽：「已关闭 N（已加载 x）」里 N 来自 `counts`、x 来自已加载的页。
3. 主列表里**没有**拉取请求行；拉取请求页签照常列出它们。
4. 顶部三个数字与状态栏那几枚都按工单口径。
5. 首屏的点数与体积低于改前（改前实测：5 页 / 约 20 点 / 4.3 MB）；改后目标 ≤2 页 / ≤5 点 / ≤1 MB，实测值记进 #677。
6. 打开一张子票超过 100 张的地图：能看到全部子票（开放与已关闭都在），拉到的张数等于 `totalCount`；超过硬上限时明说。
7. 已关闭的地图点开后也能看到全部子票（按需抓）。
8. 已关闭地图不进首屏（用点数与体积的变化证明）。
9. 后端不支持翻页时（用桩模拟）：界面显示「在网页上看全部」而不是空白或假列表。
10. `counts` 拿不到时：数字退回派生值且界面标「这份清单不全」，不显示 0、不显示旧的大数字。
11. 静默刷新之后，用户已加载的页仍在。
12. 门禁：契约测试新增一节全绿；`npm run verify` 全绿；日志门禁（条数/字段/守卫）与附录同步后全绿；文件粒度不再有新超限。
13. 夹具：契约与界面两侧都要有「池子被截断 + 总数更大」这一态的夹具，不打真网。

## 12. 风险登记与「还没证明的」

- **`counts` 与行数据的时刻差**：两次调用之间有人关票 → 数字与行差 1。缓解：同一次重建里取（6.1 的顺序），并在验收里接受 ±1 的瞬时差。
- **版号漏算**：`snapshotVersionOf` 没把 `counts`/`partial` 算进去 → 数字变了被 304 糊过去。这是本次最容易漏的一处，必须写夹具断它。
- **薄片段字段不够**：`listPage` 只取列表行需要的字段；`IssueDetail` 的兜底（`IssueDetail.js:36-37`）会拿到没有正文的行 → 详情页要能容忍「兜底行没有正文」，显示加载态而不是空白。落地前要按「谁在读快照/页数据的哪个字段」列一次清单。
- **GitLab 计数口未实测**：`X-Total` 与 `issues_statistics` 二选一，落地时实测后再定（这一轮没有环境）。
- **本地 Markdown 未逐条核**：`counts` 要数哪些文件（票文件 vs 目录），落地时按工作单元目录结构核一遍。
- **文件拆分的连锁**：拆 `ListTab` / `MapDetail` / `sessionSnapshot` 会动到门禁里的叶子清单（`tests/verify-leaves.js` 之类），拆完要跑全链。
- **点数是单次实测**：重页 4 点、地图 3 点/张、薄页 4 点/200 条，都是单次测量，不是多次平均；验收里的目标值按同一口径再测一次。

## 14. 研究结论并入（2026-09-22）：字段消费清单带回来的硬事实

出处：研究票 #687 → 底稿 `research/677-field-consumption.md`（约 600 行，坐标到文件与行号）。这一节只记**会改变落地动作**的几条，完整清单看底稿。

**三条硬事实（落地前必须先满足）**

1. **详情页兜底会说假话，换薄片段之前必须先改**：`src/client/views/IssueDetail.js:160` → `:242-244` 在没有正文时画「无描述」三个字（不是加载态）；`:182-183` → `:281` 没拿到评论时显示「只读」（把「没拿到」说成「不能评论」）；`:105` 的加载态判据 `mode === 'loading' && !src` 只要池子里有那一行就被跳过。已单独成票（「修复：单票详情页的兜底不许说错话」），并挡住阶段 2。
2. **`number` 与大写 `state` 是宿主补的，不是后端字段**：`number` 由 `src/host/sessionSnapshot.js:258/264/288` 从 `key` 现算，`state` 的大写化在 `src/host/index.js:169-181`。客户端多处直接读 `x.number` 不做 `key` 兜底（`ListTabRow.js:11/56-57/85`、`ListTab.js:110`、`api-io.js:14/23`），所以 `listPage` 拿回来的行**必须同样补**，否则点行会压进 `undefined`。
3. **`snapshot.issues` 是整个扁平票池，不是孤儿票数组**：`src/host/sessionSnapshot.js:289` 把「地图容器 + 全部子票 + 未挂图票」三段拼接去重（真机 40 + 287 + 183 = 510 行）。`IssueDetail.js:35-36` 的兜底只在这个数组里找 —— 改池子口径时必须回头核这条。

**字段层面的两张清单（薄片段照它来）**

- **画一行最少需要**：画像素那 9 项（`key`/`number`/`effortId`/`type`/`title`/`labels[].name`/`labels[].color`/`author.login`/`blockedBy[]`），加列表流水线那 6 项（`state`/`updatedAt`/`createdAt`/`labels[]`/`assignees`/`isPullRequest`；`url` 只有本地 Markdown 必需）。
- **今天确定没有任何客户端读者**：`parentKey`、`reviews`、`deck.progressOf`、`deck.blockedByKeys`、`labels[].description`、`assignees[].name/.avatarUrl/.kind`、`author.kind`、`blockedBy[].title/.state`（`reason`/`milestone`/`customFields` 只有检查页诊断卡「数在不在」这一种读者）。

**体积实测（真机那份磁盘快照，2026-09-22）**

- 整份 11,848,079 字节；`issues` 8,273,163（69.83%）、`maps` 3,526,843（29.77%）。
- 单字段大头：`body` 2.94 MB、`tickets` 2.78 MB、`comments` 1.80 MB（合计 63.5%）。
- **地图容器连同整段 `tickets` 在 `issues` 与 `maps` 里各存一份**（实测两处逐字节相同）—— 这是首屏瘦身里最大的一块重复。

**两条顺带核到的**

- `progress` 今天是「有读者没来源」：`src/client/views/shared/ticket.js` 的状态徽章读它，但真机 510 + 287 行一条都没有值；唯一产出点 `src/host/mapBody.js:71` 属已无调用点的旧路径。阶段 3 要二选一：宿主侧解析后带上，或界面不再画。
- `src/client/views/TicketRow.js` 全仓没有渲染入口（`Dock.js:302-303` 只渲染 MapDetail / IssueDetail / ListTab / PrTab / SkillsTab / ChecksTab）—— 它是死组件，统计读者时不要算它。

**时效性**：底稿第 7 节列了十条「改哪里、要重跑哪几节」的重跑清单；阶段 1 改 KPI 读 `deck` 后要重跑第 3.1/3.5 节，阶段 2 加页数据后要重跑第 3、4、6 节，阶段 3 改地图子票后要重跑第 3.2 节。
