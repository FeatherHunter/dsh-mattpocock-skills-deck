## 1. 结论（一页纸读完）

**要做的不是「再做一个面板」，而是让面板认得第二种容器，并按容器类型换一套视觉参数。**

三句话：

1. **容器是一等概念**。现有代码里能装子票的东西只有「地图」，所以代码里到处是 `maps`。实施地图在数据上是同一类东西（一张票装着若干张子票），差别在**身份**（探索用 `wayfinder:map` 标签，实施用正文文件头隐藏标记）、**正文形状**（五节 vs 七节）、**颜色**（紫 vs 贵族蓝）、**按钮**（检查/执行/完成 vs 拆票/执行/完成）。因此**不新做一套页面**，而是在同一套行渲染与详情页骨架上按「容器类型」分支。
2. **容器数组不拆开，靠类型字段分辨**。快照里那个装容器的数组历史上叫 `maps`，实施地图进去以后它装的是「容器」，数组名保持不变（改名要动二十来处读点）；每张容器带自己的 `type`（`map` 或 `spec`），客户端新增一个判定函数 `containerKindOf(x)` 统一认种类，判定与取色只在这一处做。
3. **原型里画得比代码能给的更多**。原型是手搓 HTML，把两边拍平在一页上；真面板的地图详情页有迷雾、Decisions/Fog/Out of scope 这些**读地图正文五节才有内容**的块，规格正文是七节，形状不同。落差逐条记在第 4 节，每条都写明「原型画的 / 代码现状 / 落地怎么办 / 依据」。

**这次不做**：提示词正文文案（归 #1281）、提示词 YAML 化（归 #1282/#1283）、正文形状兜底识别（归 #1275）、规格「完成」后自动关闭（归 #1281/#1274 决策）。

## 2. 词表（先统一叫法）

- **容器**：能装子票的票。两种：**探索地图**（标签 `wayfinder:map`）与**规格**（正文文件头有 `<!-- DSH-ISSUE-KIND: spec -->`；文件头指第一个一级标题之前）。
- **实施票**：规格下面的子票。由 `/to-tickets` 产出。
- **行**：列表页里的一张票卡片。
- **细节页**：点开容器后的大页面（现有代码里叫地图详情页）。

## 3. 方案（第一性原理推导）

### 3.1 为什么是「同一套界面 + 按类型分支」而不是「两套界面」

面板的每一处渲染都已经把「地图」写死了：列表行有五条地图专属分支（左侧紫条、紫底、地图角标、圆环、编号色随状态变），详情页整页按地图正文解析渲染。复制一套给规格，等于把两套代码各自演化，规格那边永远落后。

反过来看，真正需要「不一样」的地方只有四类：**身份怎么标**（颜色 + 角标 + 左侧色条）、**状态怎么算**（三态按钮与编号色）、**正文怎么渲染**（五节 vs 七节）、**点了注入什么提示词**。这四类都能塞进「按容器类型取参数」的小函数里。

### 3.2 数据模型

**票的种类多一种**。契约层 `IssueType` 从 `'issue' | 'map'` 变成 `'issue' | 'map' | 'spec'`，运行时常量 `ISSUE_TYPE` 同步加 `SPEC`。理由：容器与普通票的区别是**结构性的**（能不能装子票、正文什么形状、按钮按什么语义走），用一个布尔字段去补丁式地表达它，只会让「是不是容器」在二十来处读点里各写各的。

**容器数组不拆开**。快照里那个数组历史上叫 `maps`，实施地图进去以后它装的是「容器」：

```
snapshot.maps   // 容器数组（历史名）：探索地图与规格都住在里面
                 // 每张带自己的 type（'map' 或 'spec'），客户端据此判种类
```

不另开 `specs` 或 `containers` 数组，理由是改动面：组装、状态升格、拼列表、去重、统计、层级、信封透传这几处都按「遍历容器数组」写，拆成两个数组就要在每一处都改成「两个数组合起来」，而客户端读 `snapshot.maps` 的地方有二十来处——漏一处就会出现「列表页多出一行规格」「实施票散成孤儿票」这类**不报错但真坏**的结果。数组名是历史名，不是 bug。

**每张容器带**：`type`、`tickets`（子票）、以及按类型解析出来的正文段（地图是 destination/notes/decisions/fog/outOfScope，规格是七节）。**规格容器与它的实施票都不再作为普通票出现在池子里**（与地图同口径：组装层两道闸门都要改，漏第二道会两处都出现它）。

宿主侧识别（第一性原理只取确定的那一条通道）：

- **只认正文文件头隐藏标记** `<!-- DSH-ISSUE-KIND: spec -->`，标记必须**独占一行**、去空白后精确匹配（不做全文 `includes`：那会把正文里引用标记的例子也算成规格）。文件头指第一个一级标题之前（没有一级标题时只看前 10 行，与本地房读 parentKey 的口径一致）；#1403 起三个后端统一按这一份判据认规格容器，幂等锚占首行、标记落在第二行也认得出。
- **正文标记排在标签判定前面**：依据 GLOSSARY.md「对象类型（objectKind）」词条，正文文件头的隐藏标记是对象类型的唯一真源，判定顺序是标记 → 标签 → 形状。规格本来就不许带 `wayfinder:map` 标签（写侧会自动给 `type==='map'` 的票加上那个标签，见 #1274/#1275）；万一遇到两者同时在场的脏票，按标记算成规格——标签只在这张票没有标记时才看。
- **不做正文形状兜底**：形状判据松了会把普通票误判成规格（研究笔记 #1275 的残余风险），且规则归 #1275 定。这次把识别函数放在**一个地方**，#1275 将来在同一处补规则。

**颜色落笔时的一处现实**：贵族蓝 `#1D4ED8` 直接当小字色在深色面板上只有约 2.6:1 的对比度，看不清。所以**身份色留给左侧色条与编号徽章**（大块、实心、辨识度高），角标那种小字用同色系浅蓝 `#93c5fd`（约 7:1）。这条是原型里看不出来的落差——原型是手搓 HTML，配色没有面板实际的底色。

### 3.4 提示词怎么接（不越界到 #1281）

- 规格「执行」态：注入 `/implement-spec <链接>` 的技能调用。**不用**通用执行模板：那个模板的正文首行就是 `/wayfinder`，而 wayfinder 是探索地图的路子（规划一张决策地图，不是实施一张规格），用在规格上不对；本仓本来就带着 `implement-spec` 技能（`package/bundled-skills/implement-spec`），它开的场就是「你拿到了一张规格，它下面挂着实施票」，与规格容器正好对上。探索地图的「执行」保持现状（`/wayfinder <链接>` + 推进式提示词）。
- 规格「完成」态：复用现有的完成提示词（两类容器的完成态语义相同：汇总子票并收尾）。
- 规格「拆票」态：真代码里没有拆票动作。这次用**最小可用的技能调用形式** `/to-tickets <链接>`（面板只负责把这句话填进输入框），**最终文案归 #1281**；提示词正文将来随 #1282 搬到 YAML。

**为什么不新增提示词登记表条目**：登记表加一条要动六处门禁（登记表本体、登记表条数、工具节两张表的表态与条数断言、版本底线、内容断言、跨门禁一致的正则、夹具自锁摘要），而 #1282 正在把提示词搬到 YAML。#1286 只复用现成的两条（检查 / 完成），规格那两态用「技能调用 + 链接」的形式给出，不碰登记表。

### 4.1 这一版没做的四件事（写在这里备查，别当成已做）

1. **GitLab 房没做**。仓库有一条会话越界门禁（#326）：一次会话只准动一个房间（GitHub / GitLab / Markdown 三选一），要同时动两个房间必须分票分次做。所以这一版只改了 GitHub 房（`src/tracker/rooms/github/normalize.ts`），GitLab 房保持原样——**规格在 GitLab 后端认不出来，会被当成普通票**。GitLab 那份镜像等另一张票单独做。
2. **本地 Markdown 后端没做**。规格容器在本地 Markdown 后端要认出来、要把实施票挂上去、快照要分三层，归 #1277。
3. **REST 降级通路没兜住**。GitHub 房间有一条 REST 降级路径（`src/tracker/rooms/github/parent-repair.ts`），它只给带 `wayfinder:map` 标签的票修父子边；规格没有那个标签，所以**降级到 REST 时规格会静默变成一个没有子票的空容器**（不报错、不提示）。这条最危险，补法是让降级路径也认规格容器。
4. **颜色没收进一处**。#1280 的验收清单要求「探索紫与规格贵族蓝只能从一个按容器类型取色的地方取」。这一版新增了色表（`src/client/kernel/container-view.ts` 的 `CONTAINER_ACCENT`），但视图里仍留着兜底字面量——视图模块会被门禁单独求值（跨模块调用在那种求值方式下拿不到），所以兜底必须留。全仓 14 个文件里的 `#c084fc` 收编，是另一件事。

此外，这一版还没按日志纪律记「这一轮认出几个规格容器、几个地图容器」这类口径日志。

## 6. 验收

- 列表页从上到下：探索地图 → 规格（实施地图）→ 普通票；同组内最近更新的在前。（2026-10-21 起：同组内改为跟随面板排序档，见 #1356；本行旧说法留档备查。）
- 规格卡：左侧贵族蓝 `#1D4ED8` 色条、编号徽章蓝、角标是地图图标 + 「规格」。
- 规格卡三态：无实施票 → 「拆票」橙；有未关实施票 → 「执行」蓝；全关 → 「完成」绿。
- 「新会话」与主按钮同色实心。
- 点进规格：结构与探索地图详情页一致；计数文案是「本规格 N 张实施票（已关闭 M 张）」；编号徽章蓝；被阻塞的子票是红 `#f87171`。
- 探索地图的既有表现不回归（紫、地图角标、检查/执行/完成、计数文案「本图 N 张子票（已关闭 M 张）」）。
- 没有规格票的仓库（老宿主、没有标记）下面板照旧可用。

验证方式：新增门禁测试三份（宿主快照结构、列表行与排序、详情页分支），并跑既有冒烟与渲染测试。
