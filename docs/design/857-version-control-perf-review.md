# 版本管理面板 · 性能对抗式审查（#857）

审查对象：`src/client/views/versionControl/`（15 个文件）与宿主侧 `src/host/versionControl.js` 的读取通路。
方法：逐条读数据通路（读什么、什么时候读、读回来写进哪儿），对每个「可能泄漏 / 可能抖动 / 可能白等」的点找**证据**，
而不是凭感觉下结论。查完发现的一条**误判**也照实记在第五节。

## 一、真缺陷（按严重程度排）

### P1 未提交那一路的差异读取没有序号防乱序 —— 界面会把 A 的补丁挂在 B 的行上

**证据**：提交那一路有防乱序措施，注释明写「晚到的旧回包不许把界面钉在旧的那一笔上」（#819 发现 5）：
`vcReadCommitFiles` 的 `roll.seq` 逐次加一，回包按 seq 比对。但 `vcData.js` 的 `vcReadDiff`（未提交那一路）
**整个函数没有任何 seq 字段** —— 键只是路径。

**怎么触发的**：连点两行（A 再 B）时两枪并发；A 的回包晚到，就把 `diffs[keyA]` 写好，此时界面 `openDiff` 已经是 B，
于是一瞬间出现「B 的行开着、A 的补丁内容」。用户点得越快越容易撞上。

**修**：`vcReadDiff` 也带 seq，回包按 seq 落；组件侧对这一路补一道 stale drop（与提交那一路同款）。

### P2 换工作区后，旧工作区在飞的差异回包会写进新工作区

**证据**：`toggleDiff`/`retryDiff` 是 `loadDiff(row).then(function (next) { setReads(next) })`，
中间**不校验工作区**。而 #819 已经在身份行那条路上修过同一类问题（`vcApplyCommitReply` 有 stale drop）。

**怎么触发的**：在工作区 A 点开一行差异，趁 git 还在跑，切到工作区 B；A 的回包回来后 `setReads` 直接写进 B 的读数。
**这正是人最怕的「认错工作树」**，而且和已修的那条是同一个洞。

**修**：与 P1 一并解决（回包落地前比对 cwd 与 stateCwd）。

### P3 差异缓存只增不减 —— 内存单调增长

**证据**：`reads.diffs` 与 `reads.commitDiffs` 是两个普通对象，`.then` 里 `Object.assign({}, base.diffs)` 整份复制后加一条，
**没有任何淘汰、没有上限**。每份最多 200 行（`VC_DIFF_LINES_SHOWN`）。翻 200 个文件就是 200 份补丁常驻到面板卸载。

**修**：给两个缓存加条数上限（按首次写入顺序只留 40 条，超出的丢最先写的；反复点开同一份不会把它挪到队尾 —— 这不是 LRU，注释里已如实写清）。

### P4 连点同一行会起两个 git 进程

**证据**：`toggleDiff` 只在 `entryOf(row).state === 'ok'` 时跳过；`state === 'loading'` 时再点就会**再发一枪**。
每一次 `wf.gitDiff` 在宿主那边都要起一个 git 进程并读文件。`retryDiff` 更是无条件发。

**修**：`loading` 也跳过（同键在途不重复发）。

## 二、体验缺陷（人这次点名的）

### P5 首屏完全空白

**证据**：`vcBlocks.js` 第 10 行写明「面板刚打开、还没拿到数据（idle，或 loading 且没有旧数据）时回空数组：整块不画」，
`verify-818` 也有断言守着这条。从点开页签到第一屏出现，中间宿主要跑 `git status`、分支、工作树、提交好几条命令，
这段时间界面是全黑的 —— 用户分不清「正在来」与「坏了」。

**修**：还没拿到数据时回**骨架块**（身份行一条、计数三块、文件行若干、历史行若干），先到的那一块立刻换成真内容。

### P6 差异读取中只有一句文字，没有骨架

**证据**：`diffNode` 在非 ok 态画 `vc.diff.loading` 那一句文字。文字与补丁块高度不同，位置会跳一下。

**修**：改成骨架条（固定高度，不跳）。

## 三、记账（不是缺陷，但要知道）

- **每次 setReads 整块重建 DOM**：`blocks.map(node)` 没有 memo。折叠阶梯已把每批行数限死（上限 200），
  所以规模有界；点开一行差异会重建整页 200+ 节点。**可接受，记账**。真到量级再上 memo。
- **提交历史不走第二条路**：本来以为历史要另发一枪 `wf.gitLog`，读完发现首屏那一枪已经带了 `commits`
  （`vcScreenShapeOk` 明确要求 `s.commits` 是数组），`wf.gitLog` 只负责往回翻更早的。这条**不是问题**。
- **两个观察器都正确断开**：`ResizeObserver` 与 `IntersectionObserver` 都在 effect 的清理函数里 disconnect，
  `verify-709-no-self-continuing-timers` 也守着「不自续的定时器」那条不变量。**没问题**。
- **零定时器**：这一族没有 setInterval / setTimeout 自续。**符合纪律**。

## 四、这一版不做（记下理由）

- **虚拟滚动**：折叠阶梯已把单批行数限死（200），现在上虚拟滚动是给自己加复杂度，等真到量级再说。
- **给 diff 加 abort 通道**：宿主那条电话没有取消协议；用「回包落地前比对」这一道挡住污染，效果一样、成本低得多。

## 五、查完推翻的一条（照实记）

初查时我以为「提交历史要等第二条电话 `wf.gitLog`，所以历史这一块天生慢」。读代码后发现首屏那一枪已经带了
`commits`，`wf.gitLog` 只是往回翻更早的 —— 这条判断是错的，不写进修复清单。
写在这里是因为：审查的价值一半在于把错的判断也留下来，好让人知道哪条被查过。
