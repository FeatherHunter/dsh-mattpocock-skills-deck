## 一、要解决的是什么问题

两个会话开在同一个工作区里，一个正在构建，另一个同时在跑门禁或者开着界面。今天的构建没有任何互斥，会出四类事：

1. **读到缺文件或半截产物。** 真构建会先删 `package/lib`（除 client.js）、`package/shared`、`package/deck`、`package/tracker`，再逐个文件写回（`scripts/build.mts:1400-1423`）。每个产物文件都是 `writeFileSync` 直接覆盖，没有临时文件加改名（写文件助手在 `scripts/build.mts:162-166`，其余直写点在 1260、1302、1448、1483、1552、1784、1888 行）。另一个会话这时读产物，会读到「删了还没写回」或者「写了一半」的目录。
2. **构建缓存记下错误的一代。** `writeBuildCache()` 先算盘上产物哈希，再写本次输入指纹（`scripts/build.mts:141-158`）。两个构建交错时，A 可能把「B 刚写完的产物字节」记成「A 的输入指纹」，下一次判缓存命中就假绿，直接跳过构建。模块头注释里「构建进程是缓存唯一的写者」这句前提（`scripts/lib/build-cache.mts:11-12`、`scripts/build.mts:147`），在两个会话并行时不成立。
3. **固定名字的中间片段互相覆盖。** `.tmp/vocabulary.client.js`（`scripts/build.mts:1122-1125`）与 `.tmp/time-config.client.js`（`scripts/build.mts:1783-1786`）是同一个构建里先写后读的中间片段；两个构建交错会互相覆盖。`.tmp` 是点开头目录、在输入指纹里被跳过，所以缓存看不出这件事。
4. **界面被反复重载。** 入口产物文件每次真构建都会重写，修改时间跟着变，界面会重载（收尾递归 touch 已经删了，见 `scripts/build.mts:1555-1558`，但重写本身仍然会改修改时间）；两个会话交替构建时界面来回闪。

验证链这边已经默认了这件事：并行跑完只当第一轮，红的步骤再串行复跑一遍（`scripts/verify-parallel.mts:405-408`），注释里写的正是「有人正在构建时别人读产物」；预构建那一步的注释更直接——「预构建是提速手段，不是门禁：它失败不算链红（比如同一台机器上还有别人在构建，两边撞了）」（`scripts/verify-parallel.mts:310-312`）。

**为什么 worktree 实测之后还要做本票：** worktree 隔离已经证明成立（#1322、`research/1322-worktree-link-probe.md`）：每个并行会话用自己的 worktree，并在自己的树里独立装依赖，产物与构建缓存各一份、互不覆盖。但主工作区仍然只有一个——本机 link 只认主工作区的 `package/`，要在正在运行的界面里看到这次改动，就得在主工作区构建；两个会话都这样做时，冲突仍会发生。而且构建入口很多，全是独立进程：`npm run build`、`npm test`、`pnpm install` 后自动跑的 `prepare`、`npm run update:latest`、验证链预构建、五扇门禁自己起的构建（`tests/verify-1115-timer-handle.ts:139`、`verify-settings-view.ts:215`、`verify-settings-templates.ts:153`、`verify-settings-debug.ts:202`、`verify-1325-build-cache-nowrite.ts` 的 `runBuild()`）、以及人手敲 `node scripts/build.mts`。靠「记得别同时构建」约束不住这些入口。

## 二、今天树里已经有什么、缺什么

- **进程内的锁有现成写法。** `src/deck/shell/write-mutex.ts` 的 `withKeyLock` 是同进程里的「按 key 排队、先到先得」：默认等 60 秒（真源 `config/timeouts.yaml` 第 130 行 `keyLockMs`），等不到返回 `{ok:false, timedOut:true}` 不抛错，回调抛错时锁一定放行。它管不了构建子进程——构建是另外的进程，进程内队列看不见。
- **「临时文件 + 改名」的写法仓里也有。** `src/host/choiceStore.ts:303-319` 落盘时写 `<正式文件>.<uuid>.tmp`（`flag:'wx'` 独占创建）再 `rename`，失败时删掉临时文件；注释写明「改名之前崩掉时，正式文件仍是上一份完整内容」。门禁 `tests/verify-683-choice-store.ts` 已经按「`wx` 之后紧跟 `rename`」守这条写法。构建产物今天没用这个写法（见上面四类事）。
- **跨进程锁当前树里没有。** 全仓找 `wx` 只命中 `src/host/choiceStore.ts`、`tests/verify-683-choice-store.ts` 与两份研究笔记。`research/614-workspace-write.md:189` 记过一个旧实现：`src/host/updateStore.js:81-115` 用 `open(paths.lock,'wx',0o600)` 独占创建，里面写 pid 与时间，冲突时判活再接管，释放时核对 id，注释说「这是给同一台电脑两个宿主进程准备的」。这个文件当前树里已经不存在了，只能当形态参考，不能当现成可用的锁。
- **「跨进程不加锁」有过一次旧拍板，但它说的是日志。** `research/489-appendix.md:201-205`：两个宿主进程写同一个当天的日志文件时「以后写为准，前一次可能被覆盖，审计行可能少记，本轮不解决」。构建不能沿用这条——日志丢一行是良性损失，产物被覆盖不是：缺文件、半截文件、混合世代会让门禁假红假绿，还会让界面加载到拼不起来的一代。
- **验证链的车厢只在单个进程里有效。** `scripts/verify-parallel.mts` 把会起构建的步骤合成一节车厢、由一个工人依次跑（`280-318`），并在这节车厢最前面放一步预构建（`304-316`，`optional: true`）。这能管住「同一次 `verify:parallel` 内部」，但管不了另外启动的一个 `npm run build`、另一个会话的链、或者门禁自己起的构建。`scripts/verify-chain.ts` 里连预构建都没有，串行链只靠各门禁缺产物时自己补构建。
- **没有别处替这件事负责。** `.github/workflows/` 没有 `concurrency` 键；`docs/` 里没有讲跨会话构建互斥的说明（`docs/agents/verification.md:59` 只讲了车厢怎么合成）。

## 三、三个候选方案

| | 方案甲：文件锁包住真构建 | 方案乙：只做排程层互斥 | 方案丙：让并发无害（原子写 + 整代切换） |
| --- | --- | --- | --- |
| 做法 | 真构建全程拿一把跨进程文件锁，抢不到就等 | 不新增锁；只靠验证链车厢串行，再写规范要求「同一工作区同时只让一个会话构建」 | 产物写进本次构建独立的暂存目录再整体切换；缓存临时文件 + 改名；中间片段按构建独立目录 |
| 锁住哪些资源 | 产物树、构建缓存、`.tmp` 中间片段（整段构建都在锁里） | 同一次 `verify:parallel` 的步骤之间 | 不需要锁，写侧天然互不覆盖 |
| 跨进程有效 | 有效 | **无效**：`npm run build`、`npm test`、`prepare`、`update:latest`、门禁自起的构建、人手敲命令都是独立进程 | 有效，但读侧仍可能看到切换中的状态 |
| 改动面 | 小：新建一个锁模块 + `build.mts` 插两处 + 配置与门禁 | 最小：几乎零代码 | 大：`build.mts` 多处直写、生成器直接写 `src/`、先删再建清理、Windows 目录改名限制都要改 |
| 对验证链并发度 | 预构建与门禁自起的构建会排队；其余门禁并发不变 | 同进程内不变；跨会话靠人 | 不变 |
| 失败时的表现 | 等锁超时就让这次构建失败，并打印谁持有锁、什么时候开始的、锁在哪 | 冲突仍然发生，只是从「构建互相踩」变成「门禁偶发假红」，靠串行复跑兜底 | 写侧不会坏；读侧可能读到切换前的旧一代或切换中的混合状态 |
| 残留问题 | 读侧仍可能读到「另一进程正在重写」的混合世代；超时会让构建失败 | 把问题退回「靠人记得停手」，与地图「让并行成为正常用法」相反 | 缓存「先算产物哈希再写输入指纹」的假命中窗口仍在，写侧仍要串行 |
| 建议 | **作为本票的最小方案** | 可用的部分（规范兜底）归 #1321 | 单独立后续票，不塞进本票 |

### 方案甲：文件锁包住真构建（推荐）

具体设计：

- **锁的作用范围：从「确认缓存没命中、要真构建」到「写回构建缓存」。** 也就是 `scripts/build.mts:1651` 的 `if (tryBuildCacheHit(args)) process.exit(0)` 之后，到 `:2004` 的 `writeBuildCache()` 之后。缓存命中的路径不拿锁：命中时一个产物文件都不写（#1325 起就是这样，见 `scripts/build.mts:132-136` 的注释与打印），拿锁只会白等。整段范围同时盖住「产物写完」和「缓存写完」，再说一遍缓存那个假命中窗口必须在锁里。
- **拿锁之后先复核缓存。** 等锁的时间里，别人可能已经构建完了；拿到锁再调一次 `tryBuildCacheHit(args)`，命中就直接退出，不重复构建。这是为了「两个会话同时被触发、前一个刚构建完」这个最常见的场景。
- **锁文件放 `node_modules/.cache/`，与构建缓存 `dsh-build.json` 同一个目录。** 这样做的好处：锁跟着依赖目录走。每棵树独立装依赖时，每棵树有自己的锁，互不排队（配合 worktree 的推荐做法）；用目录联接把 `node_modules` 共享给别的树时，锁与构建缓存一起共享，跨树也排队——这与「构建缓存的写者必须串行」是同一件事。反过来把锁放系统临时目录（`os.tmpdir()`）会跟缓存分开：两棵树共享缓存却各拿各的锁，缓存还是会交错。锁文件自身也是一个文件，写坏了最多删掉重来，不影响产物。
- **拿锁用「独占创建」。** 用 `mkdirSync(lockDir)`（目录存在就抛 `EEXIST`）或者 `openSync(lockFile,'wx')`；仓里已有 `flag:'wx'` 的先例（上面第二节）。锁里写一份小 JSON：持锁进程的 pid、主机名、启动时间（`Date.now() - process.uptime()*1000`）、最近一次心跳时间、以及一个随机串用来核对「这把锁还是不是我放的」。写内容用「写临时文件再改名」或者「`wx` 建好后一次写完」，不要出现「锁建好了但内容是半截」的状态被别的进程读成坏锁。
- **心跳不保活，只证明锁还活着。** 持锁期间每隔一段时间更新一次心跳时间。定时器必须 `unref()`：它只负责刷新「锁还活着」的证据，不许替进程续命（与 `docs/adr/20261014-process-liveness-lease.md` 里「定时器只负责到点提醒」、#1114 的口径一致；注意那张 ADR 否掉的是「用轮询/心跳定时器保活进程」，这里心跳的意思是另一件事，实施时要在这行注释里写清楚区别）。
- **陈旧锁怎么恢复。** 判定顺序：读到的 pid 在本机不存活（`process.kill(pid, 0)` 抛 `ESRCH`），或者心跳时间超过阈值很久没更新，就认为持锁进程已经死了，接管这把锁（先把它改名成一个带时间戳的旧锁再重试创建，别直接删——删的时候可能正好有第三方在读它）。**活着的进程持锁超过等待上限时只报错、不抢**：两个活构建争一把锁时抢过来只会让两边都跑坏。再留一个人工闸 `--break-stale-lock`：打印当前锁的内容，人确认后删掉。这是给「pid 存活但进程实际卡死」这种少见情况准备的，不进自动判定。
- **抢不到锁就等，等多久是可配置的。** 上限登记在 `config/timeouts.yaml`（建议新键 `buildLockWaitMs: 300000`，即 5 分钟），沿用「全仓手写代码的时间参数只在这三份 YAML 写」的规矩，生成器 `scripts/generate-time-config.mts` 的键表与 `tests/verify-time-config.ts` 的逐键检查要同步加行。等待期间按固定间隔重试（例如 200-500 毫秒，别忙等），超时就 `throw`：打印持锁者的 pid、主机名、开始时间、锁文件路径、已经等了多久，并给出一句能照做的建议（等它结束；或者确认它卡死后用 `--break-stale-lock`）。
- **释放一定要发生。** 正常路径 `finally` 里释放：核对锁里的随机串确实是自己的，再删锁文件/锁目录。进程被 `throw`、被 Ctrl+C、正常退出时都要释放：在 `process.on('exit')` 里挂一个同步释放做兜底（同步删除，不能在这里做异步）。`process.exit(0)` 在锁范围外（`:1651`），不影响；不要用 `beforeExit` 代替，它对 `process.exit` 不触发。
- **锁的日志要能只看日志判断走到哪。** 加锁、等锁、接管陈旧锁、释放、超时失败各自是一条日志（事件名与字段按 `docs/design/335-logging-contract.md` 第 3 章判定常驻还是按需，字段白名单见 `research/489-appendix.md` 第 1 章；实施时同步那张对照表）。至少要能回答：这次构建等了多久、等的是谁、有没有接管过别人的锁。

**方案甲自己也要承认的失败模式：**

- 锁只排「写者」，不排「读者」。门禁与界面读产物时不会先拿锁，所以「另一个进程正在重写产物」的窗口不会消失：读者仍可能读到旧一代、新的一代、或者混合世代。这不是本方案引入的（今天就有），而且单写者已经把它从「两个写者交错写」缩到「一个写者正在写」；真要做到读侧也稳定，得等方案丙的「整代切换」。验证链对红的步骤串行复跑（`verify-parallel.mts:405-408`）继续作为兜底。
- 等锁超时会让构建失败。验证链的预构建是 `optional: true`，超时不会把链判红，但会白等到上限才继续；真需要产物的门禁自己起的构建如果超时，会如实红——这符合「失败要看得见」，但需要一个合理的上限。
- 锁放在 `node_modules` 里：有人 `rm -rf node_modules` 会把正在被别的进程持有的锁一起带走；这种操作本身已经在删依赖，写进规范即可（#1321 可以带一句）。
- Windows 上 pid 可能被复用。自动判定只看「pid 不存活」与「心跳过期」两件事，pid 被复用但心跳没更新时靠心跳兜底；诊断信息里同时打 `startedAt`，让人能看出不对。
- `npm run typecheck` 不在锁里：它的 `generate-*-config --check` 在生成物缺失时会现场生成一次（见 `.gitignore` 53、60-65 行注释），两个会话同时 typecheck 仍可能读到半截生成物。这属于读侧边界，本票不解决，写进「不解决什么」。

### 方案乙：只做排程层互斥

做法：不加锁，把验证链车厢（`scripts/verify-parallel.mts:98-114`、`280-318`）与预构建（`304-316`）当作唯一的排程点，再靠规范要求「同一工作区同一时刻只让一个会话真构建」。

好的一面：几乎零代码；同一次 `verify:parallel` 内部的并发度不变。

坏的一面：跨进程无效。车厢只在单个 `verify-parallel` 进程里有效；`npm run build`、`npm test`、`pnpm install` 后的 `prepare`、`update:latest`、门禁自己 spawn 的构建、人手敲的命令，全都绕过排程。插件/DSH 级的调度被地图的 Out of scope 排除了；再往上做仓库级队列服务，本质还是锁换一个名字。结论：乙只能把问题退回「靠人记得停手」，与地图 Destination「目标不是禁止并行，而是让并行成为正常用法」相反。它有价值的部分是「规范里写清楚什么时候必须停手」，那属于 #1321。

### 方案丙：让并发无害（原子写 + 整代切换）

做法：构建把产物写进本次构建独立的一棵暂存目录，全部写完再整体切换；缓存写临时文件 + 改名；`.tmp` 中间片段按本次构建独立命名。

好的一面：如果做到位，读侧也看不到混合世代，产物要么是上一代、要么是完整的新一代。

坏的一面：改动面很大，而且都在 `build.mts` 的核心路径上——`.tmp` 片段、逐文件直写、先删再建的清理（`1400-1423`）、生成器直接写 `src/` 的生成物；Windows 上目录改名有限制；界面热更该触发还是会触发。更关键的是，缓存那条「先算产物哈希再写输入指纹」的假命中窗口仍然要写侧串行，等于方案丙也躲不开一把锁。所以它是「方案甲之后再走一步」的独立票，不适合作本票的最小方案。

## 四、推荐方案：甲，最小实现边界（可直接转成一张实施票）

1. **新建 `scripts/lib/build-lock.mts`**：导出 `acquireBuildLock()` / `releaseBuildLock()`（内部管心跳），以及一个 `describeBuildLock()` 给超时错误信息用。模块只负责锁文件本身，不碰产物、不碰缓存；文件头注释写清锁的位置、等待上限的真源、心跳为什么 `unref`、陈旧锁怎么判。
2. **接进 `scripts/build.mts`**：`:1651` 缓存未命中之后拿锁，拿锁后复核一次缓存（命中就释放并退出）；`:2004` 之后释放；`process.on('exit')` 挂同步兜底释放；`--break-stale-lock` 参数在拿锁前处理（打印并删掉陈旧锁后退出，或者删掉后继续构建，二选一在实施票里定）。
3. **配置**：`config/timeouts.yaml` 加等待上限、心跳间隔、陈旧阈值三个键（建议名 `buildLockWaitMs` / `buildLockHeartbeatMs` / `buildLockStaleMs`，默认 300000 / 15000 / 60000 毫秒）；`scripts/generate-time-config.mts:115` 附近的键表加行；`tests/verify-time-config.ts:161` 附近的逐键检查同步加行。缺键要是构建错误，沿用现在的严格口径。
4. **验证链**：`scripts/verify-parallel.mts` 的预构建保持 `optional: true`，行为不用改（它现在会自动等锁，等到了就直接命中缓存）；只把日志区分开：等锁中、等锁后命中、等锁超时。这一条不改变「预构建失败不算链红」的既有逻辑。
5. **新增门禁 `tests/verify-1323-build-lock.ts`**：在临时目录里做子进程实验，至少断言——两个子进程争锁时真的串行（时间区间不重叠、后到者等到前者释放）；持锁进程自己抛错/退出时锁被释放；伪造一份 pid 不存活的陈旧锁能被接管；陈旧锁内容在错误信息里打印出来；等锁超时按配置上限失败且错误信息含持锁者 pid 与锁路径。真构建级别的并发人工验证一次（两个终端同时 `node scripts/build.mts`，观察后者等待并按缓存命中退出），不写进门禁（太慢，且依赖机器状态）。

## 五、不解决什么（本方案的边界）

- 不解决读侧「读者正好撞上写者」的问题（需要方案丙的整代切换，另立票）。
- 不解决 `npm run typecheck` 路径里生成器可能写生成源码的交错（不在锁内；而且它只在生成物缺失时发生）。
- 不解决跨机器、跨工作树独立依赖的并发（独立依赖天然各有一把锁；跨机器归地图 Out of scope 的验证链调度）。
- 不改变界面热更行为：构建仍会重写入口文件、界面仍会重载；只是两个会话的构建会排队，不会来回抢着重载。
- 不碰 DSH 的多会话模型（地图 Out of scope）。

## 六、怎么验收

- 两个终端在同一工作区同时跑 `node scripts/build.mts`：后启动的那个打印等锁信息，前一个结束后按缓存命中退出（产物不重写），退出码都是 0。
- 杀掉持锁进程（模拟崩溃）后再构建：能在陈旧阈值内接管锁并完成构建；错误信息与日志能指出发生过接管。
- 持锁进程抛错或 Ctrl+C 后，锁文件不残留；下一次构建不用人工干预。
- 构造一个「活进程持锁」场景：第二个构建等满上限后失败，错误信息含持锁者 pid、开始时间、锁路径；验证链预构建超时不会把链判红（`optional` 逻辑未被破坏）。
- `node --import ./scripts/ts-hook.mts tests/verify-1323-build-lock.ts` 全绿；`npm run verify:parallel` 全绿（尤其 `verify-1325-build-cache-nowrite`、`verify-time-config`、五扇会起构建的门禁）。
- 一次人工并发验证：两个终端同时构建，日志里能只看日志说清「谁先拿锁、谁等了多久、最后谁构建」。

## 七、加锁会不会降低效率、与多 worktree 流程是什么关系

**先说结论：走多 worktree 流程时，这把锁的代价是零；只有在「同一棵树里出现第二个构建写者」时它才会让人等，而那正是今天会互相踩、会出假红假绿的场景。**

### 开销发生在哪、有多大

- 锁只在**真构建**（缓存未命中）时拿。缓存命中的路径不拿锁——而验证链预构建之后的十几扇门禁、日常反复跑构建，绝大多数调用都是命中（命中约 0.2 秒，见 `research/1322-worktree-link-probe.md` 的实测）。
- 没人争用时的开销：一次原子创建加一次删除，本地盘上是亚毫秒级；持锁期间有一个 unref 的定时器，按默认 15 秒读一次心跳，不阻止进程退出。
- 争用时的开销要跟「不排队会怎样」一起算：两个构建同时改同一棵树，不是「两倍速度」，而是同一份工作做两遍，还互相覆盖产物与缓存。等锁的那个在前一个构建结束后**先复核缓存**，通常直接命中退出（约 0.2 秒），而不是自己再花 30 秒重建。所以排队省下的是重复劳动，代价最多是「前一个构建剩下的时间」。
- 验证链的并发度：受影响的是「含构建的那节车厢」，它在同一个 `verify-parallel` 进程里本来就是串行的；其余各路的 8 路并发不变。两个会话各跑一条链撞上时，先到的构建完，后来者命中缓存。
- 反过来算假红的账：一次并发假红要在第一轮之后串行复跑，至少多花几十秒到一分钟，而且会消耗人对门禁的信任。
- 实施代价：约一个锁模块（一百多行）、`build.mts` 两处插桩、三个时间参数、一扇门禁。

如果还想先看数字再拍板：可以在拍板前做一次小原型，量三组东西——无争用时一次构建多花多少毫秒、争用时「排队 + 命中」与「不排队重复构建」各耗多少秒、`npm run verify:parallel` 加锁前后各多少秒。这三组数能直接回答「值不值」。

### 与多 worktree 流程的关系

- 锁跟着**依赖目录**走（`node_modules/.cache/`）。每个 worktree 独立装依赖时，每棵树有自己的锁，互不排队——多 worktree 流程一次都不会撞锁，代价为零（#1322 实测：每棵独立装依赖 1.42 秒，缓存命中 0.23 秒，产物与主工作区逐字节相同）。
- 用目录联接把 `node_modules` 共享给几棵 worktree 时，它们会共享同一把锁。这是有意的：共享依赖时它们也共享同一份产物与缓存，本来就该排队。`research/1322-worktree-link-probe.md` 实测共享依赖下两棵并行构建「并发各约 18.9 秒、单棵约 10.6 秒」，缓存互相顶掉；排队后前一个 10.6 秒、后一个命中约 0.2 秒，反而更快。
- 主工作区仍然唯一：本机 link 只认主工作区的 `package/`，要在正在运行的界面里看到改动就得在这儿构建。#1322 记录里「把 link 指到某棵 worktree 再打开界面」那一步还没实测，在它实测并写进规范之前，主工作区构建不会消失——这把锁服务的正是这个残留场景，不替代 worktree，也不改变「worktree 优先」的流程。
- 一句话：**worktree 是首选的隔离手段；锁只补「同一棵树内还有第二个写者」这一块**。走 worktree 流程时锁几乎永远拿不到争用。

## 八、需要维护者拍板的事

**Q1 方案选型：采用「文件锁包住真构建」（方案甲），而不是排程层互斥（方案乙）或原子写 + 整代切换（方案丙）？**
➡️ 推荐采用方案甲。理由是构建入口全是独立进程，乙跨不了进程；丙改动面太大、且仍躲不开写侧串行，适合另立后续票。

**Q2 锁的粒度：锁跟着依赖目录走（`node_modules/.cache/` 里一把），而不是跟着「主工作区」走或放系统临时目录？**
➡️ 推荐跟着依赖目录走。独立装依赖时每棵树一把、互不干扰（配合 #1322 的 worktree 做法）；共享 `node_modules` 时锁与缓存一起共享、跨树也排队，符合「缓存写者要串行」。

**Q3 抢不到锁的行为：等待上限 5 分钟（可配置），超时让这次构建失败并打印持锁者信息；验证链预构建保持 `optional: true`，所以超时不会判链红？**
➡️ 推荐这样。5 分钟足够一次完整构建（约 30 秒）等待，又不至于让「真的卡死」无限等下去。

**Q4 陈旧锁恢复：pid 不存活或心跳过期就自动接管，活进程持锁超时只报错不抢；另留 `--break-stale-lock` 人工闸？**
➡️ 推荐这样。自动接管只处理「明确死了」的情况；活着但卡死的交给人工闸，避免两个活构建互相抢锁。

**Q5 `.tmp` 固定名字片段与缓存：本票只用「整段锁」盖住它们，不改成每次构建独立临时目录、不改「临时文件 + 改名」的原子写？**
➡️ 推荐同意。改成独立临时目录属于方案丙的一部分，单独一张票更清楚，也能让本票的实施面保持最小。

**Q6 票的编排：拍板后新建一张实施票（地图 #1319 的子票、带 `wayfinder:task` 标签）落上述 1-7 条，并让 #1321 追加 `blockedBy` 这张实施票（规范里要写清排队行为）？**
➡️ 推荐这样。设计票收尾只留设计结论与实施边界；实施与规范分开，验收各自清楚。
