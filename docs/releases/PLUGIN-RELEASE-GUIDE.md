# DSH（DeepSeek Harness）插件通用发布规范（可直接发给 AI 的参考文档）

> 用法：把本文件复制到任意 DSH 插件仓库，AI 读完即可按规范执行发布。后文的 DSH 都是指 DeepSeek Harness。
> 本文件不依赖任何一个具体插件的名字、仓库地址、版本号和目录结构，凡是因插件而异的地方都写成占位符（尖括号包起来的词），见第 0 节。
> 冲突规则：同一仓库内若另有更新日期的发布说明，以更新日期者为准。
>
> **总则：零手动命令 —— AI 全驱动，人只扫码一次**
> 整个发布旅程由 AI 驱动（AI 读本文档、执行构建、测试、打包、发布命令、创建议题和 Release、轮询验证结果），人只需要在浏览器授权页完成一次二次验证（扫码或点确认）。**不要要求人手动敲任何 git、npm、gh 命令**。本文档里的命令都是写给 AI 的执行清单和事后审计依据，不是让人去敲的。凡是要求人敲命令的发布过程，都视为偏离本规范，需要停下来审查。

## 0. 先填 5 个占位符（新插件接入时只改这里）

把下面 5 项换成你这个插件的真实值，后面所有占位符都按这里理解。建议把填好的值固定在仓库的一个小文件或议题模板顶部，AI 每次发布直接引用。

| 占位符 | 含义（第一次读也能懂） | 例子 |
|---|---|---|
| <PLUGIN_NAME> | 发布到 npm 官方源的包名 | dsh-my-plugin |
| <REPO_URL> | GitHub 仓库主页地址 | https://github.com/OWNER/REPO |
| <VERSION> | 本次发布的版本，形态永远是小写 v 加三段数字 | v1.2.3 |
| <DISTRIB_DIR> | 真正执行发布命令的目录。有的插件根目录禁止发布，真正的可发布包放在子目录里 | package 或 .（根即包） |
| <BUILD_CMD> | 你这个插件的构建命令 | node scripts/build.mjs、npm run build 等 |

填完再确认两件事：

1. **分发目录是哪个？**打开根 package.json，看有没有 private:true。有这一行，说明根禁止发布，真正的包在子目录（常见是 package/），发布时必须先进入该子目录；没有这一行且根就是包，分发目录填英文句号代表的当前目录。
2. **版本号现在写在几个地方？**至少有根 package.json 的 version；有分发子目录的插件还有第二处。把声明版本的文件清单记下来，作为第 1 节第 1 项的检查范围。

## 1. 每次发布必改的对外展示清单

对外展示的意思是：用户不读代码也能看到的地方。清单不随技术细节漂移，新增对外可视位置时先修订本规范。

| # | 位置 | 要求（AI 逐项核对） | 如果本仓库没有这个位置怎么办 |
|---|---|---|---|
| 1 | 所有声明版本的文件 | 版本号完全一致，都等于本次版本去掉 v 的数字部分（如 v1.2.3 对应 1.2.3） | 至少要有 1 处；有分发子目录的必须两处一致 |
| 2 | 中文 README 的安装示例 | 用户按文档复制的安装命令就是本次版本；文档里不能残留旧版本号 | 必须有中文 README；旧版本残留的检查方法是搜索上一个版本号，应为 0 处命中 |
| 3 | 英文或其他语言的安装说明 | 与中文 README 同源（同一个版本号） | 如果仓库没有第二语言文档，跳过本项并在发布议题里写一句无第二语言文档，已跳过 |
| 4 | 分发包内的说明（如 package 目录下的 README） | 开头第一段明确写出当前版本 | 如果分发目录没有独立说明文件，跳过并记录 |
| 5 | CHANGELOG 新增一节 | 按固定模板写：日期、版本、主题、一句话提炼、对应提交区间、验证过程、用户影响；与 GitHub Release 说明文字相同 | 必须有 |
| 6 | GitHub 仓库 About 描述 | 与分发包 package.json 的 description 是同一句话；人类第一次读就能准确理解是做什么的；不写夸大的话；里面出现的每个数字和能力名都能在发布产物里搜到 | 必须有；改描述前先在产物里检索 |
| 7 | GitHub 话题（Topics） | 始终包含 dsh-plugin，保证能被插件市场和搜索发现 | 必须有；用仓库设置或接口查询确认 |
| 8 | 包的介绍与关键词 | description 与 About 同源；keywords 包含 dsh、dsh-plugin 等能被发现的词；插件市场名录只在介绍有实质变化时才更新，不为单纯递增版本号去打扰市场 | 市场更新遵守三条：只改自家条目、不手改生成产物、介绍里有冒号时给整句加引号 |

产物白名单：允许装进发布包的文件名单由分发包 package.json 的 files 字段锁定。发布前用打包预览命令检查实际文件清单，只含白名单，不含密钥、私密文件和多余文档。

## 2. 文档写法要求：同源、诚实、人类第一次能读懂

- 同一句介绍在 About、包描述、市场条目里保持一致，逐字对应，不要各写各的。
- 数字和能力名先有事实再写文案：对外说自带多少个技能、支持哪些平台之前，先在产物里逐项搜到依据。
- 安装命令的版本号与本次发布同源：中文、英文、分发包内三处的锁定版本互相一致，且等于本次版本。
- 致谢名单随发布更新：新版本合入了外部贡献（Issue、合并请求、讨论）时，在 README 致谢区按现有体例增补一行，只写已经发生的事，不借机宣传新功能。每次发布核对一次有无遗漏。
- 变更历史每节建议包含：发布日期、本次版本、一句话主题、做了什么（分点提炼）、对应提交区间、跑过哪些验证、对用户有什么影响。同一文字复用到 GitHub Release 说明。

## 3. 版本号与提交口径

- 修补版本递增（最后一段数字加一，如 v1.2.3 到 v1.2.4）：只修缺陷和收口性改动，没有用户能感知的新能力，不破坏已有用法。
- 次版本递增（中间数字加一，如 v1.2.3 到 v1.3.0）：新增了用户能感知的能力，但老用法依然有效。
- 主版本递增（第一段数字加一，如 v1.2.3 到 v2.0.0）：破坏了已有用法，用户升级必须改东西。
- 标签形态永远是本次版本（如 v1.2.3），指向该发布的提交。
- 发布提交的标题用中文完整句子，不少于 10 个字，说清版本和主题，例如发布 v1.2.3：某某问题修复与文档同步。

## 4. 四种插件形态的差异对照（只看属于你的那一行）

| 形态 | 是什么样的插件 | 构建与验证的差别 | 已装形态验证看什么 |
|---|---|---|---|
| 工具包 | 只有服务端逻辑，给 AI 提供可调用的工具，没有界面 | 构建一般最轻；冒烟重点是工具能列出、能调用 | 在 DSH 里确认工具列表出现且能试调用 |
| 守护循环 | 定时器加模型自主循环，在后台长期跑 | 构建外多看定时与循环启停；冒烟加测能启动、能停止、不残留 | 确认循环能启动并在卸载后干净退出 |
| 界面面板 | 有浏览器界面面板加服务端逻辑 | 构建常分两端（界面端与服务端），两端产物都要新鲜且一致；冒烟加测界面能渲染 | 在已装 DSH 里打开面板，版本号可见且面板行为符合本版内容 |
| 混合 | 以上能力的组合 | 取各相关行的并集 | 工具、循环、面板逐项确认 |

如果你的插件是脚手架生成的，构建命令以脚手架实际生成的脚本为准（占位符 BUILD_CMD 填它），不要硬套其他插件的脚本名。

## 5. 隔离门禁（任一条不通过就阻断发布）

隔离的意思是：在临时目录或不污染当前工作区的方式下检查，不把半成品写进工作区和已安装的 DSH。

1. 隔离构建：用构建命令构建一次，产物不落当前工作区（或构建前后能证明工作区干净）。
2. 产物新鲜与一致：构建产物的时间新于源码；如果插件是一份源码产出两份产物（如根产物与分发目录产物），两份要逐字节一致；单产物的插件只验新鲜。
3. 测试与打包预览：跑通本仓库约定的测试命令（如有冒烟测试则必须全过）；再跑 npm pack 预览，检查文件清单只含白名单，不含密钥和多余文件。
4. 官方源包名预检：显式指向官方源并跳过本地缓存查询包名，例如 npm view 包名 --registry 官方源地址 --prefer-online，避免被镜像延迟误判。

以上任一条失败都不进入发布，只能先修好再重走。

## 6. npm 发布子流程（AI 执行，人只做浏览器二次验证）

完整链路是：环境检查、登录态检查、打包预览、发布、官方源验证。遇到报错先查 npm-publish 技能的失败分支表（不同错误码各有一类原因），不要猜。

- 登录与发布都显式指向官方源（带上 registry 参数），不重定向输出。
- 必须在分发目录里执行发布。根 package.json 写了 private:true 的仓库，在根误跑发布会被拒绝，这是预期的保护，不要删掉该字段去修它。
- 必须在可交互终端里执行发布。后台任务、无交互终端、输出重定向下的发布会报一次性口令错误且不给授权链接，这是已知限制：Windows 下由 AI 用系统任务计划在用户桌面弹起可见的交互式发布窗口，用户在窗口内按回车、去浏览器完成二次验证、再按回车；其他系统用各自等价的可见终端方式。
- 网页登录态不能代替发布时的一次性口令：即使刚登过录，写操作依然要过浏览器二次验证。二次验证只在交互终端弹出的浏览器授权页完成，不隔空传一次性验证码。
- 发布前包名占用预检始终跳过缓存。

## 7. 发布顺序与无回滚（AI 按序执行）

顺序固定为：

1. 本地门禁全绿后提交并推送到主分支（AI 执行 git 提交与推送）。
2. 发布到官方源（AI 在交互窗口执行 npm publish，人在窗口内按回车、去浏览器完成二次验证、再按回车；实际命令先进入分发目录再执行）。
3. 查询验证（AI 执行 npm view 查询，能查到本次版本）。
4. 打标签并推送（AI 执行 git tag 与推送标签）。
5. 创建 GitHub Release 并附产物说明（AI 执行 gh release create，说明文字与 CHANGELOG 同文）。
6. 验证已装形态（AI 在已装 DSH 里验证，见第 4 节最后一列）。

不提供回滚操作。出问题时递增下一个修补版本覆盖，流程保持极简。不可逆操作永远排在可逆校验之后。

## 8. 插件市场名录的按需更新

- 只在介绍有实质变化或文字可优化时才更新市场条目，不为单纯递增版本号频繁打扰市场。
- 更新时只改自家条目，不手改市场自动生成的产物；分类选最贴近的一项，不纠结。
- 介绍逐项对应真实能力；介绍文字含冒号时给整句加引号，保证市场检查一次通过。
- 分发包里的介绍与市场描述同源。
- 操作序列遵循 awesome-dsh-plugin-submit 技能（只改自己文件、重新生成目录、不手改产物；先发布 npm 再收录体验更好）。

## 9. 双入口：网页卡与一句话对话（两种触发，同一模板）

- 网页入口：仓库的议题模板选择器里放一张发布卡，点卡填版本号即创建发布议题，后续由 AI 接手。
- 对话入口：人对 AI 说一句话，例如按通用发布规范发版 v1.2.3，AI 找到本规范与发布议题模板，代为创建发布议题并执行发布。没给版本号时必须追问，不能猜。
- 两个入口创建的议题正文逐字一致，都由同一模板渲染，首行即引用本规范。
- 零手动命令校验：如果发布要求人手动执行创建议题、git、npm 命令，即视为偏离双入口设计，需要审查。

发布议题模板建议包含：首行规范引用、版本信息（版本号、生效规范、标签、提交标题要求）、对外展示清单复选框、隔离门禁复选框、发布验证复选框、发布顺序、备注（含版本号追问规则、市场按需原则、致谢规则）。本仓库若已有模板，把其中的具体插件名、仓库地址、旧版本号替换为对应占位符即可复用。

## 10. 验证（AI 执行，人只看失败时的待改清单）

- 推荐做法：仓库放一个单一高层校验脚本（例如 node tests/verify-release-contract.js --version 本次版本），一次覆盖第 1 节清单与第 9 节双入口一致性，失败时打印待改清单并以非零退出码阻断发布。向导或人工流程的首段即调用它。
- 还没有校验脚本的新插件：AI 按第 1、5 节逐项手工核对，把每项的校验方式写进发布议题的复选框里（如文本对比、搜索旧版本 0 命中、接口查询、打包预览），一项一项勾选。等发布两次稳定后再把高频检查沉淀成脚本。
- 已有向导脚本的仓库：向导只负责分段、进度、打开链接、确认、记录已填值、可中断重跑，真正的是否放行由校验脚本决定。没有向导的新插件可以先不要向导，用对话入口加手工清单走两版，痛点清楚了再按 wizard 技能补向导。

## 11. 新插件第一次接入的最小步骤

1. 复制本文件到新仓库（例如 docs/releases/PLUGIN-RELEASE-GUIDE.md）。
2. 填好第 0 节的 5 个占位符。
3. 按第 1 节表格的第四列，把本仓库没有的位置逐项标记为跳过并写原因，剩下的就是你这个插件的发布清单。
4. 准备发布议题模板（网页卡与对话模板同源，首行引用本文件）。
5. 跑一遍演练：只走第 5 节门禁与打包预览，不执行第 7 节的真发布，确认清单无遗漏。
6. 第一版真发布时让 AI 全程按第 7 节顺序执行，人在浏览器授权页只扫码一次。
