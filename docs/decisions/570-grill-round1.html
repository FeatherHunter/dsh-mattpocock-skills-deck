Q1

目标：第一批脚本到底管哪几条写回？

范围不清，后面参数和返回都没法定。这是根决策。

📖 前因

#570 Question 写的是“三件事”：正文格式、子议题关联，外加阻塞写法与数量校验。#568 补记又加了一句“写回脚本必须统一走文件输入”。但“重试留痕”的评论算不算正式管辖没说死——前置输入②说它“只定行为，不单独成脚本”。

⚠️ 后果

如果评论不算管辖，脚本的返回格式就只管三件事，评论失败可以只记日志；如果算管辖，评论也要走文件输入、进回包、进门禁。两种做法的验收清单差一整条，现在不定，下轮参数对不上。
🔑 帮你决策的关键信息
· 正文写回统一走文件输入（#568 补记），终端已有 --body-file 可用，宿主 issues-write.js / comments.js 当前全是行内 --body（搜不到 --body-file）。
· 子议题建边 = 先取数据库编号（--jq .id，不是 # 号）→ 建边 → 查计数（sub_issues --jq length）。
· 阻塞加边 = GitHub 原生依赖边优先，文字行只做降级（#569 修正输入）。
  • A · “3+1”：三件正式管辖 + 评论为附带行为（推荐）正文、子议题、阻塞进契约和门禁；评论只定行为（失败重试一次并留痕），同样走文件，但不单独成脚本。
  • B · “3+0”：评论完全不管脚本只管三件事，评论留痕以后再说。
  • C · “4”：评论也算正式管辖评论写回同样进回包和门禁，与正文同等验收。
➡️ 推荐答案：A
理由：前置输入②原话就是“重试留痕只定行为”，B 把它丢了违背前置，C 把它升格会扩大第一批范围。A 既守住前置，又顺手落实了 #568“统一走文件输入”（评论也是正文，一起走文件最省事）。
✅ 选 A 的利❌ 选 A 的弊 / 选 B、C 会怎样
不违背你已定的前置；验收清单最小可用；评论同样走文件，避开 PowerShell 引号坑。回包要多一个“评论是否留痕”字段（小成本）。选 B：失败无痕，以后查问题断链。选 C：第一批变大，门禁多一整条评论验收，拖慢落地。
Q2

边界：这三条“不做”是否成立？模板改不改？

边界不定，脚本会越写越大，第一批收不住。

📖 前因

前置输入③④说宿主不动、Markdown/GitLab 不写新脚本。但新建需求模板里阻塞那句是无条件文字行（用 Blocked by: #<n> 行表示阻塞关系，不分后端），和跟踪文档的“原生优先”打架（#569 打架点第一、二、六条）。这批要不要连模板一起改，必须现在定。

⚠️ 后果

模板一动，牵到提示词门禁（verify-prompt-newlines / verify-prompts）和两处技能措辞（to-tickets 是条件写法、新建需求模板是无条件写法），第一批立刻变大。不动模板，脚本行为和模板文字会暂时不一致，需要一句备注顶住。
🔑 帮你决策的关键信息
· 宿主 setParent 在 GitHub 语义齐全，GitLab 缺换父先解旧绑，Markdown 直接报不支持——三后端行为本就不一致，第一批只做 GitHub 是为了避开这个坑。
· 模板打架是事实（#569 第六条），但修模板 = 改 prompts.js newWayfinder v13 + 重跑 node scripts/build.mjs + 过两道门禁，工作量另算一票。
  • A · 三条“不做”成立，模板这批不动（推荐）宿主不动、另两后端不写新脚本、规格先行不选；脚本内先按“原生优先、文字行降级”做，模板措辞留到规格票再收。
  • B · 模板这批一起改脚本判定口径和模板措辞一次对齐，无条件文字行改成按后端条件写法。
➡️ 推荐答案：A
理由：第一批目标是“让脚本行为正确”，模板是“让提示词文字正确”，两件事可以分两票。一次全改，门禁和回归面翻倍；先让脚本跑通，模板不一致处用一句备注顶住（“已知不一致，以脚本判定口径为准”），规格票再收模板。
✅ 选 A 的利❌ 选 A 的弊 / 选 B 会怎样
第一批最小可落地；不碰提示词门禁；三后端差异 confined 在 GitHub 一房。短期内脚本行为与模板文字有一句不一致（需备注）。选 B：要过 verify-prompts / verify-progress / verify-map-subissues-352 三道门禁，第一批延期。
Q3

风险：三道门禁先死守哪一道？

资源有限，门禁必须有先后。排第一的写进脚本的强制失败语义。

📖 前因

两份研究报告摆出三个真坑：A 是 PowerShell 吞引号和 @me（#568 第 4/5 节实证）；B 是开头不可见字符和字面转义污染（normalizeBody 阈值兜底）；C 是只写清单不建原生边导致面板 0/0（#345 从 0 补到 6）。

⚠️ 后果

排第一的风险进脚本的“硬失败”（报错不吞、门禁变红）；排后面的进“软提醒”。排错了，脚本在你机器上（Windows PowerShell）第一次跑就栽，或者面板统计继续错而不自知。
🔑 帮你决策的关键信息
· A 是必现：Windows PowerShell 5.1 调原生命令吞内嵌双引号，@me 不加引号直接报缺参数。宿主走参数数组无此坑，但脚本走终端，有此坑。
· C 是最贵：#345 的 0/0 是线上事故，补链要逐子票取编号再建边。面板快照只认原生边，清单写得再全也不进统计。
· B 有兜底：normalizeBody（真实换行 < 2 且字面转义 ≥ 1 才还原）+ 门禁 verify-progress T16 / verify-parse-leaf 钉住，最多难看不断链。
  • A · 文件输入强制（推荐第一）长正文一律走文件，不走行内参数。违了直接报错。
  • C · 数量校验强制（推荐第二）建边后查计数，与预期不一致就报错不吞，纳入面板计数验收。
  • B · 正文正规化检查（推荐第三）写回前检查开头不可见字符与字面转义，命中则告警并按阈值还原。
➡️ 推荐答案：A > C > B
理由：A 不守则脚本在 Windows 下必错；C 不守则错了还显示正常（0/0 两种含义分不清）；B 有现成兜底，可以只告警不断链。三道都做，但硬失败的先后是这个序。
✅ 这样排的利❌ 排错了会怎样
脚本第一次跑就成（文件输入绕开 shell）；统计错了立刻现形（数量对不上就报错）；B 只告警，不误伤正常正文。把 B 排第一：正常正文可能被误还原，门禁噪音大。把 C 放最后：#345 重演，面板 0/0 还以为是空地图（#369 是故意空，#345 是意外空，数字一样）。
⚠️ 场景对照：#369 是故意为空的验证地图（0/0 正确），#345 是意外没挂对的事故地图（0/0 错误）。只看数字分不清，必须靠“边在不在 + 数对不对”的回包区分——这就是 Q1 回包字段的由来。
