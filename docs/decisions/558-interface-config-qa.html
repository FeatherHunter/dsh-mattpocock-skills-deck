用词说明：全程用“日志系统”指代日志功能本身。下面的“电话”都是指宿主接口方法，“落盘”都是指宿主统一写本地文件的动作，“丢弃数”都是指写不下、发不出时只计数不抛错的那个累计数。

把日志系统落地成一个独立的 TS npm 包（装日志系统的那个包），任何 DSH 插件照着文档就能集成使用。当前插件（dsh-mattpocock-skills-deck）是第一个用户，迁移过去行为零变化。

Q1：5 个电话名用哪种方案？

前因现状

日志系统两端各有一套活。宿主侧现在是两份文件：管内存队列、级别判断、按天文件名、单写者刷盘、失败计数的那份，和管导出、清空、开关三个电话实现的那份。客户端侧现在是一份拼进插件主文件闭包里一起运行的文件。

两端现在共用 5 个电话，老名字和载荷如下（这就是“行为零变化”的起点，只许参数化、不许悄悄改语义）：

  • 批量上报电话：客户端调 wf.logBatch，入参是日志条目数组（entries）加客户端累计丢弃数（droppedCount），回参是是否成功（ok）加接收条数（accepted）加宿主侧累计丢弃数（dropped）。有个如实记录的例外：宿主最外层用 try 包住，万一进 catch，回的是成功加接收 0 条（ok 为真、accepted 为 0）。
  • 导出电话：客户端调 wf.logExport，入参是可选日期（date），多传的字段现状忽略（比如多传 format:'zip' 也被忽略，行为不变）。回参是是否成功加文件名加字节数（bytes）加回退标记（fallback）加当天日志原文（text）加系统信息摘要（summary）加目录与路径（dir/path）。注意 bytes 是日志原文的字符串长度，不是真实字节数。
  • 清空电话：客户端调 wf.logClear，入参是某天或全部（date 为某天或 all），回参是是否成功加删掉几个文件（removed）。
  • 开关读电话：客户端调 wf.logGetSwitch，入参是空对象 {}（启动对账就是这么调的，不是无参）。回参是是否成功加是否开启加采样率。
  • 开关写电话：客户端调 wf.logSetSwitch，入参加是否开启加采样率；宿主只回是否成功加实际生效的是否开启（ok 与 enabled，不回采样率）。采样率以客户端本地存的值为准：写成功后客户端用请求时的采样率更新本地，不等宿主回。

失败语义现状：失败只计数不抛错。写盘失败、队列满、转发失败都只加到累计丢弃数里；所有电话失败都回“是否成功为假”的结构，不抛异常，唯独批量上报电话的最外层例外回成功加接收 0 条；开关读写失败保持旧值。

选项利弊

选项做法（大白话）好处代价
选项 A：沿用现名5 个电话名一字不改凍结。插件标识只进配置和文件名，不进电话名。当前插件迁移零改动，门禁断言不用改字面，讨论成本最低。第二个插件一接入就撞名：两个插件注册同一批电话名，宿主分不清日志该落到谁的目录。
选项 B：加插件前缀（推荐）建日志系统的工厂多收一个前缀参数，新电话名 = 前缀 + 点 + 动作名（动作名 logBatch、logExport、logClear、logGetSwitch、logSetSwitch 五个不变）。默认前缀是 wf，拼出来与现状一字不差。前缀只隔离电话名，磁盘隔离另靠目录默认派生。多插件同宿主不撞名；默认前缀下当前插件迁移零变化；第二个插件传自己的前缀就能模拟真实隔离。两端各多一层拼名字的小逻辑；门禁模板断言要按前缀参数化，不能写死字面；文档要写清默认和自定义两条路。
选项 C：电话名不变，通道内带标识5 个电话名不变，每次传日志和读写开关都多带一个插件标识字段，宿主按标识分到不同目录和文件。宿主注册表不膨胀，电话名永远 5 个。宿主按标识分开存放的逻辑最复杂；旧客户端不带标识时归到谁要另定；设计面比拼名字大得多。

选项 B 的配套细则（拍板后直接冻结）：前缀默认等于插件标识，默认都是 wf，当前插件两处都是 wf所以零变化；允许配成不同值但文档推荐保持一致。标识与前缀只许小写字母、数字、中横线，长度 1 到 32，不许含点（点留作分隔符），大写直接报错不静默转小写，不许含文件不安全字符。磁盘默认派生：标识 wf 时子目录名就是 logs、开关文件名就是 log-switch.json（与现状一字不差）；其他标识时子目录是 logs-标识、开关文件是 log-switch-标识.json，都允许显式覆盖。实例各自独立（内存队列、丢弃数、开关状态互不串）；已注册的电话名再注册时报错、不覆盖旧的；默认前缀 wf 只给当前插件用，第二个插件必须配自己的前缀。

推荐理由

推荐：选项 B，加插件前缀，默认前缀为 wf。
理由一：三个选项里唯一同时满足“行为零变化”和“多插件不撞名”的，默认拼出的字面与现状一致，迁移不用改调用处。
理由二：改动面最小且集中在拼名字一层，不碰“失败只计数不抛错”的语义，不碰日志系统的 55 个事件对照。
理由三：给第二个插件验证留了真实隔离的路，符合地图终点“任何插件照文档能集成”的要求。
不选 A：验证票一到就撞名，现在省事以后返工。不选 C：分开存放加旧客户端兼容两套复杂度，远超拼名字。

定错后果

如果定成 A，第二个插件验证时必撞名，要么日志串目录，要么后返工改电话名，连带门禁断言和文档一起返工。如果定成 C，宿主分队列分文件的复杂度一次性压到引擎实现上，旧客户端兼容规则还要另议，工期最不可控。

对 #559 / #560 / #561 的影响

  • 对 #559（宿主引擎的 TS 实现）：照搬现实现即可，另加前缀参数拼注册名，目录与文件名策略可配，撞名报错不覆盖。
  • 对 #560（客户端引擎的 TS 实现）：工厂函数加前缀参数，转发与开关读写调拼出来的名字；直接引用和文本拼接两种消费方式都要把前缀原样传给下一层。
  • 对 #561（事件清单格式与通用门禁）：字段白名单与计数检查收前缀参数做断言，默认前缀下的断言与现状一致。

Q2a：文件名默认形状是否保持按天？

前因现状

日志系统现在的落盘形状是按天文件名：年月日点 log（比如 2026-09-06.log），每天一个文件，只按天分文件，不自动清理。本票问题描述里建议的四段式（日期.插件名.进程号.启动时间）目前只是建议，代码现状仍是按天。

选项利弊

选项好处代价
保持按天为默认（推荐）当前插件迁移首版不改落盘形状，旧文件、导出、清空逻辑全部对得上，零变化铁律最稳。多进程同时写同一天文件时靠单写者排队，四段式的进程隔离好处暂时吃不到（但可选项里留着）。
默认直接切四段式新文件自带插件和进程信息，查问题时一眼看出是谁写的。落盘形状变了，旧文件匹配、导出清空正则、门禁断言全要改，违反迁移零变化，风险最大。

推荐理由

推荐：默认保持按天（fileNamePolicy 默认 daily），迁移票首版不改落盘形状。
理由：约束写明“现 5 个接口的形状是起点”，落盘形状同理也是起点；先保零变化，再用可选项满足新需求，这是成本最小的顺序。

定错后果

如果默认切四段式，当前插件一迁移就产生新形状文件，旧的按天文件对不上导出和清空的匹配，等于悄悄改语义，后面要补迁移旧文件的办法，地图范围会被撑大。

对 #559 / #560 / #561 的影响

  • 对 #559：宿主默认走 daily 分支（现有按天正则），四段式只做可选分支。
  • 对 #560：客户端基本无感，不用改转发逻辑。
  • 对 #561：门禁模板默认按按天形状断言，四段式断言只在开选项时启用。

Q2b：四段式做可选项时，细节是否按“定死版”冻结？

前因现状

四段式的四段是：日期点插件标识点进程号点启动时间。现状是建议，具体取值还没落字。宿主已有启动头写入（writeStartupHeader 写入的 pid 与 startedAt）可以作为启动时间的依据。

选项利弊

选项好处代价
按定死版冻结（推荐）：插件名取配置里的插件标识、进程号取不到回退 0、启动时间取宿主建日志系统那一刻（以现有启动头 pid 与 startedAt 为准）；清空与导出里按天匹配的正则随策略分支（daily 走现有按天正则，四段式走对应四段正则）各插件文件名形状一致，清空导出不会误匹配，查问题可比。灵活性少一点，想自定义段顺序的人要显式覆盖文件名策略。
不定死、留灵活各插件可按自己喜好拼文件名。文件名各异，清空导出正则要写一堆兼容，跨插件查问题对不上，门禁也没法统一断言。

推荐理由

推荐：按定死版冻结（含进程号取不到回退 0、正则随策略分支）。
理由：文件名是跨插件对账的依据，越死越不容易错；回退 0 保证极端环境也不崩；正则随分支保证清空导出与落盘形状永远成对，不会删错文件。

定错后果

如果不定死，第二个插件传个别的插件名或时间格式， clearing（清空）和导出就会漏文件或误删文件，旧的按天正则和新的四段正则混用最容易出错。

对 #559 / #560 / #561 的影响

  • 对 #559：宿主按策略分支拼文件名、选正则，启动头取值逻辑写死一处。
  • 对 #560：客户端只传插件标识，不拼文件名，无额外负担。
  • 对 #561：门禁按策略分支分别断言文件名形状，避免一刀切误报。

Q3：配置项里哪些必填、哪些可选？

前因现状

日志系统现在没有“配置面”的概念：宿主建日志系统时调用方传入五个依赖（文件服务、计时器、取缓存目录函数、取平台函数、默认工作目录），目录名 logs、开关文件 log-switch.json、防抖 1000 毫秒全是写死的；客户端靠闭包里现成的四个名字（宿主调用器、计时器、本地存储、开关广播函数），后继要求全部改成调用方传入。本地开关存本地存储键 dsws.debug，形状是是否开启加采样率加版本号，默认关闭；批量转发上限每批 50 条、每 1000 毫秒一次、单包约 128KB 或队列 100 条先到先截，裁掉记丢弃数；开关看门狗超时 5000 毫秒只记一行告警。

选项利弊

选项好处代价
只有插件标识必填，其余全有默认（推荐）：pluginId 必填无默认；prefix 默认 wf；logDirName 默认派生（wf 时为 logs，其余为 logs-标识）；switchFileName 默认派生（wf 时为 log-switch.json，其余为 log-switch-标识.json）；fileNamePolicy 默认 daily新插件只填一个标识就能跑，当前插件两处都是 wf所以零变化；默认派生又保证第二个插件不撞目录。文档要讲清派生规则，多一小节。
全部必填每次配置一目了然。当前插件也要重写一遍与现状相同的字面，多改多错，新手接入门槛高。
全部可选（含标识）写起来最短。不填标识就分不清日志是谁的，默认目录必撞，多插件直接串味。

推荐理由

推荐：必填只有插件标识（pluginId），其余全有默认。
理由：标识是隔离的根，不知道是谁就没法分目录、分电话名，必须强制填；其余都有与现状一字不差的默认值，不填就是零变化，填了才是定制，这是对当前插件最友好的形状。

定错后果

如果全必填，迁移票要手写一堆与现状相同的值，抄错一个就变行为变化。如果全可选，第二个插件不填标识直接撞目录撞电话名，日志串味后很难拆。

对 #559 / #560 / #561 的影响

  • 对 #559：宿主建日志系统的工厂按“必填校验 + 默认派生”实现，缺标识直接报错，目录与开关文件名走派生或显式覆盖。
  • 对 #560：客户端工厂同样校验标识、前缀拼名字，其余用默认。
  • 对 #561：门禁模板把标识当必填断言缺失，把前缀、目录、策略当带默认的可选断言。

Q4：导入路径是单入口还是双入口？

前因现状

日志系统天然分两端：宿主端管队列和落盘，客户端端管采集和转发。现在宿主是两份文件、客户端是一份拼进闭包的文件。问题描述要求拍板：包对外是一条入口，还是宿主入口与客户端入口分开。

选项利弊

选项好处代价
双入口（推荐）：包名下分宿主入口与客户端入口两条，文本拼接消费方式只走客户端入口的声明体文本宿主写盘代码进不了客户端闭包，体积小、不串环境；两端可各自演进。文档要写两条导入路径，多几行字。
单入口导入写法只有一种，好记。客户端闭包会把宿主写盘依赖一起打进去，体积大还可能在客户端环境报错；文本拼接时要手挑声明体，容易挑错。

推荐理由

推荐：双入口，文本拼接只走客户端入口的声明体文本。
理由：两端运行环境本来就不同（宿主能写盘、客户端只能调电话），硬合成一条入口就是把宿主包袱背到客户端身上；双入口让“拼进闭包”的老消费方式有明确的文本来源，不会误拿宿主代码。

定错后果

如果定成单入口，客户端闭包体积变大、可能引用到客户端没有的文件服务，运行时报错；文本拼接一旦拿错段，会把宿主逻辑拼进客户端，问题隐蔽难查。

对 #559 / #560 / #561 的影响

  • 对 #559：宿主引擎只走宿主入口，实现建日志系统的工厂。
  • 对 #560：客户端引擎只走客户端入口，实现转发与开关读写，文本拼接消费方式的声明体文本来源就此定死。
  • 对 #561：门禁模板按入口分别引用断言，不会把两端事件混到一起计数。

Q5：版本策略是否按冻结清单冻结？

前因现状

日志系统要变成公开包，就得回答“以后怎么算破坏性变更、什么时候能拆”。现状是没有版本策略，改了电话名或参数形状也没人拦。后继冻结清单草案给了完整版本策略：语义化版本；破坏性变更五类；日志系统的公共接口连续 3 个版本无破坏性变更之前不议拆，自首个公开发布起算（承接落点票的过渡条件）。

选项利弊

选项好处代价
按清单冻结（推荐）：semver；破坏性变更指电话改名、增删改入参回参形状、改配置写法、改事件清单字段形状、改文件名策略默认形状；连续 3 个版本无破坏之前不议拆，自首个公开发布起算后继三票敢按冻结接口写实现，调用方敢升级；拆分也有门槛，不会拍脑袋拆。冻结期内想改接口要走大版本，流程重一点（但这正是要的效果）。
不冻结、以后再说眼下少一条要拍板的事。后继实现心里没底，随意改名改参，迁移成本全压到调用方；门禁也不知道按哪版卡。

推荐理由

推荐：按后继冻结清单里的版本策略冻结（含破坏性变更五类与 3 个版本起算）。
理由：公开包的第一信用就是“接口稳定”，先把什么算破坏、几个版本不拆写死，后继实现、文档、门禁才有共同靶子；这也是落点票过渡条件的直接承接。

定错后果

如果不冻结，#559 改个回参、#560 改个配置写法都算“小改”，调用方每次升级都要重测；更糟的是没人攒满 3 个稳定版本，拆分议题会反复冒出来，干扰正常迭代。

对 #559 / #560 / #561 的影响

  • 对 #559：宿主电话名与目录派生按冻结实现，改形状即大版本。
  • 对 #560：客户端前缀拼名字与转发开关读写按冻结实现，改配置写法即大版本。

领导追问答案并入（本节为追加，不改上文）

下面是领导追问后补的答案，全程用大白话说，只讲日志系统这一件事，不改 issue，不碰代码逻辑。

1．“电话”一词是什么意思

这里的“电话”不是英文 log 的翻译，而是指网页端打给宿主端的可命名调用：网页端调一个起好名字的动作，宿主端接到后真正干活并回结果。日志系统里一共 5 个这样的电话，老名字是 wf.logBatch（批量上报）、wf.logExport（导出）、wf.logClear（清空）、wf.logGetSwitch（读开关）、wf.logSetSwitch（写开关）。

两端分工一句话：宿主端负责存文件、记开关、做导出和清空；网页端只负责先在本地缓存、节流后再上报。两端最后落到同一个目录，查问题只看那一个地方。

2．Q1 重问版：5 个宿主接口名字三选一

领导重问的是：日志系统的 5 个宿主接口名字到底用哪种定法。下面三选一：

选项做法（大白话）会发生什么
A．沿用现名5 个名字一字不改，一直用 wf.logBatch 这一套。当前插件不用改，但第二个插件一进来就撞名，分不清日志该记到谁头上。
B．加插件前缀，默认 wf（推荐）新名字 = 前缀 + 点 + 动作名，动作名 5 个不变；不填前缀就默认 wf，拼出来和现状一字不差。当前插件零变化，第二个插件填自己的前缀就不撞名，多插件各记各的。
C．调用时多带一个标识名字不变，每次调用多传一个插件标识字段，宿主按标识分开记。名字不膨胀，但宿主分开记的逻辑最复杂，老客户端不带标识时归到谁还要另定。
推荐 B：加插件前缀，默认 wf。
理由：只有 B 能同时做到“当前插件不用改”和“第二个插件不撞名”，改动只在拼名字这一层，不碰失败语义和事件计数。

3．Q2 结论：文件形状与真正的风险

文件名继续按天记是安全的：每天一个文件，句柄打开和刷盘的频率没有差别，不会因为按天就多占东西。单次重写的上限就算比正常量大几倍也是安全的，正常日志量根本碰不到那条线。

真正的风险不在文件名，而在宿主那边的内存队列现在没有上限：网页端一直报、宿主一直攒，极端情况下会越攒越多。后手要加一个 500 到 1000 条的上限，满了就只计数不硬收，和现有的“失败只计数不抛错”保持一致。

4．Q3 新方案：配置怎么填、工厂怎么写、怎么接入

配置只有 1 个必填，其余全可选，都有默认值，不填就能跑：

配置键必填还是可选默认值（大白话）
pluginId 插件标识必填，没有默认必须填，用来区分日志是谁的，是分目录和分电话名的根。
prefix 电话名前缀可选默认 wf，默认拼出的 5 个电话名和现状一字不差。
logDirName 日志子目录名可选默认派生：标识是 wf 时就是 logs，其他标识时是 logs-标识。
switchFileName 开关文件名可选默认派生：标识是 wf 时就是 log-switch.json，其他标识时是 log-switch-标识.json。
fileNamePolicy 文件名策略可选默认 daily，就是现在的按天记；四段式只做可选项。

建日志系统的工厂签名固定为配置在前、依赖在后：先传上面的配置，再传运行要用的依赖（宿主传文件服务这类，网页端传宿主调用器这类），顺序不许调换，缺必填的插件标识直接报错。

双入口写死两条：dsh-log/host 只给宿主端用，dsh-log/client 只给网页端用，各拿各的，不许混拿。

新插件 3 步接入、零配置可跑：第一步装日志系统的包；第二步只填一个插件标识调工厂；第三步宿主走宿主入口、网页走网页端入口接上。剩下不填全走默认值，跑起来和现状行为一致。

5．Q4 确认：双入口已定

双入口已经定了，不再摇摆：宿主代码只走 dsh-log/host，网页代码只走 dsh-log/client，拼进闭包的文本只拿网页端入口的声明体文本。这样宿主写盘的代码不会被打进网页端，体积小，也不容易拿错段。

二次更新拍板结论并入（本节为追加，不改上文）

下面是第二次拍板后补的结论，全程用大白话说，只讲日志系统这一件事，不改 issue，不碰代码逻辑。上文一个字不动，本节只做追加。

用词说明：下面统一叫“日志系统”，不换叫法；“电话”都是指宿主接口方法，“落盘”都是指宿主统一写本地文件的动作，“丢弃数”都是指写不下、发不出时只计数不抛错的那个累计数。

1．Q1 已定：B，加插件前缀，默认 wf

Q1 已经拍板，选 B：日志系统的 5 个电话名都按“前缀 + 点 + 动作名”来拼，5 个动作名不变，不填前缀就默认 wf，拼出来和现状一字不差。当前插件本来就是 wf，所以迁移时不用改调用处。

第二个插件想接入日志系统时，填自己的前缀就能分开，谁的电话归谁，日志系统的记录不会串到别人头上。标识只许小写字母、数字、中横线，长度 1 到 32，不许含点，大写直接报错，不悄悄转小写。

2．Q2 宿主队列优雅方案：默认 1000 封顶，满了按级别丢弃只计数

风险先说清：日志系统的文件名继续按天记是安全的，真正的风险是日志系统在宿主那边的内存队列原来没有上限，极端情况下会越攒越多。优雅方案一共五句，大白话如下。

  • 默认 1000 封顶：日志系统的宿主队列默认最多攒 1000 条，这个数是拍死的默认值，谁不填就按 1000 跑。
  • 满了按级别丢弃只计数：队列满了之后再上报的条目，日志系统按级别丢弃，只把丢弃数加一，不抛错，不弹窗，不卡住，和原来“失败只计数不抛错”的规矩保持一致。
  • 客户端口径对齐：网页端原来就有“单包约 128KB 或队列 100 条先到先截、裁掉记丢弃数”的做法，宿主这次也是“满了记丢弃数”，两边都是丢了只计数，查问题的人看两边的丢弃数就能对上账。
  • 迁移传 1000 零变化：当前插件迁进日志系统时，直接传 1000 这个默认值，行为和现在一致，不算改语义，门禁也不用改断言。
  • 不选阻塞、扩内存、同步落盘的理由：阻塞是指队列满了就让调用方等着，这会把网页端卡住，不符合“只计数不抛错”；扩内存是指把上限调得很大，这只是把爆的时间往后推，极端情况还是会爆；同步落盘是指每次上报都立刻写文件，这会把上报链路拖慢，一卡就全卡。所以三条路都不选，只选“封顶加记数”这一条最轻的路。

3．Q3 已认可：1 个必填加全可选默认值，加双入口加 3 步接入

Q3 的配置写法已经认可，日志系统的配置只有 1 个必填，就是插件标识，不填直接报错；其余全可选，都有默认值，不填就能跑。电话名前缀默认 wf，子目录名默认派生（标识是 wf 时就是 logs，其他标识时是 logs-标识），开关文件名默认派生（标识是 wf 时就是 log-switch.json，其他标识时是 log-switch-标识.json），文件名策略默认按天。

新插件 3 步接入日志系统：第一步装包；第二步只填一个插件标识调工厂；第三步宿主走宿主入口、网页走网页端入口接上。剩下不填全走默认值，跑起来和现状一致。
