#要定的事结论
R1按钮放在哪、怎么对齐贴那一行的右边缘——左边三枚是读数、右边这颗是动作，位置把两类东西分开，也与页签行那枚刷新按钮同侧
R2什么时候不该出现没绑定后端 / 工作区未初始化 / 后端没有体检科目：整颗不显示（点它会开出一个空会话，而「为什么没就绪」已有专门的地方在讲）
R3图标与中英文案中文「体检」、英文 Health check；图标取现成图标集，不新增资源、不用 emoji
R4窄面板怎么折先随行换行 → 收成「图标 + 件数」 → 最后才纯图标；件数是价值信号，不能跟着一起收掉
R5凭什么挑中某一张地图AI 读每张图的 Destination 与 Notes 做语义归类（这是语义问题，没有结构规则能替代）；挑不出唯一一张就列 2–3 个候选，不硬选
R6一次体检查多大范围全仓库的开放票，不跟随面板筛选——同一个动作在不同筛选下必须给出同一个结论
R7体检要不要留痕不自动往票上写评论（动手本身留下原生边就是留痕）；但那次注入按 #662 的先例记一条常驻日志，只记后端与成功/失败两个短枚举
R8一律不碰的东西只做两件事：建原生子议题边、为人点过头的票开新地图；已关闭的票、标题与正文、标签与认领状态、其它仓库都不动

落地约束（维护者交代）：开发必须尊重五层架构——界面层只消费契约产物、契约层定义接口与求值、后端层各自声明与实现、平台抽象层封装系统能力原语、系统底座层各平台实现。三张落地票的正文里都写了这一条具体怎么落实（不新增宿主电话、界面零后端分支、后端声明各在自己的房间里、按房纪律分会话改）。

Q1

这张图的终点：定完方案就收，还是一路做到真机能用？

前因：wayfinder 默认「只决策、不交付」，但你这个需求本身就是要让面板上真的出现一颗能点的按钮。仓库里两种图都有先例：悬浮技能面板那张图明说只产方案（落地另起票），性能那张图携带落地（图上查清 → 方案 → 落地 → 复测）。
后果：选携带落地，落地票要等三张讨论票关了才毕业（不会更早动手）；选只产方案，写代码要另外起票或另开一张图。
A · 携带落地我的推荐图上先把口径与提示词定版，讨论票一关就毕业出落地票与验收票，写代码与真机验收都在图上收口。
B · 只产方案图上只交代口径、按钮形态与各后端提示词，落地另起票。
➡️ 推荐 A。你要的是一颗真能用的按钮，口径定完顺势落地最省事；落地票天然会带上「被三张讨论票阻塞」的原生依赖边。
选 A 利
  • 定完就能动手，不用再开一张图接上
  • 落地票与验收票都留在同一张图里，收口清楚
选 A 弊
  • 图上会多出落地与验收票，这张图关得晚一些
Q2

点下去以后，这段体检提示词怎么送到会话里？

前因：面板里今天有两条现成写法，都有先例——写进当前会话的输入框草稿（列表每行的诊断 / 修复 / 讨论 / 执行就是这么做），或者开一个新会话并把这段文字带过去（页签行的「+ 新建需求」「+ 新增BUG单」是这么做）。
后果：写进草稿 = 你按回车它才跑；开新会话 = 立刻起一个干净会话，但你手上这轮对话留在原地。
关键信息体检会真的改仓库里的票（建 GitHub 原生子议题边、可能新开地图）。写进草稿不碰任何东西，按回车才碰；这一点决定了「先看一眼」值不值那一次回车。
A · 写进当前会话的输入框草稿我的推荐你看到那段提示词，可以改字、可以删掉，按回车才发。
B · 开一个新会话带过去点下去立刻起一个干净会话，体检在那边跑完把结论写回票里。
➡️ 推荐 A。体检要改真东西，默认让你确认一次更稳；真想开新会话时，列表每行本来就有「新会话」这颗按钮。
选 A 利
  • 默认不自作主张，随时能改字或删掉
  • 体检结论留在你正在看的这轮对话里
选 A 弊
  • 多发一次回车；想连着体检两个后端时要手动清草稿
Q3

体检的结果：让它自己动手，还是先出清单等你点头？

前因：这是这条需求里风险最高的一问——「动手」指的是直接建 GitHub 原生子议题边、直接开新地图，改的是你仓库里的真实结构；「出清单」指的是先把「哪张挂到哪张、理由一句话」摆给你，点头后再执行。
后果：动手档省一次确认，但判错就要一张张手动撤；清单档多一步，错在第一眼就能拦下。
关键信息 · 判错具体长什么样
挂错地图把一张讲性能的 bug 挂进「首开引导顺序」那张地图下——面板计数与阻塞关系立刻变错，撤边要一张张来。
空壳地图为一张孤立的小 bug 开出一张新地图，地图列表变长，图上却没有真正要推进的东西。
今天的量本仓库现开放票 19 张，其中游离 11 张；批量误挂的机会不小，而人工扫一眼成本很低。
A · 先出建议清单，你点头才动手我的推荐清单写清「这张 → 挂到哪张（理由）／建议自立成地图／建议留在原地不动」。
B · 直接动手体检跑完顺手把边建好、该开的图开好，你不用再确认。
➡️ 推荐 A（第一版）。先看它在真库上判得准不准；准了再放开自动执行，那是二期，随时可以加。
选 A 利
  • 错的边根本不会建出来，不用收拾
  • 你能顺便校准它的判断口径
选 A 弊
  • 每次体检多一步确认；批量归位时要一张张看
Q4

什么算「游离的开放票」？

前因：需求原话是「调查游离的 OPEN 的 ISSUE」。在数据上，「游离」只有一条硬判据：这张票没有父票（快照里每一行都带这个字段）。争议在要不要再按标签把一些票排除掉（例如等人动手的、明确不做的）。
后果：不排除会多几条你可能暂时不想动的票；排除得狠了会把真正没人管的票漏掉。
关键信息 · 今天 11 张游离票的标签分布
4 张只有 needs-triage 或一个标签都没有（#677、#474、#435 …）——典型「没人管」
3 张ready-for-human（#674、#672、#578）——写着等人动手
2 张wayfinder:grilling（#502、#429）——本来就是一张讨论票，却没有图
1 张ready-for-agent（#640）
没有一种标签组合能把「该管的」和「不用管的」干净分开；而且标签谁都能随手改，唯一稳定的结构事实只有「有没有父票」。
A · 只按三条件判：未关闭 + 不是地图 + 没有父票我的推荐标签不参与判定，只在报告里分区显示（一眼看出该先管谁）。
B · 三条件 + 排除 ready-for-human 与 wontfix清单更短，但会漏掉「等人动手」里其实没人管的那些。
➡️ 推荐 A。判据只留结构事实，宁可在报告里多几行字，也不要漏票。
选 A 利
  • 不漏票；判据稳定、可复算
  • 按标签分区照样能一眼看出优先级
选 A 弊
  • 报告里会出现几张你暂时不想动的票
Q5

什么时候让它「自己就是地图」？

前因：需求原话是「挂载在合适的 MAP 下或者自己就是 MAP」。剩下的选择是：单张票也允许开新图，还是要求凑够同主题的几张才开。
后果：不设门槛会多出一些只有一张子票的小地图（地图列表变长）；设了门槛会逼着把不相干的票凑成一张图（比小地图更糟）。
关键信息 · 今天的样本现有 3 张地图对 11 张游离票。其中 #427 与 #428 是同一台新电脑上的两条环境型假阴性（天然成对），而 #677（面板「已关闭」票数不准）是孤立的一个 bug——按「凑够两张」的门槛，它只能被塞进某张不相干的地图，或者继续没人管。
A · 不设数量门槛我的推荐只要「现有地图一张都装不下」且这张票自己有清楚终点，就建议为它开一张新图；开图时只写最小的 Destination 草稿，正文由你或负责人补。
B · 凑够两张以上同主题才开图地图数量更少，但孤立的需求没有容身之处。
➡️ 推荐 A。门槛会制造「硬凑」，而硬凑出来的图比一张只有一张子票的小图更难收场。
选 A 利
  • 孤立需求也有地方去，不会被硬塞
  • 判据是「装得下 / 装不下」，不靠猜数量
选 A 弊
  • 地图列表会变长，可能出现只有一张子票的图
Q6

另外两个后端，体检各查什么？

前因：需求原话是「对于不同后端会注入不同的 prompt」。GitHub 的科目已经说定（游离票归位），GitLab 与本地 Markdown 的科目要在这里定。
后果：定了才能给这两个后端写提示词；没定的话，按钮在这两个后端上只能显示一句「这个后端还没有体检科目」。
关键信息 · 两个后端今天的形态
GitLab票仓结构与 GitHub 本来是同一套（地图 + 原生子议题 + 阻塞边）；差别是它的父子边要靠链接 / 正文回退解析，解析率还没实测（研究票里那条「没查到」）。
本地 Markdown票就是工作区里的文件（.scratch/<工作单元>/ 下的 map.md 与各张票文件），没有远端接口可查，只能对着文件判。
A · GitLab 照 GitHub 同一套；Markdown 查两条文件级判据我的推荐Markdown 的两条：① 票文件存在、却没有被任何 map.md 的清单引用；② map.md 清单里列了、但对应文件不存在。做不到的地方（如 GitLab 原生边）在提示词里如实说明，不硬来。
B · 这两个后端先不做按钮在这两个后端只显示一句「这个后端还没有体检科目」，等真有人用了再说。
➡️ 推荐 A。GitLab 几乎不用另想科目，Markdown 那两条判据也简单可判；先不做的话，这两个后端上这颗按钮等于不存在。
选 A 利
  • 三个后端都有体检科目，行为一致
  • Markdown 的两条判据纯看文件，不依赖网络
选 A 弊
  • GitLab 那条路要等实测才知道能判准多少，第一版可能偏保守
Q7

按钮上要不要带一个「有 N 张游离票」的数字？

前因：那一行左边三枚指标都带数字，加一个数字你一眼就知道值不值得点。之前绕不过一个问题——这个数到底算不算得出来，所以先没问；研究票已经把它查清了。
后果：带数字 = 多一小段派生逻辑（数据不用重新取）；不带 = 按钮只有两个字，你得点进去才知道有没有活干。
关键信息 · 研究结论每张票在面板快照里都带「有没有父票」这个字段（宿主已经在用它把票挂到地图下），客户端今天没读过它。把「未关闭 + 不是地图 + 没有父票」合成一个数，要新写一小段派生，不需要新的取数、也不需要新的宿主接口。一个例外：GitLab 的父子边解析率没实测，所以「算不出来」这件事必须留一条退路。
A · 带数字，算不出来时只显示文字我的推荐正常显示「体检 11」；某个后端算不出来就显示「体检」，不显示 0。
B · 不带数字按钮只写「体检」，点进去再看有没有游离票。
➡️ 推荐 A。数字是这颗按钮唯一的价值信号——它告诉你「现在值不值得点」。退化规则写死「不显示 0」，因为 0 会被读成「一张都没有」。
选 A 利
  • 一眼看出要不要点，和三枚指标同一套视觉
  • 不用点进去也能知道票仓有没有积压
选 A 弊
  • 多一小段派生与它的门禁；GitLab 上第一版可能显示不出数字
