Q4

落点与语言：一个脚本还是两个，叫什么

名字定了，#571 #572 才能开工；合错了以后拆不动。

📖 前因

MAP #567 计划里是两张落地票：#571 正文写回脚本、#572 子议题关联脚本（含阻塞与校验）。前置输入③说脚本放仓库 scripts/ 下可执行，agent 在终端直接调。但到底是一个脚本全包，还是两个脚本一对一，还没拍。

⚠️ 后果

合一个脚本，调用简单但以后 GitLab / Markdown 第二批不好挂，改一处动全部。拆两个脚本，与 #571 #572 一对一，但提示词要记两个名字。名字起得不好，提示词和门禁全跟着错。
🔑 帮你决策的关键信息
· 现有 scripts/ 全是 .mjs 加 node 调用（如 create-release-issue.mjs），Windows 下 .sh 不好使——语言没悬念，用 .mjs。
· 正文写回与子议题建边是两条链路（#568 管正文、#569 管边），失败模式不同（正文错是格式错，边错是计数错），天然可拆。
  • A · 两个 .mjs，与 #571 #572 一对一（推荐）scripts/fix-issue-body.mjs 管正文写回；scripts/wire-subissues.mjs 管子议题与阻塞建边加校验。
  • B · 合成一个脚本一个 scripts/wf-fix.mjs 加子命令区分（如 body / wire），一次只记一个名字。
➡️ 推荐答案：A
理由：与落地票一对一，谁红了找谁；第二批挂 GitLab / Markdown 时只加新脚本，不动旧脚本。B 省一个名字，但以后加后端就要在同一个文件里分支，越长越不敢改。
✅ 选 A 的利❌ 选 A 的弊 / 选 B 会怎样
职责清、回归面小；门禁可以按脚本分别卡；第二批扩展不碰旧文件。提示词要记两个名字（小成本，用门禁顶住）。选 B：文件迅速变大，正文与建边的失败语义混在一起，回包字段也不好统一。
Q5

参数：传哪几个，多了记不住少了跑不起来

参数就是契约的入口，定死了提示词只写它。

📖 前因

第一轮定的硬规矩：正文必须走文件输入（Windows PowerShell 吞引号），子议题建边要先取数据库编号再建边再查计数。参数必须把这两件事装下，还要让你能先演练再真写。

⚠️ 后果

参数少了脚本跑不起来（比如没给地图号就不知道挂到谁下面）；多了 agent 每次都传错，提示词也变回大段文字，违背收敛初衷。
🔑 帮你决策的关键信息
· 建边三步缺一不可：地图号（挂到谁）、子票号（挂谁）、正文文件（写什么）。仓库地址可从当前工作区推导，设为可选。
· 演练开关是后悔药：先只打印不写，确认无误再真写，避免 #345 那种挂错了才发现。 
node scripts/fix-issue-body.mjs --issue 571 --body-file ./body.md [--repo owner/name] [--dry-run]
node scripts/wire-subissues.mjs --map 567 --children 571,572 --body-file ./body.md [--repo owner/name] [--dry-run]
  • A · 五个：地图或票号 + 子票列表 + 正文文件 + 仓库可选 + 演练开关（推荐）正文文件必传，不传直接报错；演练开关只打印不写。
  • B · 极简三个：只留编号与文件不要仓库可选与演练开关，默认当前仓库、直接真写。
➡️ 推荐答案：A
理由：仓库可选是给跨仓库调用留的后门，平时不传；演练开关是给人看的定心丸，第一次跑先演练。B 省两个参数，但跨仓库和误写时没有退路。
✅ 选 A 的利❌ 选 A 的弊 / 选 B 会怎样
最小可用且有退路；正文文件必传把 PowerShell 引号坑堵死；演练开关避免误写线上票。多记两个可选参数（平时可不写）。选 B：跨仓库调不动；误写后只能手动回滚，没有演练可看。
Q6

返回：回包里写什么，机器和人都能判真

回包是唯一的验收证据，#345 与 #369 就靠它区分。

📖 前因

#570 Question 要求回包说清“改了哪几处、边在不在、数对不对”。前置输入⑤要求“纠了哪几处要在回包里说清”。#345 是事故空、#369 是故意空，光看 0/0 分不清，必须靠回包。

⚠️ 后果

字段少了以后查问题断链（不知道改没改、边建没建）；多了每次都要填，脚本输出变成噪音，人不看了。
🔑 帮你决策的关键信息
· 面板快照只认原生边，不认任务清单文字——所以“边在不在”必须单独一字段。
· 数量校验要与面板计数一致——所以“预期几个、实际几个”必须成对出现，对不上就非 0 退出。 
{"changed":["#571 正文"],"edge":true,"expected":2,"actual":2,"commented":false,"ok":true}
  • A · 五个字段：改了哪、边在不在、预期数、实际数、评论留没留、总通过没（推荐）上面示例即全文，机器判 ok，人看前五个。
  • B · 只回通过没通过一个 ok 了事，细节去票里翻。
➡️ 推荐答案：A
理由：五个字段不多不少，正好回答 Question 的三问。B 省事但回到 #345 时代：显示 0/0，却不知道是没挂对还是故意空。
✅ 选 A 的利❌ 选 A 的弊 / 选 B 会怎样
一次看清改没改、边建没建、数对不对；面板计数以此为准，验收可自动化。输出多几行（JSON 一行，可接受）。选 B：出问题只能逐票手动查计数，#345 补链那种活又要重做一遍。
Q7

失败语义与判定口径：重试、报错、降级怎么写死

写不死，脚本就是“有时灵有时不灵”，门禁也无从卡起。

📖 前因

前置⑤定了四条全要：幂等可重跑、数不对报错不吞、失败自动重试一次并留评论、回包说清。#569 修正加一条：原生旗优先、裸接口只做老版本回退。但“重试几次、在哪留评论、什么算老版本”还没写死。

⚠️ 后果

不写死，失败就静默过去，面板继续显示错的 0/0；降级口径不写死，新版本永远走老路，原生边永远建不上。
🔑 帮你决策的关键信息
· 幂等 = 重复跑结果一致（想要的父已是当前父，直接返回不发请求，graph.js 已有此语义）。
· 留评论落点 = 对应子票下，固定格式一句（含脚本名、参数、失败原因），方便以后按脚本名搜出所有失败。
· 原生旗优先 = 有原生能力就用原生（子议题接口、依赖边接口），只有明确不支持（老版本、未启用）才回退到文字行。
  • A · 全写死（推荐）重复跑一致；数不对非 0 退出；失败自动重试一次，还失败就在对应子票下留固定格式评论；有原生走原生，无原生才回退文字行；提示词搜到具体 gh 命令就门禁变红，只允许脚本名加参数。
  • B · 放宽：不强制重试与评论失败只报错，由人手动处理，不自动留痕。
➡️ 推荐答案：A
理由：#345 的教训就是错了还显示正常，必须靠非 0 退出和评论留痕现形。B 省一次重试，但失败现场（当时传的什么参、挂到哪）过后就丢了，查问题只能重跑。
✅ 选 A 的利❌ 选 A 的弊 / 选 B 会怎样
失败现场永远在票下可查；重跑安全；原生优先保证面板统计正确；门禁一句话就能写（搜 gh issue create/edit/comment 即红）。多一次重试的时间（秒级）与一条失败评论（只在失败时出现）。选 B：失败无痕，下次还是同一个人踩同一个坑。
⚠️ 门禁写法预览：提示词模板里只允许出现 node scripts/fix-issue-body.mjs … / node scripts/wire-subissues.mjs …，出现 gh issue create/edit/comment/api 即红。这就是“以后只写脚本名加参数”的落地。
