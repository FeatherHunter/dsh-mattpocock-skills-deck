前因：「词表」这一个词，今天有三个所指

  • 卡片上这个「词表」＝ 用户仓库里记名词与用语的文档 → 文件就是 CONTEXT.md。英文界面今天用的词是 glossary，中文那三个词是它的译法。
  • 插件自己的代码与文档里，「词表」指的是另一个东西：界面上的中英双语字符串表（src/client/kernel/locale-*.js）。仓库文档写「留在 locale*.js 的词表里」「界面拿 key 去词表取那一句人话」，说的都是它。
  • 插件自己的 CONTEXT.md 又叫「术语表」，也是词表。

三个所指共用一个词，所以读者分不清不是读者的问题，是词的问题。

  • 还有一层会改工作量：这两句话不只活在界面上。选项原文被当作「结论」引用进注入文案，由会话里的 AI 写进用户仓库的 docs/agents/domain.md 与 AGENTS.md 的 ## Agent skills 块。所以「选项怎么改」等于「写进用户仓库的那句结论怎么改」（对应 Q4）。

关键信息：single 与 multiple 各适用什么场景

一个仓库共用一份（single）每个子项目各有一份（multiple）
根目录一份 CONTEXT.md一份 CONTEXT-MAP.md，指向各份
架构决定根目录 docs/adr/系统级的在根，各上下文自己的在 src/<上下文>/docs/adr/
谁该选只有一个应用或库；或者虽然分了多个包，但全仓库共用一套名词与同一批约定仓库里放着几个各自独立的部分，各有各的名词、各有各的架构决定，写在一份里会互相污染
代价只有一份要维护；部分一多，词条会混、界限会糊改一处不牵动别人；代价是根上多一份地图要维护，会话里的 AI 每次先读地图再挑相关的几份
AI 怎么读直接读根上那一份先读根上那份地图，再读跟当前话题相关的那几份
  • 判据不是「包多不多」。随包技能本来想让会话里的 AI 按仓库形状猜：有 pnpm-workspace.yaml、package.json 里有 workspaces、或 packages/* 每个包自带 src/，就算「多上下文信号」。
  • 这条判据当场被这个插件仓库自己推翻：它有 pnpm-workspace.yaml（packages/ 下有 dsh-log、dsh-plugin-update 两个包），按上面三条算「有信号」，但它今天明明白白是单上下文——根上一份 CONTEXT.md、没有 CONTEXT-MAP.md，docs/agents/domain.md 里写着 This repo is single-context。同一个形状两个结论，所以插件把这一问交给你，不让 AI 猜。
  • 真正能拿主意的口径是「这些部分是不是各说各的话」。
  • 选错了代价不高：两种都是懒创建——初始化只记一句结论，CONTEXT.md 与 CONTEXT-MAP.md 都等「第一次真正写下词条」时才建。改起来就是改 docs/agents/domain.md 那句话，或重跑一次初始化。
Q1

两个选项用什么词做主词？

前因：今天两个选项写的是「一个仓库共用一份词表」「每个子项目各有一份词表」，而「词表」有三个所指。后果：主词选错，用户读完仍不知道这个选择会在他仓库里产生什么。你的提议是只用文件名，下面是三个候选与改前改后的实样。
今天（真机截图）
这个仓库的词表怎么组织？（词表就是写这个仓库各模块用语的文档）
一个仓库共用一份词表
每个子项目各有一份词表
采纳推荐（A）之后
这个仓库的各部分共用一套用语，还是各有各的用语？
根目录一份 CONTEXT.md
每个子项目各一份 CONTEXT.md，根目录 CONTEXT-MAP.md 指过去
A · 只用文件名（推荐）根目录一份 CONTEXT.md ／ 每个子项目各一份 CONTEXT.md，根目录 CONTEXT-MAP.md 指过去
B · 中文名词 ＋ 文件名全仓库共用一份领域词表（根目录 CONTEXT.md） ／ 每个子项目各一份领域词表（各自 CONTEXT.md，根目录 CONTEXT-MAP.md 指过去）
C · 保持今天句式、只把「词表」换成别的中文名词术语表 ／ 领域文档 ／ 目录词典——换个词继续猜。
➡️ 推荐 A。文件名是这个词唯一不含糊的所指，而且用户迟早会在自己仓库里真的看到这两个文件。B 把让人困惑的「词表」留在选项里，等于没解决根因；C 只是换一个词。
选 A 利
  • 零歧义：选项直接指向用户将看到的文件
  • 中文界面里不再需要那半句括号解释
  • 与英文侧 CONTEXT.md 天然对齐
选 A 弊
  • 选项行变长，窄面板里会折成两行
  • 要一条拍板：ADR 第 2.1 条「不出现内部术语」怎么读（见下）
  • 附带要你拍板的一条读法：ADR 20260918-init-domain-layout-choice.md 第 2.1 条与规格 #657 用户故事 15 写的是「不出现内部术语」。我读成那条针对的是插件自己的私词（「上下文」「子工作区」「工作区根」），不是用户仓库里真实存在的文件名。采纳 A 就要把这条读法写进决议；必要时给 ADR 补一句，免得以后有人拿它当依据把文件名删掉。
Q2

选项之上那一行怎么问？

前因：今天那一行是「这个仓库的词表怎么组织？」，后面还挂半句解释「（词表就是写这个仓库各模块用语的文档）」——那半句之所以存在，就是因为前面那个词没人看得懂。后果：这一行决定用户知不知道「为什么要问我这个」。
B · 改问「共用还是各用」（推荐）这个仓库的各部分共用一套用语，还是各有各的用语？　变体：同一个东西在这个仓库里是不是只有一种叫法？
A · 保留今天句式只换词这个仓库的领域文档怎么放？——仍然要求用户先懂「领域文档」是什么。
C · 直接问最底层的形状这个仓库里是一个项目，还是几个各自独立的子项目？——会把人引到数包上，而上文那个反例正说明包数答不了这个问题。
➡️ 推荐 B。① 这是用户唯一能确定的事——他可能说不清「领域文档」，但一定知道自己仓库里那几个部分是不是说同一套话；② 选 B 之后，今天括号里那半句解释可以整句删掉，那一行也不再需要「小灰字＋解释」两层。
选 B 利
  • 按用户已知的事发问，不需要先学概念
  • 顺带删掉一行解释，卡片变矮
选 B 弊
  • 「用语」这个词仍属抽象，需要靠两个选项兜住含义
  • 问题行问的是「说法」，选项回答的是「文件」，中间靠读者自己接上
Q3

英文那份要不要同步改？

前因：今天英文是 One shared glossary for the whole repo ／ One glossary per subproject，与中文是同一套设计的两个实现。后果：只改一边，英文界面用户会看到另一个版本的两句话。
推荐 · 同步改，但英文保留 glossary 这个词、只补文件名保留 glossary 等于留住「这个东西本来就有个名字」这条信息；补上 CONTEXT.md 才和中文侧指向同一个文件。
另一种做法 · 英文也把 glossary 去掉、只写文件名与中文完全对称，但放弃了那个已有的名字。
➡️ 推荐前者。中英两份由同一条门禁管着「两边键集合全等」，改一份必然要动另一份；既然要动，就让两边都指向同一个文件、同时各保留一个可读的普通名词。
Q4

跟着注入进用户仓库的那两句结论，要不要一起改？

前因：用户选完，插件注入给会话的文案里带着这一句：「本仓库的域文档布局已在初始化时与用户确认为『一个仓库共用一份词表』：请把这一句结论写进 docs/agents/domain.md…」。后果：这句话会被 AI 抄进用户仓库的 docs/agents/domain.md 与 AGENTS.md，长期留着。界面改了、这里不改，用户下次打开自己的 AGENTS.md 还会问一遍「词表是什么」。
推荐 · 一起改结论句跟着换成同一套说法。这也是这条决定自己的要求——「界面与说明文件两处说法一致」。
只改界面改动面小，但用户仓库里留下旧词，等于把困惑搬到了他的文件里。
➡️ 推荐一起改。另需你给一个口径：结论句直接引用新选项的原文，还是另写一句更完整的说明？我倾向后者——选项若是「根目录一份 CONTEXT.md」，当成结论句读会太短，不足以告诉将来读它的人该怎么找文件。
Q5

选项顺序与默认选中项要不要动？

前因：今天「一个仓库共用一份」排第一、默认选中。措辞一改，排在前面的那句会变成另一个样子，顺序本身有可能被顺手带偏。
推荐 · 维持不动「全仓库一份」仍排第一、仍默认选中。
➡️ 推荐维持。随包技能自己定的默认就是单上下文（原话：This fits almost every repo; write it without asking），绝大多数仓库属这一种；最常见的路径应当零点击。
