提示词库 YAML 化 · 讨论结论（12 问）

现状：提示词的真源在 src/client/kernel/prompts.ts 的一个对象字面量里（23 条注册表模板 + 三处写死在函数里的片段）。它已经是单一真源，但每条模板被压成一行——正文换行只能写成 \n 转义，mapExecute 那条一行两千多字符；而且门禁被迫依赖源码排版：tests/verify-prompts.ts:540 要求「六个字段同一种引号、一条一行、字段顺序固定」，另有 tests/verify-prompt-newlines.ts 专门查排版。这张票要定的是：真源搬到 config/ 下的 YAML 之后，文件怎么分、数据长什么样、生成器怎么跑、门禁怎么改。

需求原话（2026-10-20）：「把提示词模板提取到 yaml 文件中，未来很方便修改和开发和新增，对语言也很容易支持，比如 yaml 中某个字段下拿出来的就是英语版，其他语言依次类推和 dsh 的语言配置一一对应。」这轮讨论就围绕它展开，共 12 问，全部有结论。

数据长什么样

# config/languages.yaml
default: zh
languages:
  - code: zh
    label: 中文
    fallback: []          # 缺省语言没有上一级可退
  - code: en
    label: English
    fallback: [zh]        # 英文缺了内容就退到中文
# config/prompts/workspace-initialization.yaml
prompts:
  ghAuthLogin:
    use: 登录托管站点时给用户的引导说明（为什么这么写：{cli} 由后端在渲染时填入，模板层不许出现具体命令）
    placeholders: [cli, cliBrand]
    text:
      zh: |
        请先完成 {cli} 的登录，再继续。
      en: |
        Please complete the {cli} login first, then continue.
fragments:
  vocabularyDefaults:
    use: 后端没有自报自己的命令行名时的兜底说法
    values:
      cli:
        zh: 当前后端的命令行
        en: the current backend's command line
      cliBrand:
        zh: 当前跟踪器
        en: the current tracker

没有 version 字段（靠 git 记录变化）；use 里只留一句用途与关键理由，逐版流水删除、票号引用保留。

怎么从 YAML 变成客户端里的数据

环节做法仓内出处
读取与校验新增 scripts/lib/prompt-config.mts：读 YAML、校验、产出数据对象。生成器与门禁共用同一份读取逻辑scripts/lib/ 下已有 transpile-unit.mts、select-gates.mts 这类共享库
生成器新增 scripts/generate-prompt-config.mts：写生成物，带 --check（不一致就 FAIL「请跑一次生成器」）scripts/generate-time-config.mts:423-434
生成物src/client/kernel/prompt-data.ts（不入库），只导出一个名字 PROMPT_DATAsrc/shared/time-config/src/values.ts
拼进客户端scripts/build.mts 的 KERNEL_MODULES 登记该生成物，拼到 // ==== kernel:promptData (spliced by build) ==== 标记位（放在 kernel:prompts 之前）build.mts:550-553 已登记三个生成物当内核模块；build.mts:704-721 是拼接点表
防止「改了没生成」package.json 的 typecheck 串里加 --checkpackage.json typecheck = node scripts/generate-time-config.mts --check && node scripts/typecheck.mts

日常闭环不多一步：改 YAML → node scripts/build.mts（构建里自动重跑生成器）→ 重启插件。

运行期怎么用（对外接口不变）

  • src/client/kernel/prompts.ts 删掉 PROMPTS 字面量，按仓内约定自己写 declare const PROMPT_DATA（内核模块之间源码层零 import，每个消费文件自己声明叶子值——src/client/views/pixelProps.d.ts:4-5 写明了这个做法）。
  • 对外只留四个口子：promptText / promptTextFor / promptFragment / promptLang。视图层不碰原始数据。
  • PROMPTS 的导出名与 kernel/prompts.js 的 24 个导出契约不变（docs/architecture/kernel-contract.md:44），行为零变化。
  • 运行时条目摊平成 { zh, en }（与后端自报的提示词同形，后端自报那块见 src/client/kernel/prompts.ts:258）。
  • promptLang 改成按 config/languages.yaml 的语言清单取：DSH 语言按主标签匹配（en-US → en），回退链 zh 没有上一级、en → zh。
  • vocabularyDefaults 补英文（今天只有中文，英文模式下兜底词还是中文）。

门禁怎么改

类别动什么
保留（判定强度不许降）判定式 R1–R8（模板层禁止一切具体命令、R8 禁止「先解析插件安装目录再调包内脚本」）；全部硬编码契约常量（注册表 23 条、三后端键数与字面量数、host 常量数、豁免表 8 条、PROTECTED、MUST_JUDGE、RULE_EXEMPT_EXPECTED）；豁免表 tests/prompt-gate-exempt.json 仍是唯一一张表；八个扫描面照旧存在；23 个注册表键名一个字不改（那是第三方后端 hint 用的对外协议）
改写（数据源换了，判定不变）S1 真源、S2 双产物（改成逐条比正文，因为产物里不再有 version / use / placeholders）、S5 渲染面、S6（改成 YAML 的 fragments 段）、S8；L2 机械注入改成往内存里的 YAML 注入坏条目；门禁自身 sha256 自锁同步改；verify-b2-map-newsession.ts 与 verify-1206-glossary-naming.ts 改读 YAML
退休（源码形状规则，不是质量规则）ENTRY_RE（六个字段同一种引号、一条一行、字段顺序固定）、evalRegistrySource、auditRegistryShape、tests/verify-prompt-newlines.ts 整条
补四条新断言use 不许出现在客户端产物；正文里不许有裸的换行转义；每种语言都要有正文；占位符声明与使用一一对应

判定强度不降的做法：实施时按「旧门禁能抓的违规类型」逐类列一张对照表（旧门禁能抓什么、新的靠哪条判据抓），对照表缺项就是强度降了，不许放过。这张对照表属于实施票的交付物。

Q1

这张票的目标是什么？

前因：原问题写的是「搬到 YAML 就成了单一真源」。查下来，prompts.ts 里的 PROMPTS 已经是单一真源（23 条模板在一个对象字面量里，src/ 全树无别处引用，运行期只经 promptText(id, params) 取）。所以「单一真源」不是搬过去的理由。
后果：真正的痛点是两个：可读性（每条模板一整行，正文换行写成 \n 转义，mapExecute 一行两千多字符）与门禁被迫依赖源码排版（ENTRY_RE 要求同一种引号、一条一行、字段顺序固定，另有 verify-prompt-newlines.ts 专查排版）；再加上产物体积（use、version、placeholders 运行期无人读，却随注册表整块拼进客户端）。
可读性 + 门禁可判定性 + 产物体积 + 多语言机制，四项全做结论主要是让提示词读得懂、改得动，并让门禁从「判源码长相」变成「判数据本身」。多语言这次只做中英两门，但机制一次做足：加语言 = 改数据不改代码。
Q2

搬到什么范围？

前因：除了 23 条注册表模板，prompts.ts 里还有三处写死在函数里的文字：NEW_BUG_FIELDS_BODY / _EN（新增 BUG 单的四项必填说明）、NEW_WAYFINDER_DEFAULT_WIRING（后端没自报子议题关联时的缺省说法）、VOCABULARY_DEFAULT（后端没自报词汇时的兜底说法）。
后果：另有三处不是提示词正文，不搬：三个后端各自的 prompts 块（那是后端自报面）、宿主侧 skillProbe.ts 的 prompt:installSkills 键名协议（对外协议）、界面词表（属另一张票）。
搬 prompts.ts 里全部人写文本结论23 条模板 + 三处片段，一起搬、一起生成、一起被门禁管。三处片段里 vocabularyDefaults 今天只有中文（英文模式下兜底词还是中文），搬的时候补上英文。
Q3

风险怎么处置？

前因：最大的担心是「门禁改写量超过搬家量，改着改着把判定改松了」——毕竟门禁现在的强度是靠很多硬编码常量与源码形状规则撑着的。
后果：决定按三层改：解析层换数据源、判定层保留 R1–R8 与全部硬编码常量、源码形状规则整条退休；并补四条新断言。实施时还要交一张「旧门禁能抓什么、新的靠哪条判据抓」的对照表。
门禁分三层改，自锁两处同步改，补四条新断言结论自锁指的是两处必须一起改：门禁自身的 sha256 摘要（tests/verify-prompts.ts:1675-1735）、L2 机械注入（改成往内存里的 YAML 注入坏条目）。
Q4

选哪个方案？

前因：三个档位：A = YAML 生成 TypeScript 模块（prompts.ts 变薄，24 个导出不变，与时间参数那套同构）；B = YAML 直接生成闭包片段，手写 prompts.ts 删除，契约要重写；C = 不做 YAML 化，只拆多文件 + 模板字符串。
后果：C 解决可读性但不解决门禁可判定性，而那是这张票的主要目标之一，所以不选。
档 A：YAML → 生成器 → 生成物（TypeScript 模块）结论与 scripts/generate-time-config.mts 同一套机制，仓里已有三处「生成物当内核模块」的先例（build.mts:550-553）。对外契约不动，行为零变化。
Q5

文件怎么拆、怎么命名？

前因：要求是「允许拆文件，但 yaml 文件命名要非常专业，相关的放到同一个 yaml 中」。
后果：按「什么时候被注入」分族：工作区启动 / 推进地图 / 票的动作模板 / 建票 / 仓库与布局对齐；语言清单另放 config/languages.yaml，因为它是客户端级事实。
六个文件，命名如上表结论同一时刻注入的提示词放一个文件，改一处不用翻五个文件。
Q7

第三门语言现在写不写？

前因：现在语言是二元硬编码：prompts.ts:51-56 取 locale 快照，:78 按语言二选一，:339 写死 type PromptLang = 'zh' | 'en'；界面侧还有两份重复的 LocaleLang（locale-panel.ts:27-28、locale-pages.ts:39-40）。
后果：要「加语言 = 改数据不改代码」，语言清单就得是数据（config/languages.yaml）；界面词表仍是中英两语，多语言界面另开票（#1284）。
这次只做中英，机制一次做足结论正文写成 text: { zh, en }，第三门语言以后只需要在 YAML 里加一个键 + 在语言清单里加一行 + 补内容，代码不动。
