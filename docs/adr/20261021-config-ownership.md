## 1. 背景

这个仓库里关于「配置」一直没有一条成文的规矩：一个值该留在代码里还是搬进数据文件、它的真源在哪、谁改它，全凭每个开发者当时怎么想。后果已经发生过多次：

- 技能名册历史上漂掉过六个技能；
- 同一族默认色表在仓库里有五处，其中一处把同一个色值写成了大写；
- 界面词表里留着一条没人使用的筛选状态；
- 客户端有一份手抄的标签名册，而守着它的门禁只查「这份手抄存在、形状对」，不查它与真源是否一致。

最近一轮盘点把全仓的候选列了 22 项强候选；紧接着的对抗式复核逐条回到源码找反例，又推翻了其中 13 项里的 11 项——不是那些事不该做，而是它们该用另一种办法做。这说明问题不在于「还有哪些值没进 YAML」，而在于三件事没有规矩：同一个值住在几个地方、谁被允许改它、编译期还能不能守住。没有规矩，每次盘点都要从头判一遍，判出来的结论自己也会过期：研究笔记里已经记错了两处行号，还记错了一处「第二份真源」的位置。

## 2. 决策

### 2.1 三条原则

1. **一个值只该有一处定义（真源）。** 第二份拷贝不是备份，是将来必然漂移的债；仓库里所有因「改了一处忘了另一处」吃过的亏，都出自这一条没被当成硬要求。
2. **值用什么形式，取决于「谁来改它」和「编译器能不能把两份拷贝连起来」。** 改的人是开发者、而且编译器能把两处连起来的，留在代码里就能直接拿到类型安全与编译期报错；改的人是产品、翻译、运营，或者两份拷贝根本不在同一个程序里，才值得搬成数据文件，并配一道门禁盯着它。
3. **规矩必须落在能执行的地方。** 写下来的判断，只有被门禁或编译期检查盖住的部分才算数；靠人记住的口头结论，第二次盘点就会自己漂。

### 2.2 决策测试与三条自问

**决策测试：编译器能不能直接把两份拷贝连起来？**

- 能连起来：留在代码里，用导入把两处连成一处，让漏改在编译期就红。
- 连不上（两半不在同一个程序里，或者编译器看不到那份源文件）：才搬成数据文件，配生成器与门禁。

判断一个具体值时，再问三句话：

1. 谁会改这个值？如果是写代码的人，搬走就没有收益，反而多一层生成与校验。
2. 今天是不是已经有两份会漂的拷贝？如果是，先消掉拷贝；消不掉的才上新门禁。
3. 搬走会不会丢掉编译期保证？会丢的就不搬，或者先把保证换个地方补上再说。

### 2.3 既有三条数据文件路线为什么成立

仓库里已经跑通三条数据文件路线，它们成立的共同原因不是「YAML 更好」，而是真源都不在 TypeScript 程序里（编译器连不上），且改它的人不需要读懂代码：

- **时间参数**（`docs/adr/20261016-time-config-yaml.md`）：调一个超时或间隔只需要看数值与单位，不必读代码逻辑；真源在 `config/` 下的 YAML，生成器把值烘成常量，`--check` 守生成物新鲜度。该决策同时明确「编译期配置，不做运行期可调」。
- **界面文案**（`docs/adr/20261020-ui-copy-data-driven.md`）：改措辞的人是产品、翻译、运营，不是写代码的人；界面那一半在运行时也读不到仓库里的数据文件。真源在 `config/copy/` 下的词族 YAML，生成物不入库，完整性门禁跟着语言清单走。
- **提示词**（#1278 的结论，档 A）：改提示词的人不是写代码的人，模板还带占位符与语言维度；真源搬到 `config/prompts/` 下的 YAML，语言清单是 `config/languages.yaml`。这条路尚未落地，本决策不改它的方案。

这三条路线的代价也必须一起看清：每多一条，就多一个生成器、一次 `--check`、一道门禁与一份文档；所以「能留在代码里」的时候不要轻易搬。

### 2.4 名册类值留在代码里

下面这些值的合法取值靠编译期派生的联合类型与类型守卫守着，搬成数据文件会把编译期报错降级成运行时的静默回退，所以继续留在代码里：

- 对象类型的合法取值（见 `docs/adr/20261020-object-kind-identification.md`）；
- 后端能力上限清单（见 `docs/adr/20261014-tracker-capability-ceiling.md`）；
- 版本控制写命令白名单（见 `docs/adr/20261004-version-control-write-path.md`）；
- 选择记忆的淘汰上限（见 `docs/adr/20261012-backend-decision-two-classes.md`：上限是淘汰护栏，不是可调旋钮）。

### 2.5 门禁怎么配合

1. **能消掉拷贝就不新增比对门禁。** 导入是第一选择；门禁盯拷贝是第二选择，只在两处确实不能合到同一个程序、或语义不同不能共用时使用。
2. **门禁要能红能绿。** 新增或改严一门门禁，必须当场演示「故意写错会红、改回就绿」，而不是只看它今天通绿。
3. **门禁必须进验证链。** 新增门禁要登记进 `scripts/verify-stages.json` 的阶段清单，保证按目录约定能被跑到。
4. **确实不是第二份拷贝的白名单要写理由。** 例如版本控制自带主题里的告警色、本地 Markdown 房里的标签色数据、标签色板条目、颜色元数据表：它们或是不同数据，或是所在半边不能引用客户端中央色表。白名单必须写清「为什么这不是第二份会漂的拷贝」，不能只留一个豁免名单。

### 2.6 与既有决定的关系

本决策不重开《全仓时间参数收进中央 YAML》《界面文案数据化与语言清单单一真源》《后端能力上限》《版本控制写路径》《选择记忆宿主侧持久化》《配额优先》这些已定决策；它只补「一个值该住在哪」的判断标准。时间参数、界面文案、提示词三条既有路线照旧，本轮一份新的 YAML 都不建，也不新增任何运行期读取通道。

## 4. 本轮明确不做

- 不新建任何 YAML 文件，不新增运行期读取通道；运行期可调配置继续排除。
- 不动时间参数与提示词两条既有数据文件链。
- 不为「配置化」而配置化：上一轮调查里的中候选八项与明确不该搬的十八项不在本轮范围。
- 不把界面色值整体搬进数据文件，也不改成一组样式变量重排。
- 不改变面板观感与任何用户可观察的行为；发现「必须改行为才能做对」的项目，另开票。
- 不动日志事件名台账与字段白名单、发布版本门槛、依赖放行名单与第三方步骤版本登记。
- 不把对象类型名册、能力上限清单、版本控制写命令白名单搬成数据文件。

## 5. 为什么这样定

1. **第二份拷贝的债有真实账单。** 上面那些漂移事故（技能名册、默认色表、无人使用的词条、手抄标签名册）都是同一条原则缺位的后果；只做一次性清理、不写规矩，下一次盘点还会重复判断并再次过期。
2. **编译期与导入是最便宜的执行方式。** 能靠 `import` 连起来的地方，漏改会直接在类型检查里红，不需要额外门禁，也不会有门禁自己过期的维护成本。
3. **门禁是第二选择，但有它的位置。** 两处不在同一个程序里（例如客户端与本地 Markdown 房、运行时与持续集成工作流），导入连不上，只能靠门禁；这时门禁必须能红能绿，且白名单要写清理由。
4. **数据文件不是免费的。** 一条路线带来生成器、`--check`、门禁、文档与「改了数据忘了生成」这一类故障；只有当「改它的人不是写代码的人」或「编译器确实够不着」时才值得付这笔成本。
5. **名册类搬走会丢编译期保证。** 联合类型与类型守卫把拼错变成编译错误；换成 YAML 就把错误推迟到运行时，等于拿安全换形式统一，不划算。

## 6. 后果与风险

1. **加新值时多两道判断。** 以后加一个值要先过决策测试与三条自问；短期可能有人觉得束手，换来的是不必每次重新盘点。
2. **门禁与白名单会需要维护。** 代码移动、目录改名会让门禁扫描范围过期；白名单可能被顺手放宽。缓解办法是 §2.5 第 4 条要求写理由，并让门禁在改动时能红。
3. **数据文件路线仍有扩张的诱惑。** 本文件不重开既有三份决策，但未来若要加第四条数据文件路线，必须另写决策记录并回答三条自问，不能顺手新增一层运行期读取。
4. **零变化是验收底线。** 本轮改动前后，面板在同一输入下的可观察结果必须逐例一致（按 `GLOSSARY.md` 的「零变化」词条口径）；实现怎么写不在验收范围内。
5. **死代码删除依赖编译器证明。** 不做兼容层；删除后由编译期与门禁证明没有消费方，不再为「也许有人用」保留导出。

## 7. 什么条件下重新考虑这条规矩

- 工具链变了，编译器能直接检查数据文件本身（例如数据文件变成可被类型检查的 TypeScript 源），「连不上」这个前提消失。
- 某个值改的人从开发者变成产品、翻译、运营（或反过来），第二条原则的答案跟着变。
- 门禁的维护成本超过它挡下的故障，说明这个值的形式选错了。
- 出现新的「两半不在同一个程序里」的场景（例如持续集成工作流、运行时插件目录），需要新开数据文件路线。
