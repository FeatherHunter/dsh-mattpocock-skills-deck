# ADR：判装多通道并联——任一通道有效即已安装（#296 定版）

> 日期：2026-08-28 定版
> 地位：本文件**修订** `20260828-skill-probe-redcard-and-waiting.md`（#281 ADR）的「看一眼文件只用于解释原因 / 轻探永不产生绿色」条款与 `#280`「判装唯一尺度 = 只以 DSH 注册表回答为准」条款。与旧 ADR 冲突以本文件为准（沿用 CONTEXT.md「以更新日期者为准」与「未来改动以更新日期者为准」两条规则）。

## 1. 背景（第一性原理与证据链）

- **修复协议与检测口径分裂（用户可感知的自相矛盾）**：插件自带的修复引导 `installSkills` 提示词以「`~/.agents/skills` 下技能文件齐全」为成功标准——AI 执行它时确实是"检查盘上文件"（#296 用户截图：AI 汇报"已检查 `~/.agents/skills`，指定的 10 个技能均已就位，因此未重复安装"，并列出全部 10 个技能）。但同屏状态栏横幅却报"未检测到核心技能套件……技能 wayfinder 未安装"。
- **死循环**：用户点「帮我安装 Matt 技能套件」→ 注入该提示词 → AI 按提示词如实汇报"已就位，不重复安装" → 横幅按另一把尺（注册表）继续判红 → 按钮仍在 → 再点再循环。修复动作无法让检测变绿——因为两者的"成功"不是一回事。
- **注册表结果的跨环境漂移**：绿牌此前唯一来源是 DSH 技能注册表（#280/#281）。注册表对用户标准根 `~/.agents/skills` 的收集经由 DSH fs 服务（`dsh-skill-filesystem` 对非 trusted 根走 `ctx.fs`）与工作区/宿主环境耦合：现行构建（Desktop 2.0.3）fs 读穿透；旧版/异平台环境可能受工作区作用域限制——这正是「工作区 = `~` 绿、=`~/xxxx` 红」翻转的成因。代码事实（#296 两轮诊断）：`probeSkill` 只在 `skills.get(name)` 命中时给绿；`lightProbeReason` 对"名片可读且合法"也返回"未安装（缺失）"。

## 2. 目标

判装口径回归本义，让检测与修复协议用同一把尺：

1. **任一通道有效即已安装**：以下任一通道「找到且名片合法（SKILL.md 可读、frontmatter `name:` 匹配）」即绿：① DSH 技能注册表；② DSH fs 服务读用户标准根（`~/.agents/skills`，兼查 `~/.dsh/skills`）；③ DSH fs 服务读项目根（`<项目>/.dsh/skills`、`<项目>/.agents/skills`，项目根沿 cwd 向上找 `.git`）；④ 插件只读直读同一批候选根（不经过 DSH fs 服务）。
2. **红牌说真话 + 判据可见**：通道全空才红；红时文案区分「未安装（缺失）/ 名片无效」，并附各通道判据（哪个根、哪条通道、找到/未找到/无效）；绿时若来自盘上通道，附来源路径与"注册表未收录，按盘上事实判定"的如实注记。
3. **直读通道的边界**：只读、只用于技能标准根候选路径，永不写；其他探测仍走平台抽象层（零 OS 直碰纪律仅对技能判装开此例外，本例外限定于此场景）。

## 3. 决策

### 3.1 判装真值 = 任何合格证据出现即成立

- **绿**（`level: 'ok'`）：注册表命中（原有放行）**或** 盘上任一候选根命中合法名片（新增放行）。盘上命中时 `detail` 附来源路径；注册表未收录时如实注明「按盘上事实判定」。
- **红**（`level: 'bad'`）：所有通道均未命中合法名片。分拣：存在「目录/名片存在但无效或不可读」→ 名片无效；否则 → 未安装（缺失）。`detail` 附判据摘要（`evidenceSummary`：通道·根·结果）。
- **等待**：注册表服务不可用（`skills.get` 抛错/服务缺失）仍走原有 pending 有界等待（n/3 封顶），不变。

### 3.2 根顺序与纪律

- 候选根顺序固定为：用户标准根（`.agents/skills` → `.dsh/skills`）优先，项目根次之——与 DSH 发现层「数字小者胜」的优先级一致；先 fs 通道后直读通道，直读仅在 fs 通道全部未命中时执行（省 IO）。
- 名片合法判定复用 `isSkillCardValid`（frontmatter 存在且 `name:` 与期望一致）——不合格名片在任何通道都不算证据，杜绝"文件乱放也算装好"。

### 3.3 直读通道的必要性（本 ADR 的核心取舍）

- 旧环境（读也受工作区作用域限制）下，注册表与 fs 服务通道同时瞎——唯一能自证「文件在标准根」的通道是宿主进程只读直读。若不做该通道，**正是 "#296 用户"这一类环境的故障无法被修复**（修好后的插件仍红，用户只能换主目录工作区使用）。
- 直读仅读取 `~/.agents/skills`、`~/.dsh/skills`、`<项目根>/.agents/skills`、`<项目根>/.dsh/skills` 下 `<技能名>/SKILL.md`，只读不写，失败即视为无证据，不影响其他通道。

## 4. 非目标

- 支持 `.claude/.minimax` 等非 DSH 目录（#280 已退役，不回潮）。
- 修改 DSH 宿主侧技能服务行为（若用户环境 DSH 版本过旧，仍建议升级——直读通道是插件侧兜底，不替代环境修复）。
- 端到端真机双工作区自动回归（列入 #296 验收，人工/后续自动化另票）。

## 5. 后果

- **正**：修复协议与检测口径统一——「点按钮 → AI 检查盘上 → 已就位 → 横幅绿」闭环成立；「装好了却报未安装」的误导与死循环消灭；红时用户能看到判据（哪条通道空、哪条通道被环境挡住）。
- **正**：项目自带技能（团队仓库里的 `.agents/skills`）与用户级技能同权判定，符合 #280「有效副本亦算已安装」的 B 语义。
- **负**：盘上「合法名片」从「只解释原因」升级为「可放行证据」——若某环境注册表未收录而盘上合法，检测可能绿而 DSH 会话侧未加载（#296 现场证据：该环境会话内技能实际可用，故权衡为真值优先）；绿牌附「清单未收录」注记供知情。
- **迁移**：`docs/adr/20260828-skill-probe-redcard-and-waiting.md` 的「轻探永不绿」「不新增任何文件存在即绿分支」条款自本文件生效之日起废止；`SKILL_PROBE_DIRS` 标识继续保持零出现（不恢复旧的多目录配置文件式探针）。

## 6. 验证

- **源码门禁**：`src/host/index.js` 含 `directSkillCardRead`、`probeCardViaDirect`、`evidenceSummary`、`lightProbeReason`、`isSkillCardValid`；无 `SKILL_PROBE_DIRS`。`src/client/statusbar/StatusBar.js` 横幅文案 `desc`（具体状态）优先于 `fallback`。
- **集成缝（`tests/verify-skill-probe-redcard-and-waiting.js`）**：
  - 注册表未命中 + 标准根合法名片（fs 通道可读）→ 绿 + 来源；
  - 注册表未命中 + fs 通道被挡（模拟工作区作用域）+ 直读通道可读 → 绿（#296 用户环境形态的回归）；
  - 缺失 / 名片无效 / 不可读 / 等带有界 → 原有断言不改，仍全绿。
- **回归**：`node tests/verify-skill-probe-redcard-and-waiting.js` 全绿；`node scripts/build.mjs` 后构建产物同步；#296 双工作区（`~` 与 `~/xxxx`）实机验证列入验收。
