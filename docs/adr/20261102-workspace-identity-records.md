# ADR：工作区身份改用插件写下的工作区记录（#1806）

> 日期：2026-11-02 定版（票 #1806）。方向由维护者 2026-11-02 拍板：判定要在所有场景下 100% 正确，不许靠猜人的意图。
> 地位：**修订** `docs/adr/20260918-subworkspace-identity-root.md` 第 3.1／3.2 节里「工作区根的标记」这个定义，以及 `docs/adr/20260918-init-domain-layout-choice.md` 第 2.5 节「工作区根的标记只有两个」那一句。两份决定的其余各节（数据分桶、写路径、既有工作区不迁移、用户可见措辞）仍然有效。
> 效力：这份决定取代上述两份决定里与工作区根标记相关的写法；以后若要再改，以更新版本的 ADR 为准，本文不再被悄悄「顺带」修改。
> 关联：#649（被修订的规则）· #652（旧判定落地）· #656（验收门禁）· #1806（起因与第一步落地）

## 1. 背景（第一性原理与证据链）

- 2026-09-18 的规则说：从所选目录往上，第一个「自带 `.git`」或「自带 `docs/agents/issue-tracker.md`」的目录就是工作区根（见 `docs/adr/20260918-subworkspace-identity-root.md` 第 3.1／3.2 节）。落地时被实现成一句路径存在性检查：`existsAt()` 只看那个文件在不在，不读内容（`src/host/workspaceKey.ts` 旧版）。
- 问题出在这一步：**文件在不在**不等于**这一层是不是独立工作区**。`docs/agents/issue-tracker.md` 是人按模板写下的「这一层用哪个后端」的说明，它可以由用户随手写、随手改、翻译成中文标题、换成别的后端写法。旧规则把它当成了「这一层曾经被初始化为独立工作区」的证据，而插件从来不读它，也从来无法验证它。
- 真实样本（#1806 报告人机器）：`D:\2Study\StudyNotes\SKILLS\智剪工坊` 里有一份自己写的 `docs/agents/issue-tracker.md`（标题是「智剪工坊 · 问题追踪协议」，正文第三段还写着「本文件是仓库根的子协议说明」），但这一层没有 `.git`。判定把这份说明当成独立工作区的标记，于是工作区根停在这一层；而真正的工作区根是上层 `SKILLS`（它是 `StudyNotes` 的子模块，自带一份 `.git` 文件）。面板因此以为「当前目录就是工作区根」，不显示「当前目录属于工作区 SKILLS」这句归属提示。
- 想靠解析文件内容补救也不行，因为「什么样算标准声明」本身就是猜：实测同一个解析器，开头一行标准标题、BOM 开头、空行后标题、行首缩进标题都判「强声明」；翻译标题判「弱」；其他后端的自由文本判「无可信声明」；而「开头一行标准标题、正文却自称本目录是上级仓库的子协议」照样判「强」。每补一种写法，就多一条猜错的路。
- 第一性原理：这份文件回答的是「这一层用哪个后端」，不是「这一层是不是独立工作区」。要可靠回答后者，得有一份**插件自己写下、可被看见、可被删除、可随仓库提交**的事实记录，而不是从人的自由文本里倒推。

## 2. 决策

**工作区根**：从所选目录逐层向上，第一个「自带 `.git`（文件或目录都算）」或「自带一份插件工作区记录」的目录。两样在同一层都有时，那一层就是根（判定回报的依据优先写 `.git`，不影响结果）；哪个标记更近听哪个，这条不变。一路到盘符根、POSIX 根或 UNC 共享根都没有，工作区根就是所选目录本身。

**记录有两份，内容与职责分开**：

| 记录 | 路径 | 表示什么 | 谁来写 |
| --- | --- | --- | --- |
| 后端记录 | `docs/agents/workspace.yaml` | 这个工作区绑定哪个后端（用户选定的结论） | 插件在「用户为工作区选后端」时写；人也可以手动改，但改内容不影响身份判定 |
| 身份记录 | `docs/agents/workspace-root.yaml` | 这一层是插件认可的工作区根，不表示后端 | 插件在初始化流程或用户显式「标为独立工作区」时写 |

- 判定只看这两份记录**在不在**，不读内容：空文件、内容写坏了、那个位置是个目录，都照样算一份记录。
- 旧版 `docs/agents/workspace.json` **不算记录**：它是 #652 之前的版本写在「会话所选目录」上的遗留，子目录里可能有假身份；它只继续被当作旧格式读一次做迁移，不参与身份判定。
- 判定仍然不起 `git` 子进程（旧实现也没起过），也不读任何文件内容；每层最多问三条路径（`.git`、后端记录、身份记录）。
- 缓存与失败口径不变：判定结果按所选目录的规整键缓存 30 秒，失败不缓存；无文件系统能力时诚实回退（`no-fs`／`no-probe`），不对用户报错。
- 判定结果的来源字段新增 `record`（命中插件工作区记录）；`anchor` 这个来源值删除。事件名、键名、级别与采样口径都不变，但 `source` 的取值集合变了，按日志纪律同步改 `research/489-appendix.md` 第 1 章 #63 的取值说明与 1.3 节的修订说明（已随本步改）。

## 3. 为什么这样做

- **身份是插件的持久事实，不是人写文件的副作用。** `.git` 是用户用 git 时自然产生的事实；工作区记录是插件自己写下的结论。两者都是「机器可验证、无需逐字解析」的事实。人的说明文件不再是身份凭据，写什么标题、用什么语言、写不写章节，都不会改变判定。
- **解耦后两边都变简单。** `docs/agents/issue-tracker.md` 恢复它原本的语义：回答这一层用哪个后端。它可以被翻译、可以换成「其他」后端的自由文本、可以有 BOM 或正文引用，都不影响工作区归属。
- **判定变成存在性检查，边界就封闭了。** 判定层只剩下「这一层有没有 `.git`／有没有两份记录之一」三个路径探测，不再有「标题长什么样」「置信度高不高」「读不出来怎么办」这些分支，也就不存在随内容写法漂移的判定。
- **记录可审计、可恢复。** 记录是普通文件，随仓库提交、在 git 历史里看得见；用户删掉它，那一层就退回上级工作区；重新初始化或再选一次后端会重新写下。

## 4. 后果与代价

- **历史归位**：报告人那台机器上抽查（Windows，2026-11-02）10 份 `docs/agents/issue-tracker.md` 里，只有 2 份是标准标题且都自带 `.git`，其余 8 份是手写的从属说明、所在目录没有 `.git`。按本决定，打开这些子目录会归到上级工作区（真机上归到 `SKILLS`，`智剪工坊` 这类目录不再被当成独立工作区）。这是有意的行为变化：之前的状态是旧规则猜出来的，不是用户的真实意图。后续步骤会给出一次性「把本目录标为独立工作区」的入口，让确实想独立的人一键写下身份记录。
- **旧规则已经留在子目录里的 `workspace.yaml` 保持独立**：如果某个子目录当年确实在面板里选过后端，它已经有一份后端记录，按新判定仍算独立工作区。不迁移、不删除。
- **随包脚本暂未同步**：`scripts/wire-subissues.mts` 与 `scripts/fix-issue-body.mts` 目前仍按「往上找主锚文件」找根；在「手写说明的子目录」里跑，它们还会认错根。这属于 #1806 第 4 步的同步范围，本步不动，避免一次改太大。
- **仍按主锚文件存在判初始化的读取方暂未同步**：`src/shared/tracker/check-catalog-dirs.ts`、`check-catalog-views.ts`、`guide-steps.ts` 目前仍把「主锚文件在不在」当作「工作区已初始化」；它们同样属于第 4 步。
- **根变化会换一把工作区键**：子目录里旧规则留下的 `.scratch/`、`workspace.yaml`、面板快照不再被读取。按既有决定「不删、不迁移」处理（见 `docs/adr/20260918-subworkspace-identity-root.md` 第 3.5 节）。
- **记录被误删会退回上级**：这是可接受的失败方向（宁可少认一套，不要多认一套），且可恢复。

## 5. 被否掉的方案

- **A. 只给文件名加内容资格（#1806 的第一版修法）**：认「标准标题声明」的锚文件才算强标记，其余当弱标记兜底。仍然要猜：翻译标题、其他后端、BOM、正文引用标准标题、代码块里的示例、开头声明后正文自称子协议——每一条都要补规则，每补一条就多一条猜错的路；而且它与初始化提示词「已经存在的按现状保留、不重写用户改过的内容」直接冲突：既然插件从不写、也不保证内容，就没有资格按内容判身份。
- **B. 读 `workspace.yaml` 内容来判身份（看 `version`／`backendId`／`source` 字段）**：空文件、字段缺失、写了不认识的值时，又要决定「算不算工作区」——有效性判断重新混进判定层，等于回到 A 的老路。
- **C. 只认 `.git`**：本地 Markdown 工作区本来就不是 git 仓库；只认 `.git` 会让「子目录会话归到工作区根」在本地 Markdown 后端上整体失效，等于放弃 #649 的一半目的。
- **D. 启发式推断 + 界面提示（不写记录）**：启发式只能用于第 3 步的面板提示（「看起来这里像独立工作区，要标为独立吗」），不能进入判定；否则判定依旧是猜。
- **E. 把「已初始化」等同于「有 `.git` 或有主锚文件」**：这正是旧规则本身，问题与证据见第 1 节。

## 6. 落地与门禁

第一步（本票，已完成）：`src/host/workspaceKey.ts` 判定层改为记录制；`tests/verify-656-subworkspace-acceptance.ts` 换成场景矩阵（A1–A18：记录认身份、`.git` 文件也算、嵌套仓库、旧 `workspace.json` 不算、八种说明文件写法一律不算、六种记录形态（含两份记录位置是目录）、无 `readText` 不受影响、没有标记时用所选目录兜底、同层 `.git` 与记录并存时依据报 `.git`、#1806 现场形状等），67 条判据全绿；提交前跑 `npm run verify:parallel` 时同一工作区另有一路会话在并发构建，两扇与本次无关的门禁（构建缓存不许改写产物、状态胶囊栏折叠）因此误红，单独跑均全绿，详见 #1806 的进度记录。

后续步骤（都在 #1806 里）：

1. 记录写入路径：初始化流程写身份记录；面板为工作区选后端时写后端记录；人显式「标为独立工作区／并入上级」也写记录。每条路径都要有测试。身份记录的路径只有一处定义（`src/shared/config-store/src/workspace.ts` 的 `WORKSPACE_IDENTITY_REL`，与后端记录路径同住那个文件），判定层已经 import 它，写侧也必须 import 它，不许再抄一份字面量。
2. 面板与设置页：只陈述可验证的事实（面板数据来自哪个工作区、当前目录是不是它的子目录、依据是 `.git` 还是插件记录），并给一键纠正入口。
3. 历史归位提示：沿用手写说明、没有记录的子目录给一次性「标为独立」提示；旧规则下已留下 `workspace.yaml` 的子目录显示「并入上级」入口。
4. 随包脚本与 `tracker:initialized` 读取方改为同一条记录制规则。
5. 同步文档与日志（`research/489-appendix.md` 的 `source` 取值说明已随本步更新）、真机验收、关票。

验收标准：#1806 评论里的 9 条（场景矩阵全绿、`verify:parallel` 全绿、`智剪工坊` 归 `SKILLS`、四个应当独立的目录保持不变、说明文件内容不影响归属、每条记录产生路径有测试、`tracker:initialized` 与面板第四行改看记录、ADR／GLOSSARY 同步、不迁移不删除）。
