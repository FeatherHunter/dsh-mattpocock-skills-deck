# ADR：工作区身份改用插件写下的工作区记录（#1806）

> 日期：2026-11-02 定版（票 #1806）。方向由维护者 2026-11-02 拍板：判定要在所有场景下 100% 正确，不许靠猜人的意图。
> 地位：**修订** `docs/adr/20260918-subworkspace-identity-root.md` 第 3.1／3.2 节里「工作区根的标记」这个定义，以及 `docs/adr/20260918-init-domain-layout-choice.md` 第 2.5 节「工作区根的标记只有两个」那一句。两份决定的其余各节（数据分桶、写路径、既有工作区不迁移、用户可见措辞）仍然有效。
> 效力：这份决定取代上述两份决定里与工作区根标记相关的写法；以后若要再改，以更新版本的 ADR 为准，本文不再被悄悄「顺带」修改。
> 关联：#649（被修订的规则）· #652（旧判定落地）· #656（验收门禁）· #1806（起因与第一步落地）

## 1. 背景（第一性原理与证据链）

- 2026-09-18 的规则说：从所选目录往上，第一个「自带 `.git`」或「自带 `docs/agents/issue-tracker.md`」的目录就是工作区根（见 `docs/adr/20260918-subworkspace-identity-root.md` 第 3.1／3.2 节）。落地时被实现成一句路径存在性检查：`existsAt()` 只看那个文件在不在，不读内容（`src/host/workspaceKey.ts` 旧版）。
- 问题出在这一步：**文件在不在**不等于**这一层是不是独立工作区**。`docs/agents/issue-tracker.md` 是人按模板写下的「这一层用哪个后端」的说明，它可以由用户随手写、随手改、翻译成中文标题、换成别的后端写法。旧规则把它当成了「这一层曾经被初始化为独立工作区」的证据，而插件从来不读它，也从来无法验证它。
- 真实样本（#1806 报告人机器）：`D:\2Study\StudyNotes\SKILLS\智剪工坊` 里有一份自己写的 `docs/agents/issue-tracker.md`（标题是「智剪工坊 · 问题追踪协议」，正文第三段还写着「本文件是仓库根的子协议说明」），但这一层没有 `.git`。判定把这份说明当成独立工作区的标记，于是工作区根停在这一层；而真正的工作区根是上层 `SKILLS`（它是 `StudyNotes` 的子模块，自带一份 `.git` 文件）。面板因此以为「当前目录就是工作区根」，不显示「当前目录属于工作区 SKILLS」这句归属提示。
- 想靠解析文件内容补救也不行，因为「什么样算标准声明」本身就是猜：实测同一个解析器，开头一行标准标题、BOM 开头、空行后标题、行首缩进标题都判「强声明」；翻译标题判「弱」；其他后端的自由文本判「无可信声明」；而「开头一行标准标题、正文却自称本目录是上级仓库的子协议」照样判「强」。每补一种写法，就多一条猜错的路。
- 第一性原理：这份文件回答的是「这一层用哪个后端」，不是「这一层是不是独立工作区」。要可靠回答后者，得有一份**插件自己写下、可被看见、可被删除、可随仓库提交**的事实记录，而不是从人的自由文本里倒推。

## 2. 决策

**工作区根**：从所选目录逐层向上，第一个「自带 `.git`（文件或目录都算）」或「自带一份插件工作区记录」的目录。同一层里先看 `.git`（有就是根，判定回报的依据写 `.git`）；没有 `.git` 再看从属记录（有就表示这一层已被明确并入上级，跳过本层继续往上）；最后看两份工作区记录（有就是根，回报的依据写 `record`）。哪个标记更近听哪个，这条不变。一路到盘符根、POSIX 根或 UNC 共享根都没有，工作区根就是所选目录本身。

**记录有三份，内容与职责分开**：

| 记录 | 路径 | 表示什么 | 谁来写 |
| --- | --- | --- | --- |
| 后端记录 | `docs/agents/workspace.yaml` | 这个工作区绑定哪个后端（用户选定的结论） | 插件在「用户为工作区选后端」时写；人也可以手动改，但改内容不影响身份判定 |
| 身份记录 | `docs/agents/workspace-root.yaml` | 这一层是插件认可的工作区根，不表示后端 | 插件在初始化流程或用户显式「标为独立工作区」时写 |
| 从属记录 | `docs/agents/workspace-member.yaml` | 这一层已被用户明确并入上级工作区，身份判定跳过本层继续往上 | 插件在用户显式「并入上级」时写；人也可以手动删掉它 |

- 判定只看这几份记录**在不在**，不读内容：空文件、内容写坏了、那个位置是个目录，都照样算一份记录。从属记录与两份工作区记录同等对待；它只遮住同一层的两份工作区记录，不删除它们，删掉从属记录后原来的记录重新生效。
- 旧版 `docs/agents/workspace.json` **不算记录**：它是 #652 之前的版本写在「会话所选目录」上的遗留，子目录里可能有假身份；它只继续被当作旧格式读一次做迁移，不参与身份判定。
- 判定仍然不起 `git` 子进程（旧实现也没起过），也不读任何文件内容；每层最多问四条路径（`.git`、从属记录、后端记录、身份记录）。
- 缓存与失败口径不变：判定结果按所选目录的规整键缓存 30 秒，失败不缓存；无文件系统能力时诚实回退（`no-fs`／`no-probe`），不对用户报错。
- 判定结果的来源字段新增 `record`（命中插件工作区记录）；`anchor` 这个来源值删除。事件名、键名、级别与采样口径都不变，但 `source` 的取值集合变了，按日志纪律同步改 `research/489-appendix.md` 第 1 章 #63 的取值说明与 1.3 节的修订说明（已随本步改）。从属记录不产生新的 `source` 取值：命中它只让判定跳过这一层，继续往上找真正的根。

## 3. 为什么这样做

- **身份是插件的持久事实，不是人写文件的副作用。** `.git` 是用户用 git 时自然产生的事实；工作区记录是插件自己写下的结论。两者都是「机器可验证、无需逐字解析」的事实。人的说明文件不再是身份凭据，写什么标题、用什么语言、写不写章节，都不会改变判定。
- **解耦后两边都变简单。** `docs/agents/issue-tracker.md` 恢复它原本的语义：回答这一层用哪个后端。它可以被翻译、可以换成「其他」后端的自由文本、可以有 BOM 或正文引用，都不影响工作区归属。
- **判定变成存在性检查，边界就封闭了。** 判定层只剩下「这一层有没有 `.git`／有没有从属记录／有没有两份工作区记录之一」四个路径探测，不再有「标题长什么样」「置信度高不高」「读不出来怎么办」这些分支，也就不存在随内容写法漂移的判定。
- **记录可审计、可恢复。** 记录是普通文件，随仓库提交、在 git 历史里看得见；用户删掉它，那一层就退回上级工作区；重新初始化或再选一次后端会重新写下。

## 4. 后果与代价

- **历史归位**：报告人那台机器上抽查（Windows，2026-11-02）10 份 `docs/agents/issue-tracker.md` 里，只有 2 份是标准标题且都自带 `.git`，其余 8 份是手写的从属说明、所在目录没有 `.git`。按本决定，打开这些子目录会归到上级工作区（真机上归到 `SKILLS`，`智剪工坊` 这类目录不再被当成独立工作区）。这是有意的行为变化：之前的状态是旧规则猜出来的，不是用户的真实意图。后续步骤会给出一次性「把本目录标为独立工作区」的入口，让确实想独立的人一键写下身份记录。
- **旧规则已经留在子目录里的 `workspace.yaml` 保持独立**：如果某个子目录当年确实在面板里选过后端，它已经有一份后端记录，按新判定仍算独立工作区。不迁移、不删除。
- **并入上级不删原有记录，撤销入口在本步补上**：子目录里可能本来就有后端记录或身份记录。用户点「并入上级」时只多写一份从属记录；从属记录只遮住同一层的两份工作区记录，不删除它们。设置页因此保留「标为独立工作区」这条按钮作为撤销入口：点它就写回身份记录并删掉同一层的从属记录，原来的记录重新生效。这条撤销入口在 #1806 第 5 步真机复核时补上——此前并入后没有任何回头的路，与按钮提示「以后还能改回来」不符。
- **随包脚本已按同一条规则同步**（#1806 第 4 步）：`scripts/wire-subissues.mts` 与 `scripts/fix-issue-body.mts` 逐层认根时只认 `.git` 与两份插件工作区记录；本层有从属记录（`docs/agents/workspace-member.yaml`）就跳过继续往上；子目录里手写的说明文件不再影响认根。说明文件仍被读来回答「用哪个后端」。两份自包含副本是否与宿主给出同一结论，由 `tests/verify-wire-subissues-script.ts` 与 `tests/verify-issue-body-script.ts` 的子目录用例钉住。
- **「工作区已初始化」改看身份记录**（#1806 第 4 步）：`tracker:initialized` 的检查项从「根上有 `docs/agents/issue-tracker.md`」改为「根上有 `docs/agents/workspace-root.yaml`」，面板第四行「根还没初始化」随之改口径；`.git` 本身仍不等于已初始化（理由见第 5 节方案 E）。
- **升级后已有工作区会重新看到一次初始化提示**：老工作区只有 `.git`、没有身份记录，按新判据属于「还没有初始化记录」。这是第 5 节方案 E 被否掉的必然代价：不静默迁移、不伪造记录。初始化提示词本身是「缺哪份补哪份、已经存在的按现状保留」，不会改写用户已有的产物。
- **根变化会换一把工作区键**：子目录里旧规则留下的 `.scratch/`、`workspace.yaml`、面板快照不再被读取。按既有决定「不删、不迁移」处理（见 `docs/adr/20260918-subworkspace-identity-root.md` 第 3.5 节）。
- **记录被误删会退回上级**：这是可接受的失败方向（宁可少认一套，不要多认一套），且可恢复。
- **初始化补写的时点不是「初始化真的做完」那一刻**：插件自己从不执行初始化，也看不到会话里后续写了哪些文件，能拿到的最晚信号是「初始化文案已经交给用户或已注入会话」。#1806 第 2 步把补写放在注入成功之后（注入抛错就不写），这仍早于用户实际完成初始化；代价是用户放弃初始化时，这个目录会留下一份身份记录。第 2 步的缓解措施是「只在目录自己就是工作区根时才写」；第 4 步修正为「写在判定层给出的根上」：在子目录会话里交付初始化文案时，记录落在它所属的工作区根，而不是子目录——身份不变（仍然是原来那一层），也不会因为一次放弃的初始化在子目录里凭空造出一个工作区。自带 `.git` 的根同样补写这份凭据，因为 `.git` 只证明「这一层是工作区」，不证明初始化提示发出过（见第 5 节方案 E）。
- **记录会随目录一起被复制**：把带 `workspace-root.yaml` 的目录整份拷到别处，新位置按规则也算独立工作区（`.git` 同样如此）。这是「身份写在目录自己的文件里」的必然结果；删掉记录就会退回上级，必要时由面板的一键纠正处理。
- **路径写法不影响身份**：判定层与写侧用同一条规整规则（大小写、尾斜杠、反斜杠一致化），同一目录的不同写法不会产生两份身份记录。

## 5. 被否掉的方案

- **A. 只给文件名加内容资格（#1806 的第一版修法）**：认「标准标题声明」的锚文件才算强标记，其余当弱标记兜底。仍然要猜：翻译标题、其他后端、BOM、正文引用标准标题、代码块里的示例、开头声明后正文自称子协议——每一条都要补规则，每补一条就多一条猜错的路；而且它与初始化提示词「已经存在的按现状保留、不重写用户改过的内容」直接冲突：既然插件从不写、也不保证内容，就没有资格按内容判身份。
- **B. 读 `workspace.yaml` 内容来判身份（看 `version`／`backendId`／`source` 字段）**：空文件、字段缺失、写了不认识的值时，又要决定「算不算工作区」——有效性判断重新混进判定层，等于回到 A 的老路。
- **C. 只认 `.git`**：本地 Markdown 工作区本来就不是 git 仓库；只认 `.git` 会让「子目录会话归到工作区根」在本地 Markdown 后端上整体失效，等于放弃 #649 的一半目的。
- **D. 启发式推断 + 界面提示（不写记录）**：启发式只能用于第 3 步的面板提示（「看起来这里像独立工作区，要标为独立吗」），不能进入判定；否则判定依旧是猜。
- **E. 把「已初始化」等同于「有 `.git` 或有主锚文件」**：这正是旧规则本身，问题与证据见第 1 节。

## 6. 落地与门禁

第一步（本票，已完成）：`src/host/workspaceKey.ts` 判定层改为记录制；`tests/verify-656-subworkspace-acceptance.ts` 换成场景矩阵（A1–A18：记录认身份、`.git` 文件也算、嵌套仓库、旧 `workspace.json` 不算、八种说明文件写法一律不算、六种记录形态（含两份记录位置是目录）、无 `readText` 不受影响、没有标记时用所选目录兜底、同层 `.git` 与记录并存时依据报 `.git`、#1806 现场形状等），67 条判据全绿；提交前跑 `npm run verify:parallel` 时同一工作区另有一路会话在并发构建，两扇与本次无关的门禁（构建缓存不许改写产物、状态胶囊栏折叠）因此误红，单独跑均全绿，详见 #1806 的进度记录。

第二步（本票，已完成）：记录写入路径。`src/host/workspaceRecords.ts` 提供两条电话——`wf.ensureWorkspaceRecord`（初始化流程补写，来源 `setup`；只在目录自己就是工作区根时写，正在上级工作区里的子目录回 `inside-workspace` 不写（第 4 步把写点改为判定层给出的根，见本节第四步）；判定这一步出错时失败关闭，回 `root-unknown`；已有记录、空文件、目录位置一律不重写）与 `wf.markWorkspaceRoot`（人显式「标为独立工作区」，来源 `user`，写在这一层本身，不经过判定层）。初始化流程的接线在 `src/client/kernel/prompts-setup.ts`：文案真的交给调用方或注入成功后（`injectNow:false` 交出去也算），才 fire-and-forget 发补写电话；注入抛错、还在等布局卡、没有宿主通道、没有会话目录时都不发。面板为工作区选后端写下的 `workspace.yaml` 本身就是判定层认的记录，不需要另写身份记录。写完清三样旧账：工作区快照缓存、面板缓存、根判定缓存（30 秒缓存不失效，面板会继续说旧话）。身份记录格式（`version`／`kind: workspace-root`／`writtenAt`／`source`、给人看的头注释）由 `src/shared/config-store/src/workspace.ts` 的 `stringifyIdentityRecord`／`parseIdentityRecord` 定义，路径常量 `WORKSPACE_IDENTITY_REL` 也只有那一处。`tests/verify-1806-record-write-paths.ts` 的 50 条判据覆盖三条路、失败关闭、已有记录不覆盖（含空文件与目录位置）、缓存键、注入时序与静态接线，全绿。

第三步（本票，已完成）：面板归属行只陈述可验证的事实（数据来自哪个工作区、当前目录是不是它的子目录、依据是 `.git` 还是插件记录），设置页「工作区后端总览」给两个纠正入口——「标为独立工作区」（写身份记录）与「并入上级」（写从属记录）。

第四步（本票，已完成）：`tracker:initialized` 改看身份记录；随包脚本同步记录制认根；面板浮层对手写说明、没有记录的子目录加一句一次性归位提示，指到设置页的「标为独立工作区」。第 2 步「只在目录自己就是工作区根时才写」的写点也在这里放宽为「判定层给出的根」，见第 4 节。

第五步（本票，已完成）：同步文档与日志（本 ADR、`GLOSSARY.md` 与 `research/489-appendix.md`），真机验收并关票。真机复核在 web profile 的隔离副本上走完「标为独立工作区 → 并入上级 → 撤销并入」三轮点击与清理还原，在本步内修掉两处自身故障：① 设置页读行时把「路径不存在」当成「记录存在」（平台文件服务对缺失路径回 `undefined` 而不是抛错），导致三颗纠正按钮点了都没有反应；② 并入后没有撤销入口（见第 4 节）。修复后补了对应测试判据（记录读写契约、撤销事实 `canUnjoin` 与按钮接线），并重新在真机上验收通过。
