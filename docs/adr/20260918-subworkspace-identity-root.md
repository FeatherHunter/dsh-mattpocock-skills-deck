# ADR：子工作区身份规则（子目录会话归到工作区根）

> 日期：2026-09-18 定版（地图 #647 · 票 #649）。方向由维护者 2026-09-17 拍板，判定顺序与既有工作区处置由维护者 2026-09-18 确认。
> 地位：**修订** #301/#324 的适用边界。凡与本文冲突的旧口径（「同一文件夹的会话共享一份数据」），以本文为准——与 `CONTEXT.md` 开头两条版本与效力规则同款。
> 关联：#647（地图）· #648（取证）· #649（本决定）· #652 / #653 / #654（落地）· #656（验收）· #301 / #324（被修订的旧口径）

## 1. 背景（第一性原理与证据链）

- **一个仓库只可能有一份「工作区级」的东西**：后端声明（`docs/agents/issue-tracker.md`）、标签配色文件、本地 Markdown 的票仓 `.scratch/`、以及 issue 列表本身。它们在物理上只能存在于仓库那一级。
- 2026-09-17 之前，插件把「工作区」等同于「会话所选的那条目录」，只有仓库身份（owner/name）按 git 根算。于是子目录会话成了「仓库认识、工作区不认识」：检查链的「工作区已初始化」读 `<所选目录>/docs/agents/issue-tracker.md` 必红；后端绑定与面板快照各占一桶；写路径（标签配色文件、`.scratch/`、建票目录）**真会**往子目录里写第二套。
- 真实样本（用户机）：`D:\ilife`（monorepo 根，一切正常）与 `D:\ilife\packages\skill-calorie`（子目录，提示「还未初始化工作区」）。本地 Markdown 工作区的子目录更严重——判定从不跑 git，连后端都选不出来，面板没有数据。
- 为什么不能把「子目录自成一套」当默认：那等于要求用户在每个子目录里重复初始化，同一个仓库里会长出多套配置与票仓，同一个 issue 列表在界面上被切成互不相认的几份。
- 证据：`research/648-subworkspace-failure-evidence.md`（研究票 #648）。逐层判据是——除「GitHub 与 GitLab 的启发式判定会顺着 git 上溯」这两处，插件其余每一层都只认会话所选目录。

## 2. 目标

1. 子目录会话与根会话共享同一份工作区级数据（面板数据、后端选择、检查链快照、仓库引用）。
2. 写路径一律落在工作区根：子目录里不再长出第二套 `docs/agents/`、`.scratch/`、票仓目录。
3. 三条边界（嵌套仓库、已被别人初始化过的目录、无仓库目录）不需要特例。
4. 用户看得见的地方（界面文案、注入文案）用大白话，不出现内部术语。

## 3. 决策

### 3.1 两个词

- **所选目录**：会话创建时选定的那个目录（会话的 cwd），先按工作区键规整（Windows 折大小写、统一斜杠、去尾斜杠）。
- **工作区根**：从所选目录逐层向上，第一个「自带 `.git`（文件或目录都算）的目录」或「自带 `docs/agents/issue-tracker.md` 的目录」；扫到同一层两样都有，那一层就是根；一路到盘符根或文件系统根都没有，就用所选目录本身。
- **子工作区**：所选目录 ≠ 工作区根 的那些会话，说它处在一个子工作区里。

### 3.2 判定顺序

从所选目录逐层向上：**这一层有 `.git` 或 `docs/agents/issue-tracker.md` → 它就是工作区根，停**；走到底都没有 → 工作区根就是所选目录。

把`自带 `.git`` 与`自带主锚文件`放在**同一优先级、谁近听谁**，是这条规则的关键：三条边界由此自然成立，不需要任何特例。

- 子目录自带 `.git`（嵌套仓库）→ 停在自己那一层，自成一套，面板显示它自己的远端与 issue；
- 子目录自带 `docs/agents/issue-tracker.md`（之前有人在这里初始化过）→ 同样自成一套；
- 一路到仓库根才遇到标记（`D:\ilife\packages\skill-calorie` 就是这种）→ 归到仓库根；
- 反向也成立：更近的 `.git` 会截住上溯，**不会**跳到外层带主锚文件的目录去。

缓存与失败口径：

- 判定结果按「所选目录的规整键」缓存在宿主内存里；一次判定最多起一次 `git` 子进程，并带超时；
- `git` 起不来、超时、或所选目录不存在 → 回退「所选目录」，与旧行为一致（诚实失败，不许因此让整个面板报错）；
- **失败结果不永久缓存**（修掉 `repoRoots` 把一次临时失败永久记成空的旧毛病）；
- 工作区根必须与「工作区键」走同一个出口（`src/shared/workspaceKey.js` 单源），保证读写删三侧同形——`#301` 已踩过这个坑。

### 3.3 三个后端各自的口径

| 后端 | 工作区根用来做什么 |
| --- | --- |
| GitHub | 仓库身份、后端声明、面板数据、后端绑定、检查链快照一律按工作区根；子目录会话与根会话**同桶** |
| GitLab | 同上 |
| 本地 Markdown | 票仓 `.scratch/`、配色文件 `docs/agents/label-colors.json`、建票目录一律落在**工作区根**；子目录会话读写都去根，子目录里不再长出第二套 |
| 无仓库目录（无 `.git`、无主锚） | 工作区根 = 所选目录，不做任何上溯，保持诚实形态 |
| 随包脚本（`scripts/*.mjs`） | 用同一条上溯规则找主锚；在子目录里跑要认得出后端；认不出时的文案要说清「请到工作区根目录跑」 |

### 3.4 与 #301 / #324 的关系

**修订**，不是推翻：原口径「同一文件夹的会话共享一份数据」改为「**同一工作区根的会话**共享一份数据」；「不同工作区永不合并」不变——工作区根不同就是不同工作区。磁盘快照缓存本来就按仓库名共用（`<owner>__<name>.json`），这一条不动。

### 3.5 既有工作区的处置

规则生效后，老的「按所选目录」分桶的状态（后端绑定、面板快照、链快照）不再被读取：**不删、不迁移**——插件不擅自清理用户的持久状态。设置页的工作区总览里，被并进根工作区的那几行标出归属（例如「（子目录，已并入 D:\ilife）」）。DSH 自己的工作区清单（`~/.dsh/storages/workspace.json`）属上游，插件不碰。

### 3.6 用户可见之处的措辞

`CONTEXT.md` 里的词条是**内部用词表**，服务的是读这个仓库的人与 agent，不产生用户效果。用户效果只在三处：插件的行为、界面上的字、注入给会话的提示词与写进用户仓库的文件。因此**用户可见之处一律用大白话**（例如「当前目录属于工作区 D:\ilife」），不出现「子工作区」「工作区根」这类内部术语。

### 3.7 本规则不包含什么

- 标志长什么样、放哪、文案是什么、能不能点 → #650；
- 初始化流程的多上下文（域文档布局：根 `CONTEXT-MAP.md` 与每个上下文的 `CONTEXT.md`） → #651 / #655；
- 界面上那句归属提示的渲染实现 → #653。

## 4. 验收

- **门禁**（#656）：锚点判定的边界情形（自带 `.git`、自带主锚文件、无 git、盘符根与 UNC、大小写与尾斜杠写法）、四样状态在「仓库根 / 子目录 / 兄弟目录」下的分桶断言、「子目录里不出现第二套 `.scratch/` 与配色文件」的写路径断言，全部进 `npm run verify`。
- **真机**（用户机）：在 `D:\ilife\packages\skill-calorie` 里新建会话，面板照常显示该仓库的 issue、不再提示未初始化、不再出现后端选择缺失；界面给出归属提示且文案是白话。
- **反向**：在自带 `.git` 的嵌套仓库目录里新建会话，面板显示的是**那个仓库**，不被外层仓库吞掉。
