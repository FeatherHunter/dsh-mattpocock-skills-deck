# ADR：工作路线存档的隐私口径（#1083）

## 1. 背景

工作路线要回答「哪些会话在处理哪些票」，给跨会话的在办表用（地图 #1080）。它落盘之后会长期留在用户机器上，所以「写什么、不写什么」必须是一道明确的决定，而不是顺手的实现细节。

这件事经历了两次口径变化：

1. **2026-09 的旧口径：只存散列。** 那时的处理链（今天叫工作路线）把会话分格散列、工作区根散列、后端名、票号、工作单元、时间、动作类别写到 `<进程当前目录>/.dsh-mattskillsdeck-cache/session-tickets.json`。会话 id 原文、路径原文、命令原文一个都不写。当时的检查函数是 `chainPrivacyViolations`：它把「含空白」的字符串当成命令原文，见到就判整份不干净。
2. **2026-10 的新需求：面板上要显示人读得懂的名字。** 在办表要让人一眼看出「哪个会话、在处理哪张票」，至少要显示会话标题与票标题。只存散列时，界面只能显示「会话 ab12cd34」和票号，人得自己回想这是谁、那张票叫什么。于是规格 #1259 决定：会话 id 原文、会话标题快照与票标题快照允许落盘，`chainPrivacyViolations` 不再用于新存档。

旧自检不能沿用的原因很具体：**「含空白就拒绝」等于「不许有任何自由文本」**。命令原文确实含空白，但正常会话标题（例如「修复刷新链路的两个边界」）和正常票标题同样含空白。拿它检查新存档，会把每一条合法记录都判脏，结果是整份不写、面板永远显示不出名字。它想防的是「凭证与命令原文混进来」，却用了一个会误伤正常标题的判据。隐私口径需要换一种写法：**管住字段名单，再管住值的形状**，而不是笼统地不许有空格。

## 2. 决策

### 2.1 两步检查：字段白名单 + 凭证形状检查

新存档每次写盘之前，先把「即将写出的整份 JSON 结构」交给一个检查函数，依次做两件事：

1. **字段白名单**：对象里的每一个键都必须在下面这 16 个名字里——`v`、`at`、`backend`、`workers`、`session`、`label`、`labelAt`、`entries`、`ticketKey`、`effortId`、`title`、`action`、`actionAt`、`source`、`progress`、`hasWork`。出现名单之外的键，整份不写。
2. **凭证形状检查**：每一个字符串值都扫一遍凭证的形状，命中就整份不写。至少覆盖五类：
   - 令牌：常见平台的令牌前缀（GitHub 的 `ghp_`/`gho_`/`ghu_`/`ghs_`/`ghr_` 与 `github_pat_`、GitLab 的 `glpat-`、OpenAI 风格的 `sk-`、云厂商访问密钥 `AKIA…`、Slack 的 `xoxb-` 等）；
   - 授权头：「`Authorization: Bearer …`」「`Bearer …`」「`Basic …`」这类形状；
   - 口令键值：`password=`、`passwd=`、`token=`、`secret=`、`api_key=` 这类「键名加等号加值」的形状；
   - 私钥：`-----BEGIN … PRIVATE KEY-----` 这类 PEM 块的开头；
   - 带凭据的 URL：`https://用户名:口令@主机` 这种把口令嵌在地址里的写法。

白名单管住「能出现什么字段」，凭证形状检查管住「字段里的值长什么样」。两者都通过才写盘。为什么两步缺一不可：白名单挡住未来偷偷加进来的字段；但 `title`、`label` 本身是自由文本，有人完全可能把一段令牌贴进票标题，所以还要看值。

为什么用白名单而不是黑名单：黑名单只能列出「已经想到的危险字段」，漏掉一个就永远漏掉；白名单要求新增字段先来这里登记，没登记就写不进去，失败会当场暴露。

### 2.2 允许落盘的字段（逐项说清为什么）

| 字段 | 含义 | 为什么允许落盘 |
| --- | --- | --- |
| `v` / `at` | 存档版本号、这份存档的写入时刻 | 读端要认版本、判新鲜度 |
| `backend` | 后端名（github / markdown / gitlab） | 展示与换后端时给旧文件改名用 |
| `workers` / `session` | 会话这一层，以及会话 id 原文 | 去重键是（会话 id，票号），「是不是当前这个会话」也要逐字比较，用散列前缀会有碰撞；会话 id 是 DSH 本机的运行标识，不是能拿来登录任何服务的凭证（回执与界面不回显它，只给标题快照与是否本会话） |
| `label` / `labelAt` | 会话标题快照与取标题的时刻 | 面板要显示人读得懂的名字；快照会过期，所以不当作权威 |
| `entries` / `ticketKey` | 工作条目这一层，以及票号 | 记录「在处理哪张票」，也是回查票详情的入口 |
| `effortId` | 工作单元标识 | 只作展示，帮助区分同一后端里的不同工作单元 |
| `title` | 票标题快照 | 在办表要显示「哪张票」；与会话标题同理，是快照不是权威 |
| `action` / `actionAt` / `source` | 动作类别、动作时刻、来源（上报或自动） | 回答「在办还是陈旧」「谁记的」 |
| `progress` | 进度自评（0 到 100 的整数，可缺席） | 最近一次上报带的进度；只作展示。 #1352 起上报不再新增这一格，旧存档里已经记下的原样保留、不回溯删除 |
| `hasWork` | 这个会话在这张票上做没做过实事（可缺席） | #1349 起工作路线要按「这条是真处理过还是只上报过」决定能不能释放：建过、改过、关过、建过计划、挂过边的票不能从工作路线删掉。缺格表示旧账没记过这个标记，按「做过实事」保守处理，不许删 |

一句话概括：**允许落盘的是「给人看的名片信息」与「去重用的标识」，不是「能打开门的钥匙」。** 会话 id 原文允许落盘，但不等于对外可见：工具回执与界面只出现会话标识（标题快照，取不到时显示「会话 <散列前 6 位>」）与「是否本会话」布尔值，回执里绝不出现会话 id 原文。

### 2.3 永不落盘的内容

- **任何凭证原文**：令牌、口令、授权头、私钥、带凭据的 URL。这是硬红线，不是「尽量」。
- **命令原文、文件路径原文、票正文与评论原文**：它们不作为任何落盘字段的来源。不是靠检查函数把它们过滤掉，而是从一开始就不取这些值——工作条目只从 deck 工具成功回执里的结构化字段（票号、标题、工作单元、动作、时间）取数。
- **其他会话的、与这张票无关的任何文本**：同上，不取。

这里要特别说明「不作为字段来源」与「凭证形状检查」的分工：形状检查是启发式的，可能漏（把令牌拆成两半再拼起来、用编码藏起来），也可能误判（一个正常票标题长得像令牌）。所以本 ADR 的兜底不是「检查得足够聪明」，而是 **允许清单本身就只收结构化、短小、用途明确的字段**；自由文本只收两个快照（会话标题、票标题），且这两个快照只从工具回执与宿主会话服务取，不从命令原文里抄。

### 2.4 检查不过时怎么办：整份不写，不抛错，回执里说清

- 任何一处检查不通过，**整份存档不写**。不写半份、不跳过那一条继续写，因为无法确认被拦下的值是不是已经污染了别的字段。
- 内存里的工作路线照常更新，但这次整份存档不写盘：盘上保留上一次成功写入的内容，这是安全的状态。下一次写入重新读盘、合并、重新检查，通过时自然补齐——每次都以盘上内容为起点，不是拿内存副本重写。
- **不抛异常。** 工具永不抛错是仓库的既有约定：工具一抛错，AI 会退回去用后端命令行，两条写路径同时开火。落盘失败属于「这次没落上」，不是工具失败。
- 在工具回执的 `notes` 里用完整句子说明，按失败环节分开写：记这一步失败时说「这次没写成功；盘上可能还是旧内容（换后端时旧文件已单独留档），下次上报会重新读盘再补上」；读回核对失败时说「写下去了，但读回来核对没通过」；读在办表失败时说「这次读不出来」。不笼统地说「盘上还是上一次的样子」——换后端与读回失败两种情形下这句都不成立。盘上保留的始终是上一次成功写入的整份内容，这是安全的状态。
- 检查函数只返回「哪里不干净」的说明（字段路径加一句人话，例如「像 GitHub 令牌」），供本地日志与定位用；说明里不带被拦下的值本身（否则日志又成了第二份泄漏面）。工具回执只写 reason 代号与「这次没落上」的整句说明，不回显字段路径。

### 2.5 两代存档并存过：旧宿主缓存只存散列（#1271 已退役）

> 2026-10-19（#1271）：旧宿主缓存退役——`session-tickets.json` 文件、`src/host/refresh/workRoute.ts`、
> `src/host/refresh/sessionChainReadout.ts`、快照回包的 `workRoute` 字段、面板胶囊的旧读数路整份删除；
> 旧落盘/恢复函数（`CHAIN_DISK_VERSION`、`chainPrivacyViolations`、`chainToDisk`、`chainFromDisk`）
> 按本节 2.6 的安排同步删除。下面描述并存期的文字只作追溯，现状是只有新存档。

并存期机器上可能同时存在两份记录：

| | 新存档（本文口径） | 旧宿主缓存 |
| --- | --- | --- |
| 文件 | `<用户主目录>/.dsh/mattskillsdeck/work-path/<工作区根散列>.json` | `<进程当前目录>/.dsh-mattskillsdeck-cache/session-tickets.json` |
| 代码 | `src/deck/shell/work-path-store.ts`（纯逻辑在 `work-path-ledger.ts` 与 `work-path-privacy.ts`） | `src/host/refresh/workRoute.ts`（纯逻辑与 chainPrune 在 `src/shared/refresh/src/chain.ts` 与 `src/shared/refresh/src/chain-prune.ts`） |
| 内容 | 会话 id 原文、会话标题快照、票标题快照、票号、工作单元、动作、来源、时间、后端名（#1352 前的旧存档还可能有已退休的进度自评格，原样保留） | 只存散列与票键：会话分格散列、工作区根散列、后端名、票号、工作单元、时间、动作类别 |
| 读出口 | 工具回执里的 `data.workRoute`（跨会话在办表） | `wf.snapshot` 回包的 `workRoute` 字段（本会话视角） |
| 状态 | 2026-10-19（#1261）起写入；#1083 补齐隐私检查与落盘可信 | 2026-10-19（#1271）退役：文件、读写口、读数路整份删除 |

**为什么可以暂时并存：**

1. 两份服务的是不同读出口。旧缓存给面板胶囊的「本会话在处理哪些票」，新存档给跨会话在办表。读出口不同，不存在「同一份数据两个真源互相覆盖」的问题。
2. 两代不互相读取、不迁移。新存档不读 `session-tickets.json`；旧缓存也不读新存档。各自写各自的文件，就不会出现一半按新形状、一半按旧形状的混合文件。
3. 旧缓存只存散列，个人信息比新存档更少，本身不构成新的泄漏面；真正要防的「凭证原文」两代都禁止。旧缓存没有标题字段，所以旧自检「含空白即拒绝」在它身上仍然成立，不必为它重写隐私检查——重写它不如直接退役。
4. 退役成本比并存成本高（并存期的判断，#1271 已执行）：旧缓存还挂着面板胶囊的读数，等 #1271 把面板胶囊的读数也切到新存档，旧缓存连同旧自检、旧事件一起删掉，比现在先迁移一次、以后再删一次少做一半工。

并存期间有一个已知的不一致：两份记录的内容可能对不上（旧缓存按会话分片、只留散列；新存档按工作区一份、按会话分条）。这是过渡期的正常状态，不追求两份一致；#1271 退役旧缓存时一并收口。旧文件在 #1271 之前**不读、不迁移、不删除**，留给用户自己决定要不要清理；#1271 起旧读写口已删除，不再产生新文件，残留的旧文件由用户自行清理。

### 2.6 旧自检函数的去留（#1271 已执行）

`chainPrivacyViolations` 与它服务的 `chainToDisk`（v2 形状：`shards` 加四元组行）曾在 `src/shared/refresh/src/chain.ts` 里，保护旧宿主缓存——旧缓存里只有散列、票号、动作词与时间，没有空格，所以「含空白即拒绝」不会误伤。它**从不作为新存档的隐私检查依据**，新存档也不调用它。#1271 退役旧缓存时，这两个函数连同落盘版本号（`CHAIN_DISK_VERSION`）与读回函数（`chainFromDisk`）随旧形状一起删除；新存档的隐私检查只走 `src/deck/shell/work-path-privacy.ts`（字段白名单 + 凭证形状检查）。以后不要把旧自检复制回新代码里，也不要拿它去检查新存档。

## 3. 后果

### 3.1 换来的好处

- 面板与在办表能显示会话标题和票标题，人不用靠散列前缀猜「这是谁」。
- 「什么能落盘」变成一张可以逐项对照的表。以后加字段必须同时改本文件的白名单与检查函数，漏一处就写不进去，问题当场暴露，不会悄悄落一份没人知道的字段。
- 隐私红线不再依赖「不许有空格」这种会误伤正常文本的判据；红线落在「凭证原文永不落盘」与「自由文本只收两个标题快照」上。

### 3.2 付出的代价与新纪律

1. **新增字段要走三道手续**：先改本 ADR 的白名单表，再改 `work-path-store.ts` 的落盘形状，最后改检查函数。三处不同步时，写入会被整份拒绝（fail closed），门禁会红。这是刻意的：宁可写不进去，也不许悄悄多写一个字段。
2. **正常标题可能被误判**：凭证形状检查是模式匹配，一张票如果标题就叫 `sk-…` 这种样子，会被当成令牌、整份不写，回执里会说这次没落上。宁可误判，也不放行。遇到误判不要放宽检查，先看这个标题是不是真的不该落盘。
3. **用户主目录成为新的写盘位置**：存档跟着用户走，不再跟进程当前目录走。这是规格 #1259 的决定（沿用 `src/host/choiceStore.ts` 的先例），好处是同一个工作区换会话目录也能读到同一份记录。

## 4. 风险与不承诺

- **模式匹配不是完备保证。** 凭证形状检查可能漏掉经过编码、拆分或拼接的凭证，也可能误判正常文本。本 ADR 不承诺「检查通过就绝对安全」；它承诺的是：能落盘的字段只有这 16 个，自由文本只有两个标题快照，凭证原文一旦被识别就整份不写。
- **标题快照会过期。** 会话标题与票标题都是写入时刻的快照，票后来改名、会话后来换标题，存档里仍是旧的。展示时它是「当时的名字」，不是权威；权威永远是后端里的那张票。
- **不覆盖其他写盘路径。** 工作区配置、快照缓存、日志文件各有自己的口径，不在本文件范围内。
- **不覆盖 Windows 之外的家目录差异。** 路径拼接沿用仓库既有做法（斜杠拼接、由调用方注入目录），家目录取不到时按空目录处理、写失败在回执里说明；这是 #1083 落盘可信那一半的实现细节，见 `work-path-store.ts` 的注释。

## 5. 怎么判（门禁与文档核对）

- **门禁**（#1083 的 verify 测试，与本文一起落地）：字段白名单拒绝名单之外的键；凭证形状命中时整份不写、回执 notes 有「这次没落上」的说明；合法标题（含空格的会话标题、票标题）能正常落盘；落盘内容里只有白名单字段，除会话标题与票标题两个快照外不出现其他自由文本。
- **文档**（由人读，不进门禁）：`docs/architecture/refresh-budget-architecture.html` 增补第十二章与 `docs/reports/20260924-refresh-mechanism-status.html` 第 3 节不得再把新存档写成「只存散列」；「只存散列」只能用来描述仍在服役的旧宿主缓存。两处文档都按本文更正，并在章首/节首留了口径更新说明。

## 6. 以后要改这条口径怎么做

1. 先改本文件的第 2 节（白名单、允许清单、禁止清单），写清为什么。
2. 再改 `src/deck/shell/work-path-store.ts` 的落盘形状与检查函数，两者必须同时改。
3. 跑 #1083 的落盘门禁与日志门禁（`workRoute.write` / `workRoute.read` 两个事件）。
4. 如果改了字段名或事件名，同步改 `research/489-appendix.md` 的事件对照表（那一份是日志字段的现行真源）。
5. 不要为了「多存一点方便排查」而绕开白名单；排查需要的信息走日志，不走存档。
