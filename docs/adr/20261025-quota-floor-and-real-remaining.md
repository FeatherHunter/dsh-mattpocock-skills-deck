# ADR 20261025 · AI 工具的额度看作服务端的：只留 5% 保底，每小时顶降为提醒

> 日期：2026-10-25 定版（维护者在 #1527 的讨论里逐条定下六条口径，当夜开工；文字由 #1527 的实现补记）。
> 地位：本文是「AI 工具在什么情况下才拒绝」的唯一依据。它改掉了 ADR 20261014-quota-function-first 第 4 节里「超顶照样拒绝」的一半（每小时顶那一半），也改掉了 ADR 20260924-refresh-budget-architecture 里 AI 工具档的判据；后两份 ADR 的原则与结构结论仍然有效，凡是与本文冲突的旧说法以本文为准。

## 1. 背景：服务端还剩 3669 点，插件却报「额度见底」

2026-10-25 深夜，维护者在一次长会话里被插件的 AI 工具额度挡住，原话是「额度见底：GraphQL 点数额度不够了（还剩 204 点）」。同一时刻，服务端读数显示 GitHub 的 GraphQL 点数额度还剩 3669 点、REST 请求还剩 4999 条。**服务端还有七成额度，插件却因为自己的账本说没有。**

账本那一刻的数字是这样来的：插件按「服务端剩余的 35%」给自己分这一小时的额度，`floor(3669 × 35%) = 1284` 点；本小时已经花掉 1080 点；于是账本自己只剩 204 点；写预留按 30% 算是 385 点；判据是「账本剩余 204 ≤ 写预留 385」，于是拒绝 AI 工具写入。

根因有三条，叠在一起才成了这次事故：

1. **判据看错了账。** 闸看的是插件账本里「自己那一份还剩多少」，而不是服务端真实还剩多少。插件份额是后台刷新的自律线，不是 GitHub 的余额；拿它当余额，就等于服务端还有钱、插件却先把自己拦下。
2. **判据没减去这一笔的成本。** 「现在剩多少」还没花这一笔；判据必须回答「花完这一笔之后还剩多少」，否则剩 300 点时一笔 600 点的调用会被判成够花。
3. **拒绝时没把读数里已有的恢复时刻带出来。** 读数里本来就有 `reset`，文案也能写「约 HH:MM 恢复」，但闸这条拒绝路没把 `resetAt` 交过去，人只看到「还剩 204 点」，不知道什么时候能好。

另外还有一道每小时硬顶（2000 点 / 1500 条）。一次批量建图就可能撞上它，而它拒绝时说的是「这一小时攒太多了」——那与「额度不够」完全是两件事，后者才需要人等，前者只是插件给自己的自律线。

## 2. 裁决

**决定一 · AI 工具的判定只看服务端真实剩余，只留 5% 保底。**

- 保底线 = 向下取整（服务端这一桶的上限 × 5%）；5000 点 / 5000 条的后端，保底就是 250 点 / 250 条。判据是「花完这一笔之后，服务端剩余是否仍高于保底线」，不是「现在剩余是否高于保底线」。
- 成本按这一桶的计价单位算一次：GraphQL 数点、REST 与请求桶数条，不是两样都扣。
- 上限用服务端读数里的上限；读数里暂时没有上限时按 0 处理、保底也是 0，只用「服务端还剩多少」这一格，绝不拿插件自己的份额冒充余额。
- 保底线只约束 AI 工具；插件自己的后台刷新与人在界面上的动作不看这一格。

**决定二 · 单次硬顶保留，每小时顶降为提醒。**

- 单次硬顶：一笔最多 600 点 / 400 条出站请求，建票类一笔最多建 60 张子票。超了照旧拒绝，并说清这一笔预计花多少、上限在哪、超了多少、怎么拆。它防的是一次调用失控，仍然有效。
- 每小时提醒线：2000 点 / 1500 条。越过它照常执行，不拒绝；但回执必须带一句提醒，说清这一小时已用到多少、提醒线在哪、服务端这一桶还剩多少。读数未知时如实说「读数还没同步上来」，不拿占位的「剩 1 点」冒充。
- 提醒与保底是两件事：越过提醒线的那一笔，仍然要过决定一里的保底判定。这一小时用得多，不代表这一笔可以挤掉刷新与人的动作。

**决定三 · 拒绝文案要让人能自己核对。**

- 「额度见底」的文案必须写：缺的是哪一桶（REST 请求 / GraphQL 点数）、服务端还剩多少、这一桶的上限、保底线、这一笔预计花多少、花完只剩多少、大约几点恢复（读数带恢复时刻时）；读数没带恢复时刻就不编时间，只说剩余。
- 读数未知时不拒绝，如实说「读数还没同步上来」，不拿 0 或占位数字冒充（#1435 的坑）。
- 「单次超量」与「额度见底」的文案必须分得开：前者是插件给自己设的顶，后者是额度被别人用掉了；混成一句「额度不足」，人分不清该拆小还是该等。

**决定四 · 后台刷新份额不变。**

- 35% 小时池、读写 70-30 拆分、绿黄红档、探测退避都照旧，只约束插件自己的后台刷新与探测；不约束 AI 工具，也不约束人在界面上的动作。这次改的是 AI 工具那一档看哪本账，不是把后台刷新的自律线一起拆掉。

**决定五 · 提醒写进回执的 `cost.note`，同时保留 `cost.warnings`。**

- 回执里人最先读的是 `cost.note`，所以提醒也要写进那一格；`cost.warnings` 保留同一句话，供程序读。读数未知或离网时原有的说明照留，两句用分号接起来。
- 回执形状向后兼容：没有提醒时不出现 `warnings` 这一格。

**决定六 · 数值、算式、文案各归一处。**

- 保底比例、单次硬顶、每小时提醒线只在 `src/refresh/kernel/host-budget.ts` 定义；准入判定在 `src/refresh/kernel/admission-policy.ts` 算；拒绝文案在 `src/refresh/rooms/host/refusal-messages.ts` 拼；回执字段在 `src/deck/tools/tracker-session.ts` 落。任何一处都不许再抄一份数字。
- 门禁分工：`tests/verify-policy.ts` 断准入（单次超量、提醒线放行、保底跌破、未知放行），`tests/verify-1442-tracker-tools.ts` 断回执（九工具放行、`warnings` / `note` 带提醒），`tests/verify-1418-probe-cost-and-failure.ts` 断拒绝文案的数字。

## 3. 影响与迁移

- 发布说明要写清：AI 工具不再因为插件自己的 35% 份额被拒绝；只有「单次超量」与「花完这一笔会跌破服务端上限 5%」两种拒绝；每小时顶改成回执里的一句提醒。
- ADR 20261014 第 4 节「闸的硬顶语义不变（超顶照样拒绝）」里的「超顶」从此只指单次硬顶；每小时顶不再是硬顶。那份 ADR 的「功能第一、配额第二」原则与「数值按真实最坏情况放宽」的结论不变。
- 被删掉的东西：`host-budget.ts` 的 `aiToolHourWithinCaps`（每小时顶降为提醒后没有调用方，留着会让人以为还有一道硬拦）；`refusal-messages.ts` 的每小时拒绝文案与对应用户入参。历史日志里仍可能出现旧代号 `ai-tool-over-hour-cap`，原因代号表里留着它的说明，不再产生新记录。
- 未改的：后台刷新份额与档位、面板写完票后滞后（另票）、GitLab 只计请求数后端的行为（它按请求条数走同一套保底）。

## 4. 被否掉的路

| 方案 | 为什么不选 |
| --- | --- |
| 把 35% 份额调大（例如 60%） | 只是把同一个错误换成一个更大的数：份额仍然会随插件自己这一小时的用量下降，与服务端还剩多少无关；调多大都可能在服务端还有余量时拒绝 |
| 账本剩余换成服务端剩余，但保留「现在剩余 > 保底」的旧判据 | 不减去这一笔成本，剩 300 点时一笔 600 点的调用会被判成够花，花完却跌破保底；事故里那一笔就是漏了这一减 |
| 每小时顶保持拒绝，只把文案改清楚 | 维护者已经定下「降成警告」；一次批量建图就会撞线，被拒的原因却不是额度不够，与「功能优先、配额第二」的原则冲突 |
| 读数未知时按 0 处理（保守拒绝） | 正是 #1435 的坑：本地没有额度的后端会被永久推迟。未知不是耗尽 |
| AI 工具也用后台刷新的写预留（30%）当保底 | 30% 是给后台刷新留的份额，对 AI 工具太高：服务端还剩 1500 点时就会拒；维护者定的是 5% |
| 让读数每分钟同步来兜底，不改进判据 | 同步只让数字更新，判据看错账这件事不会因此变对；同步节拍与判据是两件事 |

## 5. 代价（如实写在明处）

- 服务端余量被 AI 工具吃掉的可能变大：保底只有 5%，一笔大调用可能用掉本可留给后台刷新的余量。换来的是一句更重要的保证：只要 GitHub 还有钱，人让 AI 干活就不该被插件自己的账本拦住。
- 每小时线降为提醒之后，一小时的用量可能超过 2000 点。读数每分钟同步一次、面板照常显示；失控时人能看到回执里的提醒，自己决定收手。若以后要恢复硬拦，改 `admission-policy.ts` 的判定，不要只把删掉的 `aiToolHourWithinCaps` 恢复回来。
