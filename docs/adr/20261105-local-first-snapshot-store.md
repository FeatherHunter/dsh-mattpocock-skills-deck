# ADR：本地优先的快照库——库是唯一真相，界面读它的投影（关联：规格 #1885）

> 日期：2026-11-05 定版（由维护者逐条拍板；对抗式审查后收口）
> 地位：工作区数据「从后端到界面」这条路的唯一依据。凡与本文冲突的旧写法——把变化补进宿主内存副本、按时间决定显示与刷新、向后端要统计数字、客户端另存一份业务缓存——以本文为准。

## 1. 背景

库已经建成了存储层（#1861），但「唯一真相」只落地在存储：后台补回来的变化写进宿主内存副本、回包由编排器在内存里拼、统计一半向后端要、客户端按生成时刻挑缓存。结果是同一张票在不同时刻说出两个值（切会话或重开就回到旧值）、改一行的代价等于整棵树（实测 1000 张票一次回包约 411 KB）、总数与列表对不上。

## 2. 决策

### 2.1 两条同步、一个真相

网络 → 库是取数；库 → 界面是投影。任何一步失败只影响新鲜度，不影响正确性。

- **写侧**：后端的一切读结果与写回执换算成按字段组的写入，进一个事务；事务里按被表达的字段组过版本门（该组已写入版本比起读版本新就整批丢弃），提交时库版本 +1，并把这一批触及的行记上「最后变化版本」。
- **读侧**：只读、纯函数、显式排序；同样输入两次调用逐字相同。
- **展示**：只渲染与格式化，不拼树、不算层级、不算可接/阻塞。

### 2.2 七条决策

| # | 决策 | 结论 |
|---|---|---|
| D1 | 投影在哪一层拼 | 宿主读侧拼（领域规则一处实现），浏览器只做格式化 |
| D2 | 「工作区数据」边界 | 库里只装工单域数据 + 同步簿记；布局、通知历史、在办表、命名持久化不进库 |
| D3 | 「这条票没了」怎么表达 | 墓碑（行保留，另记版本）；重新出现即清墓碑；库损坏才整库重建 |
| D4 | 统计从哪来 | 六个数字由库里一次查询算出；库没取全时带「已知」标记，界面明说 |
| D5 | 术语 | 「面板快照」退场，改由「快照库 / 投影 / 视图状态」承担 |
| D6 | 版本号 | 所有读回包都带库版本；库版本取代内容散列作为新鲜度与 304 的判据 |
| D7 | 改造纪律 | 每期单独可发布、可回滚；宿主与客户端同包同版本发布，跨端契约变更落在一期内 |

### 2.3 七条不变量

1. 只有库的摄入事务能改数据；
2. 每个读回包都带版本；
3. 新鲜度只按版本判（时间只用于容量与「退回整份」的降级阈值）；
4. 信号不带真相（版本查询与将来的事件只回答「变了没有」）；
5. 投影是纯函数；
6. 不知道就是不知道（没取过的不许补 0 或空数组）；
7. 删除只走墓碑，行不物理删。

### 2.4 读契约

`wf.snapshot`（投影 + 版本）· `wf.snapshotVersion`（版本 + 工作区键 + 后端）· `wf.snapshotChanges`（版本 + 变化行 + 删除行；落后太多回整份）· `wf.probe`（产生变化的唯一入口：宿主探测与补行，客户端只读版本）· `wf.issueDetail` 与 `wf.issueComments`（各自带版本）。写操作一律先落库再显示，写完之后有一个回执优先窗口挡住迟到的读结果。

### 2.5 变化信号

今天用五秒轮询版本（几十字节）；平台若开放转发事件只替换信号源，事件只带版本号。事实依据：宿主到界面的转发事件由宿主侧名单决定，第三方插件不能自行登记；事件是尽力投递、断线不重放——所以它只能是加速器，不能当数据通道。

### 2.6 存储层：迁移而不是重建

库是唯一真相，结构升级必须走加列/建表迁移（#1886 起）；只有迁移失败或库结构比本代码新才整库重建，并在界面明说「本机数据被清过」。重建时版本从头开始，客户端据此整份重取。

## 3. 分期与门禁

实施分七期（库结构与迁移 → 统计从库算 → 变化先写库 → 写回执全覆盖 → 宿主两条读口 → 客户端按版本取变化 → 回包纯投影并删内存副本 → 视图模型逐屏），对应 #1886–#1899，每期一句人话可验的结论。

门禁落在四个接缝上：宿主电话边界（主缝）、库的读写门面、视图状态、可替换的信号源。预算门禁：1000 张票一次完整投影 ≤ 25 毫秒、序列化 ≤ 500 KB；改一行回包 ≤ 5 KB；六个数字一次查询 ≤ 5 毫秒。

## 4. 后果

- 宿主不再持有面板数据的第二份副本；出问题只看一个文件；
- 改一行只传变化的那几行；
- 统计与列表同源；
- 代价：宿主每次回包都要做一次投影（1000 张票约 18 毫秒），大仓库下这条成本要靠「只传变化」摊薄。
