# ADR：取消远端 verify 工作流，改用本地 Node 24 全链当唯一验证口径（#1542）

> 日期：2026-10-26 定版（#1542 的执行结论；维护者决定原文记录在 PR #1535 正文的追加一节）。
> 地位：本文件是为什么取消远端验证、之后靠什么验证、代价是什么的唯一依据。凡与本文冲突的旧写法以本文为准；未来若恢复远端验证或改动本决策，以未来版本为准。
> 关联：#1542（执行票，本文落点）、#1523（根因票据，已按 wontfix 关闭）、#1541（与 Node 版本无关的残留失败门禁）、PR #1535、研究笔记 `research/1523-node22-sync-hooks.md`（保留，不删）。

---

## 1. 背景

远端的 `verify` 工作流自 2026-09-12 起没有绿过。根因记录在 #1523：远端用的 Node 22.23 系列在装载测试用的 TypeScript 源码时存在缺陷，同一份提交在本地 Node 24 上跑全链是全绿的，在远端 Node 22 上跑同一条链会出现上百道与代码内容无关的失败。
两类失败都与代码内容无关：第一类是请求的内置模块被报成没有链接，第二类是写成 `.js` 结尾的引用找不到同名的 `.ts` 源码。本地用 Node 24.15 及以上版本跑同一条命令，两类失败都不出现。维护者本机是 Node 24.19，桌面宿主内嵌的是 Node 24.21，仓库里唯一还在 Node 22 上的只有远端配置本身。
维护者判断：花在这条长期全红的链上的等待与排查没有产出，远端结论分不清哪道门禁是真的挂了，不再承担验证裁决职责。

## 2. 决定

1. 下掉 `.github/workflows/verify.yml`：推送 main 与开 PR 都不再自动跑构建与验证。
2. 保留其余工作流，它们不是验证裁决，不受影响：`matrix.yml`（只在人手工点开始才跑）、`release-tarball.yml`（只在发布新版本时跑）、`star-history.yml`（定时跑）、`thanks.yml`（定时跑）。
3. 更新两处把远端当作验证依据的文档：根目录的 `AGENTS.md` 跑门禁一节，`docs/agents/verification.md` 全新检出一节。
4. 处置 #1523：按 wontfix 关闭，研究笔记 `research/1523-node22-sync-hooks.md` 保留，两张票互相引用。本文件与 #1542 的评论合在一起，就是这次收口的完整记录。

## 3. 之后靠什么验证（替代规则，写死三条）

1. 本地跑链必须用 Node 24.15 及以上版本。在 Node 22 上跑链本身就是 #1523 记录的故障，会出现大量与代码内容无关的失败，结论没有参考价值。
2. `npm run verify:parallel` 是唯一的裁决入口。提交之前与推送之前每次都要跑它；串行全链只在排查顺序问题时用，不能替代它。
3. 合并前要求除登记在案的已知红之外，全链真红为 0。没有登记的红一律当作真红处理。

## 4. 代价和失去的东西

1. 失去远端自动兜底。以前推送后远端会自动跑一遍，现在没有这遍了，提交人必须自己在本地跑全链并对结论负责。
2. 本地机器差异需要人自己管。不同人的 Node 版本与构建缓存状态不同，第一次在新机器上跑全链前要先确认 Node 版本并跑一次构建，否则会看到构建记录缺失的提示行，这不是代码坏了。
3. 已知红需要人工登记和人工核对。取消后若还有残留失败，归 #1541 跟踪，不在本决定里修。
4. 换来的好处是结论重新可信。本地 Node 24 全链的结论与代码内容一一对应，不再被上百道装载故障淹没，等待与排查的时间花在真问题上。
