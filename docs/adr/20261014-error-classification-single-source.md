## 1. 背景：同一个决定，今天写在四个地方

失败时后端工具吐出来的是自由文本（`gh` 的 stderr、git 的提示与退出码、DNS 的错误名），程序靠一张词表从上往下试，**谁先命中就归谁**——所以「顺序」本身就是判据。今天这份判据写了四份：

| 判据在哪 | 覆盖什么 | 顺序上的问题 |
| --- | --- | --- |
| `src/tracker/preflight.ts:30-59` 跟踪器层通用判据 | 所有后端的兜底 | 「没登录」那组的词表里含 `\b403\b`（`:44`），限流回的 403 会先被判成没登录；`not ?found`（`:50`）会把 `ENOTFOUND` 吞成「找不到」，而网络判断排在它后面（`:56`） |
| `src/tracker/rooms/github/errors.ts:64-106` GitHub 房间 | GitHub 的报错 | 这两处修过：403 且带限流文案归限流（`:92`），网络特征排在找不到之前（`:95-99`，`:42-44` 的注释记着 #620 的实测复现） |
| `src/tracker/rooms/gitlab/errors.js:12-33` GitLab 房间 | GitLab 的报错 | 又抄了一份通用词表：`not ?found` 在 `:27`、网络在 `:30`，与通用判据同款的隐患仍在 |
| `src/client/kernel/api-io.js:202-206` 客户端 | 面板显示 | 拿到结果后再从 `message` 文本里找 `404` / `not found` / `rate limit` 并改写 `err.kind`，用的还是另一套取值（`'404'`、`'notFound'`、`'rateLimit'`） |

两处实测错判——同一句报错，两处给出相反的建议：

1. **限流被说成没登录**。GitHub 限流回 HTTP 403 加 `API rate limit exceeded …`：通用判据先看认证词表，判成「没登录」，建议去登录；房间判据专门处理了这一种，判成「被限流」，建议稍后再试。
2. **网络不通被说成找不到**。DNS 失败原文 `getaddrinfo ENOTFOUND api.github.com`：通用判据的 `not ?found` 命中 `ENOTFOUND`，判成「找不到」（界面于是让人去核对标签名）；房间判据把网络判断排在找不到之前，判成「网络不通」。#620 实测复现过这起误判，房间那侧修了、注释也写了，通用那侧没修。

原文今天也不是「拿不到」，而是各写各的：`src/tracker/rooms/github/client.ts:248` 的失败对象里带着退出码 `code`，`:259` 却只留一段 `message`（`String(stderr || stdout || …).slice(0, 800)`）；`errors.ts:110` 同样只留 800 字。契约对 `TrackerError` 的注释写着「`message` 是给人看的一句话，允许直接展示」（`results.ts:23`），于是原文要么挤进 `message`，要么无处可去。

仓库自己也知道这是隐患：`src/tracker/preflight.ts:42-43` 的注释写着「两处各写了一份判据，要同改」。

## 2. 裁决

1. **判据只有一个真源。** 一张有序规则表住在跟踪器层的 `src/tracker/error-rules.ts`，判档入口是 `src/tracker/preflight.ts` 的 `classifyError(err, ctx?)`；所有后端与客户端都走它。各家只许写**前置扩展**——本后端专有的错误码名与句式（例如 `glab: command not found`），且不许复制通用项。
2. **判据的输入是事实对象，不是字符串。** 形状是 `{status: HTTP 状态码, exitCode: 进程退出码, errCode: errno 或错误码名, text: 原文}`。这些证据今天已经拿得到（403、退出码、`ENOTFOUND`），却在判据入口被拍扁成一段字符串再猜。
3. **顺序按证据的硬度排**（第一性原理：越硬的事实越先判）：结构化事实（状态码／退出码／errno）→ 该后端专有的错误码名 → 专有句式 → 通用的含糊短语（这一层收到词边界，例如把 `not ?found` 收紧）→ 兜底归网络。并且「本机缺工具」必须排在「资源找不到」之前。
4. **失败结果改成三段式，原文必填**：`{kind, message, raw}`——`kind` 是八档之一，`message` 是给人看的一句话，`raw` 是后端或命令吐出的原文。原文多路合并（stderr 优先，其次 message、stdout），过长时保留头尾、裁掉中间（合并细节与字数见 #1111）。
5. **原文必填的理由**：分类是启发式的，可能猜错；原文让人自己判断。这是本次取舍的核心——不接受「分类一定对」这个假设。
6. **规则表每条自带样本自证**（正例与反例跟规则写在一起），不另配一张样本表；谁改了规则，谁的样本必须跟着变红。
7. **客户端不再猜档位**，改成「八档 → 界面档」的映射表。原文写进日志前按既有脱敏纪律遮蔽凭据样式。
8. **归一埋点提到跟踪器层**：凡判据都发一条 `error.normalize`（只记归一前后的类别与状态码，不记原文）。今天这条埋点只有 GitHub 房间有（`errors.ts:49-62`）。

## 3. 被否掉的三条路

| 方案 | 为什么不选 |
| --- | --- |
| 甲：各处各写一份、只在文件头注明差异清单（零成本、不改行为） | 同一个决定留在四处，实测已经产生两条错判；本次口径要求把已发现的风险解决掉 |
| 乙：只补通用判据缺的那两条，房间那份不动 | 两份仍会漂移；仓库自己在 `preflight.ts:42-43` 写着「要同改」，而漂移正是这次两处给出相反建议的根因 |
| 丙：把原文塞进 `message`（不动契约形状） | `message` 的定义是「给人看的一句话」，会被各层改写与截断，也不可机读；原文要与那句话分开传递，才能在界面上单独展开 |

## 4. 代价与已知限制

- 分类仍是启发式，仍可能猜错。本决策不承诺「判对」，承诺的是「猜错时人拿得到原文、能自己判断」。
- 契约的失败形状新增一个必填字段：所有构造失败的地方都要带上原文。TypeScript 侧靠编译器逼出遗漏（契约目录 `tsconfig.contract.json`、客户端内核 `tsconfig.client.json` 都在检查范围内），但**跟踪器整棵树今天还没有自己的 tsconfig**（这条缺口归 #1095 那条测试跟随线），所以跟踪器侧改用一条静态门禁顶住：凡 `fail(...)` 调用必须恰好三个参数，外加一条真实调用样本门禁断言每个失败都带字符串原文。
- 原文里可能有路径、地址、令牌形状：展示前遮蔽、日志按既有白名单脱敏，凭据原文永不落盘（沿用日志纪律的硬红线）。
- 顺序与词表是长期维护面：以后每加一个后端，只加前置扩展，不许再加第二份通用词表。

## 5. 落地与验收面

- 落地票 #1111：失败形状、事实对象入口、规则表与自带样本、客户端「八档 → 界面档」映射、归一埋点提到跟踪器层、门禁。
- 同批 #1112：注册表不再替后端造链接，与本决策共用同一张规格单 #1110。
- 门禁（在 #1111 的 Testing Decisions 里逐条写死）：真实原文夹具含上面两条错例；「每个真实失败都带原文」的样本门禁；规则表每条自证；归一埋点门禁；既有四条缝（金标准回执夹具／注册表行为段／契约门禁／选择优先级门禁）保持绿。
- 落地后的四份门禁文件：`tests/verify-error-rule-samples.js`（规则表逐条拿自带样本自证 + 真实原文夹具逐条断言档位）、`tests/verify-error-normalize-log.js`（假上下文驱动各后端判档入口，断言都发 `error.normalize` 且原文与凭据不进日志）、`tests/verify-error-single-source.js`（静态：`fail(...)` 必须恰好三段；档位字面量只许出现在白名单里，白名单按文件加具体取值收窄）、`tests/verify-error-raw-samples.js`（起本地假后端串行走三条真实失败路径，断言每个失败都有字符串原文、凭据被遮蔽）。四份都登记在 `package.json` 的 `scripts.verify` 一串里，因而随 `npm test`、`npm run verify:parallel`、`node scripts/verify-all.mjs` 三处入口一起跑。
