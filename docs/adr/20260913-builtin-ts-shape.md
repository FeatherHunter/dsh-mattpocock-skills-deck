# ADR：插件内置 TypeScript 的形态（不发 npm 包 · 照 update-core 的形状 · #616 定版）

> 日期：2026-09-13 定版（承接地图 #610 已定的口径「这次的新功能用 TypeScript 写、但不发 npm 包」；依据是研究 #613 与 #616 六道题的答案）
> 地位：本文件是「插件内置的 TypeScript 能力」这一形态的唯一依据——源码放哪、编译产物放哪、构建怎么接、门禁加哪一条、结构纪律取哪几条、哪些东西明确不写进 TypeScript。凡与本文冲突的旧写法以本文为准；未来任何讨论若改动本决策，以未来版本为准（CONTEXT.md 同款两条规则）。
> 关联：#616（定版）· #613（研究：落点、构建与门禁的最小改动路径）· #610（父图）· #629（落地：配色核心，它阻塞 #618／#620／#621／#622）· #618 / #620 / #621（按这份定版开工的落地票）· #619（删掉初始化注入的旧调色盘文案，接口关系见 §2.9 第二条）

## 1. 背景与实测依据

1. 仓库里已经有一份「不发 npm 包的内置 TypeScript」：根级 `update-core/`。它的形状是——源码在 `update-core/src/*.ts`，用 esbuild 逐文件转译进 `src/shared/update/*.js` 并提交进 git；宿主用普通相对 import 直连（例如 `src/host/update.js` 里的 `from '../shared/update/service.js'`）；专属门禁 `tests/verify-update-freshness.js` 逐字比对源码与产物，并另跑一次 `tsc --noEmit`。
2. 这份先例有一个缺口：它没有被接进任何自动流程。根 `package.json` 的 `prepare`（第 15 行）里没有它，`scripts/build.mjs` 也不编译任何 TypeScript。结果是改它一行要跑两条命令（先 `node update-core/build.mjs`，再 `node scripts/build.mjs`），漏跑第一条要等门禁变红才发现。
3. 两条硬约束（研究 #613 核实）：
   - 宿主运行时要能拿到的代码，必须落在 `src/host/` 或 `src/shared/` 里——构建把这两棵树整树复制进 `package/lib`、`package/shared`。
   - 客户端只有一个入口：打包产物里只允许出现一处模块加载调用，没有加载第二份客户端代码的机制。
4. 一个必须避开的坑：`scripts/build.mjs` 对 `src/host/**` 与 `src/shared/**` 是整树递归复制。TypeScript 源码不能直接放在这两棵树下，否则 `.ts` 文件会跟着进 npm 包、再同步到用户机器上（不会报错，但等于把源码当死文件一路发出去）。
5. 成本实测（研究 #613，只读）：一次 `tsc --noEmit` 耗时 0.4～0.9 秒。把编译并进主构建脚本后，「改一行代码到在界面上看见效果」仍然是一条命令，只多不到一秒。
6. 客户端闭包有一个真实的历史事故（`tests/verify-generated-no-shadow.js` 文件头记录）：拼进闭包的模块，顶层函数声明会被提升，后拼的同名函数顶掉先拼的，界面会永远弹「开关保存失败」而且一条日志都发不出去。凡是新增「拼进闭包」的代码，都要考虑与已有名字撞车这件事。

## 2. 决策

### 2.1 为什么不发 npm 包

这次要做的是插件自己的一项能力（在面板上读标签颜色、写标签颜色），不是一份要交给别人复用的东西。

发包要连带维护一整套与功能无关的东西：版本号、发布配置、发布向导、发布契约门禁；更麻烦的是，包一旦发布，插件里还必须自带一份可运行的副本，于是同一份代码有了两个落点，仓库里为此写过 `scripts/derive-log-from-package.mjs` 与 `scripts/derive-update-from-package.mjs` 两个派生脚本，脚本里还包含引号归一、注释路径归一、改名避免撞车、零变化断言这些**只为两份副本保持一致**而存在的步骤（研究 #613 逐一列过）。

不发包，就没有第二份副本，上面这些步骤一条都不需要。

代价（明确接受）：别的插件用不到这套代码；将来真要给别人用，就照 `update-core/README.md` 记下的 538 决议——整个目录拎走，再按发布流程走一次。

### 2.2 结构纪律只取三条，不照搬 vscode 的 base / platform / workbench

取这三条：

1. **先写接口类型再写实现**：先定 `ports.ts` 里的形状，再写实现文件。
2. **纯逻辑不碰磁盘与网络，读写一律走注入进来的适配器**：第一批核心一行读文件、起进程、联网的代码都没有。
3. **按能力分目录、按能力命名文件**：`label-color-core/src/` 下就三件事——定形状（`ports.ts`）、色值计算（`colors.ts`）、提示词拼装（`prompt.ts`）；不设「基础层 / 平台层 / 工作台层」。

不照搬 vscode 三段式的理由：那套结构解决的问题是「一套代码要产出多个应用」（桌面版、网页版、服务端各一份），所以 base 放与任何应用无关的底层、platform 放要按应用注入的服务接口、workbench 放单个应用自己的界面与编排。本插件只有一个产物、一个客户端闭包、一棵源码树，没有第二个应用来证明分层的收益；照搬的后果是每个文件都要先回答「我属于哪一层」，还逼着同层互引门禁为三层目录各写一份白名单（那份白名单现在只许减不许增，84 条存量边已经记在 `tests/same-layer-baseline.json` 里）。

取的是那三条真正拦得住事的纪律，目录名和层数不学。

### 2.3 源码与产物落点

- **源码**：仓库根的独立目录 `label-color-core/`，内含 `src/*.ts`、`build.mjs`、`tsconfig.json`、`README.md` 四件，形状照 `update-core/`。不进 pnpm workspace（`pnpm-workspace.yaml` 仍然只有 `packages/*`），不建 `packages/<名字>/`——不制造「这里又有一个要发布的包」的假象。
- **产物**：逐文件落进 `src/shared/label-color/*.js`，与源文件同名，首行带 `// AUTO-GENERATED by node label-color-core/build.mjs — DO NOT EDIT.` 包头，提交进 git（先例：`src/shared/update/*.js`）。
- **宿主侧怎么拿**：普通相对 import，例如 `import { normalizeColor } from '../shared/label-color/colors.js'`。
- **客户端侧怎么拿**：用仓库既有的「一源两物」拼接机制——在 `scripts/build.mjs` 的 `SHARED_SPLICE` 清单里登记，并在 `src/client/index.js` 对应位置留 `// ==== shared:<名字> (spliced by build) ====` 标记。它与 `src/shared/workspaceKey.js`、`src/shared/ui/slots.js` 等八个既有共享文件走的是同一条路，不新造机制。

### 2.4 构建：转译与类型检查并进主构建脚本

- **新脚本要导出的东西，`update-core/build.mjs` 今天没有全给**：那个文件只 `export function transpileUnit(tsName)` 一个函数，`runTypeCheck()` 与 `main()` 都是文件内的私有函数。所以「照 `update-core/build.mjs` 抄、只改 `SRC_DIR`／`OUT_DIR`／`UNITS` 三处常量」这句话不完整：`label-color-core/build.mjs` 还要**新导出 `runTypeCheck` 与 `buildAll`**（在自己这份脚本里把 `main()` 改名为 `buildAll` 并导出），`scripts/build.mjs` 才能 import 到这两个函数并在 main 开头、两段派生之前调用一次。
- 照抄的还有该文件最后七行的「命令行直接执行时才跑」判据（`const invoked = process.argv[1] && resolve(process.argv[1]) === fileURLToPath(import.meta.url)`，成立时才调用入口函数并接住异常）。这与「导出的是函数、被 import 时不跑流程」并不矛盾：导出的是函数本身，会「跑起来」的入口只在命令行直接执行这个文件时触发；所以 `scripts/build.mjs` 里那次 import 不会有副作用。
- `buildAll()` 必须先判断 `label-color-core/` 源目录与 `label-color-core/tsconfig.json` 是否存在：**不存在就跳过转译、打印一行清晰提示，不许中断整个构建**。这是必须写的保护，不是可选的健壮性——npm 发布包的 `package/package.json` 里，`files` 白名单只有 `lib`、`shared`、`cordis.patch.yml`、`bundled-skills`、`scripts/`，不含也不该含 `label-color-core/`；而 `package/package.json` 的 `build` 与 `prepare` 指向 `../scripts/build.mjs`，在 `package/` 子树里构建时那棵源码树与它的 tsconfig 都不存在，用户机器上装出来的包同样没有。`update-core` 今天没有这个风险，只是因为它压根不在构建链上。
- 效果：全仓「改一行代码到看见效果」仍然是一条命令 `node scripts/build.mjs`。这与 `update-core` 的差异（它要两条命令）是本决策有意补掉的缺口。
- 根 `package.json` 的 `build`（第 10 行）与 `prepare`（第 15 行）都不用改，主构建脚本已经覆盖。
- 要不要顺手把 `update-core` 也并进主构建脚本、让全仓只剩一种节奏：**另开票**，不在本次范围（它落在两个已发布包共用的构建链上，与本票「不动现有两个已发布包」的边界相撞）。

### 2.5 门禁：只加必须的那一条，三条纪律靠文档与人守

- **要加的（必须）**：`tests/verify-label-color-freshness.js`，照 `tests/verify-update-freshness.js` 抄。它做三件事：逐字比对 `label-color-core/src/*.ts` 与 `src/shared/label-color/*.js`（转译口径直接复用 `label-color-core/build.mjs` 导出的同一个函数，永不漂移）；另跑一次 `tsc --noEmit`；断言产物文件之间零相对引用。它要登记进根 `package.json` 的 `verify` 链。没有这一条，「改了 TS 没重新生成」就没有任何机器在看。
- **不加的（本次）**：「纯逻辑不碰磁盘与网络」暂时不立机器门禁。理由与代价：核心第一批只有三个文件，人读一遍十秒；而 `verify` 链已经很长，每加一段都在此后每一次提交里付费。三条纪律写进本文件与 `label-color-core/README.md`，由人守；等核心长大（大约超过六个文件，或者真开始接适配器）再补这条机器门禁。

### 2.6 客户端半边怎么进闭包

研究 #613 给过两条路：派生成一个客户端分块放 `scripts/generated/`（要扩「同名撞车」门禁），或者当普通叶子放 `src/client/`（受 350 行上限与「文件里不许出现中文字符串」两条管，后一条即 `tests/verify-locale-completeness.js` 的中文残留基线）。本决策走**第三条既有的路：共享拼接**。

理由：宿主要用这份代码，产物本来就必须落在 `src/shared/`；而落在这里的文件本来就能被 `SHARED_SPLICE` 拼进客户端闭包。派生分块（产出到 `scripts/generated/`）这条路真正走不通的地方在语言：派生件是构建机器生成的，天然只有一种语言，它内容里的中文改不掉，而 `src/client` 下的文件被「中文残留基线」管着（清单外文件出现字符串级中文即红）——仓库里 `scripts/derive-log-from-package.mjs` 的文件头写着它当初正是因为「内容含中文错误文案、放 `src/client` 下会被中文基线门禁误拦」才落在 `scripts/generated/`。本功能的界面文案必须中英两份，共享拼接拿到的产物是被界面代码当普通函数调用的（文案由调用方从词表传进去），这一条只有共享拼接满足得了。派生分块另外还要多维护一份「改名避免撞车」的步骤，那套东西是为「已发布的包 + 插件自带一份」两份副本设计的，内置形态没有第二份副本——这是次要代价，不是否决理由。

代价（必须知道）：`src/shared/` 属于同一个层，文件之间不许互相引用（`tests/verify-no-same-layer-import.js` 会红）；`src/shared/**` 下的每个 `.js` 都在 `tests/verify-file-granularity.js` 的 350 行上限之内（这条不给转译产物豁免）。所以配色核心要按「一个文件一件事」拆，跨文件只传数据、不互相 import；要引用的类型一律写成 `import type`（转译后不留相对引用，先例是 `update-core/src/commands.ts`）。

客户端拼接还有两条边界条件（必须知道）：拼进闭包的两个产物必须满足——写清单与写核心的人要照着办。一是**产物必须是 ESM，并且要用的东西都带行首 `export` 声明**——`scripts/build.mjs` 的 `extractModuleBlock` 就是靠去掉行首的 `export ` 把声明体贴进闭包，产物若是 CommonJS 形式（`module.exports`／`exports.x =`），贴进去的名字在闭包里不成立。二是**产物里不能出现 `__DSW_VERSION__` 与 `__DSW_REPO_URL__` 这两个占位符**——构建里的顺序是「先做版本注入、再按标记拼接」（`scripts/build.mjs` 里写的是 `wireModules(injectVersion(body, version, repoUrl))`），拼接进来的文本不会再过一遍注入，占位符会原样留在产物里。

### 2.7 哪些东西明确不写进 TypeScript

- **视图渲染**：弹窗本体、标签表格的每一行、取色控件，全部留在 `src/client/` 下的普通 JS 文件里（登记 `LEAF_MODULES` 与 `tests/verify-leaves.js`，文案走词条，单文件不超过 350 行）。理由：这些代码长在界面框架上，TypeScript 换不来什么，还会把中文文案挤到不该放的地方——守 `src/client` 双语文案的那条门禁是 `tests/verify-locale-completeness.js`：它按一份「中文残留基线」给 `src/client` 逐文件封顶，清单外的文件里出现字符串级中文即红。注意它和 `tests/verify-client-hardcode-gate.js` 不是一回事：后者是业务级检查，查的是「与品牌 id 的等值比较」「平台 URL 字面量」「三后端名单字面量」这三件事，与中文文案无关，也不该被当成中文门禁来引用。
- **样式、图标、主题变量**：留在现有 JS 里。
- **拼接进闭包的叶子模块与构建胶水**：`scripts/build.mjs`、`scripts/derive-*.mjs`、`src/client/index.js` 里的拼接标记，留在 JS。
- **宿主取数层与落盘**：tracker 契约层、三个后端房间、往工作区写文件的原子写与单写者队列、日志埋点，留在 JS——它们正是要挡在核心外面的 I/O。
- **词条与文案**：留在 `src/client/kernel/locale*.js` 的词表里，中文与英文两份都要加（`tests/verify-t3-locale.js` 要求两边键集合全等）。

### 2.8 与「标签配色可编辑」功能的关系

- **读写颜色的端口类型放哪**：`label-color-core/src/ports.ts`，产物 `src/shared/label-color/ports.js`。只放形状——清单一项、一项改动、逐条记账结果、两个方法的形状；**不放操作名与错误分类**，那两样归 tracker 契约层（#615 定版、#627 规格已写定）。这个文件的产物是空壳（类型在转译时已擦除，只剩一行模块标识），没有任何运行时代码 import 它，只由门禁读一次；先例是 `src/shared/update/ports.js`，它的现状完全相同。**这个空壳保留**（总工裁决）：先例已经在那里，形态一致比省一个文件重要，它也给核心长大留了落点，门禁还靠它验证「插口由核心定」这条纪律。
- **颜色的空值语义（总工裁决，写进 TS 核心，实现前必读）**：契约层的 `color` 允许是空串（`''` = 这个标签还没配颜色，界面按灰显示），所以核心的相等判断必须把「两边都没配色」判成「没变」。四条裁决照写如下：
  1. 归一化 = 去掉开头的 `#`、转成小写、去掉首尾空白；
  2. `colorsDiffer(a, b)`：两边归一化后**相等**（包括两边都是空串，或两边都是同一个非法值）→ **没变，不发送**；不相等 → 变了，发送；
  3. 「值是否合法」是另一件事，由 `isColor` 单独判定，**不参与相等比较**：两个不同的非法值判为「变了」，照常发送，由后端按解析档报错（与「后端不做本地校验」的既有口径一致）；
  4. `pickChangedRows` 只挑 `colorsDiffer` 为真的行。
  这条裁决的理由是审查员算出的一个真实反例：按「任一边归一化失败就当作不同」的写法，`colorsDiffer('', '')` 会返回真，于是**每一条还没配色的标签都会被算成「改过了」**，一保存就白发一批请求，正好违反本功能的「只给颜色真的变了的标签发请求」。同一个反例也说明：`isColor('')` 为假，不代表 `colorsDiffer('', '')` 要为真——合法性和相等比较必须分开判。
- **适配器放哪**：两处，都在既有目录里，不新建目录——各后端房间（GitHub 房间写仓库标签颜色，本地 Markdown 房间读写工作区里的配色文件），以及 tracker 契约层的分发（没实现这两个操作的后端自动落到「做不到」的桩，见 #627）。**房间要用同一套色值口径，就得能引用这部分共享代码**：`tests/verify-no-cross-import.js` 的房间导入白名单要加一条 `src/shared/label-color/**`（见 §2.9 第一条）。
- **谁注入给谁**：tracker 层 → 宿主接线 → 注册两条宿主电话交给客户端。**这两条标签配色电话随本功能落在既有的 `src/host/workspaceCwd.js` 里，在 `src/host/index.js` 注册**，不新建 `src/host/labelColors.js`（总工裁决，理由照审查员给的写）：这两条电话依赖 `createWorkspaceCwd(deps)` 注入进来的那批依赖件，以及该文件作用域里的 `pickBackend`、`opCtxFor`、`loggedPhone`、`normCwd` 四个私有件；另建一个文件就要把这些从 `workspaceCwd.js` 里搬出去或导出，等于把一个正在被别的改动碰的文件再拆一刀，也是两张票并行时**重复注册同一个电话名**（两处都注册就会运行时冲突）最容易出事的地方；而 `src/host/workspaceCwd.js` 的行数远低于文件行数上限，装得下这两条电话。代价（明确接受）：一个文件承担两件事，后来人找「谁在改标签颜色」要多跳一次；等标签配色长大到该独立成模块时再拆，拆的时候按仓库已有的先例走「纯结构、行为零变化」那条路。**核心本身不被注入任何端口**，因为第一批核心是纯函数、不读写任何外部东西。
- **客户端侧不设端口**：理由不是「弹窗只需要共享类型」——客户端闭包里没有类型（类型在转译时就擦掉了），`ports.js` 也不在拼接清单里（`SHARED_SPLICE` 只登记 `colors.js` 与 `prompt.js` 两条），客户端侧根本没有共享类型可拿。真实理由是：全仓只有一个实现，客户端只是调用这两个纯函数、文案从词条传进去，设端口就是空壳。
- **色值校验与提示词拼装是不是第一批进 TypeScript 的东西**：**是**。理由：两件事都是纯计算，而且宿主与客户端都要用同一套口径——宿主侧要按「不带井号的小写六位」比较颜色有没有变，客户端要按同一口径判断用户填的值能不能用；两边各写一份必然漂移。仓库里同族的默认色表（含界面里的那张调色盘表）至少有五处，其中 `src/shared/labels.js` 里 `wayfinder:grilling` 那条色值写成了大写的 `9D7CD8`，就是这种漂移的既成事实。
- **新的提示词拼装与仓库里既有的调色盘文案是什么关系**：新的 `buildPalettePrompt` 是调色盘表格文案的唯一来源；旧的 `paletteNote` 那条路由 #619 负责删除或改写，边界见 §2.9 第二条。

### 2.9 落地清单里必须写清的三件事（照这份定版开工的补充施工项）

1. **房间导入白名单要加一条**：`tests/verify-no-cross-import.js` 的导入白名单（`WHITELIST_RE`，现在只有 `src/shared/tracker/`、`src/shared/labels.js`、`src/host/tracker/preflight.js`、`src/host/platform/` 四条）要加 `/^src\/shared\/label-color\//`。理由：GitHub 房间与本地 Markdown 房间要按同一套色值口径比较颜色，就得能引用配色核心这份共享代码；白名单里已经有 `src/shared/tracker/**` 与 `src/shared/labels.js` 两个同类条目，加这一条是同一类允许，不是开口子。不加的后果：照清单施工当场撞红一条门禁，或者被迫把色值口径再手抄一份进房间——那正是本决策要消灭的漂移。
2. **调色盘提示词的关系定死**：新的 `buildPalettePrompt`（TS 核心）是调色盘表格文案的**唯一来源**。仓库里旧的 `paletteNote` 那条路——`src/client/kernel/prompts.js` 里 `setupRun` 的占位符、`src/client/kernel/locale-panel.js` 里的中英文文案、以及 `tests/verify-setup-describe.js` 里所有涉及 `paletteNote` 的断言——由 #619 那张票负责删除或改写，本票只在清单里点明这层关系与要同步的门禁，不动它们。`tests/verify-setup-describe.js` 里这份行号清单已逐行复核列全（2026-09-13 实测）：金样 `PALETTE_NOTE` 定义在第 42 至 45 行（中文第 43 行、英文第 44 行），它只被第 114、115、130 行引用；断言共六处——第 83 行（markdown 后端的 `setupPrompt` 里声明了 `paletteNote` 这个键）、第 99 行（中英两份词表都有 `setup.markdown.paletteNote` 这个键）、第 114 行与第 115 行（两条精确字符串相等：词表里的键值 == 金样）、第 119 行（场景「未选择后端」：解析结果里的 `paletteNote` 是空串）、第 121 行（场景「未知第三方后端 id」：解析结果里的 `paletteNote` 是空串）；第 130 行取期望值、第 132 行拿它做 `setupRun` 全文逐字比对（markdown 用金样、其余后端用空串），这两行也在这条拆除范围内。另有两条按「调色盘」字样断言注入文本的（第 143 行 markdown 注入文本含调色盘表指令、第 146 行 GitHub 注入文本不含调色盘规则），落地时要一并核对。
3. **发布包与 `package/` 子树里没有这棵源码树**：`buildAll()` 要按 §2.4 写的那样处理「`label-color-core/` 源目录不存在」——跳过转译并打印一行清晰提示，不许中断整个构建。

## 3. 后果

- 正：新功能有一套编译期的类型约束（色值的六位十六进制口径、清单项与改动的形状）；开发循环与今天写 JS 一样长（一条命令）；不制造第二个「要发布的包」的假象，也不新增第二种客户端打包方式；后来人照 `update-core/` 这份先例就能读懂新目录。
- 代价：仓库根多出一棵与 `packages/` 同级的源码树，读代码的人要多认一类目录（本文件与 core 的 README 负责解释）；`tests/verify-build-artifacts.js` 里「共享层 23 文件」的两处计数要改成 26，并照 `#540`／`#542`／`#589`／`#600` 那几行的格式补一行来历注释（即「两处计数 + 一行来历注释」）；三个产物文件各自要守住 350 行与「互相不引用」；客户端闭包多两个拼接分块，它们的顶层名字必须在闭包里唯一，而且产物要满足 §2.6 写的那两条边界条件（ESM 带行首导出、不含两个版本占位符）；宿主这一侧一个文件承担两件事（§2.8 的代价）。
- 风险与缓解：
  - 改了 TypeScript 没重新生成产物 → 由必须加的这条新鲜度门禁拦下。
  - 中文文案被写进核心 → 管中文的那条门禁 `tests/verify-locale-completeness.js` 只扫 `src/client`，看不见 `src/shared`（`tests/verify-client-hardcode-gate.js` 是业务级检查，管不到这件事）→ 靠本文件 §2.7 与 core 的 README 拦；落地票收尾的验收票要人读一遍核心产物。
  - 核心长大后纪律失守 → 到那时补「不碰磁盘与网络」的机器门禁（触发条件写在 §2.5）。
  - 拼接进闭包的名字与既有函数撞车，静默坏功能 → 落地票把两个新产物文件加进 `tests/verify-generated-no-shadow.js` 的顶层名字比对集合（**已裁决要扩**；这条门禁就是为 #597 那次事故写的，那次真出过「界面永远弹失败、日志一条都发不出」的静默坏功能）。
  - 「客户端产物比源码旧」没有门禁看见 → **已裁决：加**。把 `src/shared/label-color/colors.js` 与 `prompt.js` 加进 `tests/verify-kernel.js` 的 `SOURCES`。那条列表是「任何一项比产物新就判产物过期」的判据，新产物是客户端闭包的输入，加进去以后「只重跑核心转译、没重跑主构建」这种漏跑会更早变红。代价说清：`SOURCES` 里第一次出现 `src/shared/` 下的文件，而另外八个既有共享拼接文件仍然不在这个列表里（存量空白，本票不为它们破例，补法是另一张票的事）；同时「只重建核心」这条单独的开发动作不再能孤立使用——必须跟着跑一次主构建，否则这条门禁会红（这正是想要的效果，但要知道这条约束）。
