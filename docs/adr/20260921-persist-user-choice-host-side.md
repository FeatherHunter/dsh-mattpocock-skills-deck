# ADR 20260921 · 用户选的后端按工作区存在宿主侧（F1：跨重启、跨访问地址不失忆）

> 状态：**已落地**（2026-09-22，客户端一半与宿主一半同一批：门禁 `tests/verify-683-choice-store.js`、`tests/verify-683-mirror-write.js`、`tests/verify-683-choice-rev.js`、`tests/verify-683-host-wiring.js` 全绿；原先的「草案」字样留作追溯——维护者 2026-09-21 拍板「用 F1」，并要求对抗式审查后再落地）
> 起因：维护者真机报告 —— 一些曾经打开过的工作区，每次进去都又出「该工作区还没有设置」，看着像每次重新调查一遍。
> 相关：#155（选择按工作区缓存）、#297（工作区已空时旧绑定视为过期）、#653（工作区键与「旧键不迁移」）、#669 第 6 件（判定顺序：用户的选择 > 锚文件 > 自动识别）、ADR `20260921-tracker-choice-precedence.md`（攻击 1/2/8）、`20260921-setup-layout-ask-and-remember.md`（布局答案）

---

## 1. 问题

「这个工作区用的是哪个后端」今天有两条**会变**的输入：用户在界面上选的那一下（存在浏览器 localStorage，按工作区键），和仓库里那份 `docs/agents/issue-tracker.md`（AI 写的）。用户的选择只存在浏览器里，而 **localStorage 按访问地址（origin）隔离**：

- 换端口（DSH 的本地服务端口变过：`http://127.0.0.1:3080` → `http://127.0.0.1:43120`）、换用「桌面端 / 浏览器」两个壳、换机器，插件就整份失忆；
- 于是那些「没有 `.git`、也没有锚文件」的目录（例如 `D:\3DeepSeekHarness\agents\<某个 agent>` 这类沙箱目录）永远认不出后端，每次进去都出蓝条「该工作区还没有设置」；
- 名单里能自动认出来的目录（有 `.git` 或锚文件）不受影响 —— 这也是为什么只有「一些」工作区有这个毛病。

本票把用户的选择**多存一份在宿主侧**（插件自己的状态文件，按工作区键），让它跨 DSH 重启、跨访问地址、跨桌面端/浏览器都还在。**同时必须解决维护者点出的第二个问题**：两份存储并存时，**旧值不许压新值**、也不许出现「一边更新了、另一边还拿着老状态继续说话」的错乱。

## 2. 两份存储与它们各自的失效模式

| 存储 | 位置 | 谁写 | 什么时候会旧 | 什么时候会没 |
| --- | --- | --- | --- | --- |
| **C**（现有） | 浏览器 localStorage（`dsws.selectionByCwd`、`dsws.setupLayoutByCwd`） | 客户端（用户点确认时） | 另一个 origin 改了 H 之后，这个 origin 的 C 还是老值 | 换 origin / 清缓存 / 换机器 |
| **H**（新增） | 插件状态文件（宿主侧，按工作区键存**散列**） | 宿主（收到用户的那通绑定电话时） | 用户在同一台机器的另一个壳里重新选过（此时该壳的 C 是老的） | 不会自己没；只在淘汰上限时被丢掉 |

两份都会旧，所以**必须有一条可判定的「谁更新」**，否则就是维护者担心的状态错乱。

## 3. 裁决：谁写、谁读、谁赢

- **R1 只有「用户亲手选」与「一次性迁移」两条路写 H**：用户亲手选的那通电话是 `wf.bind(handle, backendId)`（由两个门控窗与面板「切换后端」弹窗调用）；另一条是 R3 的迁移分支（客户端报上来一条**宿主还没有记录**的、带 `userPicked` 的选择时，把它落进 H）。**探测结论（锚文件、matches、兜底）一律不写 H** —— 否则就是 ADR 攻击 1 的翻版：把派生值当意图永久钉住，之后谁改锚文件都不生效。
- **R2 每条记录带修订号**：H 里每条 = `{backendId, rev, pickedAt, source:'user'}`。**`rev` 由宿主发号**（每接受一次用户选择 +1），客户端写 C 时同时记下「这条选择来自哪个 rev」（`baseRev`）。`pickedAt` 只用来给淘汰排序，**不参与胜负判定** —— 用墙上时钟比大小会被时钟跳变（NTP 校时、手动改时间）和同毫秒并列搞坏，而修订号没有这些问题。
  **客户端那一半必须同时落地**：今天四个「用户点确认」的写入点（`store-switch.js` 的切换确认、`StatusBackend.js` 的门控确认、`Dock.js` 的面板门控、`OverlayGate.js` 那个当前没人调的叶）写进 C 的只有 `{backendId, source, ref, userPicked}`，而上报路径（`probe-snapshot.js` / `probe-chain.js`）只带一个 `backendId` 字符串 —— **没有版本位可挂**。所以：四个写入点补 `pickedAt`（`Date.now()`，只作档案）与「这条来自哪个 rev」，上报改成 `{backendId, baseRev}`。**没有版本位的老记录按 rev=0 处理**，它们只在 H 里没有该工作区记录时被采纳一次（迁移），之后一律不许说话 —— 绝不「假定现在」。
- **R3 旧状态不许说话（按修订号判）**：宿主收到 hint 后：
  - H 里没有这条 → 采纳，写进 H（`rev = 1`，见 R1 的第二条写路），把 rev 回给客户端；
  - H 里有、且 `hint.baseRev === H.rev` → 采纳（客户端看到的就是最新那一版）；
  - H 里有、且 `hint.baseRev < H.rev`（或 hint 没带 `baseRev`）→ **不采纳**，按 H 回答，并把 H 的值与 rev 随快照回给客户端，客户端拿它覆盖 C（这就是「localStorage 还是老状态时不许说话」）；
  - **用户当场点确认的那一通 `wf.bind` 永远采纳**（不管 `baseRev`）：那是人刚做的动作，它把 `rev` 推到 `H.rev + 1` 并把新 rev 回给客户端 —— 否则「另一个壳先改过」就会让本壳刚点的这一下不生效，那才是真的错乱。
  - **代价如实写**：装了旧版本（没有 H）时在旧版本里换过后端，再升回来会以 H 为准（那条新选择会被当成「没版本位的老记录」挡掉）；再选一次即可 —— 反过来（采纳无版本位的 hint）就是拿老状态压新状态，正是本票要避免的。
  - **为什么不用「谁的时间戳新听谁的」**：对抗式审查列出三种可达排序 —— 同一毫秒落笔、NTP/手动改时间导致时钟回拨（新选择带的时间戳反而更小）、同一工作区两扇窗同毫秒各选一个 —— 这三种下时间比较都会让面板跟着旧值走。修订号没有这些洞；`pickedAt` 只留给淘汰排序用。
- **R2b 版本位必须活过一次往返**：`keepUserPick` 今天只保住 `userPicked` 标记（`Object.assign({}, incoming, {userPicked:true})`），而宿主的 selection 里没有版本位 —— 第一次快照合并就会把 `rev`（和 `pickedAt`）抹掉，于是第二次请求起上报的都是「没带版本位」，R3 把它当最旧的顶回，这个壳会被永久钉在宿主的答案上。所以：**宿主回包的 selection 里必须带 `rev`/`pickedAt`，`keepUserPick` 在后端相同时把它们一起带走**。这是「时间比较只活过一次请求」那个坑的补法（审查用真源跑过，是能复现的）。
- **R2c 宿主自己的 30 秒缓存不许把「带 hint 的那一次」当成通用答案端出去**：`detect` 命中 per-workspace 缓存（TTL 30 秒）时先于 hint 判读返回，而带 hint 的那一次结果也会进缓存 —— 于是别的壳（没带 hint、没选过）也可能被回一个 hint 派生值，而且另一个壳改了 H 之后这里还能旧 30 秒。所以：缓存条目带上 `fromHint` 与它当时的 `rev`，读的时候「`fromHint` 且 `rev` 与当前 H 不一致 → 丢掉重算」。
- **R4 客户端以宿主回的答复为准，且**每一次**答复都要带权威 selection**：今天 `wf.snapshot`（非 force，空闲面板 99% 走这条）命中内存缓存会直接返回那一份旧快照，304 分支也不装 selection，而 selection 根本不进快照版本号 —— 只换了后端时客户端会收到「没变」，于是面板头/状态栏继续显示旧后端，而链与横幅（走 detect）已经按新值答了，同屏自相矛盾（对抗式审查用源码钉住的事实 ②）。所以：**权威 `{selection, rev}` 必须挂在每一次快照回包上（含内存缓存短路与 304），客户端在 304 分支也要合并它**；这条与 R3 一起决定了「谁的答复算数」。
- **R5（原「锚文件比记忆新时文件赢」——**对抗式审查后撤掉**）**：原打算用 `docs/agents/issue-tracker.md` 的 mtime 判新旧。审查给了两条独立的否掉理由：① `git checkout` / `git pull` 会刷新这个文件的 mtime 而内容还是旧后端 —— 一次 git 操作就能把用户刚做的切换撤销；② **那条路上的 mtime 根本拿不到**：DSH 的文件服务 `stat()` 只回 `{version, type, size}`，mtime 只存在于拼出来的不透明 `version` 串里（`@deepseek-ai/dsh-fs-local` 的 `index.js`），绕过平台层去 `import node:fs` 又会把现有那套「假平台门禁」测穿。所以**不做这条**：维持既有裁决（用户的选择优先），代价如实写明 —— 手改文件不会让面板跟着变，要改就在面板上再选一次（原本就记在 `20260921-tracker-choice-precedence.md` 攻击 8）。
- **R5b 只采纳注册表里认得的后端**：写 H 之前要过 `registry.has(backendId)`（与既有 hint 分支同款守卫）；**`backendId === null` 永不写入**（退役的「无后端」逃生舱不许借这条路复活）。否则一条旧版本/已下线后端留下的选择会被永久写进文件，此后每个壳都被回一个没有模块的后端 id。
- **R5c 文件「坏」与文件「没有」要分开**：文件不存在（`ENOENT`）→ 当空，允许 R3 的迁移写入；文件存在但**解析不了/形状不对** → 当「暂时读不到」：**这一轮不采纳任何 hint、也不写**，只在日志里留一条 warn（否则一个半截文件会把浏览器里那份可能更旧的选择重新灌进来并永久化）。逐条校验形状（`backendId` 字符串、`pickedAt` 有限数、`rev` 整数），坏的条目单独丢掉。
- **R6 布局答案同一套**：H 里另存 `{layout, pickedAt}`（**与后端记录同一种形状**：今天 C 里只存了一个裸字符串，两个壳可以各答一个样而没有仲裁依据）；卡片确认时同时写 H 与 C；读的时候「卡片开着时以卡上刚点的那一下为准（已修）> 会话里答过的 > H > 缺省」。宿主那份也要随快照回包回来（同 R4），否则落后的那扇窗永远停在老答案上（对抗式审查 §9）。
  **卡上确认写的是「卡上当时显示的那一个」**，而且卡上显示的值有来源顺序（草稿 → 会话 → C/H → 兜底）：只要 H/C 里有记住的值，卡就必须显示它，**不许显示兜底值**。审查指出过一个可达的覆盖风险：某个壳还没听到宿主说过记住的布局时卡片会显示兜底 `single`，用户一点确认就把别处记住的 `multi` 覆盖成 `single` —— 所以「先让宿主的布局随快照回填到 C」是这条规则的前置条件（落地时门禁要量：H 有值时卡上显示的就是 H 那个值）。
- **R6b `currentBackendId` 的第三档要写清用途**：它现在在没有会话选择时会回读 C（`prompts.js`）。C 在本次裁决里已降级为「本壳的临时镜像」，所以这一档只允许在「宿主还没回过任何一次」之前生效 —— 落地时在那一行写明这条前提（或直接去掉那一档，由会话状态兜住）。
- **R7 写入必须原子**：临时文件 + `rename`（本仓已有现成写法可抄：`packages/dsh-plugin-update/src/store.ts` 的 `writeJsonAtomic` —— `.<uuid>.tmp` + `wx` 写 + `rename`，配一个 lock 文件与 10MB 上限）；**崩在 mkdir 与 rename 之间必须留下旧文件且可解析**；解析失败（含被截断）当空并记一条 warn、不崩；文件里**只存工作区键的散列**，不落明文路径。
  **放哪儿**：`<用户主目录>/.dsh/mattskillsdeck/choices.json`（插件自己的目录，跟日志包把日志写到 `~/.dsh/logs` 同一个家；**不要**用现在那个 `<进程 cwd>/.dsh-mattskillsdeck-cache` —— 它跟着 DSH 进程的启动目录跑，换个地方启动/换个插件版本路径就换一个文件，而 C 还在，等于「一半的记忆留在原地」）。这条是硬约束：H 的路径**不许**依赖进程 cwd。
  **形态**：`{ version: 1, workspaces: { '<keyHash>': {backendId, rev, pickedAt, source:'user'} }, layouts: { '<keyHash>': {layout, pickedAt} } }`。
  **键由宿主自己算、只认宿主规整形态**：审查实测客户端 `keyOf("D:\\…\\sub")` 得到 `d:/…/sub`，宿主规整后是 `d:\…\sub` —— 字节不同、散列不同。所以散列**只散列宿主规整后的那把键**（`canonicalKey` 的结果），客户端不许参与算键（它只送 cwd）。
- **R7b 客户端写 C 要按「键」读-改-写**：现在 `persistSelectionByCwd` / `persistSetupLayoutByCwd` 是把**进程内存里那份整表**序列化写回（`store-prefs.js`），同一个 origin 开两个窗口时，后写的那扇窗会把另一扇窗新写的键顶掉（对抗式审查 §2）。改成：读回磁盘上的表 → 只替换本工作区那一条 → 写回；并监听 `storage` 事件，别的工作区/窗口改了当前工作区那一条时重新合并。
- **R7c 写失败要看得见**：客户端 `persistSelectionByCwd` / `persistSetupLayoutByCwd` 现在把异常一口吞掉（同文件的 `saveListPrefs` / `saveLabelClicks` 都会记 `storage.fail`）—— 补上同样的日志；宿主的 H 写失败也要如实回给调用方（`wf.bind` 的回包已经有 `labelColorsFile` 这个先例，照它加 `stateWrite:{ok,error}`，面板上有一条 warn 提示）。
- **R7d 工作区根后来才认出来时，要把老键上的记录搬过去**：`rememberWorkspaceRoot` 学会一个根之后，同一个工作区原来按「会话所选目录」存的那条（选择 + 布局）要复制到根键上（对抗式审查 §5：没有这一步，重新出现 `.git` 之后一边说 Markdown、一边说「还没有设置」）。这条顺带也把 #653「旧键不迁移」留下的那批老记录救回来。
- **R8 上限与淘汰**：最多保留 N 条（按 `pickedAt` 淘汰最旧的），文件体积上限；淘汰只影响最旧的那些工作区。
- **R9 并发**：宿主的读-改-写用一个进程内队列串行化，避免两个窗口同时写丢更新。
- **R10 工作区已空**：沿用 #297 —— 工作区里文件全删时，这条记忆视为过期（宿主按「没有选择」回答，**H 的内容不动**）。要注意的是一致性：客户端那条镜像不会因为「宿主这次答了 fallback null」就自动丢掉（`mergeSelection` 的既有规则是「fallback null 尊重意图」），所以已清空的工作区里，状态栏可能继续显示记住的那一个、链上却是空的 —— 这是**已知限制**，本次不改（改它要动 mergeSelection 的裁决，另开票）；门禁要钉住的是「H 不会把一个已被 #297 判空的缓存复活成有的样子」。
- **R11 日志点**：新增事件（H 命中 / 未命中 / 被更旧的 hint 顶回 / 淘汰 / 写失败 / 文件坏），**必须与 `research/489-appendix.md` 第 1 章的对照表和 `tests/verify-log-count.js`（常驻/按需/自监控的条数与编号清单是字面写死的）、`tests/verify-log-fields.js`（逐事件字段白名单）同一个提交里改完** —— 否则门禁当场红（审查提醒过的坑）。
  - 落地时的级别划分（与本条初稿「六个全按需」有一处不同，如实记）：文件坏（`choiceStore.file.bad` #69）与写失败（`choiceStore.write.fail` #70）定成**常驻告警级** —— 这两件就是「这个工作区为什么每次都重新问一遍」的唯一线索，真出问题时用户不会先打开调试开关（客户端镜像写失败的 `storage.fail` 也是同一定性）；另三件（`choiceStore.read` #71 读到没有、`choiceStore.hint.reject` #72 被旧版顶回、`choiceStore.evict` #73 超限淘汰）是高频路径或罕见轨迹，按需。理由与落点见附录第 1 章 #683 那节。

## 4. 不做什么

- 不写用户的仓库（插件从不写 `docs/agents/issue-tracker.md`；那是 AI 的事）。
- 不把「探测结论」存进 H（见 R1）。
- 不做跨机器同步（H 只在本机；换机器仍要重新选一次，如实写进已知限制）。
- 不引入「清除后端选择」这类入口（#669 第 6 件已把那条路退役）。

## 4.1 自审发现（写进草案时自己先攻了一遍）

- **原来打算用时间戳比新旧，改掉了**：两份存储由同一台机器的不同进程/窗口写，时钟跳变（NTP 校时、手动改时间）会让「刚点的这一下」带一个更小的时间戳，于是新选择被旧记录顶回 —— 那正是维护者点名要避免的错乱。改成**宿主发号的修订号**（R2/R3），判定不依赖时钟；时间戳只留着给淘汰排序。
- **「刚点的那一下永远赢」必须写成明文**（R3 最后一条）：否则「另一个壳先改过」会让本壳刚点的动作静默失效。
- **老记录没有 `baseRev`**：按「最旧」处理（R3），所以它们只会在 H 里没有这条时才被采纳（一次性迁移），之后不再说话。

## 5. 接线（落地时照这个改，尽量不加新电话）

- **写**：`wf.bind` 的回包多一个字段 `rev`（现有回包 `{ok, cwd, backendId, labelColorsFile}` 是加字段，不是改形状；调用方只看 `ok`）。宿主在这一通里写 H：`rev = (上一条的 rev || 0) + 1`，同时写 `pickedAt`。
- **上报**：客户端在 `wf.snapshot / wf.refresh / wf.detect / wf.chain` 的入参里，把现在那个 `backendId`（hint）旁边多带一个 `baseRev`（客户端这条选择是从哪个 rev 来的；老记录没有就带 0/不带）。客户端发起「用户确认」时先用自己的旧 rev 当 `baseRev`，拿到 `wf.bind` 的新 rev 之后把 selection 上的 `rev` 也更新 —— 于是 `rev` 随选择对象一起进 C（localStorage 里那条就自带了）。
- **读**：`detectionService.detect` 里多一步读 H。判定顺序变成：
  1. 用户当场那一下（`wf.bind` 刚写的 rev）与「客户端上报且 `baseRev === H.rev` 的 hint」都算「用户的选择」；
  2. H 里那条（没被 R5 降级时）也算「用户的选择」；
  3. 否则锚文件 → matches → 兜底（与今天一致）。
  快照里回来的 selection 带着 `rev`，客户端合并进 C 时自然把它存下（不用额外字段、不用新电话）。
- **布局**：卡片确认时客户端照旧写 C，同时多打一通 `wf.setupLayout`（新电话，唯一新增的一通）把答案写进 H；宿主把记着的布局放进快照（一个字段）回给客户端，客户端拿它回填 C。
- **实现位置**：新文件 `src/host/choiceStore.js`（读、写、原子落盘、上限、散列键），`detectionService` 与 `workspaceCwd.handleBind` 各接一处；客户端只改「带 `baseRev` 上报」与「把回包里的 rev 存下来」两处。

## 6. 迁移

- 老 C 记录里**带 `userPicked` 标记**的（1.7.24 之后选的）：第一次上报时会写进 H，从此跨壳不失忆。
- 更老的记录（没有标记）：不迁移（无法区分它是用户选的还是探测算出来的），用户在那台机器上重新选一次即可；面板里的「还没有设置」蓝条就是那个入口。
- H 里已有的值会随快照回填到 C 里，所以**同一个壳不需要用户再点一次**。

## 7. 落地顺序（对抗式审查给的硬约束）

**①②必须同一次落地，不许分两次发**：
1. 先做**客户端那一半**：选择对象里带 `rev`（`baseRev`）并随 hint 上报；`wf.bind` 回包里的新 rev 落到本地那条上；
2. 同时做**宿主那一半**：写 H、按 `baseRev` 判新旧、并把权威 `{selection, rev}` 挂到**每一次**快照回包（含内存缓存短路与 304）。
   只因：今天缓存里那条记录没有时间/版本、hint 也只有 `backendId` 一个字段 —— 宿主先上线「旧的不采纳」而客户端还没带上 rev，结果是**所有** hint 都被顶回，用户刚点的选择被旧值答复（比不做还糟）；宿主只在自己那一侧兜底（比如「没带 rev 就采纳」）又会把老状态重新放进来。两半必须一起上。
3. 布局那半（`wf.setupLayout` + 快照回填）可以第二批。

## 8. 门禁（落地时逐条补，含反证）

1. **R1**：只有 `wf.bind` 与 R3 的迁移分支会写 H（静态断言 + 行为：只走一遍探测，不许产生任何 H 记录）；反证：把写入点挪到探测路径 → 「锚文件赢了也不生效」那条用例必须红。
1b. **R2b**：第一次快照合并之后 `rev`/`pickedAt` 仍在（用真 `keepUserPick` + 真 `mergeSelection` 量）；反证：把 `keepUserPick` 里那一行去掉 → 该用例必须红。
1c. **R2c**：带 hint 的探测结果进了 per-workspace 缓存之后，另一个「没带 hint」的调用不许拿到它（同一 H 版本时才可复用）；反证：把 `fromHint` 判断去掉 → 该用例必须红。
1d. **R5b/R5c**：注册表不认的后端与 `null` 不许进 H；文件存在但解析不了时这一轮既不写也不采纳 hint（日志有 warn）；文件不存在时允许迁移写入。
2. **R3 四档**：H 空 → 采纳并写 H；`baseRev === rev` → 采纳；`baseRev < rev`（含没带 `baseRev`）→ **被 H 顶回**且把 H 的值与 rev 回给客户端；`wf.bind`（用户当场点）→ 永远赢。反证：把比较写反/把 rev 比较换成「没带就采纳」，对应断言必须红。
3. **R4 每一条回包都带权威值**：`wf.snapshot` 的内存缓存短路、磁盘缓存回放、`304` 三条路径都要带 `{selection, rev}`，且客户端在 `304` 分支要合并（今天 `probe-snapshot.js` 在 304 直接 emit、不装 selection）。门禁用「只换后端、内容不变」的现场量：旧壳刷新之后必须变成新后端。反证：把 304 分支的合并去掉 → 该用例必须红。
4. **R7/R8**：文件损坏 / 被截断 → 当空且不崩、记一条 warn；超过上限 → 淘汰最旧、其余照常命中；崩在 mkdir 与 rename 之间 → 旧文件仍在且可解析。
5. **R7b**：同一 origin 两个窗口：后写的整表快照不许顶掉另一扇窗刚写的新键（按工作区键读-改-写）。反证：把实现换回「整表覆盖」 → 该用例必须红。
6. **R7d**：工作区根后来才认出来时，老键上的选择/布局要出现在根键上。
7. **R10**：工作区清空后宿主不再按 H 回答（`#297`），且这条不对「另一扇窗继续显示记住的值」负责（写成已知限制）。
8. **R7c**：H 写失败要在 `wf.bind` 回包里如实出现、客户端 C 写失败要记 `storage.fail`（两条都要有「注入了失败之后看得见」的断言）。
9. **降级回归**：装着旧版本换过后端再升回来 → 以 H 为准（不许被无版本位的老记录顶回），并把这条写进已知限制。

## 9. 已知限制（如实写，验收时对照）

- 换机器要重新选一次（H 在本机、在本用户主目录下）。
- **手改 `docs/agents/issue-tracker.md` 不会让面板跟着变**（R5 已撤：mtime 会被 `git checkout` / `git pull` 刷新而内容还是旧的，拿它判新旧会误撤销用户的切换）——要改就在面板上再选一次。这条与 `20260921-tracker-choice-precedence.md` 攻击 8 是同一条代价，本次不改。
- **另一个壳要等它自己下一次刷新才跟上**（没有推送通道）：同一工作区在两扇窗里同时开着时，落后的那扇窗在刷新前显示的可能还是旧后端。
- **装过旧版本（没有 H）期间换过的后端，升级回来会以 H 为准**（无版本位的老记录不许顶掉 H）；再选一次即可。
- **已清空的工作区**（`#297`）：宿主按「没有选择」回答，但本壳状态栏可能还显示记住的那一个（`mergeSelection` 的既有规则是「fallback null 尊重意图」）——已知限制，本次不改。
- 淘汰上限之外的老工作区会重新问一次。
