# ADR 20261014 · 房间的边界收成四个名字：契约 / 共享内核 / 房间 / 装配点

> 日期：2026-10-14 定版。维护者在 `/research` 的四路对抗式审查之后拍板「按照推荐的来」，本文按那一刻的决定写。
> 地位：本文是「内置后端房间可以依赖什么、这份依赖清单谁说了算、谁来检查」的唯一依据。凡与本文冲突的旧说法（`.dependency-cruiser.cjs:31-42` 与 `src/tracker/rooms/README.md` 房间纪律一节里那两份手抄白名单）以本文为准。
> 关联：#1136（落地票：规则起点与登记表）· #1019（房间目录归位，本次问题的起点）· #1017（房间纪律的判据换成依赖图）· #1014 Q2（deck 只许连契约层）· #1064（房间 `.js`→`.ts` 迁移）· #1152 / #1153 / #1154（同批划出的三件）· #1159（共享内核归口）· #1161（装配点与反方向规则）· ADR 20260913-builtin-ts-shape（分层与共享层形状）· ADR 20261011-deck-ts-rewrite（命名规矩）

## 1. 背景：同一个决定写在三处，已经漂了

房间纪律的判据在 #1017 从「扫文本的老门禁」换成依赖图之后，规则的**起点**没有跟着房间搬家一起改：

- `.dependency-cruiser.cjs:96` 的 `from.path` 还是 `^src/host/tracker/backends/(github|gitlab|markdown)/`，`:109` 还是 `^src/host/tracker/backends/`；`:100` 与 `:68-69` 的 `pathNot` 同样是旧路径。房间今天在 `src/tracker/rooms/<名字>/`，所以这两条规则**一条边也咬不到**。
- 守这份规则的 `tests/verify-dependency-rules.ts` 只核对规则名与严重级别（`EXPECTED_RULES`，`:58-69`），不判「起点有没有命中任何东西」。规则名字还在、`severity: 'error'` 还在，门禁就判绿。
- 实测（#1136 的诊断与第四路复核）：在房间文件里注入一条真的跨房引用，门禁仍然退出码 0；把白名单放宽成 `^src/tracker/`、`^src/host/` 两行，注入的真违规同样被吃掉、门禁仍然退出码 0。**绿灯的样子没变，它守的东西没了。**
- 白名单本身有**两份手抄**：`.dependency-cruiser.cjs:34-42` 七条、`src/tracker/rooms/README.md` 九项。两处今天已经漂了（配置里有两条指向已不存在的文件，README 有独有的一条）。配置 `:95` 与 `:132-133` 甚至写明「加一条要同时改本文件与那份 README」——把「同改两处」当规矩，就等于承认它会漂。仓里早有反例：`tests/verify-prompts.js:41` 对同类问题立过「门禁只读登记文件，代码里不留第二份」。

一句话：**病不在某个正则写错了，而在这份清单没有单一真源、也没有任何一条判据证明它还活着。**

## 2. 裁决

**决定一 · 起点判据不写房名。**
两条房间规则的 `from.path` 改成 `^src/tracker/rooms/([^/]+)/`，同房间放行仍用捕获组 `$1`（`:100` 现在就是靠 `$1` 一句顶三条规则）。房间名字是**数据**，判据自己把它推出来——将来加第四间房，配置不用动。

**决定二 · 房间的合法房外依赖收敛成四个名字。**

```
src/tracker/
├── contract/        契约层：纯类型 + 纯数据 + 名录。房间与 deck 唯一可深引的公共面
├── kernel/          共享内核：与具体后端无关、房间与宿主都要用的判定件
├── rooms/<名字>/    三间房：只许引 contract/ + kernel/ + 已登记的 shared 模块 + 自己 + Node 内置
└── registry/        注册表机制；builtins.ts 是「有哪几个内置房间」的唯一装配点
```

`contract/` 与 `kernel/` 的分界不是新造的，是仓里已经写下的那条：**契约层只有类型与数据、没有运行时实现**（`.dependency-cruiser.cjs:173-175`、`:186-188`）。`error-rules.ts` 这类带规则表的运行时实现因此进不了契约层——它今天没有名分，只能靠白名单逐文件点名。给它一个有名有界的家，清单才能从「逐文件」降到「逐目录」。

**决定三 · 白名单只有一份，形态是声明式登记表。**
写在 `.dependency-cruiser.cjs` 里，引擎与门禁读**同一份**（门禁今天已经用 `createRequire` 读这份配置，见 `tests/verify-dependency-rules.ts:360-369`，零新机制）：

```js
const ROOM_IMPORTS = {
  protected: '^src/tracker/rooms/',        // 这条规则守的是什么
  entries: [                                // 允许的例外，每条有名有据
    { pattern: '^src/tracker/contract/', why: '契约层：三房唯一公共面', ticket: 1014 },
    // …
  ],
  maxEntries: 12,                           // 只许减，照 same-layer-baseline 的「只许减不许增」
}
```

`src/tracker/rooms/README.md` 的纪律一节改成**指路**（指向本文与配置），不再抄第二份。

**决定四 · 登记表靠五条判据自证，不靠人记得。**

1. **活着**：每条 `pattern` 必须在磁盘上匹配到至少一个受管源码文件。仓里的反例就在旁边——`tests/same-layer-baseline.json` 没有这条，搬家后留下 179 条永不匹配的幽灵条目（#1154）。
2. **有名有据**：`why` 非空、`ticket` 是正整数、`pattern` 互不重复（照 `tests/prompt-gate-exempt.json` 每条必须写 reason 的先例）。
3. **不吃自己**：`entries` 与 `protected` 的交集必须为空。这一条直接杀死上面那次绕过——**白名单不许匹配它所在规则要守的那类路径**；纯正则乘文件清单，不需要注入。
4. **不被吸收**：一条登记项不得覆盖另一条的全部见证文件。一般正则的包含关系不可判定，所以用**见证文件近似**（每条自带一条真实样本路径），承诺抓住「随手抄宽」这个真实故障模式。
5. **报分母**：每条规则的图上命中数、房间进图数对磁盘数（今天门禁末行那句写死的绿灯文案换成带分母的）。

**正控与负控从常驻判据降级为样本门禁**（`tests/verify-<主体>-samples.*` 是仓里既有范式，如 #1111 那批四份门禁）：注入样本是验收手段，不是常驻判据——常驻判据必须不需要注入就能判。`maxEntries` 只许减，共享内核归口（#1159）完成后必须跟着减，否则这份登记表会变成新的永久豁免。

**决定五 · 房间实现只许被装配点引用。**
`.dependency-cruiser.cjs:147-152` 那条反方向规则当时故意没上，注释里写着启用条件是「契约层公开入口立起来」。条件今天成立，但 5 个宿主文件、7 处仍在直接连房间实现。因此先立装配点 `src/tracker/registry/builtins.ts`（用动态 `import()` 保住今天的加载时机），再上规则 `rooms-imported-only-by-assembly`。见 #1161。

## 3. 被否掉的路

| 方案 | 为什么不选 |
| --- | --- |
| 只把起点路径改对，别的不动 | 实测会当场出 62 条（四个扫描根）到 176 条（当前 `origin/main`）真违规，规则从假绿变常红；若为了让门禁绿而顺手放宽白名单，就换成了更大的假绿——第四路实测两行 `^src/tracker/`、`^src/host/` 即可让注入的真违规消失 |
| 白名单继续双写（配置 + 房间 README） | 双源已知会漂，今天就在漂；同改两处是这次事故的机制本身 |
| 把 `error-rules.ts` / `preflight.ts` 搬进契约层 | 契约层的定义是「纯类型与数据、没有运行时实现」，搬进去等于改定义，还会让 deck 侧顺带拿到运行时依赖 |
| 登记表放 `tests/` 下的 JSON | 引擎配置要多依赖一份测试资产，方向反了（配置 → 测试资产）；写在配置里是单源、零新增文件 |
| 给 dependency-cruiser 加第 11 条「规则不许空转」的配置规则 | 引擎没有「规则零命中」的信号（`ruleSetUsed` 只是把输入原样回抄），判不了；这条判据只能写在门禁里 |
| 用 project references / 包边界做物理隔离 | 今天单 tsconfig 加 esbuild 转译，代价远大于收益；本仓的分层靠依赖图判据守，够用 |
| 让 deck 直接引共享内核 | `deck-deep-import` 的 `to` 只放契约层；`kernel/` 一建，那条 `to` 必须加上它，否则新目录变成绕开「只许连契约」的后门 |

## 4. 代价与已知限制

- **本票不搬代码**：`kernel/` 是目录归口，要动三间房的 import，而房间正在 #1064 手里迁移——同一批文件不能有两个写者。搬家归 #1159。
- **白名单不会消失**：房间确实需要共享件，目标不是零条目，而是每条有名有据、机器可查、只许减。
- **判据 4 是近似的**：只承诺抓住「随手抄宽」，不承诺判定一般正则的包含关系。
- **反方向规则要先有装配点**：装配点上线前，那 7 处宿主 import 仍是合法行为。
- **未构建检出会多报构建产物假红**：`../../contract/vocabulary.js` 这类相对路径在源码树里解析不到 `.ts`，图上按「解析失败」计数。所以验收必须在跑过 `node scripts/build.mjs` 的检出上做，且登记表按**目录前缀**写（写成 `\.ts$` 会漏掉已构建检出上的产物路径）。这一支属 #1124。
