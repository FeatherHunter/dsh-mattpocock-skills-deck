# ADR 20260921 · 后端选择的优先级：用户的手动选择 > 锚文件 > 自动识别

> 状态：已定稿（维护者 2026-09-21 拍板，逐题问答见 #669 与本次对话）
> 相关：#669 第 6 件、#655（域文档布局）、#665（新工作区引导链）、#664（切换不注入长文）、#297（空工作区失效规则）
> 本文件同时是**对抗式审查记录**：第 4 节是自己攻自己，攻击不成立的要写清为什么不成立，成立的必须落到第 5 节的改法里。

## 1. 现象（用户真机报的）

面板里把后端从 GitHub 切到 Markdown：提示条说「已切换到 Markdown（旧数据已保留）」，弹窗关了，**仓库标却仍是 GitHub**；再开一次弹窗，面板认为的「当前后端」还是 GitHub。

已查明（见 `#669` 的两条评论）：绑定成功（`wf.bind` 没有报错、日志里没有失败行），但**面板与引导链的取数不看用户那一下** —— 它们先问锚文件 `docs/agents/issue-tracker.md`，那份文件写着 `# Issue tracker: GitHub`，于是快照又回 GitHub，客户端再把「真相」合并回来，把用户的选择盖掉并写进本地缓存。

## 2. 第一性原理：同一个问题有三个来源

「这个工作区用哪个后端」这个问题，今天有三个来源在回答：

| 来源 | 它是什么 | 谁写它 | 时效 | 会不会说谎 |
| --- | --- | --- | --- | --- |
| **锚文件** `docs/agents/issue-tracker.md` | **声明**：「我宣布这里是 GitHub」 | 初始化那一步的 AI（插件自己从不写 —— Q4 既有决定） | 一直有效，直到被改 | 会：过去写的、切换后没同步、或写错 |
| **用户的手动选择** | **意图**：我现在要用哪个 | 用户在面板上点的那一下（`wf.bind` + 按工作区的持久缓存） | 一直有效，直到用户再改 | 不会 |
| **自动识别（matches）** | **现场事实**：`.git/config` 里有没有 `github.com` / 目录里有没有 `.scratch/map.md` 等 | 没有谁写，是读出来的 | 随现场变化 | 不会，但证据薄（只能看眼前这点） |

三条各自的**话语权**应当按「离人的意图有多近」排：**人的意图 > 人写下过的声明 > 机器推断**。

## 3. 裁决（本次定稿）

1. **判定顺序**：`用户的手动选择` → `锚文件` → `自动识别`（`registry.select` 内的 matches 与兜底照旧在最后）。
2. **「用户的手动选择」只指「切到某个后端」**这一个动作（门控窗选后端、切换弹窗确认切换）。「清除后端选择」（显式无后端）这颗按钮**删掉**：它表达的是「我不选」，与本次裁决要建立的「一次只答一件事」不符，且它混在「选后端」那张卡上难以理解。
3. 锚文件**仍然压过自动识别**（这条不动）。#669 之前的两处真源统一（快照与链同源判定）依然成立。
4. 切换之后的**后续动作按场景分**（见第 5 节）：
   - 还没初始化 → 与黄条那条路**完全一致**（先问域文档布局，选完注入初始化全文；仓库没就绪就不注入）；
   - 已经初始化 → 注入一条新的「切换后对齐」prompt（点名 `/setup-matt-pocock-skills`），让 AI 把仓库里记录后端的那几处对齐到新后端。
   > **2026-09-22 按 #698 改口径**：上面两条「先问域文档布局」原先只有「还没初始化」那一档写了，「已经初始化」那一档没有这一问，而第 3.4 条与本文件后文都写着「与黄条完全一致」—— 代码照的是没写的那一版，真机上点「确认切换」等不到卡（维护者 2026-09-22 报的）。现在**两档都先问**（维护者拍板：与黄条同一套风格，每次都问）；「已经初始化」那一档答完之后，除原来的「切换后对齐」之外，若用户在卡上真的改了布局，**再多注入一条**把 `docs/agents/domain.md` 与 `AGENTS.md` 里记布局的那两行对齐过去的指令（新模板 `switchLayout`，两个模板都不重跑初始化）。卡上点「取消」时，「切换后对齐」照旧注入 —— 取消的是「改布局」那一问，不是「换了后端要把记录对齐」这件事。
5. 插件**自己不写用户的仓库文件**（Q4：唯一显式写路径仍是 `wf.bind`）。「把文件对齐」这件事交给 AI —— 它本来就是初始化那只手。

## 4. 对抗式审查（自己攻自己）

### 攻击 1（成立，必须改）：客户端缓存里的「选择」不一定是用户选的

派生的选择也会被写进客户端缓存：快照回来带 `selection`，客户端 `mergeSelection` 会把它写进 `selectionByCwd`，而**锚文件算出来的选择也长这样**（`source: 'explicit'`）。于是「把缓存里的选择抬到锚前面」等于让**锚文件的历史结论**反过来压住锚文件：一旦缓存里存过一次 `markdown`，之后谁把锚文件改成 GitLab 都不会再生效 —— 比修之前更糟。

**处理**：选择必须**可辨识来源**。用户点出来的选择带一个 `userPicked` 标记（随缓存持久化、随快照/链请求上报）；只有带这个标记的选择才压过锚文件。派生出来的选择（快照/链/自动识别）不带标记，照旧排在锚后面。见第 5 节第 1 条。

### 攻击 2（成立，写进已知限制）：换了机器 / 清了浏览器缓存，锚文件会重新说话

用户选择存在**按工作区的浏览器本地缓存**里；换台机器或清缓存之后，锚文件就赢了 —— 因为那时唯一的「意图」证据已经没了（宿主里那份绑定是进程内的，重启即失）。

**处理**：不额外造持久层（那要动用户仓库或插件自己的存储，代价与风险都不值）。这正是「切换后要让 AI 去改锚文件」的理由：**真正持久的真相是文件**，注入的 prompt 负责把它改成新后端。在没跑那次 AI 之前，别处（另一台机器、别的工具、AI 自己读文件）看到的仍是旧后端 —— 这一点如实写进文档与验收说明。

### 攻击 3（成立，写进验收）：文件没对齐之前，AI 面向的真相是旧的

`docs/agents/issue-tracker.md` 是给**所有**读它的人看的：技能流程、AI、以及本插件的锚判定。切换之后文件没改，AI 仍会按 GitHub 干活。

**处理**：注入的 prompt 必须**先改文件、再自证**（回读那一行并抄给用户）。验收清单里加一条「切完看一眼输入框里那段话，确认它要求改文件」。

### 攻击 4（不成立）：会不会让「没有选择」的工作区行为变差？

不会。`hintBackendId` 只在客户端**确实有选择**时才上报；没有选择时判定链与今天一字不差（锚 → matches → 兜底）。#297 那条「空工作区里旧绑定失效」的规则也不受影响：它管的是「记忆里的选择」，而带 `userPicked` 的当场选择本来就该被采纳（#665 已把这条边界钉住）。

### 攻击 5（不成立，但要在门禁里守住）：会不会让快照与链再次不一致？

不会。两条路都走同一个 `detectionService.detect`，本次只改它的内部顺序，没有第二条真源。#669 第 1、2 件把它统一过，门禁要加一条「两条路给的后端必须一致」。

### 攻击 6（成立，按用户裁决处理）：切到 GitLab / 迁移 / 清空的「按了没实现」

GitLab 后端今天能力不全；「迁移」「清空」两个选项今天**只有文案与门槛、没有实现**（全仓无实现代码）。留着能按的按钮，等于在刚修好的路上再放一个同类陷阱。

**处理**：三处**置灰不可点**（GitLab、「迁移」、「清空」），鼠标悬停给一句原因；「清除后端选择」直接删掉。

### 攻击 7（不成立，但要写清理由）：弹窗上那句「切换中…」几乎看不见

用户真机报的第一句是「没有显示切换中，弹窗消失」。查下来：弹窗上确实有「切换中…」这个状态（`switch.confirming`），点确认后立刻置位并重画；但 `wf.bind` 是宿主进程内的一次调用，几十毫秒就回来了，紧接着就把弹窗关掉 —— 这一句**本来就不可能被看清**。

**处理**：不为了让人看清而故意拖慢（人为加延迟等于让每个人多等）。真正该保证的是「切换这件事有没有发生」在被看见的地方说清楚：点确认的那一瞬间顶部那颗后端标**立刻变成新后端**（乐观写入 `st.selection` + `emit`），失败时回退并在底部报出失败原因 —— 这两条今天都在（`store-switch.js` 的 `doFail`）。弹窗上那句一闪而过的话保留原样，不当成反馈。

### 附：同一件事有两个入口，本次只改其中一个

- **右侧面板「切换后端」弹窗**（`SwitchConfirmModal` + `store-switch.js`）—— 本次改的就是它：按场景注入 / 开卡。
- **蓝条那颗「选择后端」门控窗**（`StatusBackend.js` 的 `openStatusGate` / `confirmStatusGate`）—— 它只在「这个工作区还没有选过后端」时出现（引导链上 `backendSelected` 那一步没过的状态），也就是还没有可对齐的初始化成果；它照 #663 的定版**只定后端、不注入任何文字**，本次不动，只跟着写 `userPicked` 标记。所以「切换之后要不要注入」这条规则只挂在面板弹窗那一条路上，不会从门控窗漏出去。

### 攻击 8（成立，已知限制）：用户挑过一次之后，锚文件在这台机器上再也说不赢它

只要那把「用户亲手选的」钥匙还在，客户端每一次请求都会带上它，宿主按本 ADR 的顺序采纳，于是**用户手改锚文件、或别的 AI 把文件对齐到另一个后端，都不会让面板跟着变** —— 必须用户再切一次后端，或清掉这台的浏览器缓存（钥匙的唯一凭据）。这不是实现漏洞，是「人的意图 > 人写下过的声明」这条裁决的直接代价（意图没有到期时间）。

**处理**：如实写进验收说明与本节；不额外造机制（要让「锚文件被改过」反过来作废意图，就得给意图加时间戳并与文件修改时间比大小，等于把「谁改文件谁说了算」偷偷请回来）。三条出路：再切一次后端 / 清这台浏览器的缓存 / 删掉那条按工作区存的选择记录。

### 攻击 9（成立，且**就是真机上那次回退的直接原因**）：水合会把刚点的那一下抹掉

`loadSnapshot` 的第一句是 `hydrateFromCache(st)`，它会把**内存里那份旧快照**（还写着切换前的后端）的 selection 合并进会话；那一刻 `st.selection` 正是用户刚点的新后端，合并规则按「真相 > 意图」把旧后端盖回去、并把不带标记的那一条写进本地缓存 —— 钥匙在 hint 发出去**之前**就没了，于是宿主只看到「没有用户选择」，锚文件说话，仓库标回退。首轮实现漏了这条：hint、优先级、注入分流都做了，但水合这一步把输入吃掉了。

**处理**：水合这一步不合并「已有用户标记的那条选择」（见 `store-snapshot.js` 的 `hydrateFromCache`），宿主这次的真回包仍走同一套 `mergeSelection`，照旧能纠正用户的选择；门禁里加了这一组的正反证（`tests/verify-669-choice-precedence.js` B2 组）。

### 攻击 10（成立，按「不许猜」整改）：链快照还没到时把它当成「没初始化」

链里根本没有 `tracker:initialized` 这一步（面板刚开、链还没取回来，或取链失败）时，`guideStepDone` 一律返回「没过」，于是落到「还没初始化」那一支：对 Markdown 目标会直接把初始化全文注进一个**已经初始化过**的仓库 —— 正是本票要结束的那件事（让 AI 重跑 setup）。原来写的是「宁可再问一次」，但这一档的代价不对称：多问一次代价是重跑初始化。

**处理**：把判据从「猜」改成「拿证据」——链里已经有这一步就当场决定；没有就先强制重取一次链（这一取本来也要发生），回来再决定；取回来仍然没有这一步就**一个字都不注入**，只在提示条上把下一步指向状态栏。门禁 C 组加了这一档与它的反证。

## 5. 落地清单（每条都要有门禁，门禁都要带反证）

1. **宿主判定链**（`src/host/tracker/detection/detectionService.js`）：锚文件照旧读（结果里的 `explicit` 一栏不变），但当请求带**用户标记**的选择时，那个选择胜出；否则锚 → matches → 兜底。
2. **用户标记的来源**（`src/client/kernel/store-prefs.js` + `store-switch.js` + `StoreBackend` 的门控确认 + `Dock.js` 门控 + `OverlayGate.js` 那个当前没人调的叶）：每一个「用户点确认选了某个后端」的地方写选择时都带 `userPicked: true`；快照/链合并写缓存时不带。
3. **上报**：快照与链请求把「带标记的选择」当 hint 上报（今天的 `backendId` 参数不变，另加一个布尔位，缺省 false = 今天的旧行为）。门禁里有一条**全仓扫描**：客户端里每一处带 `backendId` 的 `wf.detect` / `wf.chain` 都必须过那道闸（首轮只改了 7 处，漏了链渲染器与无仓卡两处，是对抗式审查抓到的）。
4. **弹窗与门控窗**（`src/client/views/shared/SwitchConfirmModal.js` + `Dock.js` + `StatusBar.js` + `StatusBackend.js`）：删「清除后端选择」；「迁移」「清空」置灰 + 卡片正文写明今天没实现；GitLab 在**三个**选后端的窗里都置灰不可选（判据只有 `isBackendUnavailable` 一份），确认那一步再挡一道；门控窗的提示条改说「接下来按提示完成初始化」（那个窗只在还没有后端时开，谈不上「旧数据已保留」）。
5. **切换之后**（`src/client/kernel/store-switch.js`）：
   - 判据先要求**证据**：链里得有 `tracker:initialized` 这一步；没有就先强制重取一次链再判，取回来仍然没有就一个字都不注入（见第 4 节攻击 10）。
   - 未初始化（链上 `tracker:initialized` 未过）→ 交给**注入决策器那一个函数**（它自己判「仓库那一步过没过」：没过就返回 `blocked`，一个字不注入也不开卡；没过之前不弹卡）—— 与黄条那颗按钮走的是同一个函数、同一份判据，`store-switch.js` 里不抄第二份；决策器说开了卡就等用户选完布局再注入**与黄条同一条**初始化全文。
   - 已初始化 → **也先开那张布局卡**（#698 改的口径，见第 3.4 条那一段）→ 用户答完卡（确认或取消）之后，由 `StatusBackend.js` 的 `settleSwitchCard` **重新判一次**「这个工作区现在初始化了没有」再决定注什么：仍然已初始化 → 注入新模板 `switchAlign`（对齐 `docs/agents/issue-tracker.md` + `docs/agents/domain.md` + `AGENTS.md` 的 `## Agent skills` 块，并回读自证），用户在卡上真的改了布局时**再多注入**一条 `switchLayout`；点确认那一刻已经变成「还没初始化」（AI 刚把仓库初始化完了）→ 交回决策器，一个字都不自己发。
   - 提示条三句：开了卡「已切换到 {后端}，请先回答下面那一问（域文档布局）」／未初始化「已切换到 {后端}，接下来按提示完成初始化」（决策器说 `blocked`、或链里拿不到那一步时换成「先按状态栏那条提示处理」）／已初始化且卡没开成「已切换到 {后端}（旧数据已保留）」。
   - 「同一时刻只许一张卡」：`openSwitchConfirm` 在布局卡还开着时直接挡下（提示一句、返回 `false`），两张要用户回答的小窗不叠在同一屏上。
6. **标记怎么留住**（`src/client/kernel/store-prefs.js` 的 `keepUserPick`）：快照合并时，宿主回的是同一个后端就把 `userPicked` 留着（否则刷新一次这个事实就丢了，锚文件会重新说话）；宿主回了别的后端（它不认这个 id、没采纳这条 hint）就照宿主的来，标记消失。**水合（`hydrateFromCache`）这一步不合并带标记的选择** —— 那份缓存写的是切换前的结论，合并它等于把刚点的那一下抹掉（第 4 节攻击 9，真机上那次回退的直接原因）。
7. **日志点**（`research/489-appendix.md` 第 1 章那条按需的记录）：不新增事件，只把已有的 `inject.decision` 扩一个取值 —— 已初始化那一档注入 `switchAlign` 时记一条（`prompt: 'switchAlign'` / `kind: 'align'` / `layout: 'unset'`）；未初始化那一档本来就经过决策器、它自己会记。真机出现「切完什么指令都没给」时，这是唯一能回看的轨迹。
   > **2026-09-22 按 #698 补**：切换这条路从这一票起会分成「先开卡问布局 / 直接对齐后端 / 多给一条布局对齐 / 什么都没给」四种，而原来那一行看不出「在等你答卡」与「卡根本没渲染出来」的区别。新增一条按需轨迹 `logSwitchSettle`（沿用同一个事件名 `inject.decision`，落点在 `src/client/kernel/prompts-setup.js`：`prompt: 'switchSettle'`，`kind` 取 `align` / `align-layout`，`layout` 记这次是哪种结论；外层先判调试开关）。**级别仍按需**，等维护者拍板要不要转常驻（见 #698 票面那道待答问题）。
8. **门禁**（`tests/verify-669-choice-precedence.js`，进 `npm run verify` 链）：甲两组（带标记的选择压过锚；不带标记时锚照旧说话）、两条路一致、场景分流四组（已初始化注入对齐指令／未初始化且就绪走决策器／未初始化且没就绪时提示条不许说「按提示完成初始化」）、弹窗三处；每条都配「把实现做坏就必须变红」的反证。`not-ready` 那一档的判据取的是 `prompts.js` 里 `setupBlockedByGuide` 的**真身**，不是另写一份。
