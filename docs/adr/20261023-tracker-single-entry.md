# ADR 20261023 · 后端操作只有一个入口：Tracker 会话，预算模型由后端自己声明，闸与账本在操作管线里

> 日期：2026-10-23 定版。规格 #1439 的实施决定，由实现 #1441–#1448 逐张落地。
> 地位：本文是「谁来调用后端、额度口径从哪来、准入与记账发生在哪」这三件事的唯一依据。凡与本文冲突的旧说法（旧的两桶账本入口、按后端编号写死的额度表、调用方自己过闸的写法）以本文为准，旧位置按本规格的边界改。
> 关联：规格 #1439 · 问题报告 #1435 · 实施 #1441（新脊柱）· #1442（deck 工具改走会话）· #1443（GitHub 读数归位）· #1444（刷新读路径）· #1445（刷新写路径与宿主发布）· #1446（账本换轨）· #1447（GitLab 端到端）· #1448（文档与收口）· ADR 20260924-refresh-budget-architecture（被本文接替的那份额度架构）· ADR 20261014-tracker-room-boundary（房间边界）

## 1. 背景：一个「没有 gh 的本地工作区，九个工具全被推迟」的事故

2026-10-23 的报告（#1435）：插件 1.9.0-beta.5，工作区用本地 Markdown 后端，机器上没装 gh。打开工作区后，九个 deck 工具全部返回 reason 为 gate-defer 的失败，文案是「读的额度已用完，只剩给写留的保底：读让路，写保住」。面板正常，重启不恢复；装上 gh 并登录之后，没有改一行代码，立刻恢复。

根因不是某一条 if 写错，而是三个结构选择叠在一起：

1. 选后端的探针在认出后端之前，先按 GitHub 的 REST 桶过闸。后端都还没认出来，就已经拿 GitHub 的额度口径做了决定。
2. 账本没有读数时，把「不知道」算成 0；写保底也是 0，于是「剩余 0 小于等于保底 0」命中，读操作被推迟。**未知被当成了耗尽。**
3. 每个调用方自己决定要不要过闸、自己挑后端、自己拿 backendId 写分支。规则分散在几十处调用点，任何一处漏写就会换一种坏法。

## 2. 裁决

**决定一 · 后端操作只有一条入口：Tracker 会话。**

- 会话由 `openTracker(仓库句柄, 选项)` 一次建立、一次只绑定一个后端；返回值只可能是两种：`{ ok: true, session }` 或 `{ ok: false, reason, detail }`，reason 是四种可区分的情况之一：没有可用后端（no-backend）、同时命中多个（multi-match）、选择还没做完（pending）、工作区还没就绪（workspace-not-ready）。**这个函数永远不抛异常**，失败如实回值。
- 会话上挂着全部 26 条能力：23 条操作（其中 24 条异步调用统一走操作管线，`readBudget` 直达不裁决不记账）与 `describe`、`issueAddress` 两条同步直通。
- 调用方（deck 工具、刷新读路径、刷新写路径、宿主发布、面板）不再自己选后端、不再自己过闸、不再拿 backendId 写准入分支、不再直接 import 房间实现。选后端发生在会话内部，**选后端本身不消耗额度**——这是事故 1 的直接修复。

**决定二 · 预算模型由后端自己声明，缺声明就注册不进来。**

- 每个后端模块必交五件套（描述、能力清单、操作表、装配、预算声明），其中预算声明 `budget` 是必填项。缺了它，注册表在注册时当场拒绝，并在错误信息里点名缺的是哪一格。
- 预算声明的形状是 `{ kind, countsRequests, countsPoints, independentBuckets }`，kind 四选一：两桶（two-buckets）、只计请求数（requests-only）、离网（off-network）、未知（unknown）。三个内置后端已各自声明：GitHub 两桶、GitLab 只计请求数、本地 Markdown 离网。
- 新增第 26 条能力 `readBudget`，三种读数：读到了（`known: true`，带该模型的量）、没测到（`known: false, reason: 'not-measured'`）、这后端不支持（`known: false, reason: 'unsupported'`）。读数只被查询、不被裁决也不记账；读不到时绝不拿 0 冒充。
- 算式只读声明、不读后端编号：35% 保底与两桶档位只对声明为两桶的后端成立；只计请求数的后端只看请求条数；离网后端不建额度桶、不记账；未知模型只记发出去几条请求，不编造点数额度与剩余量。

**决定三 · 闸与账本都是操作管线里的拦截器，只有一处。**

- 管线顺序固定：取读数 → 准入裁决（admit）→ 转发给后端 → 记账（account）。准入与记账各只有一份实现，由会话装配时注入；调用方看不到，也绕不过。
- 三件事必须分开说，不再互相冒充：**未知**（读不到，放行但如实标注）、**离网**（这个后端不需要额度，放行、不记账）、**耗尽**（有真实读数且余量不足，按规则推迟）。硬顶（单次调用上限）在任何情况下都有效。
- 账本以「后端 + 桶」为键（github/rest、github/graphql、gitlab/requests；Markdown 无桶；未知模型只记请求数）。同一份额度跨来源共享时不拆账；额度同步只更新当前后端的条目。
- 回执与面板按模型显示：每次操作回执带 backendId、预算模型种类、读数是否已知、是否离网；`remaining` 与 `tier` 只在有真实读数时出现，未知与离网给原因短名与一句人话，**不出现假 0、不出现红色档位**。

## 3. 影响与迁移

- **对第三方后端是破坏性变更**：模块必须补 `budget` 声明才能注册；能力总数从 25 条变 26 条。发布说明里要写明这一条。
- 旧的两桶账本入口删除，避免两套键并存；旧的按后端编号写死的额度模型表退役，不再是真源。
- 落地按三阶段走：A1 新脊柱与会话（#1441–#1443）、A2 把刷新与 deck 的所有调用方迁到会话（#1444–#1445）、A3 账本换轨与 GitLab 端到端（#1446–#1447），最后文档收口（#1448）。

## 4. 被否掉的路

| 方案 | 为什么不选 |
| --- | --- |
| 只修「读数未知当 0」这一条 if | 事故的另外两条结构原因还在：调用方仍会在认出后端前拿 GitHub 口径过闸，规则仍散在几十处调用点，下一次会换个入口复发 |
| 继续让每个调用方自己过闸、自己记账 | 同一套规则需要几十份拷贝，漏一处就是事故；也无法保证「选后端不花额度」这类跨调用点的约束 |
| 用 backendId 等值判断代替预算模型 | 三个后端的差异会被写成散落的 `if (backendId === 'github')`；新增后端要改算式。模型由后端声明后，算式只读声明 |
| 读不到读数时按 0 处理（现状） | 直接把「不知道」判成「耗尽」，正是本次事故的直接机制 |
| 读取数时顺手裁决或记账 | 读数本身不是一次后端操作，裁决与记账会让「查一下额度」改变额度，也会让未知读数误导准入 |
