## 1. 背景

面板今天有四份数据各说各话：

- 宿主整仓快照（session-snapshot-cache，跨重启靠磁盘回放）；
- 客户端 issueCache（60 秒 TTL，取数失败置 null）；
- 地图子票桶（每次返回整桶替换，加载期间先空）；
- 详情即时拉取（失败时干净空白）。

结果同一张票在不同视图里可能显示不同状态；REST 降级时快照里的依赖边与子票计数为空，出现「GraphQL 明明查出 3 个子票、界面显示 0/3、降级后变成 0/0、评论一条不剩」；详情页改完状态回到列表也要等整仓刷新才一致。

2026-10-30 的真机样本（research/graphql-rest-fallback-2026-10-30.md）说明这不是偶发：当天 33 次降级里 31 次是传输层断流（3.1–3.3 秒 EOF），当时 GraphQL 配额还剩 3850–4268 点、同一条命令直连重放 6/6 成功；列表降级 22 次共丢弃 73 个已经成功的页。降级是必须处理好的常态路径，而现在的降级会丢掉已经拿到的数据，这比慢更伤害判断。

维护者在本次讨论里给出四条要求：

1. REST 降级不允许减少 GraphQL 已经查到并显示出来的数据（例：3 个子票降级后仍是 3，不能变 0）；
2. 进入 MAP 详情时先继续显示列表页已经知道的阻塞关系，等新查询回来再更新；
3. ISSUE 详情里把票关闭后，回到列表应立即显示已关闭；
4. ISSUE 详情请求回来后应留下永久快照，之后的请求按增、删、改合并，不要每次进入都空白。

## 2. 决策

### 2.1 一个快照

- 面板快照是面板工具区的唯一业务数据快照。权威副本在宿主（含落盘回放），面板渲染读它的投影；客户端不再保留第二份业务缓存（issueCache 与地图子票桶退役为投影）。
- 快照装什么：整仓全部票的行（编号、标题、状态、标签、指派人、作者、父子关系、依赖边），加上已经取到过的按需细节（正文、评论、评审、子票清单），加上标签与后端能力。不装：版本控制页、设置、技能、检查链。
- 物理分层、逻辑一份：宿主负责存与合并，面板只读；面板里的临时取数结果必须先经宿主合并回快照，再投影回视图。

### 2.2 增量合并（增、删、改）

- 所有读结果与写操作回执都按增量合并进快照：来源明确新增则加，来源明确变化则改，完整来源明确不存在或被删除则删。
- 未知 ≠ 空：字段有三态（有值 / 明确为空 / 不知道）。来源没有表达某个字段时保留上次已知；只有完整来源能清空字段。
- 每个字段组记下「上次已知」的来源与时间；同字段冲突时以更晚的完整来源为准。
- 视图不逐字段标脏：合并后对视图就是一份普通快照；哪块数据降级了、多久没刷新、刷新失败，由通知中心统一告知（见计划文档阶段 5）。

### 2.3 刷新与显示分离

- TTL 只决定这份数据算不算新鲜、什么时候在后台重取，不决定能不能显示。
- 取数失败保留上次数据并标记，绝不因为一次失败清空已知内容（现状 failDetail 置 null 是第一处要改的）。
- 快照落盘；跨重启先画磁盘里的上次快照，再在后台校准。界面要能分辨「这是上次的快照、什么时候的」。

### 2.4 写操作回执先合并

- 写操作成功回执按 2.2 立刻合并进快照，列表、详情、地图因此立即一致；随后防抖触发一次整仓校准刷新。
- 写失败不做乐观修改；失败原因进通知中心。

### 2.5 边界与尺寸

- 详情数据进快照后是工作区共享的（同一工作区的所有会话看到同一份）；当前打开哪张票、草稿、筛选仍是会话私有，不进快照。
- 按需细节要有上限：评论与评审只保留取到过的内容，设条数与字节上限，超出按最近使用淘汰；淘汰只影响细节，不影响行数据与依赖边。

## 3. 门禁（怎么判）

- tests/verify-panel-snapshot-merge.ts（新增）：直接调用合并纯函数，逐条证明字段三态与四类合并结果（增 / 改 / 删 / 保留）；降级来源不删已知、完整来源可删、字段级保留上次已知。
- tests/verify-single-read-source.ts（新增）：静态断言客户端不再出现第二份业务缓存的写入路径（issueCache 写入、地图桶整桶赋值）；视图模块只允许引用投影读函数。
- tests/verify-detail-incremental.ts（新增）：详情取数失败后快照内容不变；成功回执只改增量字段；在详情关闭票后列表行状态立即变化。
- tests/verify-snapshot-disk-replay.ts（新增）：跨重启先画磁盘快照、校准后覆盖；来源与时间保留。
- 既有门禁回归：tests/verify-visible-truth.ts（界面不写假状态）、tests/verify-1286-snapshot.ts（快照形状）、tests/verify-rest-fallback-banner.ts（横幅退役后改为断言通知事件）。
- 新增门禁必须能红能绿：先按旧行为写红，再修到绿；门禁编号与文件以落地票为准。

## 4. 取代的旧结论

| 旧结论 | 出处 | 新结论（本文） |
|---|---|---|
| 客户端各自 60 秒缓存，失败置 null | 现有实现 | 唯一快照，失败保留上次数据并标记 |
| 地图子票加载时先空、成功后整桶替换 | 现有实现 | 先画快照已知，回来按增量合并 |
| 详情每次进入即时拉取、无持久 | 现有实现 | 永久快照 + 增量合并 |
| TTL 过期即清空或重拉 | 现有实现 | TTL 只触发后台刷新，不决定显示 |
| 降级时 blockedBy 写成空数组、诚实可读 | docs/research/424-refresh-dual-channel-spec.md §Out of Scope | 已知依赖保留为上次已知，未知才标未知 |

## 5. 后果与现在的缺口

- 快照体积会变大（评论正文进快照）：靠按需细节上限与淘汰控制，超限要记日志。
- 跨会话共享详情意味着别人的操作可见，来源与时间要保留，否则无法判断新鲜度。
- 迁移期双源并存是最大风险：旧缓存与快照同时写会让数据再次分叉；用 verify-single-read-source 防回流。
- 实施顺序、每阶段门禁与对抗式审查清单见 docs/design/20261030-panel-snapshot-and-room-layering-plan.md。
