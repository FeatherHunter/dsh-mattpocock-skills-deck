# ADR：快照库按读写锁语义工作——去掉进程级写者租约（关联：#1929、#1928）

## 1. 背景

快照库是工作区数据的唯一真相。两个 DSH 窗口打开同一个工作区时，当前实现让一个进程在开库时抢一份「写者租约」，抢不到就整个句柄只读；心跳每 5 秒续 15 秒（`src/workspace-snapshot/runtime/lease.ts`）。结果是：

- 空闲窗口只要开着就长期占着写权，别的窗口永远只读；
- 没抢到的窗口写回执时直接回 `readonly`（`runtime/open.ts`），不是排队；
- 持有者退出后只读句柄不会自动接手（`snapshot-library-handles.ts` 缓存、`snapshot-library.ts` 注释）；
- 回执优先只有 5 秒时间窗（`config/ttl.yaml` 的 `snapshotReceiptPriorityMs`），长刷新会越过。

维护者要的是**读写锁**：所有会话并发读快照；任何会话改完后端后，把写回执用一次短写事务排队写入本地库，最终一定落库。

## 2. 决策

### 2.1 读：读快照

读是 WAL 快照读，不加锁、不阻塞写、写不阻塞读。所有进程都从同一个库版本读到一致视图；读本身不需要任何「读锁」。

### 2.2 写：短写事务排队

去掉进程级写者租约；所有进程都能打开可写句柄。每次写是一次 SQLite 短写事务（`BEGIN IMMEDIATE` + `busy_timeout`），写者按数据库的写锁排队；写事务只在提交期间持有，空闲进程不持有。

### 2.3 失败：有界重试 + 后端再同步

写事务在 `busy_timeout` 后仍失败时，按有界重试（默认 5 秒 + 2 次退避）；仍失败就如实报错。后端仍是源头：下一次刷新或回执会把这一笔再同步进来。**不做本地持久队列**——它会制造第二份真相，并引入重复写与清理问题。

### 2.4 冲突：按组版本 + 后端时间

- 整份刷新带 `startMergeVersion`；某组的 `written_version` 比它新，这趟读不许覆盖该组。
- 读回来的行 `updatedAt` 比库里已存的旧，也不许覆盖。
- 回执之间同样：旧的不能盖新的，按后端返回的时间/版本判。

退役 5 秒回执优先时间窗：时间窗只能挡窗口内的迟到，长刷新会越过去；版本 + 后端时间才能覆盖「读在回执之后开始、却从远端拿到写之前状态」这一档。

### 2.5 整份刷新：一次事务

整份刷新保持一次事务（原子）：崩溃时库要么上一轮、要么这一轮（#1869 的验收依赖这一点）。用实测保证不超 `busy_timeout`；若 2000 行会超，调大超时或按容器拆。

### 2.6 整库重建：库外的短时互斥

整库重建是唯一需要互斥的破坏性操作。互斥锁不能只放在库里（库文件会被删掉重建），要放在库文件旁边或另一处；短时获取、带过期与 fencing，只在重建期间持有，空闲不持有；拿不到就等或退回在线。

### 2.7 旧机制清理

- 同一次迁移删掉 `meta.lease_owner` / `lease_heartbeat_ms` / `lease_expires_ms` 与租约 TTL/心跳配置；不保留回滚到旧租约的路径（维护者明确「不会回滚，我们都用新机制了」）。
- `lease-held-readonly` / `lease-lost-readonly` 诊断与界面文案退役（文案归 #1928）。

## 3. 考虑过的方案

- **保留进程级租约**：不采用。空闲占写权、写不排队、退出不接手。
- **只放开写回执、整份刷新仍单写者**：不采用。仍不是读写锁，刷新那条路还会空闲占权。
- **本地持久队列**：不采用。后端是源头，回执丢了可以再取；持久队列会制造第二份真相。
- **只按时间窗做回执优先**：不采用。5 秒窗挡不住长刷新；改成按版本 + 后端时间。

## 4. 后果

- **门禁重写**：`verify-1862` C1/C2（第二写者只读 → 第二写者能写、写者排队）、`verify-1869-refresh-write` D1–D4（只读窗口刷新不写库 → 任何窗口都能写）、`verify-1869-ingest-crash`（清租约行 → 无租约）、`verify-1889-write-receipts`（5 秒窗 → 版本 + 时间规则）。新增并发写回执、刷新 vs 回执、空闲不阻塞、重建互斥的门禁。
- **迁移**：删列、删配置；不提供回滚。
- **界面与诊断**：`lease-held-readonly` / `lease-lost-readonly` 退役；#1928 删界面内部状态句。
- **性能**：读不被写阻塞；写者按 SQLite 写锁排队；原子整份刷新会阻塞其他写者——用实测决定是否按容器拆。
- **风险**：并发写回执的冲突规则要按组测；整库重建的锁要跨文件重建；`updatedAt` 缺失/未知时按既有三态规则（未知不覆盖已知）。

## 5. 未决/待实测

- 整份刷新在真实工作区上的 p95 是否超过 5 秒 `busy_timeout`；超过就调大或按容器拆。
- 并发写回执的冲突规则在真 SQLite 上的压力测试。
- 重建互斥的 fencing token 具体放哪（锁文件/外部文件），实现时定。
