# ADR：快照库按读写锁语义工作——去掉本地进程级写者租约（关联：#1929、#1928）

> 日期：2026-11-06 定版（维护者逐条拍板 Q1–Q9；同日对抗式审查后修订）
> 地位：本文只改「谁可以写、怎么写、写完谁看得见」这一层；库是唯一真相、投影、三态、版本门、回执优先等旧口径继续有效。

## 1. 背景

快照库是工作区数据的唯一真相。两个 DSH 窗口打开同一个工作区时，当前实现让一个进程在开库时抢一份「写者租约」，抢不到就整个句柄只读；心跳每 5 秒续 15 秒（`src/workspace-snapshot/runtime/lease.ts`）。结果是：

- 空闲窗口只要开着就长期占着写权，别的窗口永远只读；
- 没抢到的窗口写回执时直接回 `readonly`（`runtime/open.ts`），不是排队；
- 持有者退出后只读句柄不会自动接手（`snapshot-library-handles.ts` 缓存、`snapshot-library.ts` 注释）；
- 回执优先只有 5 秒时间窗（`config/ttl.yaml` 的 `snapshotReceiptPriorityMs`），长刷新会越过。

维护者要的是**读写锁**：所有会话并发读快照；任何会话改完后端后，把写回执用一次短写事务排队写入本地库，最终一定落库。

## 2. 决策

### 2.1 读：读快照必须在一个读事务里

读是 WAL 快照读，不加锁、不阻塞写、写不阻塞读。但一次投影（列表、详情、变化集、容器）会发多条查询；必须把这几条查询包在**同一个读事务**里，并在同一事务里读取库版本。否则并发写可以在两条查询之间提交，投影会混版本，返回的版本也与数据不对应。

读事务要短：只覆盖投影需要的那几条查询；不把整页渲染放进事务。

### 2.2 写：本地磁盘短写事务排队；网络盘保留单写者回退

**本地磁盘**：去掉进程级写者租约；所有进程都能打开可写句柄。每次写是一次 SQLite 短写事务（`BEGIN IMMEDIATE` + `busy_timeout`），写者按数据库的写锁排队；写事务锁只在事务期间持有，空闲进程不持有。

**网络盘 / UNC**：多进程可写 SQLite 在 SMB/NFS 上不保证安全；这些路径保留旧的单写者回退（仍然只用一份写权，抢不到只读），原因只在设置页能力诊断与日志里说明，不放在列表状态行。读写锁语义只承诺本地磁盘。

### 2.3 失败：有界重试 + 尽快重同步 + 「本机库落后」状态

写事务在 `busy_timeout` 后仍失败时，按有界重试（默认 5 秒 + 2 次退避）；仍失败就如实报错，并在短延迟内安排一次探测/重同步，而不是等下一次常规 probe。后端仍是源头；**不做本地持久队列**（它会制造第二份真相，并引入重复写与清理问题）。

界面/诊断要有「本机库落后」的用户级状态；同步成功后清除。不能把本地写失败伪装成成功。

### 2.4 冲突：按组版本 + 严格更新的后端时间 + 回执护栏

- 整份刷新带 `startMergeVersion`；某组的 `written_version` 比它新，这趟读**跳过该组**，不是整批丢弃。
- 读结果的行 `updatedAt` **严格新于**库里已存的才覆盖；**持平不覆盖**（GitHub 的 `updatedAt` 只有秒级，同秒无法判先后）。
- 回执之间：严格更新的 `updatedAt` 才覆盖；持平按到达序（后到覆盖），并把它记为同秒的已知局限；下一次同秒整份刷新仍无法区分，依赖后端最终状态。
- **保留 5 秒回执优先窗作为第二道护栏**：它挡的是「读在回执之后才开始、却从远端拿到写之前状态」这一档；按版本判不到这一档，不能只靠 `updatedAt`。等新规则被门禁证明能覆盖这一档，再谈退役。
- 未知不覆盖已知：沿用现有三态（知道 / 确认没有 / 不知道）。

### 2.5 整份刷新：事务原子，逻辑允许按组跳过

整份刷新保持一次事务：崩溃时事务全提交或全回滚。但提交时允许按组跳过更新的组，所以**逻辑上不是「要么上一轮、要么这一轮」**，而是「这一轮 + 被跳过的旧组」的合并。 #1869 的崩溃断言要改成「事务全提交/全回滚」，不再声称整轮逻辑原子。

### 2.6 整库重建：库外的短时互斥

重建是唯一需要互斥的破坏性操作；锁不能只放在库里（库文件会被删掉重建），要放在库文件旁边或另一处：

- 用原子创建（独占创建锁文件/锁目录）获取；写 owner、过期时间与 fencing token；
- 只在重建期间持有；完成或失败立刻释放；
- 过期锁可清理；删/建前后复核锁；fencing token 防旧重建者恢复后误删新库；
- 拿不到就等或退回在线。

### 2.7 迁移与升级

- 本地磁盘去掉进程级写者租约；网络盘回退仍需要 `lease_owner` / 心跳列与配置——因此**不删这些列与配置**（对抗式审查后的修订；原 Q8 B“同一次迁移删列”撤销）。
- 升级要求所有窗口/进程重启，不允许新旧版本并发；开库加 schema 版本检查，旧版本检测到新库时明确失败而不是静默写。
- 不提供回滚到旧租约的路径；本地路径一旦切到读写锁，旧代码不再适用。

### 2.8 界面与文档

界面不再出现「只读 / 写锁 / 回放」这类内部词；数据年龄由面板头部已有的时间标签表达（界面改动归 #1928）。网络盘回退的原因只在设置页诊断与日志里说。

更新快照库 README 的写模型、ADR 与 GLOSSARY；新增本文解释「为什么本地去掉进程级写者租约、网络保留回退」。

## 3. 考虑过的方案

- **保留进程级租约（所有路径）**：不采用。空闲占写权、写不排队、退出不接手。
- **只放开写回执、整份刷新仍单写者**：不采用。仍不是读写锁，刷新那条路还会空闲占权。
- **本地持久队列**：不采用。后端是源头，回执丢了可以再取；持久队列会制造第二份真相。
- **只按时间窗做回执优先**：不采用。长刷新会越过 5 秒窗；改成按组版本 + 严格时间，窗口保留为第二道护栏。
- **所有路径都多写者（含网络盘）**：不采用。SMB/NFS 上的多进程 SQLite 不安全。
- **同一次迁移删租约列**：不采用。网络盘回退还需要这些列；撤销原 Q8 B。

## 4. 后果

- **门禁重写**：`verify-1862` C1/C2（第二写者只读 → 本地第二写者能写；网络路径仍只读回退）、`verify-1869-refresh-write` D1–D4（只读窗口刷新不写库 → 本地任何窗口都能写）、`verify-1869-ingest-crash`（清租约行 → 本地无租约；网络回退保留）、`verify-1889-write-receipts`（5 秒窗保留为第二道，版本+严格时间为主）。新增：读事务一致、同秒/陈旧读、按组跳过、并发写回执、空闲不阻塞、重建互斥、回执失败重同步、全量安装不回退。
- **迁移**：本地不删列；网络回退保留租约列与配置；升级要求全窗口重启；不提供回滚。
- **界面与诊断**：本地不再有 `lease-held-readonly` / `lease-lost-readonly`；网络回退保留这两个诊断，但只在设置页/日志显示；#1928 删列表内部状态句。
- **性能**：读不被写阻塞；写者按 SQLite 写锁排队；读事务要短，避免 WAL checkpoint 被拖住；原子整份刷新会阻塞其他写者——用实测决定是否按容器拆。
- **风险**：同秒回执的到达序是已知局限；并发写回执的冲突规则要按组测；整库重建的锁要跨文件重建；`updatedAt` 缺失/未知时按既有三态规则。

## 5. 对抗式审查修订（2026-11-06）

1. 补「读事务边界」——原规格假设 WAL 读快照一致，但投影是多条独立查询，实际会混版本。
2. 冲突规则改为「严格更新 + 持平不覆盖」，并保留 5 秒回执窗作为第二道；原「退役 5 秒窗」撤销。
3. 整份刷新改为「事务原子、逻辑允许按组跳过」；原「库要么上一轮、要么这一轮」撤销。
4. 迁移改为不删租约列与配置（网络盘回退需要）；原 Q8 B 撤销；升级要求全窗口重启。
5. 重建互斥补协议（库外锁、过期、fencing、删/建前后复核）。
6. 补「写回执失败 → 尽快重同步 + 本机库落后状态」；原「后端再同步」没有时限与失败态。
7. 网络盘/UNC 保留单写者回退；读写锁只承诺本地磁盘。
8. 测试补：读事务一致、同秒/陈旧读、全量安装不回退。

## 6. 未决/待实测

- 整份刷新在真实工作区上的 p95 是否超过 5 秒 `busy_timeout`；超过就调大或按容器拆。
- 并发写回执的冲突规则在真 SQLite 上的压力测试。
- 网络盘回退的路径判定（哪些 UNC/SMB 走回退）与真机验证。
- 重建互斥的锁文件在 Windows 上的原子性与过期清理。
