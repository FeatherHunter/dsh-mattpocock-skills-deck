# ADR：GitLab 房把 REST 请求收进根目录的请求 module，并按领域竖切目录（#1907）

> 日期：2026-11-05 定版（#1907 规格的结论落点；实施票 #1909–#1921 同批落地；#1925 收尾删除 9 个旧路径转发文件）
> 地位：本文件是 GitLab 房「请求 module 住在哪、目录按什么轴切、9 个旧路径转发文件为什么已经删除、请求收口还有哪个门禁盲点」的唯一依据。凡与本文冲突的旧写法以本文为准；未来若改这四条决定，以未来版本为准。

## 1. 背景

GitLab 房（`src/tracker/rooms/gitlab/`）在这次改造前有 27 个手写 TypeScript 文件、约 6,189 行，全部平铺在房间根目录。最大的三份是关系读写 538 行、入口 498 行、标签读写 474 行。规格 #1907 盘点出的具体困难：

- 找一个概念要翻整个根目录：票的读写、评论、标签、关系、仓库身份、项目发布互不相邻；
- 同一概念被拆在多个文件：票的列表与单票读、建票、关票、重开、改票同住一份文件，标签的读与写分居两份文件；
- 14 个操作 module 各自拼 `glab api` 的 method、路径与表单字段，请求形状没有单一出处；
- 同一份小逻辑有多个拷贝：仓库标识提取 9 份、票面正文标记有两条 import 路径、评论翻页有两份实现；
- 房外有 5 道门禁按确切路径读这个目录、9 个测试或脚本按旧路径 import，所以不能简单搬文件。

这次改造的硬约束是「不修改 `src/tracker/rooms/gitlab` 以外的任何代码」（ADR 与房间 README 除外）。因此所有结构决定都必须同时回答两个问题：怎么让房间里更好找，以及怎么让房外那些按路径写死的读者继续工作。

**请求 module 是什么**：本文说的请求 module，指房间根目录里新增的那个模块。它给每个远端端点一个具名函数（例如「取一张票」「列一页票」「写一条评论」），函数参数只收领域值（仓库引用、票号、正文、查询条件、超时），函数体只负责拼出 `glab api` 的 method、路径、表单字段与超时，并把请求发出去；它返回客户端原本的 `{stdout, stderr, code}` 三件套，不解析 JSON，也不判错误档位。JSON 解析与失败话术留在调用它的操作 module 里，因为每个调用点的解析容错与失败话术不同，收进请求 module 会让它的参数表长出一堆 message 参数。

**竖切与横切是什么**：竖切指按后端概念分顶层目录——票、评论、标签、关系、仓库、项目各占一个目录，读与写都放在这个概念自己的目录里；横切指按动作分顶层目录，例如把全房间的「读」放一个目录、把「写」放另一个目录，或者按 list、get、create 这类动作分目录。本文选竖切，理由与代价见决定二。

## 2. 决定

### 2.1 决定一：请求 module 必须住在房间根目录

**决定**：请求 module 放在 `src/tracker/rooms/gitlab/` 根目录，与入口、客户端、地址拼装、两条探针并列，不放进任何子目录。它只收操作层的 `glab api` 请求；进程边界仍由 `client.ts` 负责；环境探针（`preflight.ts`）与额度探针（`budget.ts`）留在根目录并各自保留自己的调用；非 api 的 `glab` 子命令（仓库查看与创建、登录状态等）不进请求 module。

**为什么**：房外的端点采样门禁 `tests/verify-1179-gitlab-endpoint-coverage.ts` 只扫房间根目录的直接子文件——它用 `fs.readdirSync(ROOM_DIR).filter((f) => f.endsWith('.ts'))` 读源码，不递归子目录。它把扫到的 `['api', 路径, ...]` 数组实参与 `.api(路径, ...)` 调用解析成请求形状，再与 `tests/tracker-contract/gitlab-endpoints.ts` 的登记表逐条对账：源码里发出去的每条请求都要登记，登记表里的每条也都要在源码里真的会发。请求 module 若搬进子目录，门禁就看不见它发出的任何一条请求，第二组断言会把登记表里的每条都判成「源码发不出去」，真实采样固件的可信度当场归零。门禁住在房间外，这次改造又禁止改房外代码，所以请求 module 只能放在门禁看得见的地方。

还有一层同源的原因：门禁会把助手函数的路径参数顺着调用点追回去（例如 `apiGet(path)` 里的 `path`），但只在本房根目录的文件之间追。请求 module 的具名端点函数与它们手里的字面路径必须在根目录，门禁才能把每个端点认全。

**否掉的替代方案**：

- **放进子目录（例如 `api/` 或 `channels/rest/`），同时把门禁改成递归扫描。** 否掉的理由是门禁在房间外，改它超出本规格的约束；而且递归扫描会把操作 module 里的请求也卷进来，等于换了一套判定口径，风险远大于这次结构改造。
- **维持现状：每个操作 module 自己拼请求。** 这正是这次要解决的毛病：请求形状没有单一出处，改一个端点要在多处核对 method、路径与表单字段。
- **给请求 module 一个通用入口 `request(method, path, fields)`。** 否掉的理由与规格第 2 条实施决定相同：通用入口把 method、路径、字段、编码这些实现知识推回调用方，门禁也无法解析变量路径；具名函数才能让调用方只说领域动作。

**代价**：根目录因此不是纯粹的「接口层」——它同时住着入口、出网边界与请求 module。请求 module 会随着端点收口逐渐变长，将来若想把它再拆细，必须先解决「门禁只扫根目录」这个前提，也就是先改房外代码。（#1925 删掉了 9 个兼容转发文件之后，根目录已经是「7 个真实文件 + 两份说明」；这条代价里原来提到的文件数偏多，随转发文件一起消失。）

### 2.2 决定二：按领域竖切目录，读写是文件属性而不是位置

**决定**：房间的顶层目录按后端概念划分：`issues/`（票）、`comments/`（评论）、`labels/`（标签）、`graph/`（关系）、`repo/`（仓库身份与权限）、`project/`（开仓发布）；跨领域的共享件放 `model/`（回包归一、票面正文标记、仓库标识提取）、`support/`（读路径日志、能力登记数据、读来源数据）、`room/`（链接与地址、提示文案、修复指引）。每个概念目录内部再用 `read`、`write` 或更具体的动作名区分读写。读与写是操作的属性，不是目录位置。

**提示文案的落点**：User Story 18 要求入口读起来像接口，所以提示文案也搬进了 `room/prompts.ts`，入口只 import 并再导出 `prompts`。两对历史别名（`glabInstallFix` / `cliInstall`、`glabLoginFix` / `cliLogin`）在 `room/prompts.ts` 里共用同一份文本，不再逐字抄两遍。房外的 `tests/verify-prompts.ts` 与 `tests/verify-686-accept.ts` 已改成从 `room/prompts.ts` 读提示文案块；这是「判据跟着源码走」，不是源码为门禁让路。以后提示文案再换位置，先改这两扇门禁的读取路径，再搬文件。

**为什么**：维护者与 agent 找东西时，先想到的是「这是票的事、评论的事还是标签的事」，而不是「这是读还是写」。竖切让一个概念只住一个目录，读它、改它、给它加一条新操作都在同一棵树里；横切会把每个概念劈成两半，找「票的读」和「票的写」仍要跨两棵顶层树，等于把今天的问题换个层级重演。竖切也与契约层的操作分组一致：新增一条标签操作时，落点一眼可见，不需要先判断它属于哪个横切层。

**否掉的替代方案**：

- **顶层按读与写横切（`read/`、`write/` 两个目录）。** 规格明确把它列在 Out of Scope。否掉的理由是它只把「27 个平铺文件」换成「两棵各装一半概念的树」，同一概念的读写仍分居两地；而且读与写常常共享归一、仓库标识与正文标记，横切会逼出更多跨目录引用。
- **保持平铺，只给文件名加前缀（例如 `issues-read.ts`、`labels-write.ts`）。** 否掉的理由是目录树本身没有表达出层级，27 个文件仍在同一层；前缀只是把概念写进文件名，找文件仍要扫全目录。
- **按契约动作分目录（`list/`、`get/`、`create/` 等）。** 否掉的理由是同一概念的代码会再次被拆散，而且动作名与后端能力的对应关系不如概念名稳定。

**代价**：目录变多，跨目录引用与相对路径变长；跨领域共享件必须显式放进 `model/`、`support/`、`room/`，不能再靠「反正都在根目录」随手引用；房外的旧 import 在改造期间需要转发文件兜住（见决定三，那批文件已由 #1925 删除）；以后把一个文件从概念目录搬到另一个概念目录，会被看成一次结构改动，而不是简单的文件移动。

### 2.3 决定三：9 个旧路径转发文件是过渡物，已由 #1925 删除

**决定**：改造期间只为房外确有读者的 9 个旧名字保留过根目录文件，文件内容只有 `export ... from '新位置'`，不加任何逻辑、包装或副作用；转发文件不新造默认值，新位置本身已有默认导出时，允许用 `export { default } from '新位置'` 把它原样转出（`issues.ts` 与 `idempotency.ts` 当时就是这样，文件里仍然只有导出语句）。**#1925 已把这 9 个文件全部删除，房外读者的 import 已改到新位置；根目录现在没有、以后也不要再有转发文件。**

删除的是这 9 个，表里右列是现在唯一该从那里取的位置：

| 旧路径（房间根目录） | 概念 | 现在的位置 |
| --- | --- | --- |
| `normalize.ts` | 回包归一 | `model/normalize.ts`；正文标记的六个函数在 `model/description-markers.ts` |
| `issues.ts` | 票操作 | `issues/read.ts`（listIssues / getIssue）与 `issues/write.ts`（create / close / reopen / update）；默认导出在 `issues/index.ts` |
| `maps.ts` | 地图清单 | `issues/maps.ts` |
| `repo.ts` | 仓库身份 | `repo/identity.ts` |
| `graph-membership.ts` | 亲缘挂载与指派 | `graph/membership.ts` |
| `idempotency.ts` | 建票幂等锚 | `issues/idempotency.ts` |
| `capability-register.ts` | 能力登记数据 | `support/capability-register.ts` |
| `read-log.ts` | 读路径日志 | `support/read-log.ts` |
| `read-sources.ts` | 读来源数据 | `support/read-sources.ts` |

政策要点：

1. 根目录不留转发文件。房外读者要取这些模块，直接写新位置；不要为迁就旧写法在根目录重建一层壳。
2. 转发文件只许 re-export 这条规矩随文件一起退役；将来若真有人提「再留一层」，按本节的原则否掉。
3. 新位置是唯一实现。不要另起一份拷贝，也不要用转发文件给同一个模块再留第二个名字。
4. 这次改的只有房外 import 路径与随之过期的注释：取值不变、断言的形状不变、测试语义不变。门禁与测试跟着源码搬家，是「读的人跟着源码走」，不是源码为门禁让路。
5. 改完重生成 `tests/gate-map.json`：有三扇门禁的文件头写着 `// 门禁归属: <旧路径>`，它们和 import 一起改到了新路径；这张表是生成物，没有改任何门禁判据或阈值。

**为什么删（而不是继续留着）**：维护者对这类问题的原则是「源码禁止向门禁让步，除非门禁有百分之一万的理由比我们源码需要的效果更加优秀」。只为旧 import 路径存在的转发文件不属于源码需要的东西——它让同一个模块长期有两条 import 路径，也让「根目录只剩真实文件」的结构目标永远达不到。改造期不改房外代码，所以那批文件临时存在；#1925 把房外 import 改完，前提消失，转发层随即删除。

**否掉的替代方案**：

- **永久保留转发层。** 否掉的理由就是上面的原则：它不服务任何门禁或测试需要的行为，只是历史路径的兼容壳。
- **旧文件继续当真实实现，新文件反过来 re-export 旧文件。** 否掉的理由是新的竖切目录会变成一层空壳，真正的源码仍住在平铺的旧文件里；改造没有发生，只是多了一层名字。
- **转发文件里加兼容逻辑或回退。** 否掉的理由是它会变成第二份实现，读者会继续依赖旧路径的行为。
- **#1925 里顺手改门禁的判据或阈值。** 否掉的理由与这次改造的约束相同：只搬 import 路径。删文件后重生成的 `tests/gate-map.json` 是生成物，不是判据；其它门禁脚本一条没动。

**代价**：房外有十几处 import 与三处 `门禁归属` 注释要跟着改，改错一处就是门禁跑到一半报「找不到模块」。这次一次性改完，代价只落在 #1925 这一趟；继续留着转发文件，代价则是每次改这一房都要在两条路径之间核对，而且永远不会消失。

### 2.4 决定四：请求收口没有门禁，只有约定与人工核对

**决定**：这次改造不新增「所有 `glab api` 必须经过请求 module」的门禁。请求 module 是约定，不是今天能被门禁强制的不变量。已知盲点原样写在这里：

- 今天没有任何门禁检查「一条 REST 请求是否绕过了请求 module」。
- 端点采样门禁只检查请求形状与登记表对不对得上，不检查这条请求写在哪个文件、经过哪个函数。它只扫房间根目录，还特意跳过 `client.ts`（唯一出网出口）。所以子目录里的操作 module 若直接 import 客户端的请求快捷方法并自己拼路径，端点采样门禁根本看不见，形状对不上时也未必能判红。
- 新增一条分层或递归门禁需要改房间外的 `tests/` 或 `scripts/`，这次约束不允许。

**今天的缓解**：

1. 房间 README 写明根目录语法：只有请求 module、`client.ts`、环境探针 `preflight.ts`、额度探针 `budget.ts` 可以直接发 `glab api`；其余操作 module 一律经请求 module 的具名函数。非 api 的 `glab` 子命令留在各自 module，不在此列。
2. 操作 module 不再直接 import 客户端的请求快捷方法（`glabClient(...).api`），只 import 请求 module 的具名函数；客户端的 `run` 仍可供非 api 子命令与探针使用。
3. #1921 收口时人工扫一遍房间，确认除请求 module、客户端与两条探针外没有 REST 直调；代码评审按同一条口径检查。

**为什么不在这次补门禁**：门禁文件住在房间外，改它超出规格约束；而且一条好的分层门禁要能区分「请求 module 自己」「客户端」「两条探针」「非 api 子命令」，还要处理助手函数的间接调用，写得太松等于没写，写得太紧会误伤探针。把它留成一张独立的房外票，比在这次结构改造里塞一条半成品更诚实。

**否掉的替代方案**：

- **靠端点采样门禁兜底。** 它只比形状，不比层次；子目录里的直调它看不见，根目录里另写一条同形状的直调它也会当成合法请求。它证明不了「请求形状只有一个出处」。
- **禁止房间内除客户端外 import `glabClient`。** 做不到：两条探针与非 api 子命令都要用客户端的 `run`；请求 module 自己也要用客户端。禁止 import 会把合法调用一起挡掉。
- **现在就加一条递归扫描门禁。** 见上：要改房外代码，而且判据本身需要仔细设计；这次没有这个范围。

**代价**：将来有人新增操作时，可能顺手在子目录里直接拼一条 `glab api`，请求形状就又有了第二处出处，而且端点采样门禁未必能发现。风险随着房间变深而变大。缓解只能靠 README、评审与收口人工核对；要真正消掉这个盲点，得另开一张房外票补门禁。

## 3. 代价与风险

1. **根目录已经不是「只有接口」的理想形态，但接近了。** 它同时住着入口、出网边界、请求 module 与两条探针；#1925 删掉转发文件之后，它就是「7 个真实文件 + 两份说明」，`requests.ts` 会随端点收口变长，那是这份结构的自然代价。
2. **9 个转发文件这笔临时债已经还清。** 它们在改造期间让房外读者继续工作，也让同一个模块暂时有两条 import 路径；#1925 把房外 import 改完、文件删掉之后，同一个模块只剩一条路径。以后有人再想在根目录补一层壳，按决定三的原则否掉。
3. **请求收口靠约定，不靠门禁。** 这是本文明确写下的已知盲点，不是遗漏。补门禁需要改房间外代码，应另开票。
4. **结构改造本身不改变行为。** 入口导出、返回形状、错误档位、提示话术、请求的 method、路径、表单字段与超时都逐字不变；任何行为变化都是回归，不是这次改造的成果。
5. **目录轴只有一条。** 关系与仓库身份也按领域竖切，不再另立一条「读与写」顶层轴；将来新增概念时，先问它属于哪个领域，再问读写落在哪个文件。

本文第 1 节与决定一、决定三都写着「不修改房间以外的任何代码」。实施中为让门禁跟着已经删掉的死代码走，有三处测试侧派生数据做了同步改动。它们都不是门禁判据（`tests/verify-*.ts`）的改动，也没有放宽阈值或断言：

1. **`tests/tracker-contract/gitlab-endpoints.ts` 删掉 `labels-list` 一条。** #1909 删掉了零读者的旧 `listLabels`（它只为一个被删掉的死别名存在），这条登记只为源码已经不再发送的请求作证；留着它，`verify-1179` 会要求源码发出一条永远不会发的请求。改动的是采样登记表数据，不是门禁脚本；已获主编排代理授权（理由写在 #1909 的实施评论里）。
2. **`tests/file-granularity-baseline.json` 删掉 `graph-blocking` 一行。** #1917 把关系读半边搬进 `graph/read.ts` 之后，`graph-blocking.ts` 的有效行降到 350 行以下；按那扇门禁第 6 条，达标文件必须同票移出基线，否则门禁自己会判红。这是派生棘轮名单，不是门禁判据；#1917 的实施评论写明由 #1921 收口复核，收口时按此保留。
3. **`tests/gate-map.json` 重新生成。** #1921 收口时房间树与旧路径文件都变了，门禁归属表按当前源码重新生成（提交 126c91dc）。它是生成物，不是人手维护的判据，也没有改门禁逻辑；由 #1921 收口票重生成。

除这三处外，本次改造没有改房间外的实现代码；上面三处也都没有改门禁逻辑、阈值或断言。
