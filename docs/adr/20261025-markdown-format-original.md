# ADR 20261025 · 本地 Markdown 后端的文件格式与位置以随包 Matt 技能原文为唯一真源

> 日期：2026-10-25 定版。规格 #1480 的实施决定，由实现 #1484–#1490 逐张落地（#1490 负责收口）。
> 地位：本文是「本地 Markdown 后端把票写成什么文件、放在哪个目录、插件自己的信息放在哪里」这三件事的唯一依据。它纠正 #1277 把规格做成 `.scratch/<feature-slug>/issues/` 里一张票的方向——凡与本文冲突的旧说法（规格是一张 kind=spec 的票、不再有独立的 spec.md、文件头写 `<!-- DSH-ISSUE-KIND: spec -->` 标记），以本文为准；旧文档保留作历史记录，由本文说明它们与当前口径的关系。
> 关联：规格 #1480 · 被纠正的前序方向 #1277 · #1382/#1384（把初始化说明改成 deck 工具口径，本规格要求改回随包原文）· 本轮实施 #1484–#1490 · ADR 20261020-object-kind-identification（对象类型识别，仍然有效）· ADR 20260909-effort-identity-in-repository-ref（工作单元标识进仓库引用）· ADR 20261021-config-ownership（一个值只有一处定义，本文据此不复制模板文本）

## 1. 背景：读得懂别人写的，却写不出别人能读的

插件的本地 Markdown 后端要同时服务两拨读者：随包的 Matt 技能（`setup-matt-pocock-skills`、`to-spec`、`to-tickets`、`wayfinder` 等）按 `docs/agents/issue-tracker.md` 里写明的文件布局直接读写工作区里的 Markdown 文件；deck 面板要读出结构化数据来渲染列表、地图与规格详情。两拨读者共用同一批文件，文件长什么样、放在哪里，只能有一个答案。

#1277 当时选的方向是：让规格也变成 `issues/` 目录里的一张票，靠文件头隐藏标记 `<!-- DSH-ISSUE-KIND: spec -->` 与 `parentKey` 把它认成容器，`spec.md` 不再单独存在。这个方向让 deck 的内部模型整齐了，代价是本地后端写出的文件偏离了随包技能原文：技能原文说规格是 `.scratch/<feature-slug>/spec.md`，而 deck 写出的是 `.scratch/<feature-slug>/issues/00-....md`。跟着 #1382/#1384，初始化提示词又被改成教使用者「不要照抄模板、按 deck 工具口径改写三段旧做法」，偏离从代码扩散到了首次初始化的说明里。

结果是同一个工作区里出现两种事实：技能文档说文件在哪、deck 实际写在哪，不一致；使用者按原文手写的文件，deck 能读但写回时可能换布局；初始化时被要求改写模板，等于把「以原文为准」的最后一环也拆掉了。

## 2. 裁决

**决定一 · 唯一真源是随包技能原文，pin 在 v1.3.1。**

- 本地 Markdown 后端写出的文件，格式与位置以随包技能 `package/bundled-skills/setup-matt-pocock-skills/issue-tracker-local.md` 为唯一依据。这份模板与上游 Matt 技能库 v1.3.1 逐字一致，逐字比对与哈希清单由门禁 `tests/verify-bundled-skills-upstream.ts`（清单 `tests/bundled-skills-upstream-hashes.json`）守着；说「以原文为准」时，说的就是这份被哈希钉住的文本，不是任何一份转述。
- 四类对象的位置固定为：
  - 规格：`.scratch/<feature-slug>/spec.md`，正文七节（问题陈述、解决方案、用户故事、实现决策、测试决策、不在范围内、补充说明）。
  - 探索地图：`.scratch/<effort>/map.md`，正文五节（Destination、Notes、Decisions so far、Not yet specified、Out of scope）。
  - 实施票、地图子票、普通票：`.scratch/<effort>/issues/<NN>-<slug>.md`，一个票一个文件，NN 从 01 起两位补零。
  - 地图子票完成时，在票里追加 `## Answer`，并往同一张地图的 `## Decisions so far` 追加一条带链接的指针（技能原文 Resolve 那一行的做法）。
- #1476 修过的「工作区根 `.scratch/map.md` 兜底」不再是新写入的落点：新写入一律进上面四类位置；旧布局只读兼容（决定四）。

**决定二 · deck 只是执行层，不是第二套口径。**

- 建票、认领、改状态、补边这些动作仍然走 deck 工具（`deck_issue_create`、`deck_issue_patch`、`deck_map_link` 等），工具负责取编号、写文件头隐藏注释、按原文布局落盘；但工具写出来的文件必须与原文一致，工具说明里不另立一套格式要求。
- 初始化提示词（`config/copy/panel.yaml` 的 `setup.markdown.backendNote` 中英两条）改为：生成 `docs/agents/issue-tracker.md` 时把随包本地模板逐字复制过去，模板里每一句做法说明保持原样，不改写、不省略、不追加；文件格式与位置以这份模板为唯一依据；deck 工具只负责执行落盘。旧口径「把模板里三段旧做法改成 deck 工具口径」「不要手写 `.scratch/` 下的文件」整段删除。
- `deck_context` 的本地后端用法说明（`src/deck/tools/context.ts` 的 `LOCAL_HOWTO_SUFFIX`）同步改成同一口径：先给四类对象的落点，再说明 deck 工具按原文布局维护文件，最后写明「技能原文与这段用法说明冲突时，以技能原文为准」。

**决定三 · 插件自己的信息只放文件头隐藏 HTML 注释。**

- 文件格式属于技能原文，插件不能往票面正文里加新字段。deck 需要记住的格式版本、标题、幂等键、创建时间、父票、标签、状态、认领人，一律写成文件头（第一个可见标题之前）的隐藏 HTML 注释（`<!-- DSH-FORMAT: md-v1 -->`、`<!-- DSH-TITLE: ... -->`、`<!-- DSH-IDEMPOTENCY-KEY: ... -->`、`<!-- DSH-CREATED: ... -->`、`<!-- DSH-PARENT: ... -->`、`<!-- DSH-LABELS: ... -->`、`<!-- DSH-STATUS: ... -->`、`<!-- DSH-ASSIGNEES: ... -->`）。这些注释在 Markdown 渲染里不可见，人类按原文手写文件时不需要知道它们。文件头不再按「第一个一级标题」划，而是「第一个可见标题」：有一级标题就是它，没有一级标题就是第一个二级段标题——规格与地图没有可见一级标题（见下一条），靠这条判据仍只把注释认在文件头，不会把整份文件当文件头。
- 规格与探索地图的原文模板没有标题行（技能把标题放在 tracker 的 issue 上），所以这两类文件不写可见一级标题：标题存成文件头的 `<!-- DSH-TITLE: <标题文本> -->` 注释，正文第一行直接是原文模板的第一个段标题（规格是 `## Problem Statement`，地图是 `## Destination`）；实施票、地图子票、普通票仍按原文模板写可见一级标题。读标题的顺序固定为：可见一级标题（兼容旧 deck 文件与手写文件）→ `DSH-TITLE` 注释 → 按目录名降级（规格与地图用 `effortId`，其余票用文件名去扩展名）；绝不拿 `##` 段名当标题，也绝不因为缺标题报错。改标题只改这行注释，绝不插回一级标题。
- 状态、类型、依赖这些技能原文要求的行内字段照原文写（`Status:`、`Type:`、`Blocked by:`，以及实施票的加粗字段行），不另造可见字段。
- #1486 起新写出的文件不再写对象类型标记 `<!-- DSH-ISSUE-KIND: ... -->`；但读取侧继续认旧工作区里的这枚标记（对象类型识别继续有效），整份替换正文时以盘上那一份为准保住它。

**决定三之一 · 可见正文里的插件增强段：`## 进度` 保留。**

- 规格、地图与票面的 `## 进度` 段是 deck 的增强，不是随包原文模板的段落：规格与地图建票时由 `ensureBody`（`src/deck/shell/minimal-spec.ts`）补出这一段，之后由 `deck_issue_patch` 的 `progress` 参数往里追加条目；格式映射 YAML 的 `enhancements` 单独声明它（`original-skills.yaml:234-237` 的 `progress-section`），原文模板的段落顺序里没有这一段。
- 「可见正文只放原文有的东西」按什么读：原文要求的段落、字段行与状态行逐字照抄；插件自己的**字段与标记**一律进文件头隐藏注释；插件自己的**独立段落**（`## 进度`）允许追加，但它不算原文模板的一部分——渲染、校验与读取都不把它混进原文模板的段落顺序，也不改变任何一个原文段落的含义。原文禁止的是往票面正文里加原文没有的字段行，不是禁止追加一段独立的增强段。
- 为什么不做 B 方案（把进度移出可见正文、放文件头注释或只留面板）：进度是人和 AI 每天都要直接看的最新状态，藏进文件头注释等于把一块常用信息从工作流里拿走；而且这一段是独立段落，移走并不能消除任何「原文没有的东西」，只是换一个位置藏起来，落盘与读取两端都要跟着改。**维护者 2026-10-25 拍板选 A（维持现状，由 #1501 承接），B 被否。**

**决定四 · 读写双向兼容：原文手写的文件能读能改，缺插件信息降级不报错。**

- 使用者按技能原文手写的 `.scratch/` 文件（没有 `DSH-FORMAT`、`DSH-PARENT` 等注释）能被列出、读单票、看快照、改、完成；缺插件信息时按内容推断，不当作损坏，也不报错。
- #1486 之前落在工作区根 `issues/`、工作区根 `.scratch/map.md`、`.scratch/issues/<键>.md` 的旧文件保持只读可用：列表、读取、快照跑得通；但写入路径（改状态、关闭、改正文、评论、认领、标签，凡是按写模式定位票文件的调用）在命中工作区根 `issues/` 或 `.scratch/issues/` 这两处扁平旧布局时如实失败，错误里说清「旧布局的票只读，迁移另行处理」，并记一条写日志（`issue.write` 事件的失败原因 `fail:unsupported`）。新写入不再往这些位置落；`.scratch/<feature>/issues/` 下的原文布局新票不算旧布局，读写都照常。旧数据的迁移另行开票，不夹带在本次纠正里。
- 已知边界（#1567）：旧布局里以票文件形式存在的地图（工作区根 `issues/` 下带 `wayfinder:map` 标签、没有 `map.md` 的票）只按票行的身份可读：列表里它是 `type=map`、`effortId` 是空串、`parentKey` 是 null，面板按这一行的身份打开详情。`00` 号容器路径只认 `map.md`，所以 `00` 号读不到；旧文件里没有父边，这张地图也没有子票清单（本地 Markdown 后端的 `listSubIssues` 明确不支持）。地图清单靠 `wayfinder:map` 标签（或旧的 `Type: map` 标记）认它，写路径仍按上面只读失败。这些可观测行为里，带标签地图票的列出与读回、地图清单认它、`00` 号确定 `not-found`、子票清单为空、写路径拒绝且文件逐字节不变，由 `tests/verify-1488-read-mixed-layout.ts` 场景③ 钉住。

**决定五 · 跨后端接口一致：effortId 就是 feature 目录名。**

- 契约层的 `effortId`（工作单元标识）在本地后端里就是 `<feature-slug>` / `<effort>` 目录名；规格的 00 号与实施票的 parentKey 都靠「同一个目录」表达父子关系，不新增跨后端字段。GitHub/GitLab 后端仍用原生父子关系与标签，本次零改动。
- 于是同一份规格（fixture 或真实工作区）在三个后端之间可以互换理解，deck 的归一模型、快照组装、面板渲染不需要为本地后端另开分支。

**决定六 · 00 号的读取与写入用同一套寻址顺序。**

- 规格的 00 号与地图的 00 号都叫 00，本地后端靠仓库引用里的 `mdScene`（`feature` 表规格、`effort` 表地图）区分；没给 `mdScene` 时读取侧先找规格、找不到再找地图。写入侧（`locateWriteTarget` 与 `update` 的容器解析）照抄同一顺序，两边不再各说一套：以前写侧不带 `mdScene` 就一律当地图，于是不带 feature 参数读到的规格关不掉、改正文或改标题还可能被当成地图。
- 两个 00 号（规格与地图）同时存在时，不带范围的操作落在规格上，地图一个字节不动；只有地图的工作区里，同一个操作落在地图上。

**决定七 · 建票不再回落到旧位置。**

- 仓库里还没有 feature 目录、调用方也没点名 `featureSlug`/`effortId` 时，建票（旧路径：没有原文布局依据的那条）如实失败、一个字节都不落盘，错误里说清「本仓库还没有 feature 目录；建票要先给 featureSlug/effortId，或先建规格」；绝不回落到工作区根 `issues/` 或 `.scratch/issues/`。有原文布局依据的四类对象仍按决定一的位置落盘。

### 2.6 为什么格式映射用 YAML 加生成器，而不是搬进 TypeScript 常量或直接 import

格式映射（原文模板的段落顺序、字段行形状、隐藏注释的名字与理由、状态词）住在 `src/tracker/rooms/markdown/format/original-skills.yaml`，由 `scripts/generate-md-format-config.mts` 生成运行时读的 `format/generated.ts`（不入库），门禁 `tests/verify-md-format-config.ts` 比对两边并把坏数据演练一遍。这不是「配置化」顺手做的，按 ADR 20261021 第 2.2 节的决策测试与三条自问，它属于数据文件路线：

- **一个值一处定义。** 这份映射是上游 Matt 技能原文的镜像，模板文本、隐藏注释的排列、字段行形状都随上游 pin（v1.3.1）一起升级，不是本仓库开发者随手改的常量。若把模板形状抄进 TypeScript 常量，原文升级时就要在两处各改一次——那正是 ADR 20261021 第 1 节点名过的第二份拷贝。
- **编译器连不起来。** 这台映射同时被两拨消费者读：运行时（`renderSpec`、`renderMap`、`renderTicket` 按它渲染文件）与门禁（按条目逐项核对「每一项隐藏注释都写了理由」「生成物与 YAML 对得上」）。两拨消费者不在同一个程序里，YAML 也不是 TypeScript 模块，编译器看不到它；按第 2.2 节的判断，连不上才搬数据文件、配生成器与门禁——这是这条路线成立的条件，不是偏好。反过来说，搬进 TS 常量只会得到「编译器能看懂的副本」，而丢掉门禁真正要守的两件事：生成物必须能被门禁按数据文件逐项读出核对，以及运行时与门禁读同一份源、不各写一份。
- **三条自问的回答。**（1）改它的人是维护「原文长什么样」的人，改的是数据不是代码，还要按上游 pin 升级，不是写代码的人随手调常量；（2）今天已经有 YAML 与生成物两份，所以不靠人记，靠生成器加 `--check` 加门禁盯新鲜度，生成物每次构建重算、不提交；（3）搬走会不会丢编译期保证——类型安全由 `scripts/lib/md-format-config.mts` 的校验收口（生成物结构与类型在 `typecheck` 里过，坏数据演练在门禁里过），补在生成器与门禁这一层，而不是丢掉。折中的结果是：值住数据文件、类型住 TypeScript、新鲜度住门禁，三层各管一件事。

## 3. 影响与迁移

- #1277 方向撤回：规格恢复成独立文件 `spec.md`，实施票在它同目录的 `issues/` 下靠目录层级与 parentKey 注释挂父子。旧工作区里已经写成「规格票」的文件仍能读（契约类型 spec 与对象类型识别都还在），只是新的写入不再产出这种布局。
- 初始化说明与 `deck_context` 用法说明同步改回原文口径；门禁随之更新：`tests/verify-setup-describe.ts` 的金样换成新文案，`tests/verify-1385-howto.ts` 换成新契约断言。
- 新增两扇门禁参与全链：`tests/verify-1490-declaration-file.ts` 压住「初始化声明文件逐字复制随包模板、模板与上游 v1.3.1 逐字一致、旧改写指令消失」；`tests/verify-1490-four-objects.ts` 在临时工作区里走完四类对象的建、读、改、完成、列表、快照，并把最小旧布局复制进临时目录验证只读可用。
- 两轴评审确认的四处规格偏差与一处文档论证缺口由 `tests/verify-1480-review-fixes.ts` 压住：规格与地图落盘没有可见一级标题、标题在 `DSH-TITLE`；手写无注释文件的标题降级不报错；改标题只动注释、片段正文插在文件头注释之后且不吞原段；00 号读写同一判据；空工作区不带 feature 建票失败且不落根 `issues/`；旧根 `issues/` 的票可读可列、写路径失败且文件前后逐字节不变。
- 发布说明要写清：本地 Markdown 后端写出的文件布局回到随包技能原文；规格与地图不再写可见一级标题，标题在文件头 `DSH-TITLE` 注释里；老工作区不需要手工迁移，能读、能列、能看快照，但旧布局的写路径会如实失败并说明只读，新票按新布局落盘。
- 规格、地图与票面文件里会多一段 deck 增强的 `## 进度`；它不是随包原文模板的一部分，按「决定三之一」保留在可见正文（#1501 拍板 A）。
- 不夹带：旧工作区一次性迁移、GitHub/GitLab 后端改动、T6 已知的「deck 关闭票的路径不传关闭原因」缺口，都不在本次范围内，另行开票。

## 4. 被否掉的路

| 方案 | 为什么不选 |
| --- | --- |
| 继续 #1277 方向，让规格继续是 `issues/` 里的一张票 | 随包技能原文明确写规格是 `spec.md`；技能按原文读文件，deck 写出另一种布局等于让两套读者互相不认，且使用者按原文手写的文件会被读成另一种对象 |
| 保留两套布局，写的时候按来源选一套 | 同一个工作区里会出现两种规格文件与两种 ticket 编号；快照、面板、技能三方必须各处理一遍，任何一处漏判就重复计数或读不到 |
| 把插件信息写进 YAML frontmatter 或可见字段 | 原文明确禁止 frontmatter，可见字段会改变技能读到的文件内容；隐藏 HTML 注释对渲染不可见，也不占用原文的字段 |
| 一次性自动迁移旧工作区 | 迁移会改写用户手写的文件，动作不可逆；先只读兼容，迁移另行评估并按票执行 |
| 把随包模板文本复制进配置或门禁里当第二份真源 | 违反 ADR 20261021 的「一个值只有一处定义」；模板正文只有 `package/bundled-skills/` 一处定义，门禁通过哈希清单比对，不复制正文 |
| 让 deck 自造一套更整齐的布局，再改技能文档去适应 | 技能是随上游发布的只读资产，改文档只是把分歧藏起来；下游每装一次插件就会覆盖一次 |
| 给规格与地图保留一行可见一级标题 | 随包原文的这两份模板没有标题行（标题在 tracker 的 issue 上）；写出多一行就等于落盘与原文不再逐字一致，技能按原文读文件时还会把它当正文第一段。标题放进文件头 `DSH-TITLE` 隐藏注释，既能显示和改名，又不污染可见正文 |
| 把 `## 进度` 段移出可见正文，或塞进文件头隐藏注释（#1501 的 B 方案） | 进度是独立段落，不是原文禁止的字段行；保留在可见正文不改变原文任何段落，移走反而让读进度多绕一层，还要改落盘与读取两端（#1501 选 A 维持现状） |
| 把格式映射搬进 TypeScript 常量，或让运行时直接 `import` 一份 TypeScript 模块 | 真源是上游原文的镜像、要随 pin 升级，且运行时与门禁这两拨消费者不在同一个程序里，编译器连不起来；搬成常量就是第二份手抄，详见 2.6 |
