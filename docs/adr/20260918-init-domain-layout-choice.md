# ADR：初始化时由用户选域文档布局，以及与「子目录会话归到工作区根」的边界

> 日期：2026-09-18 定版（地图 #647 · 票 #651；维护者当日确认）。
> 地位：新增决定，不修订任何旧口径。与 `docs/adr/20260918-subworkspace-identity-root.md`（#649）并行生效，两者边界见第 3 节。凡与本文冲突的旧说法，以后定版日期较新者为准——与 `CONTEXT.md` 开头两条版本与效力规则同款。
> 关联：#647（地图）· #651（讨论定版）· #657（规格单）· #655（落地）· #649 与 `docs/adr/20260918-subworkspace-identity-root.md`

---

## 1. 背景（为什么要有这条决定）

- 插件今天对「这个仓库的域文档怎么组织」**零表态**：初始化只是往会话里注入一段提示词，`CONTEXT.md`、`CONTEXT-MAP.md`、`docs/agents/domain.md` 全部由会话里的 AI 按随包技能写出，插件既不读也不写这些文件。
- 随包技能本身支持两种布局，但它的默认与判据都不够用：默认「一个仓库共用一份词表、直接写不问」；只有当探索时发现 monorepo 形状（工作区文件、`packages/*` 各有自己的 `src/`）才把另一种端给用户确认，判据还带一句「只出现在真正的大型多包仓库」的形容词，由会话里的 AI 当场心证。
- **初始化时仓库可能一个文件都没有**（新仓库），形状判据在那一刻本来就无从谈起。
- **形状判不出结论，有两条真机证据**：`D:\ilife`（有工作区文件、16 个包、其中 7 个各带自己的 `AGENTS.md`、每个包都带 `src/`）今天是一份根 `CONTEXT.md`；插件自己那个仓库同样有工作区文件与两个子包，却也按一份词表走。同一形状、两个结论。
- 连带问题：初始化写下的那份说明文件里同时画了两种结构图，却没有一句结论说这个仓库是哪一种，读的人（人或 AI）不知道该按哪张做。

## 2. 决策

### 2.1 布局由用户在初始化那一刻选定

- 两个选项，说人话，不出现内部术语（这一条管谁，见下面那条读法）：**「根目录一份 CONTEXT.md」**（默认、排第一）与**「子项目各一份 CONTEXT.md，根目录 CONTEXT-MAP.md」**。
- 读法（2026-09-19 补，票 #658 定稿 · #659 落地）：上面写的「不出现内部术语」管的是**插件自己的私词**（「上下文」「子工作区」「工作区根」这类），**不管用户仓库里真实存在的文件名**——`CONTEXT.md` 与 `CONTEXT-MAP.md` 是用户迟早会在自己仓库里看到的文件，写进界面不算违规；反过来也不许拿这一条当依据，把刚写上的文件名又删掉。
- 问的位置：点初始化后弹出的小卡上，与「选哪个后端」并列，两组单选一次答完。
- 不探测仓库形状来决定布局。

### 2.2 所有初始化入口走同一个注入决策函数（单漏斗）

布局没选定就先弹卡，选完再注入；任何入口都不许直接注入初始化文本。建仓成功后的自动补发沿用本次会话已选的答案，不再问第二次。

### 2.3 初始化只记结论，不铺文件

- 结论写两处：初始化写下的说明文件里加一行（本仓库是单上下文／多上下文）；用户仓库 `AGENTS.md` 里那一行按同一答案写。
- 地图与各子项目的词表**不在初始化时创建**——空仓库时列不准，而且这些文件本来就是「第一次真正写下词条时」才建。
- 选择只活在本次会话：不落持久状态、不加「改布局」的入口；想改就改说明文件里那句话，或重跑一次初始化。

### 2.4 插件不读域文档

不读 `CONTEXT-MAP.md` 与 `CONTEXT.md`；不做面板展示、不做环境检查行；只在注入文案里带一句「先读说明文件」。

### 2.5 与「子目录会话归到工作区根」（#649）的边界

**这是同一个仓库里两件不相干的事，各管各的轴，不许互相借用。**

| | 由 #649 管 | 由本决定管 |
| --- | --- | --- |
| 管什么 | 插件的**数据与写路径**：票仓、后端绑定、面板快照、检查链快照，以及 `docs/agents/` 下的主锚文件与配色文件 | 仓库的**领域词表怎么分**：`CONTEXT.md`、`CONTEXT-MAP.md`、`docs/adr/` |
| 谁写 | 插件（配色文件、票）或会话按技能写（主锚文件） | 人和会话里的 AI——**插件既不读也不写** |
| 放哪 | 永远在**工作区根**，只有一份；子目录里不许长第二套 | 单上下文＝仓库根一份；多上下文＝每个子项目各一份，根上一份地图指向它们 |
| 怎么判 | 从所选目录逐层向上，第一个**自带 `.git` 或自带 `docs/agents/issue-tracker.md`** 的目录 | 由用户在初始化时选定；插件不判定 |

由这张表推出两条纪律：

1. **子目录里出现 `CONTEXT.md` 是允许的**（那是领域词表，属于本决定）；**子目录里出现第二套 `docs/agents/` 或票仓是不允许的**（那属于 #649）。
2. **工作区根的标记只有两个，不许扩建**：`.git` 与 `docs/agents/issue-tracker.md`。**「这个目录自带一份 `CONTEXT.md`」绝不能加成第三个标记。**

第 2 条要防的具体后果：一旦把 `CONTEXT.md` 当成标记，用户在 `D:\ilife\packages\skill-calorie` 这类子目录里开会话时，判定会停在该子目录——面板只显示子目录自己的票、票仓与配色文件会在子目录里长出第二套。这正是 #649 花一整张图根治的事。

生效时点：#649 的判定当天只有文档、没有代码（落地票 #652／#653／#654 未开工）。所以「`docs/agents/` 与票仓只有一份、永远在工作区根」是**目标口径**，随那些落地票生效；在那之前它是本决定要守住的方向，而不是今天的实际行为。

### 2.6 既有仓库不迁移、不回填

已经被初始化过、今天按一份词表走的仓库保持原样；新规则只对「用户主动重跑初始化」与新仓库生效。与 #261（命名回填移出范围）、#649（既有工作区不删不迁移）同款口径：插件不擅自改用户仓库里已经存在的东西。

### 2.7 随包技能本体不动

`package/bundled-skills/**` 是从上游 `mattpocock/skills` 整目录复制来的（pin v1.2.3），同步一次就整目录覆盖。所有改动放进插件那段注入文字，不改技能文件。

## 3. 本文不包含什么

- 随包技能文件的改动与上游同步策略；
- 既有仓库的布局迁移与回填（见 2.6）；
- 面板上展示「当前目录属于哪份词表」、把布局纳入环境检查链；
- #649 那套判定的代码落地（判定、分桶、写路径、随包脚本）——另票；
- 与布局无关的性能问题（如 GitHub 快照慢）。

## 4. 验收

- **规格单是验收基线**：#657 规格：初始化时由用户选域文档布局（承接 #651）。落地票 #655 照它执行。
- **行为**：布局未选定时从任何入口点初始化都先出那张小卡、不注入；选定后注入的文案里是两句不同的布局句之一，且不留悬空占位符。
- **结构**：产物里只允许一条注入初始化文本的路径（检查页红牌那颗「执行初始化」按钮必须在名单内改走同一个注入决策函数）。
- **边界**：任何把「自带 `CONTEXT.md`」加进工作区根判据的改动，视为违反本决定。
