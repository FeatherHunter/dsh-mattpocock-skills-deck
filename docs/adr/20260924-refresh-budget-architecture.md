# ADR：刷新机制的六条不变量与它的形态（纯逻辑进 refresh-core · 常量单一真源 · 三个后端各一套额度模型）

## 1. 背景

刷新机制解决的是「插件把 GitHub 配额用光」这件事：开 10 个工作区时最坏约 24,300 次请求／小时，是上限的 4.9 倍（定稿第五章实测）。定稿给出的解法不是「少刷一点」，而是把「能不能花、花多少」收进一道闸里，让插件**在结构上失去把配额用光的能力**。

这套设计有一份 15 章的设计文档（`docs/architecture/refresh-budget-architecture.html`）与十二张落地票。设计文档写得细，但它不是判据：后来人改一行代码时，需要的是一句能当场对照的「这样改违背了哪一条」。所以本文件把六条不变量写成判据，并把四条形态决策（纯逻辑放哪、常量放哪、三个后端怎么记账、最坏按哪条线算）一并定下来。

本文件不重复设计文档的论证过程，只写结论与判据。

## 2. 六条不变量（判据）

六条的术语定义在 `CONTEXT.md` 的「刷新机制与 AI 工具链词条」里。这里只写**判据**：怎么算违背、哪条门禁在看。

### I1 唯一出口：对 GitHub 的每一次调用都必须经过闸

- **判据**：`src/host/` 下任何一处执行 `gh` 的代码，都必须在闸（`src/host/refresh/gate.js`）之后；闸之外的调用点数为 0。
- **怎么判**：`tests/verify-gh-gateway.js` 静态扫全部调用点，外加运行期「漏网调用数 == 0」的断言。新写的调用点绕过闸 → 红。
- **为什么要机器判**：这条不是纪律，是物理落点。靠人记的结论是「昨天还记得，今天加了个便捷函数就忘了」。

### I2 后台零定时器：正在看的那个工作区之外，没有任何长期定时器

- **判据**：除正在看的那个工作区之外，没有工作区持有长期定时器；刚离开的那个最多保留 30 秒收尾节拍，更早离开的一次都不发。
- **怎么判**：`tests/verify-attention-model.js` 断言后台档零定时器、活跃集合上限为 2、90 秒无信号后全部收摊。
- **注意（定稿第十四章改过的口径）**：原文「后台零定时器」曾被读成字面意义，与「刚离开 30 秒仍按快档探测」自相矛盾；现行写法是「刚离开的保留最多 30 秒，之后必然归零」。

### I3 首屏只付行数据的钱：正文、评论、评审、地图子票全部只在人点开时取

- **判据**：一次列表能不能只按「一页行数据」的单价记账；正文与评论不许进首屏那条查询。
- **怎么判**：`tests/verify-gate-accounting.js` 按 `budget.js` 的每页单价核对每一笔的账；`tests/verify-budget-worstcase.js` 与 `tests/verify-event-budget.js` 用同一组单价算最坏。
- **落地现状（必须知道，2026-09-24）**：这一条只落地了「按页单价分层算账」那一半（薄片段的单价 2 点／100 行已经是真源）。**「整池重建改走薄片段、把正文与评论从列表里去掉」这一半没有落地**，原因见 §7。

### I4 用量与工作区数量无关：开 3 个和开 30 个，花费同阶

- **判据**：花费只随「活跃集合（上限 2）」与「事件次数」增长，不随注册过的工作区数量增长。
- **怎么判**：`tests/verify-attention-model.js` 的活跃集合上限断言 + `tests/verify-event-budget.js` 的事件那一半上界（切换次数 × 单价、写事件次数 × 单价）。

### I5 失败必可见、必退避：取数失败不许悄悄吞掉

- **判据**：失败要在界面上说出来；重试要拉开间隔；连续失败要熔断；失败不许放大成请求风暴。
- **怎么判**：`shared/refresh/backoff.ts` 的退避序列与熔断判定（`tests/verify-*.js` 里针对它的一组断言）；`tests/verify-visible-truth.js` 断言界面上「取数时刻／刷新失败／降级中」三处文案都有真实读取点。

### I6 花费可归因、可对账：每一笔花费都记在账上

- **判据**：每一笔花费都能回答四件事——谁发起、属于哪一档、花了多少、当时剩多少；账本的累计数 == 传输层真发的 HTTP 请求数（含分页、重试、兜底链、扇出）。
- **怎么判**：`tests/verify-gate-accounting.js`。
- **口径要点**：记账单位是**真实出站 HTTP 请求数**，不是「逻辑上一次调用」；服务端读数取保守下界（本地已花与上次读数取小者，两次同步之间不再加额度）；REST 与 GraphQL 两桶各自独立档位。

### 关于余量：按上界算，读那一份额度最多用到八成七（2026-09-24 起生效）

最坏用量改成按页数上界算之后（见 §6），读那一部分用得比原来多：按现在这组常量算出来，`tests/verify-budget-worstcase.js` 报 **1008 / 1225 ≈ 82%**、`tests/verify-event-budget.js` 报 **1068 / 1225 ≈ 87%**，整桶报 1152 / 1750 ≈ 66%。两条门禁都还绿，但**余量只剩两成不到**。

这件事不是错误，是**如实**：上界口径本来就更保守（一次重建按 10 页算，而本仓典型只要 5 页）。写在这里是为了让它是一个说出口的数，而不是一个没人注意到的余量。**做法上的约定**：T14 真机实测拿到本仓真实页数之后，用真值再复核一次这道余量；**如果真值把余量压到一成以下，那时再谈要不要调上界或调旋钮**（探测间隔、对账间隔、页数上界都是旋钮，改一处门禁就跟着重算）。

## 3. 纯逻辑放哪、取数与落盘放哪

- **纯逻辑住 `refresh-core/src/*.ts`，转译成 `src/shared/refresh/*.js`**（产物带 `AUTO-GENERATED` 头、提交进仓库），由 `node refresh-core/build.mjs` 生成，`tsc --noEmit` 与新鲜度门禁一起管着。形态依据是 `docs/adr/20260913-builtin-ts-shape.md`（它定的是「插件内置 TypeScript」的通用形状：不发 npm 包、源码不进 `src/`、逐文件转译、产物提交）。
- **I/O 留 JS**：取数与落盘住在 `src/host/**`（三个后端房间、闸、账本、视野模型、行级增量）。判定一句「这段代码该放哪」的标准只有一条——**碰不碰磁盘、网络、时间、进程**：碰就留 JS，不碰就进 TS。
- **产物之间零相对引用是硬约束**（`tests/verify-refresh-freshness.js` 的「产物零相对引用」与 `tests/verify-no-same-layer-import.js` 一起守）。所以纯函数不许 `import` 另一个产物；要用的数字与形状一律**由宿主侧取好、当参数传进来**。
- **`refresh-core/` 下的 `.ts` 源文件不受「单文件 350 行」这条数字约束**（2026-09-24 统筹者定）。
  - 为什么：350 行那条门禁（`tests/verify-file-granularity.js`）只扫 `src/**/*.js`，`refresh-core/` 根本不在它的范围内；这是**有意如此**，不是漏掉。核心里几个文件（`chain.ts`、`attention.ts`、`budget.ts`）都是为了「一件事写在一处」才长到几百行的。
  - **不能靠拆 `.ts` 来满足 350 行**：产物之间零相对引用是硬约束，拆出去的那一半要读另一半的东西时，唯一的合法做法就是把那段逻辑再抄一遍——那是往核心里种重复代码，比行数超标坏得多。
  - 它们受的是另一套纪律，一共三条：**单一职责**（一个文件一件事，文件名说清是哪件事）、**纯逻辑**（不碰磁盘、网络、时间、进程）、**可单测**（能只喂参数、只读返回值地测）。
  - 真到了「一个文件里明显是两件事」的时候，拆法只有一条：**按职责边界拆，拆完两边互不 import（各自只靠参数拿数据）**；这跟 350 行那条数字没有关系。

- **产物里不再手写「来源标注」常量**（2026-09-24，#719 落定）。转译产物的第一行本来就有一行机器生成的包头 `// AUTO-GENERATED by node refresh-core/build.mjs … Source: refresh-core/src/<同名>.ts`，它按**真实文件名**生成，改不了也漂移不了；再手写一个 `export const X_SOURCE = 'refresh-core/src/x.ts'` 就是同一个事实的第二份副本，而且今天没有任何代码读它——它唯一的作用是让人以为有人在校对。所以核心里那六个（`attention` / `backoff` / `chain` / `create-write` / `delta` / `idempotency`）一并删掉。
  - **例外一：空壳产物**。`refresh-core/src/ports.ts` 的产物只剩一行模块标识（类型被编译期擦掉之后它没有别的运行时代码），那一行 `PORTS_SOURCE` 就是它唯一的可追溯内容，留着（新鲜度门禁也在断言它）。
  - **例外二：读者在测试里**。`policy.ts` 与 `write-detect.ts` 的标注各有一条门禁在断言（`tests/verify-policy.js`、`tests/verify-write-detect.js`），有人读就留着。
  - 守着这条的机器判据是 `tests/verify-contract-vocabulary.js`：整棵 `src/shared` 的字符串型常量，值必须在生产代码里出现、或名字必须被人读过，两条都不满足判红。

## 4. 额度常量的落点

- **只有一处物理真源**：`refresh-core/src/budget.ts`。节拍（探测 5 秒、对账 10 分钟、预检寿命 10 分钟、链退避序列）、额度比例（35% / 1,750 / 读 70% / 写保底 30%）、每页单价、不变量要用的阈值，全在这里；算式也在这一份里，别处不许再写一遍字面量。
- **宿主侧怎么用**：从产物 `src/shared/refresh/budget.js` 把常量取出来，折成一个参数对象再喂给纯函数。做法与既有三处完全一致——`policy.ts`（给「请求类别 + 档位 + 已用额度 + 工作区状态」返回放行／降级／推迟）、`backoff.ts`（给退避序列与各种寿命）、`tool-cost.ts`（给 AI 工具那一档的硬顶）。**纯函数自己一个数字都不写**。
- **为什么不做成「纯函数自己 import 常量」**：产物之间零相对引用是硬约束（§3），一 import 就红。真正的收益比「少写一行参数」大得多——纯函数因此可以只喂参数地单测，不必先把真额度搭起来。
- **服务端此刻还剩多少不许写死**：额度上限与剩余只能现场读（GitHub 走那个不扣配额的 `gh api rate_limit`），由账本每分钟读一次。

## 5. 三个后端各按什么口径记账

三个后端不是同一套额度形状。把它们写在一处（`refresh-core/src/backend-quota.ts` → `src/shared/refresh/backend-quota.js`），闸与账本按后端取，比在三处各写一段「如果是 GitHub 就……」可靠。

| 后端 | 口径 | 有几个桶 | 点数制 | 出站计费 |
|---|---|---|---|---|
| GitHub | 两个互相独立的桶 | REST 桶 + GraphQL 桶，各一份额度、互不折算 | 有（GraphQL 数点） | 计 |
| GitLab | 只有出站请求条数这一种口径 | 一个 | **没有**（不许编一个） | 计 |
| 本地 Markdown | 不出站 | 没有 | 没有 | **不计**（读写本机文件） |
| 认不出来的后端 | 只记请求数 | 一个 | 没有 | 计 |

- **GitLab 的额度数值今天没有实测依据，所以如实写成「待实测」**，不写一个看起来像真的数。写错的方向是不对称的：把没有点数制的后端猜成有点数制，会凭空算出一份额度、让闸以为自己有钱；反过来只是少记。所以认不出来的后端一律按更省的一侧记。
- **两桶与 35% 是 GitHub 专属**：`independentBuckets` 为真的只有 GitHub；其余后端的档位只有一个「请求数」的账。
- **本地 Markdown 后端不花任何额度**，但它照样走闸（I1 管的是「所有出站调用」，本地写入不出站，所以在闸里按 0 记账、照常放行）。

## 6. 最坏用量按哪条线算

- **实测页数与页数上界分开记、分开用**：
  - **估**（账本按每个仓库自己的实测页数估）：小仓库不必替大仓库付那份钱。账本记每个仓库最近一次翻了几页、**历史上最多见过几页**、累计重建过几次（`src/host/refresh/ledger.js` 的 `notePages` / `pagesFor` / `estimateRebuild`）。
  - **最坏**（门禁与账本的最坏列）：一律取「实测与上界里大的那个」。上界是 `budget.MAX_PAGES = 10`。实测突破上界时按实测算，并如实报出「突破了」——不许把已经发生过的事忘掉。
  - **`MAX_PAGES = 10` 的身份是「上界假设」，不是实测结论**（2026-09-24 统筹者裁定）：它没有本仓实测依据（设计文档另有一处「本仓 6 页」的记录，10 是留了余量的数）。它就该比现实宽——最坏用量算的正是「比现实更坏的那条线」。**本仓真实页数以 T14 的真机实测为准**；实测值落进 `ledger.notePages` 之后，如果真实值超过了 10，`worstPagesFor` 会自动改用实测值（取大者），门禁也会跟着变，不需要改这个常量。需要实测的是本仓真实值，不是这个上界本身，所以不另开票。
- 算式只此一处：`refresh-core/src/page-budget.ts` 的 `rebuildCost` / `worstCaseRebuildCost` / `pageCountReport`。宿主侧取好每页单价传进去。
- **典型值与最坏值是两个数，不许混用**：`budget.REBUILD_COST_POINTS`（13 点）是按典型页数（5 页）算的，只用来说明单价；最坏一律按上界算（今天 23 点、12 条请求）。门禁 `tests/verify-budget-worstcase.js`、`tests/verify-event-budget.js`、`tests/verify-budget-page-upper-bound.js` 一起守这条。

## 7. 后果与现在的缺口

- **正**：六条不变量各有一条机器判据；纯逻辑与 I/O 的分界线是「碰不碰磁盘网络时间进程」这一句可判的话；额度常量只有一处，改一个数就够；三个后端的记账口径写在一处，不再散在闸与账本里各写一段。
- **代价**：核心里有几个几百行的 `.ts` 文件（§3 说明了它们为什么不拆）；纯函数都要多收一个「参数对象」，调用点比直接 import 常量啰嗦。
- **现在的缺口（2026-09-24，如实记在这里）**：I3 的「整池重建改走薄片段」这一半没有落地。设计上要把列表查询里的正文与评论去掉，让整池重建从 25 点降到 13 点；实际动手时发现 `tracker.list()` 的正文还有两个真实读者——地图子票的进度是从子票正文里的 `## 进度：N%` 解析出来的（`src/shared/tracker/deck-derive.js` 的 `progressOf`，`src/host/tools/deckMapSnapshot.js` 走的就是它），以及地图快照里的计划块。把它们去掉，等于把这两个功能一起做掉，需要先有一条「按需取正文」的路。这一半的处置见 #719 的回报与本文件的变更记录。
