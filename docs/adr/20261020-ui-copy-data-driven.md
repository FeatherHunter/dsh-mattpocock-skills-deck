# ADR：界面文案数据化与语言清单单一真源（#1284）

## 1. 背景

界面上的每一句文案（面板标题、按钮、提示、报错、状态行）今天都写在 TypeScript 源码里。

1. **词表本身。** 界面词表由 10 份片段拼成，都在 `src/client/kernel/locale-*.ts`：`locale-panel`、`locale-flow`、`locale-word`、`locale-labels`、`locale-pages`、`locale-vcwrite`、`locale-skilldesc`、`locale-skilldetail`、`locale-cards`、`locale-spec`；合并器是 `src/client/kernel/locale.ts`（把各片段的中英两份并成运行时用的 `L.zh` 与 `L.en` 两张大表）。全仓 964 个键，每份片段里中英文并排写在同一个对象里。界面不写死文字，按键去表里取当前语言那一份（`tr('nav.word')`），表交给宿主的语言服务（`src/client/index.ts:122-135`）。
2. **语言是个二元闭集，声明了三遍。** `src/client/kernel/locale-panel.ts:28` 与 `src/client/kernel/locale-pages.ts:40` 各有一份 `LocaleLang = 'zh' | 'en'`，`src/client/kernel/prompts.ts:339` 还有一份 `PromptLang = 'zh' | 'en'`。运行期其实只有一个语言来源（DSH 的 locale 快照，`promptLang()` 与 `tr` 都问它），重复的只是类型声明。
3. **还有 9 处按语言二选一写死的文案**（`promptLang() === 'en'` 那种写法，分布在 `api-naming.ts`、`prompts.ts`、`router.ts`、`slotRenderer-modal-view.ts`、`PixelSkillOps.ts`、`naming-titles.ts`，以及 `NoRepoCard.ts` 的同形写法），它们绕过了词表。加一门语言时这 9 处会露馅。
4. **门禁靠手写清单，已经漂了。** `tests/verify-locale-completeness.ts` 的 A 面靠数「某个键名在源码文本里出现几次，必须是 2」来判断中英配齐；查哪些文件靠一张手写清单，今天少列了 `locale-cards`、`locale-skilldetail`、`locale-spec` 三份、共 65 个键。已实测：在这三份里只写中文不写英文，门禁照样报绿（另开票 #1289）。该门禁的 A2 面查词条结构，用的是同一批手写清单，同样漏这三份。
5. **提示词那一半边已经定了机制。** #1278 的结论是档 A：真源搬到 `config/prompts/` 下的 YAML，生成器产出客户端模板数据，语言清单是 `config/languages.yaml`，加一门语言不用改代码；门禁改成读 YAML 做断言，盯源码排版的规则整条退休。对应的施工票 #1282、#1283 按地图的规矩已关闭、正文写着「尚未动工」，仓库里现在还没有 `config/languages.yaml`，也没有生成器。
6. **宿主那一侧的契约查清了。** 宿主自带语言只有中英（`dsh-client-locale` 的 `lib/index.js` 里 `LOCALE_IDS = ["zh", "en"]`），但开放了插件加语言的口子：`ctx.locale.addLanguage({ id, label, fallback })` 把语言加进可选项，`ctx.locale.register(ns, 'ja', {...})` 交上那门语言的词表；回退链必须终止在英文。词表交上去时若给的是带类型的对象形式，编译器会按命名空间的键联合类型逐键检查、并要求两种内置语言都齐全。查不到译文时不会静默，会把键名本身显示在界面上。宿主自己那道 `verify-client-ui-i18n` 门禁只管宿主产品代码，且没有随运行时发布，插件侧指望不上。详见 `research/1284-locale-data-contract.md`。

## 2. 决策

### 2.1 界面词表数据化：真源是 `config/` 下的 YAML，生成器产出客户端数据

界面词表与提示词侧用同一套机制（#1278 的档 A）：

- **真源**：`config/` 下的纯文本数据文件，界面文案一族单独分文件；每个键在每种语言下各有一份译文。
- **生成物**：生成的 TypeScript 数据模块，产出物不入库（照 `src/shared/time-config/src/values.ts` 与 `scripts/generate-time-config.mts` 的先例）。源码里只留「读生成物」这一句，不再有第二份文案。
- **日常闭环**：改数据文件 → 跑生成器 → 构建 → 重启插件；不多一步。
- **生成器带 `--check`**，挂在 `typecheck` 串的最前面：改了数据忘了生成，当场判红并提示跑一次生成器（与时间参数那套同款纪律，见 `docs/adr/20261016-time-config-yaml.md` §2）。

### 2.2 语言清单是单一真源，提示词与界面共用一份

`config/languages.yaml` 装支持哪些语言、每种语言的回退链、缺省语言。它是客户端级事实：提示词侧与界面侧都从它读，界面上那三处重复的语言类型声明收成一处。

「加一门语言不用改代码」在插件侧的落法由这一条决定：**注册动作由语言清单驱动**。宿主要求插件显式做两件事才有一门新语言的位置——把新语言加进可选项（`addLanguage`）、交上那门语言的词表（按语言注册的形式）。所以插件不能把中英写死在代码里，要按清单里的每一门语言注册一遍；往清单里加一行、再补一份译文，就完成了一次加语言。

### 2.3 第三门语言的内容现在不写，只把机制做足

先把上面两条修好，第三门语言的译文等真有人要加时再补。内容是人力问题，不是机制问题。

### 2.4 完整性门禁改成对着语言清单逐门核对

判据从「数某个键名在源码文本里出现几次，必须是 2」改成「语言清单里有几门语言，每个键就得有几份译文」。

同时，**查哪些文件不再手写清单，按目录自动发现**。今天手写清单已经漂了（§1 第 4 条），自动发现把这类漏登记从根上消掉。这一条与 #1289 是同一件事：那张票的验收标准并进本决策的实施范围。

门禁改写的判定强度不许降，实施时要交一张对照表（旧门禁能抓的违规类型逐类列出新的靠哪条判据抓；对照表缺项就是强度降了，不许放过）——这是 #1283 已经用过的做法。

### 2.5 两半边合起来做一套，界面这半边排在提示词侧机制落地之后

提示词侧的机制（`config/languages.yaml` + 生成器 + 门禁改读 YAML）今天还没落地。所以界面这一半边排在它后面做，或至少共用同一份语言清单与同一个生成器；不各做一套。

理由：各做一套会在仓库里留下两套真源、两套生成器、两扇门禁，「加一门语言」要改两处代码，恰好违背 §2.3 要保住的「加语言不用改代码」；后面再合回来又是一次改写。

### 2.6 实施时必须带上的两条约束

1. **生成物要产出键联合类型。** 宿主那套逐键的编译期检查，靠的是注册时那个带类型的对象（键联合类型逐键比对、要求两种内置语言都齐全）。生成器如果只吐两份裸对象，这层检查就丢了。
2. **注册由语言清单驱动。** 见 §2.2 末段：把语言加进可选项与交上那门语言的词表，两步都由清单里的条目驱动。

## 3. 为什么这样定

1. **机制只做了一半，界面这半边要跟上。** #1278 正文第九节明确把界面文案排除在自己范围之外、另开票跟进。界面这半边停在二元硬编码不是做漏了，是范围切分的结果。
2. **运行时语言本来就只有一个来源。** 界面与提示词问的是同一份 locale 快照，宿主那一侧也只有一套偏好、回退与选择器。分成两份清单只会多一处会漂的地方。
3. **宿主契约不排斥这种做法。** 宿主对「文案放哪种文件」没有要求，它要求的是注册时的形状与带类型的键联合。所以选 YAML、选 JSON、还是继续用 .ts 词典，在宿主这一层都合法；决定这件事的是仓内一致性，不是宿主约束。
4. **完整性门禁必须留下。** 宿主那边查不到译文时会把键名直接显示在界面上（用户会看到 `nav.word` 这种字样）。这道门禁挡的是「某一门语言少一个键」，判据必须跟着语言清单走。
5. **合起来做一套更省。** 机制、清单、生成器、门禁四样都只做一次；分开做等于把同一套东西做两遍。

## 4. 后果与风险

1. **加语言的成本下降。** 今天是往 10 份文件里复制 964 个键再逐条翻译；之后是往清单里加一行、往数据文件里加一份译文。
2. **门禁强度不许降（风险）。** 门禁从「数源码里的出现次数」改成「对数据逐门核对」，判据换了对象，容易顺手放松。§2.4 的对照表就是防这个的。
3. **生成物漂移（风险）。** 数据文件改了、生成物没重生成，界面就会显示旧文案。`--check` 挂在 `typecheck` 最前面，生成物不入库、每次构建现场生成，这条风险照时间参数那套的既有办法治。
4. **9 处按语言二选一写死的文案是已知缺口。** 它们绕过词表，加第三门语言时会露馅。本决策没拍板怎么处理（那是实施范围的边界），但规格阶段必须连着界面词表数据化一起定：是把它们收进词表，还是改成按语言清单查表。
5. **宿主那道门禁指望不上。** `verify-client-ui-i18n` 只管宿主产品代码，且没有随运行时发布；插件侧的完整性只能自己设门禁，也就是 §2.4 那一道。
6. **提示词侧尚未落地。** 本决策的 §2.1、§2.2、§2.4 依赖提示词侧那套基础设施（生成器、共享配置读取模块、语言清单）。实施顺序按 §2.5 排。

## 5. 不在范围内

- 第三门语言的译文内容（§2.3）。
- 运行期从插件目录读文案：照 `docs/adr/20261016-time-config-yaml.md` §2.2 的口径，这些数据文件只活在仓库里、只在构建期被读，装到用户机器上的插件读不到它、不给运行期可调的入口。
- 提示词侧那半边的施工范围（#1282、#1283 的内容），以及后端各自自报的那部分文案（形状与来源都不同，不属这一套）。
- 宿主侧的本地化服务本身（宿主自己的语言清单与偏好管理）。

## 6. 实施阶段的交付物与验收

实施票由维护者对地图 #1274 跑 `/to-spec` 产出的规格、再跑 `/to-tickets` 拆出，不在本图上挂。实施时至少要交出这些：

- 一张「判定强度对照表」：旧的中英完整性门禁能抓的违规类型逐类列出新的靠哪条判据抓（对照表缺项就是强度降了，不许放过）。
- 改一条数据文件 → 跑构建 → 重启插件，界面文案随之变化。
- 改了数据忘了生成：`typecheck` 判红并提示跑一次生成器。
- 生成物带键联合类型：漏译一个键在编译期就红，不等到界面上露出来。
- 键数与覆盖面按新口径核对：964 个键（被读到的 899 + 漏检的 65），且门禁按目录自动发现、新加片段不用登记。
- 加一门语言的演练：从清单加一行、补一份译文，不改任何 `.ts` 源码，界面就多出一门语言。
