一、前因后果：这条提示词为什么跑不通

1. 事情是怎么被发现的

你在 web 界面触发唤醒词，让 AI 按注入的提示词写回一张 issue 的正文。AI 的回报里有三段：

  • 前置检查通过：gh auth status 显示已登录 github.com 的 FeatherHunter，令牌有效。
  • 第 ① 步卡住：提示词原话是 dsh plugin exec node -e "…"，缺 --profile 直接报错；AI 自己补上 --profile web 才拿到插件安装目录。
  • 第 ② 步正常：在工作区里跑写回脚本、--body-file 用绝对路径，回包 {"ok":true,…,"warnings":[]}，脚本自述「已经和要写的内容一样，不再发请求」；随后复核 #599 正文与文件逐字符一致（2201 = 2201）。

也就是说：问题只出在第 ① 步那一句命令上——它是给「读提示词的人／agent」照抄用的，照抄却跑不通。

2. 根因：--profile 是必填，旧提示词漏了它

dsh 的 plugin 子命令是「往某个 profile 目录里转发 pnpm」的入口，它把 --profile <name> 声明成必填选项。我把四种写法都实跑了一遍：

实测（Windows，dsh 在 PATH 上，插件装在 web 这个 profile 里）
命令形状结果
dsh plugin exec node -e "…"（旧提示词原话）报 required option '--profile <name>' not specified，退出码 1
dsh plugin exec --help同样报这个错，连帮助都看不到
dsh --profile web plugin exec …同样报这个错（顶层那个 --profile 喂不到 plugin 子命令）
dsh plugin --profile web exec …打印插件安装目录，退出码 0 ✅

顺带说明：本仓库既有的文档一直就是带 profile 的写法——README.md 里是 dsh plugin --profile web add dsh-mattpocock-skills-deck，更新模块的手工兜底命令是 dsh plugin --profile <名> add <包>@<版本>。所以这不是新口径，而是提示词这一处漏抄了参数。

3. 为什么不能干脆写死 web

试出来的事实：profile 名填一个不存在的名字，dsh plugin 会先照模板初始化出同名 profile 目录，再往下跑。实测输出：

dsh: initialized profile probe-delete-me at C:\Users\辰辰洋洋\.dsh\profiles\probe-delete-me
Already up to date
Done in 315ms using pnpm v11.25.0

这等于在用户机器上留一个空 profile（探针目录我已删掉）。所以提示词给的是「填你自己启动界面时用的那个 profile 名，Web 界面通常就是 web」，而不是写死一个 web。
