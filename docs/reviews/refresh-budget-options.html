面板刷新：四个可选方案

目标只有一个：同时开着十几个工作区，也永远碰不到 GitHub 的配额上限，同时你切回去的时候，看到的东西仍然是新的。下面从第一性原理把「刷新」拆开，给出四个各自完整、可以直接选的方案——你不用做任何决定，回一个字母就行。

所有数字都是本机实测（2026-09-22，仓库 FeatherHunter/dsh-mattpocock-skills-deck，684 张票 + 10 个拉取请求）。出处列在文末。

第一部分先把「刷新」这件事拆开

不谈方案，先立四条不能违背的前提。它们决定了什么样的设计才叫「高效」。

四条前提（事实，不是选择）

  1. 配额是两只独立的桶，各 5,000/小时。一只按「请求次数」算（REST），一只按「点数」算（GraphQL）。用光一只不影响另一只，但两只都跟你的 agent 共用同一份额度——插件花掉的，就是 agent 少掉的。
  2. 同一时刻，你只看一个工作区。其余的工作区即使开着会话、面板挂在那儿，屏幕上也看不见它们。
  3. 切换是你唯一真正在意的时刻。你从 A 跳回 B，希望 B 是新的；你在看 A 的这段时间里，B 新不新无所谓。
  4. 同一个根目录下的多个会话，是同一个工作区。仓库根和它的子目录会话看到的是同一批票，只该花一份钱。

一句话推导：既然只有一块屏幕在亮，那「一直盯着所有工作区」就是拿 90% 的预算去买你看不见的东西。真正值得持续花钱的，只有「你现在正在看的那个工作区」；其余的，等你看它的时候再花。

而「等你看它的时候再花」这件事，体验上并不会变差——因为切换本来就是「先用手上的旧数据把界面铺满（毫秒级），随后静默取一次新的、再闪一下差异」。现在缺的只是那一次「取新的」。

于是「刷新」变成四个可以各自决定的问题

要决定的事现在怎么做的可选做法
什么时候去问远端所有工作区，每 60 秒各问一次；检查链没全绿的每 8 秒问一次只在「正在看的」工作区上按节拍问；其余在切进来那一瞬间问一次
谁的额度先花没有区分。后台轮询和用户点刷新花的是同一份，谁先到谁先花分两档：用户动作发起的永远放行；后台自己发起的从一份预算里取，取不到就推迟
一次取多少每次全量重建都把正文和每票 50 条评论一起拖回来：一次 25 点列表只取「画一行要用的字段」（一次 13 点），正文和评论在你点开某张票时再取（现在本来就是这样）
失败时怎么办不计数、不退避：限流了也照原来的节拍继续打失败越多、间隔越长；并且把你「正在看的东西可能是旧的」这件事说出来

第二部分四个方案

四个方案都是完整的：每个都替你定好了上面那四个问题的答案，你不需要在方案内部再做任何选择。每个方案都标了「每小时花多少」——按 10 个工作区、你来回切 20 次、其中一个仓库很活跃来算。

A

止血版：只修最费的三处，刷新模型不动

改动最小 半天到一天

怎么跑

仍然「所有工作区都定时探测」，但把三件最费的事按住：① 检查链从固定 8 秒改成带退避（8 秒 → 30 秒 → 2 分钟 → 5 分钟封顶，一旦有进展立刻回到 8 秒）；② 环境预检（登录态 + 仓库可达）的缓存从 30 秒放宽到 10 分钟，失败时立即重试一次；③ 连续失败三次就退到 1 分钟、再失败退到 5 分钟、30 分钟，成功一次立刻回来。

每小时

REST ≈ 1,260 次（25%）；GraphQL 不变，仍是 25 点/次。三个仓库同时在动就能吃掉九成额度。

要改什么

三个文件：链的轮询、环境预检的缓存寿命、失败退避（今天这两个熔断常量在代码里没有任何调用方）。外加两条门禁测试。

你会感觉到

没什么变化——检查页从「8 秒一跳」变成「先快后慢」，修复完成后自动变绿会慢几秒。

代价

后台那九个看不见的工作区仍然在花钱；每次重建还是 25 点；并且没有任何东西拦着「以后新增的调用点」再次越线——它把 4.9 倍压到 1.3 倍，但没有把越线这件事变成不可能。

B

视线驱动版：看谁刷谁，顺手把单价减半

推荐 2～4 天

怎么跑

工作区分成两种状态，只有一种在花钱：

正在看的那个工作区

变化探测每 30 秒一次；一旦发现远端有变化，最多每 60 秒重建一次（半分钟里连改五张票，也只重建一次）。

切进来的那一瞬间

先用手上的数据把界面铺满，同时探测一次；数据超过 5 分钟、或探测到有变化，就重建一次。

其余所有工作区

一次请求都不发。检查链、命名守护、重建，全部停表；切回去时重新上表。

顺手修的单价

列表那条查询改成「只取画一行要用的字段」——把正文和每票 50 条评论从重建里去掉（点开单票时本来就另有一次取数）。实测从 25 点降到 13 点；正文与评论在单票页照旧随点随取，一个字都不少。

每小时

REST ≈ 270 次（5%） ｜ GraphQL ≈ 910 点（18%），其中约 780 点是「每分钟都有变化、每分钟重建一次」的上限。这跟你打开几个工作区无关——只跟你切换多少次、以及那个仓库有多活跃有关。

要改什么

① 把「现在在看哪个工作区」这个信号从界面传到宿主（今天判定的只是「整个应用窗口有没有被最小化」）；② 探测与链的定时器改成只服务当前这个工作区；③ 列表查询换薄片段 + 反查它用到的字段消费者；④ 面板头部补一句「上次更新：X 分钟前 / 刷新失败」；⑤ 顺手把已经写好、但今天永远不会出现的降级横幅接上线（那句「⚠ GraphQL 配额已耗尽，已切换 REST 通道」的文案和渲染都在，只缺上游给它一个字段）。

你会感觉到

切回来时先看到旧数据、一两秒后闪一下新差异——这正是今天的行为，只是现在它真的会发生，而不是「等 60 秒恰好撞上那一拍」。另外多了一句「上次更新于 XX:XX」，你终于能一眼看出「是没变」还是「没刷」。

代价

你在看 A 的时候，B 是旧的（切回去才更新）。这句诚实提示必须一起做，否则我们只是把「刷太多」换成「静默地旧」。另外「同时只能看一个」是你的使用习惯，代码里要用一个「最多允许 2 个活跃工作区」的硬上限兜住，不能当成假设。

C

出口闸版：在 B 之上，把「不会越线」变成代码保证

B + 3～5 天

怎么跑

B 的全部内容照做，再加一道闸门：所有出去找 GitHub 的调用都从这一个地方过。闸门里区分两种调用——你点出来的（刷新、翻页、点开票、发评论）永远放行；插件自己发起的（探测、重建、链、命名守护）从一份预算里取额度，取不到就把这次推迟（不是失败，界面照旧显示手上的数据）。闸门每分钟读一次配额接口（这个接口本身不扣配额，实测确认），并且只允许插件用掉剩余的 35%——因为剩下的要留给你的 agent。

分三档降级

档位触发自动做什么
绿额度充足按 B 的节拍正常跑
黄已用掉六成以上正在看的那个工作区的探测放慢到 2 分钟；其余后台刷新全停
红已用掉八成五以上，或已经撞过一次限流自动刷新全停，只留你手动点；面板上明说「配额紧张，自动刷新已暂停」

每小时

绿档下与 B 同量级（REST 5% ｜ GraphQL 18%）。它买到的不是更省，而是无论以后加什么功能、谁写了新的调用点，都不可能越过上限——新功能自动继承这道闸。

代价

多了一层间接：排查问题时要多看一眼闸门的日志；实现量最大，而且要改到所有调用点。好处是从此不必再靠「我们算过了」来安心。

D

按需版：零轮询，只在你看和点的时候取

最省 1～2 天

怎么跑

把定时刷新整块拿掉。只在三种时刻取数：切进一个工作区、你手动点「更新」、你自己在面板里写完票。

每小时

REST ≈ 100 次（2%） ｜ GraphQL ≈ 200 点（4%），几乎全是切换与点击产生的。

你会感觉到

省钱省到你察觉得到：agent 在你看着面板的时候新建了一张票，你不点「更新」就看不到它；「可接 / 阻塞 / 已认领」这些数也会停在上一次你点过的时刻。

代价

面板从「自动跟上远端」降级成「手动取数」。切进来的自动刷新还是会做（这一条不能省，否则切换体验直接坏掉），所以真正失去的只是「边看边变」这一条。同样必须配「上次更新于 XX:XX」的提示，否则你分不清「没变」和「没刷」。

第四部分不管选哪个，这三件事都建议做

一、把失败退避补上（今天完全没有）

现在无论失败多少次，探测都是固定 60 秒、检查链都是固定 8 秒接着打。代码里其实已经写好了「连续三次失败就熔断五分钟」这套常量，但它们没有任何调用方。接上去，一条命令的事。

二、把「旧」和「失败」说出来

今天只要手上还有一份旧数据，取数失败就是一个字都不显示：面板照旧画，你分不清「远端没变」和「半小时没刷上」。这不是刷新机制的问题，是它必须配的一半。做法很小：面板头部一句「上次更新于 XX:XX」，失败时那句变成「刷新失败，正在重试 / 已暂停」，再把已经写好却永远不出现的降级横幅接上线。

三、给检查链一个更像人的节拍

环境检查不是实时数据：登录态、仓库可达、技能有没有装，一分钟之内不会变。让它在「切进来」和「你点重新检查」时各算一次，再给一条退避（8 秒 → 30 秒 → 2 分钟 → 5 分钟封顶，有进展就回快档）。这一条单独就能把最坏情况从「每工作区 2,250 次/小时」压到一两百次。

第五部分怎么证明它真的没超限

「不会超限」这句话，如果只是我们俩算出来的，就还是一次信心。三件小事能让它变成可查的事实：

  1. 节拍只留一份真源，并给它配一条门禁测试。把所有「几秒一次」的常量继续收在契约层那一处（今天已经是这么做的），再加一条测试：按常量算出「最坏情况下每小时的调用数」，断言它低于预算。以后谁改快了节拍，测试先红。
  2. 每次刷新落一行账。记下这次是探测还是重建、花了多少点、当前剩余多少。按仓库已有的日志纪律做成「只在打开调试开关时记」的那一档，不占常驻名额。
  3. 真机对账一次。开 10 个工作区、来回切 20 次、看 10 分钟，用 gh api rate_limit 前后取差（这个接口不扣配额）。只要实测用量低于我们算的两倍，这套设计就算成立。

我的建议：选 B。它一次把三件事同时解决——用量不再随工作区个数增长、单价减半、切换体验反而更确定；改动集中在四五个地方，两三天能落地。

如果你希望「不会超限」从此是代码保证、而不是每次改动后重新算一遍，那就选 C（多三到五天）。如果你现在只想先把最坏情况按住、别的都先不动，选 A；如果你其实很少盯着面板看变化，选 D 最省。

第六部分你只需要回一个字母

四个方案都已经内部定好了所有细节，你不需要在方案里再拍任何一个点。回 A / B / C / D，我就把它写成能开工的规格（含每个文件的改动点与验收清单）。如果你想要「先做 A 止血、随后接 B」，也可以直接说 A→B，那是最省心的顺序。
