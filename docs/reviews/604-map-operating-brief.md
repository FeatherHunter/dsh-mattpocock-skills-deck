这份文件写给「被派去执行 #604 这张地图下某一张子票」的代理。每张子票开工前先读这份，再读那张票的正文。

仓库：`D:\dsh-plugin\dsh-mattpocock-skills-deck`（GitHub 上是 `FeatherHunter/dsh-mattpocock-skills-deck`）。

## 先读这几份

1. 本仓库根目录的 `AGENTS.md`（提交信息规范、日志埋点纪律、文字要求）。
2. 根目录的 `CONTEXT.md`（本仓库的词典，写文字时只用里面已定义或此前已说清的词）。

## 硬规则

- **先认领再动手**：`gh issue edit <号> --add-assignee @me`，这是本票的第一次写操作。没认领不算开工。
- **文字标准**：所有写下的字（对话回复、issue 正文与评论、Markdown 文档、代码注释、提交信息）以「从没看过前文的人第一次读就能准确看懂」为准；不许用只有本次会话才懂的简称或比喻；新概念要用一整句平实的话说清。
- **提交信息**：中文完整句子，说清「改了什么、为什么改」，标题至少 10 个字。见 `docs/agents/commit-convention.md`。
- **写 issue 正文**：正文先写成文件（文件里必须是真实换行，每个 `## 章节` 独占一行，段落间留空行，文件不以不可见字符开头），再走脚本写回：
  `node "D:\dsh-plugin\dsh-mattpocock-skills-deck\scripts\fix-issue-body.mjs" --issue <号> --body-file <绝对路径> --repo FeatherHunter/dsh-mattpocock-skills-deck`
  脚本回包里 `ok` 为真才算写完。不要把正文拼进命令行，不要把换行写成字面的 `\n` 两个字符。
- **日志埋点纪律**：动了跨进程/跨模块调用、新增宿主接口方法、面板打开与刷新读数据展示的链路、内存或磁盘缓存、定时触发的活（轮询、延迟扫、防抖刷盘）这五类东西之一，就必须同步加日志记录点；常驻/按需的判定与字段白名单见 `docs/design/335-logging-contract.md` 与 `research/489-appendix.md`；名单增删要同步对照表，并让 `tests/verify-log-fields.js`、`tests/verify-log-guards.js`、`tests/verify-log-count.js` 三项检查通过。
- **不动别人家**：`D:\ilife`、`dsh-im-companion`、`dsh-opencode-palette`、`dsh-prompt` 只读参考，一律不改。DSH 本体（`resources\app.asar`）不改。
- **量了才算数**：本图所有结论必须能指到实测数字。本地对照实验的绝对毫秒数不能当真机数字用，只能搬「改前 / 改后的倍数」与「结果等价性」两个结论。量不到的地方如实写「没量到」，不要用推断填空。

## 收尾动作（每张票都要做）

1. **按进度契约更新票正文**：正文末尾保留一节 `## 进度：N%`——这一行独占，与后面的内容之间**空一整行**，再写 `下一步：……`（不要写成紧挨着的两行，也不要把换行写成字面的 `\n` 两个字符）。到 95% 时必须写明「待确认什么」；没被确认过就不许关闭这张票。确实全部达成、且验收条件逐条满足，才写 100% 并关闭。
2. **关闭时留结论评论**：`gh issue comment <号> --body "..."` 写清「决定了什么 / 事实是什么」，再 `gh issue close <号>`。答案不写进正文，正文只放进度。
3. **不要改地图 #604 的正文**：地图的「Decisions so far」「Not yet specified」由总工程师（派你的那个会话）统一维护。
4. **跑验收命令**并如实回报：至少 `npm run test`（本仓库全量校验）与 `npm run build`。变红了不许说绿，也不许改验收标准来迁就结果。

## 总工程师已核验过的事实（别再重验一遍，也别把它当推断用）

下面四条是总工程师在地图上直接读代码验过的，写在这里是为了后面每一张票少走弯路。**它们是代码事实，不是实测数字**——要往票里写「影响多少毫秒」，仍然得自己量。

1. **5 秒结果缓存写了永不命中**：`src/host/tracker/snapshot.js` 里的快照缓存是拿 `createComposer()` 造出来的取数对象自己揣着的，而这个取数对象在 `src/host/sessionSnapshot.js:66-67`、`:262-263` 与 `src/host/sessionRefresh.js:31-32`、`:235` 四处都是**每次请求现造一个**，上一份随请求结束被丢掉。所以 `snapshotTtl: 5000` 这个缓存在真机上永远没命中过。
2. **同一层的日志上下文也没接上**：上面那四处现造取数对象时只传了 `{ snapshotTtl: 5000 }`，没把 `logCtx` 传进去；`snapshot.js:113-118` 里「未命中记常驻、命中记按需」的分支因此始终处于静默状态。
3. **子进程那条路的记录点缺的是一个函数**：`src/host/platformChannel.js:173` 的 `detectionExec` 是全部外部命令的唯一出口；而 `src/host/tracker/backends/github/client.js:20-26` 的记录点只在操作上下文的 `ctx.logEvent` 是函数时才写一行，`sessionSnapshot.js:65`、`:261` 与 `sessionRefresh.js:30`、`:234` 造出来的操作上下文只有 `cwd / platform / fs / exec` 四个字段——缺的正是这个函数。
4. **`logCtx` 这一圈本身是通的**：`src/host/index.js:75` 定义了 `logCtx = { fire, isEnabled }`，并且逐个传给了平台层、仓库键、议题列表、探测链、会话快照等模块。所以补记录点不需要新建管道，只需要在造操作上下文那几处把已经拿到的记录能力接进去。

**还没验的（谁做谁验，别照抄）**：三个扫描器（客户端每 60 秒探测、快照校验、命名守护）各自扫各自的、命名守护那次不带增量窗口全量拉、一串没人调用的死路径——这三条只有 #607 正文里的说法，没有代码行级复核。

## 作业时容易踩的坑（2026-09-12 由 #605 的两路审查带回并核实）

1. **`npm run build -- --no-sync` 跳过的正是「同步到已装插件目录并做 hash 校验」那一段**（见 `scripts/build.mjs` 里对 `--no-sync` 的判断）。所以：
   - 为了不打扰并行作业而用 `--no-sync` 是允许的，但**不许把它当成「构建验收通过」**，必须在结论里写明「这一次没覆盖同步与 hash 校验」；
   - 要真正验证同步与 hash 校验，就在**没有并行作业**的时候跑不带 `--no-sync` 的 `npm run build`，并把「profile 同步 hash 校验通过」那行原文记下来。
2. **判断文件是否真的被改动，要用 `git diff`，不要用 `git status`**。在独立工作区跑完构建后，`git status` 会把十几个派生文件报成已修改，但内容逐字节相同（`git hash-object` 与库里的 blob 一致、CRLF 计数为 0）——那是文件时间戳缓存造成的假阳性，不是真改动。
3. **写提交信息走「先写文件、再 `git commit -F <文件>`」**，且文件必须是**不带 BOM 的 UTF-8**。本机用 PowerShell 的 `>` 重定向会默认写入 BOM，直接落进提交信息就会让提交以不可见字符开头（2026-09-12 的提交 `2726a80` 就是这样，已核实首三字节是 `EF BB BF`）。检查办法：`git cat-file commit <哈希>` 读出来的标题，首字节不该是不可见字符。
4. **跨票的待提交文件不要长期放在共享暂存区**（`git add` 了却不提交）：别人一次不带路径限定的 `git commit` 会把它顺手带走。
5. **性能数字有测量口径问题**：测点本身会改变耗时。基线提交 `e6c871c` 里就带着上个会话的三处临时测点，所以拿它当「改前」时必须保证**改前与改后用的是同一套测点口径**，不能把它的数字当成「没装测点时的真机绝对数」。
6. **真机测量的「改前」基线，要从不含其它票未提交改动的树上取**（另开独立工作区，或先把改动收起来），因为主工作树经常同时有另一张票在改同一批文件。
7. **不许起交互式命令**（`npm login`、`npm publish`、无 `--yes` 的 `npx` 等）：它们会永久挂住，而且会锁住整条 npm 链路，把同机其它作业一起拖停（2026-09-12 上午真发生过，一个 `npm login --auth-type=web` 把工作区拖停了二十多分钟）。
8. **`tests/smoke-render.test.js` 里那行 `FAIL <组件>(src) 渲染异常: DswsCtx is not defined` 是已知限制、不阻塞**：源码文件被直接渲染时缺少构建期注入的上下文，脚本把它归到非阻塞段，进程仍以 0 退出。看到它不要当成新缺陷去查，也不要据此改门禁。

## 对抗式审查的尺子

每张票交回来后，总工程师会派两个独立的审查代理复核打分，一个查「规矩与证据」，一个查「目标与等价」，两边都不知道对方看了什么。审查时会按下面这把尺子挑刺，所以交活前你自己先按它自查一遍：

**「规矩与证据」那一侧会挑的刺：**

- 结论有没有实测数字支撑？说「快了」的地方，改前与改后各自的数字在哪、怎么量的、能不能重跑出同样的数？只说「代码上应该更快」不算。
- 本地对照实验的绝对毫秒数有没有被当真机数字用？本图只允许搬「改前改后的倍数」与「结果等价性」两个结论。
- 量不到的地方有没有如实写「没量到」，还是用推断填空？
- 该加的日志记录点加了没有？加的事件是常驻还是按需，判定依据是 `docs/design/335-logging-contract.md` 第 3 章哪一条？字段有没有超出 `research/489-appendix.md` 的白名单？名单对照表同步了没有？三项检查是否真的跑过、结果如何？
- 有没有碰不该碰的东西：别的仓库、DSH 本体、地图 #604 的正文、同一卷里别人的改动？
- 进度节写的百分比与票的实际状态对得上吗？「待确认」的事有没有在 95% 时写明？关闭一张票的前提是验收逐条有证据，不是「做完了」这句话。

**「目标与等价」那一侧会挑的刺：**

- 这票声称解决的问题，真的被解决了吗？还是只改了一处写法、把症状挪到了别处？
- 改写渲染或取数逻辑的地方，有没有做逐行等价对照（改前改后对同一份输入产出同一份结果）？「看起来没问题」不算证据。
- 改动的尺度守住了吗？宿主取数走结构性收敛，客户端渲染走保守单点改法（客户端已经证明找准一处写法就够）。超尺度的改动要单独说明理由。
- 这票的产出能不能让下一张票照着开工？如果下一张票需要的关键事实（调用次数、耗时分布、触发链归属、复现方式）没给出来，这票就没做完。
- 验收命令（`npm run test`、`npm run build`）是不是在同一个工作树上真跑过？变绿的原因是不是被改过的检查标准？

**打分**：两侧各自给 0–10 分，并逐条列出「不成立的地方」与「必须整改才能放行的地方」。总工程师按两份报告决定放行、整改还是返工。

## 给总工程师的回话格式

做完后回一段简短的中文报告，只写这几项：

- 票号与标题、结论一句话（做完 / 没做完 / 卡住）。
- 本次提交的 commit 短哈希与标题。
- 改了哪些文件（分类列，不要贴 diff）。
- 跑了哪些命令、结果如何（逐条写命令与结论）。
- 实测数字（哪些是真机数字、哪些是本地对照实验的倍数）。
- 票正文最后的进度百分比，以及票是否已关闭。
- 有没有留下未决事项、需要人拍板的事、或你判断属于「极重大决策」的事。
