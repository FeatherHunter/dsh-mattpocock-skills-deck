2 · 根因

D:\ilife\packages\plugin-bill-ilife\dist\client.js 里是未转译的 ESM 源码 （裸 import / export），而 DSH 要求客户端产物是加载器包装形态。 这个文件被拼进了所有插件共用的一条 bundle，于是整条脚本在解析阶段失败，一个插件都注册不上。

错在哪：构建脚本只做了类型编译，没有打包。

"scripts": {
  "build": "tsc -b"        ← tsc 只产出「给打包器读的 ESM 源码」，不产出 DSH 要的包装

4 · 为什么一个坏文件能让全部插件失灵

DSH 把所有插件的客户端拼成一条 bundle，交给一个普通 <script> 标签加载。本次那条是 16,386,664 字节（约 16.4 MB），包含 61 个模块。

普通脚本在执行前要先整体解析。只要有一处语法不合法，整份脚本一句都不会执行——于是每个模块开头的 window.__ModuleLoader__.load({...}) 都没跑到，加载器就逐个报告「没注册上」。

这也解释了为什么报错点名的是无关的包：加载器按顺序检查哪个模块没注册，第一个没注册上的就被写进错误里。它不代表那个包有问题。

6 · 正确格式的模板

来自你已经做对的 D:\ilife\packages\plugin-calorie。

产物长这样（plugin-calorie\dist\client.js 开头）

window.__ModuleLoader__.load({
	id: "dsh-calorie",
	factory: (require) => {
		var module = { exports: {} };
		var exports = module.exports;
		…

配置文件（plugin-calorie\tsdown.config.ts，要点照抄）

const PLUGIN_ID = 'dsh-calorie';                 // ← 换成本插件包名

const CLIENT_EXTERNALS = [
  'react', 'react/jsx-runtime', 'react-dom', 'react-dom/client',
  'cordis', '@deepseek-ai/dsh-client-ui-slots',
];

const clientBundle = {
  entry: { client: 'src/client.ts' },             // ← 指向本插件的客户端入口
  outDir: 'dist',
  format: 'cjs',
  platform: 'browser',
  dts: false, sourcemap: true, clean: false,
  define: { 'process.env.NODE_ENV': JSON.stringify(process.env.NODE_ENV ?? 'production') },
  deps: {
    neverBundle: [...CLIENT_EXTERNALS],
    alwaysBundle: (id) => !CLIENT_EXTERNALS.includes(id),
  },
  outputOptions: {
    entryFileNames: 'client.js',
    banner: 'window.__ModuleLoader__.load({ id: ' + JSON.stringify(PLUGIN_ID) + ', factory: (require) => {',
    footer: 'return module.exports; } });',
    intro: 'var module = { exports: {} }; var exports = module.exports;',
    codeSplitting: false,
  },
};

脚本与依赖

{
  "scripts": {
    "build": "npm run build:host && npm run build:client",
    "build:host": "tsc -b",
    "build:client": "tsdown"
  },
  "devDependencies": { "tsdown": "0.22.14" }
}

plugin-calorie 还带一个 tsconfig.client.json（composite:false、noEmit:true，include 列客户端相关文件），用于 typecheck，不是产出必需，但建议一起抄。

  1. 先只修 plugin-bill-ilife 一个，别的先别动。
  2. 按第 6 节加 tsdown.config.ts（改 PLUGIN_ID 与 entry）、按需加 tsconfig.client.json、改 package.json 的脚本与 devDependency。
  3. 跑 npm run build。
  4. 验收（必做）：打开 dist\client.js，开头必须是 
    window.__ModuleLoader__.load({
	id: "dsh-bill-ilife",
	factory: (require) => {
    而不是 import / export。体积也应从约 840 字节涨到明显更大（因为把依赖一起打进产物）。
  5. 把重建后的包放进 web profile 的 node_modules，重启 DSH，再打开页面。

8 · 本文中我犯过并已纠正的错误

为避免误导，把我自己走过的弯路也记下来。

我曾说实际怎么发现
「是 @deepseek-ai/dsh-client-ui-deliverables 的包坏了」 那个包本身是正确的 CJS 包装；坏的是它后面紧跟着的一段存根 读组合里该模块区间的边界，看到工厂已经正常 return module.exports 关闭
「r.create is not a function」 是我测量脚本造的假象：我的探针把 window.__ModuleLoader__ 整个换成了只有 load 的桩，覆盖掉了引导脚本提供的带 create 的版本 改成「引导脚本跑完后再包一层记录」，不再替换那个对象，错误就消失了
「是浏览器缓存过期导致的」 不是。用真页面复测，页面级错误明确是语法错误 用真实令牌打开真页面并捕获 pageerror

另外需要说明的边界：本次没有对 D:\ilife 做任何修改，只做了只读检查与在 .scratch/ 下生成证据文件。
