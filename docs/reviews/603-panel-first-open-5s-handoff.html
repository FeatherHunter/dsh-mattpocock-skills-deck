1 · 现象与用户原话

点状态栏的 MattSkills 胶囊按钮打开右侧面板，页面刷新后的首次打开要等 5~6 秒，面板才出现。用户的原话依次是：

「每个会话窗口第一次打开右侧面板时要 7~8 秒才能看到完整的右侧面板，但是后续打开就不卡了」

「为什么 better sidebar 打开其他的组件页面很快，就是一瞬间」

「从视觉效果来看，这个所谓的『关掉』，其实是把整个侧边栏给收进去了。我再点开之后，感觉这个侧边栏其实都没有关掉过。所以这时候我把它『关掉』再点开，一瞬间就能看见了」

其中第三条是最有价值的观察：它直接说明「关掉」并不卸载组件，只是收起。由此推断出「首次挂载才有成本、之后就没有」，与后面的实测数字完全吻合。

2 · 已确证的事实（附实测数字）

全部数字来自插件自己的日志（~/.dsh-mattskillsdeck-cache/logs/<日期>.log），由本次临时加入的测点写出。测点位置见第 8 节。

2.1 三种情况的耗时对照

场景点击 → 面板可见说明
页面刷新后的首次打开5668 ms / 5640 ms出现了两次，稳定
页面已加载很久后再打开404 ms / 520 msDOM 已在，只是显示
收起再打开（同一页面内）一瞬间（用户体感）组件未卸载
同一次打开里的第二次渲染14 ms / 26 ms比首次快约 200~400 倍

结论一：成本是「首次挂载」的一次性成本，不是每次打开都有。

2.2 那 5.6 秒花在哪里（分段实测）

日志里那一行是这样的：

{"event":"panel.open","fields":{"mode":"dock-render+4548ms/dockSync+0ms,compute+0ms,tabsRow+0ms"}}

含义：从进入面板组件的渲染函数算起，到整棵组件树建完并提交为止＝4548 ms；而该函数体内部三处记时刻的位置，相对渲染起点全是 0 ms。

测的是什么结果排除掉什么
面板组件的渲染函数体（含 compute 分组计算、选项卡行、工作区同步）0 ms不是插件的渲染代码慢
内层 requestAnimationFrame 回滚看到的时差5636 ms时间确实花在组件函数之外
这段时间里的宿主调用只有 wf.cwd＝0 ms不是在等数据
夹住 better-sidebar 的三个点（交给它之前 / 注册完成 / 开签返回）全部 0 ms不是它的注册或开签慢
快照水合source=memory，0 ms不是水合慢

结论二：那 5.6 秒落在「组件的渲染函数跑完之后、第一帧画出来之前」这一段。已排除的三块是：插件的渲染代码、宿主取数、better-sidebar 的开签。

2.3 为什么其他面板不慢

用户观察到「better-sidebar 打开别的面板一瞬间」。机制上说得通：开签是在点击处理器内部同步跑完的，谁的重内容塞在那一次同步渲染里，谁的浏览器就没机会先画第一帧。我们的面板客户端产物 1 MB、首次要建几千个 DOM 节点，正是这种情况。

3.2 前端这一笔（未提交，本次新做）

改动：面板侧边栏先只渲染一个空壳，等浏览器把这一帧画出来之后再挂载真正的内容。

落点：src/client/kernel/router.js 里注册给 better-sidebar 的那个组件（DeckSidebarTab）。

用户实测反馈：「体验到了，是立即出了一个壳子是黑色的，大概 6 秒后出了内容。」——外壳立即出现，改法按预期生效。

这笔改动的代价必须写清

总工作量没有减少，还是那 5.6 秒。改的只是顺序：把「点击后干等 6 秒」换成「外壳先出来、内容随后填」。用户的体感因此改善，但底层成本一分没省。若要真正把 5.6 秒降下来，必须继续第 6 节的调查。

5 · 已被实测排除的方向（别重查）

曾怀疑的方向实测结果怎么排除的
宿主取数慢（等网络）排除同一时刻宿主只有 wf.cwd＝0 ms；快照水合 source=memory
better-sidebar 的注册或开签排除夹住它的三个点全部 0 ms（beforeTab/ensureDone/tabReturned）
面板组件的渲染代码（含 compute 分组计算）排除渲染函数体内部三处记时刻全是 0 ms
懒加载的客户端分块排除插件客户端是单个 bundle，代码在各面板接入前就已加载
浏览器缓存导致的旧版本排除真页面捕获到的页面级错误是语法错误，不是缓存问题
标签折叠（fitAllTags）等强制重排量过但不是主因早前独立测过：636 行标签折叠约 158 ms，量级差 30 倍
挂载副作用（同组件里排在前面那些 effect）排除分段里 dockSync／compute／tabsRow 全 0 ms

6 · 还没查清的：那一帧在建什么

这是接手后该继续的地方。已知那 5.6 秒发生在「组件函数跑完 → 第一帧」之间，但还不知道它具体在建什么：是建 DOM 节点、是算布局、还是样式重算。

已经放好的下一步测点：在 DockSync.js 的日志行里，会额外带上首帧的节点数与嵌套深度：

{"mode":"dock-render+5636ms/dockSync+0ms,compute+0ms,tabsRow+0ms nodes=NNNN depth=NN"}

判读与下一步：

节点数的量级说明该往哪走
几千个以上 首屏一次把所有分组都画了，没有虚拟滚动或分页 减少首屏渲染量（见 7.1）。这是治本，但改得多、风险高
很少（几百以内） 时间不在建节点上，而在布局或样式重算 方向要换：去查面板容器的样式（宽度动画、filter、大面积重排）与页面整体布局

已知规模参考：该工作区快照里有 505 条 issue、48 张地图。带 tags 的表格一次建出来的节点数容易到几千。

7 · 下一步的候选做法与代价

7.1 路线 A：减少首屏渲染量（治本）

把面板首屏从「一次画完所有分组」改成「先画可见部分、其余随后补」。
收益：真正把这 5.6 秒降下来。代价：动渲染逻辑、要处理滚动/展开的加载与状态，改得多、回归风险高。

7.2 路线 B：把成本挪到空闲时间（已部分落地）

本次已经做了「先出空壳、内容随后」。可以再往前一步：页面加载完、用户还没点的时候，在空闲时预热渲染一次，让用户第一次点击时 DOM 已经在了。
收益：点击即出内容。代价：把「点击时等」换成「页面加载后默默占几秒 CPU」，可能让刚加载完的页面卡顿。需要配 requestIdleCallback 之类的空闲检测，否则等于把问题搬了个地方。

7.3 路线 C：先查清那一帧在干什么，再决定

推荐先做这个。拿第 6 节的节点数，再花一轮确认成本构成，然后才在 A 与 B 之间选。理由：前面已经因为「没量准就下结论」走过两次弯路（见第 9 节），先量清楚比先动手便宜。

9 · 我在本次调查中犯过并已纠正的错误

写下来是为了让接手的人知道哪些弯路已经走过，不必重跑。

我曾下的结论实际怎么发现
「慢在 compute(s) 分组计算」 错：函数体内三处计时刻全是 0 ms 加了分段测点，把渲染体内部逐段量了一遍
「慢在画那几百行」 错：同一次打开里第二次渲染只要 14 ms 对比首次与后续渲染的耗时，差 200~400 倍
「是 better-sidebar 的问题」 错：夹住它三点全 0 ms 在插件侧插夹子，把它包在中间量
「是浏览器缓存过期」 错 用真实令牌打开真页面，捕获到的页面级错误是语法错误
报出一个 r.create is not a function 是我测量脚本造的假象：探针把 window.__ModuleLoader__ 换成了缺 create 的桩 改成「引导脚本跑完后再包一层记录」，不替换那个对象

方法上的教训：本次凡是有价值的结论，都来自「把时间夹在明确两点之间量出来」；凡是我出的错，都来自「量到一半就下结论」。接手时请沿用前者。
