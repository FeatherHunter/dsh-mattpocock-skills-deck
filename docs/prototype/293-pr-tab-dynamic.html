原型 #293 · 顶部动态 PR 页签

归属地图 #288 GitHub 后端 PR 入口可行性 · 本票验证 动态显隐、折叠、空态、后端切换 四点。依据 #292 交互定版（独立 PR 页签、能力门控、空结果走空态、回退为列表内混入）与 #290 前端可行性（放弃硬编码、改为能力门控动态列表）。本文件为一次性验证品，只供讨论拍板，不合入生产代码。

控制区：后端切换 / PR 数据状态 / 宽度

先切后端看页签显隐，再切数据状态看空态与加载态，最后拖宽度看折叠。三组控制互相独立。
能力门控规则（按 #292 与 Notes 立场）：只有后端返回了 PR 列表能力才显示 PR 页签，不是写死后端名字；空结果与加载失败都显示空态，不隐藏入口；切到无能力后端时若正停在 PR 页，自动回到列表页。

四点验收：怎么算通过

按 #293 票面逐条对照，在本文件里亲手点一遍即算验收。
  • 动态显隐通过： GitHub 下有 PR 页签；切到 GitLab 或 Markdown 时页签消失且自动回到列表页；切回 GitHub 时恢复。日志会记录每次显隐。
  • 折叠通过： 把宽度从 640 拖到 280，页签按优先级从大到小逐个收起为纯图标（先收环境检查，再收技能，再收 PR），动作按钮最后才收；拖回宽屏时逐个恢复，全程无换行、无横向滚动条。
  • 空态通过： 空结果显示“还没有拉取请求”空态；加载失败显示“PR 列表加载失败”空态并带重试按钮，两者都不隐藏入口。
  • 后端切换通过： 在 PR 页停留时切后端不白屏；门控信号行实时显示当前后端与能力值。

给 #294 总体裁决的输入

原型只回答体验是否成立，不回答数据形状与契约增量。
问题原型给出的答案
独立页签是否放得下放得下。新增一页后贪心折叠仍稳定，优先级 5 插在列表与技能之间，窄屏回退为纯图标。
能力门控是否可用可用。以后端是否返回 PR 资源为准，不写死后端名字；切换工作区跟随选择变化自动显隐。
空态是否误导不误导。空结果与失败都保留入口，只换内容区，分得清“无能力（无页签）”与“有能力但无数据（有页签加空态）”。
回退方案若独立页签被否，列表内混入仍可作为回退，但本原型不展开混入形态。
未回答、留给 #294 的事：PR 数据最终形状（复用工单加扩展字段还是新增实体）、契约与快照最小增量清单、多后端演进是否复用同一门控。
