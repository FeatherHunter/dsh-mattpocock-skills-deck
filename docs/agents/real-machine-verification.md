# 版本真机验证清单

每个要发布的版本有一张 `[真机验证] <版本号>` 票，下面简称**清单票**。开发完成的票可以没有经过真机验证就关闭，但关闭前必须把「这次改动要在真机上验什么」登记到清单票；版本发布前，清单票里的场景必须全部验完（通过，或豁免被接受），清单票必须已经关闭。发布脚本会检查这件事，没关就发不出去。

一句话分工：**开发票负责做完并登记场景，清单票负责攒场景和执行验证，发布前检查负责拦。**

## 为什么要把验证集中到一张票

- 一张开发票的「做完」写的是代码层面的验收条件，不等于它在真机上真的有效果。两件事分开记，才不会用「门禁全绿」冒充「用户看得见的效果已经对」。
- 验证记录散在各开发票的评论里，发布前没人能一眼说出「这版还差什么没验、证据在哪」。清单票把这些集中在同一处，发布前逐个核对就行。
- 发布前检查是脚本自动跑的，不依赖谁记得。忘记登记场景，清单票就关不上；清单票没关，发布就中止。

## 名词

- **来源票**：产生「需要真机验证的东西」的那张开发票，可能是 bug、新功能或改造。
- **清单票**：`[真机验证] <版本号>`，一个要发布的版本一张。标题里的方括号前缀是它的身份标志，不靠标签识别。
- **验证主持人**：负责发起验证批次、执行验证、记录结果、维护清单票正文的人。发布准备阶段指定，可以由同一个人或 AI 担任。
- **批次**：一次集中验证。几个版本的改动攒到一起验，或者每版单独验，都算一批。
- **场景块**：清单票里的一条固定格式评论，由一张来源票产出一条或几条场景。
- **豁免**：某条来源票的改动经判断不需要单独做真机验证（例如纯文案修改），按格式登记并由主持人接受，算作「已处理」，但不算「通过」。

## 一、开发中：来源票关闭前登记场景

来源票可以没有真机验证就关闭，这样做的前提是把场景登记好了。关闭前做三件事：

1. **找本版清单票**：用 `deck_issue_list` 搜 `[真机验证]`。有就用；没有就按 [清单票模板](checklist-issue-template.md) 建一张，并先确认要发布的是哪个版本号（版本号还没定就先用占位标题，见模板里的说明）。
2. **在清单票发一条场景块评论**。格式见下一节。同一张来源票只有一条场景块；后续补充场景，在**新评论**里追加，已经写下的场景编号不改、不复用。
3. **关闭来源票时写明去处**：关闭评论里写一句 `真机验证场景已登记到 #<清单票号> 的「场景块：<来源票号>」`，读票的人能直接跳到验证记录。

场景明细为什么写在评论里而不是清单票正文：正文只能有一个写者（主持人），多人同时改会互相覆盖，还会撞上正文 60KB 的上限；评论一条一个作者、一条一个时间，只追加不覆盖，天然不会冲突。正文只放规则、总览和批次记录。

### 场景块格式

标题固定写：

```text
## 场景块：<来源票号> <一句话说明这张票要在真机上验什么>
```

正文按下面的结构写，没有内容的段落写「无」，不要留空段：

- **前置条件**：环境、数据、后端选择、网络状态等，开始验证前要准备好的东西。
- **操作步骤**：编号步骤，写清人手动做什么。
- **预期结果**：做完以后看得见的现象。
- **通过标准**：什么算通过、什么算失败。有硬指标（必须满足）和目标值（期望达到）的，分开写；例如「网络恢复后不点任何按钮，黄条在 5 分半内自消」里的时间就是目标值，硬指标是「一定会自消」。
- **证据看点**：要留下的截图、日志或接口返回，以及看哪个字段才能判定通过。

场景编号写成 `<来源票号>-01`、`-02`……。建议每张来源票写 1 到 3 条，只写用户看得见的变化；纯内部重构可以只写一条「行为与改动前一致」的抽查。编号一旦写进清单票正文就不再改动；作废的场景标「作废」并说明原因，编号不复用。

登记时先看来源票是不是已经在真机上验过了。验过的（来源票评论、走查记录或发布记录里能查到证据）场景状态直接写「已验证」，并在清单票场景总览的备注里写清证据出处——哪张票的哪条评论、哪份走查记录、截图或日志在哪里。已验证的场景不再排进验证批次；找不到证据的一律按「待验证」排进批次，不要凭印象标「已验证」。

示例：

```text
## 场景块：1474 断网恢复后黄条自己消失

- 前置条件：装有候选版本的 DSH，工作区已绑定 GitHub，网络先断开（例如把代理指向没人监听的端口）。
- 操作步骤：1. 打开该工作区的 MattSkills 面板；2. 确认出现「登录状态暂时确认不了」的黄条；3. 恢复网络，不点任何按钮，面板保持可见。
- 预期结果：黄条在退避档内自己消失；链快照里 `gh:authed` 与 `gh:repoAccess` 从 pending 变成 done。
- 通过标准：硬指标是不点按钮一定自愈；目标值 2 分钟内自消，最坏约 5 分半。
- 证据看点：黄条前后截图；日志里 `chain.event reason=auto-retry` 与 `chain.flow request reason=auto-retry`。
```

## 二、工具与环境

真机验证用的工具台在 [scripts/real-machine/README.md](../../scripts/real-machine/README.md)（#1645 把它从临时目录提升进了仓库）：复制隔离 home、造工作区、起停实例、抓日志与截图、冻结候选、清理批次产物，每条都是一条命令。这一节只写与规则有关的部分：环境和产物放在哪、验完怎么清、怎么确认验的是哪个候选。

- **命令怎么跑**：从仓库根目录跑，统一写法是 `node --import ./scripts/ts-hook.mts scripts/real-machine/commands/<命令>.mts <参数>`。成功时 stdout 只有一段 JSON；失败时退出码非 0，stderr 用一句中文说清原因。完整参数与输出字段看每个命令文件的开头注释。
- **工作根**：默认是仓库里的 `.scratch/verify-run/`，这个目录被版本库忽略，批次产物不会进提交。换位置用环境变量 `DSH_VERIFY_WORK_ROOT`，或单条命令的 `--out` / `--batch` / `--root`。工具只往工作根、系统临时目录和命令显式给的目录写，写别处会被拒绝。
- **启动**：每个实例用自己复制出来的 `DSH_HOME`、独立启动目录、独立 `USERPROFILE`/`HOME`，端口用 `--port 0` 交给系统分配，所以多开不会抢端口。冷启动到打印访问地址约 10 到 18 秒，页面可交互再等约 6 秒。
- **浏览器窗口**：判断「浮层会不会被别的界面元素盖住」「提示贴到屏幕边缘会不会越界」这类空间问题时，必须有头、必须真全屏：页面视口与外框（`innerWidth`/`outerWidth`、`innerHeight`/`outerHeight`）都要等于 `screen.width`/`screen.height`。固定视口（例如 1600x1000）或无头窗口只看得到「这个尺寸下长什么样」，不能拿来判定遮挡与越界——2026-10-29 验 1655-01 时，Playwright 的 `--start-fullscreen` 被忽略、窗口只有 1083 像素宽，再用 `setViewportSize` 强设页面视口，截图看起来铺满屏幕，据此得出的「浮层被右侧面板盖住」结论后来被真全屏复核推翻。工具台已把这层保护做进 `lib/browser.mts`：`openInstance(url, { headless: false })` 会自动切真全屏并核对尺寸，切不成直接报错，全屏测量写进 `page-diagnostics.json` 的 `fullscreen` 字段；细节见工具台 README 的「有头验证」一节。
- **三款窗口尺寸**：2026-10-29 定版，真机验证只跑三款窗口形态，定义在 `scripts/real-machine/lib/presets.mts` 的 `VIEWPORT_PRESETS`：`wide` 真全屏、`narrow` 外框宽 800 且高铺满屏幕（插件面板落在 300–359 像素、`.dsws-narrow` 生效）、`short` 外框宽铺满屏幕且高 600。用 `applyViewportPreset(page, '<编号>')` 设置窗口并核对插件真的进了那一支布局，对不上直接抛中文错误（调用前先打开 MattSkillsDeck 面板，默认要求 `.dsws-body` 已渲染）；实测快照（窗口外框、页面视口、面板宽、窄态）写进 `page-diagnostics.json` 的 `viewport` 字段，空间类结论的证据里必须有它。窄窗是 800 不是 720：窗口宽与面板宽不线性，720 宽时宿主把右侧面板切成整宽覆盖，反而进不了插件窄态；实测映射与理由见工具台 README 的「三款窗口尺寸」一节。
- **隔离原理**：四层隔离（home、启动目录、USERPROFILE、浏览器上下文）的细节见工具台 README 的「隔离是怎么做到的」。隔离是否真的生效由 `isolation-probe` 回答：它对比真实用户设置文件在探针前后的 SHA256，没变才算通过；验证批次里要保留这条结论。
- **日志位置**：插件日志写在 `<启动目录>/.dsh-mattskillsdeck-cache/logs/<日期>.log`。用 `log-query` 按事件名、级别、字段过滤；写证据时把关键几行贴进评论，只给路径不算证据。
- **工作区注入**：无头环境点不了原生目录选择器，所以由 `seed-workspace` 直接写 home 的 `storages/workspace.json` 完成登记。验证用的工作区夹具放在批次目录里，不要放在本仓库里，否则插件会把本仓库的 git 根当成仓库身份，结论会被污染。
- **GitLab 沙箱项目**：需要 GitLab 后端时，先用 `gitlab-sandbox create --batch <批次目录> --path <group>/<project>` 在 gitlab.com 建一个带批次标记的私有空项目（记录写在 `<批次目录>/gitlab-projects.json`），再用 `make-workspace --kind gitlab --project <group>/<project>` 生成工作区：本地空仓库，`origin` 指向沙箱项目地址，工作区文件写 GitLab 后端。GitLab 的删除接口返回 202 之后延迟生效，所以 `gitlab-sandbox delete --batch <批次目录> --id <项目 id>` 会按 id 读回 `marked_for_deletion_at`，读到才算删掉；读回失败时项目 id 保留在清单里、状态标成 `delete-failed`，重跑 delete 可以补完。每批只建 1-2 个，场景验完立刻删。
- **GitLab 种子票池**：票池用 `seed-gitlab --batch <批次目录> --project <group>/<project>` 幂等种出：默认 101 张票（含 5 张已关闭）、两张地图与子票、5 个标签、指派、父子与阻塞关系。每张票正文文件头带稳定键 `<!-- DSH-SEED-KEY: … -->`（子票另带 `<!-- DSH-PARENT: <地图 iid> -->`），重跑按稳定键认回已有的，只补缺的；种好后 `<批次目录>/gitlab-seed.json` 的 `mode` 是 `read-only`，之后补种必须显式加 `--unlock-readonly`，补完自动恢复只读。免费档可能拿不到原生 `is_blocked_by` 边，命令会自动回落成正文成对两行（`Blocked by: #N` 与 `<!-- DSH-BLOCKED-BY: N -->`），验证结论里要写清实际用了哪种。B1 批次要核对票数与关系，并把 `gitlab-seed.json` 的 `stats` 抄进批次记录。
- **批次前置巡检**：每批开始前先跑 `preflight --batch <批次目录>`（写法见工具台 README 的「批次前置巡检」一节），它以一段 JSON 回执回答九项环境预检：候选包身份、隔离 home 与 profile、工作区与 git remote、glab 版本与认证、沙箱项目 id 与状态、票池数量、日志目录可写、屏幕分辨率与主屏、Node 版本。任一硬项失败退出码非 0 并逐项写清原因；全绿之前不开批。
- **证据目录**：每个批次一个目录 `<工作根>/batches/<批次名>/`，证据先落在 `evidence/` 下，再由 `collect-evidence` 生成带每个文件 SHA256 的 `evidence.json`。规则要求证据能独立看懂：评论里贴截图关键区域、日志关键行或接口返回字段，不把临时目录路径当唯一证据。
- **候选身份判据**：用 `freeze-candidate` 冻结候选，清单写在 `<工作根>/pkg/candidate.json`，记着提交、版本、包内每个文件的 SHA256 与 tgz 的 SHA256。界面里的插件脚本是宿主把多个插件合并成一次请求加载的，所以界面核对比的是「这段内容里本版的版本常量是不是期望值」，不要拿合并后的包哈希当身份（带启动期构建标识的产物每次启动哈希都会变）。
- **清理要求与上限**：用 `cleanup` 先报账、确认后再删。工作根总量建议不超过 15GB、批次目录不超过 20 个、单个批次不超过 2GB；每次批次结束、发布前、换版本重跑之前各清一次。批次里的 GitHub 工作区是源仓库的 `git worktree`，批次目录删掉之后在源仓库跑一次 `git worktree prune` 清掉失效登记。
- **从零可用**：`two-instance-smoke` 用一条命令在一个从没跑过真机验证的检出里跑通双实例冒烟（复制两份 home、造两种后端工作区、起两个实例、浏览器核对、收证据、停实例），用来证明工具台本身是好的。
- **GitLab 实例环境**：批次实例要访问 GitLab 时，用 `start-instance --instance-env-file <批次>/env.txt` 把 `GLAB_CONFIG_DIR`、`PATH`、`GITLAB_TOKEN` 传进实例进程；token 只写在环境文件里，不进命令行、批次评论、证据文件与日志。先加 `--launch-plan` 可以只看启动命令与变量名、不起进程。写法与失败行为见 `scripts/real-machine/README.md` 的「带 GitLab 环境起实例」一节。
- **GitLab 写场景直调入口**：要证明「隔离实例里能直调 deck 写工具」时，用 `deck-write --tool <工具名> --args <入参 JSON 文件> --ref <group>/<project> --workspace <工作区目录>` 按固定入参调一次 `deck_issue_create` / `deck_issue_patch` / `deck_map_link`，回执是无损 JSON（`--out` 另存一份，缺省 `tool-response.json`）；再用 `deck-readback --ref <group>/<project> --key <票号>` 直接走 `glab api` 独立读回，写与读是两条路径，读回一致才算数。缺 `GLAB_BIN`、`GLAB_BIN` 指向的文件不存在、工作区不存在或仓库标识不是 `<group>/<project>` 时退出码 3 并说明原因；工具名不在清单或入参文件读不了时退出码 2；工具回失败时退出码 1。命令细节见 `scripts/real-machine/README.md` 的「直调 deck 写工具」一节，提交门禁是 `tests/verify-1709-deck-entry.ts`（加 `--negative` 可单独触发负例）。B0 批次要真建一张票、真改一次、真挂一次父票，再用 `deck-readback` 读回并把回执与读回两份 JSON 贴进证据。

### 证据归档、不可变与批次环境记录

批次留下的证据是发布结论的唯一凭据，但批次目录会被清理、文件也可能被下一次重跑覆盖，所以另外定三条规矩：

- **每批结束立刻归档**：结果评论发出前后，把整批证据复制到 `<工作根>/evidence-archive/<批次名>-<时间戳>/`。归档目录放在批次目录之外（`cleanup` 只删批次目录，不碰归档），原文件不删不改；同时复制 `pkg/candidate.json`，并生成一份 `SHA256SUMS.txt` 记录每个文件的哈希。归档副本至少保留到下一版发布结束。起因：2026-10-30 beta.32 批次重跑一次就覆盖了 `measure-banner.json`，1661-02 矮窗的机器可读证据丢失，只剩一张截图和一份日志。
- **证据不可变**：证据 JSON 与截图写出之后不再编辑。需要更正（例如脚本里残留了旧提交号）时，新写一份旁注文件说明「哪个文件、哪个字段、为什么改、以哪份为准」，再在清单票评论里写清楚，不要直接改原件冒充当时的记录。beta.32 批次手动改过证据副本里的 `commit` 字段，虽然测量数值没动，但「测量当刻写下的原件」因此不复存在。
- **每批开始记录宿主显示状态**：批次开始那条评论的「验证环境」里要有这一项。直接抄 `preflight` JSON 的 `items[]` 里 id 为 `screen` 的那一项：`details.primaryDevice` 是主屏的宽、高与设备名，`details.devices` 是全部显示器及是否主屏。预检自己执行屏幕命令，不靠人抄；批次记录以这份 JSON 为准。

这只是「批次开始那一刻主机是什么样」的快照，不能证明整个批次期间都稳定；真正的视口以真全屏实例的 `page-diagnostics.json` 里 `fullscreen` 与 `viewport` 字段为准。宿主在多个显示器或分辨率之间自动切换时，先请人把显示器固定住再开批；不要用看门狗去抢每次只出现两三分钟的横屏窗口——切屏会打断测量，留下的证据不可信，还要整批重跑。beta.32 批次因此两次作废 1660 的证据，最终 wide/short 没能按登记尺寸复跑。

### 报告索引：把批次证据汇总成报告能用的数字

批次归档之后，用一条命令汇总 `evidence-archive/index.jsonl` 与 `conditions.jsonl`：

```
node --import ./scripts/ts-hook.mts scripts/real-machine/commands/report-index.mts --markdown-out evidence-archive/report-summary.md
```

它按 8 条支持度断言分组计数，给出 P0/P1/P2 缺陷票与重验状态、每个候选的通过率与未测数、条件账本条数，并把同一份汇总渲染成 Markdown，贴进验证报告即可。三点要记住：`index.jsonl` 一行只记一次尝试（verdict 六类、candidate 写完整 40 位提交哈希），同一场景多次尝试会被合并统计，所以断言次数相加会大于行数；缺陷票在 `index.jsonl` 里只有票号没有等级，报告默认按该行场景在 #1675 里的最高 P 级上限推定，需要精确等级时用 `--defects` 传 `[{"ticket":"#2001","level":"P1"}]` 这样的清单；条件清单来自 `conditions.jsonl`，一行一个条件，字段是 condition、scope、scenario、evidence、alternative、expiry、owner，报告里的条件条数由它汇总。更正记录按现行约定另写在 `corrections.jsonl`，本版汇总脚本还没有读它。

## 三、验证批次

验证主持人在候选构建（即准备发布的那个产物）上跑一批。每批做四件事：

1. **批次开始时发一条评论**：批次号、版本与提交、构建产物及其 sha256、验证环境（操作系统、DSH 版本、隔离的 home/profile、已装插件版本、网络条件、前置巡检结果（preflight JSON，含屏幕分辨率与主屏））、本批要验的场景编号清单、开始时间。
2. **逐场景执行并记录结果**。每验完一条就记下通过还是失败，不要等整批结束再凭记忆补。
3. **批次结束时发一条结果评论**：逐场景写 `通过` / `失败（→ #新票号）` / `未测（原因）`，每条附决定性证据。证据要能独立看懂：截图路径、关键日志行、接口返回字段；临时目录里的文件路径不能作为唯一证据，因为目录会删，要把关键几行贴进评论。

   发布前检查要读这条评论，所以每条结论请用下面任一种明确格式写（散文里顺口提一句不算结论，读不到就会按「找不到明确结果」拦住发布）：

   - `场景 <编号>：<结果>`，多个编号并列写 `场景 1600-01 / 1600-02：通过`；
   - Markdown 表格行：首格写编号，第二格写结果；
   - 加粗要点：`**<编号> <结果>**`。

   同一条评论里同一个场景出现多个结论时（常见于收口评论既写分批叙述、又写最终计数），按「失败 > 豁免 > 通过 > 已验证 > 未测 > 阻塞 > 待验证」取最终结论；所以收口评论要把最终结论写清楚，不要把过程结论当成最终结论。
4. **更新清单票正文**里的「场景总览」与「批次记录」两张表。正文只有主持人写，每批开始和结束各更新一次，保护性地说：只改表格状态，不改场景说明。

其他规则：

- 失败立即开 bug 票，或重新打开来源票；修好后进入下一批重验。重验通过之前，这条场景不算通过，也就不能计入发布。
- 因为环境原因（网络不可用、缺 gh 等）没法验的，记「未测」并在下一批重跑，不记失败，也不当成通过。
- 批次之间新登记的场景照常进下一批；已经通过的场景，除非后来被改动直接影响，不重复验（改了就直接补验那一条）。
- **批次评论不要用收口关键词，也不写收口计数行**：`发布就绪`、`验证收口`、`收口关闭`、`已登记场景` 这四个词只留给清单票真正关闭时那一条收口评论；`通过 N / 失败 M / 豁免 K` 这种斜杠计数也只在收口评论里写。原因：`scripts/lib/checklist-consistency.mts` 会把**所有**含这四个词的评论都当成收口评论，逐条核对计数；批次评论里写一次，等到最终统计变化时，后来的人就只能去改历史评论，而历史评论又不该改写。beta.31 阶段那条旧收口评论就是这样被迫作废的（2026-10-29 写下「通过 4」，beta.32 收口前要改成作废说明）。
- **收口评论只发一条，只在真正关闭清单票时发**：给批次做汇总时写「本批 5 条全部通过」这样的自然句就够，不要写斜杠计数、不要带上面四个词。
- **历史评论不改写**：批次评论、收口评论、发布记录发出后不再编辑；需要更正时追加一条新评论，写清更正哪一条评论的哪句话、为什么。GitHub 不提供可查的评论编辑历史，改掉原始结论等于让审计链断掉。

## 四、豁免

豁免是正式状态，不是「口头略过」。核准一条豁免需要四样东西，缺一不可：

1. **类别**：纯文案 / 纯内部重构 / 只影响构建或工具链 / 已被其它场景覆盖 / 紧急发布（先发后验，必须写拍板人和补验期限）。
2. **可观察面声明**：说明这次改动在真机上能观察到什么、为什么不需要单独验。属于「已被覆盖」的要给出覆盖它的场景编号。
3. **登记人**：谁提出这条豁免。
4. **主持人接受**：主持人必须明确接受，不接受就只能转成正式场景。

有争议的豁免转成正式场景验证。主持人每批可以抽一条豁免做冒烟，抽检结果记在批次结果评论里。豁免不算通过，发布计数时把「通过」和「豁免」分开写。

## 五、发布前：机器检查三道

发布前检查有三条判据，由 `scripts/release-preflight.mts` 执行：

1. 本版清单票**恰好一张**。
2. 这张清单票**已经关闭**。
3. 这张票的**正文与评论记录内部一致**：场景总览表的编号集合、每条场景的状态，与评论里的场景块、批次结果、收口计数对得上；正文自称的条数、分组计数、发布计数也和表的实际统计一致。

三条都满足才能继续发布。检查挂在两条发布路径上，走的都是同一个脚本：

- `scripts/publish-token.ps1`（有写权限 token 时的无人值守路径，token 经 `-TokenFile` 临时文件传入，命令行里只有路径；传法与轮换见 [`RELEASE-RUNBOOK.md` 第 12 节](../releases/RELEASE-RUNBOOK.md)）：发布前检查失败就中止，`-DryRun` 试运行时只提示不阻断。
- `scripts/wizard-release.sh`（需要人扫码的交互向导）：同样在发布步骤之前检查，失败就中止；`--dry-run` 时只提示。

清单票什么时候能关：所有已登记场景都是「已验证」「通过」或「豁免被接受」。如果验的过程中发现了新问题，就开新 bug 票；这个问题需要真机复验的话，把场景追加进清单票并标成待验证，于是清单票关不上、发布自然被拦。这就是整套机制的闭环，不需要额外检查代码改了什么。

关闭评论里写一行计数给读的人看（例如 `[发布就绪] 通过 12 / 失败 0 / 豁免 3`；开发期已验过的场景计入「通过」，在备注里写明验证时间与证据出处）。这一行以及正文里各处的数字现在也参与机器核对：正文「## 场景总览」一节开头写的条数、各状态分组计数、来源票数，正文「## 发布前对账」与关闭评论里的通过/失败/豁免计数，以及收口评论里「N 条已登记场景」「N 条登记前已验证」「N 条本版真机通过」「N 条豁免」这类自称计数，都必须和场景总览表的实际统计一致；对不上会逐条列出「哪里写了什么、实际是什么、按什么改」，修正前发布被拦住。脚本只核对记录是否自洽；某个豁免该不该接受、场景是不是真的验过，仍然由人判断。

发布前建议再做一次人工对账：用 CHANGELOG 里的「对应提交」与自上一版发布以来合并的提交逐票对照，确认每个影响使用方的票都有场景块。代码冻结只是安排批次的建议（最后一批贴近发布），不是规则；验完之后如果必须再改代码，只补验受影响的那几条场景，不必重验全清单。

## 六、发布之后

- **版本真正发布后**，在清单票补最后一条评论：发布版本与时间、通过/失败/豁免计数、证据位置、对应的 CHANGELOG 提交。清单票保持关闭。
- **发布后记录由脚本做**：`scripts/release-postflight.mts` 在发布成功后给本版清单票补一条「发布记录」评论（评论里写实际发布包的逐文件清单摘要——文件数、字节数、清单指纹，由 `scripts/release-integrity.mts` 做字节对账——与各 dist-tag 的最终指向，读记录的人不用再去翻发布日志），并创建下一版的占位清单票 `[真机验证] 下一版（自 <刚发布版本> 之后）`；如果已经存在同名的占位票就跳过。下一版开发期间，由关闭第一张来源票的人把占位票改名成实际版本号并开始登记场景。
- **版本取消或并入下一版**：清单票关闭，最后一条评论写「并入下一版清单票 #N」，把已登记的场景转录过去，不丢。
- **紧急发布**：在清单票里把场景标成「紧急发布」类别的豁免，写清拍板人和补验期限；发布后按期限补验，结果补在该票评论里。
- **已经发布过、代码没再改的改动**不进下一版的清单；版本号跳过不发的版本不开清单票。

## 七、常见问题

- **谁负责验**：发布准备时指定验证主持人，可以是发布人，也可以是 AI。没指定也没关系，发布前检查照样会拦。
- **验哪个产物**：必须验候选发布产物，并记下它的 sha256；在开发机上随手构建一个版本跑一遍不算数。
- **清单票什么时候存在**：开发早期就要有，占位标题也行，否则来源票关闭时无处登记。本规则落地之前的版本，按 CHANGELOG 一次性把场景回填到该版本的清单票。
- **检查本身坏了怎么办**：发布前检查失败就中止发布，先修环境（例如 gh 没登录）；没有「跳过检查」的开关。检查是发布路径的一部分，坏了和发布不了是一回事。
- **规则从什么时候生效**：从这份文档落地开始的新动作；之前的版本一次性回填，不追认历史过程。
