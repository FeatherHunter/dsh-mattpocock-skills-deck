# 版本真机验证清单票模板

这张票用来攒一个版本要做的真机验证，一个要发布的版本一张，标题固定写成 `[真机验证] <版本号>`，下面简称**清单票**。规则写在 [real-machine-verification.md](real-machine-verification.md)。

## 建票步骤

1. **先搜一遍**：用 `deck_issue_list` 搜标题里的 `[真机验证]`，看本版清单票是不是已经有了。已经有的不要再建，重复的那张要合并掉。
2. **确定版本号**：版本号已经确定就直接写进标题；还没确定（开发早期）就先建占位票，标题写 `[真机验证] 下一版（自 <上一发布版本> 之后）`，等发布准备时再改名。
3. **建票**：用 `deck_issue_create`，`kind: 'issue'`，标题按上面格式，正文用下面模板（替换尖括号里的内容）。
4. **不打的标签**：这张票是发布流程的跟踪票，不打 `bug` / `needs-triage` / `wayfinder:grilling` 这三枚必备标签（理由是它不是三档里的任何一档），靠标题前缀识别。

## 谁建

- 正常路径：**关闭本版第一张来源票的人**。关票前搜清单票，没有就建。
- 发布之后：发布后检查脚本 `scripts/release-postflight.mts` 会自动建下一版的占位清单票。
- 兜底：发布负责人在发布准备时发现没有，就自己建一张并回填场景。并发撞车时，后建的人发起「追加场景」评论之前先再搜一次，发现已经有了就把内容迁到先建的那张，自己这张关闭并写「重复，并入 #先建票」。

## 关闭这张票

- 关闭条件是所有已登记场景都是「通过」或「豁免被接受」。
- 关闭时在关闭评论（或同一条评论）里写一行计数，供读的人一眼看到：`[发布就绪] 通过 N / 失败 0 / 豁免 M`。
- 发布前检查脚本会检查「本版清单票恰好一张且已关闭」；计数不参与机器判断。
- 版本真正发布后，在票上补最后一条评论（发布版本与时间、计数、证据位置、CHANGELOG 提交），票保持关闭。

## 规则（给读票的人）

- 场景明细写在评论里，每张来源票一条「场景块」评论；本票正文不写场景明细。
- 正文里三张表由验证主持人维护：场景总览、豁免、批次记录。
- 关闭条件：所有已登记场景都是「通过」或「豁免被接受」。
- 发布前检查会确认本票恰好一张且已关闭，没关就发不出去。
