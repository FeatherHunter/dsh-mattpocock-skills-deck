# 版本真机验证清单票模板

这张票用来攒一个版本要做的真机验证，一个要发布的版本一张，标题固定写成 `[真机验证] <版本号>`，下面简称**清单票**。规则写在 [real-machine-verification.md](real-machine-verification.md)。

## 建票步骤

1. **先搜一遍**：用 `deck_issue_list` 搜标题里的 `[真机验证]`，看本版清单票是不是已经有了。已经有的不要再建，重复的那张要合并掉。
2. **确定版本号**：版本号已经确定就直接写进标题；还没确定（开发早期）就先建占位票，标题写 `[真机验证] 下一版（自 <上一发布版本> 之后）`，等发布准备时再改名。
3. **建票**：用 `deck_issue_create`，`kind: 'issue'`，标题按上面格式，正文用下面模板（替换尖括号里的内容）。
4. **不打的标签**：这张票是发布流程的跟踪票，不打 `bug` / `needs-triage` / `wayfinder:grilling` 这三枚必备标签（理由是它不是三档里的任何一档），靠标题前缀识别。

## 谁建

- 正常路径：**关闭本版第一张来源票的人**。关票前搜清单票，没有就建。
- 发布之后：发布后检查脚本 `scripts/release-postflight.mts` 会自动建下一版的占位清单票。
- 兜底：发布负责人在发布准备时发现没有，就自己建一张并回填场景。并发撞车时，后建的人发起「追加场景」评论之前先再搜一次，发现已经有了就把内容迁到先建的那张，自己这张关闭并写「重复，并入 #先建票」。

## 关闭这张票

- 关闭条件是所有已登记场景都是「已验证」「通过」或「豁免被接受」；开发期已经真机验过的场景要写「已验证」并注明证据出处，不再排进批次。
- 关闭时在关闭评论（或同一条评论）里写一行计数，供读的人一眼看到：`[发布就绪] 通过 N / 失败 0 / 豁免 M`。
- 发布前检查脚本会检查五件事：本版清单票恰好一张、已经关闭、票面记录内部一致（正文场景总览表里的编号与状态，要和评论里的场景块、批次结果、收口评论里的计数对得上）、批次评论都带候选身份行、所有候选提交都是发布提交的祖先（候选提交与发布提交不同时，本票有「候选与发布差异审计」说明差异为什么可以接受）。计数现在参与机器判断：正文自称的条数、分组数与发布计数，必须和总览表的实际统计一致；对不上时脚本逐条列出哪里不一致，改完才能发布。
- 版本真正发布后，在票上补最后一条评论（发布版本与时间、计数、证据位置、CHANGELOG 提交），票保持关闭。
- 收口评论只发一条，只在清单票真正关闭时发；批次评论与批次结果评论里不要出现「发布就绪」「验证收口」「收口关闭」「已登记场景」这四个词，也不要写 `通过 N / 失败 M` 的计数行——发布前检查会把它们当成收口评论核对计数，而历史评论又不能改写。完整原因见 [real-machine-verification.md](real-machine-verification.md) 第三节。
- 评论发出后不改写；需要更正时追加一条新评论，写清更正了哪一条评论的哪句话、为什么。

## 目的

把本版所有需要真机验证的场景集中到这张票，发布前在这里逐条验完。来源票可以在没有真机验证的情况下关闭，但关闭前要把场景登记到本票评论。

## 版本范围

- 版本号：<版本号>
- 上一发布版本：<上一发布版本>
- 范围：自上一发布版本之后合入 main、随本版发布的改动，以 `CHANGELOG.md` 的「对应提交」为准。

## 规则（给读票的人）

- 场景明细写在评论里，每张来源票一条「场景块」评论；本票正文不写场景明细。
- 正文里三张表由验证主持人维护：场景总览、豁免、批次记录。
- 关闭条件：所有已登记场景都是「已验证」「通过」或「豁免被接受」。开发期已经真机验过的场景标「已验证」并注明证据出处，不再排进批次。
- 发布前检查会确认本票恰好一张、已关闭，核对正文与评论记录是否对得上（场景编号、每条场景的结论、各处计数），并要求批次评论带候选身份行、候选提交是发布提交的祖先（候选与发布不同时本票有差异审计）；对不上就逐条提示改法，没改好就发不出去。

## 候选与发布差异审计

最后一批验证的候选提交与发布提交不同时，这里写一行说明差异为什么可以接受（发布前检查会读这一行）：

- 候选提交 <40位小写提交> → 发布提交 <40位小写提交>：<一句话说明差异为什么可接受，例如「候选之后只有文档与工具台提交，插件产物没有变化」>

两者相同时写「无」，并说明为什么不需要审计，例如「最后一批就是发布提交上的干净构建」。

## 发布前对账

- [ ] 场景总览里的每一条都已是「已验证」「通过」或「豁免被接受」。
- [ ] CHANGELOG 的「对应提交」与自上一发布以来合并的提交逐票对过，影响使用方的票都有场景块。
- [ ] 「候选与发布差异审计」已写：候选提交与发布提交一致时写「无」并说明为什么不需要；不同时写清差异为什么可以接受。
- [ ] 场景总览表的条数、各状态条数、来源票数与「## 场景总览」一节开头写的数字一致；表里每一行在评论里都能找到归属（来源票的场景块或批次结果），评论里登记的场景也都在表里。
- [ ] 本票关闭评论里写了通过/失败/豁免计数，且与场景总览表的统计一致（开发期已验证的场景计入「通过」）。
