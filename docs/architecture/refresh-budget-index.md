## 二、材料之间的关系

- **定稿是唯一结论来源。** 其余五份都是它的上下游：拷问记录与方案对比记的是定稿**之前**的讨论；对抗审查原文与两份调查底稿是定稿过程中被吸收进来的外部输入，结论已经并进定稿正文（合并的位置在第十三～十五章里逐条写明）。
- **两份调查底稿是"事实"，不是"决定"。** 它们只回答「平台实际是怎么做的」；要改设计，改的是定稿，不是底稿。底稿被推翻时，做法是重测并更新底稿，再回头看定稿里引用它的地方要不要跟着改。
- **对抗审查原文与定稿第十四章是一对。** 第十四章末尾逐条写着「由这份审查改掉了哪四个决定」；要核对某条结论的出处，从第十四章往下追原文。
- **票据地图管"什么时候做"，不管"做什么"。** 做什么看定稿，顺序与边界看 `#704` 的票面。

## 三、新机制的实现形态

**纯逻辑走 TypeScript 核心 `refresh-core/`，取数与落盘留 JS。**

依据是 `docs/adr/20260913-builtin-ts-shape.md`（2026-09-13 定版）——它定的是插件内置 TypeScript 的形态：源码放仓库根的独立目录，用 esbuild 转译进 `src/shared/` 并提交进 git，不发布 npm 包；仓库里已有的先例是 `update-core/` 与 `label-color-core/`。照这份 ADR 的分工：

- 进 TypeScript 核心的，是**不碰磁盘、不联网的纯计算**（分类、裁决、记账口径、判定表这一类可以拿数据直接跑、直接测的逻辑）；
- 留在 JS 的，是**取数层与落盘**（tracker 契约层、三个后端房间、往工作区写文件的原子写与单写者队列、日志埋点）——它们正是要挡在核心外面的 I/O。

落地这张形态的票是 `#720`。

## 五、配套的自动检查

- `tests/verify-deck-event-gate.mjs`：守「订阅会话事件必须先过工作区那道门」这条硬约束（对应 `#710`）。它做三件事——每条会话事件监听器都必须在登记表里、必须在消费事件数据之前过工作区门、事件对象不许整份进日志或落盘出口。扫仓库用 `node tests/verify-deck-event-gate.mjs`；跑运行期自检（证明平台侧没有隔离、门只能自己守）用 `node tests/verify-deck-event-gate.mjs --selfcheck --dsh "<DSH 安装目录>\resources\app\node_modules"`。
- `tests/fixtures/deck-event-gate/`：上面那条门禁的探针样本。`violating/` 是故意写坏的样本（期望判红），`compliant/` 是合规写法（期望判绿，它的登记表由同目录的 `compliant.registry.json` 提供）。扫仓库时这个目录会被门禁自己跳过，要检查样本本身得用 `--root` 指过去。
