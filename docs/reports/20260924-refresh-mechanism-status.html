刷新机制与工具链：现在到了哪一步

一句话：刷新的机制已经落地并且被门禁守着；工具也做出来了、在宿主里被证明真跑通，但 AI 在会话里还调不到它们。

先给结论

刷新机制 已落地

唯一出口闸与账本、预算真源、行级增量、视野模型、写事件订阅、检查链事件驱动、诚实显示，全部落地并各带门禁与反证。

对外工具 做出但未通电

七个后端无关工具在宿主里能真建票、真过闸；但还没挂到 DSH 的模型工具面，AI 今天在会话里调不到。

工作路线（旧名会话↔票记录）已落地

只记「写」不记「读」。新存档落在用户主目录、一个工作区一份；上报成功的回执里带 data.workRoute，面板胶囊仍读快照回包的同名字段。旧的宿主缓存仍在写、随 #1082 退役（细节见第 3 节与 2026-10-19 修订）。

终局真机验收 未跑

所有结论目前都是门禁与离线证据；真机上的六项实测（含真 GitLab 建票、真会话走工具）还没做。

1 · 刷新机制长什么样

整条主线只有四句话：谁在看才去刷 → 每次出站都先过闸 → 变化只补那几行 → 界面只说实话。

谁在看才去刷（视野模型）　只有当前真的在被看的工作区才值得刷新；同时活跃上限 2 个；同一个工作区根只占一个名额、只产生一次探测；90 秒没有信号就把这一整套收摊，后台没有自续定时器。
客户端心跳（三道门）　窗口标识放在 sessionStorage（不用 localStorage，同源会互相覆盖）；面板可见时每 20 秒一次本地心跳，焦点、可见性、人类输入三道门都过才发；90 秒没回话就判定「自动刷新已暂停」。
每次出站都先过闸（唯一出口）　跑 gh、起子进程、探测版本，每一笔都在起进程之前登记给闸并记账；此前绕开闸的存量口子从 3 处降到 0 处，门禁里那条上限也跟着归零——以后再有新口子会当场变红。
变化只补那几行（行级增量）　只有变了的那几张票被单独重查，新行并进原列表，其余行连对象引用都不动；水印只在变化真的并进列表之后才前进，被推迟或丢弃时一个字节不动，并把变化记进待办下次补上。
写事件订阅（工具改完立刻知道）　订阅工具出结果与会话事件；第一道门是工作区白名单——别的仓库的事件一个字都不判、不写日志、不取数；10 秒合并窗口把连着的几笔并成一次取数。
检查链改成事件驱动　删掉 8 秒自续循环与 20 秒轮询；退避 8 秒 → 30 秒 → 2 分钟 → 5 分钟，一有进展立刻回快档；全绿时缓存 30 分钟；环境预检（登录态、仓库是否可达）在一次求值里只真问一次（实测出站从 5 条降到 3 条）。
界面只说实话　新鲜度、失败形态、降级标记全部读宿主写下的真实值，界面不现算、不写死文案；读不到就如实说读不到（「读不到」与「确实没有」是两件事，分开显示）。

2 · 对外工具清单（七个，全部后端无关）

这七个是给 AI 用的票务工具。它们只认契约、不认后端 id，并且对每一条边如实报出它落在后端的哪里。

工具做什么后端差异（实测矩阵跑出来的）
deck_context取当前上下文（当前工作区、后端、正在看的票）—
deck_issue_get看一张票（正文、状态、标签）—
deck_map_snapshot看整张地图与每张子票的进度—
deck_issue_create建票（带幂等锚，重复调用不会建出第二张）GitHub / GitLab：一次调用只发一次写；本地 Markdown：落到票文件
deck_map_plan_create建地图骨架（母票 + 子票 + 顺序）—
deck_map_link补边：父子关系、阻塞关系GitHub：父子＝原生层级、阻塞＝原生依赖边；GitLab：父子＝平级链接（不是层级）、阻塞＝正文里的一行；本地 Markdown：父子做不到（如实说做不到）、阻塞＝正文里的一行
deck_issue_patch改票：状态、标签、正文、认领、关闭、评论本地 Markdown 只改状态不记认领人时，如实回「部分完成」

这里必须说清楚一句

这七个工具已经在宿主里被证明真跑通（真工作区里真建票、闸真的放行、每笔调用至少过两次闸），但还没有挂到 DSH 的模型工具面——也就是说，AI 今天在会话里还调不到它们。这是工具链的最后一公里，已经立票跟踪。

3 · AI 在会话里处理了哪些票：现在有机制记录吗

有。它叫「工作路线」（旧名「会话↔票处理链」）。它只记「写」不记「读」——AI 看一眼票不算处理，真去建票、改票、评论、关票才算。

2026-10-19 修订（#1083）：这一节原来写的是 2026-09-24 的状态，当时工作路线只存散列与票键。现在新存档已按 <用户主目录>/.dsh/mattskillsdeck/work-path/<工作区根散列>.json 重做，隐私口径改成「字段白名单 + 凭证形状检查」，允许会话 id 原文与标题快照落盘（不然面板显示不出人读得懂的名字）；旧宿主缓存 session-tickets.json 仍只存散列，随 #1082 退役。判据见 ADR docs/adr/20261019-work-route-archive-privacy.md。

记了什么

  • 会话 id 原文、会话标题快照（取不到标题时显示「会话 <会话散列前 6 位>」）
  • 工作区根散列、后端名
  • 票号、票标题快照、时刻、动作类别（上报 / 建票 / 改票 / 改状态 / 关闭 …）、来源（上报或自动）
  • 同一会话同一张票只留最近一次；不设每会话条数上限，保留 30 天

记在哪

  • 内存表：宿主进程内，随刷新机制的那一套实例一起建起来。
  • 新存档（2026-10-19 起）：<用户主目录>/.dsh/mattskillsdeck/work-path/<工作区根散列>.json，一个工作区一份。写前先读旧文件合并、写临时文件再改名、最后读回确认；超过 30 天的条目清掉，单文件超过 2MB 从旧到新裁；写失败不抛错，只在工具回执的 notes 里说明这次没落上。
  • 旧宿主缓存（仍在写，将退役）：<进程当前目录>/.dsh-mattskillsdeck-cache/session-tickets.json（与命名守护用同一个缓存目录，所以重启不丢）。它仍只存散列与票键，不存会话 id 原文与标题；不读、不迁移、不删除，随 #1082 的跨会话在办表退役。
  • 隐私：新存档落盘前走两步检查——字段白名单（只认固定的十五个字段名）加凭证形状检查（令牌、口令、授权头、私钥、带凭据 URL 的形状，命中就整份不写）。允许落盘会话 id 原文、会话标题快照、票标题快照、票号、工作单元、动作、来源、时间、进度自评、后端名；凭证原文永不落盘；命令原文与路径原文不作为字段来源。检查不通过时整份不写、不抛错，回执 notes 说明这次没落上，盘上保留上一次成功写入的内容。判据见 ADR docs/adr/20261019-work-route-archive-privacy.md。

界面怎么读到它（这就是你要的那条 API）

两条路拼起来，缺一不可：

① 在办表          上报成功的回执里带 data.workRoute（跨会话在办表）；
                 #1261 先接通上报这一条，其余写工具随 #1082 陆续接上

   {
     at: '2026-10-19T05:34:13.000Z',       // 这份读数是什么时候取的
     entries: [
       { ticketKey: '1083',
         title: '地图14开发：落盘可信，日志与隐私口径收口',   // 票标题快照
         sessionLabel: '修复工作路线落盘',   // 会话标题快照；取不到时是「会话 ab12cd」
         action: 'report',
         actionAt: '2026-10-19T05:30:00.000Z',
         active: true,                     // 24 小时内动过
         currentSession: true,             // 是不是当前这个会话记的
         source: 'reported' }
     ],
     staleCount: 0,                        // 在办但超过 24 小时没动的条数
     collisions: [ … ]                     // 同一张票 30 分钟内被另一个会话记过时才出现
   }

② 票 → 路径/链接    wf.issueDetail（票详情）或 wf.issuesPage（列表页）

关键一点：这份读数里没有 issuePath，也没有凭证。这是刻意的隐私决定——工作路线只记「写到哪张票」，不搬路径与命令原文。所以界面要拿到「某个会话在处理哪张票、那张票在哪」需要两步：先用 data.workRoute 拿到票号与票标题，再用票号问 wf.issueDetail 拿路径/链接。

（面板胶囊那条「本会话在处理哪些票」仍读 wf.snapshot 回包的 workRoute 字段，数据来自旧宿主缓存、仍是散列与票键；跨会话在办表的展示归 #1082。同机的脚本也可以直接读新存档的 JSON 文件，但那是内部存档格式，不建议 UI 直接依赖。）

现在这块在界面上的样子

面板正文最上面有一条「每个会话在处理哪些票」：一行一张票，点一行跳到那张票。它有三种诚实的显示——读不到（字段缺失或宿主说这一轮没取到）、取到了但确实没有（整块不画）、有数据（照实画出来）。

如实说明：喂数据（写事件订阅）与读数（快照回包）两头都已接线，离线门禁证明两头都通；但真机上还没有验证过——在终局真机验收跑完之前，界面在生产里可能照实显示「工作路线读不到」。那不是故障，是它还没被真人看过一眼。
