# 代码库设计

设计**深模块**：在一个干净的接缝处，把大量行为放到一个小接口后面，并可通过这个接口测试。凡是正在设计或重构代码的地方，都使用这套语言和这些原则。目标是：给调用方杠杆，给维护者局部性，给所有人可测试性。

## 术语表

严格使用这些术语：不要替换成「组件」「服务」「API」或「边界」。语言一致正是全部意义所在。

**模块**：任何有接口和实现的东西。刻意不限定规模：一个函数、类、包，或横跨多层的切片。_避免_：单元、组件、服务。

**接口**：调用方为了正确使用这个模块而必须知道的一切：类型签名，还有不变式、顺序约束、报错方式、必需的配置，以及性能特征。_避免_：API、签名（太窄，它们只指类型层面的表面）。

**实现**：模块内部的东西，它的代码主体。与**适配器**不同：一个东西可以是一个实现很大的小适配器（一个 Postgres 仓库），也可以是一个实现很小的大适配器（一个内存里的假实现）。当话题是接缝时用「适配器」；否则用「实现」。

**深度**：接口处的杠杆。调用方（或测试）每学一单位接口，能驱动多少行为。当一个模块把大量行为放在一个小接口后面时，它是**深**的；当接口几乎和实现一样复杂时，它是**浅**的。

**接缝** _（Michael Feathers）_：一个你可以在不编辑该处的前提下改变行为的地方；一个模块的接口所在的那个*位置*。接缝放在哪里本身就是一项设计决策，与它后面放什么不同。_避免_：边界（与 DDD 的限界上下文相冲突）。

**适配器**：在某个接缝处满足一个接口的具体东西。它描述的是*角色*（填的是哪个槽），而不是实质（里面是什么）。

**杠杆**：调用方从深度中得到的东西。每学一单位接口，得到更多能力。一份实现，在 N 个调用点和 M 个测试上回报。

**局部性**：维护者从深度中得到的东西。改动、缺陷、知识和验证都集中在一个地方，而不是散布到各个调用方。修一次，处处都修好。

## 深与浅

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│   Small Interface   │  ← Few methods, simple params
├─────────────────────┤
│                     │
│  Deep Implementation│  ← Complex logic hidden
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 少量实现（避免）：

```
┌─────────────────────────────────┐
│       Large Interface           │  ← Many methods, complex params
├─────────────────────────────────┤
│  Thin Implementation            │  ← Just passes through
└─────────────────────────────────┘
```

设计一个接口时，问：

- 我能减少方法的数量吗？
- 我能简化参数吗？
- 我能把更多复杂度藏在里面吗？

## 原则

- **深度是接口的属性，不是实现的属性。** 一个深模块内部可以由小的、可 mock、可替换的部件组成；它们只是不属于接口的一部分。一个模块除了接口处的**外部接缝**，还可以有**内部接缝**（对它的实现私有，供它自己的测试使用）。
- **删除测试。** 想象把这个模块删掉。如果复杂度消失了，它就是个直通管道。如果复杂度在 N 个调用方那里重新出现，那它就是在挣自己的饭吃。
- **接口就是测试面。** 调用方和测试穿过同一个接缝。如果你想*绕过*接口去测试，这个模块大概形状就不对。
- **一个适配器意味着假想的接缝。两个适配器才意味着真实的接缝。** 除非确实有东西在接缝两侧变化，否则不要引入接缝。

## 为可测试性而设计

好的接口让测试变得自然：

1. **接受依赖，不要自己创建依赖。**

   ```typescript
   // Testable
   function processOrder(order, paymentGateway) {}

   // Hard to test
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要制造副作用。**

   ```typescript
   // Testable
   function calculateDiscount(cart): Discount {}

   // Hard to test
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小的表面积。** 方法更少 = 需要的测试更少。参数更少 = 测试准备更简单。

## 关系

- 一个**模块**恰好有一个**接口**（它向调用方和测试呈现的表面）。
- **深度**是**模块**的属性，是相对于它的**接口**来衡量的。
- **接缝**是**模块**的**接口**所在的地方。
- **适配器**坐在**接缝**处，满足**接口**。
- **深度**为调用方产生**杠杆**，为维护者产生**局部性**。

## 被否定的说法

- **把深度看作实现行数与接口行数的比值**（Ousterhout）：这会奖励往实现里灌水。我们改用「深度即杠杆」。
- **把「接口」理解为 TypeScript 的 `interface` 关键字或一个类的公开方法**：太窄了：这里的接口包含调用方必须知道的每一个事实。
- **「边界」**：与 DDD 的限界上下文冲突。请说**接缝**或**接口**。
