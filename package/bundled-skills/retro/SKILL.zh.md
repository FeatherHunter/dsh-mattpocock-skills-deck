用户要求做一次**复盘**。你要提的是对编码智能体的**环境**的改进建议，让以后的运行更顺。

## 步骤

1. 调用 Skill 工具加载 `writing-for-agents`，拿到写作风格指南。

2. 阅读用户指定的那次会话的一手记录。这可能意味着要在这台机器上翻查会话日志。如果用户没有指定会话，就默认用当前这次。

3. 在下面这些类别里找可以改进的点。

- **导航**：智能体找到正确文件有多容易？文件之间存在隐藏依赖吗？加一个**导航指针**会不会更容易？_适用于_会话花了很长时间才找到某条信息的情况。
- **自动检查**：有没有能抓住智能体所犯错误的自动检查？代码检查（lint）、类型检查、测试、文件系统检查器？先读仓库自己的检查命令（它的 `package.json`/构建工具的 `lint`/`check` 脚本、它的 CI 工作流），这样如果某个检查其实已经存在、只是没接上或者悄悄坏了，那就是一条发现，而不是去重新造一个。一个没有**护栏**的仓库（既没有 pre-commit 钩子，也没有跑它 lint/typecheck/test 命令的 CI 任务）本身就是一条发现：没有 lint 的仓库是一个持续存在的错失机会，而不是中性的默认状态。_适用于_智能体犯了某个本可以被自动检查抓住的错误，或者仓库压根没有任何护栏的情况。
- **编码规范**：是不是该给**评审智能体**一条新规则去执行？某条已有规则是否该删掉或写清楚？先给违规定性：**机械性**的违规（固定的语法模式、被禁用的 API、某种导入写法、文件位置的规则）要用确定性检查来解决，没有例外：在仓库自己的检查器里加自定义规则、加一个 pre-commit 钩子，或者加一个 CI 任务，看仓库的语言和现有护栏哪种最省事。默认优先把检查建起来，而不是写规则。`CODING_STANDARDS.md` 只留给真正需要**人为判断**的地方（跨文件的一致性、「与周围风格保持一致」这类，任何护栏都永远替代不了的东西）。_适用于_评审智能体没能抓住某个错误的情况。
- **全局 AGENTS.md**：有没有哪些指挥性指令应该挪到编码规范（或自动检查）里去？_适用于_AGENTS.md 文件特别大的情况——无论是仓库里的还是用户全局作用域里的。
- **工具开销**：智能体有没有做出本可以更精简的昂贵工具调用？有没有哪些自研工具（CLI、MCP）特别费 token？_适用于_智能体做出了昂贵工具调用的情况。
- **无效指令**：在指挥类文件里找那些并不会改变智能体行为的指令。_适用于_指挥类文件又大又难用的情况。
- **信息获取**：找机会扩大智能体获取信息的渠道。把开发服务器的日志分流出来，给第三方服务开只读访问。_适用于_某条关键信息当时对智能体不可用的情况。

4. 把这些候选按严重程度排序，呈现给用户。

## 参考

### 实现与评审

记住所有工作都要经过两个阶段：实现和评审。实现智能体的**上下文压力**最大。它负责探索、写代码和调试失败。

评审智能体的上下文压力最小——它拿到的是一个 diff，所以不需要探索。它通常也不需要写代码或调试。

这意味着，编码规范应该由评审智能体来强制执行，而不是实现智能体。

### 文件

仓库里有几个文件归你用：

- `CLAUDE.md`/`AGENTS.md`：这些文件会被推进任何在这个仓库里干活的智能体的上下文窗口。它们应该被极其节制地使用，通常只用来放指向其它文件的**导航指针**。
- `CODING_STANDARDS.md`：这个文件在评审时读，不在实现时读。如果规范文件长度超过 1,000 行，就往文档目录里加**导航指针**。
- 文档：把文档当参考文件用，由其它文件指向它们。写新文档之前先找找有没有现成的。
- 技能：技能用来放文档（因为技能的 description 会进入智能体的上下文窗口），或者放用户主动触发的命令。遵循 `writing-for-agents` 技能里的建议。
