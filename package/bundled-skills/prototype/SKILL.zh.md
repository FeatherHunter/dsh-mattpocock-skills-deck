# 原型

原型是**用来回答某个问题的用完即弃的代码**。问题决定它的形态。

## 选择分支

先判断当前要回答的是哪个问题：看用户的提示词、看周围的代码，如果人在旁边就直接问。

- **「这套逻辑／状态模型顺不顺手？」** → [LOGIC.md](LOGIC.md)。做一个可以分享的单个 HTML 文件（自由操作按钮，加上分标签页的引导式走查），把状态机推到那些在纸上很难推演的情形上，并且让非开发人员也能操作。
- **「这东西应该长什么样？」** → [UI.md](UI.md)。在同一条路由上生成若干套截然不同的界面方案，用一个 URL 查询参数加一条悬浮底栏来切换。

这两条分支产出的东西差别极大，选错就会把整个原型都浪费掉。如果问题确实模棱两可，又联系不上用户，就默认选与周围代码更匹配的那条分支（后端模块 → 逻辑；页面或组件 → 界面），并在原型顶部写明这个假设。

## 两条分支都适用的规则

1. **从第一天起就是用完即弃，并且明确标注。** 把原型代码放在它真正会被使用的位置附近（紧挨着它所模仿的模块或页面），这样上下文一目了然；但命名要让人随便扫一眼就知道这是原型，不是生产代码。用完即弃的界面路由要遵守项目已有的路由约定，不要另造一套新的一级结构。
2. **跑起来要毫无门槛。** 界面原型从项目任务运行器里的一条命令启动：`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示就是用户双击打开的一个 HTML 文件。无论哪种，启动都不该需要动脑子。
3. **默认不做持久化。** 状态放在内存里。持久化正是原型要_检验_的东西，而不是它应该依赖的东西。如果问题明确涉及数据库，就去连一个临时数据库，或者用一个名字写得很清楚的本地文件，比如 "PROTOTYPE, wipe me"。
4. **别做打磨。** 不写测试，除了让原型_能跑起来_所需之外不做错误处理，不做抽象。重点是把东西快速学明白。
5. **把状态露出来。** 每次操作之后（逻辑分支），或每次切换方案时（界面分支），打印或渲染出完整的相关状态，让用户看得见什么变了。
6. **做完就归档。** 把验证过的决定并回真实代码，然后把原型本身作为一份**一手材料**留存：把它提交到一个用完即弃的分支上，不放在 main 上，并在实现议题里留一个指向该分支的上下文指针。答案也要留档（结论，以及它解决的那个问题），写进议题或某次提交里。main 分支只保留那条被验证通过的决定。
