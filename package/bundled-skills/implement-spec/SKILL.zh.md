你已经拿到了一份规格。这份规格应当配有工单，说明该怎么实现它。

议题跟踪器应当已经提供给你了。如果没有，就让用户去跑 `/setup-matt-pocock-skills`。

目标是在一条**集成分支**上把整份规格实现完，并且让每一张工单都按议题跟踪器收尾工作的方式关掉。

工单不是一串步骤。它们是一张带阻塞关系的**任务图**。这意味着任何时刻都存在一批随时可以抓取的**前沿**工单。

与子代理之间的往来通信要稀疏。主要靠**上下文指针**沟通：指向规格、工单、研究笔记和以前的提交。已经能通过指针拿到的信息，不要重复。

**实现者子代理**尽可能放到后台跑，以获得最大的并发度。

## 步骤

1. 读规格和工单，弄清任务图。

2. （可选）用**探查子代理**去做工单要求的任何探查——相关的代码库文件或外部文档。要确保探查子代理能保存文件——它应当把 markdown 笔记保存在仓库之外、所有后续子代理都能访问的某个目录里。这样**实现者子代理**就能专注在实现上，而不必去做探查。

3. 建集成分支。如果议题跟踪器是通过拉取请求收尾工作的，或者用户要一个，那就在第 5 步第一次合并之后开一个草稿拉取请求（一个还没有领先 main 的提交的分支开不了），并标注它会关闭这份规格和这些工单。

4. 用**实现者子代理**实现每张工单，每张工单各在自己的工作树、自己的分支上。每个实现者子代理都要：
   - 动手之前先确认自己的工作树是基于集成分支的，如果不是就重置到集成分支上；
   - 调用 Skill 工具，传入 `tdd`，把这张工单做出来；
   - 在报告完成之前，把集成分支的最新提交合并进自己的分支

5. 一个**实现者子代理**做完之后，用**合并子代理**把它的成果合并到集成分支。

6. 如果这一步改变了可用工单的**前沿**，就再起几个**实现者子代理**去做新冒出来的工单。这样可以获得最大的并发度。

7. 所有工单都完成之后，在集成分支上调用 Skill 工具，传入 `code-review`。用一个**实现者子代理**把代码评审提出的所有问题一次性修完。

8. 如果存在草稿拉取请求，就把它标记为可评审。否则，按议题跟踪器收尾工作的方式逐张解决工单，并报告集成分支。

9. 清理掉所有**实现者子代理**的工作树。
