# 逻辑原型

一个自包含的单个 HTML 文件（一份**可分享的演示**），让任何人都能靠点按钮来操作一个状态模型。当问题涉及**业务逻辑、状态转移或数据形状**时使用它：这类东西在纸面上看着合理，但只有真正拿具体情形跑一遍，才会发现不对劲。

因为它只是一个文件、什么都不用安装，你可以直接交给非开发人员（设计师、产品经理、领域专家），让他们亲自感受这个模型。所以它说的是他们的语言，不是代码的语言。

## 什么时候适合用这种形态

- 「我不确定这个状态机是否处理了先 X 后 Y 这种边界情况。」
- 「这个数据模型到底能不能表达……这种情况？」
- 「我想在动手写之前，先摸清这个 API 应该长什么样。」
- 凡是有人想**按按钮、看状态变化**的情形。

如果问题是「这东西应该长什么样」，那就不该走这条分支，请用 [UI.md](UI.md)。

## 流程

### 1. 写出要回答的问题

动笔写代码之前，先把你要做的是哪个状态模型、要回答的是哪个问题写下来。一段话就够，放在演示的顶部（写成看得见的开头说明，不要只放在注释里）。一个回答了错误问题的逻辑原型纯粹是浪费，所以要把问题写明确，方便以后核对：无论用户是现在就在看，还是离开一阵（AFK）之后再回来看。

### 2. 把逻辑隔离到一个可移植的模块里

把真正的逻辑（也就是回答问题的部分）放进单独一个 `<script>` 块，写成一个小的纯模块，以后可以整个抬出来、放进真实代码库。包在它外面的页面是用完即弃的，这个模块不是。

合适的形态取决于要回答的问题：

- **纯归约器（reducer）**：`(state, action) => state`。当动作是离散事件、状态是单个值时，适合用这种形态。
- **状态机**：明确写出状态与转移。当「当前到底哪些动作才合法」本身就是问题的一部分时，适合用这种形态。
- **作用于普通数据类型的一组小型纯函数**。当不存在隐含的当前状态、只有变换时，适合用这种形态。
- **方法集合清晰的类或模块**，适用于逻辑确实要自己持有一段持续变化的内部状态的情形。

选最贴合所要回答问题的形态，而*不是*最容易接到页面上的那种。保持纯粹：不碰 DOM，不碰 `document`，按钮事件处理函数也不要伸到它里面。是页面调用它，没有反方向的流动。这正是原型在自身生命周期结束之后仍然有用的原因：问题一旦有了答案，验证过的归约器／状态机／函数集合就可以原样搬进真实模块。

### 3. 构建可分享的 HTML 文件

一个文件，用朴素的 HTML/CSS/JS：不引框架，不用打包器，不起服务器，所有内容都内联，双击就能打开，邮件传来传去也不会散。任何人打开它就能跑。

要按非开发人员的视角来写。每个标签都用**领域语言**，而不是代码语言：按钮和状态读起来像业务本身，而不是像归约器。用平实的话解释正在发生什么。

按清晰的层级从上到下组织：

1. **标题和一句说明**：这个演示让你探索什么（也就是第 1 步写下的问题）。
2. **当前状态**：完整的相关状态，渲染成一块读得懂的面板（带标签的字段，而不是直接倾倒 JSON），每次点击之后重新渲染，让变化看得见。在能帮非开发人员跟上思路的地方，点明刚才改了什么。
3. **自由操作按钮**：每个动作一个按钮，始终可用，任何人都可以按任意顺序摆弄这个模型。每次点击都会派发对应的动作，并重新渲染状态。
4. **引导式走查**：一组**情景**，每个标签页一个。每个标签页里有一段用平实语言写的情景说明（它设定了什么处境、要留意什么），下面按顺序列出该点哪些**按钮**。每一步都是真实的按钮：点下去就执行那个动作，并前进到下一步。开始一次走查时会重置到一个已知的初始状态，这样同一个情景每次跑起来都一样。

挑选那些能展示别扭情形的情景——也就是在纸上难以推演的那些：正常路径、一个棘手的边界情况，以及一次本应不合法的尝试。

做得好看，但克制：排版干净、留白充足、只用一种强调色。不要动画，不要花哨的小把戏：不要让任何东西抢走状态和按钮的注意力。

### 4. 交给用户

把文件发给他们，或者替他们打开。他们有空时会点一点走查和自由操作；有意思的时刻，是他们说出「等一下，这不该发生」或者「咦，我以为 X 会不一样」的时候——那些是_想法_本身的缺陷，而这正是整件事的意义所在。如果他们想要新的动作或新的情景，就加上去。原型是会演进的。

### 5. 归档答案与原型

原型回答了它的问题之后，先把答案归档，再按 [SKILL](SKILL.md) 里说的方法把原型归档。逻辑分支的具体对应关系是：验证过的归约器／状态机／函数集合搬进真实模块（决定被吸收）；HTML 外壳则跟着进入那条以一手来源形式保存原型的用完即弃分支；由于它就是一个自包含的文件，在那里重跑起来依然毫无门槛。

## 反模式

- **不要加测试。** 一个需要测试的原型就不再是原型了。
- **不要把它接到真实数据库上。** 除非问题专门问持久化，否则用内存状态。
- **不要做泛化。** 不要写「万一以后要支持 X 呢」。原型只回答一个问题。
- **不要把逻辑和页面搅在一起。** 如果那个纯模块引用了 DOM、`document` 或按钮事件处理函数，它就不再可移植了。页面要始终是罩在纯模块外面的一层薄壳。
- **不要引入框架、打包器或服务器。** 接收方双击打开一个文件就好；做成一个 React 应用或起个开发服务器，就毁掉了「可分享」。
- **不要把 HTML 外壳发布到生产环境。** 这个页面是为人工逐点点开而优化的。真正值得保留的是它背后的逻辑模块。
