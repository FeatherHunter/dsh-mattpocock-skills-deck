# 界面原型

在单条路由上生成**若干套截然不同的界面变体**，用一条悬浮底栏来切换。用户在浏览器里来回翻看，挑中一套（或从每套里各取一点），然后把其余的扔掉。

如果问题涉及逻辑／状态，而不是某样东西看起来该是什么样，那就不该走这条分支，请用 [LOGIC.md](LOGIC.md)。

## 什么时候适合用这种形态

- 「这个页面应该长什么样？」
- 「我想在定下来之前，先看看这个仪表盘的几种变体。」
- 「给设置页换一种版式试试。」
- 只要是用户本来得花一整天、在脑子里那三个模糊的草稿之间挑来挑去的情形。

## 两种子形态：强烈优先子形态 A

当一个界面原型**紧挨着应用的其他部分**呈现时，判断起来会容易得多：真实的页头、真实的侧栏、真实的数据、真实的密度。单独摆一条用完即弃的路由就像放在真空里：每一套变体孤立地看都没问题。只要存在一个合适的已有页面可以承载这些变体，就默认采用子形态 A。只有当原型确实在附近找不到落脚处时，才动用子形态 B。

### 子形态 A：调整一个已有页面（首选）

路由已经存在。变体渲染**在同一条路由上**，由一个 `?variant=` URL 查询参数来分流。已有的数据获取、参数和鉴权全部保留，只有渲染部分替换掉。这是默认做法；除非有明确的理由不这么做，否则就选它。

如果原型要做的东西目前还没有页面，但*本来就应该放在某个页面里*（仪表盘里新增的一个区块、设置页上新增的一张卡片、已有流程里新增的一步），那仍然属于子形态 A。把变体挂载在宿主页面内部。

### 子形态 B：新建一个页面（最后手段）

只有被做原型的东西确实没有已有页面可以容身时（例如一块全新的顶层页面，或者一条无法合理嵌入任何地方的流程），才使用这种形态。

按照项目已有的路由约定，创建一条**用完即弃的路由**。不要另造一套新的一级结构。命名要让人一眼看出这是原型（例如在路径或文件名里带上 `prototype` 这个词）。同样用 `?variant=` 那套模式。

在决定采用子形态 B 之前，先做一次合理性检查：真的没有一个已有页面能把它嵌进去吗？一条空路由会掩盖设计问题，而一个内容充实的页面会把问题暴露出来。

两种子形态里，悬浮底栏完全相同。

## 流程

### 1. 写出问题并选定变体数量 N

默认做 **3 套变体**。超过 5 套就不再是「截然不同」，而开始变成噪音，所以上限就定在这里。

用一句话把计划写下来，放在原型所在的位置或文件顶部的注释里：

> 「设置页的三套变体，通过 `?variant=` 切换，挂在已有的 `/settings` 路由上。」

无论用户是否在旁边准备反驳，这句话都用得上。

### 2. 生成截然不同的变体

逐个起草变体。每一套都要满足：

- 这个页面的用途，以及它能拿到的数据。
- 项目自己的组件库／样式系统（TailwindCSS、shadcn、MUI、纯 CSS，或别的什么）。
- 一个清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须在**结构上不同**：版式不同、信息层级不同、首要的操作入口不同，而不只是颜色不同。三张只做了细微调整的卡片网格不叫界面原型，那叫墙纸。如果两份草稿出来太像，就带着明确的「不要用卡片网格」的要求重做其中一份。

### 3. 把它们接起来

在这条路由上创建一个切换器组件：

```tsx
// pseudo-code, adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

做子形态 A（已有页面）时：把已有的数据获取全部留在切换器上方，只有渲染出来的子树随变体变化。

做子形态 B（新页面）时：`/prototype/<name>` 下那条用完即弃的路由挂载同一个切换器。

### 4. 构建悬浮切换器

屏幕底部居中一条固定定位的小横栏，里面有三样东西：

- **左箭头**：切到上一套变体（循环）。
- **变体标签**：显示当前变体的键，如果该变体导出了名字，也显示那个名字。例如 `B (Sidebar layout)`。
- **右箭头**：切到下一套变体（循环）。

行为：

- 点箭头会更新 URL 查询参数（使用框架自己的路由，例如 Next 上的 `router.replace`、React Router 上的 `navigate` 等），这样变体可以直接分享，刷新后也保持不变。
- 键盘：`←` 和 `→` 方向键也能循环切换。当焦点在 `<input>`、`<textarea>` 或 `[contenteditable]` 里时，不要拦截方向键。
- 视觉上与页面明显不同（例如高对比度的胶囊形底栏、轻微阴影），让人一眼看出它不是被评审的设计的一部分。
- 在生产构建里隐藏：用 `process.env.NODE_ENV !== 'production'` 或等效判断来控制，这样一次误合并的原型也不会把这条横栏带给用户。

把切换器做成一个共享组件，让两种子形态都能复用它。放在项目里共享 UI 代码通常所在的位置。

### 5. 交给用户

把 URL（以及各个 `?variant=` 键）告诉用户。用户有空时会自己翻看。有意思的反馈通常是**「我想要 B 的页头配 C 的侧栏」**，那才是他们真正想要的设计。

### 6. 归档答案并清理

一旦某套变体胜出，先把答案归档（哪一套胜出、为什么），再按 [SKILL](SKILL.md) 里说的方法把原型归档。把胜出的那套并进真实代码，其余的移到那条用完即弃的分支上，不要留在 main 里：

- **子形态 A**：把胜出的那套并进已有页面；把落选的变体和切换器从 main 里删掉。
- **子形态 B**：把胜出的变体提升为一条真实路由；把那条用完即弃的路由和切换器从 main 里删掉。

整套变体就是一手来源，因此它要落到那条用完即弃的分支上，而不是扔进垃圾桶；因为留在 main 分支上的变体组件和切换器会很快腐坏，还会让下一个读者困惑。

## 反模式

- **只在颜色或文案上有差别的变体。** 那只是微调，不是原型。真正的变体在结构上各持己见。
- **变体之间共享太多代码。** 共享一个 `<Header>` 没问题；共享一个 `<Layout>` 就违背了初衷。每套变体都应该可以自由地扔掉版式。
- **把变体接到真实的写操作上。** 只读的原型就够了。如果某套变体需要做写操作，就把它指向一个桩：这里问的是「该长什么样」，不是「后端能不能跑通」。
- **把原型直接提升到生产环境。** 变体代码是在原型的约束下写出来的（没有测试，错误处理只做到最低）。并进真实代码时要按正式标准重写。
