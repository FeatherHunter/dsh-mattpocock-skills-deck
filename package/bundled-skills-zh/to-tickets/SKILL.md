# 拆成工单

把一份计划、规格说明或对话拆成一组**工单**：每张都是曳光弹式的垂直切片，并声明有哪些工单**阻塞**它。

议题跟踪器和分诊标签的词表应该已经提供给你了。如果没有，就让用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

从对话上下文里已有的内容出发。如果用户把某个引用（规格说明的路径、议题编号或 URL）作为参数传了进来，就把它取来，读完它的完整正文与评论。

### 2. 探索代码库（可选）

如果你还没探索过代码库，现在去探索一遍，弄清代码当前的状态。工单的标题与描述要用项目领域词汇表的说法，并遵守你正在触碰的那片区域的 ADR。

顺便找找有没有可以先做预重构的地方，让后面的实现更省力。「先让改动变容易，再做容易的改动。」

### 3. 起草垂直切片

把工作拆成一张张**曳光弹**工单。

<vertical-slice-rules>

- 每个切片都要穿过每一层（数据结构、API、UI、测试），切出一条狭窄但完整的路径：是垂直的，而不是只切某一层的水平切片
- 一个做完的切片本身就能演示或验证
- 每个切片的大小要放得进一个全新的上下文窗口
- 任何预重构都应该最先做完

</vertical-slice-rules>

给每张工单标出它的**阻塞边**：也就是哪些工单必须先做完，它才能开始。没有阻塞项的工单可以立刻开始。

**大范围重构是垂直切片的例外。** **大范围重构**指一次机械性改动（重命名一列、给共享符号改类型），它的**爆炸半径**铺满整个代码库，一次编辑就会同时打断成千上万个调用点，没有任何垂直切片能单独落地还保持全绿。不要硬把它塞进一张曳光弹工单；把它排成**先扩展后收缩**。先扩展：把新形式加在旧形式旁边，让什么都不坏。然后按爆炸半径分批把调用点迁移过去（按包、按目录），每一批各自一张工单、被扩展那张工单阻塞；因为旧形式还在，可以一批接一批地让 CI 保持全绿。最后收缩：等没有调用方留下来时删掉旧形式，这张工单被所有迁移批次阻塞。如果连分批也没法各自保持全绿，就保留这个顺序，但让它们共用一条集成分支，并让所有批次都阻塞一张最终的集成验证工单；全绿只在这张工单上兑现。

### 4. 向用户确认

把提议的拆分作为编号清单呈现出来。每张工单都要列出：

- **标题**：简短、能说明内容的名字
- **被谁阻塞**：还有哪些工单（如果有）必须先做完
- **交付什么**：这张工单让哪一段端到端行为真正可用

然后问用户：

- 粒度是否合适？（太粗 / 太细）
- 阻塞边对不对：每张工单是不是只依赖那些真正拦住它的工单？
- 有没有哪些工单该合并，或者该再拆开？

反复迭代，直到用户认可这份拆分。

### 5. 把工单发布到已配置的跟踪器

把用户认可的工单发布出去。**怎么发布**取决于 `/setup-matt-pocock-skills` 配置的是哪种跟踪器；两种方式下工单本身一样，变的只是阻塞边的形态：

- **本地文件** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下，一张工单写一个文件，按依赖顺序从 `01` 开始编号（先写阻塞方）。每个文件的「被谁阻塞」列出它依赖的编号／标题。用下面的单工单文件模板：一张工单一个文件，绝不要把所有工单写进同一个文件。
- **真实的议题跟踪器（GitHub、Linear、……）** → 按依赖顺序（先写阻塞方）一张工单发布一个议题，这样每张工单的阻塞边都能引用真实的标识符。平台有原生阻塞关系的就用原生的；没有的话，就把每张工单的「被谁阻塞」写成那些阻塞它的议题。如果来源本来就是一张已有的议题，就把每张工单建成它的子议题（操作见跟踪器文档）。除非另有交代，否则打上 `ready-for-agent` 分诊标签；这些工单本来就是按代理能直接领取的标准拆出来的。

处理**前沿**：也就是阻塞项都已经做完的工单。对于一条纯线性的链条，这就是从最上面一路做到最下面。

不要关闭或修改任何父议题。
