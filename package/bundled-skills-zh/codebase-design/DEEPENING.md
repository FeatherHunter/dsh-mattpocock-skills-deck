# 加深

在给定依赖的情况下，如何安全地加深一簇浅模块。假定你已掌握 [SKILL.md](SKILL.md) 里的词汇：**模块**、**接口**、**接缝**、**适配器**。

## 依赖分类

在评估一个待加深的候选对象时，先给它的依赖分类。依赖属于哪一类，决定了加深后的模块如何跨接缝测试。

### 1. 进程内

纯计算、内存内的状态，没有 I/O。永远可以加深：把这些模块合并，直接通过新接口测试。不需要适配器。

### 2. 本地可替代

有本地测试替代实现的依赖（Postgres 用 PGLite，文件系统用内存文件系统）。只要替代实现存在，就可以加深。加深后的模块在测试套件里带着这个替代实现一起跑。接缝是内部的；模块的外部接口处没有端口。

### 3. 远程但自有（端口与适配器）

跨网络边界的自家服务（微服务、内部 API）。在接缝处定义一个**端口**（接口）。深模块持有逻辑；传输方式作为**适配器**注入。测试使用内存适配器，生产环境使用 HTTP／gRPC／队列适配器。

建议的说法：*「在接缝处定义一个端口，为生产实现一个 HTTP 适配器，为测试实现一个内存适配器，这样即使逻辑跨网络部署，它仍然待在一个深模块里。」*

### 4. 真正的外部依赖（模拟）

你无法掌控的第三方服务（Stripe、Twilio 等）。加深后的模块通过一个注入的端口接收这个外部依赖；测试提供一个模拟适配器。

## 接缝纪律

- **一个适配器意味着假想的接缝，两个适配器才意味着真实的接缝。** 除非至少有两个适配器站得住脚（通常是生产 + 测试），否则不要引入端口。只有一个适配器的接缝只是多一层间接。
- **内部接缝与外部接缝。** 深模块除了接口处的外部接缝，还可以有内部接缝（对它自己的实现私有，供它自己的测试使用）。不要仅仅因为测试在用，就把内部接缝通过接口暴露出去。

## 测试策略：替换，不要分层

- 一旦加深后的模块接口处有了测试，浅模块上原有的单元测试就成了浪费；删掉它们。
- 在加深后的模块接口处写新的测试。**接口就是测试面**。
- 测试通过接口断言可观察的结果，而不是断言内部状态。
- 测试应当能在内部重构后继续存活，因为它们描述的是行为，不是实现。如果一个测试不得不随实现改动而改动，那它就是在测接口背后的东西。
