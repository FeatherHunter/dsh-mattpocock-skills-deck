# ADR 格式

ADR 放在 `docs/adr/` 里，按顺序编号：`0001-slug.md`、`0002-slug.md` 等。

按需创建 `docs/adr/` 目录：只在需要第一条 ADR 时才建。

## 模板

```md
# {Short title of the decision}

{1-3 sentences: what's the context, what did we decide, and why.}
```

就这样。一条 ADR 可以只有一个段落。它的价值在于记下*做过*某个决定这件事，以及*为什么*做，而不在于把各个小节填满。

## 可选小节

只有当它们带来真正的价值时才写这些小节。大多数 ADR 用不上。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：在决定被重新审视时有用
- **Considered Options**：只有当被否决的备选方案值得记住时才写
- **Consequences**：只有当存在不明显的下游影响、需要点明时才写

## 编号

扫描 `docs/adr/`，找出已有的最大编号，然后加一。

## 何时提议写 ADR

以下三条必须同时成立：

1. **难以逆转**：日后改变主意的代价不小
2. **没有上下文会让人意外**：未来的读者看到代码会琢磨「他们究竟为什么这么做？」
3. **真正权衡后的结果**：当时确实有别的选择，而你出于具体理由选了其中一个

如果一个决定很容易逆转，就跳过它：反正你到时候直接改回来就是了。如果它并不让人意外，没人会琢磨为什么。如果当时没有真正的备选方案，那除了「我们做了显而易见的事」之外也没什么可记的。

### 哪些内容值得写

- **架构形状。**「我们在用 monorepo。」「写模型是事件溯源的，读模型投影到 Postgres。」
- **上下文之间的集成方式。**「Ordering 和 Billing 通过领域事件通信，而不是同步 HTTP。」
- **会带来锁定的技术选择。** 数据库、消息总线、身份认证提供商、部署目标。不是每个库都要记：只记那些换掉要花一个季度的。
- **边界与范围决策。**「Customer 数据归 Customer 上下文所有；其他上下文只按 ID 引用它。」明说「不做什么」和明说「做什么」一样有价值。
- **有意偏离显而易见的路子。**「我们用手写 SQL 而不是 ORM，因为 X。」凡是一般读者会默认成相反做法的地方，都算这一类。这些记录能拦住下一位工程师去「修好」一个本来就是有意为之的东西。
- **代码里看不见的约束。**「因为合规要求，我们不能用 AWS。」「因为合作方的 API 契约，响应时间必须低于 200ms。」
- **否决理由不明显的备选方案。** 如果你考虑过 GraphQL，又出于不易察觉的理由选了 REST，就把它记下来；否则半年后又会有人提议用 GraphQL。
